Design flow

The staged flow an AI agent follows to design a screen, and the gate that refuses a design which skipped one. Screen-agnostic: the reusable method, with a copy-paste artifact template per stage.

Process spec · rev 2026-09-02 · Trawler · T1 (docs/)

How to run this flow

This page is the flow spec — what an agent reads and follows. The checker (cargo xtask verify-doc) enforces the structural rules; its failure output names each failing check and its fix. Never read the checker source (xtask/src/doc.rs) — the failure output and the rulebook rows are the oracle. The edits are batched: apply all changes in one pass, verify-doc once, then batch residuals and verify again. The norm is edit twice, verify twice — never twelve edit→verify cycles.

Each command below is named again at the stage that needs it; this table is the single place they are all together.

Principles (apply to every stage)

  • Load the substrate before stage 1. The registry index and the rulebook are inputs, read once at the start and never edited mid-run. The versions read are named in the receipt.
  • Representation is load-bearing — optimize for human perception. The reviewer is the bottleneck. Every artifact is picture- or table-first; prose is demoted to a compact reference.
  • State the conclusion, collapse the proof. Every dense cell is a one-line <div class="gist"> with the reasoning behind <details class="why">. Checked: elements·gist and interaction·gist red a row with no gist, a row that collapses nothing, and a gist over 14 words.
  • Cite by name, not coded ids. Drivers by driver name, rules by slug, components by component name.
  • Reuse-or-propose, fit-first. Every element resolves to reuse, extend, or propose. Fit is judged against the entry's @use/@avoid: forcing a component past its @avoid line is a propose, not a reuse. Read @avoid first.
  • Never re-decide what a component owns. A component's states, tones, hover/focus, microcopy and internal layout are its design file's truth; the screen cites them and never restates them.
  • Compose the artifacts, not just the components. A specimen is the component. A run mounts the component; it does not re-type its values and it does not draw a picture of it.
  • Every convention here is machine-checked — the checker is the truth, this page is the reading copy. cargo xtask verify-doc reds on every write (PostToolUse) and at every turn end (Stop). Never read the checker source — read verify-doc's failure output and the rulebook rows instead.
  • Findings live in one table, tagged by stage — never as prose inside a stage.
  • Nothing rides on taste alone. Every structural call cites a Frame driver; every judgment call cites a soft-rule slug.
  • One artifact per stage, cheapest commitment first. Each stage's artifact is the next stage's input. Stages loop back — Elements → Layout and Tune → Layout; both are real.
  • Gaps escalate, they are never invented. Anything the design cannot decide because something upstream is missing goes on the blocked-on list.

The stages

Which rules bind where is the rulebook's own Binds at column — read it there, per stage, and never copy the list into a run or into this spec. Each stage below names only how it consumes the substrate.

1 · Frame

data-item="frame"

Question: who reads this screen and in what context, what job does it do, what are its ranked goals, hard constraints, and experience qualities?

Form: a driver table — driver → why → therefore → on this screen; the row is the reasoning, and it lands on a concrete ✓/✗ pair. Grouped Goals / Constraints / Qualities. Every cell is a clause, not a sentence, and never a paragraph.

Density is machine-checked — six predicates on two budgets:

frame·example-lengthlongest pair ≤ 36

Key distinctions: Not given is a first-class line — a screen is shaped as hard by what it cannot observe as by what it can. The on this screen pair is screen-specific and falsifiable, never a restatement. Anything the rulebook already binds is not a driver (a11y, spacing, wrapping, state handling, calm microcopy, zero accent): the Frame holds only what is case-specific. Every Given capability is answered by the end of the run — used, deliberately unused, or blocked.

2 · Layout

data-item="layout"

Question: how is the frame divided into regions, and what is their priority/hierarchy? (Zones only — no content yet.)

Form: an annotated ASCII region sketch — labelled boxes with a one-line priority/behavior note per zone.

┌───────────────────────────────┐
│ A  <zone name>                 │  ← <priority / behavior note>
├───────────────────────────────┤
│ B  <zone name>                 │  ← <note>
│                               │
├───────────────────────────────┤
│ C  <zone name>                 │  ← <note>
└───────────────────────────────┘

                   unbounded zone's cap and who owns it>

Key distinctions: The overflow line under the sketch is not decoration — it is what overflow-declared checks.

3 · Elements

data-item="elements" — the same element carries data-map

Question: what concrete components fill each region, and for each one — does the registry already have it?

Form: a tiered component catalog — a placement/composition tree tied to Layout zones, plus a one-row-per-distinct-component table whose load-bearing column is the registry verdict: reuse · extend · propose. The registry index is read here, once. Wrap both in data-map and give every component mention data-key="<component-file-slug>". Both halves are checked.

Key distinctions: Tier · verdict · placement share one cell. Colour @use and @avoid in the Fit column. The Shape sketch is reference only. The States column is filled by reference, never by re-listing what the component's design file already owns. An @avoid hit is the stage's most valuable output — it means the design wants something the vocabulary does not have.

4 · Interaction

data-item="interaction"

Question: what does the user actually do with this screen? (The use-cases — not each element's default states.)

Form: a use-case table, each row grounded in a Frame goal. The response is zone → delta lines, never prose — one line per affected zone, UNCHANGED spelled out where not-changing is the decision.

Use caseGoalUser doesScreen respondsKeyboard path
<task><Frame goal><trigger / action>
<zone> → <delta>
<zone> → <delta>   ← <why, only where it is a decision>
<zone> → UNCHANGED  <when that is the point>
<the keys, from the rulebook's keyboard conventions — or "proposed: <keys>">

Key distinctions: Per-element default interaction belongs to the component, not here. The keyboard column exists because keyboard-parity is checked per row.

Closing artifacts — receipt · capabilities · proposals · blocked-on · review

A run ends with five lists, not with the mockup. They are what a reviewer and (from W7) the harness consume.

ListOne row per…Row shape
Receipt — data-item="receipt", a <pre> of YAML, machine-readevery soft slug in the rulebook, in rulebook order. Hard rules are never receipted
rulebook: <blob sha>

Blocked-onevery decision the design could not make because something upstream is missingwhat is missing · which stage hit it · whose call it is · what the run did meanwhile
Review — data-item="review"every reviewer instruction the run acted onwhat the reviewer said · what it moved (name the stages) · the contract it hit: a rule slug, a component's @use/@avoid, a decision record, or taste. Checked: review·recorded

Why forced coverage: a receipt that only lists the rules the design happened to think about proves nothing. inherited is a first-class verdict, not a dodge. Coverage is checked against the rulebook on disk.

Why the hard/soft split: the receipt exists for what a machine cannot judge. Hard rules leave the receipt and become predicates; each one still unimplemented is printed on every verify.

7 · Close the run a step, not a side effect

Edits are batched, not cycled: apply all changes in one pass, verify-doc once, then batch residuals and verify again. The norm is edit twice, verify twice — never twelve edit→verify cycles.

8 · The design review Tier-3 — the reviewer is not the author

Everything up to ⑦ is the designing agent judging its own work. The one thing missing is the rule the dev workflow has always had — never judge your own diff. So the closed run goes through the same door code goes through: the design dimension of the code review.

How
What activates it cargo xtask design-scope <base> <head> — a closed run (data-status="archived") or a component design file in the diff
What it judges soft rules and the new-component warrant, on the artifact — the rubric is .claude/skills/code-review/design-rubric.md
What it catches that ⑦ cannot a receipt that is complete, fluent and false — a satisfied the design does not earn
Where the verdict lives the tip's cr/v3 note, in a design: section
What refuses it 9·design at the merge

9 · Hand over to the build Tier-3 passed — now something gets built

A judged design is still nothing but a file. The hand-over is the step that makes it consumable.

HalfWhat it saysWhat refuses it
The build names its design a Working Unit that adds a registry component or a screen cites design.implements: [{path, blob, built}] in its cr/v3 note9·design at the WU merge
An edit answers for itself every other UI-rendering file the diff touches is cited or design.undesigned: [{path, why}]9·design at the WU merge

Nothing judges the build against its design. The gate answers is there a design, and is it this one — never whether the code honoured it. The pointer is a mechanical check (DEC-25).

What proves the harness — the flow e2e xtask/tests/e2e_design_flow.rs

Every stage above is a rule an agent must follow and a predicate that refuses it, and the whole point is the sequence. A fake designing agent emits one artifact at a time and a fake human answers each; all three tiers then judge the result over a real git tree. Feature-gated (--features design-e2e).

AssertsThe failure it refuses
After every stage the run is red for exactly the stages not yet written the flow stalling, or prompting for work it has not reached
The rulebook moving under an open run re-opens both halves of the close's step ① a receipt that is complete against a rulebook nobody has read since
A rule-violating mockup reds at the stage that wrote it, and the chain from there keeps it out of the tree a breach surfacing only at the end, where it is expensive
