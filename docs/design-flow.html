Design flow

The flow an AI agent follows to design a screen: one mockup doc, five lists beside it, a three-step close and a hand-off. Screen-agnostic — the reusable method, with a copy-paste template per item.

Process spec · rev 2026-09-17 · Trawler · T1 (docs/) · cut to this shape by DEC-53

How to run this flow

This page is the flow spec — what an agent reads and follows. The checker (cargo xtask verify-doc) enforces the structural rules; its failure output names each failing check and its fix. Never read the checker source (xtask/src/doc.rs) — the failure output and the rulebook rows are the oracle. The edits are batched: apply all changes in one pass, verify-doc once, then batch residuals and verify again. The norm is edit twice, verify twice — never twelve edit→verify cycles.

Principles (apply to every item)

  • Load the substrate first. The registry index and the rulebook are inputs, read once at the start and never edited mid-run.
  • Representation is load-bearing — optimize for human perception. The reviewer is the bottleneck. Every artifact is picture- or table-first; prose is demoted to a compact reference.
  • The lists are short. One row, one fact. A list is a record the build and the next epic read, not a place to argue — the argument is the mockup, and the human reads that.
  • Cite by name, not coded ids. Drivers by driver name, rules by slug, components by component name.
  • Reuse-or-propose, fit-first. An element the collection already ships is mounted; one it does not goes on proposals. Fit is judged against the entry's @use/@avoid: forcing a component past its @avoid line is a proposal, not a reuse. Read @avoid first.
  • Never re-decide what a component owns. A component's states, tones, hover/focus, microcopy and internal layout are its design file's truth; the screen cites them and never restates them.
  • Compose the artifacts, not just the components. A specimen is the component. A run mounts the component; it does not re-type its values and it does not draw a picture of it.
  • Every convention here is machine-checked — the checker is the truth, this page is the reading copy. cargo xtask verify-doc reds on every write (PostToolUse) and at every turn end (Stop). Never read the checker source — read verify-doc's failure output and the rulebook rows instead.
  • The human is the judge of everything a predicate cannot reach. Hierarchy, grouping, microcopy, idiom: the reviewer reads the mockup and the review item records the call and the contract it hit. No agent second-reads that judgment (DEC-53).
  • Gaps escalate, they are never invented. Anything the design cannot decide because something upstream is missing goes on the blocked-on list.
  • An input is never designed away in silence. Every capability the screen was handed ends the run answered on the Given list — used, deliberately unused, or blocked.

Which rules bind where is the rulebook's own Binds at column — read it there, and never copy the list into a run or into this spec. A run is one doc carrying data-artifact="design-run" and the six items below; anything else it declares is refused by name.

Given — data-item="capabilities"

Question: what is this screen handed, and what may it not assume exists?

Form: one row per input, each ending the run used · deliberately unused · blocked, with where or why. A Not given line names what the screen may not assume.

<p>Not given (may not be assumed to exist): <absent capability> · <absent capability></p>
<table data-item="capabilities">
| Given            | State                | Where / why                        |
| <prop/callback>  | used                 | <the control that consumes it>     |
| <prop/callback>  | deliberately unused  | <why the screen ignores it>        |
| <prop/callback>  | blocked              | <what is missing — also a blocked-on row> |

Key distinctions: the list exists so an input cannot be designed away in silence — a past run marked an action deliberately unused for a reason the shipped code disproved, and this is where it was caught. Completeness is mechanical; the truth of a deliberately unused row is the human's to read.

Draft mockup — data-item="mockup"

the tagged element contains the zone hosts, the overflow line and the state toggle

Question: assembled, does it hold together as one screen?

Form: a real build that mounts the real components — load the CDN plus doc-assets/components/specimens.bundle.js (../../ from docs/work/, the folder a run lives in) and render each composed element from window.Trawler. Stateful: a toggle across every state the screen can reach.

LayerSourceRule
composedthe component itself, mounted from window.Trawlereverything the collection already ships. The bundle is the only route to a component's rendering, so a run that does not load it can mount nothing. Checked: assets·specimen

The three declarations the mockup carries, in plain HTML. data-zone="<name>" on each zone host; one overflow paragraph under the mockup, opening with the word and naming every zone; data-wire="<what it is>" on each payload element, data-wire="collection" plus data-order on each captured-collection host, and data-wire="none" once when the screen renders no payload. They are plain HTML on purpose: the checker reads them whatever the mounts render inside.

Key distinctions: Mounting is what closes the fork for good — a hand-drawn component in correct utilities is still a fork no class check can see. Zero colour literals in the doc's own CSS — the tokens live in ui/tailwind.config.js and the mockup only ever writes their utility names. Build what the screen decides, stub what a component owns.

Keyboard — data-item="keyboard"

Question: can every pointer interaction be driven from the keyboard?

Form: one row per pointer interaction, naming its key path from the rulebook's keyboard conventions. This item exists for the one thing a static mockup cannot show.

<table data-item="keyboard">
| Pointer does        | Where             | Key path                                   |
| <click / hover / drag> | <zone>         | <the keys, from the conventions — or "proposed: <keys>"> |

Key distinctions: a screen the pointer cannot drive says so in a row of its own — an empty Keyboard item is a screen nobody asked about, and it reds. A key path a convention does not have is a proposal, not an invention.

The three lists — proposals · blocked-on · review

What the run hands on: two lists later epics read, and the record of what the human said.

ListOne row per…Row shape
Proposals — data-item="proposals" entry the design needed and the vocabulary lacked kind · what · why nothing existing fits · owner
Blocked-on — data-item="blocked-on" decision the design could not make because something upstream is missing what is missing · whose call it is · what the run did meanwhile
Review — data-item="review" reviewer instruction the run acted on what the reviewer said · what it moved (name the items, or nothing when the design argued and held) · the contract it hit: a rule slug, a component's @use/@avoid, a decision record, or taste. Checked: review·recorded
The review item is the record of the gate. No agent re-reads the design after the human has; what survives of that judgment is this list, and it is where a run declares DEC-34's truncation escape — the constraint, the visible cut, and the route to the full value.

Close the run three steps

Edits are batched, not cycled: apply all changes in one pass, verify-doc once, then batch residuals and verify again. The norm is edit twice, verify twice — never twelve edit→verify cycles.

Hand over to the build the design step

A closed run is still nothing but a file. The hand-off is the step that makes it consumable, and it is the whole of the design step: design-scope, the accounting, and the note. Nothing here judges the design — the human did that, at the mockup (DEC-53).

Nothing judges the build against its design. The gate answers is there a design, and is it this one — never whether the code honoured it. The pointer is a mechanical check (DEC-25).

What proves the harness — the flow e2e xtask/tests/e2e_design_flow.rs

Every item above is a rule an agent must follow and a predicate that refuses it, and the whole point is the sequence. A fake designing agent emits one item at a time and a fake human answers each; the checker and the merge gate then judge the result over a real git tree. Feature-gated (--features design-e2e).
