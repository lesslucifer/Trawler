Context

The capture core is complete (HTTP/1.1 + HTTPS MITM, capped body capture, SSE stream, filtered read-only API, in-memory ring) and nothing product-shaped is planned beyond it. The 2025–26 market read: table stakes everywhere are breakpoints, map local/remote, rewrite, HAR, replay/composer, WebSocket display, session persistence. Four gaps are real: no tool has a stable public control API (mitmproxy's is deliberately internal; only MS Dev Proxy has one, M365-scoped) · LLM traffic debugging is unserved in general proxies · OpenAPI-from-traffic demand is proven (mitmproxy2swagger ≈9.5k stars) but nobody does it first-class · WebSocket is weak everywhere. Trawler's API-first core sits exactly on the first gap.

Choices

ChoiceWhy — do not "simplify" it away
Two pillars, not one directionThe GUI is the adoption gate (nobody evaluates a proxy via curl; Charles proves a complete feature set doesn't survive bad ergonomics) and functionality is the retention floor (mitmproxy is the benchmark). The API-first core fuses them: every GUI capability is a call on the public API, so the GUI never forks the feature surface.
UI is four epics (E-UISHELL → E-UIFOUND → E-UIINSPECT → E-UISETUP), not oneOwner decision. One "UI epic" is unboundable; four bounded epics each carry their own requirement and test plan. E-UIFOUND exists as its own epic so every later UI surface slots into a designed layout — accreting features without one is the Charles failure mode.
Minimal shell (E-UISHELL) ships before the foundation epic (E-UIFOUND)Owner-confirmed order: visible traffic first. The shell's chrome is deliberately minimal and is migrated onto the foundation's layout as its first tenant — a small, accepted rework, priced in rather than accidental.
Native desktop app is the primary UI, not a web page reversal · DEC-12E-UIFOUND reversed the web-primary framing this roadmap opened with. The primary surface is a native Tauri desktop app (Vite + TS + React + Tailwind, mirroring Strata), an out-of-process client of the control API; the embedded web shell is kept as a second client, to be retired later at native-UI parity. The API-first invariant is unchanged — the app reaches no core internals, only 127.0.0.1:7421. Recorded as DEC-12; E-UIINSPECT / E-UISETUP build on this stack.
REST API + rules (E-RULE) instead of embedded scriptingmitmproxy's addon power without shipping a script runtime: anything that can drive HTTP can automate Trawler. Revisit (in-process WASM/JS hook) only if real rule usage proves insufficient.
HTTP/3/QUIC MITM and DNS/TCP/UDP proxying deferredLarge protocol investment with poor client CA support for QUIC; not what the two pillars need first. Revisit after the Wave 1–3 parity set lands.
Differentiators (E-LLM, E-MCP, E-OAS) last, not firstThey lead the market but sit on capture/replay/persistence machinery from earlier waves — sequencing them first would build that machinery twice. E-LLM additionally requires deciding to tee-capture text/event-stream bodies, today a deliberate passthrough invariant.

Streaming the capture in both directions, and the peak memory a one-shot body costsDeferred at E-EXPORT's plan review for the export, and the epic's own close review found the import half owes the same. Export: GET /flows/export serializes the whole filtered capture into one in-memory response; W2's review measured roughly 4× the 256 MB cap on binary bodies, because the cloned flows, the base64-expanded document and the serialized JSON are all live at once — so the bound is that multiple, not the cap. Import: POST /flows/import holds the raw body, the deserialized HAR tree and the decoded flows at once, and its admission ceiling is now twice the cap (the epic close raised it, because the old one refused the store its own export), so its peak scales with that. A streaming parse is the one fix for both. Revisit when a real capture proves either too heavy.
The ring is weighted by body bytes, so a header-heavy capture has no export size any multiple of the cap can boundFound by E-EXPORT's close review. A capture of body-less exchanges — polling, heartbeats, chatty auth traffic — accumulates rows the ring's byte cap does not bound, so its own HAR export can outgrow any constant multiple of that cap. The mechanism, and what the import door therefore does and does not guarantee, are stated where they bind: import_body_limit in src/api/mod.rs. What is deferred is the fix, not the finding — two candidates, neither this epic's to choose: weight the ring by whole rows rather than body bytes, or stream the parse. A review round is not cheap relative to the draft: round 3 spent 38 turns and 68k output to change four things against round 2's 81 turns and 77k to write the whole amendment, because three of the four calls needed a component contract re-read before they could be answered. W4's round is unmeasured and is recorded as unmeasured — no clock and no token count was taken at the time, and this project writes no estimates, so a reconstructed second data point would poison the first bill the flow has ever had. DEC-48's discipline, applied to the flow. What it still does not say: nothing here is a per-item cost — the six items were not written serially and cannot be billed apart.
