Work Planning & Result Reports

What the planning phase of an epic or WU must output, what the result report after the work must contain — minimum-content checklists verified by a script the agent harness triggers at authoring time. Never fixed templates, never git hooks.

v2 · 2026-07-11 · Trawler · T1 process doc

The four outputs

Every epic produces two governed docs and every WU produces two more — all T3, all named by the normal rule in the documentation system (docs/work/YYYY-MM-DD-<slug>-plan.html / …-result.html), all distilled then archived like any T3. The checklist constrains substance (items that must exist), never form: a plan may be prose, tables, diagrams or widgets, shaped to fit its task. A skeleton to copy-paste is exactly what this standard refuses to be (DEC-4).

Collapsed epics. A one-WU epic may combine the two plans into a single doc and the two results into a single doc — each declares both roles (data-artifact="epic-plan wu-plan" for the plans, data-artifact="epic-result wu-result" for the results) and must satisfy the union of both checklists; an item whose tag both checklists share is satisfied once.

The verification loop

flowchart LR
  A["author a governed doc
data-status='draft' — silent,
iterate freely"] --> RDY["flip it ready"]
  RDY --> H{"PostToolUse hook
verify-doc on every write
of a ready doc"}
  H -- "red — problems fed back" --> F["fix the doc now"] --> H
  H -- green --> W["work proceeds on a green doc"]
  W --> S{"Stop hook at turn end
any ready governed doc red?"}
  S -- "red — turn refused" --> F
  S -- green --> D["turn ends"]
Drafts iterate in silence; declaring the doc ready is the checkpoint. From there every edit re-verifies and red never survives a turn.

The markup contract

Free form and a mechanical check coexist through four attributes. Tagging is strict by design: the tag is the contract. Content sitting under a wrong or missing tag is red on purpose — tag each checklist item as you write it, with the exact tag from the tables below, on whatever element holds it (any element, any order, any form around it).

AttributeWhereMeaning
data-artifactonce per doc (the <html> or <body> tag, or any one element)declares what the doc is: epic-plan · wu-plan · wu-result · epic-result · design-run, space-separated when combined. A doc with no data-artifact is not governed and is ignored — pre-standard docs are skipped, never retrofitted
data-statusnext to data-artifactdraft while authoring — all checks silent; ready or absent = ready, verified on every write. The flip to ready is the checkpoint. Flipping back to draft to silence a red doc is visible to the reviews that read these docs
data-itemthe element holding a checklist itemexactly one of the type's tags below, non-empty content inside
data-wuepic plan only, inside the wu-summaries itemone block per WU, value = the WU id (e.g. E-CAP.W2); each block carries the four data-item sub-tags

The mechanical check — cargo xtask verify-doc

cargo xtask verify-doc <path> [<path>…]    # exit 0 green/draft/ungoverned · exit 1 red

The script reads the doc's data-artifact, selects its checklist(s), and checks exactly this — nothing cleverer, no content heuristics (DEC-4):

  • every item's tagged section is present with non-empty content (whitespace-only counts as empty);
  • the type's structure holds: an epic plan carries ≥ 1 data-wu block, each with its four sub-tags, all non-empty;
  • no unknown tags for the type — the typo guard: an unknown data-item is reported by name next to the missing item it likely misspells ("unknown tag expcted / missing item expected"), so "content there, tag wrong" is a named, fixable problem, never a mystery;
  • an unknown data-artifact value is red.

Anything red prints one problem block per item — check id, expected vs found, fix → — exit 1, same house style as the DoD gate. Depth of content is review territory: whether an "observable expected result" is truly observable is judged where judgment already lives — the review that reads the plan, the user's comment round — on top of, never instead of, the script.

Who triggers it — the harness, at authoring time

Git hooks are the wrong point: by commit or merge the work already stands on the low-quality doc. An agent that must remember a check will eventually forget it. So the trigger is the agent harness itself, via hooks versioned in .claude/settings.json — the harness executes them, not the agent, and in an AI-first repo every author is a harness session, so authoring-time coverage is total.

HookFiresDoes
PostToolUse (.claude/hooks/verify-doc-post.sh)every Write/Edit of an .html fileruns verify-doc on the written file; red ⇒ the problem blocks are injected into the session as feedback — the write itself is never blocked, the doc gets fixed now; drafts and ungoverned docs stay silent
Stop (.claude/hooks/verify-doc-stop.sh)turn endruns verify-doc over every doc under docs/ in the working tree (tracked or untracked; gitignored archives excluded); any ready governed doc red ⇒ the turn is refused with the problems as the reason — the backstop that also catches docs edited around the file tools (shell, scripts)

Manual runs work anytime for feedback; no workflow step depends on anyone remembering one.

Relation to the DoD gates

Quality is checked at authoring time (the harness hooks above); existence and exact content are checked at the gate (DEC-10): every WU/epic tip's mr/v1 note must name the level's result report — path + sha256, recorded by mr confirm from the bytes the human read, covered by the key-backed signature — and gate check 8 refuses a tip whose note names none; a WU report is re-hashed against the tracked file at the tip, an epic report (archived per DEC-3) survives as the signed hash. Substance stays judgment: the reviews read the plan and result docs as inputs. A docs-only WU or epic is exempt from test evidence, never from its plan and result docs — those exist precisely when code doesn't, and the gate now proves it.
