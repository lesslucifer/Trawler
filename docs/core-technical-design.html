Core Technical Design

A technical discussion of Trawler's core functions: how traffic is captured, modelled, and served — how we sniff it, how the network and CA are configured, the stack we build on, and the hard problems we can't wish away.

Draft v2 · 2026-07-03 · Trawler

Where we are today

Today src/main.rs is a correct but minimal spine: a hudsucker MITM proxy on 127.0.0.1:3000, a persisted self-signed CA, and a LogHandler that logs request/response metadata via tracing. Bodies are never touched, nothing is stored, and there is no interface. This doc is the technical discussion of the core functions only — it is not a project plan, and it deliberately excludes replay, breakpoints, and WebSocket-frame features.

Decisions locked for v1

Three forks are settled; all are reversible behind the store and interface boundaries.

API-first core

trawler-core is UI-agnostic. The product surface is a local control API; any UI (TUI, web, or curl) is a client. No UI committed to yet.

In-memory ring buffer

A bounded live buffer, no disk. Nothing survives restart. SQLite / HAR slot in later behind the store boundary.

Bounded drain-then-forward capture

Drain each body frame by frame up to a flat 10 MB per-request cap; the moment the cap is crossed the rest streams through untouched, so reads are memory-bounded. One special case: streaming bodies.

Chosen defaults (easy to flip): axum 0.8 · SSE + REST over WebSocket · Arc<Mutex<Store>> + broadcast over an actor · 10 MB per-request body cap.

Architecture spine

The whole system is one domain object — the Flow — plus a stream of events about it. The proxy handler is a dumb producer; a central store owns the canonical flows; every interface is a subscriber. Live-tailing and filtering fall out of this rather than being bolted on.

flowchart LR
    client(["client apps"]) <--> hud["hudsucker MITM"]
    hud <--> rec["Recorder HttpHandler"]
    rec -- record --> store[("Store: ring buffer")]
    rec -- FlowEvent --> bus{{"broadcast bus"}}
    bus -- live --> sse["SSE /stream"]
    store -- queries --> rest["axum REST"]
    sse --> ui["UI / curl"]
    rest --> ui
Capture path knows nothing about interfaces. Writes go to the store; live events ride a broadcast channel.

Concurrency: no actor ceremony. The Recorder holds an Arc<Store> (a lock around the ring buffer) plus a broadcast::Sender<FlowEvent>; axum wraps a broadcast::Receiver in a BroadcastStream for the SSE endpoint. The body-cap counter is a plain std::sync::atomic::AtomicUsize (not a tokio primitive) to stay off the async hot path.

Core types

The Flow is the top-level unit of capture — one per HTTP exchange. Everything else is a field of it. Concrete shapes and the reason each exists:

Flow

Flow {
    id: FlowId(Uuid::new_v4()),
    started_at: SystemTime::now(),
    request:  RequestRec  { method: GET, uri: "https://api.example.com/v1/items", .. },
    response: Some(ResponseRec { status: 200, .. }),
    duration_ms: Some(84),
}

Why: the unit the ring buffer stores, the SSE stream fans out, and the REST API returns. response is an Option because a flow exists the moment the request is seen, before any reply.

RequestRec / ResponseRec

RequestRec {
    method:  POST,
    uri:     "https://api.example.com/v1/upload",
    version: HTTP_2,           // the version actually spoken on the client leg
    headers: { content-type: application/json, authorization: Bearer … },
    body:    BodyRec::Captured { bytes, size: 14 },
}
ResponseRec {
    status:  201,
    version: HTTP_11,          // the version actually spoken on the upstream leg
    headers: { content-type: application/json },
    body:    BodyRec::NotCaptured { reason: TooLarge { actual: 15_728_640 } },
}

Why: splitting request from response lets the store emit a partial Flow (request-only) the instant handle_request fires — before the upstream round-trip completes — enabling low-latency live updates.

BodyRec

enum BodyRec {
    Captured    { bytes: Bytes, size: usize },
    Streaming   { content_type: String },   // text/event-stream etc. — forwarded, never buffered
    NotCaptured { reason: NotCapturedReason },
    Empty,
}

Why: a plain Option<Bytes> can't distinguish "empty body", "skipped because streaming", and "too large" — distinctions the UI must render differently and a consumer must handle without guessing.

FlowEvent

enum FlowEvent {          // broadcast; axum SSE maps each variant to an SSE event
    RequestCaptured  { flow_id: FlowId, req: RequestRec },
    ResponseCaptured { flow_id: FlowId, res: ResponseRec, duration_ms: u64 },
    FlowEvicted      { flow_id: FlowId },
}

Why: the stream must push incremental lifecycle transitions (request before response, ring-buffer eviction). A single "flow updated" event can't express these without overloading its payload. Events deliberately carry the full record — the clone this costs on insert is an accepted trade, see DEC-1.

FlowView

// The JSON returned by GET /flows/:id — a flattened, UI-ready projection
{
  "id": "3fa85f64-5717-4562-b3fc-2c963f66afa6",
  "started_at": "2026-07-03T12:34:56.789Z",
  "duration_ms": 84,
  "method": "POST", "uri": "https://api.example.com/v1/items", "status": 201,
  "request_http_version": "HTTP/2.0", "response_http_version": "HTTP/1.1",
  "request_body":  { "state": "captured",  "size": 14, "data_base64": "eyJuYW1lIjoiZm9vIn0=" },
  "response_body": { "state": "streaming", "content_type": "text/event-stream" }
}

Why: a read-only serialized projection for REST/SSE consumers. Decoupling it from the internal Flow lets the storage layer evolve without breaking the API contract.

Body capture

In handle_request / handle_response the body is drained frame by frame (http_body_util::BodyStream), accumulating at most the cap. A body that ends within the cap is recorded and reconstructed with Body::from(bytes) before forwarding (the read is destructive). The moment the cap is crossed, the decision is made immediately: the buffered prefix frames are replayed and the remainder chains through as a stream — so a capture decision never breaks the connection, and an oversized or hostile body can never force more than cap-plus-one-frame into memory.

v1 rule — kept deliberately simple: one config value, a 10 MB cap applied per request. A body that exceeds 10 MB is forwarded in full and recorded as BodyRec::NotCaptured { TooLarge }; actual is the declared content-length when one exists, otherwise the bytes counted when capture stopped. The cap bounds both what is stored and what is ever buffered. Every body is judged on its own size — there is no shared or global budget across requests, so parallel traffic never interferes.

The one special case — streaming responses

A flat per-request cap handles ordinary bodies cleanly. The single case it doesn't cover is a body that never ends: a Server-Sent Events stream (Content-Type: text/event-stream) or a live log tail trickles bytes and may never reach the 10 MB cap or send an EOF. If Trawler waits to finish buffering before forwarding, that exchange stalls and the client sees nothing.

Example. A page subscribes to GET /notifications (SSE); the server pushes one small event every few seconds and never closes the stream. Buffering waits forever, so the page never receives its events — a break caused by the proxy, not the server.

sequenceDiagram
    participant C as Client
    participant P as Trawler
    participant O as Origin
    C->>P: GET /notifications
    P->>O: GET /notifications
    O-->>P: event 1
    O-->>P: event 2
    Note over P: still buffering, waiting for the body to end
    O-->>P: event 3, stream stays open
    Note over C: client received nothing, looks frozen
Buffering a body that never ends hangs the whole exchange. Fix: detect streaming Content-Types and forward as-is, recording a BodyRec::Streaming marker instead of bytes.

The fix is small and doesn't complicate the cap: detect streaming Content-Types and forward those bodies without buffering, recording a BodyRec::Streaming marker instead of bytes. Everything else uses the flat 10 MB-per-request rule.

Control API surface (inspect-only)

SSE + REST, scriptable from day one. v1 is purely for inspecting traffic — no mutation endpoints.

EndpointPurpose
GET /flows?host=&method=&status=&content_type=&q=Filtered listing — where filter/search lands
GET /flows/:idFull flow detail (a FlowView)

GET /ca.crtDownload the root CA — the delivery path for iOS / Android trust

Decoding stays view-side

Capture stores raw bytes + content-encoding faithfully. The ?decode=1 path runs the chain lazily at view time: content-encoding (gzip/deflate/br) → charset → format detect (JSON/XML/form) → pretty-print. Same bytes, many renderings — the capture path stays fast and honest. Decoded output is capped (64 MB) as a zip-bomb guard: stored bodies are bounded by body_cap, but their decompressed form is not — past the cap the endpoint falls back to the raw bytes.

How interception works (sniffing the data)

Trawler is an explicit proxy: clients are configured to send their traffic to it. Two cases follow — plain HTTP, an unencrypted pass-through we can read directly, and HTTPS, which is decrypted via two TLS legs with a plaintext gap in the middle. A diagram for each is below.

Explicit proxy vs. transparent (NAT) interception. An explicit proxy is one the client knows about and is configured to use: the app sends its requests — or a CONNECT for HTTPS — straight to 127.0.0.1:3000. That is Trawler v1.

Transparent (NAT) interception is the opposite: the client is not configured and has no idea a proxy exists. A router or firewall rule (macOS pf, Linux iptables/nftables) silently rewrites the packet's destination so it lands on the proxy instead of the real server — "NAT" because it rewrites network addresses in transit. Since there is no CONNECT line announcing the target, the proxy must infer the destination host from the TLS SNI field in the ClientHello. It catches apps that ignore proxy settings, but it needs root and OS-specific network plumbing — so it is out of scope for v1.

Case 1 — Plain HTTP

No TLS, nothing to decrypt. The client sends the proxy a full absolute-form request line — GET http://api.example.com/items — Trawler records it, forwards it to the origin, records the response, and passes it back. Both handle_request and handle_response see everything in the clear.

sequenceDiagram
    participant C as Client
    participant P as Trawler
    participant O as Origin
    C->>P: GET http://api.example.com/items
    Note over P: handle_request, capture in the clear
    P->>O: GET /items
    O->>P: 200 OK plus body
    Note over P: handle_response, capture and broadcast
    P->>C: 200 OK plus body
Plain HTTP: no encryption, a straight pass-through. Trawler reads request and response directly — no CA and no TLS involved.

Case 2 — HTTPS via CONNECT

The encrypted case is the interesting one: two TLS legs — one to the client, one to the origin — with a plaintext HTTP gap in the middle, and that gap is where the handler observes decoded requests and responses. Step by step:

  1. Client is pointed at 127.0.0.1:3000 (system proxy settings or HTTP_PROXY/HTTPS_PROXY).
  2. Client sends CONNECT host:443; handle_request fires on the CONNECT — an inspect / short-circuit point.
  3. should_intercept decides; if false, a raw copy_bidirectional TCP tunnel is opened with no visibility.
  4. If intercepting, the proxy replies 200 OK and peeks 4 bytes — 0x16 0x03 marks a TLS ClientHello (literal GET marks plain HTTP re-sent through the tunnel).
  5. gen_server_config(host:port) returns a cached leaf ServerConfig or builds one signed by the CA; TlsAcceptor completes the client-leg TLS handshake (ALPN offers h2, http/1.1; the client picks).
  6. The first decrypted request arrives; handle_request fires with a fully-parsed Request before the upstream send.
  7. The proxy drains the body, applies the cap, rebuilds the body, and lazily opens the upstream leg (TCP + TLS) — ALPN offers h2, http/1.1 and the origin picks; normalize_request marks the forwarded request HTTP_11, but that field never forces the wire — the pooled connection speaks whatever ALPN negotiated, and each leg's true version lands in the flow.
  8. Origin responds; the proxy drains and captures the response body the same way.
  9. handle_response fires; the flow lands in the ring buffer and a FlowEvent is broadcast to SSE subscribers.
  10. The response is re-encrypted over the client leg and delivered.
sequenceDiagram
    participant C as Client
    participant P as Trawler
    participant O as Origin
    C->>P: CONNECT host:443
    Note over P: handle_request on CONNECT
    P->>C: 200 OK
    Note over P: peek 4 bytes, 0x16 0x03 means TLS
    Note over P: gen_server_config, cache hit or build leaf
    C->>P: TLS ClientHello
    P->>C: ServerHello plus leaf cert
    Note over C,P: client-leg TLS up, ALPN h2 or http/1.1, client picks
    C->>P: GET /v1/items decrypted
    Note over P: handle_request, drain and capture body
    P->>O: TLS handshake, lazy upstream leg
    O->>P: ServerHello
    Note over P,O: upstream TLS up, ALPN h2 or http/1.1, origin picks
    P->>O: GET /v1/items
    O->>P: 200 OK plus body decrypted
    Note over P: handle_response, capture and broadcast FlowEvent
    P->>C: 200 OK plus body re-encrypted
CONNECT + dual-TLS interception. The upstream leg opens lazily on the first tunneled request; each leg negotiates its HTTP version independently via ALPN.

Certificate & trust model

Trawler holds a single self-signed CA (ECDSA P-256), generated on first launch and persisted to ca/trawler-ca.pem / .key. A partial state — one file of the pair missing — aborts startup instead of regenerating: silently overwriting the survivor would invalidate every client that already trusts the old certificate. For each HTTPS connection, the host:port from the CONNECT line keys a moka cache (1,000 entries, ~182-day TTL, W-TinyLFU eviction). On a miss, rcgen builds a leaf whose CN + DNS SAN is the hostname, signs it with the CA, and caches the Arc<ServerConfig>. Warm hits are sub-microsecond.

flowchart TD
    A["CONNECT host:443 arrives"] --> B{"Cache hit for host:port?"}
    B -- yes --> E["Return cached ServerConfig"]
    B -- no --> C["Build leaf cert for hostname"]
    C --> D["Sign with CA key; subject key = CA key"]
    D --> F["Build ServerConfig; ALPN h2, http/1.1"]
    F --> G["Store in moka cache 1000 / ~182d TTL"]
    G --> E
    E --> H["TlsAcceptor.accept client-leg TLS"]
Per-host leaf lifecycle. A cold miss is a single ECDSA sign (~15–50 µs), not a keygen — see below.

Two hudsucker realities to know (both verified):

  • Every leaf reuses the CA's key as its subject key — no per-host key is generated (signed_by(&ca_key, &ca_cert, &ca_key)). All hosts share one private key. It's a deliberate shortcut: a cold miss is one sign op, not a keygen. Fine for a local debug tool.
  • IP-address CONNECT targets are a bug: hudsucker always emits a DNS-type SAN, even for an IP literal. RFC 5280 requires an IP-type SAN for IPs, so modern TLS stacks reject these — connecting to https://a.b.c.d through the proxy fails. Worth documenting / patching.

Network configuration & CA trust

Two independent problems: routing traffic to 127.0.0.1:3000, and trusting the CA so leaf certs are accepted. Configure the proxy without trusting the CA → TLS errors; trust the CA without routing → no captured traffic. v1 supports explicit forward-proxy mode only (transparent/NAT interception is out of scope). ECH is a non-issue here: browsers suppress ECH under an explicit proxy, so the CONNECT line always carries the plaintext host.

Technical challenges & limits

An honest catalog — what breaks interception, and Trawler's stance. Severity for a debug-your-own-traffic tool: blocker major minor.

ChallengeWhat it means for TrawlerSeverity
Certificate pinning Apps that pin a cert/key (most mobile banking, payments, high-value apps) reject our leaf regardless of CA trust — the connection fails app-side and no flow is recorded. Only bypass is owning the server key, or app instrumentation (Frida), both out of scope. Browser traffic is unaffected (Chrome ignores static pins for locally-installed roots). blocker
Streaming bodies With a flat 10 MB-per-request cap there is no shared-budget or race issue; the only special case is a body that never ends (SSE, live log). Detect streaming Content-Types and forward without buffering — see Body capture. major
HTTP/2 end-to-end Solved by E-H2: hudsucker's http2 feature flips the MITM ALPN offer to h2, http/1.1 and the upstream connector offers the same (enable_all_versions) — each leg negotiates independently and the flow records the true version per leg (UC-1 · UC-2). h2 arrives via ALPN on TLS only (no h2c); HPACK, priorities and push stay invisible — the capture surface is the decoded exchange, not h2 framing. resolved
HTTP/3 / QUIC UDP-based; a TCP CONNECT proxy is transparent to it → QUIC bypasses Trawler entirely (a growing slice of browser traffic). Mitigation: optional, opt-in blocking of outbound UDP/443 to force TCP fallback, with guaranteed cleanup on shutdown; breaks non-browser QUIC that lacks fallback. major
Mutual TLS (client certs) If the origin requests a client cert, Trawler can't complete the upstream handshake (no client key) — the flow fails. Needs a per-host bypass/tunnel list. Full interception is possible only when the client credentials are supplied to the proxy. major
Non-proxy-aware apps Raw-socket / custom-stack apps ignore proxy settings (Go to localhost, Java w/o JVM flags, Flutter desktop, bare Node http in Electron) → no flow recorded. Explicit-proxy covers browsers, CLI, CFNetwork/WinINet. Transparent mode is future work (root + per-OS). major
Encrypted Client Hello (ECH) Not a threat to explicit-proxy host discovery (browsers suppress ECH under a proxy; CONNECT carries the plaintext host). The only exposure is the upstream leg to ECH-enforcing origins, which relies on retry-without-ECH fallback today. Becomes major only if transparent mode is added. minor
Performance under load Cold leaf = one ECDSA P-256 sign (~15–50 µs; CA key reused, no keygen); warm moka hits sub-µs; the double handshake adds ~5–15 ms/conn, dominated by networking. Not a bottleneck for localhost debugging. One requirement: ring-buffer eviction must weight by body bytes, not flow count. minor
HSTS / preload No impact once the CA is trusted — HSTS only forces HTTPS, which Trawler terminates normally. minor
wss transport wss flows through the tunnel; the Upgrade request is captured as a normal HTTP record, but frames are currently forwarded uninspected (NoopHandler). Frame-level capture is available later via hudsucker's WebSocketHandler — out of v1 scope. minor

Authorization boundary. Interception requires a locally-trusted root CA and decrypts everything routed through it. Trawler is for inspecting your own traffic on devices and services you own or are authorized to test — this constraint is a first-class part of the design, not a disclaimer.
