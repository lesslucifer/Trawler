Core Architecture

How the codebase is actually built: the crate shape, the modules and the types they own, the request/response lifecycle through the code, the concurrency model, and where each decision from the Core Technical Design landed in source.

v2 · 2026-07-12 · Trawler

What this is

This is the implementation companion to the Core Technical Design. The design doc argues the why; this doc maps the how onto the source tree that now exists. The v1 core is complete and verified end to end: plain-HTTP and HTTPS-via-CONNECT capture, a byte-weighted in-memory store, a broadcast bus, and an inspect-only REST + SSE control API. Replay, breakpoints, and WebSocket-frame capture remain out of scope by design.

Verified working (smoke test): CA generated + served plain HTTP GET/POST captured HTTPS MITM decrypt + capture /flows filtering /flows/{id} detail raw + ?decode=1 bodies live SSE lifecycle.

Crate shape — core is a library

The product is an API-first core, so the core is a library crate (trawler, src/lib.rs) and the executable is a thin launcher (src/main.rs) that only installs logging and calls trawler::run(Config). Any interface — TUI, web UI, curl — is a client of the running control API, never a compile-time dependency of the core.

Runtime wiring

One tokio runtime hosts both servers. The proxy (hudsucker) listens on 127.0.0.1:7420; the control API (axum) listens on 127.0.0.1:7421. The Recorder is the only bridge between them, and it only ever writes to the store — it holds no reference to any interface.

flowchart LR
    client(["client apps"]) <--> hud["hudsucker MITM :7420"]
    ca["CaMaterial → RcgenAuthority"] --> hud
    hud <--> rec["Recorder (HttpHandler)"]
    rec -- "insert / set_response" --> store[("Store: byte-weighted ring")]
    store -- "FlowEvent" --> bus{{"broadcast::Sender"}}
    bus -- "BroadcastStream" --> sse["axum SSE /stream :7421"]
    store -- "get / list" --> rest["axum REST :7421"]
    sse --> ui["UI / curl"]
    rest --> ui
The capture path knows nothing about interfaces. The Store owns the broadcast sender and emits a FlowEvent on every insert/set_response/eviction; the API is purely a subscriber and reader.

Concurrency, no actor ceremony. Recorder holds an Arc<Store>. Inside, the ring buffer is a std::sync::Mutex<Ring> — critical sections are pure, synchronous data ops (push, lookup, evict), so a std mutex keeps locking off the async machinery. The broadcast::Sender<FlowEvent> send is non-blocking and is called while the lock is held only for the eviction list; axum's SSE endpoint wraps a broadcast::Receiver in a tokio_stream::wrappers::BroadcastStream. There is no global body-cap counter — the v1 cap is judged per body, so parallel traffic never contends on a shared budget.

Request / response lifecycle in code

hudsucker calls handle_request then handle_response on the same cloned handler instance for each exchange. That is exactly what lets the Recorder correlate a response with its request: it stashes the FlowId and a start Instant in per-exchange scratch fields between the two calls — no external map, no request id plumbing.

sequenceDiagram
    participant C as Client
    participant R as Recorder (per-exchange clone)
    participant Cap as capture()
    participant S as Store
    participant B as broadcast bus
    participant A as axum API
    C->>R: handle_request(req)
    Note over R: return early if method == CONNECT
    R->>Cap: capture(headers, body, cap)
    Cap-->>R: (BodyRec, rebuilt Body)
    R->>R: stash flow_id + start Instant
    R->>S: insert(Flow::new(request))
    S->>B: FlowEvent::RequestCaptured
    R->>C: forward request upstream
    C->>R: handle_response(res)
    R->>Cap: capture(headers, body, cap)
    Cap-->>R: (BodyRec, rebuilt Body)
    R->>S: set_response(flow_id, response, duration_ms)
    S->>B: FlowEvent::ResponseCaptured
    B-->>A: SSE subscribers receive events live
    A-->>C: GET /flows/{id} → FlowView
The read is destructive, so capture() always hands back a freshly rebuilt Body to forward — even when the body is too large to keep. A capture decision can never break the connection.

Why the CONNECT guard matters. In hudsucker 0.24, handle_request fires on the CONNECT line itself (before the tunnel is set up), not only on the decrypted requests inside it. Without the method == CONNECT early-return, every HTTPS exchange would record a bogus CONNECT host:443 flow. The guard is the first line of handle_request.

Store — byte-weighted ring buffer

The design calls out one hard requirement: ring-buffer eviction must weight by body bytes, not flow count. The Ring tracks a running total_bytes and evicts oldest-first until it is back under ring_max_bytes.

flowchart TD
    A["insert(flow) / set_response(...)"] --> B["total_bytes += flow.retained_bytes()"]
    B --> C{"over max_bytes AND more than 1 flow?"}
    C -- "no" --> D["done"]
    C -- "yes" --> E["pop oldest FlowId from order"]
    E --> F["remove from map; total_bytes -= its retained_bytes"]
    F --> G["push FlowId to evicted list"]
    G --> C
    D --> H["emit FlowEvent::FlowEvicted for each evicted id"]
Insertion order lives in a VecDeque<FlowId>; the flows themselves in a HashMap<FlowId, Flow> for O(1) lookup and in-place response updates. The order.len() > 1 guard keeps the newest flow even if it alone exceeds the cap.

FlowFilter backs GET /flows: case-insensitive matching on host (parsed from the URI authority), method, exact status, content_type (request or response), and a free-text q over the URI. Listing walks the deque newest-first.

Capture path

Buffer-then-forward, per-request 10 MB cap. capture() drains the body with http_body_util::BodyExt::collect().await, then decides: Empty (0 bytes), NotCaptured { TooLarge } (over the cap — forwarded intact but not kept), or Captured. Because the drain is destructive, it always rebuilds the outgoing body with Body::from(Full::new(bytes)) before returning it.

The one special case — streaming. A body with Content-Type: text/event-stream may never end, so it is never buffered: capture() checks the content type first and, on a match, records BodyRec::Streaming and forwards the original body untouched. Buffering it would hang the exchange forever. The streaming content-type list is a single spot in capture.rs, easy to extend.

Control API surface (inspect-only)

Built with axum 0.8 (note the {id} path-parameter syntax — a 0.8 change from :id). All endpoints live on the API port.

EndpointHandler → returns
GET /ui_page → the embedded web UI shell (api/ui.html via include_str!) — a plain client of the endpoints below, no dedicated API surface. The native desktop app (ui/) is a second such client, out of process (DEC-12).
GET /flows?host=&method=&status=&content_type=&q=list_flows → [FlowSummary]
GET /flows/{id}get_flow → FlowView (400 on bad id, 404 if missing)
GET /flows/{id}/request/body?decode=1request_body → raw bytes, or decoded (204 if no bytes retained)
GET /flows/{id}/response/body?decode=1response_body → raw bytes, or decoded
GET /streamstream → SSE of compact request/response/evicted events
GET /ca.crtca_cert → the root CA PEM (application/x-x509-ca-cert)

Every response carries an open CORS grant (Access-Control-Allow-Origin: *, with OPTIONS preflights short-circuiting to 204), a one-line axum middleware in api/mod.rs. The native app's webview is a cross-origin client, so without it its fetch/EventSource are blocked. Safe because the API is read-only and bound to 127.0.0.1 — everything it exposes is already curl-reachable, so * adds no exposure the bind address does not (DEC-12).

Decoding stays view-side. Capture stores raw bytes faithfully. ?decode=1 runs api/decode.rs lazily: reverse content-encoding (gzip/deflate today via flate2), then pretty-print if the content type is JSON. Brotli, charset transcoding, and XML/form pretty-printing are the obvious next extensions — all isolated in that one module. Unknown encodings pass through untouched rather than failing.

Native UI app (ui/)

A second client of the control API, in its own out-of-process project — the core does not compile, link, or know about it (DEC-12). The stack mirrors the sibling Strata app: Tauri 2 (native window) hosting a Vite + TypeScript + React front end styled with Tailwind (Warp tokens). Everything it shows is a REST read or an SSE subscription against 127.0.0.1:7421; it reaches no core internal.

Data flow — server-authoritative, replace-not-append. useFlows holds the current filter and calls api.listFlows(filter), which hits GET /flows?… with the same query params the web shell uses — the API owns the filter semantics, the front end never filters client-side. Every SSE lifecycle event (request/response/evicted/lagged) triggers the same debounced refetch, and the result replaces the list. So the rendered set is always exactly what a fresh GET /flows returns for the filter — no client-side merge, no unbounded growth, and eviction on the core side is reflected for free. The LiveDot tracks the real EventSource connection (onopen→live, onerror→not), not fetch success.

Configurable API base URL, resolved per call. defaultBaseUrl() picks, most-specific-first: a runtime window.__TRAWLER_API__, then a sessionStorage value (both survive without a rebuild — the released app's configuration hook and how the e2e injects an ephemeral port), then the build-time VITE_TRAWLER_API, then the :7421 dev default. createApi resolves it inside each request rather than capturing it, so an injection after mount takes effect on the next fetch. Component code never sees a port.

Build & e2e topology. cargo xtask ui build|dev|e2e drives the front end: build runs the pnpm install+build to ui/dist/; dev launches the Tauri window against a running core; e2e builds an e2e-flavoured app and drives the real WebKit window via WebdriverIO's @wdio/tauri-service. The WebDriver plugins are gated behind an e2e Cargo feature and a VITE_E2E flag so release builds tree-shake them out. The e2e's ephemeral core + local origin run in a standalone launcher crate under ui/e2e/harness/ (its own Cargo.toml, calling trawler::serve(Config) — the programmatic entry that returns a RunningServer with the bound ephemeral addrs and a deterministic shutdown, rather than run(Config)'s boot-until-interrupted) — outside the core workspace, so a headless cargo build/test of the proxy never pulls the GUI toolchain.

Certificate authority

ca.rs produces a CaMaterial { issuer, cert_pem }. On first run it generates an ECDSA CA (self-signed via rcgen), persists ca/trawler-ca.pem / .key, and serves cert_pem at /ca.crt. The issuer feeds hudsucker's RcgenAuthority, which caches and issues a per-host leaf on each CONNECT.

rcgen 0.14 / hudsucker 0.24 shape (the breaking change the design doc flagged). The CA is now an rcgen::Issuer<'static, KeyPair> built with Issuer::from_ca_cert_pem(cert_pem, key_pair), and RcgenAuthority::new(issuer, cache_size, provider) takes an explicit rustls CryptoProvider — here aws_lc_rs::default_provider(), also passed to the upstream connector via with_rustls_connector(...). The two hudsucker realities from the design still hold: every leaf reuses the CA key as its subject key, and IP-literal CONNECT targets get a DNS-type SAN (a known quirk). See the design doc.

Implementation decisions & deviations

Where the code makes a concrete choice the design left open — or deliberately diverges — it is recorded here. All are reversible behind the store / interface boundaries.

Library + thin binary

The API-first core is a real lib crate; main.rs is ~10 lines. Makes the core embeddable and unit-testable without a process.

/ca.crt on the API port

Design text shows :7420/ca.crt. A forward-proxy port expects proxy-form requests, so a browser opening :7420/ca.crt is ambiguous. We serve every control endpoint — including /ca.crt — on :7421. Mobile devices just point at the API port.

Correlate via handler clone

hudsucker clones the handler per exchange, so request↔response correlation is per-exchange scratch state in Recorder — no shared request-id map.

Store owns the bus

Events are emitted by the Store on write, not by the Recorder. One place decides what a "captured / evicted" event means, and it is the same place that mutates state.

Per-request cap, no global budget

Following the locked v1 rule: each body is judged on its own size. No shared atomic counter, no cross-request interference.

Compact SSE payloads

SSE events are lifecycle notifications (ids, method/uri/status, body state) — not base64 bodies. Clients fetch detail on demand, keeping the live stream light.

Dependencies

Applied the design's mandated upgrade. hudsucker 0.22 → 0.24 and rcgen 0.13 → 0.14 together (the Issuer + CryptoProvider break). Added as direct deps: axum 0.8 tokio-stream (sync) serde + serde_json http-body-util uuid (v4) base64 flate2 time (formatting). Dropped the unused rustls-pemfile and async-trait (hudsucker 0.24's HttpHandler uses native async fn).

What is intentionally not built (v1)

Out of scope by design, and where each will slot in: replay / breakpoints / request rewriting (new mutation endpoints + a handler hook), WebSocket-frame capture (hudsucker's WebSocketHandler), persistence — SQLite / HAR (behind the Store boundary), and transparent / NAT interception (root + per-OS plumbing). The current store and interface boundaries were chosen so none of these force a rewrite. See the design doc's challenges table.
