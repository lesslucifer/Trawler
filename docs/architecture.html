Architecture

The shape of the system: its layout and conventions, how a request moves through it, the client/core boundary, the load-bearing decisions, and the stack. The why behind each choice lives in Core Technical Design; the exact mechanics live in the source.

Trawler · T1 architecture spine

What this is

Trawler is an API-first, inspect-only MITM debugging proxy. A single process runs two servers: a capture proxy that intercepts HTTP(S) traffic, and a control API that exposes the captured flows over REST + SSE. Any interface — a native app, a browser, curl — is a client of that API, never a compile-time part of the core.

Layout & conventions

The core is a library crate with a thin binary launcher; the native UI is a separate out-of-process project. Everything is organised by role, one concern per module.

Runtime wiring

One async runtime hosts both servers: the capture proxy on one port, the control API on another. They bind loopback by default, and a user may add a second pair on one named interface address so another device can reach them — an authorization act costing one explicit confirm, off by default and dead with the process (DEC-55). The loopback pair is never displaced, so the app's own client cannot lose its connection to a disarm. The proxy handler is the only bridge between the two servers, and it only ever writes — it holds no reference to any client.

flowchart LR
    client(["client apps"]) <--> proxy["capture proxy (MITM)"]
    ca["CA material"] --> proxy
    proxy -- "record request / response" --> store[("Store")]
    store -- "lifecycle event" --> bus{{"broadcast bus"}}
    bus -- "subscribe" --> sse["control API — SSE stream"]
    store -- "read / query" --> rest["control API — REST"]
    sse --> clients["UI · browser · curl"]
    rest --> clients
The capture path knows nothing about clients. The Store is the single source of truth: it owns the broadcast bus and emits a lifecycle event on every write, eviction and clear. The control API is a subscriber and reader; it also ingests and removes — HAR import inserts flows the proxy never saw, marked as imported, through the same ring rules, and a clear takes out what the listing selects — but it never rewrites or reinterprets what the capture path recorded.

Request / response lifecycle

The proxy handles each exchange in two halves — request in, response back — and correlates them per exchange, with no external request-id map. Capture is buffer-then-forward: a body is drained to be recorded, then rebuilt and forwarded, so a capture decision can never break the connection.

sequenceDiagram
    participant C as Client
    participant P as Proxy handler
    participant S as Store
    participant B as Broadcast bus
    participant A as Control API
    C->>P: request
    Note over P: skip the tunnel-setup line itself
    P->>P: record request, remember this exchange
    P->>S: insert flow (request only)
    S->>B: request-captured event
    P->>C: forward request upstream
    C->>P: response
    P->>S: attach response + timing to the same flow
    S->>B: response-captured event
    B-->>A: SSE subscribers receive events live
    A-->>C: clients fetch flow detail on demand
One flow is emitted the moment the request is seen, then completed when its response arrives. Live events are compact notifications; clients pull full detail (headers, bodies) from the REST surface when they want it.

The client / core boundary

Every interface is a client of the running control API, decoupled from the core across loopback. The web shell served by the API, the native desktop app, and curl are all the same kind of thing: they issue REST reads and subscribe to the SSE stream. The core neither compiles, links, nor knows about any of them. This is the single most important invariant — it keeps capture independent of presentation and lets interfaces evolve, or multiply, without touching the proxy (DEC-12).

Technical decisions

The load-bearing choices in the code, one line each. Each is reversible behind the store / client boundaries; the rationale lives in the linked record or the source.

DecisionWhat & why (short)
Library + thin binaryCore is a real library; the binary just launches it — embeddable, testable without a process.
Store owns the event busEvents are emitted where state is mutated, so one place defines what "captured / evicted / cleared" means — and a user's clear is a distinct event from the ring's own eviction.
Per-exchange correlationRequest↔response is matched with per-exchange handler state, not a shared request-id map.
Tunnel-setup guardThe proxy skips the CONNECT line itself, so HTTPS setup never records a bogus flow. See design.
Byte-weighted evictionThe in-memory ring evicts by retained body bytes, not flow count, so memory — not row count — is the bound.
Per-request body cap, no global budgetEach body is judged on its own size; no shared counter, so parallel traffic never contends.
Buffer-then-forward captureBodies are drained to record, then rebuilt to forward — capture can't break the connection.
Never buffer streaming bodiesEvent-stream responses are recorded as "streaming" and forwarded untouched — buffering them would hang forever.
Synchronous store lockRing operations are pure/synchronous, so a plain mutex keeps locking off the async machinery — no actor ceremony.
Compact live eventsSSE carries lifecycle notifications (ids, method/uri/status, body state), not encoded bodies; clients fetch detail on demand.
View-side decodingCapture stores raw bytes faithfully; decoding (content-encoding reversal, charset→UTF-8, JSON/XML pretty-print) is an opt-in read transform (?decode=1), isolated in one place.
Control endpoints on the API portEverything a client needs — including the CA certificate download — is served off the API port, not the forward-proxy port.
Open CORS, bounded by the confirm rather than by the bindThe API carries an open CORS grant so an out-of-process webview client can reach it, widened to the methods its mutating routes need (DEC-12 for the grant, DEC-38 for the widening). It was once justified by "adding no exposure beyond the bind address"; DEC-55 retires that sentence, because the bind is now the user's to widen. The grant does not widen with it — what bounds exposure is the confirm: reach is off by default, arms one named address (never the unspecified one), and is not persisted. Arming exposes the proxy and the whole control API, captured flows included, on that address; the confirm says so. Anything finer — a token, TLS, a per-origin policy — is deliberately not here, and is its own epic.
UI out of processThe native app is a separate project and a network client only, so a headless core build stays GUI-free (DEC-12).

Build, run, test, debug

All commands are cargo tasks or the xtask driver, so the whole project — backend, front end, tests — is driven from one place.

GoalHow
Run the corecargo run — starts both the proxy and the control API on their loopback ports (raise verbosity via the log env var). Reach beyond loopback is off until something arms it.
Trust the CAFetch the CA certificate from the control API's cert endpoint and install it per the platform table.
Quick checkSend a request through the proxy, then read it back from the flows endpoint of the control API.
Backend testscargo test — unit + integration + e2e for the core (hermetic: ephemeral ports, local origins).
Lintcargo clippy — pedantic, warnings-as-errors, unsafe forbidden. Front end: npm run lint in ui/, which also runs the project-local design/vocabulary rule that judges every class against the closed token vocabulary (DEC-17).
Front-end build / devcargo xtask ui build bundles the webview; cargo xtask ui dev launches the native window against a running core.
UI e2ecargo xtask ui e2e — drives the real native window via WebDriver against an ephemeral core + local origin.
Gate & debug toolingThe xtask crate also runs the DoD gate and a live browser view of the evidence trail (see the workflow standard).
