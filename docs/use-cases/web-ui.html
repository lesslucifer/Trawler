Use Cases — UI surfaces

What a user can do against a running Trawler from a UI, stated as observable contracts. Two surfaces, one API: the zero-setup web shell (UC-3) and the native desktop app (UC-4 watch · UC-5 inspect), plus the native app's guided onboarding to the first captured flow (UC-ONBOARD) the HAR round trip — taking a capture out and bringing one back (UC-6) — and clearing the capture (UC-7).

UC-3 — Watch live traffic in the browser, zero setup

With Trawler running, opening GET / on the control API port in a browser serves a self-contained flow-list page straight from the binary — no install, no build step, no configuration, no external assets required for the list to function.

  • The page lists captured flows newest-first (time, method, host, path, status, duration) and updates live as traffic passes the proxy — new flows appear without a manual refresh, driven by the GET /stream SSE events.
  • A filter bar narrows the list by host, method, status and free text with exactly the GET /flows query-parameter semantics — the page delegates filtering to the API rather than reimplementing it.
  • The page is a plain client of the public control API; everything it shows is equally reachable with curl. It renders untrusted capture data (URIs, methods from proxied traffic) as text, never as markup.
  • Shutting Trawler down stays clean even while the page holds its never-ending SSE connection open.

Pinned by ui_shell_serves_live_filterable_flow_list in tests/e2e_capture.rs (page served, filter narrows, SSE event arrives, clean shutdown with the stream open) and the shell contract tests in tests/api.rs. In-browser rendering is covered by a recorded manual check. The shell's minimal chrome is deliberate; the native app (UC-4) is the designed surface.

UC-4 — Watch live traffic in the native app

With Trawler running, launching the native desktop app (E-UIFOUND, Tauri + React) shows the captured flows (method, host, path, status, duration) in the Warp-styled base layout and updates live as new traffic passes the proxy, via the existing GET /stream SSE stream.

  • A filter bar narrows the list by host, method, status and free text — the same GET /flows query-parameter semantics as UC-3, because the app delegates filtering to the API rather than reimplementing it. Status color distinguishes 2xx / 4xx / 5xx at a glance. The two keys the API matches exactly are chosen, not typed: method from the closed set of verbs, host from the hosts capture has seen, each with an "any" option that clears it. Free text and status stay typed — the API substring-matches the first, and the second is deferred (a status class query is not expressible against the current API at all).
  • The app is a pure cross-origin client of 127.0.0.1:7421 — it reaches no core internals; everything it shows is equally reachable with curl. Because the webview origin differs from the API's, every API response carries an open CORS grant (DEC-12); without it the webview's fetch/EventSource would be blocked.
  • The API base URL is configurable (never a hardcoded port in component code): a runtime value wins over a build-time env, which wins over the :7421 dev default — the released app exposes it as configuration.

Six capabilities the redesign (E-REDESIGN W2/W4, designed at the flow-list design run — archived) made observable. The contract keeps its shape — these are things a user can now do or perceive that they could not before:

GainWhy it is a contract change and not a restyle
A status carries its reason phrase 403 announces as "403 Forbidden" in its title and accessible name. A screen-reader user previously got a naked number, and colour was the only channel telling outcomes apart.
The capture indicator is a real target with a name A 24 px hit area and an accessible name carrying its state phrase, so the app's one route back to setup is reachable and announced rather than a 10 px unnamed disc.
A row is operable by keyboard The list is a listbox with one tab stop: ↑/↓ move the selection without wrapping and Enter or Space opens the detail. Selecting a flow previously required a pointer — there was no keyboard path at all.
An empty list says which nothing it is Nothing captured yet names the proxy address to send traffic to; a filter that excludes the traffic says so and names the act that widens it. One sentence previously served both, telling users to send traffic they had already sent.
An exactly-matched filter is chosen rather than typed Method and host are dropdowns. Typing GE into the old free-text method box returned an empty list indistinguishable from no traffic, because the server matches the verb whole — a query the user could write but never satisfy. What the dropdown costs is stated: a partial host (api. matching every API host) is no longer expressible there, and the free-text key covers it.
The verb is toned by what it does to the resource GET/POST/PUT/PATCH/DELETE read apart at a glance in the method column, which previously carried no tone.

One rule is knowingly unmet, and now bounded. The host and path cells truncate rather than wrap, because a virtualized fixed-height row cannot both wrap and stay one line. The full value stays reachable — the path on the row's title, both in the detail pane's URI — and the cut is visible as an ellipsis. Those are the three conditions DEC-34 now sets on the escape: the rulebook clause the design run escalated was written at the epic close, and the rule's Tier-1 red is unchanged.

The capture-management controls

The flow list is where UC-6 and UC-7 reach a person rather than only a client (E-EXPORT W6, built from the capture-controls design run). These are the first controls in the app that change server state, and they sit behind one ⋮ trigger at the header's trailing edge, past the filters that scope them. Beside it a fixed-width slot reads the count those filters selected, and reads exporting… or importing… while a transfer runs — the same box either way, so starting one moves nothing else in the row.

ActWhat a user gets
export as har… The filtered capture, through the OS save dialog, under the filename the server stamped rather than one the app invented. Dismissing that dialog is an outcome, not a failure: the line clears and nothing claims a file was written.
import… One modal taking either way in — choose a .har file, or paste a curl command into the target it opens focused on. A refusal is the server's own sentence (DEC-37), shown verbatim under the text that caused it, with the text left in place to edit.
clear… A modal ask titled with the count it will remove, whose initial focus is on the answer that does nothing — the act behind it cannot be undone. The consequence carries the only alarm on the screen; the button carries none.

Two things the list itself gained. An imported row carries a ↑ mark in its time cell, with its own accessible name, so a capture someone handed you is tellable from live traffic without a column of its own (DEC-36). And a cleared list gets a third absence of its own — "capture cleared", with the same remedy the never-captured one gives, because after a clear the remedy genuinely is the same and the heading is what says which nothing this is.

Every one of the three refills the list from the event bus, never from its own response: the responses carry counts, not rows, and two sources of truth for one list is a race. The cleared event exists for exactly this.

Pinned by the epic e2e (ui/e2e/specs/flows.spec.ts, cargo xtask ui e2e): WebdriverIO drives the real WebKit window against an ephemeral run(Config) core — empty layout renders, a proxied request appears live carrying every column, the status pill carries its reason phrase, the filter narrows and restores, an unmatched filter states its own absence, the keyboard alone selects a row and opens its detail, and a second request appends without refresh. Unit + integration layers (Vitest + Testing Library) cover the status-color mapping, the typed client, filter→params, and the layout+list against a mock API. Existing API contracts (GET /flows, GET /stream) are consumed unchanged; the CORS grant is the one API-response addition. UC-3 (web shell) stays valid — both surfaces are clients of the same API.

UC-3 · UC-4 — the listing pages, opt-in

Both surfaces read one listing contract, and it is bounded only when a client asks:

RequestAnswer
GET /flows, with or without filters the whole filtered capture, newest-first, as a bare JSON array — unbounded, and unchanged by paging's arrival
GET /flows?limit=n an envelope: at most n rows plus the next_cursor that continues the walk, null once the walk reaches the oldest row the ring still holds
GET /flows?source=captured · ?source=imported only that provenance. Every row carries its source, because the ring now holds flows the proxy never saw (UC-6) and a listing that mixes a live capture with a colleague's file has to say which is which
a limit that is not a positive integer · a cursor that is not a flow id · a cursor with no limit · a source that is neither refused 400 with a reason naming the parameter — never an unbounded read a client did not ask for, and never a silently empty listing that reads like "nothing matched"
  • The cursor names a row, not an offset — the id of the page's last row, resolved against the ring's order. So a flow captured mid-walk lands newer than the cursor and is never served twice (a client watching live gets it on GET /stream; a paged read is a read of the past), and eviction of rows the walk has not reached yet simply shortens it. Paging composes with every filter and re-slices the same listing rather than defining a second one.
  • A cursor the ring no longer holds ends the walk — an empty, final page, whether the row was evicted under memory pressure or deleted (UC-7): the walk cannot resume from a row that is gone, and the cause does not change the answer. It never restarts at the newest row, which would re-serve every row the client already holds.

Delivered by E-EXPORT.W1. Pinned by the paging tests in tests/api.rs (the unparameterised summary row's field set is locked; a cursor walk yields exactly the unpaged listing, filtered and unfiltered; each refusal) and by Store::page's unit and property tests in src/store.rs — the no-duplicate/no-skip invariant is proven over interleaved inserts, evictions and page reads, not by example. Neither surface pages today: both read the unparameterised listing, which is why the contract had to stay additive.

UC-5 — Inspect a captured flow in the native app

Clicking a flow row in the native app (E-UIINSPECT, rebuilt by E-REDESIGN) opens the detail panel over GET /flows/{id} — a pinned identity row (verb, status with the 2xx/4xx/5xx functional color and its reason phrase, the leg selector, total duration, close), then the flow line (the full URI, both HTTP versions, copy-as-curl), then the selected leg's Headers and Body. No new endpoint; the panel is a pure client of the existing API.

  • One leg at a time, under one selector (DEC-31): the identity row's request | response switch governs both the header table and the body pane together; the URI, versions and curl are the flow's and never move. The panel always opens on request. A leg that sent no headers says none — this leg sent no headers and stays selectable; a flow still being fetched shows loading this flow… and nothing else.
  • Every wire value is a copy target: headers render in wire order with duplicate names preserved, and clicking a header value — or the URI — copies exactly that value, confirming at the value for ~2 s; drag-selecting still selects.
  • The body is the main zone and the panel never scrolls as a whole (DEC-32): the headers take their natural height up to about a third of the panel and scroll inside it, the heading naming how many there are; the body takes the rest and scrolls inside itself. A header value taller than three lines — a cookie, a token, a policy — is clamped with more / less under its name: lines are hidden, never characters, the value still copies whole, and one act shows all of it.
  • Esc dismisses the panel, as does ✕, and focus returns to the list that opened it, so a keyboard user lands back on the row they came from.
  • Bodies render by content type over GET /flows/{id}/{leg}/body: JSON and XML/HTML as their pretty-printed source in a navigable, foldable surface, image/* as the image over a transparency checkerboard, form-urlencoded as decoded key/value rows (each value individually copyable), other text as text, anything else as a toned hex dump.
  • Raw shows the source, not the compression frames: the raw / decoded toggle switches between the bytes the server sent (?decode=source — transport encoding reversed, nothing re-indented or transcoded) and the fully rendered view (?decode=1 — decompressed, charset-normalised, JSON/XML pretty-printed). A gzipped JSON body therefore reads as its minified source in raw rather than as a hex dump of gzip frames, and hex is reserved for payloads that genuinely have no text form. The stored bytes stay reachable at ?decode=0.
  • A truncated body says so: renderings are capped (128 KiB of characters, 4 KiB of hex) and a capped body states "showing N of M — save to see all" in warn tone, naming the size shown, the real total, and the way to the rest. No cap is silent, and no body is re-indented client-side — what is shown is what crossed the wire, so a copy is evidence.
  • States are never blank: an empty, streaming-passthrough, too-large, read-error, not-yet-responded, in-flight or failed-to-load body shows an explicit notice instead of a viewer — one distinct sentence per cause, and warn tone only on the one that is a fault.
  • Copy-as-curl reproduces the request (method, URL, headers, body, shell-quoted) from a labelled button beside the URI; the command itself is never rendered, and the button reads copied for ~2 s before reverting; copy body puts the shown body on the clipboard (the hex dump for hex-rendered bodies; hidden for images); save body writes the shown leg's bytes to a file via the OS save dialog, named after the endpoint — the URI's last path segment, or the host when the path names nothing — plus the leg and the extension the served content type implies (charges-response.json, example.com-response.html), so a saved body is recognisable in a downloads folder and opens in the right application.
  • The ?decode=1 contract is server-side — gzip/deflate/brotli reversal, charset→UTF-8, JSON + XML pretty-printing — so curl and the web shell gain the same decoded view the app shows.

Pinned by the inspector e2e (ui/e2e/specs/flows.spec.ts): row click → the request leg's headers / timing / versions; the leg selector switches headers and body together while the flow line stays; under a wall of long headers the window gains no scroll, the body zone is the taller of the two and stays on screen, and a clamped header value expands on more; a JSON response renders as copy-exact source; the raw toggle shows the served source as text; copy-as-curl's payload is read back from a recording clipboard stub installed through WebDriver (the OS clipboard itself cannot be read there — the real write, like the native save dialog, stays a recorded manual check); Esc closes the panel; a brotli-compressed JSON body still renders decoded — the decode chain proven through the UI; a proxied PNG renders as an image; an XML body renders as XML rather than falling through to text; a brotli body in raw shows its minified source rather than a hex dump of its frames; and a body past the render cap states its truncation. The decode chain itself is pinned at the API seam in tests/api.rs and the src/api/decode.rs unit suite; viewer dispatch, states, and copy/save are covered by the Vitest unit + integration layers. scripts/seed-proxy.mjs seeds one flow per case for manual checks.

UC-ONBOARD — Onboard a fresh machine to the first captured flow

On a machine that can't yet decrypt HTTPS, the native app opens a three-step guided setup — Trust the CA · Set the proxy · Make a request — instead of the flow list. Its rule (E-UISETUP): do the work for the user in the common case, tell the truth in every case, and prove success only by real capture.

  • Least manual work. On macOS/Windows each step offers one native action (install the CA, set the system proxy — both elevation-gated); the per-OS manual steps sit behind a "Set it up manually" disclosure that auto-opens if the action fails. Other OSes show the manual steps inline. Instructions are always plain text, never markup.
  • Two layers of status, never blended (never the stepper cursor — a step is never ✓ just because you clicked past it; DEC-33).
    • This machine — steps 1 and 2 report the two read-only probes and nothing else: does this machine trust the CA, does its system proxy point at Trawler. Their verdicts say "on this machine" and mean it; traffic, however much of it, never turns them green.
    • Traffic — step 3 reports what is reaching Trawler now, from timestamps: a decrypted flow inside the last 30 s reads capturing traffic; a tunnel no flow answered reads arriving but not decrypting, with the remedy naming the client that lacks the certificate; plain HTTP only is its own verdict; traffic seen earlier but nothing recent reads idle — nothing arriving now, and the open step dates the last flow. An old flow can only ever produce idle.
    When a probe can't conclude (an un-probeable OS) the wording says so and points at step 3, where the traffic answer will show — it never shows a false "not set up". A phone that trusts the certificate and points here reads as two true facts side by side: "not trusted on this machine" and "capturing traffic".
  • A tunnel is observable before decryption. An HTTPS attempt from a client that doesn't trust the CA fails its TLS handshake and produces no flow — so the core counts the tunnel itself: GET /stats returns a monotonic connections tally and a connection SSE event fires. The live event is stamped and feeds step 3's verdict; the tally carries no time and can only distinguish idle from waiting for your first request. The verdict and what to do about it are two elements, so a short verdict never costs the instruction.
  • Only a decrypted flow reveals the list. A probe-green step or a bare connection never ends onboarding — the payoff (the last step → flow list) fires solely on the first https:// flow (a decrypted request the MITM rewrote to absolute form). The last step shows a concrete prove-it: open any site, or run a copyable curl -x http://<addr> https://example.com with the real proxy address. Capture, once proven, latches (the status dot re-invokes setup on demand; "Back to flows" returns).
  • The certificate is saved from the step that names it (E-REDESIGN.W10). Every manual route's first step names trawler-ca.pem, so that step produces the file: a ↓ ends the sentence, fetches /ca.crt and writes it through the OS save dialog (native) or a download (browser), under exactly the name the following steps run against, with the outcome stated beneath the sentence inside the same step. The save reports what actually happened rather than assuming it: a failure says so, a cancelled dialog says nothing was saved (it resolves exactly like a write), and a save the user renamed — the offered name is only the dialog's default — is confirmed under the name that landed, with the mismatch against the steps below named outright.
  • A probe reading is a dated snapshot, re-taken on demand (E-REDESIGN.W10). Nothing pushes when the user changes the trust store or the system proxy outside Trawler, so a green verdict outlives its truth until something re-reads the machine. One row above the steps reads checked at HH:MM:SS · check again; the control re-runs both probes, and so does the window regaining focus — the moment the user is most likely to have just changed a setting. While a re-read runs the control is disabled and both probed steps show the in-flight verdict; the answer that comes back replaces the stale one, green or not.
  • A copied command says whether it copied (E-REDESIGN.W10). Both commands — the prove-it and the per-OS proxy snippet — are the copy target themselves, confirming at the value; a clipboard write the browser refuses says copy failed rather than doing nothing visible.
  • Quitting with a proxy still set asks first, and can fix it (E-REDESIGN.W10). Where a proxy is set on this machine — Trawler's or another's, since turning the OS proxy off does not depend on whose address is set — the dialog offers to turn it off, and a failed attempt says so and opens the manual steps instead of quitting onto a dead proxy. Where nothing is set locally but a remote device may still route here, it is a notice with a durable "don't show this again". Esc, the backdrop and ✕ all cancel the quit.

  PR --> ST["Steps 1–2: this machine's verdicts, stamped 'checked at'"]

Two layers. The probes answer for this machine and are re-read on demand; the traffic verdict answers for the wire, judged against a clock. Neither borrows from the other. The list reveal is decrypted-flow-only.

New API surface (consumed by onboarding, usable by any client): GET /stats → { connections } and the connection SSE event ({ authority }) on the existing /stream. The connection tally is a monotonic counter in the store, bumped when the proxy opens a CONNECT tunnel — kept outside the flow ring so eviction never touches it. The two local probes (CA-in-trust-store, system-proxy-address) live in the Tauri app, not the core; they read the real machine so they are not hermetically testable (the status derivation they feed is fully unit-tested). This deliberately supersedes two earlier "prove by capture only" stances (no trust-store inspection / no OS self-test): the probe covers the 90% for instant honest feedback; capture is the sole thing that reveals the list, and — as of E-REDESIGN.W10 — the sole input to step 3, where it is judged by recency rather than by having ever happened. Pinned by tests/e2e_capture.rs::untrusted_https_records_a_connection_not_a_flow (a failed handshake bumps /stats + emits connection, records no flow), the status derivation + probe-parser unit tests, and the UC-ONBOARD e2e spine. Why these reversals were approved: DEC-13.

UC-6 — Take the capture out as a HAR file, and bring one back

GET /flows/export answers with the currently filtered capture as a single HAR 1.2 document — the interchange format the tools in this space already read — served as application/json with a Content-Disposition naming a .har file, so a browser or the native app saves it under a timestamped name.

RequestAnswer
GET /flows/export every captured exchange as a log.entries element — method, URL, both HTTP versions, headers (order and duplicates preserved), query string, cookies, status and reason, the time it was captured, its duration and a timings block, and its bodies
GET /flows/export?host=…&method=…&status=…&content_type=…&q=… the same document over the filtered set: the export selects exactly what the listing with those parameters lists, in the same order — the same filter, not a second implementation of it
an empty capture, or a filter matching nothing 200 with log.entries: [] — a valid, empty HAR file, not a 404: the client asked what is captured and the answer is "nothing"

Two consequences a reader cannot infer from the endpoint signature:

  • A body Trawler never captured is marked as such, never exported as empty. A streamed body, one skipped for being too large, and one lost to a read error each appear as a body with no text and a comment naming the reason — so a 4 MB event stream is never indistinguishable from a 204. A too-large body additionally reports the size it had, because that size is known and is exactly why the bytes were dropped. Only a genuinely empty body is a measured zero. Every other fact Trawler does not hold — the raw header-block sizes, the wire reason phrase, a cookie's optional attributes — is HAR's own "unavailable" sentinel rather than an invented value. The timings are the one place HAR forbids that sentinel: an exchange whose duration was never measured reports an unknown total with its phases zeroed, because a negative phase is a value no reader accepts.
  • A flow still awaiting its response is omitted from the file, because HAR requires a response on every entry and there is nothing truthful to put there. So an export taken mid-exchange can hold one entry fewer than the listing shows.

The exported bytes are the bytes captured, with the Content-Encoding that describes them still attached — the file stays a faithful record of the wire, and GET /flows/{id}/{leg}/body?decode=1 remains the decoding surface. The export is never paged: a HAR file split across pages is not a HAR file, so the filter is the way to export less.

Bringing one back

POST /flows/import takes a HAR 1.2 document — Trawler's own export, or one any conforming tool wrote — and its entries become flows in the listing, each marked source: "imported". An imported flow is otherwise an ordinary flow: the same GET /flows/{id}, the same body endpoints and their ?decode=1, the same /stream announcement as it lands, and the same ring rules — it evicts by retained bytes like anything else, so a large import can push a live capture out.

RequestAnswer
POST /flows/import + a HAR 1.2 document 200 with { "imported": n } — the count, because a client that posted a 900-entry file needs to know whether all 900 landed. The entries add to the capture; replacing it is a clear followed by an import, not a mode hidden inside a POST
a malformed or hostile document — not JSON, a version other than 1.2, no log.entries, an entry with no request, an unparseable timestamp, an impossible status, a body whose base64 is not base64 400 with a reason, and an entry-level fault names its index. All-or-nothing: the whole document parses before the store is touched, so a refused import changes nothing at all — never a partially-populated capture
log.entries: [] 200 with { "imported": 0 } — a valid document saying nothing was captured, which is not an error; the same reading an empty export has

Three consequences a reader cannot infer from the endpoint signature:

  • Fresh ids, original timestamps. An id is this store's handle and must be unique here, so an imported flow takes a new one; the instant the exchange happened is the captured truth and is preserved, so an imported capture sorts by when it happened, not when it was read. Import the same file twice and you get two independent sets of flows carrying the same instants.
  • A body the file does not carry comes back as an explicit not-captured, never as empty. Trawler's own markers restore the exact state (streamed, too-large with the size it had, read error). A foreign writer's body with no text but a size claiming one existed becomes a not-captured too — calling it empty would assert a 4 MB response was a 204. Only a measured zero is empty.
  • What the format cannot carry is dropped, not invented. The derived and unretained fields — the query string, the parsed-out cookies, the timing phases, the reason phrase, the header-block sizes — are read past in silence, because each was either derived from a header the flow still carries or was never Trawler's to hold. A body's bytes outrank a size that disagrees with them: the ring weighs what it actually holds.

A single request, pasted

The same door takes one curl command — the inverse of UC-5's copy-as-curl — under POST /flows/import?format=curl, with the command as the raw text body. It becomes one request-only flow: method, URL, headers and body as the command states them, source: "imported", no response and no duration, because nothing was sent — the shape a captured flow already has between its request and its reply, so every reading endpoint and the app's row already know how to show it.

RequestAnswer
POST /flows/import?format=curl + what a browser's "Copy as cURL" (Chrome, Firefox, Safari — bash shape) or Trawler's own copy-as-curl emits: the URL, -X, -H, the -d family, -b, -u, --compressed, in single, double or $'…' quoting with backslash line-continuations 200 with { "imported": 1 }. -u, -b and --compressed arrive as the Authorization, Cookie and Accept-Encoding headers they stand for; several -d join with &; the method defaults to GET, or POST when a body flag is present, as curl's own does. Nothing curl would add at run time — Host, User-Agent, Accept, a Content-Type for -d — is invented
the same command carrying transfer-only flags — -s, -k, -L, -o file, --connect-timeout 5 and the rest of an enumerated list the same flow: they shape curl's own behaviour and never reach the wire, so they are consumed in silence — the one silent case
anything else — -F, -T, --data-urlencode, an unknown flag, a second URL, no URL, a URL that is not absolute http(s), a value curl would read from a file (-d @body, -b jar), a -u with no password, a header with no colon, an unterminated quote, a first word that is not curl 400 with a one-sentence reason naming the token — unsupported flag -F, a second URL: "http://other/" — and the capture unchanged. Refused rather than guessed, because a silently dropped flag yields a flow subtly unlike the request that was pasted
?format= anything but har or curl 400 format must be har or curl; absent means HAR, unchanged

The flow's instant is the moment it was read. Windows cmd's "Copy as cURL" shape (^ continuations) is not spoken and is refused, not half-read. Why the boundary sits exactly here, which headers are expanded and which are never invented, and where the toCurl round trip stops: DEC-37.

Export delivered by E-EXPORT.W2, import and the source mark by E-EXPORT.W3, the curl paste by E-EXPORT.W7 (src/api/curl.rs, its toCurl inverse proven as a property against a mirror anchored to the app's own pinned outputs); the route a person takes to all three is UC-4's capture-management controls (E-EXPORT.W6). Both HAR directions live in src/api/har.rs — the parser is defined against the projection it inverts, so the two cannot drift into a format Trawler writes but cannot read — and the exported document's shape is snapshot-locked in tests/api.rs. Round-trip fidelity is proven as a property over generated flows, not by example, and the parser's never-panics claim the same way. The export-selects-what-the-listing-lists guarantee holds by construction (both endpoints build the same filter) and is asserted endpoint-to-endpoint. Why HAR and only HAR, and what a round-trip does and does not preserve: DEC-35; why an imported flow is a first-class flow carrying a mark, and the CORS widening its POST required: DEC-36.

UC-7 — Clear the capture

A debugging session accumulates noise, and reproducing a bug against a clean listing is the reason the ring needed a third door. DELETE /flows removes what the listing filters select and DELETE /flows/{id} removes exactly one — and every live subscriber learns of it on /stream, so an interface never discovers a clear by refetching.

RequestAnswer
DELETE /flows 200 with { "removed": n } — the whole capture is gone, with no row kept back. The count is the same envelope the import answers with, so both mutating endpoints report what they did
DELETE /flows?host=…&method=…&status=…&content_type=…&q=…&source=… only the matching rows leave: a delete selects exactly what the listing with those parameters lists — the same filter as the listing and the export, not a third implementation. Every survivor stays whole: still listed, still readable at GET /flows/{id} and at both body endpoints
a filter matching nothing 200 with { "removed": 0 } — the request expresses an end state and that state is already true. An unrecognised source= is the exception: 400 with a reason, because a destructive request must never act on a set the caller did not name
DELETE /flows/{id} 200 with { "removed": 1 }; 404 when that id is not in the ring — the one delete that 404s, because here the client named something specific that does not exist — and 400 when the id is not a flow id

Three consequences a reader cannot infer from the endpoint signature:

  • A cleared store is empty, not restarted. The connection tally GET /stats reports is untouched by any delete, and the proxy keeps running: the tally is a monotonic "traffic reached us" measure, not storage. Clearing the capture is not a way to reset the session.
  • The clear arrives as one event for the whole batch — event: cleared carrying every id that left — not one event per flow, so emptying a full ring cannot lag a subscriber past the stream's buffer and drop it into the lagged gap. It is a distinct event from the ring's own evicted: an interface that conflated them would announce "capture cleared" every time memory pressure dropped a row.
  • Removing is not replacing. Loading someone else's capture over your own is a delete followed by an import — two operations the client already has — rather than a destructive mode hidden inside the POST.
  • A delete can end another client's paging walk. If the removed row was the cursor some client is paging from, that client's next page is empty and final — the same answer eviction has always given, because the walk cannot resume from a row that is gone and the cause does not change the answer (the listing contract).

Delivered by E-EXPORT.W4; the app's own clear control — the modal ask, and the absence a cleared list lands on — is UC-4's capture-management controls (E-EXPORT.W6). The API half is the whole contract above: both routes converge on one Store removal, which shares its unlinking with eviction so the ring's byte accounting cannot differ between the two — the invariant is asserted as a property over arbitrary sequences of inserts, imports, evictions and removals.
