Use Cases — UI surfaces

What a user can do against a running Trawler from a UI, stated as observable contracts. Two surfaces, one API: the zero-setup web shell (UC-3) and the native desktop app (UC-4 watch · UC-5 inspect), plus the native app's guided onboarding to the first captured flow (UC-ONBOARD) and the HAR round trip — taking a capture out and bringing one back (UC-6).

UC-3 — Watch live traffic in the browser, zero setup

With Trawler running, opening GET / on the control API port in a browser serves a self-contained flow-list page straight from the binary — no install, no build step, no configuration, no external assets required for the list to function.

  • The page lists captured flows newest-first (time, method, host, path, status, duration) and updates live as traffic passes the proxy — new flows appear without a manual refresh, driven by the GET /stream SSE events.
  • A filter bar narrows the list by host, method, status and free text with exactly the GET /flows query-parameter semantics — the page delegates filtering to the API rather than reimplementing it.
  • The page is a plain client of the public control API; everything it shows is equally reachable with curl. It renders untrusted capture data (URIs, methods from proxied traffic) as text, never as markup.
  • Shutting Trawler down stays clean even while the page holds its never-ending SSE connection open.

Pinned by ui_shell_serves_live_filterable_flow_list in tests/e2e_capture.rs (page served, filter narrows, SSE event arrives, clean shutdown with the stream open) and the shell contract tests in tests/api.rs. In-browser rendering is covered by a recorded manual check. The shell's minimal chrome is deliberate; the native app (UC-4) is the designed surface.

UC-4 — Watch live traffic in the native app

With Trawler running, launching the native desktop app (E-UIFOUND, Tauri + React) shows the captured flows (method, host, path, status, duration) in the Warp-styled base layout and updates live as new traffic passes the proxy, via the existing GET /stream SSE stream.

  • A filter bar narrows the list by host, method, status and free text — the same GET /flows query-parameter semantics as UC-3, because the app delegates filtering to the API rather than reimplementing it. Status color distinguishes 2xx / 4xx / 5xx at a glance.
  • The app is a pure cross-origin client of 127.0.0.1:7421 — it reaches no core internals; everything it shows is equally reachable with curl. Because the webview origin differs from the API's, every API response carries an open CORS grant (DEC-12); without it the webview's fetch/EventSource would be blocked.
  • The API base URL is configurable (never a hardcoded port in component code): a runtime value wins over a build-time env, which wins over the :7421 dev default — the released app exposes it as configuration.

Pinned by the epic e2e (ui/e2e/specs/flows.spec.ts, cargo xtask ui e2e): WebdriverIO drives the real WebKit window against an ephemeral run(Config) core — empty layout renders, a proxied request appears live, the filter narrows and restores, a second request appends without refresh. Unit + integration layers (Vitest + Testing Library) cover the status-color mapping, the typed client, filter→params, and the layout+list against a mock API. Existing API contracts (GET /flows, GET /stream) are consumed unchanged; the CORS grant is the one API-response addition. UC-3 (web shell) stays valid — both surfaces are clients of the same API.

UC-3 · UC-4 — the listing pages, opt-in

Both surfaces read one listing contract, and it is bounded only when a client asks:

RequestAnswer
GET /flows, with or without filters the whole filtered capture, newest-first, as a bare JSON array — unbounded, and unchanged by paging's arrival
GET /flows?limit=n an envelope: at most n rows plus the next_cursor that continues the walk, null once the walk reaches the oldest row the ring still holds
GET /flows?source=captured · ?source=imported only that provenance. Every row carries its source, because the ring now holds flows the proxy never saw (UC-6) and a listing that mixes a live capture with a colleague's file has to say which is which
a limit that is not a positive integer · a cursor that is not a flow id · a cursor with no limit · a source that is neither refused 400 with a reason naming the parameter — never an unbounded read a client did not ask for, and never a silently empty listing that reads like "nothing matched"
  • The cursor names a row, not an offset — the id of the page's last row, resolved against the ring's order. So a flow captured mid-walk lands newer than the cursor and is never served twice (a client watching live gets it on GET /stream; a paged read is a read of the past), and eviction of rows the walk has not reached yet simply shortens it. Paging composes with every filter and re-slices the same listing rather than defining a second one.
  • A cursor the ring has evicted ends the walk — an empty, final page, because the capture no longer reaches back that far. It never restarts at the newest row, which would re-serve every row the client already holds.

Delivered by E-EXPORT.W1. Pinned by the paging tests in tests/api.rs (the unparameterised summary row's field set is locked; a cursor walk yields exactly the unpaged listing, filtered and unfiltered; each refusal) and by Store::page's unit and property tests in src/store.rs — the no-duplicate/no-skip invariant is proven over interleaved inserts, evictions and page reads, not by example. Neither surface pages today: both read the unparameterised listing, which is why the contract had to stay additive.

UC-5 — Inspect a captured flow in the native app

Clicking a flow row in the native app (E-UIINSPECT) opens the detail panel over GET /flows/{id} — request line, status with the 2xx/4xx/5xx functional color, total duration, per-leg HTTP versions, and the full request + response header tables. No new endpoint; the panel is a pure client of the existing API.

  • Bodies render by content type over GET /flows/{id}/{leg}/body: JSON as a collapsible tree, XML/HTML as (pretty-printed) text, image/* as the image, form-urlencoded as a decoded key/value table, other text as text, anything else as a hex dump. A raw / decoded toggle switches between the stored bytes (?decode=0, sniffed to text or hex) and the server-decoded rendering (?decode=1). Oversize renderings are bounded — hex and the JSON tree cap and fall back rather than hang the window.
  • States are never blank: an empty, streaming-passthrough, too-large, read-error, or not-yet-responded body shows an explicit notice instead of a viewer.
  • Copy-as-curl reproduces the request (method, URL, headers, body, shell-quoted); copy body puts the shown body on the clipboard (the hex dump for hex-rendered bodies; hidden for images); save body writes the shown leg's bytes to a file via the OS save dialog, with a filename derived from the flow id, leg, and content type.
  • The ?decode=1 contract is server-side — gzip/deflate/brotli reversal, charset→UTF-8, JSON + XML pretty-printing — so curl and the web shell gain the same decoded view the app shows.

Pinned by the inspector e2e (ui/e2e/specs/flows.spec.ts): row click → headers / timing / versions; a JSON response renders as a tree; the raw toggle shows the stored bytes as text; the curl text is asserted in the DOM (WebDriver clipboard is unreliable — the real clipboard write is a recorded manual check, as is the native save dialog); a brotli-compressed JSON body still renders as a tree — the decode chain proven through the UI; a proxied PNG renders as an image. The decode chain itself is pinned at the API seam in tests/api.rs and the src/api/decode.rs unit suite; viewer dispatch, states, and copy/save are covered by the Vitest unit + integration layers. scripts/seed-proxy.mjs seeds one flow per case for manual checks.

UC-ONBOARD — Onboard a fresh machine to the first captured flow

On a machine that can't yet decrypt HTTPS, the native app opens a three-step guided setup — Trust the CA · Set the proxy · Verify — instead of the flow list. Its rule (E-UISETUP): do the work for the user in the common case, tell the truth in every case, and prove success only by real capture.

  • Least manual work. On macOS/Windows each step offers one native action (install the CA, set the system proxy — both elevation-gated); the per-OS manual steps sit behind a "Set it up manually" disclosure that auto-opens if the action fails. Other OSes show the manual steps inline. Instructions are always plain text, never markup.
  • Two-truths status per step (never the stepper cursor — a step is never ✓ just because you clicked past it). Each step's honest status comes from either of two independent signals:
    • a fast local probe — does this machine trust the CA / route its system proxy to Trawler? (the ~90% single-machine case; instant, read-only OS queries), or
    • observed traffic — has anything actually reached Trawler, from any device?
    When the probe can't conclude (un-probeable OS, or a remote device) the wording says so and points at capture — it never shows a false "not set up".
  • The proxy step goes green on any connection, decrypt or not. An HTTPS attempt from a client that doesn't trust the CA fails its TLS handshake and produces no flow — so the core counts the tunnel itself: GET /stats returns a monotonic connections tally and a connection SSE event fires. That proves "traffic is routing through Trawler" even before decryption works. Traffic seen but not decrypting ⇒ the Trust step says "install the certificate on the device you're capturing from".
  • Only a decrypted flow reveals the list. A probe-green step or a bare connection never ends onboarding — the payoff (Verify → flow list) fires solely on the first https:// flow (a decrypted request the MITM rewrote to absolute form). The Verify step shows a concrete prove-it: open any site, or run a copyable curl -x http://<addr> https://example.com with the real proxy address. Capture, once proven, latches (the status dot re-invokes setup on demand; "Back to flows" returns).
flowchart TD
  E["Enter setup (no decrypted flow yet)"] --> PR["Probe this machine: CA trusted? proxy set?"]
  PR --> ST["Trust and Proxy steps show local status instantly"]
  E --> W["Watch traffic: GET /stats + connection and flow SSE events"]
  W --> C{"What arrived?"}
  C -- "any connection" --> PX["Proxy step green: receiving traffic"]
  C -- "http flow, no https" --> TR["Trust: not decrypting, install the CA on the sending device"]
  C -- "https flow (decrypted)" --> OK["Trust green + Verify green: reveal the flow list"]
Probes light the steps instantly for the local case; observed traffic confirms — and, for a remote device, is the only thing that can. The list reveal is decrypted-flow-only.

New API surface (consumed by onboarding, usable by any client): GET /stats → { connections } and the connection SSE event ({ authority }) on the existing /stream. The connection tally is a monotonic counter in the store, bumped when the proxy opens a CONNECT tunnel — kept outside the flow ring so eviction never touches it. The two local probes (CA-in-trust-store, system-proxy-address) live in the Tauri app, not the core; they read the real machine so they are not hermetically testable (the status derivation they feed is fully unit-tested). This deliberately supersedes two earlier "prove by capture only" stances (no trust-store inspection / no OS self-test): the probe covers the 90% for instant honest feedback; capture stays the authority for the remote cases and the sole thing that reveals the list. Pinned by tests/e2e_capture.rs::untrusted_https_records_a_connection_not_a_flow (a failed handshake bumps /stats + emits connection, records no flow), the status derivation + probe-parser unit tests, and the UC-ONBOARD e2e spine. Why these reversals were approved: DEC-13.

UC-6 — Take the capture out as a HAR file, and bring one back

GET /flows/export answers with the currently filtered capture as a single HAR 1.2 document — the interchange format the tools in this space already read — served as application/json with a Content-Disposition naming a .har file, so a browser or the native app saves it under a timestamped name.

RequestAnswer
GET /flows/export every captured exchange as a log.entries element — method, URL, both HTTP versions, headers (order and duplicates preserved), query string, cookies, status and reason, the time it was captured, its duration and a timings block, and its bodies
GET /flows/export?host=…&method=…&status=…&content_type=…&q=… the same document over the filtered set: the export selects exactly what the listing with those parameters lists, in the same order — the same filter, not a second implementation of it
an empty capture, or a filter matching nothing 200 with log.entries: [] — a valid, empty HAR file, not a 404: the client asked what is captured and the answer is "nothing"

Two consequences a reader cannot infer from the endpoint signature:

  • A body Trawler never captured is marked as such, never exported as empty. A streamed body, one skipped for being too large, and one lost to a read error each appear as a body with no text and a comment naming the reason — so a 4 MB event stream is never indistinguishable from a 204. A too-large body additionally reports the size it had, because that size is known and is exactly why the bytes were dropped. Only a genuinely empty body is a measured zero. Every other fact Trawler does not hold — the raw header-block sizes, the wire reason phrase, a cookie's optional attributes — is HAR's own "unavailable" sentinel rather than an invented value. The timings are the one place HAR forbids that sentinel: an exchange whose duration was never measured reports an unknown total with its phases zeroed, because a negative phase is a value no reader accepts.
  • A flow still awaiting its response is omitted from the file, because HAR requires a response on every entry and there is nothing truthful to put there. So an export taken mid-exchange can hold one entry fewer than the listing shows.

The exported bytes are the bytes captured, with the Content-Encoding that describes them still attached — the file stays a faithful record of the wire, and GET /flows/{id}/{leg}/body?decode=1 remains the decoding surface. The export is never paged: a HAR file split across pages is not a HAR file, so the filter is the way to export less.

Bringing one back

POST /flows/import takes a HAR 1.2 document — Trawler's own export, or one any conforming tool wrote — and its entries become flows in the listing, each marked source: "imported". An imported flow is otherwise an ordinary flow: the same GET /flows/{id}, the same body endpoints and their ?decode=1, the same /stream announcement as it lands, and the same ring rules — it evicts by retained bytes like anything else, so a large import can push a live capture out.

RequestAnswer
POST /flows/import + a HAR 1.2 document 200 with { "imported": n } — the count, because a client that posted a 900-entry file needs to know whether all 900 landed. The entries add to the capture; replacing it is a clear followed by an import, not a mode hidden inside a POST
a malformed or hostile document — not JSON, a version other than 1.2, no log.entries, an entry with no request, an unparseable timestamp, an impossible status, a body whose base64 is not base64 400 with a reason, and an entry-level fault names its index. All-or-nothing: the whole document parses before the store is touched, so a refused import changes nothing at all — never a partially-populated capture
log.entries: [] 200 with { "imported": 0 } — a valid document saying nothing was captured, which is not an error; the same reading an empty export has

Three consequences a reader cannot infer from the endpoint signature:

  • Fresh ids, original timestamps. An id is this store's handle and must be unique here, so an imported flow takes a new one; the instant the exchange happened is the captured truth and is preserved, so an imported capture sorts by when it happened, not when it was read. Import the same file twice and you get two independent sets of flows carrying the same instants.
  • A body the file does not carry comes back as an explicit not-captured, never as empty. Trawler's own markers restore the exact state (streamed, too-large with the size it had, read error). A foreign writer's body with no text but a size claiming one existed becomes a not-captured too — calling it empty would assert a 4 MB response was a 204. Only a measured zero is empty.
  • What the format cannot carry is dropped, not invented. The derived and unretained fields — the query string, the parsed-out cookies, the timing phases, the reason phrase, the header-block sizes — are read past in silence, because each was either derived from a header the flow still carries or was never Trawler's to hold. A body's bytes outrank a size that disagrees with them: the ring weighs what it actually holds.

Export delivered by E-EXPORT.W2, import and the source mark by E-EXPORT.W3; the app's own controls follow in the same epic. Both directions live in src/api/har.rs — the parser is defined against the projection it inverts, so the two cannot drift into a format Trawler writes but cannot read — and the exported document's shape is snapshot-locked in tests/api.rs. Round-trip fidelity is proven as a property over generated flows, not by example, and the parser's never-panics claim the same way. The export-selects-what-the-listing-lists guarantee holds by construction (both endpoints build the same filter) and is asserted endpoint-to-endpoint. Why HAR and only HAR, and what a round-trip does and does not preserve: DEC-30; why an imported flow is a first-class flow carrying a mark, and the CORS widening its POST required: DEC-31.
