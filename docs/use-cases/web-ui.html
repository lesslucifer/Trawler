Use Cases — UI surfaces

What a user can do against a running Trawler from a UI, stated as observable contracts. Two surfaces, one API: the zero-setup web shell (UC-3) and the native desktop app (UC-4), plus the native app's guided onboarding to the first captured flow (UC-5).

v3 · 2026-07-15 · Trawler · seeded by E-UISHELL · UC-4 by E-UIFOUND · UC-5 by E-UISETUP

UC-3 — Watch live traffic in the browser, zero setup

With Trawler running, opening GET / on the control API port in a browser serves a self-contained flow-list page straight from the binary — no install, no build step, no configuration, no external assets required for the list to function.

  • The page lists captured flows newest-first (time, method, host, path, status, duration) and updates live as traffic passes the proxy — new flows appear without a manual refresh, driven by the GET /stream SSE events.
  • A filter bar narrows the list by host, method, status and free text with exactly the GET /flows query-parameter semantics — the page delegates filtering to the API rather than reimplementing it.
  • The page is a plain client of the public control API; everything it shows is equally reachable with curl. It renders untrusted capture data (URIs, methods from proxied traffic) as text, never as markup.
  • Shutting Trawler down stays clean even while the page holds its never-ending SSE connection open.

Pinned by ui_shell_serves_live_filterable_flow_list in tests/e2e_capture.rs (page served, filter narrows, SSE event arrives, clean shutdown with the stream open) and the shell contract tests in tests/api.rs. In-browser rendering is covered by a recorded manual check. The shell's minimal chrome is deliberate; the native app (UC-4) is the designed surface.

UC-4 — Watch live traffic in the native app

With Trawler running, launching the native desktop app (E-UIFOUND, Tauri + React) shows the captured flows (method, host, path, status, duration) in the Warp-styled base layout and updates live as new traffic passes the proxy, via the existing GET /stream SSE stream.

  • A filter bar narrows the list by host, method, status and free text — the same GET /flows query-parameter semantics as UC-3, because the app delegates filtering to the API rather than reimplementing it. Status color distinguishes 2xx / 4xx / 5xx at a glance.
  • The app is a pure cross-origin client of 127.0.0.1:7421 — it reaches no core internals; everything it shows is equally reachable with curl. Because the webview origin differs from the API's, every API response carries an open CORS grant (DEC-12); without it the webview's fetch/EventSource would be blocked.
  • The API base URL is configurable (never a hardcoded port in component code): a runtime value wins over a build-time env, which wins over the :7421 dev default — the released app exposes it as configuration.

Pinned by the epic e2e (ui/e2e/specs/flows.spec.ts, cargo xtask ui e2e): WebdriverIO drives the real WebKit window against an ephemeral run(Config) core — empty layout renders, a proxied request appears live, the filter narrows and restores, a second request appends without refresh. Unit + integration layers (Vitest + Testing Library) cover the status-color mapping, the typed client, filter→params, and the layout+list against a mock API. Existing API contracts (GET /flows, GET /stream) are consumed unchanged; the CORS grant is the one API-response addition. UC-3 (web shell) stays valid — both surfaces are clients of the same API.

UC-5 — Onboard a fresh machine to the first captured flow

On a machine that can't yet decrypt HTTPS, the native app opens a three-step guided setup — Trust the CA · Set the proxy · Verify — instead of the flow list. Its rule (E-UISETUP): do the work for the user in the common case, tell the truth in every case, and prove success only by real capture.

  • Least manual work. On macOS/Windows each step offers one native action (install the CA, set the system proxy — both elevation-gated); the per-OS manual steps sit behind a "Set it up manually" disclosure that auto-opens if the action fails. Other OSes show the manual steps inline. Instructions are always plain text, never markup.
  • Two-truths status per step (never the stepper cursor — a step is never ✓ just because you clicked past it). Each step's honest status comes from either of two independent signals:
    • a fast local probe — does this machine trust the CA / route its system proxy to Trawler? (the ~90% single-machine case; instant, read-only OS queries), or
    • observed traffic — has anything actually reached Trawler, from any device?
    When the probe can't conclude (un-probeable OS, or a remote device) the wording says so and points at capture — it never shows a false "not set up".
  • The proxy step goes green on any connection, decrypt or not. An HTTPS attempt from a client that doesn't trust the CA fails its TLS handshake and produces no flow — so the core counts the tunnel itself: GET /stats returns a monotonic connections tally and a connection SSE event fires. That proves "traffic is routing through Trawler" even before decryption works. Traffic seen but not decrypting ⇒ the Trust step says "install the certificate on the device you're capturing from".
  • Only a decrypted flow reveals the list. A probe-green step or a bare connection never ends onboarding — the payoff (Verify → flow list) fires solely on the first https:// flow (a decrypted request the MITM rewrote to absolute form). The Verify step shows a concrete prove-it: open any site, or run a copyable curl -x http://<addr> https://example.com with the real proxy address. Capture, once proven, latches (the status dot re-invokes setup on demand; "Back to flows" returns).
flowchart TD
  E["Enter setup (no decrypted flow yet)"] --> PR["Probe this machine: CA trusted? proxy set?"]
  PR --> ST["Trust and Proxy steps show local status instantly"]
  E --> W["Watch traffic: GET /stats + connection and flow SSE events"]
  W --> C{"What arrived?"}
  C -- "any connection" --> PX["Proxy step green: receiving traffic"]
  C -- "http flow, no https" --> TR["Trust: not decrypting, install the CA on the sending device"]
  C -- "https flow (decrypted)" --> OK["Trust green + Verify green: reveal the flow list"]
Probes light the steps instantly for the local case; observed traffic confirms — and, for a remote device, is the only thing that can. The list reveal is decrypted-flow-only.

New API surface (consumed by onboarding, usable by any client): GET /stats → { connections } and the connection SSE event ({ authority }) on the existing /stream. The connection tally is a monotonic counter in the store, bumped when the proxy opens a CONNECT tunnel — kept outside the flow ring so eviction never touches it. The two local probes (CA-in-trust-store, system-proxy-address) live in the Tauri app, not the core; they read the real machine so they are not hermetically testable (the status derivation they feed is fully unit-tested). This deliberately supersedes two earlier "prove by capture only" stances (no trust-store inspection / no OS self-test): the probe covers the 90% for instant honest feedback; capture stays the authority for the remote cases and the sole thing that reveals the list. Pinned by tests/e2e_capture.rs::untrusted_https_records_a_connection_not_a_flow (a failed handshake bumps /stats + emits connection, records no flow), the status derivation + probe-parser unit tests, and the UC-5 e2e spine.
