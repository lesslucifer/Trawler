Use Cases — UI surfaces

What a user can do against a running Trawler from a UI, stated as observable contracts. Two surfaces, one API: the zero-setup web shell (UC-3) and the native desktop app (UC-4 watch · UC-5 inspect).

v3 · 2026-07-13 · Trawler · seeded by E-UISHELL · UC-4 by E-UIFOUND · UC-5 by E-UIINSPECT

UC-3 — Watch live traffic in the browser, zero setup

With Trawler running, opening GET / on the control API port in a browser serves a self-contained flow-list page straight from the binary — no install, no build step, no configuration, no external assets required for the list to function.

  • The page lists captured flows newest-first (time, method, host, path, status, duration) and updates live as traffic passes the proxy — new flows appear without a manual refresh, driven by the GET /stream SSE events.
  • A filter bar narrows the list by host, method, status and free text with exactly the GET /flows query-parameter semantics — the page delegates filtering to the API rather than reimplementing it.
  • The page is a plain client of the public control API; everything it shows is equally reachable with curl. It renders untrusted capture data (URIs, methods from proxied traffic) as text, never as markup.
  • Shutting Trawler down stays clean even while the page holds its never-ending SSE connection open.

Pinned by ui_shell_serves_live_filterable_flow_list in tests/e2e_capture.rs (page served, filter narrows, SSE event arrives, clean shutdown with the stream open) and the shell contract tests in tests/api.rs. In-browser rendering is covered by a recorded manual check. The shell's minimal chrome is deliberate; the native app (UC-4) is the designed surface.

UC-4 — Watch live traffic in the native app

With Trawler running, launching the native desktop app (E-UIFOUND, Tauri + React) shows the captured flows (method, host, path, status, duration) in the Warp-styled base layout and updates live as new traffic passes the proxy, via the existing GET /stream SSE stream.

  • A filter bar narrows the list by host, method, status and free text — the same GET /flows query-parameter semantics as UC-3, because the app delegates filtering to the API rather than reimplementing it. Status color distinguishes 2xx / 4xx / 5xx at a glance.
  • The app is a pure cross-origin client of 127.0.0.1:7421 — it reaches no core internals; everything it shows is equally reachable with curl. Because the webview origin differs from the API's, every API response carries an open CORS grant (DEC-12); without it the webview's fetch/EventSource would be blocked.
  • The API base URL is configurable (never a hardcoded port in component code): a runtime value wins over a build-time env, which wins over the :7421 dev default — the released app exposes it as configuration.

Pinned by the epic e2e (ui/e2e/specs/flows.spec.ts, cargo xtask ui e2e): WebdriverIO drives the real WebKit window against an ephemeral run(Config) core — empty layout renders, a proxied request appears live, the filter narrows and restores, a second request appends without refresh. Unit + integration layers (Vitest + Testing Library) cover the status-color mapping, the typed client, filter→params, and the layout+list against a mock API. Existing API contracts (GET /flows, GET /stream) are consumed unchanged; the CORS grant is the one API-response addition. UC-3 (web shell) stays valid — both surfaces are clients of the same API.

UC-5 — Inspect a captured flow in the native app

Clicking a flow row in the native app (E-UIINSPECT) opens the detail panel over GET /flows/{id} — request line, status with the 2xx/4xx/5xx functional color, total duration, per-leg HTTP versions, and the full request + response header tables. No new endpoint; the panel is a pure client of the existing API.

  • Bodies render by content type over GET /flows/{id}/{leg}/body: JSON as a collapsible tree, XML/HTML as (pretty-printed) text, image/* as the image, form-urlencoded as a decoded key/value table, other text as text, anything else as a hex dump. A raw / decoded toggle switches between the stored bytes (?decode=0, sniffed to text or hex) and the server-decoded rendering (?decode=1). Oversize renderings are bounded — hex and the JSON tree cap and fall back rather than hang the window.
  • States are never blank: an empty, streaming-passthrough, too-large, read-error, or not-yet-responded body shows an explicit notice instead of a viewer.
  • Copy-as-curl reproduces the request (method, URL, headers, body, shell-quoted); copy body puts the shown body on the clipboard (the hex dump for hex-rendered bodies; hidden for images); save body writes the shown leg's bytes to a file via the OS save dialog, with a filename derived from the flow id, leg, and content type.
  • The ?decode=1 contract is server-side — gzip/deflate/brotli reversal, charset→UTF-8, JSON + XML pretty-printing — so curl and the web shell gain the same decoded view the app shows.

Pinned by the epic e2e (ui/e2e/specs/flows.spec.ts): row click → headers / timing / versions; a JSON response renders as a tree; the raw toggle shows the stored bytes as text; the curl text is asserted in the DOM (WebDriver clipboard is unreliable — the real clipboard write is a recorded manual check, as is the native save dialog); a brotli-compressed JSON body still renders as a tree — the decode chain proven through the UI; a proxied PNG renders as an image. The decode chain itself is pinned at the API seam in tests/api.rs and the src/api/decode.rs unit suite; viewer dispatch, states, and copy/save are covered by the Vitest unit + integration layers. scripts/seed-proxy.mjs seeds one flow per case for manual checks.
