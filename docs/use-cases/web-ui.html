Use Cases — UI surfaces

What a user can do against a running Trawler from a UI, stated as observable contracts. Two surfaces, one API: the zero-setup web shell (UC-3) and the native desktop app (UC-4 watch · UC-5 inspect), plus the native app's setup screen for capturing this machine or another device (UC-ONBOARD), the HAR round trip — taking a capture out and bringing one back (UC-6) — clearing the capture (UC-7), and sending a request again, edited or from scratch (UC-8).

UC-3 — Watch live traffic in the browser, zero setup

With Trawler running, opening GET / on the control API port in a browser serves a self-contained flow-list page straight from the binary — no install, no build step, no configuration, no external assets required for the list to function.

  • The page lists captured flows newest-first (time, method, host, path, status, duration) and updates live as traffic passes the proxy — new flows appear without a manual refresh, driven by the GET /stream SSE events.
  • A filter bar narrows the list by host, method, status and free text with exactly the GET /flows query-parameter semantics — the page delegates filtering to the API rather than reimplementing it.
  • The page is a plain client of the public control API; everything it shows is equally reachable with curl. It renders untrusted capture data (URIs, methods from proxied traffic) as text, never as markup.
  • Shutting Trawler down stays clean even while the page holds its never-ending SSE connection open.

Pinned by ui_shell_serves_live_filterable_flow_list in tests/e2e_capture.rs (page served, filter narrows, SSE event arrives, clean shutdown with the stream open) and the shell contract tests in tests/api.rs. In-browser rendering is covered by a recorded manual check. The shell's minimal chrome is deliberate; the native app (UC-4) is the designed surface.

UC-4 — Watch live traffic in the native app

With Trawler running, launching the native desktop app (E-UIFOUND, Tauri + React) shows the captured flows (method, host, path, status, duration) in the Warp-styled base layout and updates live as new traffic passes the proxy, via the existing GET /stream SSE stream.

  • A filter bar narrows the list by host, method, status and free text — the same GET /flows query-parameter semantics as UC-3, because the app delegates filtering to the API rather than reimplementing it. Status color distinguishes 2xx / 4xx / 5xx at a glance. The two keys the API matches exactly are chosen, not typed: method from the closed set of verbs, host from the hosts capture has seen, each with an "any" option that clears it. Free text and status stay typed — the API substring-matches the first, and reads the second at either resolution: status=404 is the exact code and status=4xx the class, with anything that names neither refused as a stated 400 rather than an empty list (E-RFINISH). The status control takes either resolution and says so in its placeholder — status — 404 or 4xx — and a refusal is rendered rather than swallowed (below).
  • The app is a pure cross-origin client of 127.0.0.1:7421 — it reaches no core internals; everything it shows is equally reachable with curl. Because the webview origin differs from the API's, every API response carries an open CORS grant (DEC-12); without it the webview's fetch/EventSource would be blocked.
  • The API base URL is configurable (never a hardcoded port in component code): a runtime value wins over a build-time env, which wins over the :7421 dev default — the released app exposes it as configuration.

Six capabilities the redesign (E-REDESIGN W2/W4, designed at the flow-list design run — archived) made observable. The contract keeps its shape — these are things a user can now do or perceive that they could not before:

Three further capabilities came from E-RFINISH W5/W6, designed at the shell and flow-list second pass (archived). The first two are the same underlying change: a failed fetch was discarded three times over, so the screen could not tell an unreachable API from a quiet proxy.

GainWhy it is a contract change and not a restyle

It appears with the user doing nothing: the dropped SSE stream is the signal, so a core that dies under an idle window is stated rather than waiting for the next keystroke. It is not the connection statement and never appears alongside it: the API answering and saying no is a different fact from the API not answering. Typing a letter in the status box previously stalled the list with no explanation — the one state on this screen the user's own keystroke caused.

The width and the window are one decision: a wider pane alone makes the screen worse at the size the app opens at.

One rule is knowingly unmet, and now bounded. The host and path cells truncate rather than wrap, because a virtualized fixed-height row cannot both wrap and stay one line. The full value stays reachable — the path on the row's title, both in the detail pane's URI — and the cut is visible as an ellipsis. Those are the three conditions DEC-34 now sets on the escape: the rulebook clause the design run escalated was written at the epic close, and the rule's Tier-1 red is unchanged.

The capture-management controls

The flow list is where UC-6 and UC-7 reach a person rather than only a client (E-EXPORT W6, built from the capture-controls design run). These are the first controls in the app that change server state. Export and import sit behind a ⋮ trigger at the header's trailing edge; clear is the ⌫ shortcut beside it. Both sit past the filters that scope them. Beside them a fixed-width slot reads the count those filters selected, and reads exporting… or importing… while a transfer runs — the same box either way, so starting one moves nothing else in the row. A turning ring joins the in-flight line, and a second one turns inside the menu in place of the running act's own face: reopening the menu mid-transfer is the one way to ask why an act is withheld, so the answer is there and not only in the header.

Each act wears a face, and none of them is minted for the menu: ↓ is the save glyph the app already spends on writing something out, ↑ and ↗ are the very marks an imported and a sent row carry in the list below, and ⌫ is the erase the clear act is. The box holding them is drawn whether or not it is filled, so every label hangs off one left edge, and none of the faces reaches the accessible name — the label is what the act is called.

ActWhat a user gets

The curl target is what opens focused and what the primary button acts on, so the words lead with it too — the title names the command before the .har file, and the target states its own act instead of opening on an …or that made the one thing the ask is mainly for read as an aside. Choosing a file stays one muted button beside it. A refusal is the server's own sentence (DEC-39), shown verbatim under the text that caused it, with the text left in place to edit. While the import runs the ask says so on its own surface — a ring beside importing… — and holds the command read-only rather than disabled: that target is what the ask opened focused on, and disabling it would drop focus to <body>, outside the dialog, taking Esc with it. By default it opens a modal ask titled with that count, whose initial focus is on the answer that does nothing — the act behind it cannot be undone. The consequence carries the only alarm on the screen; the button carries none. A checked don't show this again is persisted only when clear is confirmed. Later clicks clear the live filter immediately, with no ask; cancelling never changes the preference. With no ask open there is no dialog to carry a refusal, so a clear the store rejects states its reason beside the control instead — the same header slot an export failure uses, and each names the act it came from.

Two things the list itself gained. An imported row carries a ↑ mark in its time cell, with its own accessible name, so a capture someone handed you is tellable from live traffic without a column of its own (DEC-38). A sent row carries ↗, named sent, in the same reserved box (UC-8). And a cleared list gets a third absence of its own — "capture cleared", with the same remedy the never-captured one gives, because after a clear the remedy genuinely is the same and the heading is what says which nothing this is.

Every one of the three refills the list from the event bus, never from its own response: the responses carry counts, not rows, and two sources of truth for one list is a race. The cleared event exists for exactly this.

Pinned by the epic e2e (ui/e2e/specs/flows.spec.ts, cargo xtask ui e2e): WebdriverIO drives the real WebKit window against an ephemeral run(Config) core — empty layout renders, a proxied request appears live carrying every column, the status pill carries its reason phrase, the filter narrows and restores, an unmatched filter states its own absence, the keyboard alone selects a row and opens its detail, and a second request appends without refresh. Three assertions came with the second pass: a status class narrows the list to that class while 2xx and 5xx traffic is present and an exact code still narrows to the code; the core is killed under the open window and the band appears above rows whose count is unchanged; and its control — a reachable core whose filter matches nothing — renders the absence instead, which is what proves the two screens differ. Unit + integration layers (Vitest + Testing Library) cover the status-color mapping, the typed client, filter→params, and the layout+list against a mock API. Existing API contracts (GET /flows, GET /stream) are consumed unchanged; the CORS grant is the one API-response addition. UC-3 (web shell) stays valid — both surfaces are clients of the same API.

UC-3 · UC-4 — the listing pages, opt-in

Both surfaces read one listing contract, and it is bounded only when a client asks:

RequestAnswer
GET /flows, with or without filters the whole filtered capture, newest-first, as a bare JSON array — unbounded, and unchanged by paging's arrival
GET /flows?limit=n an envelope: at most n rows plus the next_cursor that continues the walk, null once the walk reaches the oldest row the ring still holds
GET /flows?source=captured · ?source=imported · ?source=sent only that provenance. Every row carries its source, because the ring now holds flows the proxy never saw (UC-6, UC-8) and a listing that mixes a live capture with a colleague's file, or with requests Trawler sent itself, has to say which is which. Every row also carries seed: the flow a sent one was replayed from, null otherwise
a limit that is not a positive integer · a cursor that is not a flow id · a cursor with no limit · a source that is none of the three refused 400 with a reason naming the parameter — never an unbounded read a client did not ask for, and never a silently empty listing that reads like "nothing matched"
  • The cursor names a row, not an offset — the id of the page's last row, resolved against the ring's order. So a flow captured mid-walk lands newer than the cursor and is never served twice (a client watching live gets it on GET /stream; a paged read is a read of the past), and eviction of rows the walk has not reached yet simply shortens it. Paging composes with every filter and re-slices the same listing rather than defining a second one.
  • A cursor the ring no longer holds ends the walk — an empty, final page, whether the row was evicted under memory pressure or deleted (UC-7): the walk cannot resume from a row that is gone, and the cause does not change the answer. It never restarts at the newest row, which would re-serve every row the client already holds.

Delivered by E-EXPORT.W1. Pinned by the paging tests in tests/api.rs (the unparameterised summary row's field set is locked; a cursor walk yields exactly the unpaged listing, filtered and unfiltered; each refusal) and by Store::page's unit and property tests in src/store.rs — the no-duplicate/no-skip invariant is proven over interleaved inserts, evictions and page reads, not by example. Neither surface pages today: both read the unparameterised listing, which is why the contract had to stay additive.

UC-5 — Inspect a captured flow in the native app

Clicking a flow row in the native app (E-UIINSPECT, rebuilt by E-REDESIGN) opens the detail panel over GET /flows/{id} — a pinned identity row (verb, status with the 2xx/4xx/5xx functional color and its reason phrase, the leg selector, total duration, close), then the flow line (the full URI, both HTTP versions, copy-as-curl), then the selected leg's Headers and Body. No new endpoint; the panel is a pure client of the existing API.

  • One leg at a time, under one selector (DEC-31): the identity row's request | response switch governs both the header table and the body pane together; the URI, versions and curl are the flow's and never move. The panel always opens on request. A leg that sent no headers says none — this leg sent no headers and stays selectable; a flow still being fetched shows loading this flow… and nothing else.
  • Every wire value is a copy target: headers render in wire order with duplicate names preserved, and clicking a header value — or the URI — copies exactly that value, confirming at the value for ~2 s; drag-selecting still selects.
  • The body is the main zone and the panel never scrolls as a whole (DEC-32): the headers take their natural height up to about a third of the panel and scroll inside it, the heading naming how many there are; the body takes the rest and scrolls inside itself. A header value taller than three lines — a cookie, a token, a policy — is clamped with more / less under its name: lines are hidden, never characters, the value still copies whole, and one act shows all of it. How much a clamped value shows before that act is the panel's width, and the width is a chosen number: 520 px, with the app's default window at 1440 to pay for it (DEC-36, E-RFINISH) — about 168 characters of a 900-character cookie instead of about 108.
  • Esc dismisses the panel, as does ✕, and focus returns to the list that opened it, so a keyboard user lands back on the row they came from.
  • replay sits in the flow line beside copy-as-curl: both send this request again, one elsewhere and one here. It turns the pane into the composer with a draft seeded from this flow (UC-8), and the list stays beside it.
  • Bodies render by content type over GET /flows/{id}/{leg}/body: JSON and XML/HTML as their pretty-printed source in a navigable, foldable surface, image/* as the image over a transparency checkerboard, form-urlencoded as decoded key/value rows (each value individually copyable), other text as text, anything else as a toned hex dump.
  • Raw shows the source, not the compression frames: the raw / pretty toggle switches between the bytes the server sent (?decode=source — transport encoding reversed, nothing re-indented or transcoded) and the fully rendered view (?decode=1 — decompressed, charset-normalised, JSON/XML pretty-printed). A gzipped JSON body therefore reads as its minified source in raw rather than as a hex dump of gzip frames, and hex is reserved for payloads that genuinely have no text form. The stored bytes stay reachable at ?decode=0.
  • A truncated body says so: renderings are capped (128 KiB of characters, 4 KiB of hex) and a capped body states "showing N of M — save to see all" in warn tone, naming the size shown, the real total, and the way to the rest. No cap is silent, and no body is re-indented client-side — what is shown is what crossed the wire, so a copy is evidence.
  • States are never blank: an empty, streaming-passthrough, too-large, read-error, not-yet-responded, in-flight or failed-to-load body shows an explicit notice instead of a viewer — one distinct sentence per cause, and warn tone only on the one that is a fault.
  • Copy-as-curl reproduces the request (method, URL, headers, body, shell-quoted) from a labelled button beside the URI; the command itself is never rendered, and the button reads copied for ~2 s before reverting; copy body puts the shown body on the clipboard (the hex dump for hex-rendered bodies; hidden for images); save body writes the shown leg's bytes to a file via the OS save dialog, named after the endpoint — the URI's last path segment, or the host when the path names nothing — plus the leg and the extension the served content type implies (charges-response.json, example.com-response.html), so a saved body is recognisable in a downloads folder and opens in the right application.
  • The ?decode=1 contract is server-side — gzip/deflate/brotli reversal, charset→UTF-8, JSON + XML pretty-printing — so curl and the web shell gain the same pretty view the app shows.

Pinned by the inspector e2e (ui/e2e/specs/flows.spec.ts): row click → the request leg's headers / timing / versions; the leg selector switches headers and body together while the flow line stays; under a wall of long headers the window gains no scroll, the body zone is the taller of the two and stays on screen, and a clamped header value expands on more; a JSON response renders as copy-exact source; the raw toggle shows the served source as text; copy-as-curl's payload is read back from a recording clipboard stub installed through WebDriver (the OS clipboard itself cannot be read there — the real write, like the native save dialog, stays a recorded manual check); Esc closes the panel; a brotli-compressed JSON body still renders decoded — the decode chain proven through the UI; a proxied PNG renders as an image; an XML body renders as XML rather than falling through to text; a brotli body in raw shows its minified source rather than a hex dump of its frames; and a body past the render cap states its truncation. The decode chain itself is pinned at the API seam in tests/api.rs and the src/api/decode.rs unit suite; viewer dispatch, states, and copy/save are covered by the Vitest unit + integration layers. scripts/seed-proxy.mjs seeds one flow per case for manual checks.

UC-ONBOARD — Set up capture, for this machine or another device

With nothing decrypted yet, the native app opens Set up capture instead of the flow list. The user names which device's traffic they want to see — and that answer is the screen's only axis: every instruction, every task and every state below it belongs to that platform. Its rule (E-UISETUP, rebuilt by E-ONBOARD): do the work for the user in the common case, tell the truth in every case, and prove success only by real capture.

No promise narrowed in the rebuild. The probes still answer for this machine and nothing else; a decrypted flow is still the only thing that moves setup to the list on its own (DEC-61: the user can switch at any time); the certificate save still reports what actually happened; the quit dialog is untouched. DEC-33's two layers and DEC-13's one-confirm-per-host-change rule are both kept, and both are re-asserted by test. What changed is who the sentences are written for.

When setup shows: only while capture is unproven for the device being set up now (E-ONBREV). Every opening starts a setup session at the moment it opened (DEC-60).

Reach beyond loopback is an authorization act, not a setting (DEC-55). Trawler binds loopback only until the user allows one named interface, through one explicit confirm the shell raises; the loopback pair is never touched, arming adds a second proxy and control API, and nothing is persisted — the exposure dies with the process that confirmed it. For the five platforms that need it, this is task 1, and until it is done the tasks that depend on it are dimmed rather than given steps that cannot work. The task names the address it will arm before it is armed, even when there is only one, and its button and warning name that address's interface. With no reachable address, it says to join the network the device is on and offers a re-read. The CORS grant does not widen with the bind; the opt-in is this contract's whole authorization boundary.

Two layers of status, never blended, and never a stepper cursor — a task is never ✓ because the user clicked past it (DEC-33). A task's number is a reading order; its state is a reading something took.

Each task has one reading: a probe that concludes, else this session's traffic. A decrypted request settles the certificate task, and any request that reached Trawler settles the route task. This machine's route is the exception: its try-it command names the proxy itself, so only its probe may settle it. Where a probe can't conclude, the wording says so and points at the traffic task — never a false "not set up". The dated row and its re-read show only on a host where a probe can answer. A phone that trusts the certificate and points here reads as two true facts side by side: not trusted on this machine, and capturing traffic.

One act on this machine, one password prompt. Where the host can do the work (macOS, Windows), installing the certificate and setting the system proxy are a single elevated action — one prompt, not two — and the two single commands survive as the manual route beneath it. An action follows its task's reading. The one act is offered only while both halves read undone. Once either reads done, each task carries its own: "Set the system proxy" with its steps, or the certificate's steps. There is no install-only button and no command behind one. A task read done offers no action and keeps only its undo. A refused authorization is the user's own outcome, worded as one, with the tool's text under a disclosure; a real failure keeps the OS's words and opens the manual route.

UC-6 — Take the capture out as a HAR file, and bring one back

GET /flows/export answers with the currently filtered capture as a single HAR 1.2 document — the interchange format the tools in this space already read — served as application/json with a Content-Disposition naming a .har file, so a browser or the native app saves it under a timestamped name.

RequestAnswer
GET /flows/export every captured exchange as a log.entries element — method, URL, both HTTP versions, headers (order and duplicates preserved), query string, cookies, status and reason, the time it was captured, its duration and a timings block, and its bodies
GET /flows/export?host=…&method=…&status=…&content_type=…&q=… the same document over the filtered set: the export selects exactly what the listing with those parameters lists, in the same order — the same filter, not a second implementation of it
an empty capture, or a filter matching nothing 200 with log.entries: [] — a valid, empty HAR file, not a 404: the client asked what is captured and the answer is "nothing"

Two consequences a reader cannot infer from the endpoint signature:

  • A body Trawler never captured is marked as such, never exported as empty. A streamed body, one skipped for being too large, and one lost to a read error each appear as a body with no text and a comment naming the reason — so a 4 MB event stream is never indistinguishable from a 204. A too-large body additionally reports the size it had, because that size is known and is exactly why the bytes were dropped. Only a genuinely empty body is a measured zero. Every other fact Trawler does not hold — the raw header-block sizes, the wire reason phrase, a cookie's optional attributes — is HAR's own "unavailable" sentinel rather than an invented value. The timings are the one place HAR forbids that sentinel: an exchange whose duration was never measured reports an unknown total with its phases zeroed, because a negative phase is a value no reader accepts.
  • A flow still awaiting its response is omitted from the file, because HAR requires a response on every entry and there is nothing truthful to put there. So an export taken mid-exchange can hold one entry fewer than the listing shows.

The exported bytes are the bytes captured, with the Content-Encoding that describes them still attached — the file stays a faithful record of the wire, and GET /flows/{id}/{leg}/body?decode=1 remains the decoding surface. The export is never paged: a HAR file split across pages is not a HAR file, so the filter is the way to export less.

Bringing one back

POST /flows/import takes a HAR 1.2 document — Trawler's own export, or one any conforming tool wrote — and its entries become flows in the listing, each marked source: "imported". An imported flow is otherwise an ordinary flow: the same GET /flows/{id}, the same body endpoints and their ?decode=1, the same /stream announcement as it lands, and the same ring rules — it evicts by retained bytes like anything else, so a large import can push a live capture out.

RequestAnswer
POST /flows/import + a HAR 1.2 document 200 with { "imported": n } — the count, because a client that posted a 900-entry file needs to know whether all 900 landed. The entries add to the capture; replacing it is a clear followed by an import, not a mode hidden inside a POST
a malformed or hostile document — not JSON, a version other than 1.2, no log.entries, an entry with no request, an unparseable timestamp, an impossible status, a body whose base64 is not base64 400 with a reason, and an entry-level fault names its index. All-or-nothing: the whole document parses before the store is touched, so a refused import changes nothing at all — never a partially-populated capture
log.entries: [] 200 with { "imported": 0 } — a valid document saying nothing was captured, which is not an error; the same reading an empty export has

Three consequences a reader cannot infer from the endpoint signature:

  • Fresh ids, original timestamps. An id is this store's handle and must be unique here, so an imported flow takes a new one; the instant the exchange happened is the captured truth and is preserved, so an imported capture sorts by when it happened, not when it was read. Import the same file twice and you get two independent sets of flows carrying the same instants.
  • A body the file does not carry comes back as an explicit not-captured, never as empty. Trawler's own markers restore the exact state (streamed, too-large with the size it had, read error). A foreign writer's body with no text but a size claiming one existed becomes a not-captured too — calling it empty would assert a 4 MB response was a 204. Only a measured zero is empty.
  • What the format cannot carry is dropped, not invented. The derived and unretained fields — the query string, the parsed-out cookies, the timing phases, the reason phrase, the header-block sizes — are read past in silence, because each was either derived from a header the flow still carries or was never Trawler's to hold. A body's bytes outrank a size that disagrees with them: the ring weighs what it actually holds.

A single request, pasted

It becomes one request-only flow: method, URL, headers and body as the command states them, source: "imported", no response and no duration, because nothing was sent — the shape a captured flow already has between its request and its reply, so every reading endpoint and the app's row already know how to show it.

UC-7 — Clear the capture

A debugging session accumulates noise, and reproducing a bug against a clean listing is the reason the ring needed a third door. DELETE /flows removes what the listing filters select and DELETE /flows/{id} removes exactly one — and every live subscriber learns of it on /stream, so an interface never discovers a clear by refetching.

RequestAnswer
DELETE /flows 200 with { "removed": n } — the whole capture is gone, with no row kept back. The count is the same envelope the import answers with, so both mutating endpoints report what they did
DELETE /flows?host=…&method=…&status=…&content_type=…&q=…&source=… only the matching rows leave: a delete selects exactly what the listing with those parameters lists — the same filter as the listing and the export, not a third implementation. Every survivor stays whole: still listed, still readable at GET /flows/{id} and at both body endpoints
a filter matching nothing 200 with { "removed": 0 } — the request expresses an end state and that state is already true. An unrecognised source= is the exception: 400 with a reason, because a destructive request must never act on a set the caller did not name
DELETE /flows/{id} 200 with { "removed": 1 }; 404 when that id is not in the ring — the one delete that 404s, because here the client named something specific that does not exist — and 400 when the id is not a flow id

Three consequences a reader cannot infer from the endpoint signature:

  • A cleared store is empty, not restarted. The connection tally GET /stats reports is untouched by any delete, and the proxy keeps running: the tally is a monotonic "traffic reached us" measure, not storage. Clearing the capture is not a way to reset the session.
  • The clear arrives as one event for the whole batch — event: cleared carrying every id that left — not one event per flow, so emptying a full ring cannot lag a subscriber past the stream's buffer and drop it into the lagged gap. It is a distinct event from the ring's own evicted: an interface that conflated them would announce "capture cleared" every time memory pressure dropped a row.
  • Removing is not replacing. Loading someone else's capture over your own is a delete followed by an import — two operations the client already has — rather than a destructive mode hidden inside the POST.
  • A delete can end another client's paging walk. If the removed row was the cursor some client is paging from, that client's next page is empty and final — the same answer eviction has always given, because the walk cannot resume from a row that is gone and the cause does not change the answer (the listing contract).

Delivered by E-EXPORT.W4; the app's own clear control — the modal ask, and the absence a cleared list lands on — is UC-4's capture-management controls (E-EXPORT.W6). The API half is the whole contract above: both routes converge on one Store removal, which shares its unlinking with eviction so the ring's byte accounting cannot differ between the two — the invariant is asserted as a property over arbitrary sequences of inserts, imports, evictions and removals. Why the mutating methods widened the CORS grant without reversing the read-only reasoning behind it: DEC-38.

UC-8 — Send a request again, edited or from scratch

A developer who sees what their client sent can ask what would happen had it sent something else, and the answer is captured like everything else. Trawler sends the request itself, and the exchange lands as an ordinary flow marked source: "sent": the same ring and eviction, the same GET /flows/{id} and body endpoints, announced on /stream as request then response, and selectable by ?source=sent. Replay and compose use one sender, so the only difference is where the starting values come from.

RequestAnswer
POST /flows/{id}/replay + { "method"?, "url"?, "headers"?, "body"? | "body_base64"? }, or no body at all 201, Location: /flows/<new>, and the new flow, with seed naming {id}. An absent field is the seed's own value. A given headers list replaces the seed's list whole. body is text, body_base64 is bytes, and "" is an empty body
POST /flows + { "method", "url", "headers"?, "body"? | "body_base64"? } the same 201, with seed: null
a malformed request: not JSON, an unknown field, a missing method or url, a URL that is not absolute http(s) or that carries user:pass@ (credentials travel as an Authorization header, never inside the URL), a method that is not a token, a header the wire cannot carry, body and body_base64 both 400 with a one-sentence reason naming the field, and nothing sent
a replay of a seed that cannot be sent as it stands: its request body was never captured (streamed, too large, read error), or its URL is not absolute or carries credentials, and the caller gave none 422 naming the absence (the seed's request body was not captured (too_large); give a body to replace it). A missing body is never sent as an empty one. A seed the ring no longer holds is a 404
the upstream refused, could not be resolved, failed TLS verification, or sent no reply head within 30 s 502 / 504 with the reason in words, and no flow lands: a flow asserts that an exchange happened, and none did

Three consequences a reader cannot infer from the endpoint signature:

  • The call answers when the reply exists. The flow lands complete, never as a pending row. It carries the versions actually negotiated (HTTP/2.0 against an h2 upstream), and its bodies obey the capture cap: an over-cap reply is not_captured / too_large. TLS is verified exactly as the proxy verifies an upstream.
  • Some headers follow the request, not the list. Content-Length is the body's. Host follows the URL unless the caller wrote one: a seed's own Host is not the caller's. Connection headers are the client's to set, and several Cookie headers are joined, as the proxy does.
  • The seed link can dangle. Once the ring evicts the seed, its id 404s while the sent flow still names it. The link records where the request came from, not a flow the ring keeps alive.

It is opened by replay in the inspector (UC-5) or new request in the capture menu (UC-4). Three zones: the identity (method, URL, where the draft came from), the request (headers, then the body), and the send zone pinned at the bottom.
