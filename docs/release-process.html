Release process

How a version becomes a published release: numbering, notes, the tag, what the owner ticks when publishing, the final's cut, and rollback.

v1 · 2026-11-06 · Trawler · T1 process · written by E-PRORELEASE.W7 · mechanism and its why: DEC-86 · update channel: DEC-82 · hand checks: matrix

The flow

Every arrow into a tag is a new version; nothing published is ever replaced.

Version policy

Change since the last finalNext finalIts rcs
fixes onlypatch: 0.1.0 → 0.1.10.1.1-1, 0.1.1-2, …
any feature or behaviour change (breaking included while 0.x)minor: 0.1.x → 0.2.00.2.0-1, …
1.0.0owner decision—
  • One version for the workspace (Cargo.toml, Cargo.lock, ui/package.json; cargo xtask package refuses drift). Numeric rcs only, numbered from 1: ‹final›-N, never rc.N (DEC-86 rule 7).
  • A version is used once: a red run, a bad draft or a bad release takes the next number. A pushed tag is never moved or deleted.
  • Every final is preceded by an rc of the same final whose matrix passed.

Installed apps read releases/latest/download/latest.json; GitHub's latest skips drafts and pre-releases. The workflow never ticks anything (DEC-86 rule 6).

From the last rc to the final (0.1.0)

A final is not a promotion of the rc's files: it is a new tag v0.1.0 and a fresh build of a gated commit whose version is 0.1.0. The rc's draft, assets and tag stay as they are.

  • Never move, delete or re-push v0.1.0 or an rc tag; a red run or bad draft of v0.1.0 burns the number: the next final is 0.1.1, after its own rc (Version policy, Rollback).
  • Never reuse an rc number or re-cut 0.1.0-N with new code: a fix is 0.1.0-N+1 and its own matrix pass.
  • Never upload the rc's installers or edit its latest.json into the final.

Rollback

FoundDoNever
a red run or a bad draftdelete the draft (or leave it: a re-run replaces it); fix; next numbermove or delete the tag
a bad published releasegh release edit v‹bad› --draft: the channel falls back to the previous release; then fix forward with the next version, published as latestreplace an asset (the .sig, latest.json and SHA256SUMS bind them); reuse the number
installs already on the bad versionthey stay on it until the fix-forward release, which the updater offers themexpect a downgrade: the updater only offers a newer version (DEC-82)
