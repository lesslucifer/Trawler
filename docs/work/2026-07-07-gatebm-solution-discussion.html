E-GATEBM — solution discussion

The back-merge false-positive is one instance of a general question the epic-gate seam walk cannot yet answer: is this merge net-new work to gate, or already-gated history being integrated? This doc generalizes the problem across every merge direction the workflow can produce, and recommends a discriminator.

Decision (owner, 2026-07-07). Go with #2 — target-reachability (skip a seam when its merged-in parent is already on main). Additionally, add R5 — a walk-error waiver valve: any walk failure is suppressable by a recorded, per-seam entry in the tip's cr/v2 review note, so a walk misfire is overridden surgically and on the record — never with --no-verify, which skips every gate. TL;DR

The reported bug (a stale epic back-merging main is flagged as an ungated WU seam) is not a special case of main. It is the seam walk failing to recognise any integration of already-gated history. The walk's job — for every merge on the epic's first-parent chain — is a two-way classification: net-new ungated work → gate vs already-gated history being merged in → skip. Today it only recognises one narrow shape of the second class.

Recommendation: skip a seam when its merged-in parent is already reachable from the gate target (merge-base --is-ancestor wu_tip target). This provably fixes the reported case, provably preserves the real WU-seam gate, and covers every back-merge of landed history. Cross-epic integration of unlanded siblings is deliberately out of scope — the workflow answer is to serialize through main.
This already happened on main, silently. Epic E-NMWF was gated green at tip 7523de7 (it carries the full dod/v1 epic receipt + test/cr/doc/mr notes). It then back-merged main → 31982b7 (parents [7523de7, 67c3c8f]) and landed as 8871d7b. Neither 31982b7 nor 8871d7b carries any receipt — the back-merged tip was never re-gated green, so the epic reached main with the gate bypassed. The content was sound (it was gated at 7523de7), but the mechanism DEC-2 exists to enforce was defeated in practice, not in theory. E-GATEBM closes that.

The merge model, and what the walk actually sees

Branches are main ← epic/* ← wu/*. Work flows up as gated --no-ff seams. But branches diverge, so integration merges (pulling newer history back down or sideways) become unavoidable — e.g. a stale epic must back-merge main to get coherent tooling. The epic gate's walk (gate.rs, base..tip --first-parent --parents) is the only place that re-inspects seams, and it walks only the epic tip's own first-parent chain. It never recurses into a WU seam's internal history.

That single fact collapses the user's "what about merging between WUs / between epics?" question into a much smaller real surface. Only four shapes ever appear on the walked chain:

Directly answering "merging between WUs / between epics":
  • Between WUs inside an epic (B2, B4) — nothing to build. A WU-to-WU or epic-to-WU merge lives inside a WU branch's history. The epic walk gates a WU seam as a single leaf (verify(Wu, …) has no inner walk), so those internal merges are never re-inspected; their content is gated when the host WU seam is gated. The gate is already correct here by construction.
  • Between epics (B3) — same fix as B1. A sibling epic merged into this epic shows up on the walked chain and must be recognised as already-gated history. The clean path is to serialize through main: land the sibling, then back-merge main — which turns B3 into B1. Merging two unlanded epics into each other is not a workflow the model sanctions and has no precedent; see scope.

The one question the fix must answer

For a merge line [merge, mainline, wu_tip] on the walked chain: is wu_tip net-new ungated work, or already-gated history? A too-loose answer lets genuinely ungated work slip past the epic gate (violates R2); a too-narrow answer keeps false-positiving legitimate integrations (violates R1). The discriminator must be mechanical — an AI committer's assertion is forgeable (DEC-2 / DEC-7 principle).

The current guard answers only one direction:

// skip if wu_tip is already reachable from the mainline
if git(&["merge-base", "--is-ancestor", wu_tip, mainline]).is_ok() { continue; }

That catches an epic re-merging its own landed history (wu_tip ⊑ mainline). It says nothing about the merged-in tip being gated elsewhere (on main, or a sibling epic).

Key finding: the problems doc's leading candidate (#1, symmetric ancestry) does not fix the reported bug. It only helps the non-divergent back-merge (epic pulled main having added nothing since branching) — and candidate #2 already subsumes that case. The intuition "a back-merge means one side contains the other" is false once both sides have advanced, which is the normal state of a stale epic.

Recommendation

primary

Skip on target-reachability (#2)

Add: skip the seam when merge-base --is-ancestor wu_tip target holds. Keep the existing wu_tip ⊑ mainline check (cheap; catches self-history re-merges without needing the target). The rationale is airtight: content already on main was gated by main's own history — there is nothing new to re-gate. A forward WU seam always carries commits absent from main, so it can never be an ancestor of the target — R2 is preserved by construction, not by luck.

mechanics

Thread the target into walk

walk() has report.base and report.tip but not the target ref. Pass target_ref through (or check against report.base, which is an ancestor of the target — but the direct --is-ancestor wu_tip target is clearer and exact). Implementing WU picks the form and defends it in its plan; it is a small, local change to the three-parent arm.

deferred

Gated-lineage (#3′) — only if needed

#3′ is the fully-general answer (covers unlanded siblings) but re-derives the gate recursively and is costlier. There is no evidence the workflow needs it: no unlanded cross-epic integration has ever occurred. Defer it behind a real need; if that need arrives, it is its own decision, not a pre-built abstraction.

The anti-pattern #2 deliberately does not cover. If B merges A's tip directly (git merge epic/A) before A lands, the walk sees [B-seam, A_tip] and A_tip ⊑ main is false → #2 GATEs it → false positive again. This is intentional: an unlanded sibling has no gate of its own yet, so the walk can't know it's safe. Serialize through main instead; or, if you must integrate it live, waive that one seam via R5's valve (recorded, reviewable) rather than reaching for the heavier gated-lineage check (#3′) or --no-verify. See the open question.

R5 — walk-error waiver valve: a recorded bypass that isn't --no-verify

The walk is subtle — E-GATEBM is the proof, and it already forced a blanket --no-verify on main. #2 fixes the known misfire; R5 insures against the next one. Any walk failure must be overridable surgically and on the record, never by the nuclear --no-verify that skips every gate. This keeps the walk's backstop value while defusing its blast radius — a misfire becomes a logged door, not a wall. It also gives the out-of-scope cases (unlanded-sibling B3, any future topology #2 can't classify) a real escape without weakening the discriminator.

Why not dod, and why cr not test. dod/v1 is the gate's output — written only on green (write_receipt), never blind-trusted as input (DEC-2: "a hand-minted receipt fails recomputation") — so it cannot authorise its own pass. And test/v2 is for test coverage. A walk waiver is neither: it is a review judgment — "I looked at this seam the walk can't classify and skipping its re-check is acceptable" — so it rides the tip's cr/v2 review note. Bonus: cr/v2 is diff-bound (base + diff_sha256), so if main moves and the epic's effective diff changes, the review — and the waiver riding it — is forced to be re-validated; a waiver cannot silently outlive the diff it was judged against. (Git notes are mutable — git notes --ref=cr add -f <tip> / append — and adding a walk_waivers field leaves the PASS verdict, base and hash intact.)

Shape & behaviour

An entry in the epic tip's cr/v2 note names the seam the walk may skip, and why:

walk_waivers:
  - seam: <seam-sha>        # the commit the walk flagged, exactly as shown in the error
    why: "<why this specific walk error is safe to skip>"

RecordedLives in the tip's cr/v2 note with a mandatory why; persists as a git note after the branch is deleted, queryable like every other receipt.

Implementing WU: add walk_waivers to the CrNote struct (notes.rs), read the tip's cr note inside walk(), and check for a matching non-empty-why entry before pushing each seam failure (empty/missing why ⇒ no waiver, mirroring the existing waived-with-reason checks). The waiver applies to the whole named seam's walk failures; per-check granularity is deferred unless it proves too coarse.

Per-check waiver granularity — key by seam sha and waive the whole seam; refine only if it proves too coarse. A new dedicated note ref — reuse cr/v2 (a waiver is a review judgment, and cr is diff-bound).

The requirements R1–R4 in the problems doc stand; this discussion refines two of them:

  • R1 generalizes: "recognise the back-merge in both directions" → "recognise an integration of already-gated history from any lineage that reaches main", not just a back-merge of main by name.
  • R2 is the load-bearing constraint and candidate #2 satisfies it structurally (forward seams are never ancestors of the target) — the regression test in R3 exists to freeze that property, not to hope for it.

Open question for the owner

Candidate #2 makes the workflow rule explicit: cross-epic dependencies serialize through main (land one, back-merge, build the next). Is that acceptable as the standing rule, or is there a concrete case where two epics must integrate before either lands? With R5 in place the unlanded-sibling case now has a recorded, reviewable escape (waive that seam), so #3′ is only worth building if such live integrations become frequent enough that per-seam waivers turn noisy — otherwise we'd build for a case that has never occurred.
