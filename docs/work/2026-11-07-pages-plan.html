E-PAGES — plan: a GitHub Pages landing site for Trawler

Audit and plan only. One page that explains Trawler in ten seconds, hands each visitor the right installer for the latest release, and sends them to the guide. It makes no request outside its own origin and repeats no fact it does not take from the root markdown.

Purpose and audience

Who lands

A developer debugging HTTP/HTTPS from an app, a phone or a simulator, arriving from a search, a link, or the repo's website field.

The one job

In 10 s: what it is (pitch + screenshot) → the right installer for this OS → the guide.

What it does not do

No analytics, telemetry, cookies, storage, forms, newsletter, comments, search, or third-party request of any kind. No second copy of the guide. No roadmap, no other tool named (DEC-91 rule 2).

  • Links are versioned (releases/download/v0.1.0/Trawler_0.1.0_universal.dmg), never latest/download/<name>: asset names carry the version, so a latest link to a named file breaks on the next release.
  • The build refuses a release whose assets lack a kind Os::bundles names for a final (a pre-release never reaches releases/latest, DEC-86 rule 6), and refuses a draft or pre-release JSON.
  • A link click is a navigation to github.com, not a request the page makes; the CSP does not and need not cover it.

The workflow — .github/workflows/pages.yml

"on":
  push: { branches: [main] }
  release: { types: [published] }
  workflow_dispatch:
permissions: { contents: read }
concurrency: { group: pages, cancel-in-progress: false }
jobs:
  build:    # ubuntu-22.04, timeout 15
    steps: checkout@11d5960a… # v4.4.0 (persist-credentials: false)
           rust-toolchain@b725eda5… # 1.99.0, as release.yml
           run: gh api repos/${{ github.repository }}/releases/latest > release.json   # GH_TOKEN: github.token
           run: cargo xtask site build --release release.json --out target/site
           upload-pages-artifact@fc324d3547104276b827a68afc52ff2a11cc49c9 # v5.0.0 (path: target/site)
  deploy:   # needs build; environment: github-pages (url: deploy output)
    permissions: { pages: write, id-token: write }
    steps: deploy-pages@368f82528645a54fb793d4d04e342629a3f51346 # v5.0.1

SHAs of the two Pages actions were read from their release tags today (read-only gh api); W4 re-reads them. actions/configure-pages is skipped: its only use here would be the base URL, which is a constant (Q1). A release event skips a pre-release (if: !github.event.release.prerelease); the build always reads releases/latest, never the event payload.

Use-case requirements

Extends UC-INSTALL: a new entry point before the installer. Contract added: a visitor of the project site finds, per OS and arch, a direct link to the installer of the latest published final, the first-open step for that OS, and the guide; the site makes no request outside its own origin. No other UC changes; UC-UPDATE is untouched (the updater keeps reading latest.json).

Expected result

  • cargo xtask site build --release <json> --out <dir> writes a one-page site whose download block names every v0.1.0 installer kind with working releases/download/v0.1.0/… links.
  • .github/workflows/pages.yml exists, pinned and tested; after the owner's settings and the merge, https://lesslucifer.github.io/Trawler/ serves it.
  • DevTools Network on the live page shows requests to lesslucifer.github.io only; the page has no script.
  • Publishing the next final redeploys the site with its files, with no manual step.
  • The deny-list, link and contrast tests hold the site text like the root markdown.

Non-goals

  • A custom domain, analytics, a blog, docs search, translations, a rendered copy of the guide.
  • Any change to release.yml, ci.yml, the updater channel or the app's links.
  • OS auto-detection or any JavaScript.
  • New screenshots or brand art: the site uses what DEC-89/DEC-91 already generate.
  • Setting repo settings, pushing, tagging or dispatching (owner only).
