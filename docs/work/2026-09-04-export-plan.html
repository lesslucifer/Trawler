E-EXPORT — a capture leaves the ring and comes back

HAR export and import, a pasted curl command as a flow, a store that can be cleared, and a listing that pages — the first epic in which a flow outlives the process that captured it.

v4 · 2026-09-06 · Trawler · T3 epic plan · E-EXPORT — W9 added; the redesign baseline arrived as a back-merge, not a WU

Intent

Every flow Trawler has ever captured dies with the process. The Store is a byte-weighted ring (src/store.rs) with no way out and no way in: nothing serializes a capture, nothing reads one back, and nothing removes a flow except eviction under memory pressure. That makes the three things a debugging session actually needs impossible — hand a capture to someone else, open the capture they handed you, and clear the noise before reproducing a bug. This epic delivers all three over the interchange format the tools in this space already speak, HAR 1.2, plus a second, single-request way in — paste a curl command, the exact inverse of the copy-as-curl the app already ships — and the paging a listing needs once a session is long enough to be worth exporting. Now, because the roadmap makes E-EXPORT the independent Wave-2 Function track alongside the UI work, and because every later epic that produces flows (E-REPLAY, E-RULE, E-PERSIST) is easier to build and to test against a store that can already be seeded and emptied.

Use-case requirements

Two new records and one amendment. The new behaviour is a user-facing capability, so it lands in the use-case KB, not only in the API surface.

RecordContract stated at this epic's close
UC-6 new — take a capture out and bring one back A client can download the current filtered capture as a HAR 1.2 file that other HTTP tools open, and can upload a HAR file to have its entries appear as flows in the listing. An imported flow is marked imported, is filterable by that mark, and is otherwise an ordinary flow — same detail endpoints, same body endpoints, same ring rules. Export then import of the same capture preserves method, URI, status, versions, headers, timings and captured bodies. A single request can also come in as a pasted curl command — the inverse of UC-5's copy-as-curl — landing as a request-only flow, marked the same way.
UC-7 new — clear the capture A client can delete the whole capture, or only what a filter selects, and every live subscriber learns of it on /stream rather than by polling. A cleared store is empty, not restarted: the connection tally and the running proxy are unaffected.
UC-3 · UC-4 amended The listing contract gains opt-in paging: GET /flows with no paging parameters still returns the whole filtered list (the shell and app keep working untouched), and with limit returns a bounded page plus a cursor for the next one. The native app's flow list gains the export, import (file and curl paste) and clear controls (UC-4's surface is where they live).

Non-goals

  • Persistence. The store stays an in-memory ring; a HAR file is an artifact a user asks for, not an autosave. Named sessions surviving restart is E-PERSIST, and this epic must not smuggle in a durable store behind the export path.
  • Replaying an imported flow. Import puts a flow in the ring so it can be read; firing it at a server is E-REPLAY. An imported flow is inspectable, not executable.
  • Capture formats other than HAR 1.2. No .saz, no Charles .chls, no Postman collection. One capture format, done properly — the curl parser below is a single-request convenience, not a second capture format.
  • Exporting a whole capture as a curl script. W7 parses a pasted curl command in; it does not write a shell script out. Copy-as-curl already serializes one request (UC-5), and a runnable multi-request script is a different artifact with its own ordering and dependency problems.
  • Editing on import. Entries land as they are read. Rewriting a header or a host on the way in is a rules concern (E-RULE).
  • Making the API writable in general. The CORS grant currently advertises GET, OPTIONS (src/api/mod.rs) because the API is read-only. This epic widens it exactly as far as the new methods require, and states that widening as a decision — it does not open the surface.

Working units

E-EXPORT.W1 — the listing pages, and nothing that reads it notices

Opt-in paging on GET /flows: limit and cursor query parameters, a page read on the Store that walks the ring under one lock, and a cursor that survives concurrent inserts and evictions without duplicating or skipping a row. Absent both parameters the endpoint returns exactly what it returns today — the shell, the native app and the existing e2e are untouched by construction. Chosen first because it is the only WU that changes an existing wire contract, and everything after it reads the ring the same way.

E-EXPORT · UC-3 / UC-4 listing contract, amended additively · the roadmap's "pagination".

Expected result 5 holds. GET /flows?limit=2 returns two rows and a cursor; following it walks the whole capture exactly once. No existing test changes.

none — first WU.

E-EXPORT.W2 — a capture leaves as HAR

The HAR 1.2 projection and GET /flows/export. A new src/api/har.rs maps Flow → HAR entry (request, response, headers, query string, cookies where present, startedDateTime, time, the timings block, and content with base64 for non-text bodies), and the endpoint reuses FlowFilter so export and listing cannot drift. Bodies that were never captured (streaming, too-large, read-error) are represented honestly rather than as empty — a HAR reader must not be told a body was empty when it was skipped.

E-EXPORT · UC-6 (the export half) · the roadmap's "HAR export".

Expected results 1 and 3 hold. The document shape is snapshot-locked (insta), so a later change to the projection surfaces as a reviewable diff.

none — independent of W1; may land in parallel.

E-EXPORT.W3 — a capture comes back, marked

POST /flows/import and the source field it forces onto the domain model. Flow gains source: FlowSource (Captured | Imported), surfaced in FlowSummary/FlowView and filterable via FlowFilter, because the store now holds flows the proxy never saw and a user must be able to tell them apart and select them separately. The parser is the inverse of W2's projection and refuses malformed input with a reason, never a panic and never a half-filled store. Import respects the ring: entries insert like any flow and evict like any flow.

E-EXPORT · UC-6 (the import half) · the roadmap's "HAR import".

Expected results 2 and 7 hold. Round-trip fidelity is proven as a property, not by example: an arbitrary generated flow exported and re-imported compares equal on every field the format carries.

E-EXPORT.W2 — the parser is defined against the projection.

E-EXPORT.W4 — the capture can be cleared

DELETE /flows (all, or only what the filter selects) and DELETE /flows/{id}, over new Store removal that keeps total_bytes honest and announces what left on the bus. A new FlowEvent variant carries the clear, because an interface that learns about removal only by refetching cannot be live. The connection tally stays outside the ring and outside this — it is a monotonic "traffic reached us" tally, not storage. Also the CORS widening the mutating methods require, recorded as a decision alongside DEC-12.

E-EXPORT · UC-7 · the roadmap's "DELETE /flows".

Expected result 4 holds. The ring's byte accounting after any sequence of inserts and removals equals the sum of what it holds — the existing ring_accounting proptest extended with removals rather than a new test beside it.

E-EXPORT.W7 — paste a curl command, get a flow

The inverse of the copy-as-curl the app already ships (toCurl, ui/src/flow.ts:67): a parser that turns a pasted curl command line into a flow, reached as POST /flows/import?format=curl and, in the app, as a paste target on the same import control W5 designs. It accepts exactly the set settled in question 8 — what a browser's "Copy as cURL" and Trawler's own toCurl emit, with -u and --compressed expanded into the headers they imply, shell quoting and backslash line-continuations handled, and transfer-only flags consumed silently — and refuses everything else with a reason naming the flag it did not understand. A parsed command yields a request-only flow, marked imported exactly as a HAR entry is: it has no response, because nothing has been sent — the same shape a captured flow has between request and reply, which the store, the API and the UI already handle.

Open questions — all settled

None are open — all eight were settled at the plan review, every proposed default confirmed as written. They stay on the record as the decisions they are, and the work starts against them. A question reopens only if the work proves a default wrong, and that reopening is a deviation the WU result must record.
#QuestionAnswer
1 What is the cursor? The id of the last row on the page, resolved against the ring's order. It survives eviction of rows before it (the walk simply starts where the ring still has content) and never re-serves a row an insert pushed past. An index would silently skip rows the moment the ring evicts. W1 decides on the merits.
2 Does export page too, or always export the whole filtered set? The whole filtered set. A HAR file split across pages is not a HAR file; the filter is the way to export less. Bounded by the ring's byte cap, which is already the memory ceiling.
3 Does import replace the capture or add to it? Adds. Replacing is DELETE /flows followed by an import — two operations the user already has, rather than a destructive mode hidden inside a POST.
4 Do imported flows keep their original ids and timestamps? Fresh ids, original timestamps. The id is this store's handle and must be unique here; startedDateTime is the captured truth and is preserved, so an imported capture sorts by when it happened, not when it was read.
5 Which word does the UI use for export, given the rulebook reserves it against copy? Export — for the file operation only — the reserved meaning bans it as a synonym for copy (putting bytes on the clipboard), which is a different operation. W5 states this in the run and the rulebook row is clarified at distillation rather than left ambiguous.
6 Does a DELETE with a filter that matches nothing succeed or 404? Succeeds, reporting zero removed. The request expresses an end state, and that state is already true. DELETE /flows/{id} on an unknown id is the one 404 — there the client named something specific that does not exist.
7 Is insta a new dependency, given the WU obligation to snapshot-lock a new wire contract? Yes, dev-dependency, added in W2. The testing standard names it as the tool for exactly this and nothing in the tree has needed it until a serialized document format arrived.
8 How much of curl does W7's parser accept? The tool has hundreds of flags and a full shell grammar sits behind any pasted command. The flags browsers emit, and a refusal for the rest — settled at review, and fixed here rather than left to W7 so the contract is testable before a line is written. The parser's job is to accept what a developer actually pastes — a browser's "Copy as cURL" and Trawler's own toCurl — not to reimplement curl. Anything outside the set below is refused naming the flag: honest and actionable, where silently ignoring one would produce a flow subtly unlike the request the user pasted.
AcceptedBecomes
-X / --requestthe method (absent ⇒ GET, or POST when a body flag is present, matching curl)
the bare URL argument · --urlthe URI
-H / --headera request header
-d / --data / --data-raw / --data-binary / --data-asciithe request body
-b / --cookiea Cookie header
-u / --useran Authorization: Basic header — expanded, because dropping it changes what the request is
--compressedan Accept-Encoding header — same reason
shell quoting · \ line continuations · -s/-k/-i/-v and other transfer-only flagsconsumed and ignored — they shape curl's own behaviour, never the request on the wire
Everything else — -F, -T, --form-string, a second URL, anything unrecognized — is a refusal naming it. The ignore list is deliberately the only silent case, and it is safe precisely because those flags leave no trace in the request.
