E-DFLOW.W1 — Base flow + hand-run

WU plan. Define a first-cut staged design flow and run it by hand on the flow detail panel — no harness, no rules — to learn what the flow actually needs.

WU plan · 2026-07-16 · Trawler · T3 (docs/work/) · wu/design-flow/base-flow-hand-run · epic: docs/work/2026-07-16-design-flow-plan.html

Requirement

Define a first-cut staged design flow and run it by hand on the flow detail panel — no harness, no rules — to a draft mockup, capturing what the flow actually needed.

Maps to: E-DFLOW intent (the flow · process) and the bottom-up build order — W1 is the empirical bottom. Everything W2–W7 seed/build (registry, rulebook, harness) is extracted from what this hand-run surfaces. Depends on: none.

Expected result: a written first-cut base flow (stages + per-stage artifact shapes — in this doc), one worked example (flow-detail-panel artifacts for all stages — in the run doc), and a findings note of gaps tagged for W2 / W3 / the flow itself.

Why hand-run first (not build the harness)

The epic can't know the right stages, artifact shapes, component tiers, or rules by fiat — raw instruction is exactly what this epic distrusts. So W1 discovers the requirements by doing the work once, unassisted: an agent designs a real screen following only the staged flow, and every time it reaches for something that isn't there (a component to reuse, a token to cite, a rule to obey) that friction is logged. Those friction points are the seed lists for W2 (registry) and W3 (rulebook). Build-first would hard-code guesses; run-first turns guesses into evidence.

Deliberately absent in W1: no component registry, no rulebook, no harness, no receipt, no gate. The only structure is the stage sequence below. Wanting any of the absent things mid-run is not a blocker — it is the finding.

Decisions for this WU

Two forks the epic left to this plan. Both resolved here; override by comment if wrong.

D1 · Artifact medium — one HTML scratch doc, no ui/ code

All six stage artifacts, including the draft mockup, live inline in a single T3 run doc (docs/work/2026-07-16-dflow-run-1.html). The draft mockup is a lo-fi structural wireframe — plain HTML boxes / ASCII, no real styling, no JSX in the app.

Why: lightest medium that stays commentable + diffable under htmldoc; one place to review the whole run. Critically, writing zero ui/ code keeps the epic's promise honest — this is proof the flow works, not a UI change that could be mistaken for a shipped redesign. Rejected: a real rendered mockup in ui/ (heavier, blurs proof-vs-product); markdown files (breaks the HTML-docs rule, loses the comment/diff layer).

D2 · Guinea-pig framing — design fresh, cross-check the shipped panel last

The flow detail panel already exists (ui/src/FlowDetail.tsx, shipped by E-UIINSPECT). W1 runs the flow as if the panel does not exist — deriving each artifact from the screen's purpose, not from the current code. Only at the very end do we diff the draft mockup against the shipped panel, and any divergence is recorded as a finding (about the flow or the existing screen), never silently "corrected" to match.

Why: the point is to test the flow's generative power. Reverse-engineering the shipped panel would test our ability to document an existing screen — a different, weaker thing that would launder the flow's gaps.

The first-cut base flow

Six stages, cheapest commitment first, each producing one artifact that feeds the next. This is a first cut — the hand-run is licensed to find a stage redundant, mis-ordered, or missing, and say so in the findings.

  F[Frame] --> L[Layout] --> E[Elements] --> I[Interaction] --> D[Draft mockup] --> T[Tune]
  T -. revise .-> L
Linear stages with a single tune-back loop; each stage's artifact is the next stage's input.
StageQuestion it answersArtifact shape
1 · FrameWhat is this region for, who reads it, what job does it do, and which states must it handle (loading / empty / error / populated)? Where does it sit in the app shell?Frame statement — a short paragraph + a bullet list of required states.
2 · LayoutHow is the frame divided into regions, and what is their priority/hierarchy? (No content yet — zones only.)Region map — labelled boxes (wireframe) with a one-line priority note per zone.
3 · ElementsWhat concrete UI elements fill each region? What is each one? (No registry in W1 — elements are free-named; reaching for "does this already exist?" is a finding.)Element inventory — region → list of named elements, each with a one-line role.
4 · InteractionFor each interactive element: what triggers it, what states it has (hover / focus / active / disabled), and how the screen handles the empty / error / loading transitions from Frame?Interaction table — element → trigger → states → transition behavior.
5 · Draft mockupAssembled, does it hold together as one screen?Lo-fi wireframe — HTML/ASCII structure realizing layout + elements, with interaction notes annotated. The finish line.
6 · TuneStepping back from the whole: what grouping, hierarchy, or redundancy is off, and why?Tune notes — a short before/after list; may loop back to Layout.

The hand-run protocol

  1. An AI agent walks the six stages in order on the flow detail panel, writing each artifact into the run doc as it goes — nothing skipped, nothing back-filled from FlowDetail.tsx (D2).
  2. At every stage the agent keeps a friction log: any moment it wishes a component, token, or rule existed, or the stage prompt felt ambiguous/underspecified. One line per friction, tagged →W2 (registry), →W3 (rules), or →flow (the stage sequence/artifacts themselves).
  3. The "fake taste" role (the human stand-in the epic's e2e will later automate) is played lightly here: a sanity read after Layout and after Draft mockup, its reactions folded into Tune. W1 does not build any stubbed roles — that is W7.
  4. After Tune, diff the draft mockup against the shipped panel; record divergences as findings (D2).
  5. Distil the friction log into the findings note — the ranked gap list W2/W3 consume.

Deliverables

  • This plan doc — decides W1 scope, the first-cut base flow, and D1/D2.
  • Run doc — docs/work/2026-07-16-dflow-run-1.html: the worked flow-detail-panel example, all six stage artifacts inline, plus the shipped-panel cross-check.
  • Findings note — a section of the run doc: the friction log distilled into a tagged, ranked gap list feeding W2 / W3 / the flow revision (W4).

No ui/ or src/ code, no T1/T2 doc changes. The base-flow definition here is a first cut that only becomes the T1 process doc after W4 validates it — W1 distils nothing upward yet.

Test plan

Level: WU → integration — waived (process / docs-only). W1 changes no app code; its deliverables are three docs. Per the project rule, docs/infra-only diffs are exempt from the test layers, so the WU tip carries test/v2 with waived: "process WU — deliverables are the plan + worked run + findings docs; no app code. The flow's plumbing gets its scripted e2e in W7 (fake user + fake agent); the receipted acceptance run is W4/W7."

The hand-run itself is the informal validation: if the flow stalls, produces an empty artifact, or its stages read as ambiguous, that surfaces as a finding rather than a passing gate — which is exactly W1's job.

Open questions

  • Does Tune earn a distinct stage? Default: keep it distinct in the first cut; if the hand-run finds it a no-op or inseparable from Draft mockup, that is a →flow finding for W4.
  • Are states (loading/empty/error) a Frame output or their own stage? Default: an output of Frame, exercised in Interaction. Revisit if the hand-run shows they need first-class treatment.
