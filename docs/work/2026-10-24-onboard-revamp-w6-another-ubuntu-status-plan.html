#What goes wrong todayProposed fixRuling
C1The only numbered route reaches no browser. ② numbers one command, which writes the system store. Step ④ asks for a website, and neither Firefox nor Chrome reads that store, so ② done as written ends in a refusal every time. Firefox's import is a note with no path. Chrome's sits under "other ways", which the guide model reserves for a second route to the same end.② numbers one step per store, as drawn above: Firefox's import path, Chrome's NSS command, then the system command, led "for curl and the system's own tools". The Firefox note goes, because it becomes a steptake
C2Chrome's command fails on a stock Ubuntu: certutil is not installed. It comes from libnss3-tools, which Chromium's own Linux guide installs first. The shell says "certutil: command not found". The NSS removal under "to remove it later" fails the same way.the command installs it first: sudo apt install -y libnss3-tools && certutil …take
C3Chrome's command writes a database a new Chrome does not open. Since M146, Chromium's NSS DB is ~/.local/share/pki/nssdb, and ~/.pki/nssdb only where an older Chrome already made it. On a machine whose Chrome first ran at M146 or later, -d sql:$HOME/.pki/nssdb names no database and certutil fails. The removal names the same path.both commands pick whichever database exists: db=$HOME/.pki/nssdb; [ -d "$db" ] || db=$HOME/.local/share/pki/nssdb; certutil -d "sql:$db" …take
C4The download path is English only. W5's C2 made the trust command read ~/Downloads/trawler-ca.pem. Ubuntu names that folder in the session's language (~/Téléchargements, ~/Descargas), and the browser saves there, so cp and certutil find no file.Linux's commands read "$(xdg-user-dir DOWNLOAD)/trawler-ca.pem". xdg-user-dir ships with the Ubuntu desktop. The path stays one constant with the download step's file, as W5 made ittake
