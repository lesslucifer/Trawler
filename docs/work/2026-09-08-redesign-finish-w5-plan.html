E-RFINISH.W5 — the core accepts a status class

The useful debugging query is “show me the failures”, and today the API can only be asked for one exact code. This WU widens GET /flows?status= to accept a class alongside a code, and makes everything outside that grammar a stated 400 instead of an empty list the reader has to interpret.

WU plan · 2026-09-08 · Trawler · T3 (docs/work/) · wu/redesign-finish/status-class → epic/redesign-finish

Requirement

GET /flows?status=4xx returns only 4xx flows, ?status=404 still returns exactly 404s, and any value that is neither an HTTP status code nor an HTTP status class is a 400 that says what the grammar is — the widening lives in the core, behind the same query parameter the UI already sends, so no client changes to keep working and W6's designed control has a contract to speak to.

The grammar, exhaustively

ValueReadingResponse
404exact codeflows whose response status is exactly 404
4xx · 4XXclass — case-insensitiveflows whose response status is 400–499
absentno status filterevery flow, as today
9xxno such class400 — stated
999no such code400 — stated
4x · 40x · xxx · abc ·   (empty)outside the grammar400 — stated

A code is 100–599; a class is 1xx–5xx. One sentence carries both refusals: status must be an exact code (100-599, e.g. 404) or a class (1xx-5xx, e.g. 4xx) — plain text with a 400, the shape bad_id already established for a malformed path segment.

One deliberate narrowing: ?status=999 stops being an empty list and becomes an error. It parses as a u16 today and matches nothing, so the reader sees the same screen as “no failures captured”. The epic plan asks for a nonsense class to be stated; making a nonsense code silent would leave the parameter with two different answers to the same question. The rule is one rule: the value denotes a real status or a real class, or it is refused.

One grammar, two shapes, one refusal. The in-flight case is unchanged: a status filter of any form excludes a flow that has no response yet, exactly as Option<u16> does today.

Where it changes

src/store.rs

the domain half

A StatusMatch enum — Exact(u16) | Class(u8) — with a FromStr that is the grammar above, and a matches(code) that is the only place the / 100 lives.

FlowFilter.status becomes Option<StatusMatch>; its arm in matches asks the enum instead of comparing.

src/api/routes.rs

the wire half

ListQuery.status becomes Option<String> — serde must stop rejecting 4xx before the parser can ever see it.

list_flows returns Response rather than Json<Vec<FlowSummary>>, because it now has two answers: the listing, or the stated 400.

nothing under ui/src/

the half this WU does not do

The app keeps sending what it sends; filterParams already trims and drops an empty value, so no app request changes shape. The designed control, its placeholder and the dropped inputMode="numeric" are W6.

No .tsx in the diff, so this WU carries no design accounting at all.

The core stays strict about whitespace. " 4xx" is refused, not trimmed — the trim belongs where the human typing lives, and the client already does it. W6 inherits that as a fact, not a task.

Expected result

  • GET /flows?status=4xx against a store holding 2xx, 4xx and 5xx traffic returns the 4xx flows and only those — proven with a 5xx present, so “not 2xx” cannot pass for “is 4xx”.
  • GET /flows?status=404 returns exactly the 404s with a 400 and a 451 in the store — the exact form did not become a prefix match on the way through.
  • GET /flows?status=9xx and ?status=999 both return 400 with the grammar sentence in the body. Neither returns 200 with [].
  • Every other filter is untouched: host, method, content_type and q keep their existing assertions, and status still composes with them.
  • A flow still awaiting its response is excluded by a status filter of either form, which is the behaviour Option<u16> has today and the one existing test that pins it.
  • cargo clippy stays clean under pedantic, and UC-4's text no longer claims a class query is inexpressible.

What could go wrong, and what stops it

RiskWhat stops it
A permissive parser turns a typo back into a silent empty list.The unit table lists more refusals than acceptances, including the near-misses (4x, 40x, 0xx, 6xx) a loose implementation would let through.
The class match is off by one at the boundary — 500 counted as 4xx.Edge assertions at both ends of every class, and the integration test keeps a 5xx flow in the store precisely so a too-wide match fails.
Refusing 999 breaks a caller that relied on it.Nothing does: the only client is the app, whose field a human types a code into, and the change makes the typo more legible. The narrowing is recorded above and repeated in the WU result.
Making list_flows return Response loses the typed JSON body. The integration tests parse the success path as JSON and assert on its contents, which is what the type was buying.
