The ordering defect this WU found in itself

The human sign-off was taken before the code review ran. The owner attested a result report whose cost section then turned out to state a conclusion that was backwards — exactly what the review existed to catch, obtained in the wrong order.

WhatDetail
Why it was possibleThe lifecycle diagram shows R → MR (review, then sign), but the DoD gate tables list the evidence without stating any sequence. Reading the checklist rather than the diagram, nothing contradicted the wrong order
Why the order is load-bearingRecorded in DEC-27, with the alternatives it rejected — this row does not restate them
The circularity that made it worseA test/v2 receipt that honestly reports a missing test can only be acted on by adding the test — a tree change, which invalidates the signature already given. So the receipts must precede the signature, not follow it
The rule nowTree-changing work (code, tests, docs, report) → test/v2 + doc/v1 → cr/v3 PASS → then mr confirm → merge
Enforcedmr confirm refuses before the signing prompt, so a signature is never spent on a tip a later fix would orphan. 4 unit + 4 integration tests, and the 10 pre-existing confirm tests now settle their tip first

The token target, measured and missed

W10 anticipated ~3.4M prompt tokens for a run-6-class design run and deferred the measurement to W11. Measured here from ~/.claude/projects/…/8a7cf683….jsonl over the run's own window (06:19:28 → 08:53:37 UTC):

W10's cost model measured the wrong thing. It optimised file sizes — flow spec and rulebook, 113,882 → 65,616 bytes, a real 42% cut — and predicted the total would fall with them. It did not, because prompt cost is context re-sent per call, not bytes read once. The substrate that W10 shrank is ~0.5M of cache creation; the 17.2M is that same context multiplied by 169 calls. Halving a file halves one number in a sum dominated by the other.
What actually drives the totalEvidence
Call count, near-linearly169 calls × a ~100K working context ≈ the 17.2M. The single biggest lever, and W10 addressed it only for the fix loop
Context held, not context readPeak 164K. Once the substrate is in context it is re-sent whether or not the run still needs it
File size467K total cache creation — the entire "read each artifact once" surface is 2.6% of the bill

The honest conclusion: W10's interventions were sound but small. A run-cost target expressed in prompt tokens cannot be met by compacting documents; it needs fewer, larger turns. This run took 169 calls where the flow's own norm (edit twice, verify twice) implies far fewer.

Baseline caveat. Run #6's 11.4M is taken as W10 recorded it. No transcript from 2026-08-30 survives in this project's session store, so it could not be re-derived here. The two numbers are comparable in kind (both prompt totals) but were produced by different methods.

The one real DEC-13 question

Run #8 first marked the unset the proxy capability deliberately unused, reasoning that undoing setup belongs to a settings surface rather than the doorway, and that offering it mid-setup would compete with the step it completes. The design review found both reasons false against the shipped code: ui/src/Onboarding.tsx renders Stop routing inside this screen's own set-proxy step, gated on showStop = auto && state === "done" — so it appears only after that step succeeds, competing with nothing. The run now carries the capability as blocked, with a blocked-on entry naming the missing decision. DEC-13 names symmetric revert as part of why the app may write OS state at all.

Owed, as a question and not an edit: either the build keeps an unset affordance — in which case assertion #14 is inherited, not retired — or the removal is argued on its own merits and DEC-13 is amended to record where revert now lives. A design run may not narrow a shipped capability by listing it as unused.
