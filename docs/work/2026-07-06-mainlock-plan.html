E-MAINLOCK — main is merge-only

Epic plan (collapsed: one WU) — the pre-commit hook refuses any direct commit on main with branch guidance, closing the ungated standalone-commit path.

v1 · 2026-07-06 · Trawler · T3 epic plan + WU plan · hardens the DoD gate system (DEC-2/DEC-3)

Intent

Today a standalone commit made directly on main is gated only by the pre-push range check, which demands a self-attested test/v2 note but never a code review (check_review is skipped at commit level) — and future epic gates never re-walk main-side history, so the miss is permanent. E-MAINLOCK removes the path instead of patching it: the pre-commit hook refuses every non-merge commit on main with a message that tells the (AI) committer exactly what to do — start an epic/<slug> or wu/<epic-slug>/<slug> branch and land through the merge gate. All work, including docs-only changes, follows one uniform route; the merge gate already exempts docs/infra-only diffs automatically.

Use-case requirements

Process epic — no product-facing use case; the lasting contract is a decision record (DEC-6, distillation plan below). Behavior delivered:

ContractBehavior
main is merge-only On branch main, git commit for anything that is not a merge completion fails in pre-commit before fmt/clippy run, printing the epic/WU branch commands and pointing at docs/workflow.html. Merge commits (clean via pre-merge-commit, conflicted completions via the existing MERGE_HEAD path in pre-commit) land exactly as before. Commits on every other branch are unaffected.

Expected result (epic = WU, collapsed)

Observable after the epic lands, checkable by anyone with the repo:

  • On main, git commit of any staged change is refused; stderr names the rule and shows the git checkout -b epic/<slug> main / wu/<epic-slug>/<slug> commands.
  • A conflicted-merge completion on main (MERGE_HEAD present) still commits, still gated by verify-dod hook epic.
  • A clean --no-ff merge into main is untouched (pre-merge-commit path).
  • Commits on epic/*, wu/* and any other branch behave exactly as before.
  • docs/workflow.html no longer documents a direct-to-main path; DEC-6 records why it was removed.

Approach

One guard at the top of .cargo-husky/hooks/pre-commit: branch is main and no MERGE_HEAD → print guidance, exit 1. No xtask change — range() stays as the pre-push backstop for note validity on whatever history already exists. The existing MERGE_HEAD block in the same hook keeps handling conflicted-merge completions; the guard simply sits before everything else so the refusal is instant and unambiguous.

Non-goals

  • Blocking direct commits on epic/* branches — plan docs and epic-level notes legitimately land there; the epic gate walks and gates them at merge time.
  • Requiring cr/v2 at commit level in gate.rs — moot once the standalone-on-main path is gone; epic-branch standalone commits are already walked by the epic gate.
  • Server-side (remote) enforcement — local hooks are this repo's gate mechanism throughout (DEC-2); a hosted branch-protection rule is deployment config, not code.
  • Retroactive judgment of existing main history — the rule applies from now on.

E2E test plan

The epic's end-to-end surface is the git workflow itself, and the integration tests above already drive the real hook binary inside a real (hermetic, temp-dir) git repo — commit refused on main, merge completion allowed, other branches untouched. That IS the full flow for a hooks-only epic; there is no product/runtime surface beyond it. The test/v2 note therefore records e2e: waived with this reason, and the review judges it. (Per the testing standard, waivers are explicit and reviewed, never silent.)
