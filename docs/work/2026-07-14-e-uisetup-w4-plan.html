Requirement

On launch the app decides its own entry: it reads GET /flows once, and if a decrypted HTTPS flow is already present it goes straight to the list (proven); otherwise it shows onboarding. While unproven it watches GET /stream, and the first decrypted HTTPS flow that arrives flips the machine to proven — the Verify step turns from red to green and the flow list is revealed (never re-forced back to onboarding). "Decrypted HTTPS" is the flow's own truth: an https:// absolute-form request URI, which only a MITM'd (decrypted) exchange produces — a plain-HTTP proxied flow (http://…) does not count (epic: "Works" = a decrypted HTTPS flow). Nothing self-reports done; capture is the sole proof. The status dot re-invokes setup; from a re-invoked onboarding, Back to flows returns to the list only because capture was ever proven. No core / API change — reads the existing /flows + /stream.

The detector — one predicate, the flow's own truth

A decrypted HTTPS flow is exactly one whose request URI is https://…. hudsucker rewrites a MITM'd request to absolute form with the real scheme (see recorder.rs — uri: parts.uri.to_string()), so the scheme in FlowSummary.uri is authoritative: only a decrypted exchange yields https://; a plain proxied request stays http://. The predicate is therefore a one-liner — flows.some(f => f.uri.startsWith("https://")) — living beside toRow in flow.ts as isDecryptedHttps, so both the launch check and the live check share the same definition of "done".

Why the flow, not a self-test? The epic's "done when" mentions the app firing its own HTTPS request when the proxy was auto-set. That request can only route through a real just-set system proxy on a real OS — it is not hermetically runnable and belongs to the privileged auto path the epic already waives from e2e. The universal, testable proof is the same for auto and manual users alike: a decrypted flow was observed. W4 wires that. A native self-test request is a thin later add-on over the same detector, not this WU's contract — noted, not built (consent/elevation path, deferred with the auto paths).

Test plan

Every layer this WU touches gets its test; the machine's own transitions are already covered by W1's onboardingMachine.test.ts (this WU adds no machine logic, so nothing to re-test there).

LevelWhereAsserts
unit flow.test.ts isDecryptedHttps: true for an https:// URI, false for http://, false for a relative/opaque URI, false on an empty list.
integration (seam) App.test.tsx Launch with a pre-existing https:// flow ⇒ list directly (no onboarding). Launch with only an http:// flow (or none) ⇒ onboarding. From onboarding, an SSE event that brings in a decrypted-HTTPS flow ⇒ Verify green + list revealed. A plain-HTTP flow arriving does not flip it. Re-invoke via the dot then Back to flows returns to the list (everProven).
e2e ui/e2e/specs/ + harness The epic spine: fresh launch shows onboarding; a real proxied HTTPS request through the ephemeral core produces a decrypted flow; the Verify check flips to green and the list shows it; a relaunch/already-proven start goes to the list directly.

The e2e harness must serve HTTPS. Today harness/main.rs's origin is plain HTTP, so its /hit produces an http:// flow — which by design does not prove capture. W4 adds a CA-signed HTTPS origin (the exact pattern from e2e_capture.rs's https_mitm_decrypts_and_captures: generate a CA, sign a localhost leaf, feed the CA to the core via upstream_extra_root_pems, serve TLS with axum_server), so /hit drives a request that the core decrypts and records as https://. The proxy client trusts the core's own CA (from /ca.crt) exactly as the integration test does. This keeps the e2e hermetic (ephemeral ports, tempdir CA, no public network) while proving the real thing the check keys on.

Waiver (judged at review), inherited from the epic. The auto CA-install and auto-proxy paths need OS elevation and are not hermetically runnable; their command builders are unit-tested (W2/W3) and the journey is proven here via a real proxied HTTPS request. Success is proven by capture — a decrypted flow observed — never by reading a trust store or self-reporting. The native auto-proxy self-test request is deferred with those auto paths (noted above), not a gap in this WU.

Done when

  • A decrypted HTTPS flow (real proxied request) flips the Verify check to success and reveals the flow list; a plain-HTTP flow does not.
  • A fresh launch (no decrypted flow yet) shows onboarding; an already-proven launch (a decrypted flow already present) shows the list directly, onboarding not forced.
  • Re-invoke via the status dot re-opens setup; Back to flows returns to the list because capture was ever proven.
  • Detector predicate unit-tested; launch + live transitions integration-tested on a mock stream; the full journey proven in e2e against a real ephemeral core over a proxied HTTPS request.
  • Gates green headless: vitest + cargo clippy (harness crate) + cargo xtask ui build; e2e run green.

Non-goals

  • Any machine change — the setup lives in W2/W3; W4 only observes the result.
  • A native self-test HTTPS request on auto-set — deferred with the elevation-gated auto paths; the universal proof (a decrypted flow) covers both auto and manual users.
  • A new store / persisted onboarding state — entry is derived from live capture every launch (epic non-goal).
  • Proving plain-HTTP capture — "works" means a decrypted HTTPS flow.
  • Proxy teardown / auto-revert — that is W5.
