E-EXPORT.W2 — a capture leaves as HAR

A HAR 1.2 projection of the ring and the GET /flows/export that serves it — the first time a Trawler capture exists outside the process that recorded it.

v1 · 2026-09-04 · Trawler · T3 WU plan · E-EXPORT.W2 · epic plan · W1 result

Requirement

GET /flows/export returns the currently filtered capture as a single HAR 1.2 document — one log.entries element per flow, newest-first, carrying method, URI, HTTP versions, headers, query string, cookies, status, the startedDateTime the flow was captured at, its time and a timings block, and each body either as its captured bytes (base64 when not text) or as an explicit statement that the body was never captured — never as an empty one. It accepts the same filter parameters as GET /flows and exports exactly the set that listing lists.

Mapping

E-EXPORT · the epic plan's W2 summary block · UC-6, the export half ("a client can download the current filtered capture as a HAR 1.2 file that other HTTP tools open") · the roadmap's "HAR export" line. Independent of W1 — it reads the whole filtered set via Store::list, never a page, because question 2 settled that a HAR file is never split across pages. W3's parser is defined against this projection, so the mapping this WU pins is the contract that WU inverts.

Where the projection lives

Hình 1 — one new module and one new route. The filter is built by the same code path the listing uses, so export and listing cannot select different sets.
The filter is shared, not re-implemented. Expected result 3 is that /flows/export?host=x exports what /flows?host=x lists. The only way to guarantee that rather than test for it is for both handlers to construct the same FlowFilter from the same query type — so ListQuery's filter fields are extracted into one conversion both routes call, and paging's limit/cursor stay out of the export's query type entirely (an export cannot be paged, so accepting the parameters would be a lie).

The honest-body problem — the one real design call

A HAR reader must never be told a body was empty when it was skipped. BodyRec distinguishes four states and HAR's content object has no vocabulary for three of them. Reporting { size: 0, text: "" } for a streamed body would make a 4 MB event stream indistinguishable from a 204 — the exact loss the domain model was built to prevent (BodyRec's own doc comment).
BodyRecHAR content / postDataWhy
Captured, text-ish content type { size, mimeType, text } the bytes as UTF-8. A text content type whose bytes are not valid UTF-8 falls through to the base64 branch — the encoding claim has to be true
Captured, anything else { size, mimeType, text, encoding: "base64" } HAR 1.2's own binary convention: encoding names how text is wrapped
Empty { size: 0, mimeType }, no text the one state where "nothing" is the truth
Streaming { size: -1, mimeType, comment: "trawler: body not captured (streaming)" } size: -1 is HAR's "unavailable" and the absence of text says the same thing structurally; comment is a HAR-standard field, so the reason survives into any reader that shows comments — and W3 reads it back to restore the variant
NotCaptured { TooLarge { actual } } { size: actual, mimeType, comment: "trawler: body not captured (too_large)" } the size is known — that is why the body was dropped — so it is reported; the missing text plus the comment carry "we know how big, we do not have it"
NotCaptured { ReadError } { size: -1, mimeType, comment: "trawler: body not captured (read_error)" } neither the bytes nor the size were obtained
The comment strings are a wire contract, not prose. W3 restores the BodyRec variant by reading them, so the four reason tokens (streaming, too_large, read_error) are pinned by the snapshot test in this WU and reused — not re-spelled — in W3. They deliberately reuse BodyRec::state()'s existing token vocabulary rather than inventing a second spelling of the same four states.

The HTTP response

RequestStatusResponse
GET /flows/export 200 application/json · Content-Disposition: attachment; filename="trawler-<utc-timestamp>.har" · the whole document
GET /flows/export?host=x&method=post 200 the same, over the filtered set — identical filter semantics to GET /flows
an empty capture, or a filter matching nothing 200 log.entries: [] — a valid, empty HAR file, not a 404: the request asked what is captured and the answer is "nothing"

application/json rather than the unregistered application/har+json: a HAR file is JSON, every reader accepts it, and the .har filename in Content-Disposition is what tells a browser and the native app what to save it as. The CORS grant is untouched — this is a GET, so DEC-12's read-only reasoning still holds and the widening the epic plan schedules belongs to W4's mutating methods.

Calls this plan makes, so the build does not have to invent them

QuestionCall
Does /flows/export accept limit/cursor? No — and it does not silently ignore them either: the export query type simply has no such fields, so an unknown parameter is ignored exactly as GET /flows ignores unknown parameters today. A paged HAR file is not a HAR file (question 2), and accepting a parameter that cannot be honoured is worse than not offering it.
Where does the route live in the router? /flows/export, registered before /flows/{id}. axum 0.8's router prefers the static segment, so export is never captured as an id — asserted by a test, not assumed, because it is exactly the kind of routing precedence that silently regresses.
Is a flow with no response exported? Omitted. HAR requires entry.response and Trawler has nothing truthful to put there. Recorded as observable 6 so the count difference against the listing is a documented contract rather than a surprise.
Does the projection decode compressed bodies? No — the bytes exported are the bytes captured, with the Content-Encoding header that describes them still attached, so the file stays a faithful record of the wire. /flows/{id}/response/body?decode=1 remains the decoding surface, and a decoded export would contradict its own headers. Stated in DEC-35 as part of what round-trip preserves.
