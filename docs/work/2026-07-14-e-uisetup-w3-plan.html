E-UISETUP.W3 — Set the proxy

Route the machine's traffic through Trawler from inside the native app: one click sets the system proxy on macOS and Windows; a copy-pasteable snippet carries the real proxy address everywhere else. The proxy-config half of the onboarding stepper — W2's sibling step.

Draft v1 · 2026-07-14 · Trawler · T3 WU plan · epic: E-UISETUP · builds on: W1 · sibling: W2

Requirement

The onboarding Set the proxy step points the system at Trawler's proxy natively: on macOS one confirm + an OS elevation prompt runs networksetup -setwebproxy/-setsecurewebproxy on every enabled network service; on Windows one click writes the per-user WinINET registry proxy (ProxyServer/ProxyEnable) and nudges running apps via InternetSetOption — no elevation, HKCU is user-writable. A client selector (defaulting to the detected host) shows the correct snippet and guided steps for any client — Linux, Firefox's own proxy settings, terminal/CLI, simulators, devices — as text (UC-3/UC-4 invariant), with a working Copy for the command-shaped ones. Every snippet carries the real proxy address from configuration (DEC-12 — default 127.0.0.1:7420, never hardcoded in component code). The privileged command is built in ui/src-tauri from fixed per-OS templates — the webview passes only host + port, never a command. The set command's exit status gives the weak "it ran" signal (step → done/failed); the authoritative "traffic actually routes through Trawler" answer is W4's live capture. Decline or failure ⇒ the snippets carry them the rest of the way (consent, never silent).

Design

W2 shipped the app's first Tauri command (install_ca) and the per-OS template/elevation plumbing in setup.rs. W3 adds the second command, set_proxy, reusing the same file, the same osascript elevation wrapper, and the same UI shape (selector + auto button + guided text) from W2's trust-ca step.

Trust boundary — same rule as W2, sharper edge. W2's PEM went to a temp file and never entered the command line; W3's host and port are interpolated into an elevated shell string (the osascript script). The command still never takes an argv from the webview: set_proxy(host, port) takes data only, port is a u16 by type, and host is validated against ^[A-Za-z0-9.-]+$ before use — no spaces, no quotes, no shell metacharacters, so injection into the elevated script is impossible by construction. macOS service names come from networksetup -listallnetworkservices output (not from IPC) and are single-quoted with quote-escaping when spliced into the script.

Where the address comes from (DEC-12). The epic forbids a hardcoded proxy port and a new API endpoint, so the proxy address is frontend configuration mirroring the API base chain: window.__TRAWLER_PROXY__ → sessionStorage → VITE_TRAWLER_PROXY → default 127.0.0.1:7420. defaultProxyAddr() lives beside defaultBaseUrl() in api.ts — one home for "how the app learns addresses". Snippets and the Rust command receive the address as data; setup.ts stays pure.

How universal can the address be? Two layers — and the snippet is only the second. Reaching Trawler is a bind question before it is an address question:

  • Bind (core, not this epic). The core binds 127.0.0.1:7420 (config.rs). A loopback socket is unreachable from any other device whatever address you advertise. Serving a LAN device needs the core bound to a routable interface (0.0.0.0 / the LAN IP) — a real exposure decision: a decrypting MITM proxy open on the network is an interception surface, and the API's blanket CORS grant is safe today because everything is loopback (api/mod.rs). DEC-12 put "no core/API change" on this epic, so W3 cannot change what Trawler binds to — only advertise it.
  • Advertised address (what W3 puts in snippets) depends on the client's vantage:
    • Same host (system proxy, terminal, same-machine Firefox) → 127.0.0.1:7420. Correct and working today — the 90% onboarding case.
    • LAN device (phone, tablet, another laptop; Android emulator via 10.0.2.2) → needs the machine's LAN IP and the core bound beyond loopback. The LAN IP is cheap to find (UdpSocket::connect → local_addr() — stdlib, sends no packets), but surfacing it is pointless until the bind decision is made, so it rides with that decision rather than being stranded here.
    • Internet → non-goal. An internet-facing decrypting proxy is an open relay and a mass HTTPS-interception surface, and needs NAT traversal (port-forward or a tunnel). We document why not; we do not build it.

The universal hook W3 does ship is the configurable defaultProxyAddr() above: bind Trawler wherever you like, set the config once, and every snippet + the auto-set follow — no hardcoded port anywhere. Making the LAN case easy (auto-detect and show the LAN IP) is gated on the bind / exposure decision, now raised as an epic open question.

What the manual path looks like to the user. "Set it up manually" is not a wall of prose — it is the same stepper card, driven by the client selector:

  • A client dropdown defaulting to their detected OS; picking a client (Firefox, terminal, a phone) swaps the card to that client's instructions.
  • Numbered steps + a one-click Copy of the exact command, with the real configured address already filled in — nothing to hand-edit, no <proxy port> placeholder to decode.
  • On an auto-capable host the one-click Set system proxy button sits above those steps; the steps stay as the fallback and as the way to configure any other client from the same screen.

The Verify step (W4) is what makes manual bearable. The user never has to judge whether they got it right: the moment a real decrypted flow arrives the check flips green and the list appears. Manual setup gets the same closed-loop confirmation as the one-click path — proof by capture, not a self-reported checkbox.

Windows runs unelevated — deliberately. WinINET's proxy is per-user (HKCU\Software\Microsoft\Windows\CurrentVersion\Internet Settings), writable without admin rights. Elevating would be worse than unnecessary: UAC can run the write as a different (admin) account and set the proxy in the wrong user's hive. Consent here is the in-app button click itself — the OS has no prompt to add, and nothing is silent: the button says exactly what it will do. After the two reg add writes, a fixed PowerShell one-liner calls InternetSetOption (SETTINGS_CHANGED then REFRESH) so running WinINET apps pick the change up immediately instead of at next poll. macOS keeps W2's osascript elevation: networksetup writes need admin, and every enabled service (Wi-Fi, Ethernet, …) is set in one elevated compound script — one password prompt, both web and secure-web proxies, matching what Charles/mitmproxy do.

Turning it off matters more than turning it on. A system proxy left pointing at a stopped Trawler breaks the machine's connectivity, so the step always exposes per-client turn-it-off steps in a details fold (like W2's certificate removal). Each is the exact inverse of what the set path did:

  • macOS — networksetup -setwebproxystate '<service>' off and -setsecurewebproxystate '<service>' off on each enabled service: keeps the saved host/port but stops routing through them.
  • Windows — reg add … /v ProxyEnable /t REG_DWORD /d 0 /f: flips the WinINET proxy off (0 = disabled) without deleting the address.
  • Terminal / CLI — unset HTTPS_PROXY HTTP_PROXY: clears the environment variables the snippet exported.
  • Firefox / devices — the guided text names the setting to switch back to "No proxy" / off.

Doing that revert automatically — on app quit, and reconciling a stale proxy after a crash — is real app-lifecycle scope (a symmetric unset_proxy command + Tauri exit hooks + a "we set it" marker so we only ever revert what Trawler set). The Owner asked for it; it is split into its own W5 rather than bloating this step. Re-running Set system proxy is safe and idempotent: the same values are simply written again.

Turning it off without quitting is the same unset_proxy command exposed as a manual control — a "stop routing through Trawler" toggle — which also lands in W5, alongside the automatic revert. No core change: it just clears the system proxy, so traffic flows normally until you switch it back on. That is distinct from pausing capture (proxy stays up, recording toggles off — the Charles "stop recording" model): that needs a core capture-toggle + a control-API endpoint the onboarding epic deliberately doesn't add, so it is a separate future epic. If the intent is just "stop intercepting my traffic," the manual proxy-off covers it with zero core work.

One auto-capable predicate, renamed. "This OS has a one-click local setup path" is one concept covering both steps (macOS + Windows, per the epic's client table), not two — W2's canAutoInstall(os) is renamed canAutoSetup(os) and shared, rather than growing a duplicate canAutoSetProxy with the same body. Host detection stays W2's hostOs() UA check; Rust still decides from std::env::consts::OS at the moment of action.

fn parse_services(list: &str) -> Vec<String>
//   `networksetup -listallnetworkservices` output → enabled services
//   (drops the "An asterisk…" header and any *-prefixed disabled service)

fn set_proxy_commands(os: &str, services: &[String], host: &str, port: u16) -> Option<Vec<Vec<String>>>
//   macos   → [ one osascript-elevated compound script:
//               networksetup -setwebproxy '<svc>' <host> <port> && networksetup -setsecurewebproxy '<svc>' <host> <port>
//               … for every enabled service — one password prompt ]
//   windows → [ reg add "HKCU\…\Internet Settings" /v ProxyServer /t REG_SZ /d <host>:<port> /f,
//               reg add "HKCU\…\Internet Settings" /v ProxyEnable /t REG_DWORD /d 1 /f,
//               powershell InternetSetOption(SETTINGS_CHANGED=39) + (REFRESH=37) ]   // NOT elevated — HKCU
//   other   → None                                                                   // snippets only

#[tauri::command]
fn set_proxy(host: String, port: u16) -> Result<(), String>
//   reject host !~ ^[A-Za-z0-9.-]+$ (elevated-shell injection guard) →
//   (macos: run -listallnetworkservices, parse; err if none) →
//   run each argv in order, every one must exit 0 → map status/stderr like install_ca
// ui/src/api.ts — config resolution (DEC-12), beside defaultBaseUrl()
defaultProxyAddr(): string        // __TRAWLER_PROXY__ → sessionStorage → VITE_TRAWLER_PROXY → '127.0.0.1:7420'

// ui/src/setup.ts — pure, no I/O
type ProxyTarget = 'macos' | 'windows' | 'linux' | 'firefox' | 'terminal' | 'ios-sim' | 'android';
canAutoSetup(os: HostOs): boolean          // renamed from canAutoInstall — shared by trust-ca + set-proxy

Expected (done when)

  • On macOS/Windows the set-proxy step shows a Set system proxy action; clicking it invokes set_proxy with the configured address — macOS: one elevation prompt sets web + secure-web proxies on every enabled service; Windows: HKCU registry + refresh, no elevation. All exit 0 → step done; declining or a non-zero exit → failed, with the snippets still visible.
  • A client selector (default = detected host) shows the correct snippet / guided steps as text for every client in the matrix; each command-shaped snippet has a Copy that puts the exact command — carrying the real configured address — on the clipboard.
  • No hardcoded proxy address anywhere in component code: defaultProxyAddr() resolves global → sessionStorage → env → default (DEC-12), and both the snippets and the Tauri invoke consume it.
  • The Rust builders emit the exact per-OS argvs (compound elevated networksetup script · unelevated reg+refresh) and None elsewhere; host validation rejects shell metacharacters; service parsing drops disabled entries. Unit-tested, cargo test in ui/src-tauri, headless.
  • Turn-it-off steps are visible per client; the onboarding machine is untouched — a successful set does not mark capture proven; only W4's flow does. cargo xtask ui build (tsc) clean.
