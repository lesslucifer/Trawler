Outcome

Delivered as planned, and smaller than planned — the W1 state machine already carried every event (captured, not-detected, re-invoke, exit), so W4 is pure wiring: one detector predicate + two effects in App.tsx, plus an HTTPS-serving e2e harness. No machine change, no core / API change. Against the W4 requirement and its "done when":

One detector, the flow's own truth. flow.ts gained isDecryptedHttps(flows) — flows.some(f => f.uri.startsWith("https://")). The MITM rewrites a decrypted request to absolute form with its real scheme, so an https:// URI is proof the exchange was intercepted and decrypted; a plain proxied request stays http:// and does not count (epic: "Works" = a decrypted HTTPS flow). Both the launch check and the live check share this one definition of "done".

Launch self-test + live check, two effects. The W1 placeholder that dropped every fresh launch into onboarding is gone. On mount (while phase==="checking") App reads listFlows({}) once: a decrypted flow already present ⇒ captured (straight to the list, everProven latched); else ⇒ not-detected (onboarding). A second effect observes useFlows' flows — which already refetches on every SSE event — and, while onboarding and not yet ever proven, dispatches captured on the first decrypted flow. No second EventSource; the live check rides the hook's existing stream.

Reveal is the existing phase branch. captured sets phase="proven" and App's pre-existing phase !== "proven" check reveals the list — Verify red → green → list, never re-forced. The status dot still re-invokes setup; Back to flows returns because everProven latched.

Deviations

Live check gated on !everProven, not just "unproven". A naive "unproven && a decrypted flow exists ⇒ captured" bounces a user who deliberately re-invokes setup (the dot / help path) straight back to the list, because the proving flow is still in the list. The live check therefore fires only on the first-ever capture (phase==="onboarding" && !everProven); after that, the dot and Back-to-flows drive navigation. Caught while tracing the re-invoke path, covered by a dedicated integration test.

The e2e harness now serves HTTPS. The old harness origin was plain HTTP, so its /hit produced an http:// flow — which by design does not prove capture, so it could never turn Verify green. The harness now generates a CA, signs a localhost leaf, serves the origin over TLS (axum-server), feeds the CA to the core via upstream_extra_root_pems, and has /hit proxy through the core while trusting the core's own /ca.crt — the exact pattern from e2e_capture.rs. /hit now records a real https://localhost:<port>/ decrypted flow. Still hermetic: ephemeral ports, tempdir CA, self-signed origin CA, no public network.

UC-4's flows.spec.ts folded into onboarding.spec.ts. Post-W4 a fresh launch shows onboarding, not a bare empty list, so UC-4's "empty list" premise no longer holds in isolation — and wdio's alphabetical spec order would have run the old list spec before onboarding. The list/filter/append checks now run after the journey reveals the list, in one coherent spec, and the old file is deleted. The revealed row now shows localhost (the HTTPS origin's SNI host), not 127.0.0.1.

Dot re-invoke dropped from e2e, kept at integration. The 10px status-dot click interaction did not drive reliably through WebKit WebDriver; the behaviour it asserts (re-invoke re-opens setup and does not bounce, Back-to-flows returns) is fully covered by an integration test in jsdom. The e2e keeps to its stated role — the capture-driven journey spine — rather than re-proving a unit-covered interaction.
