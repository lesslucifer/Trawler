E-DFLOW.W1 Run #1 — flow detail panel

The base design flow run by hand on the flow detail panel — no harness, no rules, no registry. Six stages, a friction log per stage, a lo-fi draft mockup, a cross-check against the shipped panel, and the distilled findings.

Design run · 2026-07-16 · Trawler · T3 (docs/work/) · wu/design-flow/base-flow-hand-run · flow: docs/work/2026-07-16-dflow-w1-plan.html

How to read this

Each stage below has its artifact (the design output) and a friction log (every moment the flow made me reach for something absent, or felt ambiguous). Friction is tagged →W2 registry, →W3 rules, or →flow the stage sequence itself. The friction log is the point — it becomes the findings that seed the rest of the epic. Per D2 the panel is designed fresh; the shipped FlowDetail.tsx is consulted only in the cross-check.

1 · Frame

Purpose. Show one captured HTTP(S) flow in full — request and response — so a developer debugging API traffic can see exactly what went over the wire and act on it. It is the detail region of the list→detail shell (reads GET /flows/{id}).

Given capabilities (functional input — received, not designed): show one flow (request + response, each with headers + body) · copy the flow as a runnable curl · inspect each body by type (JSON/XML/image/form/hex), raw ↔ decoded. The design frame below decides how those are housed.

The frame is a driver table: each driver forces a design consequence, the row carries the why, and the success criterion that verifies it sits in the last column. This is what every later stage designs through.

Friction / resolution:
  • →flow Resolved (manager, several rounds). Frame's artifact went through: purpose+state-list → functional requirement list → design brief → mindmap (overwhelming) → the driver table above. The settled shape: each driver (goal / constraint / quality) forces a design consequence, the row carries the why, and the verifying success criterion sits in the last column. Functional capabilities are stated once as input; general principles (state handling, a11y, spacing) live in the rulebook; only case-specific drivers appear here, overriding a principle on conflict.
  • →flow Ids dropped. The coded ids (G1/C2/SC3…) read as noise once every stage cites drivers by name; the row's driver name is citation enough. So the harness coverage-check keys off the driver rows, not id strings.
  • →flow Representation is load-bearing. The winning form was found only by A/B/C/D comparison in a side file — walls of text, over-compaction, and mindmaps all failed the human reader first. The flow should expect a stage's artifact form to be chosen, not assumed.

2 · Layout

Layout consumes the Frame — every region traces to a driver (goal / constraint), nothing placed by taste. This is a region draft (zones only); the fuller element mockup is stage 5, a separate draft. An ASCII sketch carries it — draw.io was trialled and dropped, it added no value over this.

│ A · Outcome bar     (fixed)   │  ← triage: outcome at a glance
├──────────────────────────────┤
│ B · Overview  [ copy curl ]   │  ← URL wraps (narrow) · curl subordinate
├──────────────────────────────┤
│ C · REQUEST                   │  ← debug: the bulk
│    ▸ headers  (collapsible)   │
│    ▼ body     (focus)         │
├──────────────────────────────┤
│ D · RESPONSE                  │  ← mirror · degrades when in-flight
│    ▸ headers  (collapsible)   │
│    ▼ body / "awaiting…"       │
└──────────────────────────────┘
Derived decision — collapsible headers. Content priority ranks bodies › headers, but reading order puts headers first. Flat, a long header block buries the body (hurts the debug goal); below the body, headers need scrolling-past (breaks "find a header without scrolling past a body"). Compact/collapsible headers resolve both — a decision that fell straight out of the Frame, not present in the first cut.
Friction:
  • →flow Consuming the Frame changed the stage's character — zones now derive from named drivers (triage → outcome bar, narrow → single column) instead of asserted "priority" prose. Much less invented. The flow only works once Frame states drivers each stage can point back to; a vaguer first-cut Frame left Layout hand-waving.
  • →flow Layout and Elements still bleed — I reach for element names ("status pill") while zoning. The boundary "Layout = kinds of content, Elements = the actual components" needs stating, or the two stages merge.
  • →W3 Two conventions I asserted with no rule to cite: fixed outcome bar + scroll the body (detail-panel scroll behavior) and request-before-response ordering. Both should be stated rules so every two-leg/detail screen agrees.

3 · Elements

Each element gets a reusability tier from the epic's ladder (design-flow-discussion.html): T0 Foundation (external) · T1 Primitive (no business logic) · T2 Widget (has business logic) · T3 Local · T4 Composition (build local, break down). Collection = T1+T2. The collection is empty in W1, so every tier call is a propose-new proposal, not a lookup.

Friction (what the tiered catalog above can't itself show):
  • →W2 The collection is empty, so every tier call is a propose-new proposal, not a lookup — and the shared components the "used in" column exposes (header table, copy button, body viewer, each in two places) are the first reuse candidates the registry must hold.
  • →flow The flow needs two things it lacked: a per-element tier verdict as a first-class artifact column, and a break-down step for T4 compositions (header table, body viewer) whose parts are the real reusable seeds — feeds W4.

4 · Interaction

Component defaults (a button's hover/focus, the copy button's confirm, the pill's tones, the body toggle) stay with the components. This stage describes the use-cases — what the user actually does with the panel — each grounded in a Frame goal, with the user's action and the screen's response:

Move to the next—clicks × (close)dismisses the panel, returns focus to the flow list
Friction:
  • →flow The first cut mis-defined this stage. It asked for "each element's trigger + states", which merely re-derives what the components already own. The stage's real output is the feature's use-cases — user tasks grounded in the Frame goals. W4 should redefine Interaction as use-case-driven — the single biggest flow finding.
  • →flow State handling folds in as use-cases, not a separate lens: "watch a live call" is the in-flight state; the missing error case shows up as a use-case with no defined screen response — a real domain gap the flow can only route to findings.
  • →W3 Empty/placeholder wording ("none", "loading…", "awaiting response…") invented ad hoc. Without a wording rule these drift screen to screen. Soft rule.
  • →W2 Per-element defaults (hover/focus/active/disabled, confirm swap) are component-level concerns — they belong to the registry entry, which is exactly why they don't recur here.

6 · Tune

Tune notes — stepping back from the assembled mockup:

  • Copy-as-curl weight. Before: a full-width action taking its own visual band in B. After: a small right-aligned button so the URI stays the hero of the overview — ideally an icon, but none fit, so the word curl carries it. (The shipped panel gives copy-as-curl a whole titled section — my instinct is the opposite; flagged in cross-check.)
  • Zone labels. Before: REQUEST / RESPONSE as plain caps headings. After: keep, but the identity bar already implies direction; the labels earn their place only because the narrow column separates C and D by a lot of vertical scroll. Kept — this is a genuine loop back to Layout, confirming the tune-back arrow is real.
  • Header + body proximity. Within each zone, headers then body reads correctly; no change.
  • In-flight honesty. Before: response zone hidden entirely. After: show zone D with an "awaiting response…" placeholder, so the structure doesn't jump when the response lands.
Friction:
  • →flow Tune genuinely sent me back to Layout (the zone-label decision) — so the loop-back is not a no-op. This validates keeping Tune as a distinct stage (the plan's open-question default holds, now with evidence).
  • →W3 Every tune call ("hero", "weight", "proximity", "hierarchy") is a soft judgment with no rule to cite. These are precisely the Tier-3 soft rules the rulebook must enumerate so Tune isn't pure vibes.

Findings — the seed lists

The friction log distilled and ranked. This is what W2 / W3 / W4 consume.

For W2 · component registry

  1. Confirmed reuse candidates (each surfaced ≥2×, or already reinvented in shipped code): header key/value table, copy-with-transient-confirm button, status pill (exists as StatusPill), section container (exists as local Section), icon button (close ×).
  2. Composition needs tiers: the body viewer is a component built of lower components (toggle, buttons, hex grid). The registry model must express "made of" — validates the five-tier Foundation→Compositions scheme.
  3. The tier verdict is now a catalog column (T0–T4 per element); the registry plugs into it — with the collection empty, each T1/T2 is a propose-new seed and each T4 (header table, body viewer) carries a break-down list of the lower-tier parts to seed.
  4. Discovery gap: the only way I found the existing StatusPill/Section was reading source. The index-file-an-agent-loads is exactly the fix.

For W3 · tokens + rules

  1. Hard (Tier-1 checkable): every interactive element declares hover/focus/active/disabled; monospace for wire data (URI/headers/bodies) vs UI font for chrome; status tone from tokens, never raw hex; a spacing scale (I invented paddings/gaps with nothing to cite).
  2. Soft (Tier-3 judged): visual weight ∝ importance (the copy-curl disagreement); related things grouped (request/response zoning); consistent, professional placeholder/empty wording ("none" / "loading…" / "awaiting response…").
  3. Ordering conventions: request-before-response; headers-before-body — should be stated rules so every two-leg screen agrees.

For W4 · the flow itself

  1. Frame artifact = a driver table (decided this run, several rounds). Columns: driver → design consequence → why → checked by, grouped goals / constraints / qualities, capabilities stated once as input. The key distinctions the T1 flow doc must carry: functional requirements are Frame inputs, the Frame's own output is the design lens (goals = hierarchy, qualities = Tune's yardstick); each success criterion rides in the driver's "checked by" cell (it verifies that driver's consequence); and no coded ids — drivers are cited by name, the harness coverage-checks the rows.
  2. Two requirement levels, cleanly split: general design principles (states, a11y, spacing) live once in the rulebook; case-specific goals/qualities/constraints live in the Frame and override on conflict. The first-cut flow had nowhere for either "survive being narrow" (now C1) or live-traffic in-flight (now C2).
  3. Layout and Elements bleed together. Zoning and naming-what's-in-the-zone happen at once. Either merge, or sharpen the boundary ("Layout = empty boxes only").
  4. Elements = a tiered component catalog. One row per distinct component with a tier verdict (T0–T4; T1↔T2 split = business logic), a "used in" column that exposes reuse, and a break-down step for T4 compositions whose lower-tier parts are the real registry seeds. The first-cut "region → element → role" inventory carried none of this.
  5. Interaction = the feature's use-cases. Biggest redefinition: the first cut asked for each element's trigger + states, which just re-derives what the components already own. The stage's real output is the use-cases — user tasks grounded in the Frame goals (triage/debug/reproduce), each with the user's action and the screen's response. State handling (in-flight/error) folds in as use-cases; per-element defaults stay with the registry.
  6. No escalation path for upstream gaps. The undefined error state is a domain/UX gap the flow found but can't route anywhere except findings. A real gate may need a "blocked-on" output.
  7. Tune is load-bearing. It looped back to Layout with a real change — keep it distinct (open question resolved, with evidence).
  8. Artifacts must be visual, not prose. The human reviewer is the bottleneck: walls of text failed review at Frame, Layout, and Elements. Every stage needs a picture-first form with prose demoted to a compact table — settled this run: a driver table for Frame, an ASCII region sketch for Layout (draw.io trialled and dropped — no added value), an interactive tree + tier catalog for Elements, and a native HTML/CSS build for the Draft mockup (draw.io trialled again and dropped — a light-canvas island, static, poor diffs). The flow should mandate a visual per stage; W2/W7 formalise the house forms.
  9. The mockup does design work, not just assembly. Building it in real HTML forced detail decisions the earlier stages never surfaced: click-to-copy + long-URL wrap on the URI, a copy affordance per body, raw/decoded semantics (decompress+charset, then pretty-print — not the same as "formatted"), and collapsible headers. A picture (ASCII/draw.io) would have let these slide. So Draft mockup is a decision stage, and these specifics feed W2's body-viewer (T4) breakdown.

Verdict

The six-stage flow ran end to end and produced a coherent lo-fi draft mockup of the flow detail panel without a harness — so the skeleton holds. It also earned its keep by surfacing (a) a tiered reuse vocabulary, (b) a first split of hard/soft rules, and (c) several concrete weaknesses in the flow itself — including two stage redefinitions (Elements → tiered catalog, Interaction → feature-specific interaction only) — exactly the evidence W2/W3/W4 were waiting for. Nothing distils upward yet; that is W4's call after the substrate exists.
