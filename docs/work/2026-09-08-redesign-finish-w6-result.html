Delivered, to the plan's sentence. The shell renders at 520px in a 1440 window, a status class narrows the list end to end against the real core, and a failed fetch is stated rather than swallowed. Two things the design left to the build

the pane's failure, minus one cause

A 404 is not the shell's silence

W4 sent useFlowDetail's swallowed failure here and said the band explains the pane's silence. But getFlow also 404s when the ring drops the selected flow — a cause W4's own absence table names and reserves for the pane's design, with the lexicon's “no longer captured” held for it.

So failed excludes a 404 and means only no answer. Folding the drop into the band would have made the shell claim an unreachable core every time the ring evicted a selected row, on a core that was answering perfectly.

the signal, not just the sentence

The band has to appear while the user does nothing

W4's Interaction table gives the unreachable row a user act of “nothing — the core dies under the window”. Nothing in the shipped code could honour that: the list refetches on SSE events and on filter change, and a dead core sends no events — so the band would have waited for the next keystroke to appear.

The dropped stream is the only signal that arrives unprompted, and it was a fourth swallowed failure: api.stream ignored the EventSource's own errors entirely. It now reports onDown/onUp, and the e2e proves the band appears with no act at all. This is the row-4 family, extended by what the row's own design required — recorded here rather than folded in silently.

How the two sentences are told apart

W4 designed two causes and left the client no way to distinguish them: listFlows threw the same untyped Error for a dead socket and a refused query. One typed error settles which answer arrived; the two facts it feeds are held apart in two values, which is what five review rounds were about.

What the API didWhat reaches the callerWhat renders
answered 2xxthe listrows, no band
answered 400ApiError(400)4xz is not a status · type a code (404) or a class (4xx) — in the row region, no retry, and the value named is the one that was asked
answered anything elseApiError(status)the connection statement — a core not behaving like the core leaves the rows just as unverified
did not answera plain TypeError, never an ApiErrorthe connection statement
The absence of the type is the signal. instanceof ApiError means the API answered; anything else means it did not. That is why the error carries a plain status: number rather than a nullable one — a null status would have been a second way of saying what the type already says, and a caller could forget to check it.

Deviations from the plan

WhatWhy
ApiError.status is a plain number, not the plan's number | null. Writing it showed the null was redundant: a fetch that never answers rejects with a TypeError and never constructs an ApiError at all, so the type's own presence already carries “the API answered”. A nullable field would have been a second encoding of the same fact, and one a caller can forget to check. The discrimination the plan specified is unchanged; only its representation got smaller.
A fourth swallowed failure was opened — the SSE stream's own errors. Row 4 named three .catch sites, but W4's Interaction table requires the band to appear with the user doing nothing, and none of the three can fire on a dead core. Named in full under two things the design left to the build rather than folded into row 4's count.
A new module, NotAnswering.tsx, that the plan's file list did not name. The sentence is mounted in two zones — the band and the row region — and FlowList importing it from App would be a cycle. One definition, two placements, which is exactly the shape W4's own mockup used. Cited to the design as a new surface.
Focus lands on the main region, not on the listbox. W4 says “focus moves to the list region”. The listbox exists only when there are rows, and a successful retry can return an empty list — so targeting it would leave focus on <body> in exactly the case the rule exists to prevent. main is the zone, and it exists in every state the retry resolves into.
The e2e harness gained two origin routes and an abrupt /kill. A status-class assertion needs a capture holding more than one class, and the harness produced only 2xx. And /stop is a graceful shutdown: it waits for in-flight requests, and an SSE stream never finishes — so it would hold open the very connection the assertion is about. /kill exits the process, which is what “the core died under the window” means.
The rejected sentence is tone="mute", with no ⚠. W4's absence table gives the glyph to the two not answering rows and not to this one, and its wording is explicit that a rejection “is a rejection rather than a failure — the API answered, and said no”. Mute puts it with the two inherited empties, where it belongs.
Three test doubles in useFlows.test.ts were rebuilt per render at first, and one test caught it. Constructing the fake API inside the renderHook callback gives the hook a new api identity every render, so its effects re-ran forever and never settled. The file's pre-existing tests already build the double once, outside; the new ones now match. No production code changed — the defect was only in the new tests, and it is recorded because a passing-by-luck test is worth naming.

Review — five rounds, and the one mistake under all of them

Rounds 2, 3 and 4 each found defects inside the previous round's fix. That pattern was the finding. Three facts — whether the core answered, what it said, and whether one flow's fetch produced a flow — were encoded in two values with precedence baked into the encoding, so every fix traded one wrong state for another. Round 4 stopped patching and split them; rounds 5 and 6 judged the split. The rounds below are kept in order because the sequence is the evidence, not the noise.
RoundVerifiedWhat it found
13 of 10 A latched pane failure spoke for the list, never expired, and a straggling refresh could un-do a retry. Fix: pass the list's real failure through; count listings to retire a stale pane failure; a generation guard.
22 of 2 Both inside round 1's fix. The listing counter cleared the pane's failure without re-fetching, so the pane sat on “loading this flow…” with nothing saying otherwise; and with the list empty for its own reason, neither zone stated the pane's failure at all. Fix: the band becomes the connection alone; the pane states its own fact; the counter is deleted.
34 The flip side: with the core down and a flow selected, band and pane both raised a warn for one cause — the second voice the run refused. Plus the stream overwriting a refusal, a retry's focus claim that never expired, and a test title arguing the opposite of the code.
42 of 2 Both inside round 3's fix. Gating the pane on the connection meant a core going silent after the pane failed put “loading this flow…” back over a settled fetch; and refusing to record silence over a refusal lost real outages. Fix: the model, not the encoding.
53 Correctness and design converged from opposite directions on the same thing: the build had invented a precedence the run never made, hiding a refusal behind the silence. Plus the refusal quoting the wrong value, and a trailing clause claiming things about the region below that were not true of it.
60 Clean, and by case analysis rather than by the tests passing: the band and the row region are structurally mutually exclusive (one branch requires refused !== null with no rows, the other requires refused === null), and flows.length > 0 && refused !== null is unreachable because every path that sets a refusal empties the rows in the same update. The one genuinely reachable both-facts-true state is the one round 5 added a regression for.

Round 1 — what it found, and what it cost

Six finders over the build's own diff, then a verifier per candidate. Ten candidates, three verified. All three were the same underlying mistake seen from different angles, and it was mine: the pane's failure and the list's failure are two independent facts, and I folded them into one boolean.

Verified findingWhat it actually didFix
A latched pane failure spoke for the list
correctness + altitude, important		 failure={notAnswering ? { kind: "unreachable" } : failure} synthesized a connection failure out of detailFailed and handed it to FlowList, which gives it precedence over everything. A 500 on one flow's fetch, followed by a mistyped status, replaced “4xz is not a status” with “trawler is not answering” and a retry button that could not help — defeating the precedence rule this WU exists to build. The list's real failure is passed through unsynthesized. The band still folds both causes; the row region never does.
The pane's failure never expired
altitude, important		 useFlowDetail resets failed only when api, id or nonce change — nothing clears it when the list recovers. So one non-404 pane failure pinned the band up permanently on a healthy core, still claiming “the rows below are the last it sent” while the list was being answered live. useFlows counts listings that arrived; a listing that arrives is proof the core answers, and it retires an older pane failure without re-fetching anything.
A straggling refresh could un-do a retry
correctness, important		 Four things trigger a listing and refresh had no sequencing guard. Before this WU that only risked stale rows; now the loser also writes failure, so a slow straggler resolving after a successful retry flips the band back on immediately after the user watched it clear. A generation counter: only the newest request may write.

Round 1, refuted and worth recording as refuted: that the three new test doubles in useFlows.test.ts should be one parameterized builder (they follow the file's existing one-double-per-concern convention, and merging them yields a config object with five knobs); that shellApi duplicates mockApi (they are different control modes — raw answer injection versus store-and-filter simulation); that the retry's unconditional nonce bump is a defect (it is the design's “one cause, one retry”, costing one idempotent GET on a rare user-initiated click); that the detail pane still showing “loading this flow…” is a bug (the design puts that sentence in A′ deliberately — “covered by A′, said once”); and a duplicated comment. The design finder returned clean: no unexplained departure from the run, no unwarranted component, no misapplied @use/@avoid.

The comment was the tell. The line above the folded boolean read “the list's fetch and the pane's fail together when the core stops answering” — true of the case the design walked through, and quietly assumed of every other case. Three of the ten candidates were that assumption being wrong in three different ways. A comment asserting an invariant the code does not enforce is worth reading as a question.
