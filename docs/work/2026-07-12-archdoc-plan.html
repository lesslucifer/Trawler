E-ARCHDOC — rework the T1 architecture doc

Collapse the bloated core-architecture.html into a lean, shape-only architecture.html: the fastest complete mental model of the codebase for an AI reader, with everything that duplicates the design doc, the use-cases, or src/ stripped out and linked down instead.

Plan v1 · 2026-07-12 · Trawler · T3 · one-WU epic (epic-plan + wu-plan)

Intent

Today docs/core-architecture.html is the T1 architecture spine, but it has grown into a second copy of half the repo: per-endpoint tables, per-type shape tables, per-file UI tables, CA/rcgen API shapes, a dependency inventory, "verified working" smoke badges, and a "what's not built" section that all restate what src/, the use-cases, or core-technical-design.html already own. That makes the doc slow to read, quick to rot, and in violation of the T1 altitude rule (documentation system: T1 = permanent and shape-level, no per-feature detail, no copied code). We rework it now into docs/architecture.html — the name the documentation system already points distillation at ("Component map or invariant changed? → architecture.html") — keeping only what makes an AI reader understand the system's shape fast and completely, and linking down for everything else. This is the current filename's last chance to earn its T1 slot before more epics distill into it.

Use-case requirements

Process/docs epic — touches no UC-* contract. No product behavior changes: the proxy, store, API and native UI are untouched. The only artifacts that change are documentation files. No use-case topic file is added or edited; the use-cases index is unaffected. (The distillation targets below are T1/T2 doc updates, not use-case behavior changes.)

Expected result

Observable after the epic, checkable by a reader who wasn't here:

  • docs/architecture.html exists as the T1 architecture doc; the old docs/core-architecture.html is deleted (new file, not a git mv — Owner decision).
  • The new doc is shape-only and generic: it describes the folder layout and file-name conventions, the runtime wiring, the request/response lifecycle, and the two-client (API-first) boundary — without naming today's specific files in prose or diagrams, so it survives the project growing. No per-type shapes, no endpoint table, no eviction algorithm, no cert API, no dependency version list, no "not built" scope.
  • It carries the two new consolidation sections: a single Technical decisions list (one short line per load-bearing choice, linking to its DEC-*/src/) and a concise Tech stack table (library → purpose, no versions).
  • The build/run section covers the whole project — backend run, front-end build/dev, test, and debug scripts — not just cargo run.
  • Every dropped-detail need is served by a link down a tier, not by silence: core-technical-design.html for rationale, the use-cases for behavior contracts, src//ui/ for mechanics.
  • No inbound link is left dangling: every reference to core-architecture.html across the whole project — docs/, README.md, the code-review rubric, and the T0 CLAUDE.md pointer — resolves to architecture.html.
  • The doc passes the htmldoc conventions (dark mode, Mermaid dark theme, stable ids, data-htmldoc-id, single htmldoc.js tag) and the documentation-system T1 rules (no copied code, no work estimates). No doc-version tag needed (Owner).

Direction (from the Owner comment round)

The rework is more aggressive than "trim", and it must be evolution-proof, not a photograph of the current early-stage tree:

  • Generic layout, no specific files. Diagrams and the layout map describe the folder structure and file-name conventions (e.g. "one module per domain concept under src/", "React app under ui/src/"), never today's exact file list (config.rs, App.tsx, …). It stays true as the project grows.
  • Cut hard. Every specific technical decision, per-type shape, per-endpoint contract, eviction algorithm, cert API, dep inventory, and the "not built" scope comes out of the body.
  • Consolidate what's cut. The dropped technical decisions are gathered into one section — a short line each, not a card grid, not a re-explanation.
  • Add a tech-stack table. One concise table: library → what it's used for.
  • Build/run covers the whole project — backend + front-end + test + debug scripts, not just cargo run.

The two new consolidation sections

1 · Technical decisions (consolidated). One section gathering every specific decision pulled out of the body — one short, direct line each, no card grid, no re-explanation. Candidates from the current doc: std-mutex over async lock · no global body-cap (per-request judged) · per-exchange handler-clone correlation · CONNECT-line guard · store owns the event bus · byte-weighted ring eviction · buffer-then-forward capture · never buffer text/event-stream · compact SSE payloads (no base64 bodies) · open CORS on loopback, read-only · decode stays view-side · /ca.crt on the API port · library + thin binary. Each line links to its DEC-* or src/ where deeper "why" lives; the section is a shape-level index of load-bearing choices, not their justification.

2 · Tech stack. One concise table, library → purpose (no versions): the proxy engine, the control-API framework, the CA/cert library, the async runtime, and the front-end stack (native shell, bundler, framework, styling). Short, direct, replaces the old dependency inventory.

Non-goals

  • No code change. src/, ui/, tests/, xtask/ are untouched. This is docs-only.
  • Not touching core-technical-design.html. It stays as the "why" doc; the reworked architecture doc links to it for rationale. (Owner picked "rename arch, keep design".)
  • No new use-case or decision records. Nothing about product behavior or a new design choice changes. The rework itself is a doc-hygiene action, not a DEC.
  • Not a redesign of the doc's information — a subtraction. The kept sections keep their proven structure and diagrams; we remove and link, we don't re-architect what survives.
