Intent

E-REDESIGN.W10 shipped Onboarding.tsx (563 lines) gated but not endorsed, and two design runs have since said the arrangement is wrong at the root: a wizard cursor over a model that observes no per-step progress, and the same target question asked three times by three independent pickers. The design that replaces it is already written and parked — E-SIMPDF ran the screen through the flow DEC-53 cut and committed the run open (data-status="draft", commit bfdc345) precisely so this epic could close it. Its review round rebuilt the screen around one platform choice: the user names what they are setting up — this machine, another machine, a simulator, a device — and every instruction below that choice belongs to it. Doing that honestly exposed what the old shape could hide by never naming a platform out loud: Trawler binds 127.0.0.1 only, so five of the eight platforms the picker offers have no address to point at and no route to fetch the certificate. This epic therefore lands two things in order — reach, then the screen that needed it — and rebuilds the setup surface from a closed design instead of from a review round's leftovers.

Use-case requirements

UC-ONBOARD is the one use case this epic changes. Contract-level, what it gains and what it may not lose:

E-ONBOARD.W1 — reach: Trawler answers off this machine

What it buildsA decision record (DEC-55) ruling that reach beyond loopback is an authorization decision, not a flag: off by default, armed by one explicit confirm, and narrower than the open CORS grant architecture.html justifies today with "adding no exposure beyond the bind address". Then the code: Config gains a listen choice, src/config.rs stops hard-coding Ipv4Addr::LOCALHOST for both servers, the control API reports the address(es) a second device can use, and /ca.crt is fetchable over that address. The Tauri shell carries the confirm, as it already does for the trust store and the system proxy (DEC-13)
Maps toUC-ONBOARD's gains reach row; the design run's first two blocked-on rows (no reachable address, nothing to render); DEC-13's rule that an OS- or host-affecting action costs one explicit confirm
Expected outcomeWith reachability off, both servers bind loopback exactly as today and the API reports no external address. With it on, a second host on the same network reaches the proxy and fetches /ca.crt, and the address the API reports is one that works. The CORS grant does not widen with the bind. Integration tests assert all three over ephemeral ports; no test touches the public network
DependenciesNone — the first WU. Everything downstream waits on it, because a mockup may not print an address that does not exist

E2E test plan

ui/e2e/specs/onboarding.spec.ts is rewritten, not extended. Two journeys, both through the real app over ephemeral ports and a local server — never the public network.

JourneySpine
this machine — the existing journey, re-aimed fresh app, nothing captured → the verdict reads nothing has reached Trawler yet → the picker already shows this machine → install the certificate → set the proxy → make one request → the verdict reads Trawler is capturing → back to flows. Proves the one thing DEC-13's invariant allows to end onboarding: a real decrypted flow
another platform — new, and the reason W1 exists pick iPhone or iPad → with reachability off the precondition says what is missing and offers no steps that cannot work → turn reachability on through the confirm → a host, a port and a certificate URL render → the probe row is absent throughout, because there is nothing here it could read

Coverage map. Each of the 8 assertions in the current spec gets a named successor or a recorded reason for retiring — the discipline E-DFLOW.W11 established. An assertion that dies with the stepper is retired with its reason on the record, never silently.

Harness note, from the roadmap. WebdriverIO's *= partial-text selector matches nothing against this app in the embedded WebKit provider and does not error — three E-RFINISH.W6 runs failed against a screen that was rendering correctly. Every assertion in the rewrite goes through a data-testid, which is what every other zone in the suite already uses.

No waiver. The epic owes an e2e and takes it. W1's core seam is covered at integration level in its own WU (tests/), not here — an e2e that drove a second host would need the network this suite is forbidden to touch, so reach is asserted against a loopback-bound second listener and the screen's rendering of it.

Open questions

QuestionProposed defaultDecided by
Does reachability bind 0.0.0.0, or one interface the user names? One named interface. 0.0.0.0 is a wider promise than the screen needs, and the screen must print an address anyway — so the user picks from what the API enumerates and Trawler listens there. It also keeps the blast radius of a mistaken confirm to one network W1 · DEC-55
Does the control API need more than the opt-in once it is reachable — a token, TLS, a narrowed CORS policy? No, and the boundary is written down. The opt-in is this epic's authorization boundary; the CORS grant does not widen with the bind. Anything finer is its own epic and leaves as a backlog row rather than as unstated debt owner, at W1's DEC round
Does the opt-in survive a relaunch? No — re-armed per launch. It matches the revert-on-quit symmetry DEC-13 already requires of the system proxy: a host-affecting state Trawler set does not outlive the session that confirmed it W1
Does the selected platform persist across relaunches? No. The run's Not-given list already says no persistence is given, so a relaunch returns to this machine. Adding it is a store question this epic does not need — and the design is honest either way W3
