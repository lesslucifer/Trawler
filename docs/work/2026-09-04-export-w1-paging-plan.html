E-EXPORT.W1 — the listing pages, and nothing that reads it notices

Opt-in limit + cursor on GET /flows, over a ring walk that neither duplicates nor skips a row when inserts and evictions land mid-page.

v1 · 2026-09-04 · Trawler · T3 WU plan · E-EXPORT.W1 · epic plan

Requirement

GET /flows accepts an optional limit and an optional cursor: with neither, it returns byte-for-byte what it returns today (the whole filtered list as a bare JSON array, newest-first); with limit=n it returns an envelope carrying at most n summaries and the cursor that fetches the next page, and following cursors from any page walks the capture with no row served twice and no row skipped, even while inserts and evictions run concurrently.

Mapping

E-EXPORT · the epic plan's W1 summary block · amends the UC-3 / UC-4 listing contract additively (paging is opt-in; the unparameterised contract is unchanged, so the embedded shell, the native app and every existing test keep working by construction) · the roadmap's "pagination" line. First in the epic because it is the only WU that touches an existing wire contract, and every later WU reads the ring through the same walk.

The wire contract

Two response shapes, selected by whether paging was asked for. A bare array cannot carry a cursor, and wrapping the unpaged response in an envelope would break every existing reader — so the envelope appears exactly when limit does. The absence of limit is the switch; cursor alone is a client error rather than a silent unbounded read, because a client that sends a cursor believes it is paging.

What the cursor is, and why it holds

The epic's settled question 1 fixes it: the cursor is the FlowId of the last row on the page, resolved against the ring's insertion order at read time — not an index, and not an opaque blob. The store walks order newest-first, drops everything up to and including the cursor id, then takes the next limit matches. One lock for the whole walk, so a page is a consistent snapshot of the ring.

What happens mid-walkWhy the invariant survives
a flow is inserted after page 1 was served it lands at the newest end, ahead of the cursor, so the next page never reaches it. Newer-than-the-cursor rows are outside the walk by construction — no duplicate. The client learns of it on /stream, which is what live-tailing is for; a paged read is a read of the past.
rows older than the cursor are evicted they are simply gone from order; the walk yields what remains. A row that no longer exists cannot be skipped — the capture no longer holds it.
the cursor row itself is evicted the id is not found in order, so the walk has no position to resume from. It returns an empty page with next_cursor: null — an honest "the capture no longer reaches back that far", never a silent restart from the newest row, which would re-serve every row the client already has.
the cursor names a row the filter excludes the cursor is a position in the ring, resolved before filtering, so it is valid regardless of the filter — a client may legitimately narrow the filter between pages. Rows after it are filtered normally.

Expected result

The epic's expected result 5 holds, and nothing else moves:

#Observable after
1 curl 'http://127.0.0.1:7421/flows' returns exactly what it returns today — a bare array, whole filtered list, newest-first. No existing test changes, and the embedded shell (src/api/ui.html) and the native app (ui/src/api.ts) are untouched files in this diff.
2 curl 'http://127.0.0.1:7421/flows?limit=2' returns two summaries and a next_cursor; following that cursor repeatedly walks the whole capture and ends with next_cursor: null, every row seen exactly once.
3 Paging composes with every existing filter: ?host=x&limit=2 pages the filtered set, not the whole ring.
4 A malformed limit or cursor, and a cursor sent without a limit, are refused 400 with a reason naming the parameter — never an unbounded read, never a panic.
5 Inserting and evicting between pages never duplicates or skips a row among those the capture still holds; an evicted cursor ends the walk rather than restarting it.

Test plan

LevelWhereWhat asserts what
unit src/store.rs page against a seeded ring: the first page is the newest n; a cursor yields the following n; the last page reports no further cursor; a page under a filter pages the filtered set; an unknown/evicted cursor id yields an empty page rather than the newest rows; a limit beyond the ring size returns everything once. Byte accounting and the newest-first order are already proptested — page joins that family below rather than beside it.
unit src/store.rs (proptest) the no-duplicate / no-skip invariant. Over arbitrary interleavings of inserts, evictions (via the byte cap) and page reads: the concatenation of every page walked to exhaustion contains no id twice, and contains every id that was present at the start of the walk and never evicted during it. This is the WU's central claim and it is proven as a property, not by example.
unit src/api/routes.rs the parameter contract at the handler boundary: no limit ⇒ the bare array; limit ⇒ the envelope; limit=0, a non-numeric limit, a non-uuid cursor, and a cursor without a limit each ⇒ 400 naming the parameter.
integration tests/api.rs the WU contract over the real router. (a) GET /flows on a seeded store returns the identical JSON it returned before this WU — the unparameterised shape is locked, not merely believed; (b) walking ?limit=2 by cursor to exhaustion yields the same id sequence, in the same order, as the single unpaged read — paging is a re-slicing of the listing, never a second listing implementation; (c) the same equivalence under a filter; (d) each 400 case over the router.
e2e — waived at WU level: the epic's e2e (tests/e2e_export.rs, step 2 — "GET /flows?limit=1, then follow the cursor to the end · every captured flow seen exactly once") covers W1 end-to-end through the running system over real proxied traffic, and lands with the epic per its e2e plan. Nothing about paging is provable at e2e level that the epic's own step does not prove; a second e2e boot for one query parameter is duplicated cost, not coverage. Waiver reason recorded on the test/v2 note.
Hermetic per the testing standard: every test here builds its own Store or drives the router in-process via tower::ServiceExt::oneshot — no ports, no files, no network.

Shape of the change

FileChange
