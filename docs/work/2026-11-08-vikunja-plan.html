E-VIKUNJA: Vikunja as the router↔owner surface

Replaces the abandoned Obsidian-Kanban router surface (E-KANBAN) with a self-hosted Vikunja instance, after a retro and a tool survey ruled kanban columns out.

Draft v1 · 2026-11-08 · Trawler

Why this epic exists

E-KANBAN stood up an Obsidian-Kanban board as the router↔owner interface. It worked mechanically, but broke down on task coordination: column moves are a lossy signal (Done vs Approved had to be patched after a near-miss), and card text can't carry comments/decisions without a side rule. Full retro: docs/.archive/kanban-router-retro.html (once archived) — see the owner's own survey answers there for the root complaint: "lost context/nuance" and "ambiguous signals."

A tool survey (Gitea/Forgejo, Vikunja, git-bug, Redmine, Huly, Plane — verified against primary docs, not blog summaries) ranked Vikunja first: native reciprocal blocking/blocked-by task relations, comments on the same object as the task, single-binary + bundled SQLite footprint, a real webhook system with typed events, and an existing third-party MCP precedent for AI-driven updates.

Owner's rulings (apply exactly)

QDecision
MappingOne Vikunja project total. Each epic is a parent task; each WU is a subtask of its epic (Vikunja's parent/child relation). Blocking/blocked-by relations express sequencing and cross-epic dependencies on top of that hierarchy.
Needs-owner signalAssignee + label, not a column/bucket. When something needs the owner: assign the task to the owner and add a needs-owner label. A saved filter ("assigned to me, open, needs-owner") is the owner's single "what needs me" view. A plain comment is not itself a signal — the label is the explicit, unambiguous marker (this directly fixes the Done/Approved ambiguity kanban hit).
NotificationsReal webhook receiver. Vikunja calls a small local HTTP listener on relevant events; the listener bridges to Telegram. Chosen over reusing the poll+Telegram pattern — lower latency, and it's the owner's explicit call despite being a new standing process to host.
MigrationStart clean. Only E-APIDOC (parked) and E-KANBAN's own close-out are live; create those fresh in Vikunja. The Issues Log and the retro stay as historical git/doc artifacts, not re-entered as tasks.
Carry over from the kanban postmortem, don't re-litigate: (1) "watch X" is a standing responsibility from day one, not a per-ask action — the webhook listener needs the same immediate-relaunch + heartbeat discipline the board watcher eventually got. (2) Detection ≠ prevention — the orphan-worktree check from E-KANBAN.W4 is a pattern to port, not re-derive. (3) Verify board/task claims against real git/gate state before asserting status in a report.

Working units

E-VIKUNJA.W1 — stand up the instance

Install Vikunja locally (single binary, bundled SQLite, no Docker). Create the "Trawler Router" project, the needs-owner label, an API token for the router, and the saved filter. Write .claude/skills/trawler-router/references/vikunja-protocol.md: the authoritative spec for how epics/WUs map to tasks/subtasks/relations/labels, and the lifecycle (who creates a task, when a label goes on and comes off, what a comment vs a label-change means). This is the board-protocol.md replacement.

Test plan: doc/infra-only — no code. Exempt from test/cr; still needs mr/v1.

E-VIKUNJA.W2 — xtask vikunja CLI client

xtask vikunja: init (store token, verify connectivity), show (list open tasks, filtered), read <id>, put <id> [--label] [--assignee] [--comment] [--relation blocked-by:<id>]. REST calls only (Vikunja's JSON API) — no markdown parsing needed, unlike the old board client. Token read from a git-ignored config path, same pattern as the old ~/.config/trawler/obsidian.key.

Test plan (WU → integration): a fake local HTTP server standing in for the Vikunja API, exercising every subcommand end-to-end (request shape, response parsing, error on a non-2xx). Unit tests for request building / response parsing in isolation.

E-VIKUNJA.W3 — webhook receiver → Telegram bridge

A small standing local HTTP listener (xtask vikunja webhook-listen or similar — worker's call, state reasoning) that Vikunja's webhook config points at. Filters for events that matter (assignee = owner AND needs-owner label present; a comment added to an owner-assigned task), and on a match, prints a one-line JSON event the router can watch for (same style as the old board wait events) — actual Telegram sending stays the router's job via the Telegram plugin, same division of labor as before. Document the standing-process discipline explicitly (must survive a relaunch, heartbeat-checked) in the protocol doc from W1.

Test plan (WU → integration): a tempdir + real local HTTP round-trip — POST a synthetic Vikunja webhook payload at the listener, assert it emits the expected event line for a matching case and stays silent for a non-matching one. Unit tests for the event-matching predicate in isolation.

E-VIKUNJA.W4 — orphan check + skill wiring

Port the E-KANBAN.W4 orphan-worktree detector: scan git worktree list for epic/*/wu/*/* branches with no Vikunja task referencing them (via a stored branch-name field or convention), same honest detection-not-prevention framing. Update router-agent/SKILL.md and trawler-router/SKILL.md to route status/asks/rulings through Vikunja instead of the board; retire the board-specific routing language (the old xtask board code stays in the tree, untouched, as E-KANBAN's shipped artifact — this epic doesn't delete it, just stops routing through it).

Test plan (WU → integration): same shape as E-KANBAN.W4's — a tempdir with real git worktrees (some with matching tasks, one without) plus a fake Vikunja API, exercising the actual CLI command end-to-end.

Epic-level test plan (e2e)

With a real local Vikunja instance running: create an epic+WU pair through the CLI, drive it through needs-owner → labeled/assigned → commented → label removed (approval), fire a real webhook at the listener for each transition, and assert the listener's event stream matches exactly what the protocol doc says should happen at each step. This is the test that would have caught the kanban Done/Approved ambiguity, applied to the new model.
