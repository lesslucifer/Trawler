Two shapes

A · in-window dialog (recommended)

Settings renders inside the main webview through ModalShell, over a scrim. The shell's open = reopen main, then tell it to show Settings (the request_quit flag + event pattern, lifecycle.rs:203-212). The settings window and its geometry go.

same on every OS no unsafe no taskbar entry dark mode for free

Cost: Settings is bounded by main (min 850×600, so the 640-high panel scrolls); the quit dialog must close it first.

B · native modal window

Keep the settings window, add .parent(&main) and main.set_enabled(false) while it is open (re-enable on its destruction).

macOS: blank dummy sheet over main per-OS quirks

Cost: macOS shows a grey empty sheet sliding over main; a disabled main cannot run DEC-64's quit check (the quit lands in main) unless Settings closes first; three OS paths to hand-check.

Edge cases

CaseRecommendation
Opened twice (menu while open, tray while open)focus the open dialog; keep its page
Quit request while Settings is openSettings closes, then the DEC-64 check shows; a cancelled quit leaves Settings closed
Main ✕ while Settings is openthe ✕ is the window's, runs the usual close flow (UC-BG); the dialog goes with the window
Main window still being built (tray, windowless)the open request is a flag the new window takes on its first read, plus an event for a window that already listens
The keep-capturing ask or onboarding is already upone dialog at a time: the Settings request waits until the other dialog closes (Q5)
A setting that needs the OS (open at login) failsunchanged: the error shows inside the dialog
