Outcome

Delivered. pnpm bench and cargo xtask ui bench run the same committed suite; all three named costs carry a before number taken at the benchmark's own commit and an after number from the tip. Two of the three are paid — the time column re-renders 2.9× faster where its timestamps repeat — which is what an SSE refresh does — and is free rather than faster where they do not, and the host merge 249× — and the third is paid on the member the benchmark could show it helping (54.1×) and reverted on the member it could not. The 741 assertions that existed before this WU all pass unchanged; 21 joined them, and one more on the xtask side. Two are named regression tests for a defect this WU's own review found in it.

What the benchmark refused

Two of the plan's three proposed mechanisms did not survive measurement. Both are recorded here rather than quietly re-written, because the reason this WU was ordered benchmark-first is that neither could have been caught any other way.

refuted before it landed

Counting UTF-8 by arithmetic is slower than allocating

The plan proposed replacing new TextEncoder().encode(text).length with a non-allocating scan over code units. Measured over the same 10 MiB body: the scan runs 17.19 ms against the encoder's 14.16 ms. A native encode beats a JS loop even when the loop allocates nothing.

byteLength is therefore unchanged. A chunked encodeInto into one reused buffer did measure faster — 8.74 ms — and is recorded as a follow-up rather than taken, because after the real fix nothing calls it on a body that large except FormRenderer.

landed, then reverted

FormRenderer's cost is its DOM, not its byte count

FormRenderer was given the same size prop as its sibling and it is reverted in the same commit that added it. The pair that decided it was measured in one run, the member with the size and without: 1.9408 against 1.9577 hz at 40k pairs, and 1.9183 against 1.9332 hz at 10 MiB, where the byte count is largest and the drawn DOM identical. Both sit inside that run's ±1.7% error. (The table above reports a different comparison for the same member — this WU's whole before against its tip — and its noisier ±7.1% is the same verdict read another way.)

The cut leaves it drawing roughly 6000 KeyValueRow nodes, ~520 ms, and the byte count is ~3% of that. The epic's rule is explicit — a fix the benchmark cannot show helping is reverted, not kept because its sibling's worked.

diagnosis corrected

The Set rebuild was never the cost

E-REDESIGN named merge's new Set(known) rebuild alongside the URI re-parse. known holds a handful of hosts, so that rebuild is noise; the 5000 new URL() parses were all 96 ms of it. The Set is left exactly as it was.

Splitting the two also priced them: even where the memo never hits, dropping toRow's discarded pathname + search concatenation is worth 2.09× on its own.

Deviations from the plan

PlannedWhat happened, and why
The benchmark commit touches no src/ merge gained an export keyword in it, and nothing else. The alternative was to benchmark a copy of merge written into the bench file, which would drift away from the code it claims to speak for. No behaviour edit is in that commit, so the baseline it records is still one nothing was tuned against.
Cost 3 is byteLength made non-allocating Refuted — the scan is slower than the encoder (17.19 vs 14.16 ms). The fix taken is the one the epic plan's own sentence names: a size the fetch already knew. BodyViewer holds the bytes, HexRenderer has always passed their count that way, and TextRenderer now does too. byteLength is untouched.
Both character-rendered members are fixed Only TextRenderer. FormRenderer's half was written, measured, and reverted — see above. This is the plan's own stated discipline firing, not a scope cut.
Cost 2 is the Set rebuild plus the URI re-parse Only the re-parse existed as a cost. The Set is untouched.
Unit-test the day/year boundary helper directly Tested through the component instead — the bounds are asserted as rendered strings a millisecond either side of midnight and of new year, and the memo's generation as a re-label after the clock moves. The testing standard prefers the observable contract, and the helper stays private.
A property test over byteLength against TextEncoder Dropped with the change it was written for. byteLength is still TextEncoder, so a property test asserting they agree would compare a function with itself.
— Added while measuring: a third merge case where no two flows share a host, so the memo can never hit. Without it the 251× would be a claim about a fixture rather than about the code, and the 2.09× floor it exposes would be invisible.
— Regression this WU introduced, found by its own review and fixed: a text/*-labelled body is dispatched on its declared type, never on its bytes, so an unreadable one reaches TextRenderer — routine on a MITM proxy, where a mislabelled charset is one of the things the proxy exists to reveal. Its byte count and its decoded text's byte count then measure different things, and taking the first as total while measuring the shown slice with the second printed showing 384 KiB of 133 KiB — shown greater than total, inverting the one statement CutMarker exists to make. Every test written for the size prop used well-formed multi-byte text, where the two counts coincide by construction and cannot show it. Fixed in c31ee98: the caller's size is refused where the shown slice carries a replacement character, which is bounded by the cap. Two named regression tests, one per seam, each failing against the unguarded version.
— Benchmark gap, found by its own review and closed: both timestamp cases ran against a memo warmed by the setup render, so the suite priced the repeat case and never the first-sight one — while flows.bench.ts had carried a deliberate memo-miss control from the day it landed. The asymmetry was the omission, not the warm measurement: a flow's started_at never changes, so an unscrolled re-render really is all hits. The added case answers what the warm-only suite could not — the miss path does not regress (1.05×), so the memo is free on a miss and 2.9× on a hit, and the headline belongs to the case it names rather than to the component in general.
— Five more found by the second review round, all in this WU's own new code. The first fix's guard was a proxy — TextRenderer read a replacement character in the shown slice as proof the decode had failed, but a body can carry that character on purpose, and downstream the two are identical. Such a body is valid UTF-8 with a free size, and the guard spent a whole-body encode on it — landing the false positive on exactly the mis-encoded traffic this proxy exists to show. Output was never wrong, only re-derived. Moved to where the answer is a fact: decodeBody tries the strict decoder and falls back, the same single decode for a whole body, and BodyViewer passes a size only when it means what the renderer compares it against. The memo enforced its cap on lookups as well as inserts, so the render after the 4096th distinct timestamp threw away the entry it was about to find. Its key held a raw value with no type tag, and a numeric string keys the same as the number while moment reads them differently. Its comment claimed the cache holds only what is on screen; nothing evicts a row that scrolls away. And the memo-miss bench's pool overlapped the warm one at index 0, so its purity rested on warm-up happening to consume the overlap — the number was never contaminated, verified, but the pools are now disjoint by construction.
— This report misstated its own method, and the second round caught it. It claimed every before number came from a run at bf7a449; three of the cases did not exist there. The rows now carry the method that produced each, and the two routes are described above the table. The numbers were right and the method was sound — the account of it was not, which in a repo where the report is the durable record is the same kind of defect as a wrong number.
— The third round found no defect in the shipped behaviour, and one in the WU's own discipline. The second round's fix swapped a lenient decode for a strict one on the claim that a whole body pays nothing and only a failed body is decoded twice — and measured neither, in a WU whose entire premise is that a cost is a number rather than an assurance. Both are benched now: whole, 388.98 hz against the lenient decode's 379.15, so the claim holds; failed, 104.68 hz — 9.55 ms against 2.64 — which is the fallback's real price. The fix stands regardless, because what it replaced answered wrongly, and the price is recorded as a follow-up beside the re-decode it compounds. The round also found this report saying 51.6× in its Outcome and 54.1× in the table beneath it for the same case, an over-count and a misattribution in its own test evidence, a stale error figure on the FormRenderer card, and three comments narrating this WU's history rather than stating what holds. A BOM-prefixed body was raised as a defect and refused — a save writes the mark, so the bytes' length is the size the marker should state — but it was untested, and now is.
— Defect found and fixed in flight: the memo key's separator went into the source as a literal NUL byte, which made git classify TimestampText.tsx as binary — its diffs rendered as Bin 4443 -> 2262 bytes and grep refused to read it. Fixed as \u0000 in 626f91e; the whole tree was then scanned for other NULs and has none.

Distillation

Nothing citable at T2. No use case moves and no decision is made: all three costs are cost, not behaviour, and the rendered output is identical everywhere the existing suite could see it. DEC-22's four forks are preserved exactly — absolute, seconds, local, 24 h — and were re-asserted, not merely left alone.

The one design record this WU does change lives in the code, where DEC-16's rule puts it: TextRenderer's TSDoc gains a @props line stating that size is the count its caller already holds and why re-deriving it is what this WU removed. FormRenderer's TSDoc is unchanged, because its component is.

One candidate is left for the epic to judge rather than taken here: the discipline itself — a performance fix lands only against a number, and is reverted when the number does not move — is the epic's own stated rule and belongs in its distillation at W10, not duplicated downward into a WU report.
