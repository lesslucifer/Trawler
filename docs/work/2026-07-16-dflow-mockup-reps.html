What the medium requires

The mockup lives in an htmldoc: a single self-contained HTML file, opened from file:// (no server), dark-mode, and — critically — commentable and diffable by the htmldoc layers. Any tool has to survive that filter. A lo-fi mockup also wants to show states (complete / in-flight / empty), which the Interaction use-cases demand.

Rep C · draw.io embed the question

Yes, draw.io can be embedded (below, live — pan/zoom works). But note what it costs: it renders on a forced white canvas (a light island in a dark doc), the diagram is opaque XML that doesn't diff meaningfully, authoring the embed needs an encoding workaround for the htmldoc linter, and it is static — no state toggle. Its real edge (vendor icons, precise geometry, a full UI mockup shape library) doesn't buy much for a narrow box-stack like this. We already trialled and dropped it for Layout for the same reasons.

draw.io wireframe, live-embedded. Note the white island and the lack of a state toggle.

Recommendation

Rep B — native HTML/CSS. The mockup is a UI and the doc is HTML, so express the UI directly: zero dependencies, exact dark-mode, diffs as plain HTML, fully commentable, and — uniquely — it can carry the state toggle the Interaction use-cases call for (complete ↔ in-flight). It's a truer "lo-fi build" than a picture of one. Keep ASCII as the throwaway sketch when a full render isn't worth it; keep draw.io in reserve for diagrams that genuinely need vendor icons or precise geometry — not for UI mockups. External SaaS tools are out: they break the self-contained/offline/diffable contract this whole doc system rests on.

If you want a hand-drawn "clearly not final" aesthetic, the fallback is Excalidraw exported to inline SVG — but it loses interactivity and diffs as a blob. Say so and I'll add a fourth rep to compare.
