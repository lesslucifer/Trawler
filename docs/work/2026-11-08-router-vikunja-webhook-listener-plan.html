E-VIKUNJA.W3 plan: cargo xtask vikunja webhook-listen

A standing loopback listener that turns Vikunja webhooks into one JSON line per owner-relevant transition, and loses nothing across a relaunch.

v1 · 2026-11-08 · Trawler · T3 WU plan · E-VIKUNJA.W3 · wu/router-vikunja/webhook-listener → epic/router-vikunja

Requirement

cargo xtask vikunja webhook-listen [--port <p>] [--state <file>] [--secret-file <file>] [--poll <secs>] binds 127.0.0.1, registers itself as project 3's webhook with a secret kept in a 600 file, reconciles every open task (and every task it last saw asking) against the live API, then stays running and prints to stdout one JSON line per real transition — needs-owner, answered, closed, comment, unreachable/reachable — rejecting and logging any delivery whose HMAC-SHA256 signature does not verify.

Mapping

E-VIKUNJA, summary block W3 "webhook receiver → Telegram bridge" (the bridge itself stays the router's: this process only prints). Fills the "Webhook listener (W3)" row of vikunja-protocol.md's Standing processes. Process epic, no UC.

Flow

flowchart TD
  S["start"] --> B["bind 127.0.0.1:port"]
  B --> R["register: delete any project-3 webhook with this target_url, PUT a new one with the secret"]
  R --> C["reconcile (remind): open tasks ∪ tasks last seen asking"]
  C --> L["print listening"]
  L --> W{"delivery"}
  W -- "signature fails" --> X["401 + stderr log, nothing read"]
  W -- "verifies" --> T["GET the task + its comments → diff vs state → lines"]
  L --> P["every --poll s: reconcile; failure → unreachable once, recovery → reachable"]
Bind before register, register before reconcile: a delivery arriving during the reconcile waits in the accept backlog, so no change falls between the read and the subscription.

Transitions

asking = open ∧ assignee vuluu ∧ label needs-ownerLine
not asking → asking (or asking at startup: a relaunch re-announces every pending ask){"event":"needs-owner","task_id":9,"title":"…","by":"…"}
asking → not asking, label gone{"event":"answered",…} — the only answer signal
asking → not asking, label still on (marked done, or unassigned){"event":"closed",…} — left the queue without an answer
a comment newer than the task's last seen comment id, not by trawler-router{"event":"comment","task_id":9,"title":"…","by":"vuluu","text":"…"} — never a lifecycle transition
the reconcile poll fails / succeeds again{"event":"unreachable","error":"…"} / {"event":"reachable"}
The payload is a trigger, never the truth: the live probe saw deliveries arrive out of order and after later writes, so every delivery re-reads the task and its comments from the API and diffs them against the state file. A duplicate delivery therefore diffs to nothing.
