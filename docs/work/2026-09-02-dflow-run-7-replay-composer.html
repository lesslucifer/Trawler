1 · Frame

Purpose: a developer debugging an API takes a captured request, changes one thing, and fires it again to see what changes. Given (functional input — received, not designed): seed a draft from a captured flow · override method · override URL · override headers · override body · send · the result lands as a new flow · compose from scratch Not given (may not be assumed to exist): saved request collections · environments or variables · auth helpers · multi-request sequences · response assertions · send history beyond the flow list

Non-goals: request collections · scripting · environment substitution · diffing two responses

2 · Layout

Three zones. The draft is the screen; the seed is a reference the draft cites, and the outcome lands where the eye already is — under the button that caused it.

├─────────────────────────────────────────────┤
│ B  request body — headers, then body         │  ← the edit surface; the tallest zone

│                                              │
├─────────────────────────────────────────────┤

why
  • send zone order — the verdict was reading before the control that causes it. The row now says what you are about to do, then what happened. Loops back to Layout: no.
  • edited mark — a zone-level "modified" badge is chrome that informs less than the per-row mark already does, and it duplicates it. Stripped; the row mark is the whole signal. Loops back to Layout: no.
  • result weight — the border around status and duration added no information; StatusPill's tint is already the channel. Loops back to Layout: no.
  • zone C position — C sat directly under the identity bar, which put the act before the thing it acts on and pushed the edit surface below the fold. Moving it to the bottom, pinned, serves the scan order identity → edit → fire. Loops back to Layout: yes — the sketch above is the post-tune order.
