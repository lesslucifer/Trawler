E-PKG2.W1 — the app asks, verifies and relaunches as the new version

Self-update through tauri-plugin-updater, signed by the project's own key, always asked, never silent, and always through DEC-64's quit check.

v3 · 2026-11-05 · Q20–Q22 ruled · v2 carried from E-PKG.W3 into E-PKG2 · Trawler · T3 WU plan · E-PKG2.W1 · branch wu/packaging-v2/updater off epic/packaging-v2 (main 398f6dfe, E-PKG.W1 landed) · epic plan · owner rulings Q20 (a), Q21 (a), Q22 (b), 2026-11-05
Why the updater comes first. W2 needs E-CI's ci.yml on main (Q19), and it has not landed. The updater depends only on cargo xtask package (E-PKG.W1, on main).

Requirement

An installed Trawler checks releases/latest/download/latest.json at launch (at most once a day) and on Check for Updates…. For a newer version it asks in a native dialog, naming both versions and saying that the captured list will be cleared. On yes, it downloads the update and verifies its signature against the public key in tauri.conf.json. It then quits through DEC-64's check, stops its core, installs the update and relaunches as the new version with the CA unchanged. A forged signature, an unreachable channel or a no changes nothing, and the app says why only when the user asked to check.

Owner rulings

#QuestionRuling
Q20The epic planned that a .deb or .rpm install opens the release page, because the updater could not install those packages. tauri-plugin-updater 2.14 now can: it runs dpkg -i or rpm -U through pkexec, which shows the desktop's own password prompt. Should deb and rpm update in place too?owner ruling 2026-11-05 (a) Yes, in place. The flow, the signature check and the relaunch are the same on every bundle type. The release-page branch and its install-kind detection disappear, and the release then needs .deb/.rpm updater signatures (W4). UC-UPDATE's deb/rpm sentence changes at distillation
Q21The user says Install, then cancels DEC-64's quit dialog. What happens to the update? owner ruling 2026-11-05 (a) It is dropped. Nothing installs on a later, unrelated quit, and the next check offers it again. A pending update never outlives the quit it was asked for
Q22Who generates the updater key and stores the secrets (Q7)?owner ruling 2026-11-05 (b) The owner generates the key, keeps both halves and sets the two repository secrets. No agent ever sees the private key, and the owner sends back only the public key for plugins.updater.pubkey. Consequence: no agent can build updater artifacts, so cargo xtask package adds them only when TAURI_SIGNING_PRIVATE_KEY is in its environment, as in the release workflow. Without the key it builds the installers and says the updater artifacts were skipped. Tests sign with keys they generate themselves
