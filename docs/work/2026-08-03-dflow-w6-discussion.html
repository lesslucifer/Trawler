The mandate, and the thing that moved under it

Epic plan, W6: "Apply W4 findings to the rulebook — add/remove/retag rules, sharpen ids and hard/soft tags." That was written when the rulebook's job was to be read. Since then W5 turned the collection into code, and the rulebook's vocabularies section — colour, type, spacing, radius — is now a stale second copy of ui/tailwind.config.js. Its own rule says "values live in code where code exists — code wins", and code now exists. So W6 is the findings pass plus a reconciliation the epic plan could not have known to ask for.

The drift W5 created

The forks

Eight. D1–D3 are the drift; D4–D6 are scope; D7–D8 are method.

D1 · Do the vocabularies stop being a list?

OptionWhat it means
A · point, don't copy defaultThe vocabularies section names each set and its governing rule, and links ui/tailwind.config.js as the member list. Zero token names in the KB. Adding a token becomes a code change plus a rule check, never a doc edit. Follows the KB's own "code wins" line and the T-tier rule against copying code into docs, and is the same move W5 made with specimen.css.
B · keep the names, add the missing onesThe KB stays readable standalone but is a second copy that will drift again — exactly what W5 just spent a step deleting.
C · split — sets in the KB, values in codeWhat it does today. The drift table above is the evidence it does not hold: membership drifted, not values.

D2 · The 8px floor — two independent sightings say the rule is wrong

Run #2 hit it on a 4px grid row gap. Run #3 hit it from the other side: an 11.5px control cannot carry 8px of vertical padding. W5 then shipped 14 named chrome tokens below the floor, each documented as a decision. Both sightings agree the rule as written is unsatisfiable for dense chrome.

OptionWhat it means
A · two scales, one rule defaultspacing-scale becomes: layout spacing from the 8px scale; control chrome from a named chrome token — never a raw value in either case. The predicate reads the config's key names rather than a hard-coded set, so it checks the real invariant (no raw px) instead of a number list. This is what W5 already built and commented; W6 ratifies or overrules it.
B · lower the floor to 4pxCheapest edit, weakest rule — control-x: 9px and glyph: 9px still break it, so it does not even fix the sighting.
C · keep the floor, exempt chrome by nameAn exception list that grows per component; the same shape as zero-accent's exception list, which D3 is about to strain.

D3 · zero-accent vs eight chromatic tokens

The rule permits two exceptions (ok, warn). Shipped code has three syntax tints (DEC-11-confirmed, body-scoped) and five method tints (MethodLabel fork D3), and the config comments defer permissibility here. Run #3 adds a ninth candidate: a chromatic meaning for unknown.

OptionWhat it means
A · rule by scope, not by list defaultRestate as: chrome carries no chromatic colour; payload rendering and status identity may, each via a token whose meaning is fixed in the chromatic-meanings table. The exception list stops growing per token and starts being a scope boundary — which is what every one of the eight tokens' own comment already argues. The chromatic-meanings table then grows three rows: syntax, verb, and (per D4) unknown.
B · extend the exception list to eightHonest and mechanical, but the list has grown 2 → 8 in one WU with no principle bounding the ninth.
C · admit syntax, reject method tintsWould force a MethodLabel re-design after W5 shipped and tested it. Only worth it if the reviewer actually wants monochrome verbs.

D4 · Does unknown get a colour?

Run #3's dominant status is neither ok nor warn — a probe that fails and a probe that shrugs both return unknown, and on the setup screen that is the permanent case, not an edge one. Default: no third tint — the neutral ink channel is the answer, and the chromatic-meanings table says so explicitly so the next screen does not re-ask. Cheaper than a token, and colour-plus-text already guarantees the text channel carries the meaning.

D5 · Does W6 touch the harness?

OptionWhat it means
A · rulebook only; W7 writes every predicate defaultW6 ships rule content and hands W7 four unblocked predicates. Matches the epic plan's split and keeps this WU docs-mostly. The hard rules: 1/13 line reprints itself; if a rule is added or killed the count moves on its own.
B · also implement the four unblocked predicatesTempting — settling a rule and checking it in one pass is how W4 ended. But it takes 4 of W7's 12 and blurs the WU boundary; W7 is then "the remaining 8 plus two tiers plus an e2e", which is a worse plan doc, not a better one.

D6 · Does the rulebook govern the collection, or only screens?

Finding 4 asks for a binds: screen · component · both axis. It was cheap when components were docs. Now they are code with 226 unit tests, and the axis decides something real: whether generous-targets is judged against IconButton's 24px control token or against the screen that places it. Default: add the axis — it is one column, and without it every component-level rule is judged twice or not at all.

D7 · The two unvalidated imports

The seed marked familiar-idioms and progressive-disclosure as principle imports that "W4 must validate or kill". Two runs later neither has driven a single Tune call. The lifecycle table says imports that pull no weight are W6 kill candidates. Default: kill both, with a one-line deprecation pointer so the past receipts that cite them stay valid — that is the slug-immutability contract, and this is its first exercise.

D8 · What test level does a docs WU carry?

W4 waived tests on "no code changes" and then shipped 269 of them. W6 under D5·A genuinely changes no code — but the KB it edits is read by xtask verify-doc at runtime for receipt coverage. Default: an integration test asserting the checker still parses the revised rulebook and that every slug a past run doc cites still resolves — that is the WU's bounded contract, and it is the mechanical proof that no rename slipped in. Unit level waived (no unit added); e2e waived to W7 as in W4 and W5.
