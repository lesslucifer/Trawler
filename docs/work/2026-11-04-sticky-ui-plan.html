E-STICKY — plan: what the user chose stays chosen

A view choice made on one flow carries to the next flow and across a relaunch, instead of resetting to its default.

v1 · 2026-11-04 · Trawler · T3 epic plan · E-STICKY · branch epic/sticky-ui · worktree ../Trawler-sticky-ui

Intent

Today a user who switches the detail pane to Response gets Request again on the next flow they open, and every relaunch forgets the choice too. The cause is structural: App.tsx mounts <FlowDetail key={inspected}>, so each new flow remounts the pane and its useState("request") leg, along with BodyViewer's pretty. This epic makes view choices belong to the user rather than the flow. They stick within the session and come back at launch. It also adds a small preference store that later epics (E-QUERY's query text, the deferred tabs and presets) can grow into.

Non-goals

  • Restoring the selected flow, an open composer, or the draft after a relaunch. The ring is in memory, so the ids would point at nothing.
  • Persisting the filter or query text. E-QUERY owns that (Q4).
  • Syncing a choice live across several open windows. E-INSPWIN's data windows and the deferred multi-instance epic own that question.
  • Changing anything in layout.json or how View › Reset Layout behaves (Q2).

WU summaries

view-prefs store. A view-prefs.json in the app config dir, written whole through layout::replace_whole. Every field is #[serde(default)] and unknown fields are tolerated, so the file can grow without discarding saves. Adds view_prefs_read/view_prefs_write commands registered in both shell builds, plus the TS viewPrefsStore.ts and a useViewPrefs hook (read once, a choice made first wins, debounced write flushed on unmount).

Intent: the reusable store. It is the foundation for UC-5's restore.

A written prefs record reads back unchanged. Missing, corrupt or wrong-typed fields read as defaults, field by field. An extra field is ignored.

none

Sticky detail. Lift leg and pretty out of FlowDetail/BodyViewer into Shell as controlled props, backed by useViewPrefs. Nothing changes visually; the touched UI files are declared undesigned with that reason.

E2E test plan

Extend ui/e2e against a real ephemeral core with two captured flows. Open A, pick Response and raw, open B, and assert Response and raw. Quit for real and relaunch, then open a flow and assert both again, and assert the Settings window's rect. Run once more with view-prefs.json corrupted and assert the defaults with no notice. The launchers remove view-prefs.json before and after, as they already do for layout.json and windows.json.

Distillation plan

  • docs/use-cases/web-ui.html: UC-5, UC-ONBOARD and UC-SVC, plus their index rows.
  • A new DEC: a choice belongs to the user, not the flow. It covers the store's shape, its field-by-field tolerance, and why it is separate from layout.json.
  • docs/backlog/roadmap.html: any residue.

Open questions

#QuestionProposed default
Q1Is the body mode one setting, or one per leg (request raw, response pretty)?One shared setting. It matches the owner's “select once” intent.
Q2Does View › Reset Layout also reset view prefs?No. Layout means sizes; a separate file keeps them apart.
Q3Should setup's platform choice survive a relaunch, given that chosen also decides whether adb runs and which device the quit dialog names?Yes, but a remembered Android choice does not start adb until setup is opened.
Q4Should the filter or query text survive a relaunch?Leave it to E-QUERY, which writes through this store. A restored query is shown in the bar, so the list is never narrowed without the user seeing why.
Q5Should a pending flow (no response yet) opened while Response is the sticky leg show Response anyway?Yes, with its existing “no response yet” state. The choice stays put and is not overridden.
