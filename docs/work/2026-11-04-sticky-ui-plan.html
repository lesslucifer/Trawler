E-STICKY — plan: what the user chose stays chosen

A view choice made on one flow carries to the next flow and across a relaunch, instead of resetting to its default.

v2 · 2026-11-04 · decisions locked · Trawler · T3 epic plan · E-STICKY · branch epic/sticky-ui · worktree ../Trawler-sticky-ui

Intent

Today a user who switches the detail pane to Response gets Request again on the next flow they open, and every relaunch forgets the choice too. The cause is structural: App.tsx mounts <FlowDetail key={inspected}>, so each new flow remounts the pane and its useState("request") leg, along with BodyViewer's pretty. This epic makes view choices belong to the user rather than the flow. They stick within the session and come back at launch. It also adds a small preference store that later epics (E-QUERY's query text, the deferred tabs and presets) can grow into.

Non-goals

  • Restoring the selected flow, an open composer, or the draft after a relaunch. The ring is in memory, so the ids would point at nothing.
  • Persisting the filter or query text. E-QUERY owns that (Q4).
  • Syncing a choice live across several open windows. E-INSPWIN's data windows and the deferred multi-instance epic own that question.
  • Changing anything in layout.json or how View › Reset Layout behaves (Q2).

WU summaries

Every behaviour, each part with its unit and integration tests.

PartBuilds
Storeview-prefs.json in the app config dir, written whole through layout::replace_whole. Every field is #[serde(default)]. Unknown fields are captured by #[serde(flatten)] into a map and written back, so another version's fields survive. view_prefs_read/view_prefs_write are registered in both shell builds (real and scenario). TS side: viewPrefsStore.ts and useViewPrefs.
One writerShell holds the only useViewPrefs instance and the whole record. Every field, including E-QUERY's later one, goes through it. The Settings page never mounts it. The hook reads once, a choice made before the read lands wins, and writes are debounced.
Sticky detailleg and pretty leave FlowDetail/BodyViewer for Shell as controlled props. Nothing changes visually; the touched UI files are declared undesigned with that reason.
Setup platformA separate lastPlatform field. state.chosen still starts at "this" on every launch. A user's re-invoke (the dot, “set up capture”, “set up another device”) seeds chosen from lastPlatform, with R6 still applied. The launch check's own not-detected opening stays on This machine. adb therefore runs only after the user has opened setup on Android, at quit included (Q3).
Settings windowsettings::open builds the window hidden, calls window_geometry::restore, then shows it, so it never visibly jumps. Its record lands in windows.json. open's generic Runtime and restore's concrete &Window are reconciled.

UC-5, UC-ONBOARD and UC-SVC.

E2E test plan

Extend ui/e2e against a real ephemeral core with two captured flows. Open A, pick Response and raw, open B, and assert Response and raw. Quit for real and relaunch, then open a flow and assert both again, and assert the Settings window's rect. Run once more with view-prefs.json corrupted and assert the defaults with no notice. Both launchers remove view-prefs.json before and after, as they already do for layout.json and windows.json: SAVED_STATE in wdio.conf.ts and SAVED_SIZES in walkthrough.conf.ts.

Every spec shares one app process, so a choice leaks into the specs after it, and a relaunching spec reloads it from the file. Existing specs therefore select the leg and body mode they assert instead of relying on a default. That covers flows.spec, which assumes “the panel opens on the request leg”, running after replay.spec picks Response and raw. Only the new spec's corrupt-file run asserts the defaults.

Distillation plan

  • docs/use-cases/web-ui.html: UC-5, UC-ONBOARD and UC-SVC, plus their index rows.
  • A new DEC: a choice belongs to the user, not the flow. It covers the store's shape, the one writer, why it tolerates and keeps unknown fields while layout.json rejects them (DEC-67), and why it is a separate file.
  • DEC-31 amended: the body view (raw | pretty) is the user's, held by Shell. The body pane receives it as a prop, as it already receives the leg.
  • DEC-60 amended: rule 6's last device outlives the app session for setup the user opens. The launch check's own opening stays on This machine.
  • docs/backlog/roadmap.html: any residue.

Open questions

None open. Locked by the owner on 2026-11-04:

#QuestionDecision
Q1Is the body mode one setting, or one per leg (request raw, response pretty)?One shared setting. It matches the owner's “select once” intent.
Q2Does View › Reset Layout also reset view prefs?No. Layout means sizes; a separate file keeps them apart.
Q3Should setup's platform choice survive a relaunch, given that chosen decides whether adb runs (in setup and at quit) and which device the quit dialog names?Only as lastPlatform, the answer for setup the user opens. chosen starts at "this" every launch, and the launch check's own opening stays on This machine. So no adb runs, and no evidence rule changes, until the user opens setup. This also avoids a restore landing after setup has already read its platform.
Q4Should the filter or query text survive a relaunch?Leave it to E-QUERY, which writes through this store's one writer (its plan's Q4 agrees). A restored query is shown in the bar, so the list is never narrowed without the user seeing why.
Q5Should a pending flow (no response yet) opened while Response is the sticky leg show Response anyway?Yes, with its existing “no response yet” state. The choice stays put and is not overridden.
Q6How many WUs?Two: W1 builds every behaviour with its unit and integration tests; W2 is the e2e and distillation.
