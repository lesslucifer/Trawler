E-INSPWIN — epic plan

A data window: hand it a piece of data and it gives the user room and tools to read, find in, reformat, decode and freely edit a working copy — the original always one click away.

v6, owner rulings recorded; Q4 re-ruled 2026-11-04 (filter deferred); Q11 re-ruled 2026-11-04 (one shared record); W8 added 2026-11-05 (time decoder, Q13) · opened 2026-11-03 · Trawler · T3 (docs/work/) · branch epic/inspect-window · WU branches wu/inspect-window/<slug>

Intent

Components that show data are built for a glance — BodyViewer cuts text and JSON at 128 KiB, hex at 4 KiB, squeezes a long form into a 520 px grid, and offers only pretty/raw, copy and save. This epic adds a data window: a pure front-end tool that is given data and helps the user work with it. It has no idea whether the data is a body, a header or anything else, knows nothing of flows, and never calls the core. Any component holding data can open it; BodyViewer is the first. Inside, the user works on a working copy — edits, reformats and decodes are scratch, the original is kept untouched and restorable, and nothing ever flows back to where the data came from.

The data window's model

ConceptDefinition
Payload{key, title, bytes, typeHint?} — all the window ever receives. title is an opaque caption the opener writes; typeHint is a media type of the data (e.g. application/json), optional; key is opaque, used only to focus an already-open window. No flow id, leg or source kind.
OriginalThe bytes as handed in. Never mutated; restore original resets the working copy to it.
Working copyWhat the user edits. Free text edits, reformat, sort, decode-in-place all change it, each step undoable; a modified marker shows whenever it differs from the original.
Find marksHighlights over the working copy, never a change to it. The JSONPath / text filter view is deferred (Q4).
KindDetected by the window from typeHint, else by sniffing the bytes: json · form · xml · text · hex · image. The user can override it (e.g. treat this text as JSON).
Copy / saveDeliver what is on screen, the working copy; copy original and save original deliver the handed-in bytes.

Expected result

#Observable after the epic
1BodyViewer shows open in data window; using it opens a native window with the opener's title and the bytes the pane holds.
2Opening with the same key focuses the open window (its edits intact); another key opens a second window. Closing a data window asks nothing (DEC-64); data windows close with the main window.
3A 2 MB JSON payload renders whole, scrolls smoothly, folds per node, all, and to depth N.
4JSON find counts and steps through matches.
5Edits and reformats (indent, minified, sorted keys) change the working copy, undo step by step, raise the modified marker; restore original returns the exact original bytes.
6A form payload over 128 KiB shows every pair whole; find, sort, edit and copy as JSON work.
7Text, XML and hex payloads past the pane's caps render whole with find.
8A JWT, base64 or URL-encoded selection, or a timestamp / date-time read in local time, decodes beside it; replace and open-in-window both work; a malformed input says why in the user's words.
9Copy/save original yields the handed-in bytes regardless of any edit; copy and save yield exactly what is on screen.
10Nothing in the data window changes the pane, the capture or any core state; the window makes no network request.

Non-goals

Out of scopeWhy / where it goes
Any knowledge of flows, legs, headers or the core inside the windowThe window is a generic data tool; the opener owns where the data came from and writes the title.
Writing edits back (to the capture, the pane, or the composer)Edits are scratch in the working copy; the original is always restorable. Sending a modified request stays the composer's (UC-8).
Openers other than BodyViewer / CutMarkerThe payload contract makes them a one-call addition; follow-ups (Q5).
Any core change or new endpointPure front end + shell window plumbing.
Remembering each data window's size and position on its ownEvery data window shares one geometry record (Q11); a record per key would grow windows.json by one entry per payload ever opened.
Diff (original vs working copy, two payloads); jq; schema-bound decoders (protobuf, msgpack, gRPC)Follow-ups.
The web shell (UC-3)Retired at native parity per DEC-12.
Changing the pane's capsThe pane stays the glance; the window is the way past them.

E2E test plan

One spec over the existing wdio harness (ephemeral-port core, seeded flows); the data window is reached through wdio window handles. The core only seeds the opener — the window itself is asserted to make no request.

JourneyAsserts
J1 · open and focusA seeded JSON body over 128 KiB shows a cut in the pane → open in data window from the cut marker → second handle, title as the opener wrote it, whole document; open again from the toolbar → still two handles, focused.
J2 · work a JSON documentFind reports the seeded count and steps; sorted keys + a hand edit → modified; copy = edited text, copy original = seeded bytes; undo twice → unmodified; edit again → restore original.
J3 · a long form and a tokenSeeded 300 KiB form: last pair present and whole; find one key; right-click its JWT value → decode → header + payload JSON; open the decoded payload in a new data window; right-click the decoded payload's exp in that window → decode → the local time.
J4 · no write-backAfter edits, the pane still shows the captured body, GET /flows/{id}/response/body is unchanged; close the data window → main window open, nothing asked.

Questions — all decided

#QuestionStatusAnswer / proposed default
Q1One window per opened data, or one reused data window?decidedOne per opener-supplied key (BodyViewer: its flow + leg, opaque to the window); reopening focuses it with its working copy intact.
Q2Hand the data over by reference or by value?decidedBy value.
Q3Live or snapshot?decidedSnapshot; the window knows nothing of flows — it works with the data it was given.
Q4JSON filter language?decidedRe-ruled by the owner on 2026-11-04 (W2's round 1): the filter is deferred to a later epic; this epic ships find only. It was JSONPath (RFC 9535) plus a text filter, jq deferred.
Q5Which components open a data window in this epic?decidedThe window is generic — it never knows what the data is. BodyViewer and its CutMarker ship as openers now; header values and single form values are one-call follow-ups.
Q6Value decoders (base64, URL, JWT)?decidedIn this epic (W6).
Q7Render caps in the window?decidedNone; the opener's payload is rendered whole (a body is at most the 10 MiB body_cap).
Q8Lifecycle vs the main window and DEC-64?decidedData windows close with the main window; closing one asks nothing.
Q9Entry points?decidedBodyViewer's toolbar, the CutMarker, and a keyboard shortcut while the body has focus; keys set in the design run.
Q10E-ONEAPP and the core address?decidedMoot: pure front end, the window never talks to the core.
Q11Remember window size and position?decidedRe-ruled by the owner on 2026-11-04 (W3): yes, through E-PANELS' windows.json, as one record shared by every data window — whichever data window moved or resized last writes it, and a new data window opens there. It was a record per window, deferred until E-PANELS landed.
Q12Do edits survive closing the window?decidedNo — the working copy lives as long as its window; closing a modified window asks nothing (scratch by definition).
Q13Decode timestamps and date-time strings to local time?decidedYes, added by the owner on 2026-11-05 as W8, on W6's peek. A date-time that names no zone is not guessed (see the W8 plan's open choice).
