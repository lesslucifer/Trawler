E-UISETUP.W2 — Trust the CA

Make the machine trust Trawler's CA from inside the native app: one confirm + elevation installs it on macOS and Windows; correct guided steps everywhere else. The first Tauri command in the app — the CA-trust half of the onboarding stepper W1 shipped.

Draft v1 · 2026-07-13 · Trawler · T3 WU plan · epic: E-UISETUP · builds on: W1

Requirement

The onboarding Trust the CA step installs Trawler's CA (PEM bytes from GET /ca.crt) into the OS trust store natively: on macOS and Windows, one confirm + an OS elevation prompt runs the install for the user (security add-trusted-cert into the System keychain · certutil -addstore ROOT). A system selector (defaulting to the detected host) lets the user read the correct guided steps for any system — Linux, Firefox's own store, simulators, devices — as text (UC-3/UC-4 invariant); the steps stay visible even on the auto path, as the manual alternative. The privileged command is built in ui/src-tauri from a fixed per-OS template — the webview passes only the PEM, never a command. Verifying it worked: the install command's exit status gives a weak "the command ran" signal (step → done/failed); the authoritative "trusted on this system?" answer is W4's live capture. No trust-store inspection. Decline the elevation prompt ⇒ the guided steps carry them the rest of the way (consent, never silent).

Design

W1's frontend is a pure HTTP client with zero Tauri IPC; lib.rs registers no commands. W2 adds the first: a Rust install_ca command, and the frontend's first invoke(). @tauri-apps/api is already a dependency — no new JS package.

Trust boundary — Rust owns the privileged command; JS passes only data. The command never takes an argv or shell string from the webview (that would be arbitrary elevated code execution over IPC). install_ca(pem) accepts the PEM string only, validates it looks like a certificate (-----BEGIN CERTIFICATE-----) before writing it to a temp file, and builds the install command from a fixed per-OS template. Because the app never reads the trust store back, there is no store-parsing attack surface either — success is a real captured flow (W4), not a self-report.

The selector always shows the manual steps for the chosen system; the auto Install button appears only when the detected host is mac/win. Any decline or failure leaves the guided steps in place. One confirm, one elevation prompt.

"Installed properly?" — two signals, and why not a third. The trust-ca step is a local 3-state, idle → installing → done | failed. done means only that the elevated command exited 0 (security/certutil reported success) — real, but weak: it says the command ran, not that the client trusts us. The authoritative answer, "is the CA trusted on this system right now?", is W4's live self-test: a proxied HTTPS request that comes back decrypted. We deliberately do not inspect the trust store as a third signal — store presence is OS- and store-specific (system vs login vs Firefox's NSS vs per-app), brittle to parse, and still wouldn't prove decryption works. Capture is the ground truth (epic: prove by capture).

Reopened the app, or trusted the CA some other way? Nothing to redo, and nothing to persist. Onboarding entry is driven by live capture, not a remembered checkbox: at launch W4's self-test fires a proxied HTTPS request, and if it returns decrypted — however the CA got trusted (a prior session, a manual install, another tool) — the machine goes straight to proven and the onboarding surface is skipped entirely. So "already done" shows up as never seeing the step, not as a pre-ticked one. We do not persist per-step status and do not read the trust store (both epic non-goals — see the epic open question "persist across restarts": derive from capture, no new store). If the user does land back on the trust-ca step — e.g. the CA is trusted but the proxy isn't set, so capture can't yet confirm — re-running Install is safe: certutil -addstore -f overwrites and add-trusted-cert re-applies trust; no duplicate cert, no error.

Two independent OS reads, by design. The frontend picks which step content to render (auto button vs guided text) from navigator.userAgent — synchronous, no new dependency, and reliable for the mac/win/linux family because the webview's UA always reflects the host OS. Rust builds the actual privileged command from std::env::consts::OS — authoritative at the moment of action. They serve different moments and need no shared source; if they ever disagreed, Rust is still correct for the install. Considered and declined: @tauri-apps/plugin-os (new JS + Rust dep + capability) and a host_os IPC round-trip — both heavier than a three-line UA check for family detection.

Contracts (the shape the tests pin)

// ui/src-tauri/src/setup.rs — Rust owns the privileged command
enum HostOs { MacOs, Windows, Other }          // from std::env::consts::OS at call time

fn install_command(os: HostOs, cert: &Path) -> Option<Privileged>
//   MacOs   → security add-trusted-cert -d -r trustRoot -k /Library/Keychains/System.keychain <cert>
//   Windows → certutil -addstore -f ROOT <cert>
//   Other   → None                             // guided-only; no auto path

#[tauri::command]
async fn install_ca(pem: String) -> Result<(), String>
//   reject if !pem.contains("BEGIN CERTIFICATE") → temp .pem →
//   wrap install_command in elevation (osascript "with administrator privileges" / UAC) → run → map status
// ui/src/setup.ts — pure, no I/O
type HostOs      = 'macos' | 'windows' | 'linux' | 'other';
type TrustTarget = 'macos' | 'windows' | 'linux' | 'firefox' | 'ios-sim' | 'android';
hostOs(): HostOs                             // navigator.userAgent (webview UA == host OS)
canAutoInstall(os: HostOs): boolean          // true only for macos | windows
guidedSteps(t: TrustTarget): string[]        // per-system instructions, plain text — for ANY target
// selector default = hostOs() mapped to its TrustTarget

The install action lives outside the state machine — the W1 reducer stays pure and unchanged. The step's done/failed status and the selected system are local step state, not phase transitions; only W4's live captured flips the machine to proven.

Expected (done when)

  • On macOS/Windows the trust-ca step shows an Install certificate action; clicking it fetches the PEM, invokes install_ca, and one OS elevation prompt runs the real install. Command exit 0 → step done; declining or a non-zero exit → failed, with the guided steps still visible.
  • A system selector (default = detected host) lets the user read the correct guided steps for any system as text — reachable even on the auto host, no browser "download" UX.
  • The Rust install_command builder emits the exact per-OS argv (security … / certutil …) and None elsewhere; the PEM validation rejects non-certificate input. Unit-tested.
  • setup.ts (UA→os · canAutoInstall · guidedSteps per target) and the text-safe render are unit-tested; the install seam (fetch → invoke; selector switches steps; failure → failed) has an integration test.
  • The onboarding machine is untouched; a successful install does not mark the step proven, and the trust store is never read — only W4's capture proves trust. cargo xtask ui build (tsc) clean; cargo test in ui/src-tauri green, headless.
