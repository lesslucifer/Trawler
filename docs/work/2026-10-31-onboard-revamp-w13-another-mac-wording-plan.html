Your rule: help on request

#WhatBuilt as
R1 A screen shows only what the user acts on. Always on screen: the title, the state, the next action, the values and commands it needs, and an action's own outcome. Everything else that explains (why lines, notes, captions, risk warnings, what to check when something fails to load) sits behind a help control and shows only when the user asks. You confirmed both on 2026-10-31: the control reveals that text, and a risk warning is no exception. Predicate: on the mockup, every muted prose element that is none of those sits inside a data-help host. On the setup screen the matrix test checks the same in built markup
R2 Where it applies, when. This epic: the setup screen. W13 applies it to Another Mac, the code it shares with the other platforms, and This machine (same screen, same control, the pattern W14–W19 copy). W14–W19 apply it to their own words. Every other screen (flow list, detail, composer, the close dialog): a new epic. A roadmap row for that epic. The rule enters the design rulebook when that epic lands, since the rulebook records no rule a screen still breaks
H1 The help control. A bare ? beside the thing it explains. It opens its text in place, under it, and closes again. Closed by default and on every new screen state. Enter / Space toggle it; it carries aria-expanded. A component design (Help), reviewed with round 21, retired into its TSDoc once built (DEC-16)

Requirement

On Another Mac, on every host, each state of the setup screen leads with the one thing to do next and shows the optional, the explanatory and the done as secondary. Every word names one thing one way and is true on the host it is shown on. Each by-hand step on that Mac offers a route without a terminal where one exists, with verified media, and keeps its command as another way. Every way back undoes every way in. Across the setup screen, what explains shows only on request (R1). A test holds each rule.
