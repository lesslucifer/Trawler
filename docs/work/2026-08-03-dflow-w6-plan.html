The sweep surfaced a distinction the ruling did not make: values vs keywords. Some off-list classes are scale values (p-5 = 1.25rem — a number someone picked). Others are keywords with no numeric choice in them: rounded-full, max-w-full, min-w-full, border-none, border-t, leading-none, w-px. All are in use in the shipped collection.

The rule, following the zero-value precedent confirmed by ⓪ and ①: a keyword that expresses a relationship or a reset rather than a magnitude is always legal — full, none, px, auto, and the side-only border utilities. It is the same argument that settled min-w-0: "100% of the parent" is not a value picked off a scale. Everything with a number in it stays closed. This is the one ruling the plan makes on its own, so it was called out here for review rather than buried in step 1.

It survived both checks. ⓪ tested it against all 31 real sightings — every one is a relationship or a reset, zero counter-examples, so the offered fallback ("if it is wrong the fix is 7 class usages") was never needed. ① then proved it survives closure: with every scale closed, all 17 relationship-keyword and zero classes still emit, while every magnitude drops. ⓪ also extended it without amendment — border-t selects a side at the DEFAULT width and leading-none is a reset, so five further scales resolved under the existing test rather than needing a new ruling.

leading-relaxed (1.625), leading-normal (1.5) and tracking-wide (0.025em) are not keywords by this test — they are named magnitudes, and became project tokens in ① (as loose, normal, tracking-label).

A fair reading of "hard rules are machine-checked" is the shipped UI is machine-checked. The code check — where it runs, and why it is not the collection test

The plan said "collection.test.tsx asserts every class in every component resolves to a project token" and left it there. Measured against the real tree, that deliverable is scoped wrong. Three facts, all checked:

FactConsequence
collection.test.tsx covers only the 24 components in src/components/, via a hand-written ROSTER literal of mounted elementsIts reach stops at the barrel. A screen is not in the roster and never will be — the roster is a vocabulary of reusable parts by design.
~168 of 235 className sites live outside src/components/ — Gallery 50, Onboarding 40, BodyViewer 20, FlowDetail 19, FlowList 14, ProxyCloseDialog 13, App 7, Layout 5 ⓪-correctedScoping the check to the collection would leave ~71% of the class surface unchecked — including every screen, which is exactly what binds: screen rules are about. Corrected deliverable: a local ESLint rule over ui/src/**/*.tsx, not a render assertion in the collection test. It reads class literals statically, resolves the scale-bearing ones against the closed config, and reds on anything off-list — no mounting, no roster, no dependence on which branches a test happens to exercise. Coverage is ESLint's config glob, so a new screen is covered the day it is added rather than when someone remembers to register it. Measured feasibility ⓪-corrected: 29 of the 235 sites are computed className={…} expressions — not the 7 this plan first claimed, four times the figure. The strategy still holds: every one was inspected and holds its classes as string literals inside the expression (template literals interpolating literal maps — ${TONE[tone]}, ${FRAME[frame]}, ${METHOD_COLOR[verb]}), so reading literals inside the expression gets them right.

What the correction changes is the rule's obligation, not the choice of host. At 12% the "report unresolvable fragments rather than silently pass" path is a routine path, not an edge case: it needs its own RuleTester case, and the interpolation boundary must be handled explicitly — a naive scan of a template literal yields junk tokens like ${TONE[tone]}, ? and : as if they were classes. And the deeper ⓪ finding supersedes the whole "literals at className=" framing: the dominant idiom in src/components/ is module-level constants and lookup maps whose literals sit nowhere near a className= at all — binding requirement below.

collection.test.tsx is left alone: it keeps asserting the collection's contract (roster completeness, @madeof composition), and the vocabulary check moves to the lint rule that can actually see all of ui/src/.

Could it be a lint rule? — yes, and it is

It is the natural home, and review chose it. Cost stated plainly: the project has no ESLint today — no eslint.config.*, no .eslintrc*, no lint script, zero eslint packages installed; the UI's static gates are npx tsc -b and npx vitest run. So this WU introduces the lint toolchain rather than extending one.

②ᵃ The check — an ESLint rule, scoped to scale-bearing classes only

Two corrections to the previous draft, both from review. The host becomes ESLint, not a vitest scan — asked for twice, and the editor-squiggle benefit is the deciding argument: an AI agent editing a component sees the violation at the offending class instead of in a test report after the fact. And the check is narrowed to classes a theme scale actually governs, because the previous "every class resolves to a project token" framing would have red-flagged 55 structural classes that carry no value at all.

The discriminator is mechanical, not a hand-written allowlist — which is what makes it maintainable. Verified with resolveConfig: it exposes 119 theme scales; spacing, width, opacity, zIndex, borderWidth are all present, while position, display and flexDirection are absent entirely. So "does a scale govern this?" is answerable from the config itself, with no per-class exceptions.

But prefix alone is the wrong key, and this plan's original phrasing — "iff its utility prefix maps to a theme key" — is under-specified in a way that manufactures the very false positives it was designed to prevent ⓪-corrected. Four prefixes are overloaded: text- spans three things — text-chrome (fontSize), text-ink (colour) and text-center/-left/-right (alignment, no scale at all), so a naive prefix match reds the alignment trio · border- spans width, colour and the border-none reset · outline- and font- likewise. The rule must classify on the resolved (prefix, value) pair. This is a correctness requirement, not an implementation detail — it is the single most likely source of false positives in the whole check.

Two further edge cases, both handled by normalising before lookup rather than by exclusion: variant prefixes (12 sightings — hover:text-ink, disabled:opacity-40, focus-visible:outline-1, placeholder:text-ink-mute) are stripped, then the base class is judged · slash opacity (4 sightings — bg-black/50, border-hairline/40, bg-canvas-soft/30) splits into colour token + opacity modifier, each checked against its own scale. Step ① found the consequence that ruling implies: the opacity scale must carry named modifier steps, or closing it silently kills every slash-opacity class.

The three tiers — and why only Tier-1 lands here

The harness enforces three tiers over a design run. They differ in who judges, which is what decides the ordering.

TierJudgeScopeWhat it catchesWU
Tier-1 mechanical code — verify-doc the 13 hard rules + completeness + receipt-coverage an off-token value, a missing catalog column, an unreceipted soft rule. Deterministic, no judgement. W6
Tier-2 self-reflex the designing agent, on itself its own receipt — one verdict + citation per soft rule a design that satisfies every hard rule and is still bad. Forces the agent to state why each soft rule is met before it can pass. W7
Tier-3 adversarial a second, independent agent soft rules + new-component warrant a self-serving Tier-2 receipt, and a component invented when an existing one fit. The check that cannot be self-administered. W7
Why the deferral holds — and it is not "capacity". Tier-2 and Tier-3 judge soft rules against the rulebook. This WU is rewriting that rulebook: zero-accent is rewritten, mono-for-wire-data re-subjected, familiar-idioms re-scoped, progressive-disclosure promoted, and new rules adopted or rejected. Building the two judged tiers first means writing a judge against rules that change underneath it, then rewriting it — the same rework the epic plan avoided by putting the rulebook before the harness. Tier-1 is different in kind: it reads the config and the doc's structure, and the closed vocabulary this WU ships is precisely its input. The ordering is a dependency, not a queue — and if the rulebook had been settled, moving Tier-2 here would be defensible.

Two honest caveats. Nothing enforces the soft rules until W7 lands — after this WU the 13 hard rules are design-time checked and the ~12 soft rules rest entirely on reviewer attention, which is the status quo, not a regression. And the flow e2e stays in W7 because it exercises the complete three-tier flow; an e2e over one tier would be rewritten twice.
