⓪ The sweep — which scales are actually open

The discussion flagged that closing four scales leaves the vocabulary half shut. Resolved against the real config: ~800 utilities resolve across 22 scales, and the project defines tokens in only six.

The sweep surfaced a distinction the ruling did not make: values vs keywords. Some off-list classes are scale values (p-5 = 1.25rem — a number someone picked). Others are keywords with no numeric choice in them: rounded-full, max-w-full, min-w-full, border-none, border-t, leading-none, w-px. All are in use in the shipped collection.

Proposed rule, following the zero-value precedent: a keyword that expresses a relationship or a reset rather than a magnitude is always legal — full, none, px, auto, and the side-only border utilities. It is the same argument that settled min-w-0: "100% of the parent" is not a value picked off a scale. Everything with a number in it stays closed. This is the one ruling the plan makes on its own; it is called out here for review rather than buried in step 1, and if it is wrong the fix is 7 class usages, not a re-plan.

leading-relaxed (1.625) and tracking-wide (0.025em) are not keywords by this test — they are named magnitudes. Both become project tokens in step 1.

Doc check or code check? — both, and they are not the same check

A fair reading of "hard rules are machine-checked" is the shipped UI is machine-checked. That is not what the thirteen predicates do, and the plan should not imply it. colour-tokens-only as shipped in W4 reads the design doc's own mockup CSS (xtask/src/doc.rs → mockup·colour-literals); it has never opened a file under ui/src/.

So the 13/13 line means "thirteen hard rules have a design-time predicate" — not "the UI is verified". The gap that leaves is real, and it is why the lint rule is a first-class deliverable in this WU rather than a nicety: it is the only thing in the project that will judge ui/src/ against the vocabulary. The code check — where it runs, and why it is not the collection test

The plan said "collection.test.tsx asserts every class in every component resolves to a project token" and left it there. Measured against the real tree, that deliverable is scoped wrong. Three facts, all checked:

FactConsequence
collection.test.tsx covers only the 24 components in src/components/, via a hand-written ROSTER literal of mounted elementsIts reach stops at the barrel. A screen is not in the roster and never will be — the roster is a vocabulary of reusable parts by design.
164 of 206 className sites live outside src/components/ — Gallery 50, Onboarding 40, BodyViewer 20, FlowDetail 19, FlowList 14, ProxyCloseDialog 13, App 7, Layout 5Scoping the check to the collection would leave ~80% of the class surface unchecked — including every screen, which is exactly what binds: screen rules are about.
The existing test asserts against rendered DOM after mountingIt can only see classes on code paths a test actually renders. A class behind an unexercised branch is invisible to it.
Corrected deliverable: a local ESLint rule over ui/src/**/*.tsx, not a render assertion in the collection test. It reads class literals statically, resolves the scale-bearing ones against the closed config, and reds on anything off-list — no mounting, no roster, no dependence on which branches a test happens to exercise. Coverage is ESLint's config glob, so a new screen is covered the day it is added rather than when someone remembers to register it. Measured feasibility: only 7 of the 206 sites are computed className={…} expressions (BodyViewer · FlowList · Onboarding ×2 · components.tsx ×3); the other ~96% are plain string literals a static reader gets exactly right. The 7 are handled by scanning the string literals inside the expression — a tone map like { ok: "text-ok" } still holds its classes as literals — and any class assembled from runtime fragments is reported as unresolvable rather than silently passed.

collection.test.tsx is left alone: it keeps asserting the collection's contract (roster completeness, @madeof composition), and the vocabulary check moves to the lint rule that can actually see all of ui/src/.

Could it be a lint rule? — yes, and it is

It is the natural home, and review chose it. Cost stated plainly: the project has no ESLint today — no eslint.config.*, no .eslintrc*, no lint script, zero eslint packages installed; the UI's static gates are npx tsc -b and npx vitest run. So this WU introduces the lint toolchain rather than extending one.

OptionCostVerdict
A · vitest static scan — one test file globbing ui/src/**/*.tsx Zero new dependencies. Runs in the gate that already runs. Not taken. Was this plan's first answer, on dependency cost. Overridden at review: it reports violations in a test run, never at the class being edited.
B · local ESLint rule — adopt ESLint 9 + typescript-eslint, author design/vocabulary chosen New dev dependencies, a flat config, a gate step, and a rule-authoring surface. Take it. The deciding argument is where the feedback lands: an agent editing a component sees a squiggle on the offending class, in the editor, before the commit — not a test failure afterwards. For a codebase written entirely by agents that is the difference between a rule that teaches and a rule that scolds. Shape.
C · Tailwind's own content scan Free. Rejected — it cannot red. Tailwind 3 drops unknown utilities silently; that is the same non-alarm noted above.

Recorded because it is a real scope addition: adopting ESLint is infrastructure this WU did not originally carry, and the ~39 sites it reds are the same either way. A second benefit worth naming — once the toolchain exists, later WUs can add rules for the other binds: component hard rules (uppercase-mute-labels, radius-tokens) in the same place, instead of each inventing its own check.

What binds actually means

A rule states where it can be violated — which decides which surface above judges it, and whether a screen must answer for it at all. Today the KB leaves this implicit, so familiar-idioms demands a receipt row from a bespoke detail pane it was never about (finding 15, D7).

bindsViolated inJudged byExample
screena screen's layout / composition decisionsthe design run + its receipt — and the lint rule once the screen is built, since it lints screen files toofamiliar-idioms · overflow-declared
componenta built component's own markupthe lint rule, against real coderadius-tokens · uppercase-mute-labels
botheither — a screen can pick an illegal value, so can a componentboth surfacesspacing-scale · zero-accent

Concretely it buys three things: a binds: screen rule stops asking components to answer it · a binds: component rule stops filling design receipts with n/a · and each predicate knows which surface it belongs on, which is what keeps the two columns above from drifting into one another.

②ᵃ The check — an ESLint rule, scoped to scale-bearing classes only

Two corrections to the previous draft, both from review. The host becomes ESLint, not a vitest scan — asked for twice, and the editor-squiggle benefit is the deciding argument: an AI agent editing a component sees the violation at the offending class instead of in a test report after the fact. And the check is narrowed to classes a theme scale actually governs, because the previous "every class resolves to a project token" framing would have red-flagged 55 structural classes that carry no value at all.

The false-positive problem, measured

The concern is correct and it is not marginal. Enumerated over the real tree — 180 distinct classes across ui/src/:

KindCountExamplesVerdict
No theme scale exists — structural, state, alignment 77 absolute flex grid truncate uppercase items-center justify-between sr-only animate-spin whitespace-pre font-mono out of scope These would have been 77 false positives. Tailwind has no scale to close for them — there is no value in absolute to pick wrongly.
Scale-bearing — a spacing/size/colour/type value 103 px-2 w-64 text-chrome gap-1 z-20 max-h-64 rounded-card in scope The only classes the rule judges. A value was picked here, so it can be picked off-list.
The discriminator is mechanical, not a hand-written allowlist — which is what makes it maintainable. A class is in scope iff its utility prefix maps to a key in the resolved Tailwind theme. Verified with resolveConfig: it exposes 119 theme scales; spacing, width, opacity, zIndex, borderWidth are all present, while position, display and flexDirection are absent entirely. So "does a scale govern this prefix?" is answerable from the config itself. Running the discriminator over the 180 real classes splits them exactly 103 / 77 with no per-class exceptions.

Two edge cases the enumeration surfaced, both handled by normalising before lookup rather than by exclusion: variant prefixes (12 sightings — hover:text-ink, disabled:opacity-40, focus-visible:outline-1, placeholder:text-ink-mute) are stripped, then the base class is judged · slash opacity (4 sightings — bg-black/50, border-hairline/40, bg-canvas-soft/30) splits into colour token + opacity modifier, each checked against its own scale.

The three tiers — and why only Tier-1 lands here

The harness enforces three tiers over a design run. They differ in who judges, which is what decides the ordering.

TierJudgeScopeWhat it catchesWU
Tier-1 mechanical code — verify-doc the 13 hard rules + completeness + receipt-coverage an off-token value, a missing catalog column, an unreceipted soft rule. Deterministic, no judgement. W6
Tier-2 self-reflex the designing agent, on itself its own receipt — one verdict + citation per soft rule a design that satisfies every hard rule and is still bad. Forces the agent to state why each soft rule is met before it can pass. W7
Tier-3 adversarial a second, independent agent soft rules + new-component warrant a self-serving Tier-2 receipt, and a component invented when an existing one fit. The check that cannot be self-administered. W7
Why the deferral holds — and it is not "capacity". Tier-2 and Tier-3 judge soft rules against the rulebook. This WU is rewriting that rulebook: zero-accent is rewritten, mono-for-wire-data re-subjected, familiar-idioms re-scoped, progressive-disclosure promoted, and new rules adopted or rejected. Building the two judged tiers first means writing a judge against rules that change underneath it, then rewriting it — the same rework the epic plan avoided by putting the rulebook before the harness. Tier-1 is different in kind: it reads the config and the doc's structure, and the closed vocabulary this WU ships is precisely its input. The ordering is a dependency, not a queue — and if the rulebook had been settled, moving Tier-2 here would be defensible.

Two honest caveats. Nothing enforces the soft rules until W7 lands — after this WU the 13 hard rules are design-time checked and the ~12 soft rules rest entirely on reviewer attention, which is the status quo, not a regression. And the flow e2e stays in W7 because it exercises the complete three-tier flow; an e2e over one tier would be rewritten twice.
