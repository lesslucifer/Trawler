Outcome

Manual review: run #7, a function that does not exist

The optimised flow run on E-REPLAY's replay composer — the first run on a greenfield function rather than a shipped screen, so the Frame reads the roadmap line and the owner's capability list, not code. It is also the first editing screen designed against a registry of 24 read-only components: four entries (KeyValueRow, Select, SourceSurface, CopyText) refuse the job in their own @avoid text, so the run proposes one component (Field) instead of bending a reuse — against run #6's zero proposals. Closed green: 17/17 soft, 13/13 hard, 0 suppressions. Archived as 2026-09-02-dflow-run-7-replay-composer.html.

Every governed doc answers for its htmldoc layer

Run #7 first shipped unstyled: it carried neither the minted data-htmldoc-id nor the htmldoc.js bootstrap that injects doc.css, so every var(--…) it wrote resolved to nothing — and verify-doc was green throughout, because it checks the design-run contract and says nothing about whether a doc can render. Two predicates now refuse it: htmldoc·id and htmldoc·bootstrap, run before the exempt gate so an archived run is held to them too. The predicate immediately found a second instance — this WU's own proof run, which carried the bootstrap but no id, rendering styled with both interactive layers dead.

Tier-3 caught what the harness cannot

The design dimension found the proof run's receipt complete, fluent and false: it claimed visual-weight-follows-goals and ordering-by-priority satisfied while its own Layout sketch and mockup mount order still rendered guidance first — the Tune call was recorded and never applied. Fixed by applying it. The review also found both new predicates under-verified their own names: the id was read from anywhere in the document (a stray <div> passed while the layers stayed dead) and the bootstrap matched any src ending in the filename (a local copy serving no stylesheet passed). Both now checked where the runtime actually reads them.

Never read the checker source

The flow spec's "How to run this flow" section and the principles both state: Never read the checker source (xtask/src/doc.rs) — verify-doc's failure output and the rulebook rows are the oracle.

Batched fix loop

The flow spec's close step states edit twice, verify twice as the norm. The "How to run this flow" section directs: apply all changes in one pass, verify once, then batch residuals and verify again.
