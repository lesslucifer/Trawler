E-ONBREV — epic plan

Make the setup screen appear, open its instructions, and claim success only at the moments UC-ONBOARD says it does. That covers every way into the screen, not only the first run.

v5 · 2026-09-26 · W2 records since, W3 reads it · Trawler · T3 (docs/work/) · branch epic/onboard-review · built from the timing review (R1–R22)

Intent

E-ONBOARD shipped a setup screen whose content is right but whose timing was designed for one moment only: a first run on a working core with an empty capture. The review found that a launch still checking, a core that is down, a capture holding imported or sent rows, and coming back to set up a second device each show the wrong instructions or none (R1–R9). A sweep of all 282 screen states then found the owner's example (R12) to be one case of a general rule the screen does not keep: actions, steps and sentences follow what the host can do, not what each task reads (R12 – R18). A probe that cannot read also reports "off" (R19). The user-visible change is that setup shows exactly when capture is unproven for the device the user is setting up now. It opens that device's instructions, and it says "set up" only after that device's first captured request. It comes now because E-EXPORT and E-REPLAY added the two row provenances that quietly broke the proof rule (R3), and each new source makes the gap wider.

Non-goals

  • Re-designing the setup screen's content, copy or layout. The design of record stands, and only the moments it appears at change.
  • Attributing a request to a device. The core still cannot say which device sent a flow, and the re-entry session uses time, not identity.
  • New probes (for example a Linux trust probe). R10 is answered by the owner's rule decision, not by a new reading.
  • The quit dialog, reach's bind semantics (DEC-55), and the core's API. Every fix here is client-side. source is already on every row.

Working units

E-ONBREV.W1 — the walkthrough recording

A scripted, mocked walk through the real app window, recorded as captioned video: every step of every platform the screen offers, on each host OS. The shell gains a scenario build feature (never in a release build). It replaces the machine-touching commands (the two probes, the three confirms, the elevated actions, the host OS) with answers the harness scripts, while traffic stays real through the e2e core harness. A WebdriverIO walkthrough spec takes one screenshot per step, and ffmpeg stitches them into one video per host × platform. Each step's caption says what the screen should show and names the finding it checks. The output is cargo xtask ui walkthrough → target/walkthrough/: the videos plus an index page with a chapter per step and a tick-box per expectation. This WU records the before; W6 re-runs the same script for the after.

Open questions

#QuestionProposed default
Q1What does the checking moment render? The shell and the checking dot, with an empty main area. Declared undesigned (no new surface), with no design run.
Q2What does "set up another device" open on? The last platform chosen in this app session if it was not this. Otherwise the picker opens with no answer, and the tasks appear once one is chosen. That no-answer state is new, so it costs a small design amendment in W3.
Q3R10: should the open guide advance by reading order where nothing observes? No. Keep the rule and state it in UC-ONBOARD. Advancing on a guess would be the stepper cursor DEC-33 refuses.
Q4R11: should Disclosure follow the rule only when the rule's answer changes? Yes, by keying the guide on its platform so a switch remounts it. There is no controlled open/onToggle pair (the component's @avoid).
Q5Should the Android emulator stay offered on every host? Yes. The emulator runs on all three.
Q9Record the real Tauri window, or the UI in a plain browser? The real window, through the existing WebdriverIO harness. It is the app you run, and the scenario feature is the only mock seam. Screenshots stitched per step, not a live screen capture, so it needs no Screen Recording permission and every run is frame-identical.
Q10Where do the videos live? target/walkthrough/, out of git. Optionally the index page is published as a private artifact for viewing in a browser.
Q7R19: read the Linux proxy (gsettings get), or answer unknown? unknown. A new reader is the "new probes" non-goal, and unknown already words the task truthfully.
Q8R16: does a failure open the manual route even though "a guide under a button is never the open one"? Yes. UC-ONBOARD already promises it. The rule reads "…while the button can still do the job".
Q6R12: is falling back to the per-task layout a design-of-record amendment or a new design run? An amendment. Both layouts already exist in the design of record (the Simulator renders the per-task one on this host), so W4 cites the amended run and adds no new surface.
