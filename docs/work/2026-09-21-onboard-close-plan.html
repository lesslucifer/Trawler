1 · The e2e spine

ui/e2e/specs/onboarding.spec.ts is rewritten, not extended. Every assertion goes through a data-testid — the harness note the roadmap keeps, because WebdriverIO's *= partial-text selector matches nothing in the embedded WebKit provider and does not error.

The epic plan's journey 2 is not drivable as written, and this is the one place the plan deviates. It asked for turn reachability on through the confirm → a host, a port and a certificate URL render. Three facts make that unreachable from a spec:
FactWhere it isConsequence
Arming goes through a native message dialog before any bind confirm_reach in ui/src-tauri/src/reach.rs WebDriver drives the WKWebView, not an AppKit alert — there is no click to issue
Reach is read once on mount and re-read only from the two calls that change it ui/src/App.tsx, the client.reach() effect an out-of-band POST /reach binds the listener and the running window never learns of it
One core, one window, three specs sequential ui/e2e/wdio.conf.ts there is no second launch in which the core could come up already armed

What this WU does instead. Journey 2 asserts the unarmed half only — the half W1 exists to make honest. The armed rendering stays covered where it already is: integration (App.test.tsx drives armReach against a mocked invoke) and unit. This is a scope statement, not a waiver: the spec is written and green, and it asserts what a spec can observe.

What was considered and refused. Auto-confirming the dialog under the e2e cargo feature would make journey 2 whole. It is refused: that feature today adds the wdio plugins and changes no behaviour, so the e2e build and the release build are the same shell. Stubbing the confirm would make the first behavioural divergence between them, and it would divert exactly the act DEC-55 says must be confirmed — an e2e that proves arming by removing its authorization proves the wrong thing. Recorded as a backlog row rather than taken here.

2 · UC-ONBOARD restated

In docs/use-cases/web-ui.html, against the tip — once. W4 deferred it and W5 wrote the source the restatement reads, for the reason that held both times: a contract restated against a screen the epic is still closing around is a contract written twice.

What the contract says todayWhat replaces it
"a three-step guided setup — Trust the CA · Set the proxy · Make a request" a platform axis: the user names what they are setting up, and every instruction below belongs to that answer. The task count is the platform's
steps 1 and 2 are the two probes; step 3 is the traffic layer unchanged in substance and restated in the screen's terms — a task's state comes from a probe, the traffic layer or the reach this app holds, and never from a click. DEC-33's two layers are kept, and the restatement says so explicitly
"install the CA, set the system proxy — both elevation-gated", two actions one act on this machine, one password prompt, with the two single commands surviving as the manual route. A refused authorization is the user's outcome, worded as one
(nothing about a proxy already set)a foreign proxy is named and its replacement confirmed, and the ask says the old one does not come back
(nothing about reach)the opt-in: off by default, one address, one confirm, dead with the process — and what the screen may promise per platform, which is the row the five off-machine platforms exist to constrain
(nothing about the moment setup succeeds)the list's first paint says it, and offers the next device
(nothing about how much is on screen at once)one guide open; a command on a surface of its own; a caveat under the steps rather than numbered among them
pinned by "the UC-ONBOARD e2e spine"re-pointed at the rewritten spine, by journey name
The explicit statement the epic plan requires: no promise narrowed. The restatement must say outright that nothing the contract guaranteed was withdrawn — the probes still answer for this machine, capture is still the only thing that reveals the list, the save still reports what actually happened, and the quit dialog is untouched. What changed is who the sentences are written for. A restatement that quietly drops a guarantee is the failure mode this row exists to prevent.

5 · The design flow's bill

E-SIMPDF's expected result 6, left standing deliberately: the cut that produced the new flow shape was argued from what artifacts cost the review to re-edit, never from what a round costs to run. This epic ran the flow twice.

RoundStateWhat W6 does

The W2 result already carries a staged table: wall clock from the restore to the close commit, agent turns, output tokens, cache read and cache write — and the reading that matters, that output (145k) and cache read (19.2M) are not one number and a bill reporting a single total would be reporting cache traffic and calling it design effortcarried into the epic result verbatim, with its reading
W4 — the run re-opened, the reading round, re-closednot measured. The W4 result records no clock and no token countrecovered from the session transcript if it is still reachable; if it is not, the epic result states the round was not billed and why — never an estimate. rounds 5 and 6 — the owner's readings inside W5owner-run, not flow rounds named as out of the bill, with the reason: they are readings of a built screen, not runs of the design flow, and folding them in would inflate the flow's cost with work the flow did not do
The bill's one hard rule. Per CLAUDE.md this project produces no work estimates. A measured round is reported; an unmeasured round is reported as unmeasured. The value of this deliverable is that the next cut to the flow is argued from a measurement — a fabricated second data point destroys exactly that.
