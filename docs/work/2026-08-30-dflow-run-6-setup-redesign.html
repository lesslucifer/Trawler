Design run #6 — the setup screen, redesigned

The sixth run of the design flow, on the same screen as run #4 but designed fresh: the milestone is a verdict row (StatusLine, not Notice), the proof command lives with its verdict, and the way out is chrome. Zero proposals.

Design run · 2026-08-30 · Trawler · T3 (docs/work/) · rulebook b769f7e4 · run #4's target: the setup screen, greenfield · the flow it follows

Why this run exists

The reviewer found run #4's design not right. This run re-designs the same setup screen from scratch — same substrate, same capabilities, a different design thesis. Run #5 (the DSH project explorer panel) is a separate draft; this run is numbered #6 to avoid the collision.

Redesign thesis: one milestone zone, one precondition zone, a chrome way out.
  • Run #4 rendered the milestone as a headline Notice (zone A) + a separate proof command (zone C) + a back button (zone D). The Notice needed a headline-size extension — the run's only proposal.
  • Run #6 merges the milestone verdict and its proof into one zone (A, StatusLine + CopyText), keeps the preconditions in a band (B), and moves the way out to chrome. The Notice extension is no longer needed: the milestone is a verdict row (StatusLine @use: "a health check, a diagnostic row"), and the proof command sits under it, one glance away. The redesign proposes nothing.

1 · Frame

Purpose: a first-run operator gets from a fresh install to one decrypted request.

Given (functional input — received, not designed):

  • trust probe (trusted · untrusted · unknown)
  • proxy probe (ours · foreign · none · unknown)
  • observed traffic — any connection reaching Trawler
  • observed decrypt — a real https:// flow (trust proven)
  • one-click CA install (macOS, Windows)
  • one-click proxy set (macOS, Windows)
  • proxy unset
  • per-target instructions (6 trust · 7 proxy · removal · turn-off · unset)
  • copyable proxy command (per target)
  • copyable prove-it command (per target's proxy addr)
  • the configured proxy address
  • host OS from the webview UA
  • the ever-proven latch (once decrypted, capture is proven)
  • step navigation (next · back · goto) — deliberately unused

Not given (may not be assumed to exist):

  • remote trust probe (to a device on the network)
  • per-device attribution (which device each flow came from)
  • a reason for a failed handshake (the decrypt error is opaque)
  • firing the request itself (the app never fires; it only guides)
  • progress inside an elevated action (the OS prompt is opaque)
  • any confirmation that a manual install worked (the user tells us by closing the loop)

Findings this run produces:

  1. The milestone was split across two zones in run #4. The capture verdict lived in a Notice (A) and the proof command lived in a separate zone C. Merging them into one zone reduces the screen's zone count and makes the milestone a single concept — one-term-per-concept.
  2. Run #4's only proposal (Notice headline size) dissolves when the milestone is a verdict row. The extension existed because the milestone was rendered as a headline sentence, which Notice doesn't support. With the milestone as a StatusLine (a health-check verdict), the registry covers the whole screen without growing. This is evidence that a proposal can be an artifact of the previous design's shape, not a registry gap.
  3. The way out was a bottom zone in run #4. Chrome placement matches the shipped app's exit affordance and saves a zone — data-ink-first.
  4. wire-order-preserved: n/a. The setup screen renders no captured collection. Same as run #4's finding 6 (the third time this rule answers n/a).
