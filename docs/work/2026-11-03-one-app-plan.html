E-ONEAPP — epic plan

One launch, one app: the window starts the capture service as a supervised child process, shows its health, and stops it when it quits. cargo run builds and opens the whole app.

v3 · opened 2026-11-03 · owner rulings on Q1–Q14 2026-11-03 · Trawler · T3 (docs/work/) · branch epic/one-app · WU branches wu/one-app/<slug>

Intent

To a user Trawler is one program, but today it runs as two. The core (cargo run: proxy :7420 + control API :7421) and the native window (cargo xtask ui dev, a pure API client per DEC-12) are started separately, and the window cannot start, stop or locate the core it depends on. This epic makes the app own and supervise its core. The core runs as a child process of the app, so a core crash never takes the window down. The app exposes the core's status, a restart, and its live log. The repo becomes one workspace, so cargo run builds and opens the whole app. The core's API-first contract is unchanged: the webview still talks to it over loopback HTTP, and curl still reaches the same API.

Supervised lifecycle

stateDiagram-v2
  [*] --> Attached: TRAWLER_API set
  [*] --> Starting: spawn trawler --core
  Starting --> Running: ready line (proxy, api)
  Starting --> Conflict: exit, port in use
  Conflict --> [*]: native dialog names the port → quit
  Running --> Exited: child exits / crashes
  Exited --> Starting: Restart (Settings or Not-answering)
  Running --> Starting: Restart (Settings)
  Running --> Stopping: quit (✕ · ⌘Q · Dock · logout)
  Exited --> [*]: quit
  Stopping --> [*]: stdin closed → graceful exit, kill after timeout
  Attached --> [*]: quit, attached core untouched
The ready line carries the bound addresses, so fixed ports (production) and ephemeral ports (e2e) use one path. The stdin pipe is the lifeline: if the app dies by any route, including SIGKILL, the child reads EOF and exits, so no orphan holds the ports.

E-ONEAPP.W1 — the repo is one workspace, and cargo run is the app

What it buildsThe decision record DEC-next (E-ONEAPP: the app supervises its core). It supersedes DEC-12's out-of-process and GUI-free-root-build clauses, and keeps its API-first clause. ui/src-tauri joins the workspace as a default member, with one lockfile and lints shared through [workspace.lints]. The app crate gets default-run and the trawler lib as a path dependency. The app embeds the front-end bundle (Tauri custom-protocol), and its build script rebuilds ui/dist when ui/src is newer (Q13). The core's entry gains the flags the supervisor needs: --ca-dir, --proxy-port/--api-port, a ready line on stdout and exit-on-stdin-EOF. These flags are shared by cargo run -p trawler and the app's --core mode.
Maps toUC-4 (one launch). Expected #3 and #6, plus #1 for the window opening (owning the core comes in W2). Q2, Q3, Q10, Q11 and Q13.
Expected outcomecargo run opens the window, and cargo run -p trawler is the headless core. An integration test fails if tauri or wry enter the trawler package's dependency tree. Another integration test spawns the core entry with port 0 and reads a parseable ready line, sees the API answer at it, closes stdin and sees the process exit with both ports rebindable. Unit tests cover flag parsing, the ready-line format and the stale-bundle check.
Dependenciesnone — the first WU

E-ONEAPP.W2 — the app supervises its core

What it buildsA supervisor module in the shell. It spawns current_exe() --core on fixed 7420/7421 (Q4, Q11), waits for the ready line, and injects the bound API address before first paint into every webview the shell opens, including E-INSPWIN's inspector windows, whichever epic lands second. This generalizes e2e_core_address into production. It keeps the child's state (starting · running · exited(code) · attached) and a bounded ring of its stderr lines, and exposes both, plus Restart, as Tauri commands and events. On every exit path (RunEvent::Exit, terminate, logout) it closes stdin, waits, then kills. A port conflict gets a native dialog naming the port, then a quit (Q5). A second launch focuses the first instance (Q8, tauri-plugin-single-instance). Attach mode: TRAWLER_API (renamed from TRAWLER_E2E_API) in every build skips the spawn (Q9). The CA moves to the app data directory and adopts an existing ./ca on first launch (Q6).
Maps toUC-4. Expected #1, #2, #4, #5, #7 and #8. Q4–Q9, Q11 and Q12.
Expected outcomeAn integration test drives the supervisor on ephemeral ports through start → running → kill the child → exited(signal) → restart → running → quit, and asserts both ports are rebindable and no child remains. A second test kills the supervising process and asserts that the child exits. Unit tests cover attach-mode selection, the conflict message, the log ring's bound, and CA-dir resolution and adoption. The quit-dialog rules are untouched.
DependenciesW1 — the workspace, the core flags and the ready line

E-ONEAPP.W3 — the Capture service page

What it buildsA new settings surface, Capture service, opened from the app menu (Settings… ⌘,). It shows the state, pid, uptime and bound ports; a Restart that warns it clears the captured list (flows live in the core's memory); and a live, auto-scrolling tail of the core's log. The attached state shows the address and no Restart. The existing "core not answering" state gains the same Restart when the core is owned. This is a new surface, so it goes through a design run (mockup + lists, DEC-53) and the design-review step before any code.
Maps toUC-SVC, and UC-4 (the not-answering Restart). Expected #10. Q12 and Q14.
Expected outcomeVitest covers each state's rendering, the Restart confirmation, the attached variant, and the log tail's bound and auto-scroll against the supervisor's command and event contract. A shell integration test asserts that the Restart command round-trips through the supervisor.
DependenciesW2 — the supervisor's state, log and Restart it renders

Open questions

#QuestionAnswer
Q1The core in the app's process, or as a sidecar child process? owner ruling 2026-11-03 Sidecar, managed from the GUI process, with a settings page for its status, a restart and its log (→ UC-SVC, W3). A core crash no longer takes the window down.
Q2How does cargo run open the GUI? owner ruling 2026-11-03 Refactor: the packaging is now the whole app. ui/src-tauri joins the workspace as a default member with default-run, and the core stays the root package. No launcher binary is needed.
Q3May cargo build / cargo test at the root compile the GUI? owner ruling 2026-11-03 Yes, as the base for packaging the whole app in a future epic. This replaces v2's "No". The trawler lib itself stays GUI-free, and a dependency-tree test guards it.
Q4Fixed ports or ephemeral? owner ruling 2026-11-03 Fixed 7420/7421. A conflict gets a dialog with no silent fallback. Ephemeral only in the e2e build.
Q5A headless core is already on the ports: attach automatically? owner ruling 2026-11-03 No. Only an explicit TRAWLER_API attaches. Otherwise the conflict dialog appears.
Q6Where does the CA live? owner ruling 2026-11-03 As proposed: ~/Library/Application Support/dev.trawler.app/ca, adopting an existing ./ca on first launch. The headless core keeps ./ca.
Q7Closing the last window: quit, or keep capturing in the background? owner ruling 2026-11-03 Quit for now. A later epic brings the background service and tray icon.
Q8A second launch?owner ruling 2026-11-03 Single instance: focus the running window.
Q9Attach mode in release builds, or e2e only? owner ruling 2026-11-03 Every build, as TRAWLER_API.
Q10May the epic edit the T0 lines in CLAUDE.md that describe cargo run and the out-of-process app? owner ruling 2026-11-03 Yes, at W5 once the truth has changed, via mr commit with a Reviewed-By trailer. This includes the "headless build stays GUI-free" line, which Q3 makes untrue.
Q11What binary runs as the sidecar? owner ruling 2026-11-03 As proposed: the app binary re-executes itself as trawler --core, which calls the same core entry as cargo run -p trawler. A plain cargo run builds only the app package's binaries (checked), so a separate trawler-core binary would be missing on a fresh clone. Tauri's externalBin also needs a target-triple-named file staged before its build script runs. With self-spawn there is one binary to build, bundle and sign. The cost: the child links the GUI frameworks without ever initializing them.
Q12The core dies mid-session: restart it automatically? owner ruling 2026-11-03 As proposed: no. The window stays up, the state shows exited(code) with the log tail, and one press restarts it. A silent restart would hide the crash and would quietly empty the captured list, which lives in the core's memory.
Q13The root build now compiles the app, which embeds the front-end bundle. How does cargo build get ui/dist? owner ruling 2026-11-03 As proposed: the app's build script runs pnpm build when ui/src is newer than ui/dist, and fails with a message naming pnpm install when Node/pnpm is absent. As a consequence, the root cargo test needs Node + pnpm installed. Server/CI use without them is cargo test -p trawler.
Q14Does the Capture service page offer Stop as well as Restart? owner ruling 2026-11-03 As proposed: Restart only. A stopped core while the system proxy points at :7420 leaves the machine without internet, which is exactly what DEC-64 guards. Quitting remains the way to stop, and it goes through DEC-64's check.
