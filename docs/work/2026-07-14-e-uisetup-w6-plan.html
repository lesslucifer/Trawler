E-UISETUP.W6 — Onboarding UX enhancement

The onboarding journey shipped (W1–W4) but under-delivers on the epic's own UX rules. W6 makes each step's status honest, device-aware, and immediate: it reads the real machine state (trust store + system proxy) for the ~90% local case, treats any traffic reaching Trawler as proof the proxy routes, and turns the ambiguous cases into clear messages instead of a dead-end "Waiting…". This deliberately reverses two earlier "prove by capture only" calls (see Reversed decisions) and adds one small core signal so the proxy step is observable even before decryption works.

Built v3 · 2026-07-15 · Trawler · T3 WU plan · epic: E-UISETUP · builds on: W1 + W4 · sequenced after: W5

As built — one WU, three layers. W6 spans the core (connection-seen signal), the Tauri app (one read-only CA-trust probe; the proxy probe reused W5's proxy_status), and the UI (status model + P1/P3 + copy pass). It shipped as a single coherent contract — honest per-step setup status — not split. One deviation from plan, owner-approved: the CA-trust probe matches on the CA's Common Name, not a SHA-256 fingerprint — avoids a crypto dep in the thin Tauri shell; the stale-cert ceiling + fingerprint upgrade path are marked with a ponytail: note in setup.rs.

Requirement

Every onboarding step answers its own question truthfully, with the least user work, and never misleads in the edge cases. Three fixes plus one enabling core signal:

  • (1) Verify is actionable (P1). Instead of a bare "Waiting for your first decrypted HTTPS flow…", the step renders a concrete, text-only prove-it instruction — open any site (the proxy is system-wide once set), or a copyable curl -x http://<addr> https://example.com carrying the real proxy address. Success still flips green only from a real captured flow (W4).
  • (2) Honest, device-aware per-step status (P2). Each step derives a separated status from two independent signals — a local probe (does this machine trust the CA / point its proxy at Trawler?) and observed traffic (has any request/connection reached Trawler, from any device?). Trust is confirmed by the local fingerprint probe or a decrypted flow; when neither holds it shows a clarifying message, never a red error. Proxy is confirmed by the local probe or by any connection reaching Trawler. Verify is the decrypted flow that also reveals the list. No extra user step: the remote / manual / un-probeable cases are inferred from the signals and shown plainly.
  • (3) The happy path is unburied (P3). Where a one-click action exists (macOS / Windows) the manual per-OS steps collapse behind an on-demand "set it up manually" disclosure; where there is no auto path the manual steps stay inline.
  • Enabling core signal. The proxy passes CONNECT through untouched (recorder.rs), so an undecryptable HTTPS attempt leaves no trace. W6 adds a connection seen signal (count + event) so "proxy is routing" is observable for every device, decrypt or not.

Instructions and snippets stay text, never markup (UC-3/UC-4 invariant).

Maps to

Epic E-UISETUP · UC-5 — the epic's own UX rules "do the work for the user / least manual work wins" and "show the user a truthful state". Touches: the core (event.rs, store.rs, recorder.rs, api/) for the connection signal; ui/src-tauri for two read-only probes; and Onboarding.tsx + setup.ts for the status model + P1/P3. Design

Two truths per step

The fix for P2 is recognising each step has two independent signals that answer different questions — a fast local precondition and an authoritative outcome. Per-step status is driven by the probe; Verify by capture; and capture can retro-confirm a step whose probe was blind (the remote case).

SignalAnswersScopeSpeed
Local probe (trust store / system proxy)"Is this machine configured?"local, ~90%instant
Observed traffic (connection / flow)"Is traffic actually reaching & decrypting through Trawler?"any deviceneeds traffic

  C -- "https:// flow (decrypted)" --> OK["Trust ✓ + Verify ✓ proven → reveal list"]
Probes light the steps immediately for the local case; observed traffic confirms (and, for other devices, is the only thing that can).

Per-step status — separated and truthful

Every row below is a state the app can honestly distinguish. The ✗/⚠ cases are actionable; the "can't tell" cases are worded to guide, never to alarm.

No mode toggle, no extra step. The remote-device case is inferred, not declared: if the local probe finds nothing but traffic is arriving, the wording already says "on the device sending traffic". The existing target picker still switches the manual steps to a device's instructions; nothing new is asked of the user.

Core: the "connection seen" signal

A CONNECT is passed straight through today (recorder.rs — if req.method() == Method::CONNECT { return req.into(); }), and a flow is only created for a fully-decoded request. So an HTTPS attempt from a client that doesn't trust the CA fails its handshake and leaves nothing in /flows. W6 records the connection itself, reusing the existing broadcast bus so every interface tails it exactly like flows:

FileChange
event.rsAdd FlowEvent::ConnectionSeen { authority } (the bus is the "what the proxy observed" channel; update its doc comment).
store.rsA connections counter + note_connection(authority) that increments and broadcasts ConnectionSeen; connection_count() reader.
recorder.rsIn the CONNECT branch, read the target authority and call store.note_connection before returning — no behavioural change to the tunnel.
api/view.rssse_event maps ConnectionSeen → event name connection, data { authority }.
api/routes.rs + mod.rsGET /stats → { connections } for the launch/entry read (mirrors W4's one-shot /flows read); live updates ride the connection SSE event.

UI consumption. On entry the onboarding reads /stats once (any connections so far?) alongside W4's /flows read, then updates live from the connection and flow events on the one existing /stream. "Any traffic seen" = connections > 0 or any flow present; "not decrypting" = traffic seen with no https:// flow.

Match the CA by fingerprint (computed from the /ca.crt bytes the UI already fetches) so a stale certificate can't false-positive. Where a probe can't conclude, the step shows ◐ Can't verify here — capture will confirm — never a false "not set up". Probing is reliable exactly where auto-setup is (macOS / Windows), which is the same ~90%.

P3 — one primary action, manual behind a disclosure

On an auto-capable OS the one-click action stays primary and the per-OS "Steps for [OS]" list moves inside a <details> — "Set it up manually instead" — the same disclosure pattern already used for "Remove the certificate later". Where there is no auto path the manual steps render inline. Pure render reshuffle.

Reversed decisions (logged at distillation). W2 stated "no trust-store inspection — trust is proven by capture, not by reading the store" and W4 deferred any OS probe / self-test. W6 supersedes both on owner review: local probes cover the 90% single-machine case with instant, honest per-step feedback (and detect a manually-trusted CA that the old model couldn't). Capture remains the authority for the remote/other-device cases and for revealing the list. A DEC recording this reversal + the new /stats · connection API fact lands with distillation.

Waiver (judged at review). The two probes read the real machine, so they are not hermetically runnable — their output parsers + the status derivation are unit-tested and the live probe is waived, exactly as W2/W3's auto-set commands are. The connection signal is hermetic (drive a CONNECT at an ephemeral core) and is proven at integration, no waiver.

Done when

  • Verify shows a concrete, text prove-it instruction with the real address; the green flip is still capture-driven.
  • Each step shows a separated, honest status: Trust from the local probe or a decrypted flow (else a clarifying, non-alarming message); Proxy from the local probe or any connection reaching Trawler; a step never acted on shows no false ✓; un-probeable OSes show "can't verify — capture will confirm".
  • An undecryptable HTTPS attempt (untrusted-CA handshake) records no flow but bumps /stats connections + emits a connection event; the proxy step reflects it.
  • On macOS / Windows the one-click action is primary with manual behind a disclosure; text-only render.
  • Gates green headless: cargo test + cargo clippy (core) · vitest · cargo xtask ui build; e2e run green.

Non-goals

  • A one-action "Set up Trawler" chain (CA → proxy → verify behind one button) — deferred; W6 keeps the three discrete, consent-per-change steps.
  • An app-initiated self-test request — the prove-it prompt guides the user; the app fires no network of its own.
  • Recording undecryptable requests as flows — connections are a lightweight count + event, not entries in /flows (no CONNECT pseudo-flows cluttering the list).
  • Probing remote devices — impossible; remote trust/proxy is shown from observed traffic + clear wording only.
  • A settings / preferences panel — epic non-goal.
  • Proxy teardown / auto-revert — that is W5.

Carried from W5 (deferred here). W5's quit-time proxy check shows a remote-device "check your proxy" notice whenever no Trawler proxy is detected on this system (a device elsewhere may still route through Trawler). That fires even for users who never proved capture, so it can nag on quit before Trawler has done anything. W6 refinement: when no system proxy is detected, only show that notice once capture has been proven (a request was actually proxied through Trawler), so a user who never routed traffic isn't warned about a proxy that cannot exist. Gate the info-only (non-"ours") branch of the quit confirm on the same everProven / captured signal W4 already tracks.

Sequenced after W5. W6 depends only on the merged W1–W4 surface; W5 (proxy teardown) is independent and also touches the onboarding surface / setup module. Landing W5 first means Onboarding.tsx is polished once, over the complete feature set, rather than twice. W6 needs nothing from W5 — the ordering is efficiency, not a hard dependency.
