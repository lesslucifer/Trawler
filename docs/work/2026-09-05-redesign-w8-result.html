Deviations

What changedWhy
A third bodyNotice sentence, not two. The plan said the too-large notice would state a human size. The type says actual: number | null, so there are two too-large cases, and the build wrote a sentence for each: not captured — too large (12 MiB) and, when the server reported no size, not captured — too large. The obvious transcription — humanBytes(body.actual ?? 0) — renders "too large (0 B)", which is a false statement in the one place the pane exists to make true ones. Dropping the parenthetical says exactly what is known. The same rule the design applied when it refused to quote a string the code does not produce.
The e2e origin gained two routes. /xml serves application/xml; /big serves 200 000 bytes of text/plain — past the UI's 128 KiB render cap and far under the 10 MiB capture cap, so the body is captured whole and the pane must state what it left out. The epic plan names both as UC-5's new e2e contracts. Neither could be proven against the existing origin, which serves only JSON, brotli-JSON and a PNG. Hermetic — the harness's own local HTTPS origin on an ephemeral port, no public network.
A data-testid="body-viewer" with data-leg on the pane. Not in the design, which does not concern itself with test hooks. Two panes put two of every body testid on the page, so every e2e body assertion had to be scoped to its leg. The alternative was adding a prop to registry Section — a change to a component this WU is meant to consume unchanged, and outside its scope. The hook lives on the element the screen owns.
The old BodyViewer.test.tsx was rewritten, not extended. Its assertions encoded a <details> tree, leg tabs and a copied that never reverts. All three are things this WU deliberately removes; each deleted assertion maps to a design line that removed it. A suite kept green by keeping the defect is the failure mode the plan named as a risk. The replacement is 21 tests where the old file had 16 — the 21st added at review.
Two e2e assertions in the existing spec changed wording, not intent. "renders a JSON response body as a tree" → "as copy-exact source"; the brotli case likewise. The tree is gone by design (DEC-01). The assertion now checks what replaced it — that the rendered document carries the braces and quotes the tree form dropped, which is what makes a copy valid JSON. The spec's spine is unchanged.

What the design asked for, and what the build did with it

Three places where the design's instruction was to not do something, and the build's evidence that it did not:

The design's ruleWhat the code does
"Every cap is the member's own, and the caller sets none of them." BodyViewer.tsx imports no TEXT_MAX, HEX_MAX or TREE_MAX, and passes no threshold to any member. The caps arrive because the members apply them.
"C carries no mount in this screen's tree" — CutMarker is rendered by the members, never by the screen. No CutMarker import. The screen's only truncation duty is the Tune call that followed: B is a bounded scroll box, so the marker at the member's output foot cannot scroll out of sight.
"No retry — a retry is a new user-facing capability and the epic's non-goals forbid it." Notice's action slot is recorded as deliberately unused. No action prop is passed on any of the seven notices, and a unit test asserts no retry control exists on the failure state — so a later edit that adds one turns a test red rather than passing silently.

The Tier-3 review, and what it changed

Eight candidates from six finders; one survived verification, and the fix it prompted led to a second change the review itself had refuted. Recorded because a report that absorbs review findings silently is the failure the report exists to prevent.

FindingSevWhat it was, and the fix
"Both are small"nit The eager-mounting follow-up justified deferring the two-fetch question by calling both fetches small — an unsupported claim contradicted by this WU's own numbers: the capture cap is 10 MiB per leg, getBody buffers the whole response, and this WU built a 200 000-byte e2e fixture precisely because bodies are not small. Fixed: the entry now states what is actually true (each fetch is cancelled on unmount; nothing is measured), names the unbounded size, and adds the second-order cost the first draft omitted — two CodeMirror surfaces when both legs are structured.
The eager value proprefuted, then real The efficiency finder called value={"{shownText()}"} beside getPayload wasted work: getPayload wins at click time, so value only seeds useConfirm's reset key, yet it decoded the whole body on every render. The verifier refuted it — it probed CopyButton in isolation, found that dropping value leaves the reset key undefined, and concluded the prop was load-bearing. That refutation is wrong at this call site, and checking it is what settled the matter: every mode or leg change runs setFetched(null), which unmounts the whole action group, so the confirm can never survive a payload change here with or without value. Proved by deleting the prop and watching the suite stay green — a test that cannot fail was not evidence. Fixed: the prop is gone, and the test that was written to guard it now states the invariant that actually holds (unmount clears the confirm), so a refactor keeping the button mounted across a refetch has to answer for a stale one.

Six candidates were refuted and are recorded so finder quality stays visible: that the two new Section call sites should use the registry Section (that swap is W6's row in the epic plan, W5's design is unmerged and unreachable from this tip, and the two components' heading tokens differ — text-chrome against text-body — so it is not the drop-in it appears to be); that shownText duplicates the renderer's decode (true, and pre-existing — the base commit's copyBody did the same); that the comment's zone letter B is undefined (it is the design run's own vocabulary, which is where CLAUDE.md puts this rationale); that the follow-up omitted the CodeMirror cost (folded into the fix above rather than left refuted); and two design findings arguing design run #9 misread W5 — both aimed at an artifact this diff does not touch, landed by a previous WU, and judged against a sibling branch that is not reachable from this tip.

Follow-ups

WhatWhose
Where the panel puts the two body sections. This build stacks them at the foot of the panel, after the header tables — the arrangement design run #9 sketched and named as the panel's call. The pane is leg-agnostic under any arrangement, so moving them costs nothing. W5/W6 — the flow-detail design owns the panel's zoning. W5's run exists on wu/redesign/flow-detail but is not merged into the epic and was not read here.
Eager vs lazy mounting. Two panes mean two body fetches whenever a flow is opened, where the shipped screen made one — and a flow whose legs are both JSON or XML now mounts two CodeMirror surfaces at once rather than one. Neither fetch is bounded: the capture cap is 10 MiB per leg and getBody buffers the whole response, so this is not a small cost by assertion — the render caps this same WU applied exist precisely because bodies are not small. What is true is narrower: each fetch is cancelled on unmount, and nothing here has been measured. Recorded so the question is visible rather than discovered. W6, with the panel's zoning — deferring a body's fetch until its section is scrolled to is a panel decision, not a pane one.
Whether raw mode should offer a decoded-JSON view of a compressed body. Carried forward unchanged from design run #9's blocked-on list — a capability question, not a layout one, and this build invented no third mode. owner — unchanged.
