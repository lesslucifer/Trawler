Design run — the capture-management controls

The first three controls that change server state: take the capture out, bring one back, and empty it. Designed onto the flow list, the screen whose chrome is currently a filter bar and a list.

Design run · 2026-09-05 · Trawler · T3 (docs/work/) · E-EXPORT.W5 · UC-4 · UC-6 · UC-7 · flow: design-flow · rulebook pinned aeff5b0 · registry 24 entries · builds in W6

1 · Frame

Purpose: a developer hands their capture over, opens one they were handed, or empties it before a repro.
Given: GET /flows/export, filtered · POST /flows/import → {imported:n} or 400 + reason · DELETE /flows, filtered → {removed:n} · DELETE /flows/{id} · source on the flow and in FlowFilter · FlowsCleared on /stream · Tauri dialogs.

Not given (may not be assumed to exist): progress on export or import (both are one-shot, no byte counter) · an undo for a clear · ?format=curl and its flag-naming refusal (W7, unbuilt) · a per-flow delete affordance in the list · any confirm-before-act primitive in the collection.

IconButton ×3
T1		 A′ · the three doors
reuse
Its @use is icon-only triggers; the header has no room for words.
why

Clears @avoid "actions with no fitting glyph" — out, in and empty are the three most conventional glyphs in the genre (⇧ ⇩ ⌫), and familiar-idioms is why they read without labels. Clears @avoid "primary actions (no visual weight at rest)": none of the three is primary, and the list stays the subject quality wants exactly the bare, unweighted rest state this component has. Lands in @use "icon-only triggers unambiguous in place". The accessible name is the component's own guarantee, which is what stops three unlabelled glyphs being three unlabelled glyphs to a screen reader.

The near-miss worth stating: Button with a word label was the first choice and is the better control in isolation — a word never needs a tooltip. It loses on the header is already full constraint, not on merit: "export · import · clear" is ~180px of the same line that holds four fields. Recorded here so the build does not re-open it as taste.

TonedText
T1		 A′ · progress line
reuse
The second half Button's fork D4 makes mandatory.
why

IconButton composes Button, whose @states is explicit: no loading state of its own — for a slow action the caller MUST render both halves: the control disabled for the whole in-flight window, AND a progress line in the same zone naming what is awaited. So the progress line is not a decoration this run added; it is the contract the component imposes on any caller with a slow action, and export and import are both slow. Lands in @use "any short value whose meaning is carried by tone". Clears @avoid "a toned sentence or prose with an action" — "exporting…" is a value, not a sentence, and carries no action.

Tone is muted: in-flight is neither success nor failure, and the chromatic set has no third meaning for it. That is also why the outcome does not flash green here — see the outcome table.

Button ×2
T1		 E, F · the ask's two answers
reuse
A word each, and deliberately no emphasis on either.
why

Lands in @use "any action that needs a word and is not a copy". The interesting clearance is @avoid "emphasis by styling: pick which actions to offer instead, a Button never carries a primary/filled variant" — so the destructive answer cannot be made red or heavy, which is the convention most confirm dialogs use. The alarm lives in the question instead (the Notice below), and the two answers are peers. Also clears @avoid "warn-toning it inside a warn Notice (the message owns the alarm, the button is the way out)" — that @avoid line describes this exact composition, so the design follows it rather than fighting it.

Per its TSDoc — rest · hover · focus · active · disabled. No confirming state of its own.
Notice
T1		 E, F · the question and the refusal
reuse
One sentence at a tone, with the action slot left empty.
why

The question ("this removes 214 flows — the capture is not saved anywhere") is tone="warn": a failure-or-alarm sentence, which is the tone's fixed meaning. The refusal ("not a valid curl command — --data-raw is not supported") is also warn. Both clear @avoid "transient confirmations of an action" because neither is transient — the ask stands until answered, the refusal stands until the paste changes.

The action slot stays empty on purpose. Notice can hold a Button, which would make the whole ask one component. Rejected: the ask needs two answers and the slot takes one, and a cancel that is not a peer of the act is a dark pattern. The two Buttons sit beside the notice in the screen-owned panel instead.

AskDialog
T4 → T3 here		 E, F · the modal frame
propose
Nothing in the collection is a dialog, and two doors now need one.
why

The registry has 24 entries and no modal, no scrim, no focus trap. ProxyCloseDialog exists in ui/src/ but is a screen, not a collection entry — it hand-rolls its own scrim and panel. This run needs the same frame twice (the clear ask, the curl paste), and W7's paste makes a third caller likely, so the second sighting the vocabulary waits for has arrived.

What the plan got wrong. The epic plan says the clear confirmation is "wired through the existing useConfirm". It cannot be: useConfirm is a ~2 s after-the-fact flash shared by CopyText and CopyButton — it reports that something happened, it never asks permission. Using it for a destructive act would mean clearing first and flashing afterwards. Recorded as a deviation, not silently corrected.

Proposed rather than built here, and deliberately not designed in full: a component's states, tones and internal layout are its own design file's truth. This run states the two things it needs from it and leaves the rest to the proposal's owner.

The four outcomes, and why only one of them is chromatic

ActWhat the user sees at the endWhy not something louder
export succeeds The progress line clears. The native save dialog already closed — the file is on disk. The OS dialog is the confirmation; a second "saved" in the header would confirm what the user just watched happen. data-ink-first.
import succeeds The progress line clears and the list refills with marked rows; the count moves. The list changing is the feedback, and it is impossible to miss. A toast would also violate confirm-at-point.
clear succeeds The ask closes; the list empties to Notice "no flows yet — send traffic through the proxy". An empty list after asking to empty the list needs no announcement. The existing empty state already orients.
any of them fails A warn Notice at the point of the act — in the ask for import and clear, in A′ for export — carrying the server's reason verbatim. This is the one case that must be loud, because nothing else on screen would change. absence-names-itself: a failed import and a failed clear never share a sentence.

So three of four outcomes are silent by design: the screen already shows the result. Only failure gets a channel of its own, and the epic's FlowsCleared event means a clear triggered from another client reaches this list the same way — the list is the truth, not a message about the list.

The keyboard gap this stage found. Every control above reaches the keyboard through Button, which already owns focus and activation — so unlike the flow row, nothing here needs a new grammar. What is genuinely new is the modal contract: focus into the dialog on open, trapped while it stands, returned to the trigger on dismiss. That is three keyboard behaviours no shipped surface in this app implements, and it is why AskDialog is proposed as a component rather than hand-rolled twice — focus-returns-to-origin binds per dismissable surface, and two hand-rolled copies is two chances to get it wrong.

The lexicon collision — which word the UI uses

The epic plan flagged this as the run's to settle. The rulebook's Lexicon row reads: copy means "put on the clipboard, verbatim", never "grab · export · save". So export is reserved against copy — it is not a banned word, it is a word that must never be used to mean copy.

CandidateVerdictWhy
exportadoptedIt is the literal, correct name for the operation, it is the word HAR tooling uses, and familiar-idioms prefers the genre's term. The reservation it seems to collide with is a rule about copy, and this operation is not a copy — it writes a file, and the clipboard is not involved.
saverejectedAlso on the same forbidden list, and worse: it implies persistence, which the non-goal explicitly denies (a HAR file is an artifact, not an autosave).
downloadrejectedWrong genre for a native app writing a local file, and it would be a second term for one concept.

The write-back this run owes the rulebook (at distillation, not mid-run — DEC-14): the Lexicon gains a row so the next design does not re-litigate it.

| Term   | Means                                    | Never                        |
| export | write the capture out as a HAR file      | copy · save · download       |

And copy's existing "Never" list keeps export — the two rows are consistent: copy is never called export, and export is never called copy. One term per concept, both directions.
