Requirement

Another Windows PC's steps keep a proof once that PC has made one, so a refusal from an app that will never decrypt does not turn step ④ red. Each status line's advice is true of Windows. Each command runs as written in Windows' default shell and finds the file the step before it downloaded. A test holds each rule.

Findings

#What goes wrong todayProposed fixRuling
S1A refusal after ④'s proof undoes it. Once a browser on that PC goes quiet for 30 s, any tunnel nothing decrypts turns ④ "⚠ not working" and tells the user to finish the certificate step, under a ② that reads done. Windows starts its own background HTTPS the moment its proxy is set. While any of it pins its certificate, the ⚠ stays, and no step the user takes clears it.on an off-machine platform whose ② holds a decrypted proof, ④ keeps "done — decrypted at 14:02". The refusal becomes a muted note under it, naming what a proof rules out. ② is unchanged: one decrypted request already outranks any refusal there
S2The certificate's advice is wrong for Windows. Both ②'s note ("Firefox keeps its own store — import it there too") and its ⚠ line ("… and Firefox keeps its own") say Firefox needs a separate import. Firefox on Windows reads the machine root store by default (Mozilla), and certutil -addstore ROOT writes to that store.Windows' guide drops the Firefox note. Its ⚠ advice reads: "Already did? A browser reads Windows' store when it starts — restart it. Apps that pin their own certificate never decrypt."

Part 2 — steps that cannot be done as written

Each of these leaves its step "can't check here" forever. That status is honest, but it waits for a request the step as written can never produce.

#What goes wrong todayProposed fixRuling
C1③'s command fails in Windows' default shell. It joins two reg add commands with &&. Windows PowerShell 5.1, the shell that Windows 10 and 11 open from Start, Win+X and Terminal, rejects that: "The token '&&' is not a valid statement separator in this version." Nothing is set. The lead says "Run:" and names no shell. This machine's manual steps on a Windows host print the same command.the lead is "In PowerShell, run:", and the two writes are joined by ;, which works in PowerShell 5.1 and 7
C2②'s command names a file the terminal cannot see. certutil -addstore -f ROOT trawler-ca.pem is relative, and the step before it saved the file to Downloads. An elevated terminal starts in the home folder (Windows 11) or C:\Windows\System32 (Windows 10), so certutil cannot find the file. Another Mac's and Ubuntu's trust commands use the same bare name from a terminal that opens in the home folder."In PowerShell as administrator, run: certutil -addstore -f ROOT "$HOME\Downloads\trawler-ca.pem"". The download step's file and the command's path stay one constant, so they cannot drift apart
