Hình 1 — every mechanical check a design run passes through, and the one lane that stays human.
The split is the point. The harness proves a receipt is complete and well-formed — never that it is true. What makes a false row expensive to write is composing specimen.css; the checker only makes a missing row impossible.

Nothing in the first two lanes is new wiring: verify-doc-post.sh (PostToolUse) and verify-doc-stop.sh (Stop) already run on every governed doc. A new artifact type inherits both for free.

The slug list is read, never copied. A new pure extractor pulls the first <code> of each row in the rulebook's own hard-rules-table / soft-rules-table — so when W6 adds, kills or retags a rule, every receipt goes red until it answers the new list. No second copy of the slugs exists anywhere.

The receipt is parsed as YAML, not scraped your comment — serde_yaml 0.9 is already an xtask dependency and every gate note (test/v2, cr/v2, dod/v1) is already a #[derive(Deserialize)] struct in xtask/src/notes.rs. The receipt joins them instead of inventing a parser:

#[derive(Deserialize)]
pub struct Receipt {
    pub rulebook: String,              // the substrate pin
    pub soft: BTreeMap<String, String>, // slug -> "<verdict> — <why>"
}

pub struct Rule { pub slug: String, pub hard: bool }
pub fn rules_from_rulebook(html: &str) -> Vec<Rule>

pub fn verify_html(html: &str) -> Verdict                                  // unchanged — 18 call sites untouched
pub fn verify_html_against(html: &str, rules: Option<&[Rule]>) -> Verdict   // run_paths loads the rulebook once

All the checker does by hand is lift the <pre>'s text (existing helper), decode entities, and split_once('—') the value into verdict + why. Indentation, quoting, duplicate-key detection and error positions are serde_yaml's problem. The checker stays pure (no filesystem); run_paths reads the rulebook and passes it in.

Why this is right your comment: a hand-written satisfied on spacing-scale is the one row an agent can be wrong about for free — and it was, until the mockup composed the real CSS. A rule with a predicate should be judged by the predicate, never by the run's own claim about itself. What is left in the receipt is exactly what has no predicate: judgment.

Verdict enum, fixed at seven: satisfied · inherited · satisfied-via-proposal · blocked · n/a · violated · violated-inherited. The last closes finding 26 — a receipt could not say whose violation it was, which made re-authoring a component's CSS the cheapest way to turn a red row green. Soft rules inherit too (6 of this run's 14), so the split still earns its place.

Also recorded conventionally, because a printed line is not a plan: a W6 row and a W7 row in the W4 result's follow-ups, and the receipt section of design-flow-base stating that hard rules are gate predicates and never receipt rows.

One thing genuinely lost: the receipt no longer demonstrates the two substrate contradictions, it asserts them via findings. The demonstration comes back stronger when W7's predicate goes red on the composed sheet — that is a machine proving it, not a run claiming it.
