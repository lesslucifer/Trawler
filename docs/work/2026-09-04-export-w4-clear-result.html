How removal is shaped, and the one thing that decided it

Two things leave a flow behind: the map entry and its weight, and the row in the order. The first is shared — Ring::debit is the one place a flow is removed from the map and its retained bytes subtracted, called from evict's pop-front loop and from unlink, so the arithmetic exists once. The second is not, deliberately: eviction already holds the row it popped, while a removal has to find it — a single delete finds its one row, and a batch rebuilds the order, where that cost is proportionate to a scan the filter already did. The first shape this WU shipped had unlink claiming to unify both halves while evict quietly kept its own copy; the review caught it, and the review section records what changed and why the obvious fix was the wrong one. remove_matching and remove are the two public doors, and the plan's five decisions all landed as written: one store method for the filtered case, an id addressed directly rather than through a FlowFilter that has no id field, one batch event, a variant distinct from FlowEvicted, and the same { "removed": n } envelope from both routes.

The guardrail worth restating because it is the one asymmetry with eviction: removal has no last-row floor. evict keeps a single oversized flow alive so it stays inspectable; a clear that left a row behind would not be a clear, and a_default_filter_clears_everything_with_no_last_row_floor asserts exactly that against a store the cap has already reduced to one row.

The review round

Five finders over the WU diff produced nine candidates; adversarial verification confirmed four and refuted five. The refutations mattered as much as the confirmations — two finders agreed on a fix that the verifier showed would be a regression, and the altitude finder returned a clean verdict resting on a premise the other finders had already disproved, which is why a finder's conclusion is not evidence until something tries to break it.

FindingVerdictWhat shipped
evict never called unlink, so the byte arithmetic still existed twice — while unlink's comment claimed "one helper either way" and this WU's own test/v2 note claimed unlink "is the only place a flow leaves the ring". real · nit The claim was false and had been written three times — in the plan's reasoning, in a doc comment, and in the note that serves as gate evidence. Ring::debit is now the single place a flow leaves the map and its bytes are subtracted, called from both evict's loop and unlink. The verifier refuted the fix both finders implied — routing evict through unlink would make every insert O(ring) and drop the last-row floor — so only the two-line arithmetic is shared and each keeps its own order-mending.
unlink's order.retain rebuilt the whole order for a single-id delete: a scan plus a hash probe per row, under the lock the live capture path contends on. real · important The severity rests on a fact worth stating plainly: retained_bytes() counts only body bytes, and eviction fires only on the byte cap — so a capture of body-less exchanges (GETs, 204s) grows the row count without limit while total_bytes stays near zero. A single removal now finds its one row; a batch still rebuilds, where the cost is proportionate to a scan the filter already did.
A cursor row can now vanish by deletion as well as eviction, and neither the listing contract nor UC-7 said so. real · nit The listing contract said "a cursor the ring has evicted"; it now says "no longer holds", naming both causes, and UC-7 gained the consequence that a delete can end another client's paging walk. A regression test pairs a cursor with a delete — no test had.
Two reborrows in unlink and remove_matching were dead scaffolding from a borrow error already solved another way. real · nit Both verified by compiling them away, then removed with the rewrite.
removed.clone() is an avoidable copy · the delete() test helper duplicates post() · three further candidates. refuted The clone's return value is consumed by tests that assert on the ids, not just the count; and one helper per verb is the file's established convention (get()/json() already pair that way), where a method-parameterised helper would cost call-site clarity.

Both behaviours the fix introduced were pinned before being trusted: a middle row removed by the single-id path, and an id named twice debited once. Each was mutation-tested against deliberately broken code and observed to fail, so neither passes vacuously.
