How removal is shaped, and the one thing that decided it

evict pops from the front of the order and subtracts as it pops; a filtered removal takes rows from the middle. Rather than a second copy of the byte arithmetic — the way total_bytes drifts from what the ring holds — both go through one private Ring::unlink that removes from the map, subtracts what was actually held, and rebuilds the order by retaining survivors. remove_matching and remove are the two public doors onto it, and the plan's five decisions all landed as written: one store method for the filtered case, an id addressed directly rather than through a FlowFilter that has no id field, one batch event, a variant distinct from FlowEvicted, and the same { "removed": n } envelope from both routes.

The guardrail worth restating because it is the one asymmetry with eviction: removal has no last-row floor. evict keeps a single oversized flow alive so it stays inspectable; a clear that left a row behind would not be a clear, and a_default_filter_clears_everything_with_no_last_row_floor asserts exactly that against a store the cap has already reduced to one row.
