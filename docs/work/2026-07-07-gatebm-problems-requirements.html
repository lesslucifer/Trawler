E-GATEBM — the DoD gate's back-merge blind spot

The epic gate's seam walk only recognises a back-merge in one direction; a stale epic branch that back-merges an up-to-date main is falsely flagged as merging an ungated WU seam.

Draft v1 · 2026-07-07 · Trawler · T3 problems & requirements

TL;DR

Fix target: xtask/src/gate.rs, the three-parent arm of Gate::walk (the epic-gate seam walk, ~line 285).

The back-merge skip at line 289 asks only “is the merged-in tip already an ancestor of the mainline?”. That catches an epic re-merging its own landed history, but not the reverse: an out-of-date epic branch merging a newer main into itself. In that case the merged-in tip is main's tip, which is not an ancestor of the epic mainline, so the walk treats it as an ungated Working-Unit seam and demands test/v2/cr/v2/doc/v1 notes on main's merge commit — notes that legitimately never exist there.

How it surfaced

Task: merge epic epic/notes-view (Working Units E-NV.W2 + E-NV.W3) into main. The branch had diverged: main already merged epic E-NV's W1 and a later epic (E-MAINLOCK) on top, while epic/notes-view branched off the earlier E-NV distillation commit and carried W2/W3.

Two independent problems chained together — only the first is E-GATEBM's scope; the second is context that forced the merge direction.

context

Tooling/binary mismatch on the stale branch

cargo-husky installed the newer commit-msg hook (from E-MAINLOCK-era code), which runs cargo xtask verify-dod commit-msg. The epic branch's xtask predates that subcommand, so every commit on the branch dies on the _ => Err(USAGE) arm with exit 1. Resolution: the epic branch must back-merge main to get coherent tooling (commit-msg support, .mr-allowed). This is expected and correct — it is why a back-merge is unavoidable, and it is what exposes E-GATEBM.

E-GATEBM

The gate false-positive on the back-merge

Once main is back-merged into the epic branch, the epic gate's walk (dry-run verify-dod epic HEAD --target main) reports:
7·walk·1·notes [working-unit <tip>] no test/v2 note on tip <main-tip> (and cr/v2, doc/v1). The gate mistakes main's already-gated epic-merge tip for an ungated WU seam.

Root cause

The walk iterates base..tip with rev-list --first-parent --parents. For a merge line [merge, mainline, wu_tip]:

flowchart TD
    A["merge line: [merge, mainline, wu_tip]"] --> B{"is wu_tip an ancestor
of mainline?"}
    B -->|yes| C["skip — back-merge of
landed history"]
    B -->|no| D["gate as a WU seam:
verify(Wu, wu_tip, mainline)"]
    D --> E["FALSE POSITIVE when wu_tip = main's tip
merged into a stale epic branch"]
gate.rs:285–292 — the skip is one-directional.

The current guard (verbatim):

[merge, mainline, wu_tip] => {
    // --first-parent ordering: parent one is the epic mainline, parent two the
    // merged-in WU tip. A wu_tip already reachable from the mainline is a
    // back-merge of landed history, not a WU seam - nothing new to gate.
    if git(self.repo, &["merge-base", "--is-ancestor", wu_tip, mainline]).is_ok() {
        continue;
    }
    (*merge, self.verify(Level::Wu, wu_tip, mainline)?)
}

The check only covers the case where the second parent (merged-in tip) is old news. It has no symmetric handling for the case where the first parent (mainline) is the stale side and the merged-in tip is a newer, already-gated integration branch.

What legitimately distinguishes a back-merge

Design question the fix must answer: how does the gate tell “I merged an already-gated integration branch (main) into my epic — nothing new to gate” apart from “I merged a real, ungated WU seam”? A too-loose rule would let genuinely ungated work slip through the epic gate. The requirement below frames candidate discriminators; the implementing WU must pick one and defend it in its plan.
Candidate discriminatorIdeaRisk
Symmetric ancestryAlso skip when mainline is an ancestor of wu_tip (the merged-in tip already contains the mainline — i.e. it's an integration/back-merge, not net-new work branched off the mainline).Must confirm this can't mask a real forward WU merge. A WU tip normally is not a descendant that contains the whole epic mainline, so this is likely safe — verify against the walk's invariants.
Target-ref identitySkip a merge whose second parent is the gate target (or an ancestor of it) — i.e. the thing merged in is main itself.Only covers merges of the target; misses back-merges of other already-gated branches. Narrow but explicit.
Receipt presence on the merged-in tip's historyTreat the second parent as gated if its own first-parent chain is already fully receipted.More expensive; risks re-deriving the whole gate recursively.

Requirements

R1

Recognise the back-merge in both directions

The epic-gate seam walk must NOT flag a merge as an ungated WU seam when the merge is a back-merge of already-gated history — regardless of which parent is the stale side. Concretely: back-merging an up-to-date main into a stale epic branch must walk clean.

R2

Preserve the genuine WU-seam gate

A real forward merge of an ungated WU tip into its epic must STILL be gated exactly as today. The fix must not widen the skip into a hole. This is the load-bearing constraint — R1 is worthless if it weakens R2.

R3

Regression test both arms

Add hermetic tests (feature-gated with the existing hook-test suites) covering: (a) back-merge of the target into a stale epic → walk clean; (b) forward merge of an ungated WU seam → still red. Both in the same test module as the existing walk/seam tests.

R4

Record the rationale

The chosen discriminator is a load-bearing gate decision — capture the why in the existing workflow-gates decision record (docs/decisions/workflow-gates.html), alongside the sibling back-merge-guard rationale already noted there. One fact, one tier.

Out of scope

  • Landing E-NV.W2/W3 on main. That is the original task, blocked on this fix. Once E-GATEBM lands, epic/notes-view can back-merge main and pass the epic gate. Sequence: E-GATEBM → back-merge main into epic/notes-view → epic gate → merge to main.
  • The tooling/binary mismatch (the commit-msg USAGE failure). It self-resolves the moment a branch is current with main; no code change owed.

Reproduction (for the implementing WU)

  1. From a branch that predates a later main merge, back-merge main: git merge main --no-ff --no-verify.
  2. Dry-run the epic gate: cargo xtask verify-dod epic HEAD --target main.
  3. Observe 7·walk·1·notes [working-unit …] no test/v2 note on tip <main-tip>. That line is the bug. After the fix it must be absent while the genuine-seam test stays red.
