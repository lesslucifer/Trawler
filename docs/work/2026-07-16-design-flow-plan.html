E-DFLOW — Design System & Harness

Epic plan. A repeatable, gated flow by which AI agents design app UI consistently and verifiably, wired into the dev workflow.

Epic plan · 2026-07-16 · Trawler · T3 (docs/work/) · epic/design-flow · direction: docs/work/design-flow-discussion.html

Intent

UI screens are starting to land (E-UI, E-UIINSPECT) and each new screen risks being designed ad-hoc, so the app drifts toward inconsistency — different components reinvented, rules applied unevenly. Raw instruction ("follow the design rules") does not hold: agents hallucinate and forget. This epic builds a design system + harness — a shared component vocabulary, an enumerable rulebook, a staged design flow, and a gate that mechanically proves every rule was considered — so that any UI an agent designs is consistent and verifiable, exactly as code quality already rests on clippy + tests + verify-dod rather than good intentions. It ships the method, not a redesign; a later epic uses it to actually design/ship UI.

Use-case requirements

Process epic — touches no app use-case. No UC-* contract is delivered or changed; the app's runtime behavior is unchanged. The flow-detail-panel design produced during this epic (W1/W4) is proof the flow works, not a shipped UI change. The truth this epic creates lives in T1 process docs + a T2 decision record, not in docs/use-cases/. A future UI epic that consumes this flow may then update web-ui.html.

Expected result

After the epic, a reader who wasn't here can observe all of:

  • A T1 design-flow process doc describing the staged flow (Frame → Layout → Elements → Interaction → Draft mockup → Tune) and its per-stage artifacts.
  • A component registry: a collection folder of components, each carrying a structured usage doc-comment, plus an index file an agent loads; a mechanical check fails when the index omits a collection file (unless waived).
  • A T1 rulebook doc of enumerable, stable-id'd rules, each tagged hard (Tier-1 checkable) or soft (Tier-3 judged).
  • A design harness that enforces three tiers (mechanical completeness + fixed rules + receipt-coverage · self-reflex receipt · adversarial review scoped to soft rules + new-component warrant) and emits a design receipt, red/green like the DoD gate.
  • The flow run once on the flow detail panel to a passing, receipted design spec (draft-mockup fidelity).
  • A flow e2e (fake user + fake agent) proving the harness/flow plumbing runs end-to-end without getting stuck or misleading — separate from app e2e, run-once + manual re-run.
  • The completed design flow connected to the dev workflow.

Non-goals

  • No Trawler UI re-design — a later epic uses this flow to design/ship UI.
  • No hi-fi visual design — draft mockup (lo-fi, structural, interactions defined) is the finish line.
  • No automated verification of design quality — the gate proves rules were considered (citation-backed verdict per rule), never that the design is good.
  • No building of real feature components — the registry is seeded only from what the guinea-pig screen needs.
  • The design→dev integration shape (mandatory vs optional gate, conformance back-check) is decided in W8, not pre-committed here.

E2E test plan

Flow e2e (built in W7). A scripted run that stubs both the human (fake taste feedback at each stage) and the designing AI agent, driving the full flow through all three harness tiers. Asserts the plumbing: the flow never stalls or emits a misleading/ambiguous prompt, every stage yields its required artifact, the receipt covers every rule id, and a deliberately rule-violating input is caught red while a compliant one passes green. It tests mechanics, not design quality. Like the workflow e2e, it is excluded from the app e2e suite — run once, re-run manually when the flow/harness changes.

Acceptance demonstration. The real hand/assisted run on the flow detail panel (W1 then W4, gated in W7) standing as the concrete end-to-end proof that the flow produces a passing, receipted draft-mockup spec. No waiver intended.

Open questions

  • W9 scope — default: a second-screen reuse proof; final scope realized when W9 is reached (user's call).
  • #4 integration shape — default: a passing design is a mandatory upstream gate for UI-touching WUs, with the dev gate later checking impl-vs-design; decided in W8 with evidence.
  • Harness runner location — default: a cargo xtask design-verify subcommand that shells to Node/TS checks (design lives in the ui/ toolchain), plus authoring-time harness hooks mirroring verify-doc; settled in W7.
  • Tier names — default: Foundation / Primitives / Widgets / Locals / Compositions (alts noted in the direction doc).
