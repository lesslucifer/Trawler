E-NV — workflow-notes viewer

Collapsed epic + WU plan: a local dev server that reads the git-notes workflow trail live and renders the epic → WU → commit story as one HTML page.

v1 · 2026-07-06 · Trawler · T3 · epic E-NV (one WU: E-NV.W1)

Intent

The workflow leaves its whole evidence trail in git notes — four refs, one YAML note per commit each: test (level + per-layer counts/coverage), doc (tier changes + distillation), cr (code-review verdict + diff binding), dod (the green receipt). Together they narrate every Working Unit: tested → reviewed → docs distilled → gate passed. Today the only way to read that story is git notes --ref=<r> show <sha>, one commit and one ref at a time — there is no way to see a WU's four-note story side by side, or scan an epic's WUs in one view. This epic gives devs a readable window onto the trail: a small local debug server (cargo xtask debug serve) that reads the notes live on every request and renders the epic → WU → commit tree with each commit's four notes laid out in full. The notes stay the single source of truth; the page is a disposable live render, nothing committed, nothing to go stale. The command is deliberately a debug group, not a notes-only name — the workflow-notes view is its first surface, and later debug features (other repo/workflow state a dev wants to eyeball) attach as further debug subcommands or page sections without a rename.

Why xtask and not the product API: this is dev-workflow tooling, not a Trawler runtime surface. It reads git notes, which only exist in a dev's working clone; it must not ship in the :3001 control API the product exposes. xtask already owns every other notes-reading command (dod list, the gate), so the parsing, the git plumbing, and the deps all live here already.

Use-case requirements

No product UC-* record — this is internal tooling, not a capture/inspect contract, so it seeds no docs/use-cases/ doc. The requirement is a developer workflow one:

  • Read a WU's full story at a glance — a dev running the viewer sees, for any commit in the workflow, all four notes (test, doc, cr, dod) rendered together, grouped under their WU and epic, in the order the workflow produces them.
  • Always current, never committed — the page reflects the notes as they are in the repo at request time; making a new note and reloading shows it, with no regeneration step and no artifact checked into git.

Expected result

Observable after the epic:

  • cargo xtask debug serve prints a localhost URL (default http://127.0.0.1:3002) and serves until Ctrl-C.
  • Opening that URL shows every commit that carries any workflow note, grouped epic → WU → commit, newest epic first; each commit shows its four notes' bodies (or a clear "— none —" for a ref with no note on that commit).
  • Commits with no epic/wu field (standalone commit-level notes) group under an "ungrouped" bucket rather than being dropped.
  • Adding a note to a commit and reloading the page shows it — no rebuild, no stale file.
  • Running it in a clone with no notes shows an empty-state page, not a crash.

Non-goals

  • Editing, adding, or deleting notes from the page — read-only view.
  • Live push / SSE / auto-refresh — reload is the refresh (server renders full HTML per the delivery decision).
  • Any JS framework or build step — server-rendered HTML only.
  • Exposing notes on the product control API (:3001) or shipping in the product binary.
  • Authentication, remote access, multi-user — localhost dev tool.
  • Diffing notes across time, or gate re-evaluation — that is the gate's job (verify-dod), not the viewer's.

Open questions

  • HTTP listener — stdlib vs crate? Leaning std::net::TcpListener with a hand-written single-route handler: one GET, one page, localhost, one user — a framework is over-build. Risk is parsing the request line / writing the response by hand; if it turns fiddly, fall back to tiny_http (single small dep, blocking, no async runtime). Decide at implementation, record the pick in the result. ponytail: stdlib first; crate only if the raw socket handling earns its keep.
  • Commit ordering within a WU? Default to git's own order (git log topological / date) for the commits in a group; the workflow's note order (test → cr → doc → dod) is fixed per commit. Confirm the group sort (newest epic first) reads right once there's real data on the page.
  • Epics with no epic field on old notes? Some early notes may predate consistent epic/wu fields — the ungrouped bucket covers them; verify against the real 22/21/14/10 notes currently in the repo when rendering.
