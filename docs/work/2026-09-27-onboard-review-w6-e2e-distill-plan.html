Requirement

ui/e2e/specs/onboarding.spec.ts drives three journeys through the real window against the ephemeral core. First, a core holding only a sent https row launches into setup, and the try task reads "waiting for the first request". Second, "set up another device" after proving this machine keeps the dot connected, answers no device, and shows no success line until a new captured request, then one after it. Third, re-entry with the list filtered to nothing reads the new captured request as capturing. The walkthrough is re-run at this tip for the after. UC-ONBOARD states every changed contract in the epic plan's use-case table, and the core's API table lists the three certificate routes.

The journeys, in one window

flowchart TD
  S["launcher: core up, then POST /flows sends one https request → a sent row"] --> L["the window launches"]
  L --> J1["J1 · setup shows, try task waiting, no row"]
  J1 --> OFF["existing: another platform's unmet reach, back to this machine"]
  OFF --> P["existing payoff: /hit → the list, the banner, the sent row beside the captured one"]
  P --> J2["J2 · set up another device → dot connected, no task, no success line"]
  J2 --> J2b["choose Android emulator → task 1's guide open, try waiting"]
  J2b --> J2c["/hit → capturing, success line"]
  J2c --> J3["J3 · back, filter to nothing, click the dot → try waiting"]
  J3 --> J3b["/hit → capturing, success line"]
  J3b --> E["back → the filtered list is empty; cleared → rows; existing append"]
The suite has one core and one window, and capture being proven latches, so the journeys are ordered on it. J1's sent row is seeded before the window launches, because the launch read is what J1 is about. Each journey reads the other journeys' state only where the epic's contract speaks to it (J2 needs capture proven, J3 needs a way back into setup).
