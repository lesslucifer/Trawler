E-QUERY — plan: one bar to filter, search and command

Four separate filter controls and a scatter of menus become one typed query bar. It understands filters such as status:4xx host:api, and with a > prefix it runs commands.

v1 · 2026-11-04 · Trawler · T3 epic plan · E-QUERY · branch epic/query-bar · worktree ../Trawler-query-bar

Intent

Narrowing the list means learning four controls with four different rules: a free-text field that searches only the URI, a host dropdown, a method dropdown, and a status field that takes 404 or 4xx. Two filters the core already has (content_type and source) are unreachable from the app. Actions are scattered across an icon button, a menu, the detail pane and the native menu. The owner wants one place to type: one query bar whose grammar is visible as you type, with completions that teach it. This epic reverses UC-4's ruling that “an exactly-matched filter is chosen rather than typed”, so it carries a new DEC.

Non-goals

  • Searching header values or body text, or filtering on duration or size. Each needs index and cost decisions of its own (Q2 records it as a roadmap row by default).
  • Saved queries, preset filters, tabs. These are the deferred tabs & presets epic, which builds on this grammar.
  • Filtering GET /stream; the UI keeps refetching on events.
  • Changing the legacy embedded web shell's four inputs (UC-3).
  • Removing the existing buttons or menu items that the commands mirror.

WU summaries

Core query grammar. A query module that parses a string into FlowFilter, with negation, OR within a key, quoting and is:. ?query= on GET /flows, /flows/export and DELETE /flows, with a 400 that names the token and its offset. host: matches host or host:port.

E2E test plan

Run against a real ephemeral core with seeded flows of mixed host (one with a port), method, status, type and source. Each step asserts the list:

  1. Type keyed, negated and OR queries.
  2. Type a misspelt key and assert the explanation.
  3. Use >export and assert the HAR holds exactly the listed flows.
  4. Use >clear through its confirmation and assert that only the queried flows went.
  5. Use ⌘K and then >settings, and assert the Settings window opens.

Hermetic: local upstreams only.

Distillation plan

  • docs/use-cases/web-ui.html: UC-4's filter-bar text, the listing contract (UC-3·UC-4), UC-6 and UC-7, plus their index rows.
  • A new DEC that reverses UC-4's “chosen rather than typed” and records where the grammar lives and why.
  • docs/design-rules/: any rule the design run settles, such as the completion-popup conventions.
  • The roadmap: strike the absorbed items, and add rows for header and body search (Q2).

Open questions

Q1Should the grammar be parsed in the core (?query=) or translated to today's params in the client?In the core. Export, clear and API clients then share it, and negation and OR need the core anyway.
Q2Which new predicates belong in this epic?Negation, OR within a key, is:pending and is:https. Header, body, duration and size become a roadmap row.
Q3Which shortcuts should focus the bar: ⌘F, ⌘K, or both?Both. ⌘F opens filter mode and ⌘K opens it with > typed.
Q4Should the query survive a relaunch?Yes, through E-STICKY's store, restored visibly in the bar. If E-STICKY lands second, it adopts this.
Q5When should a query apply: on every keystroke (debounced, as today) or on Enter?Debounced as today. A parse error only marks the token and keeps the last valid result listed.
Q6Should commands sit in the same bar or in a separate palette?The same bar, with a > prefix, as the owner asked.
