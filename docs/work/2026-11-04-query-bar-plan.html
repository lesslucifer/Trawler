E-QUERY — plan: one bar to filter and search

Four separate filter controls become one query bar of filter chips. Typing status:4xx and accepting it adds a chip, and the list follows the chips.

v5 · 2026-11-04 · Trawler · T3 epic plan · E-QUERY · branch epic/query-bar · worktree ../Trawler-query-bar

Intent

Narrowing the list means learning four controls with four different rules: a free-text field that searches only the URI, a host dropdown, a method dropdown, and a status field that takes 404 or 4xx. Two filters the core already has (content_type and source) are unreachable from the app. The owner wants one place to type: one query bar where every filter is a chip, with suggestions that teach the grammar as you type. This epic reverses UC-4's ruling that “an exactly-matched filter is chosen rather than typed”, so it carries a new DEC.

Use-case requirements

Typing writes a draft, and suggestions follow it: the keys while a key is being typed, then that key's values (the hosts seen, methods, status classes, types, sources, is: states). Non-goals

  • A query grammar in the core (?query=). The core stays keyed parameters (Q1).
  • OR syntax within one key (method:GET,POST). Repeating the key covers it (Q2).
  • Searching header values or body text, or filtering on duration or size. Each needs index and cost decisions of its own and becomes a roadmap row.
  • Saved queries, preset filters, tabs. These are the deferred tabs & presets epic, which builds on these chips.
  • Filtering GET /stream; the UI keeps refetching on events.
  • Changing the legacy embedded web shell's four inputs (UC-3).
  • Actions in the bar (export, clear, settings, …). They stay in the existing menus and buttons (Q8).

WU summaries

Core: lists, negation and is. Through the shared FilterQuery, so GET /flows, /flows/export and DELETE /flows all take: a repeated q (all of), any other keyed parameter repeated (any of), each key's not_ form (none of), and is=pending|https. FlowFilter becomes include and exclude lists per key. Repeated keys need an extractor that reads them, because axum's Query (serde_urlencoded) refuses a duplicate key today. The host filter matches host or host:port.

none (can run beside W1)

Build the bar. A client parser that turns a draft into a chip, or into a reason naming what is wrong. The registry component is built from W2's design: chips, a draft whose suggestions update on each keystroke for keys and for values (hosts seen, methods, status classes, types, sources, is: states), accepted by a click, Tab or Enter and moved through with ↑/↓, removal by × or Backspace, and a core refusal mapped back to its chip. Suggestions are computed in the client and need no request. The bar replaces the four controls in App.tsx; useFlows sends the chips' parameters only when a chip is added or removed, and the chips persist through E-STICKY's store (Q4).

W3

E2E test plan

Run against a real ephemeral core with seeded flows of mixed host (one with a port), method, status, type and source. Each step asserts the chips and the list:

  1. Press ⌘F and assert the draft has focus. Build status:4xx and host:localhost:8080 from suggestions alone (type a prefix, Tab). Assert the list holds still while typing and narrows at each chip.
  2. Add keyed, negated and repeated-key chips, and two text chips.
  3. Type a misspelt key, press Enter, and assert there is no chip, the draft explains, and the list is unchanged.
  4. Remove a chip with Backspace and assert the list widens.
  5. Export from the capture menu and assert the HAR holds exactly the listed flows.
  6. Clear from the capture menu through its confirmation and assert that only the listed flows went and the chips stayed.

Hermetic: local upstreams only.

Open questions

#QuestionAnswer
Q1Should the grammar be parsed in the core (?query=) or translated to today's params in the client?Decided: in the client. The core gains what negation and lists need, but parses no query string.
Q2Which new predicates belong in this epic?Decided: negation, is:pending and is:https. No OR syntax; the same key repeated becomes a list. Header, body, duration and size become roadmap rows.
Q3Which shortcuts should focus the bar?Decided: ⌘F only.
Q4Should the query survive a relaunch?Decided: yes, through E-STICKY's store, restored visibly in the bar. If E-STICKY lands second, it adopts this.
Q5When should a query apply?Decided: when a chip is added or removed. Typing never refetches, so there is no keystroke debounce.
Q6Should commands sit in the same bar or in a separate palette?Decided: neither. Commands stay out of the bar (Q8).
Q7Should an accepted filter turn into a chip inside the bar, or stay highlighted text?Decided: a chip, text search included. A colon inside a value is never ambiguous, because the parser reads one draft at a time.
Q8How are commands reached in the bar?Decided: they are not. Actions stay in the menus and buttons, and the bar only filters and searches.
Q9What is the wire form of a negated key?Decided: not_host=, not_method=, … one per key, repeatable.
Q10Do several text chips match any of them or all of them?Decided: all of them, so each text chip narrows. Every other repeated key matches any of them.
