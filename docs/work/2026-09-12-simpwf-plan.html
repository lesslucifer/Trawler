E-SIMPWF — the workflow costs less to obey

Cut the two costs that dominate a unit of work — hand-authoring facts the tooling already knows, and re-running the whole review when nothing it judged changed — without lowering a bar the gate holds today.

Draft v5 · 2026-09-12 · Trawler · T3 · epic/simpwf → main · E-SIMPWF

Intent

Settle one rule — the code review judges code and nothing else, in what it decides, what it binds and what it reads — and make the workflow cheaper to obey at its two dominant costs: an agent hand-writing facts the tooling already knows, and a passing review becoming worthless because something later changed the tree. The same bar is held with fewer agent passes, on a review that is entirely about code.

Where the cost actually is

Every check in the project is either a program an agent runs or a generation an agent performs. The program half is cheap and measured: verify-dod is under 0.5% of an epic's wall-clock (DEC-11). The generation half is where the time goes, and it is spent in two shapes.

ShapeWhat it looks likeWhy it repeats
Authoring YAML notes carrying hashes, bases, branch names, tiers, changed-doc paths and per-layer counts — all of them already known to a tool that just ran. A hand-typed derived field is a red check, and a red check is a repair.
Re-running The review fleet — five finders plus a design finder, and one adversarial verifier per candidate finding. Its PASS is stamped with a fingerprint of the whole diff, so any later change — a nit, a failing test, a fix found after the review — voids it and buys the fleet again.

The expensive path is not the review. It is the review bought a second time because something else moved late.

The evidence is a real epic, not a model: E-RFINISH ran eight Working Units through 144 candidate findings and 47 verified, needed a second round on one WU, and its close took three review rounds. DEC-11 separately measured that landing a gate-heavy epic cost 45–106 minutes of active agent time, with the review fleet at a stable ~25% and main-loop generation at 32–56%.

A third cost is neither of those: the fleet's own size. Five finders plus a design finder, and one adversarial verifier per candidate finding, is a shape the skill states rather than a number anyone counted against what each finder returns — and a fixed shape that a new subsystem might justify is paid by every one-line fix. W6 counts it and cuts what the count does not justify; a cut that does not hold is dropped rather than argued for.

The rule this epic lands

The code review judges code, and only code. Documentation is not its business at any point — not as a subject, not in the binding that makes a PASS mean something, and not as an input. A doc is answered by verify-doc where it is written, and by the human sign-off at the merge.

In — the review's worldOut — answered elsewhere
Subject The code paths, the same set the workflow already names: src/, xtask/, tests/, ui/src/, ui/e2e/ Every file under docs/ — plans, result reports, design runs, decision records, use-cases, the rulebook
Binding A fingerprint recomputed over those code paths, so a PASS is void when the code moves A doc-only commit never moves it, and a diff that changes no code asks for no review at all
Inputs The code diff, the repository, and test/v2 — a claim about the tests that back this code, so an unjustified waiver stays a code finding The plan, the result, doc/v1, design runs and decisions — no finder reads them
Accountability The review's verdict, bound to the code it judged The doc predicate at authoring time, plus the human sign-off the merge already requires

The design dimension is separated too, not exempt. The ruling covers it: the code review's five dimensions are code-only, and the design dimension stops being one of them. Its judgment moves to its own step with its own carrier, so 9·design keeps working while nothing about design runs through the code review — no finder, no verdict, no binding. What that step finally looks like, and whether the design flow keeps its 17-row receipt, is the design epic's call, and it opens after this one.

Use-case requirements

This is a process epic: it changes how work is planned, evidenced and merged. It touches no product use-case, and no UC-* contract changes. The behavior it governs is the workflow itself, whose standard is workflow.html.

How this epic's Working Units are reviewed — owner's ruling, 2026-09-12. E-SIMPWF changes the review flow itself, so its WUs are not put through the code-review skill. Each WU tip still carries a cr/v3 note — the gate reads one, and the diff binding is what makes the evidence hang together — but the note records the findings of whatever review did run and waives them with a reason, because the review is the owner's own reading at the merge. What replaces it is the human sign-off (mr/v1), unchanged and never waivable: the owner reads the WU result and authorises the tip. This ruling is evidence-shape for this epic only; it changes no gate check and no rule outside it, and W4 — which removes the review's documentation scope — still stands as planned.

Open questions

None left open: plan review answered all five. They are recorded with their answers because each one is a decision a WU implements, and two of them changed the plan.

QuestionAnswer at plan reviewWhat it changed
Does the code-only rule silence the design dimension too, which judges design artifacts — docs by definition? Yes. The design dimension stops being a finder of the code review and is separated into a judged step of its own, so 9·design keeps a carrier. Simplifying the design flow itself stays the design epic's work.
Does the code-only review still read the test note? Yes — it may read it to understand the scenario more clearly. test/v2 stays an input. The plan, the result report and doc/v1 do not.
Is the measurement of W1 a note, or local? Local. W1 keeps its tally in a local file in the shape of Gate 0's cache, never a git note and never gate evidence.
Do the authoring-time doc checks need a harness-independent backstop? No — no doc format check at commit or merge level; the owner finds them useless. The W2 preflight drops the doc predicates and covers only what can void the PASS. The consequence is stated below rather than hidden.
Does the design epic open before or after this one closes? After. This epic's distillation writes its roadmap row; the two never judge each other's seams.

The consequence, stated rather than hidden. The doc predicates run only where the authoring hooks fire. On a harness that does not run them, nothing reads the document at all: the merge gate still holds that the docs a diff touched are listed in doc/v1 and that the human's signature names its result report, but no check opens the file. That is accepted here, on the owner's ruling that the commit- and merge-level doc checks are useless — this epic adds none.
