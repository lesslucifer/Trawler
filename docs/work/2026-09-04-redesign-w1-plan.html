Requirement

Design — not build — the three components the registry lacks and its own docstrings already redirect to: Field (the app's one text input), StatusDot (the tri-state capture indicator that doubles as the setup entry) and Disclosure (the collapse primitive Section defers to), each landing as one component design file under docs/work/components/ carrying the full nine-section contract and a complete TSDoc block — so that every element W3/W5/W7/W9 meets resolves to a registry entry or a genuine propose, and no screen run has to invent a primitive.

The three gaps — what each one is, and who is waiting

Field T1

blocks · App's filter bar (UC-4)

The app's one text input. Four of them sit in the header — free text, host, method, status — and today they are components.tsx:9, the legacy kit's only input.

Ships today, unregistered: it is a real precedent to cite, not a greenfield guess. The design decides what a registry Field owns that the legacy one does not — a label contract, the Select-shared box (DEC-18), and the states an input has that a bare <input> does not declare.

StatusDot T2

blocks · App's header (UC-4, UC-ONBOARD)

Capture health, and the always-available way back to setup. One element carrying two jobs — components.tsx:38 ships it as a bare tinted <button>.

Its broken/checking/connected semantics are its own and do not reduce to StatusTone — that is the claim the design must earn, and the one likely to force a rulebook line.

Disclosure T1

blocks · Onboarding's ManualPanel (UC-ONBOARD)

The collapse primitive. Onboarding.tsx:123 hand-rolls it as ManualPanel, and two more raw <details> sit beside it in the same file.

Section's @avoid already routes here by implication. The epic plan's open question — tier — is answered in this file: T1, slot-based, no business logic; the host owns what is inside and whether it starts open.

Two of the three already ship in the legacy kit. That is the WU's central constraint, not a shortcut: a design that merely transcribes components.tsx proves nothing, and a design that ignores it discards a shipped precedent the format requires be cited ("every spec traces to a driver or a shipped-code precedent — cite file:line"). Each file states what it keeps, what it changes, and why.

What could go wrong

RiskHandling
A design file reds because its component already exists. components·unretired fires on any file under docs/work/components/ whose name matches a roster entry — the registry and the design files are disjoint by construction (DEC-16). None of the three is in the roster today (24 entries, verified against node scripts/design-registry.mjs) — Field and StatusDot live in the legacy components.tsx, which the registry does not read. The check is a real hazard for W2, not here: the moment W2 lands the .tsx, these three files must retire in DEC-16's order. Recorded as a W2 obligation in each file's hero.
The design merely transcribes the legacy component, adding a file but no thinking — the failure mode a fluent-and-false contract takes. Each file's identity table carries an exists-today row naming the legacy file:line, and the forks section must show what was contested. A design whose forks are empty for a component that already ships is the reviewable defect; Tier-3's design dimension is pointed at it.
StatusDot's tri-state forces a rulebook entry — the epic plan predicts this ("Expected for StatusDot's tri-state, which is not a StatusTone"). Record it as a proposal in the file, not as a rulebook edit. The rulebook is frozen input for a run; the distillation checklist lands it after, per DEC-14. The epic's distillation plan already reserves the row.
A specimen needs a value the closed vocabulary has no token for (DEC-17). That is a config change, not a literal: "a value that has no utility needs a named token in the config, not a literal here". A token this WU cannot add without product code is a blocked-on entry handed to W2 — not a hex escape.
