Why 4 finders agreeing on one function was worth less, not more

Four of five finders independently flagged the same ~15 lines: catalog_rows and row_key still scan HTML by substring search, while ⓪ of this very WU replaced four such scanners with a tokeniser. The convergence looked like corroboration. It was correlation — every one reasoned from "hand-rolled scanning is fragile" without testing whether the tokeniser behaves differently.

Its verifier tested the counterfactual instead of asserting it, and ran the same input through both: nodes()/attrs() produced the identical spurious row. <pre>/<code> are ordinary parsed content in HTML5 — RAW_TEXT covers only <script>/<style> — so any conformant reader must treat an unescaped < there as a tag open. The project already names that case, via check_escaped_markup.

Two of the refutations are stronger still, because each found the consequence false rather than the mechanism. The >-in-attribute drop is real — a row does vanish — but markup·escaped reds any raw > inside a tag, runs first and unconditionally, and the only fix it accepts (escaping) disarms the drop. And elements_of, the helper two finders said to reuse, returns an element's body — while data-key rides the opening tag it strips.

The one waiver, stated plainly. The quadratic path is currently unreachable: every design-run doc in docs/ is draft or archived, both of which short-circuit to Exempt before check_hard_rules runs, and component-design docs never call check_colour_plus_text. Forced onto the largest real doc it adds ~100ms over a ~200ms floor already dominated by unconditional subprocess spawns. The fix — caching the parsed nodes per document — threads state through ~25 predicates, which is not a change to make at hand-over. Carried as follow-up 10.
