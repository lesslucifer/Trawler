E-EXPORT.W3 — a capture comes back, marked

POST /flows/import, the inverse of W2's projection, and the source field it forces onto the domain model — the first flow in the ring the proxy never saw.

v1 · 2026-09-04 · Trawler · T3 WU plan · E-EXPORT.W3 · epic plan · W2 plan · W2 result

Requirement

POST /flows/import accepts a HAR 1.2 document and inserts each of its entries into the ring as an ordinary flow marked source: "imported" — carrying the entry's method, URL, both HTTP versions, headers in order, status, its captured instant and duration, and each body restored to the BodyRec state the file states it was in — reporting how many entries it took, adding to the capture rather than replacing it. Malformed or hostile input is refused with a status and a reason, never a panic and never a partially-populated store. source is visible on every flow view and selectable via GET /flows?source=captured|imported.

Mapping

E-EXPORT · the epic plan's W3 summary block · UC-6, the import half ("a client can upload a HAR file to have its entries appear as flows in the listing… an imported flow is marked imported, is filterable by that mark, and is otherwise an ordinary flow") · the roadmap's "HAR import" line · DEC-35, whose stated consequence is that "the importer is defined against this projection rather than against the HAR spec independently, so the two cannot drift into a format Trawler writes but cannot read". Depends on W2: the projection this WU inverts, including the two places W2's result deviated from its plan — the parser reads that row, not the plan's. Independent of W1 and W4. W7 reuses this WU's source marking and refusal contract for its curl format.

The parser lives beside the projection it inverts, in src/api/har.rs, because DEC-35's consequence is that the two are defined against each other — a second module could drift, and the reason tokens W2 made public (not_captured_comment) exist precisely so the vocabulary has one spelling. The deserializable HAR types are separate from W2's Serialize types: what Trawler writes is a fixed shape, what it reads is a permissive one (unknown fields ignored, optional fields absent), and forcing one struct to do both would either make the export lax or the import strict.

The source field — why the domain model changes

Until this WU every flow in the ring came from the proxy, so nothing recorded that fact because nothing else could. An imported flow makes provenance a real distinction: a user looking at a listing that mixes a live capture with a colleague's file must be able to tell which is which, and must be able to select one set without the other.

WhereWhat lands
src/flow.rs FlowSource (Captured | Imported) and Flow.source. Flow::new keeps producing Captured — the capture path is untouched by construction, and the recorder never learns a new field exists. An importer sets the mark explicitly.
src/api/view.rs a source string on both FlowView and FlowSummary, spelled captured / imported — the same token the filter accepts, so a client that reads a row can filter for its kind without translating. An added field on both: the paging envelope and the bare array keep their shapes, so W1's contract and every existing client stay valid.
src/store.rs FlowFilter.source: Option<FlowSource>, matched exactly (not a substring — it is an enum, not free text) and composing with every other filter like any other field. The export inherits it for free: both endpoints build the same FlowFilter from the same FilterQuery, so /flows/export?source=imported works the day this lands, with no export change at all.
src/api/routes.rs FilterQuery.source, parsed into the enum. An unrecognised value is a 400 naming the parameter, on the same rule W1 set for a bad limit — never a silent empty listing, which reads to a caller exactly like "nothing matched".
Not a separate collection. An imported flow goes into the same ring, evicts by the same byte weight, is read by the same GET /flows/{id} and the same body endpoints, and appears on /stream like any other. A second store would double every read path in the API for a distinction one field expresses. Recorded as a decision (DEC-36 below), because it is the reason the ring's rules apply to a flow nobody captured.

The inversion — reading back what W2 wrote

Every row is the inverse of a row in W2's field mapping, read against W2's shipped code where its result recorded a correction. What HAR carries but Trawler's domain model has no home for is dropped, not smuggled: DEC-35 already states the round-trip's boundary in both directions, and a field invented on the way in would be as dishonest as one invented on the way out.

Restoring the body state — the inverse of the honest-body problem

W2's hard call was representing four BodyRec states in a format with vocabulary for one. The inverse call is reading that representation back without mistaking a foreign HAR's ordinary body for one of Trawler's marked ones. The reason tokens are a wire contract W2 made public for exactly this, and the parser reads them rather than re-spelling them.

What the file carriesRestored asWhy
text present, encoding: "base64" Captured { bytes: decoded, size } the bytes are exactly the bytes W2 wrote. Invalid base64 is refused rather than silently kept as literal text — the encoding field is a claim, and a false one means the file is broken
text present, no encoding Captured { bytes: text.as_bytes(), size } the UTF-8 branch of W2's encode_body. The size is the decoded byte length, never the file's size field — a size that disagrees with the bytes is the epic's expected result 7 ("a body claiming a size it does not have"), and the ring's byte accounting must weigh what it actually holds or eviction goes wrong
no text, comment ends (streaming) Streaming { content_type: mimeType } the token W2's not_captured_comment writes. The mimeType is where the content type lived on the way out
no text, comment ends (too_large) NotCaptured { TooLarge { actual: size } } W2 reports the known size for exactly this state, so it round-trips. A negative or absent size here degrades to ReadError rather than being refused — the state "we do not have the bytes" is still true, and it is the narrowest honest reading
no text, comment ends (read_error) NotCaptured { ReadError } neither bytes nor size, on both sides
no text, size: 0, no reason comment Empty W2's one state where "nothing" is the truth
no text, size > 0 or -1, no reason comment NotCaptured { ReadError } the foreign-HAR case, and the one place the parser must not guess. A browser writing a body it did not keep produces this, and calling it Empty would assert a 4 MB response was a 204 — the exact loss the domain model exists to prevent. ReadError is the honest "the bytes are not in this file", and the UI already renders it as an explicit notice
request leg: no postData, bodySize: 0 or absent Empty the asymmetry W2's result recorded: postData has no shape for an uncaptured body, so its absence plus bodySize is the whole signal. A GET with no body is the overwhelmingly common case and must not become ReadError
request leg: no postData, bodySize > 0 or -1 NotCaptured { ReadError } the file states a body existed and does not carry it — the same honest reading as the response side, and the exact inverse of what W2 writes for a skipped request body
The round-trip is a property, not an example. The requirement is that any flow the ring can hold, exported and re-imported, compares equal on every field DEC-35 says the format preserves. That is an all-inputs claim, so it is a proptest over generated flows — not three hand-picked ones — and its failure output is a shrunk flow that names the field that lost data.

The refusal contract

Import is the first endpoint in Trawler that takes untrusted structured input from a client. Every refusal is a 400 with a JSON { "error": "" } — the shape W1's paging refusals already use — and the store is never touched, because the parse completes before Store::import is called at all.

InputAnswer
not JSON400 · the deserializer's reason, prefixed so a caller knows it was the document and not the request
JSON but no log, or no log.entries400 · naming the missing member
log.version not "1.2"400 · naming the version it found
an entry with no request, or an empty method/url400 · naming the entry index, so a caller with a 900-entry file can find it
an unparseable startedDateTime, a status outside 100–599, invalid base64 in a body400 · naming the entry index and the field
a body whose size disagrees with its textaccepted, and the bytes win — see the body table. Refusing here would reject files real tools emit, and the ring must weigh what it holds
log.entries: []200 { "imported": 0 } — a valid document that says nothing was captured, which is not an error (the same reading the export's empty document has)
a body larger than the ring's capaccepted, then evicted by the ring's own rule — import respects the ring, it does not bypass it. Nothing special is needed for this and nothing special is added

Never a panic is asserted as a property: arbitrary bytes fed to the parser return Ok or Err, never unwind. That covers the fuzz-shaped half of the epic's expected result 7 that no list of named malformations can.

The CORS grant widens here, not in W4. The epic plan scheduled the widening with W4's DELETE because it assumed W4 would land the first mutating method. W3 does. The grant becomes GET, POST, OPTIONS now and W4 adds DELETE to the same list — a deviation from the plan's placement, not its reasoning, and recorded as such in this WU's result. Without it the native app's webview cannot POST at all (its origin is not the API's), so W6's import control would be dead on arrival. DEC-12's reasoning is extended, not reversed: the surface is loopback-only, and everything it now accepts is equally reachable with curl.

What the store gains

One method: Store::import(flows: Vec<Flow>). It exists rather than the handler calling insert in a loop, for two reasons the loop cannot give:

  • One lock for the whole batch. A 900-entry import taking and releasing the ring lock 900 times lets a live capture interleave into the middle of an imported capture, so the ring's order no longer reflects the file's. One lock makes the batch a contiguous slice, which is what the round-trip's order observable needs.
  • Eviction is settled once. Inserting in a loop can evict rows the same batch just inserted while later rows are still coming; the batch inserts, then evicts, then announces — the same three-phase shape insert already has, just once.

It announces each flow on the bus as RequestCaptured (+ ResponseCaptured where the entry had one), reusing the existing events: a live subscriber's job is "a flow appeared and here it is", which is true of an import, and a new event variant would force every subscriber to learn a second way to hear the same fact. W4's clear is where a genuinely new variant is warranted, because removal is a fact no existing event carries.

Calls this plan makes, so the build does not have to invent them

QuestionCall
One module for both directions, or a separate import.rs? One — src/api/har.rs. DEC-35's stated consequence is that the parser is defined against the projection; separating them is exactly how the two drift into a format Trawler writes but cannot read. The deserializable types are separate types in that module, because reading must be permissive where writing is fixed
Does the import content type have to be application/json? No. The body is read as bytes and parsed; the content type is not checked, because browsers and curl -d @file send several and a HAR file is identified by its content, not its label. The one thing that decides acceptance is whether it parses as a HAR 1.2 document
Is a partial import ever served — n of m entries, with the rest reported as errors? No — all or nothing. The requirement is "never a partially-populated store", and a caller who cannot tell which of 900 entries landed cannot recover. One bad entry refuses the document, naming the index so the file can be fixed
Does the response echo the imported flows? No — just the count. A caller that wants them calls GET /flows?source=imported, which already exists after this WU; echoing a 900-entry document back doubles the response size for data the client just sent
Where does the route sit, given /flows/{id}? /flows/import as a static segment, registered like /flows/export, and it is a POST so it cannot collide with the GET on /flows/{id} at all. The router test covers it anyway, on the same reasoning W2 used: routing precedence regresses silently
Does source belong on the summary row, or only the detail view? Both. A user scanning a mixed listing needs the mark in the row (the epic's expected result 6 puts it there), and a client that filters on a field it cannot see in the results it gets back has to re-fetch to confirm
Is the request body size limit changed? Yes — to the ring's max_bytes, on the import route only. axum's 2 MB default would reject files far smaller than the store's 256 MB capacity, which is a limit no part of the contract implies. The ring's own cap is the honest ceiling and it is already the export's
