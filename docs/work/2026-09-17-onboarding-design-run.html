Set up capture

Trawler sits between a device and the internet. To show a device's HTTPS traffic, that device has to trust Trawler's certificate and send its traffic to Trawler.

which device's traffic do you want to see

overflow: lead, platform, probe, done, blocked and back cannot overflow; steps grows with the platform and the column scrolls whole — no inner scroller.

Payload is mono and copies whole: a command such as xcrun simctl keychain booted add-root-cert trawler-ca.pem, the certificate URL http://192.168.1.24:7421/ca.mobileconfig (on a phone, with a code under it that encodes exactly that URL), the server 192.168.1.24 and port 7420, and a failed command's own text under details.

Done = the certificate reads trusted, the proxy reads ours — or, where the probe cannot answer, This machine's own request came through decrypted this session (round 12). Anything else, "can't check" included, is not done. A re-check in flight changes the state line, never the layout; a quiet re-read changes neither until its answer does.

Evidence is what this setup's traffic has shown, not what it shows this second, so a task does not flip back when the clock's window closes. One decrypted request outranks any refusal. On the Simulator and the emulator the screen infers the device from the platform chosen, so a request from this Mac would also count — the blocked-on attribution row stays open. This machine's own request carries a mark (?trawler-check=…, visible in the list) and its tasks read nothing else (round 12). Another device's carries one too, opened there, and its tasks read unmarked traffic only from after its address was allowed and while this Mac's proxy does not point here (round 13). The matrix test renders every host × platform × reach × probe pair × traffic history × own request × marked request and judges each against this table.
