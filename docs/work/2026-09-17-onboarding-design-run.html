Design run — the onboarding screen

A run of the simplified design flow on the screen that gets a user from a fresh install to a first decrypted flow. Its purpose is two-fold: a real design of the screen, and the first end-to-end exercise of the flow as DEC-53 cut it — six items, one human gate, a three-step close.

Parked, then resumed. Round 1 ran under E-SIMPDF and committed this run open (data-status="draft", bfdc345) on purpose: its own top blocked-on row was that Trawler binds 127.0.0.1 only, so five of the eight platforms it offers had nothing to point at and the design could not honestly close. E-ONBOARD.W1 built that bind and its address. Round 2 resumes the run here, amends it against what W1 actually shipped, and closes it as this epic's design of record — same document, same id, one continuous record.

Read again, by a user. The screen round 2 closed was built (E-ONBOARD.W3) and then run the way a first-time user runs it — 29 scenarios against the real core, written up here. It came back truthful, complete, and unreadable: a user could not answer what do I do now? from it. This run had been reviewed as a design and never read as an end user reads it, so round 4 adds exactly that reading, decides the three of its own rules the reading re-opened, and closes the run again for W5 to build.

Read again, at the window. W5 built round 4's screen and the owner read it running, at 1440×800. Three things the reading round had not looked at came back: the column is a dialog's width in a window two and a half times wider, eight tiles are a wall where the question needs one control, and a task's instructions are longer on the screen than the job they describe. Round 5 answers those three and nothing else — no sentence about what is true changes, and the truth model is untouched. It reverses round 4's own tiles call, which is the second time this run has reversed itself on the reviewer's word and the first time on evidence from the built screen at its real size.

Read again, at the rhythm. Round 5's column shipped and the owner read it with the window given to it: now it's full window, please add some gap. What the width exposed was a rhythm rather than a width. A task separates its title, its reason and its state by 8px, and 16px was all that separated one task from the next — at a dialog's width the eye had the column edge to group by, and at the window's it had nothing, so three tasks read as one list of nine lines. Round 6 gives the rhythm to the column and takes it off the zones. It changes no sentence, no state, no control and no route.

Given — what the screen is handed

Not given (may not be assumed to exist): any attribution of observed traffic to a platform or a device · a network-reachability check — nothing tells the screen a device actually arrived at the address, only that Trawler is listening there · any memory of a reach the user armed, which dies with the process and is re-armed per launch (DEC-55) · any observable completion of a step performed on another device · any persistence of the selected platform, so a relaunch returns to this machine · a notification channel outside the window.

What round 4 changed here. Round 1 wrote any observable per-step completion into this line and built the no-stepper ban on it. It was too wide: the two probes observe this machine's two steps and the traffic layer observes the third, and the screen has read all three since round 1 — as verdicts, under a rule that forbade numbering them. What is genuinely absent is narrower and now says so: nothing observes a step taken on a phone, an emulator or another machine, which is why those tasks are worded as promises to confirm rather than as states.

What round 2 changed here. Round 1's not-given line opened with a network address a device could reach Trawler at (it binds to 127.0.0.1 only). That is no longer true, so it leaves this line and arrives below as five given rows. What replaced it is narrower and still absent: Trawler now says where it is listening, and still never says whether anyone came.

Draft mockup

Every composed element is mounted from the collection — window.Trawler, the real ui/src/components/ — so what renders below is the shipped component, not a drawing of one. Screen-owned: the zoning, the column, the task list's assembly, the tiles. Stubbed: the clipboard write's host permissions and the elevated commands themselves; every control is otherwise live. The buttons under the mockup pick the platform and flip the lifecycle states; they compose, but each is meant to be read alone.

What round 4 rebuilt, and why. The screen this mockup designed was built, shipped and then read by a first-time user, who could not answer what do I do now? from it. Three of this run's own decisions were the cause, and round 4 reverses two and splits one: the screen leads with what this is and not with a status sentence; the platform axis is seen as tiles rather than discovered in a dropdown; and the preconditions become numbered tasks. The no-stepper ban keeps the half that was right — no step ever reports itself done — and loses the half that was not: a number is a reading aid, and every state below is read from a probe or from the traffic layer, never from what the user clicked.

overflow: lead, platform, probe, done and back are bounded by their content — two sentences, one question and the control that answers it, one chrome row, one outcome and one button. The picker's own popup caps itself at ~7 rows and scrolls inside, which is Select's contract and not this screen's; it overlays and never lengthens the column. steps is the one unbounded zone: a task's body holds a StepList that grows with the platform it renders, and neither StepList nor Disclosure may cap or scroll its own content. Its cap is therefore the page — the column scrolls whole, the window owns it, and no zone here holds an inner scroller.

The column is the window's, not a dialog's. It takes 60% of the window up to a ceiling of 880px — max-w-reading — so it grows with the window instead of sitting at a dialog's width inside it, and stops where a line of prose stops being comfortable to read. The ceiling is also where the longest trust command still renders on one line inside a task's indented body, which is the widest thing the screen ever has to show.

The column owns the rhythm, and owns all of it. A task separates its own parts — title, reason, state, body — by 8px. The column separates its zones by 24 and the task list adds 16 to the 16 a task already carries, so one task stands 32 from the next: four times the distance inside it, which is what makes three tasks read as three. The rule is the column's alone. A zone that brings a top padding of its own is a second spacing rule nothing reconciles with the first, and at a dialog's width that was invisible because the column edge did the grouping instead.

A number is a reading aid; a state is a reading. Every task carries its number and a state, and the state has exactly two possible sources: a probe of this machine, or the traffic layer. A task about a device nobody can probe says so in the words it will be confirmed by — we'll confirm this when your iPhone's first request arrives — and never renders a ✓ the user clicked into existence. A task whose precondition is not met yet is dimmed and still numbered, so the shape of the whole job is readable before any of it is done.

One guide is open, and it is the first unfinished one. A task's instructions sit behind a summary that counts them — 3 steps — and the first task whose work is not done has its own open. Everything above it is finished and everything below waits on it, so the reader meets one route at a time instead of every route at once. A count promises no automatic alternative, which is what set it up by hand did wrong (F10); where a button really is the first route, the summary is do it manually and starts closed. Nothing observes a task on another device, so off-machine the first guided task stays open until a decrypted request says the job is over.

A command is a block; a value stays in its sentence. A command is carried to a terminal whole, so it leaves the prose and takes a surface of its own with the copy control in its corner. A value — a server, a port, a certificate URL — is typed into the field the sentence beside it names, so it stays inside that sentence. What is neither is neither: a fact about the platform is a line under the steps rather than one of them, and a second way in sits behind other ways, because a numbered step the reader cannot perform and a route they need not take both read as work.

The address is an offer, not a menu. The core answers GET /reach best-first — the address this host would route from, IPv4 before IPv6, never a temporary IPv6 above a stable one — and names each device the way its owner does (Wi-Fi · 192.168.1.24). The task renders that first address as a line and the rest inside other addresses. Round 2's cardinality rule is retired with the control it governed: no segment group, and nothing that has to fit four 39-character labels across one column. Round 5's return to Select for the platform question does not revive it: this is one line of one address, and the picker above is a different question with a different control.

Payload, and what each one is. Every value the screen renders verbatim is mono, copyable whole and never truncated — the elevated commands xcrun simctl keychain booted add-root-cert trawler-ca.pem, the certificate route a device opens http://192.168.1.24:7421/ca.crt, and the two values a device's proxy settings want, 192.168.1.24 and 7420. The raw text of a failed elevated command is payload too and stays under details, unwrapped and unedited. Nothing else on this screen is wire data: every other line is chrome, and reads in the UI family. Round 5 moves where a command renders, never what it is: a CommandBlock carries the same data-wire="shell command" on the same mono text, wrapping at any character, with the copy control beside it instead of on it.
