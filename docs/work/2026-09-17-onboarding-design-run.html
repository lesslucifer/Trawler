Design run — the onboarding screen

A run of the simplified design flow on the screen that gets a user from a fresh install to a first decrypted flow. Its purpose is two-fold: a real design of the screen, and the first end-to-end exercise of the flow as DEC-53 cut it — six items, one human gate, a three-step close.

Parked, then resumed. Round 1 ran under E-SIMPDF and committed this run open (data-status="draft", bfdc345) on purpose: its own top blocked-on row was that Trawler binds 127.0.0.1 only, so five of the eight platforms it offers had nothing to point at and the design could not honestly close. E-ONBOARD.W1 built that bind and its address. Round 2 resumes the run here, amends it against what W1 actually shipped, and closes it as this epic's design of record — same document, same id, one continuous record.

Given — what the screen is handed

Not given (may not be assumed to exist): any attribution of observed traffic to a platform or a device · a network-reachability check — nothing tells the screen a device actually arrived at the address, only that Trawler is listening there · any memory of a reach the user armed, which dies with the process and is re-armed per launch (DEC-55) · any observable per-step completion · any persistence of the selected platform, so a relaunch returns to this machine · a notification channel outside the window.

What round 2 changed here. Round 1's not-given line opened with a network address a device could reach Trawler at (it binds to 127.0.0.1 only). That is no longer true, so it leaves this line and arrives below as five given rows. What replaced it is narrower and still absent: Trawler now says where it is listening, and still never says whether anyone came.

Draft mockup

Every composed element is mounted from the collection — window.Trawler, the real ui/src/components/ — so what renders below is the shipped component, not a drawing of one. Screen-owned: the zoning, the column, the guide captions. Stubbed: the clipboard write's host permissions and the elevated commands themselves; every control is otherwise live — the platform Select really opens and filters, CopyText really copies and confirms, Disclosure really discloses. The first two buttons under the mockup stand in for the platform Select (it is live, but a real selection cannot drive the mockup's CSS); reach armed flips the second axis — it only changes anything under iPhone or iPad, because it is the only platform whose instructions depend on it; the rest flip the lifecycle states. They compose, but each is meant to be read alone.

overflow: verdict, platform, probe, try and back are bounded by their content — one sentence, one control, one chrome row, a command plus the one-sentence outcome under it, and one button — and none of them scrolls; the platform Select's own popup is capped by the component (listing-max), not by this screen. preconditions is the one unbounded zone: its guide's StepList grows with the platform it renders, and neither StepList nor Disclosure may cap or scroll its own content. Its cap is therefore the page — the column scrolls whole, the window owns it, and no zone here holds an inner scroller.

The address control's shape is decided by a count the design cannot know. A host holds one address as often as it holds four, and no single control covers the range inside its contract. One rule, three renderings, and each one sits inside the entry it uses: one address — no control at all; the action names it (let devices reach Trawler at 192.168.1.24), because a choice of one is chrome pretending to be agency. Two to four — SegmentedControl, all addresses visible, which is what the mockup renders. Five or more — Select, whose @use names a target picker and whose @avoid excludes exactly the two-to-four case the segment group takes. Nothing is forced past an @avoid line, so this is reuse across the whole range and not a proposal — see the review item, where the fit was judged.
