Set up capture

Trawler sits between a device and the internet. To show a device's HTTPS traffic, that device has to trust Trawler's certificate and send its traffic to Trawler.

overflow: lead, platform, probe, done and back cannot overflow; steps grows with the platform and the column scrolls whole — no inner scroller.

Payload is mono and copies whole: a command such as xcrun simctl keychain booted add-root-cert trawler-ca.pem, the certificate URL http://192.168.1.24:7421/ca.crt, the server 192.168.1.24 and port 7420, and a failed command's own text under details.

Done = the certificate reads trusted, the proxy reads ours. Anything else, "can't check" included, is not done. A re-check in flight changes the state line, never the layout.

Where each task's reading comes from

TaskWhere a probe concludesEverywhere else — this setup's traffic
certificatethis machine: trusted · untrusted. Traffic never overrules ita request decrypted → done — a request decrypted · a tunnel past its grace and nothing decrypted → ⚠ not done — nothing decrypted · neither → we'll confirm this on …'s first HTTPS request
proxythis machine and the Simulator: the probe, always — its can't read stays a promise, since this machine's try-it command names the proxy itself and cannot prove the system oneany request reached Trawler → done — requests reached Trawler · none → we'll confirm this on …'s first request
try itthe traffic now, against a 30 s clock — unchanged

Evidence is what this setup's traffic has shown, not what it shows this second, so a task does not flip back when the clock's window closes. One decrypted request outranks any refusal. The screen infers the device from the platform chosen, so a request from this Mac would also count — the blocked-on attribution row stays open. The matrix test renders every host × platform × reach × probe pair × traffic history and judges each against this table.
