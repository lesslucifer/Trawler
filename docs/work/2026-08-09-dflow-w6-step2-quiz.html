Primer — the four words everything above assumed

Your comments all land on the same thing, and it is my omission, not a gap in you. Three questions were unreadable and three diagram nodes were undefined because the debrief used scale, token, prefix and project token as if they were settled words. They are Tailwind mechanics, and nothing in W6 explains them. This section does, against ui/tailwind.config.js as it stands after ① — real keys, real values, no abstractions.

The vocabulary, in one table

WordWhat it isReal example
scale A named group in the config that maps keys to CSS values. Tailwind has 119 of them: spacing, colors, fontSize, zIndex, borderRadius, opacity… fontSize — our nine type sizes
key (= token) One entry in a scale. The left side is the name, the right side is the CSS value. body: "12px" inside fontSize
project token A key we wrote, naming a decision rather than a magnitude. Opposed to Tailwind's stock keys (xs, lg, 5, 96), which name nothing. chrome-x = 8px · ink-mute · popup = z-index 20
prefix The front half of a utility class. Tailwind maps each prefix to a scale, then looks the rest up as a key. class = prefix + key. px- → spacing, so px-chrome-x → padding-inline: 8px
closed vocabulary The config replaces a scale instead of extending it. Keys we did not write no longer exist — the class resolves to nothing and emits no CSS. Silently, which is the whole problem. p-5, text-lg, w-96, z-20 — all dead since ①

"If we cancel the scaling classes, what do we write instead?"

Nothing was cancelled — it was renamed from a magnitude to a decision. p-5 means "1.25rem, because someone typed 5". px-chrome-x means "the horizontal padding of a control's chrome", and that it is 8px is a fact of the config, not of the component. "How do we know a scale governs this prefix?" — worked, on text-

The rule does not guess and does not carry a hand-written list. It asks the resolved config — resolveConfig hands back the merged theme as a plain object — and it asks about the prefix and the value together. Here is why together, on the one prefix that breaks everything:

ClassWhich scale could text- mean?Is the value a key there?Verdict
text-bodyfontSizebody ✓in scope · legal
text-ink-mutecolorsink-mute ✓in scope · legal
text-lgfontSizelg ✗ — deleted with Tailwind's scalein scope · RED
text-centerneither — it is text-align, which has no theme scale at alln/aout of scope · silent
text-[11px]fontSize, bypassedarbitrary value — Tailwind emits it regardless of the configin scope · RED, always
Read row 4 against row 1 and the requirement writes itself. Both classes start text-. One is governed by a scale, one is not governed by anything. A rule keyed on the prefix reds text-center — a class with no value in it to pick wrongly. That is binding requirement 1, and border-, outline- and font- are overloaded the same way. Out of scope means silent, never passing: the rule has no opinion on absolute, flex or truncate, because there is no scale to be off.

"Literals at className=" vs. where the classes really live

Q10 was unreadable without a concrete case. Here is the real one — ui/src/components/MethodLabel.tsx, unedited:

The file
line 1–7
a module-level lookup map		 const METHOD_COLOR = { GET: "text-method-get", POST: "text-method-post", PUT: …, DELETE: …, PATCH: … }
line 22
the className		 className={`inline-block min-w-[4.5ch] font-mono text-body ${METHOD_COLOR[verb] ?? "text-ink-body"} ${className}`}
A reader anchored at className= sees four classes here and none of them is the one that matters. It reads inline-block, min-w-[4.5ch], font-mono, text-body, then hits ${METHOD_COLOR[verb]} — an expression, not a string — and moves on. The five text-method-* classes sit twenty lines above, in a plain object.

They are the classes this entire WU exists to delete. ⓪'s scanner had exactly this blind spot and missed 41 classes across the tree. Ship the lint rule with the same blind spot and it goes green while MethodLabel renders five unstyled verbs — the rule would certify the headline change as done, having never seen it. Hence: read string literals in module-level constants and lookup maps too, not just at the attribute.

The 144/56 question, plainly

Q13 was asking one small thing in too many words. Of the ~224 classes written across ui/src/, how many are in scope for the rule (scale-bearing, like px-2) and how many are out (structural, like flex)? Three answers have been published — the plan guessed 103/77, ⓪ measured 144/56 with a scanner later proven unsound, and nobody has counted it soundly yet.

The answer to "what does ② do with it" is: nothing — it produces it. The number is whatever the finished rule reports once reconciled against the built CSS, and until then it stays out of DEC-17. The point being: a number nobody measured properly should not become a permanent decision record just because it has been repeated three times.

Gap ③ — how the rule decides what to judge your O2, and all four skips

You skipped Q9, Q10 and Q13, and O2 asks the same thing: "how do we handle which class to assert and which not, and how". That is one mechanism, and it is the core of ②ᵃ. It runs in four moves.

The rule's decision path. Step 2 is the answer to "which classes" — and it is a lookup in the config, not a hand-written allowlist.
MoveHowWhy it has to be this way
0 · find the strings Q10 Three sources, not one: className string literals · string literals inside the 29 computed className={…} expressions · string literals in module-level constants and lookup maps anywhere in the file. The third is the dominant idiom in src/components/ — const METHOD_COLOR = { GET: 'text-method-get', … } sits nowhere near a className=. ⓪'s scanner had exactly this blind spot and missed 41 classes, including all five text-method-*. A rule with the same blind spot reports the WU's headline change as already done, while MethodLabel is still broken.
1 · normalise Strip variants (12 sightings: hover:text-ink, disabled:opacity-40, focus-visible:outline-1, placeholder:text-ink-mute), then split slash opacity (4 sightings) into colour token + opacity step. Both are handled by normalising before lookup, never by excluding. Exclude them and you carve a hole in the check; normalise them and each half lands on its own scale. ① found the consequence: the opacity scale had to gain named steps (wash, hairline, scrim) or every slash-opacity class dies.
2 · in scope? Q9 · your O2 Ask the resolved config — resolveConfig exposes 119 theme scales — whether a scale governs the prefix + value pair. spacing, width, opacity, zIndex, borderWidth are all there; position, display, flexDirection are absent entirely. This is the direct answer to your O2, and it is mechanical, not a maintained allowlist — which is the whole reason it survives a year of edits. But the pair matters, not the prefix: text- alone spans three things — text-chrome (fontSize), text-ink (colour), text-center (alignment — no scale at all). Prefix-only matching reds text-center, which is precisely the false positive the scoping exists to prevent. border-, outline- and font- are overloaded the same way.
3 · judge In scope: is the value a project token? Green. An off-list magnitude, or an arbitrary […]? Red. A zero or a relationship keyword? Legal by the ⓪ ruling. Unresolvable at runtime? Reported, never silently skipped. Out of scope means silent, not passing — there is no value inside absolute for anyone to pick wrongly, so the rule has nothing to say about it. That distinction is what keeps ~56 structural classes from becoming 56 false positives, which would get the rule turned off in a week.
4 · prove the scope Q13 ESLint's RuleTester carries one valid case per false-positive family — a structural class, a variant-prefixed class, a slash-opacity class, a zero, a relationship keyword — plus one case per binding requirement. So a future edit cannot silently re-widen the scope. And the scale-bearing/structural split (103/77 wrong, 144/56 provisional) is whatever this rule computes once reconciled against the built CSS — an output, not an input. It does not reach DEC-17 before then.

Gap ④ — the two surfaces Q7 skipped · your O1

Your O1 said: both must be consistent, and the code side needs "a stricter check with lint". That is the one thing to unlearn. They are not the same check at two strictness settings. They ask different questions, at different times, and each is blind to what the other sees.

That is why Q7's answer is B: hard rules: 13/13 machine-checked (design). The surface label was added to the gate line for one reason — so the number is never read as a claim that the shipped UI is verified. It is not. Only the lint rule speaks for ui/src/.

Where your instinct was right: consistency is the reason the vocabulary is closed at all — one token list, one source of truth, config over rulebook. It is just not the reason there are two surfaces. Two surfaces exist because one artifact is a document and the other is code, and no single reader can open both.
