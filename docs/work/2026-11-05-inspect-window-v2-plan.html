E-INSPWIN2 — epic plan

The inspector keeps long values to one line and hands them whole to a data window; the data window reads what the bytes are, not what the label says, and gains JavaScript, CSS and a safe HTML preview.

v3, owner rulings recorded 2026-11-05: Q1 open all only, Q3 confirmed, every other question at its proposed default · v2, the find bar takes the query bar's UX (W8; e2e and distillation move to W9) · v1, open questions carry proposed defaults · opened 2026-11-05 · Trawler · T3 (docs/work/) · branch epic/inspect-window-v2 · WU branches wu/inspect-window-v2/<slug> · follows E-INSPWIN (DEC-76)

Intent

E-INSPWIN shipped the data window with one opener, the body. Everything else in the inspector still has to fit inline: a 4 KiB cookie or token clamps to three lines with more, and a long URI wraps across the flow line, so a few headers bury the panel. Now that a whole-value route exists, the inspector can show every header value and the URI on one line, cut with an ellipsis, and open the URI, or the leg's headers all together, in a data window. Separately, kind is decided by the served label today, so JSON served as text/plain renders as flat text and an HTML page has only XML tools. This epic makes the bytes decide the kind and treats the label as a hint, and adds JavaScript, CSS and HTML as kinds, with HTML gaining a preview that runs no script and makes no request. Last, the data window's find bar is a bare field, while the flow list's query bar already teaches typed chips, key suggestions and inline faults; find adopts the query bar's UX, so one way of typing a search holds across the app.

Expected result

#Observable after the epic
1A flow with a 4 KiB set-cookie and a 2 KiB URI: every header value and the URI sit on one line ending in an ellipsis; the panel never widens or scrolls sideways; no more / less remains.
2Clicking a cut value still copies the whole value.
3Open on the URI opens a data window titled by the opener holding the whole URI; open all on the Headers section opens one holding the leg's headers as Name: value lines in wire order, every value whole; reopening either focuses it. No header row carries an opener of its own.
4A JWT header value, in the open all window, decodes with the existing decoders from a right-click on it.
5JSON served as text/plain renders as a JSON tree in the pane, which states served as text/plain; the data window opens it as JSON and names its bytes as the source. HTML served as application/octet-stream opens as html. Text that merely starts with { stays text.
6A minified JS response opens as javascript: highlighted, find works, reformat expands it as one undoable step that marks modified; restore original returns the exact bytes. The same for CSS.
7An HTML response shows source and a preview toggle; the preview renders the working copy's markup and inline styles.
8A previewed page carrying a <script>, a remote <img>, a CSS url() and a meta refresh runs nothing, navigates nowhere, and a local beacon server receives zero requests.
9In a data window, find types like the flow list's filter: Space makes a chip, suggestions offer the kind's keys, Backspace removes the last chip, a bad re: or a near-miss key says why and makes no chip.
10With chips key:id and "user" on a JSON document, the count is the sum of both chips' matches and Enter steps through them in document order; switching the kind to text refuses the key: chip and drops its marks.
11The flow list's query bar behaves exactly as before (its existing tests unchanged and green).

Non-goals

Out of scopeWhy / where it goes
Running JavaScript, or a preview with scripts or remote resourcesCaptured content is untrusted; the window makes no request (DEC-76). A "load remote resources" switch is a later epic, if ever.
Guessing JS, CSS or form from bytesNo whole-parse test is cheap and reliable for them (Q6); the label or the picker names them.
A kind picker in the paneThe pane stays a glance; the window is where a kind is overridden.
Other kinds (YAML, CSV, protobuf, msgpack), source maps, deobfuscationFollow-ups.
Middle-ellipsis (keeping a value's tail visible)Q2: end ellipsis is pure CSS; a measured middle cut is a later refinement.
Truncation anywhere else (list rows keep DEC-34; body surfaces never truncate)The new escape binds only values with a named data-window route.
Writing edits back, any core change or endpointDEC-76 rule 6; pure front end.
A find that narrows (filter view, JSONPath, jq) or negatesDEC-76 keeps the filter deferred; the chips only mark.
Replace (find-and-replace)Follow-up; edits stay the surface's.

Questions — all decided

Ruled by the owner on 2026-11-05: Q1 and Q3 by comment; every other question at its proposed default, accepted as written.

#QuestionAnswer
Q1Which header openers?Open all only (owner): the leg's headers as Name: value text, every value whole. No opener per header value.
Q2Where does the cut fall?End ellipsis, pure CSS. Middle-ellipsis is a non-goal.
Q3Keep the three-line clamp with more / less?No, more / less is dropped (owner): one line; the data window is the way to the whole value.
Q4Does the pane also switch to bytes-first, or only the window?Both, through one detector; the pane states served as … whenever the bytes overrule the label.
Q5When do bytes beat a specific label (e.g. JSON served as text/html)?When the bytes do not read as the labelled kind and read whole as another. An image/* label is never overruled by text bytes; a binary body is hex whatever its label.
Q6Guess JS / CSS / form from bytes?No — label or picker only.
Q7CSS in scope, beside JS?Yes: the same formatter and a CodeMirror language, little extra.
Q8Which formatter?js-beautify (JS, CSS, HTML in one small dependency), lazily loaded; prettier's standalone build with its parsers is far heavier.
Q9Preview reach: its own record, or rule 12 on DEC-76?Its own record (DEC-next-c): it is the first surface that renders untrusted markup, and its threat table deserves one home.
Q10Preview: a toggle inside the html kind, or a second window?A source ⇄ preview toggle; the preview is read-only and follows the working copy.
Q11The URI opens as what?Its whole text, no hint (text); the URL-encoding decoder covers the query.
Q12Share QueryBar with find, or copy its look?Share: extract a grammar-agnostic chip box that both bars are made of, each with its own grammar .ts. A copy would drift; widening QueryBar past its @avoid would make one T2 own two grammars.
Q13Keep find's live draft and Enter-steps, which the query bar does not do?Yes. Marking is local and cheap, so waiting for a chip buys nothing; Enter stays next match, and Space / Tab make the chip.
Q14What do several find chips mean?A union: each chip marks its own matches, counted and stepped as one set in document order. No negation, since find marks rather than narrows.
Q15Suggest values for key: from the document?Yes, for JSON and form: the distinct keys present, as the query bar suggests hosts seen; capped to the first 200 by occurrence.
