Requirement

Every setup status reads a fixed state word beside its glyph, and each fact on the setup screen is said once. This machine's last task offers a button that makes one request to example.com. The list's ⋮ menu leads into setup. A phone's certificate URL carries a scannable code. Problems found, and your rulings

#Example of what happens todayFixProposed ruling
R1 · F5Your iPhone's tasks read "◐ we'll confirm this on your iPhone's first request", "✓ done — requests reached Trawler" and "○ waiting for the first request". To learn a task's state you must read the whole sentence, and each sentence is built differently. A screen reader skips the glyph, so it hears only the sentence.Each glyph gets one fixed state word, which StatusLine prints itself. The screen supplies only the reason after it: "◐ can't check here — your iPhone's first request confirms it". The words are proposed in the vocabulary. W3–W10 reuse them.take
R2 · F5◐ is both "can't be checked from here" and "arriving — plain HTTP only". ○ "not done — the system proxy is off" and ⚠ "not done — nothing decrypted" share the words "not done", although only the second is a failure.One glyph, one meaning. Plain HTTP only becomes ○ "not done — only plain http so far". ⚠ gets its own word, "not working".take
R3 · F19You click "Set up this Mac". Task 1 reads "⟳ setting up — approve the prompt…", task 2 reads the same, and the note under the button reads the same again: one sentence three times. "Set the system proxy" says it twice.Each fact is said once. The status lines state what is happening: "⟳ setting up". The note under the button says what you must do: "approve macOS's password prompt". A running note stays only where no status line changes. For example, "stop routing through Trawler" leaves its task reading "done" while it runs.take
R4 · F24You have set up this Mac and don't know curl. The last task asks you to "open any website". Your browser keeps its own proxy, so nothing arrives, and the screen gives you no other way to check.A third route in This machine's last task: a button, "make a request to example.com". It sends one https request through this Mac's system proxy, only when clicked (DEC-56). The task's status still comes only from what Trawler captured. If the request fails, the note says it did not complete, and the status lines say which step is left. The two manual routes stay.take, by Q1's route
R5 · F26You have 400 flows on screen and want to set up your phone. The only way is the 10px dot in the header, and nothing says it opens setup until you hover it.The ⋮ menu gains "set up another device". It behaves exactly like the success banner's link, per W1's table: setup opens, and the device question is empty if you last chose This machine.take
R6 · F28On your iPhone, step 2 says to open http://192.168.1.24:7421/ca.mobileconfig in Safari. You type it on the phone, one character is wrong, and it fails the same way an untrusted certificate would.A scannable code beside the certificate URL, for iPhone and Android device only. Scanning it opens the URL in the phone's browser. It is drawn locally from a vendored, zero-dependency encoder (DEC-57), and it is a new registry component with its own design. There is no code for the proxy host and port: a scan cannot fill in Wi-Fi settings, and an iPhone camera does nothing with plain text.take, scope by Q3
R7 · -60007You click "Set up this Mac" and see no prompt at all. The screen says "The password prompt was cancelled. Try again, or follow the manual steps." You cancelled nothing. This is the only case found where the screen says something false.-60007 gets its own note: "macOS couldn't show its approval prompt. The steps below do it by hand." The OS's own text stays under "details". A real cancel keeps its current note.take
R8 · -60007You enter your password, and the setup fails with -60007, yet sometimes the certificate works (your Q4 answer). The combined action runs security add-trusted-cert as root inside osascript's password prompt, which did show. The command then asks macOS for a second approval, to change trust settings, and a root process with no terminal has no way to show it. Its failure stops the proxy half too, because the two are joined by &&.The script stops judging trust by that command's exit code. It reads trust back with security verify-cert -p basic, and it goes on to set the proxy only when the certificate is really trusted. If trust holds, the action succeeds. If not, R7's note shows and the proxy stays untouched, as today.take (your Q4 answer)
R9 · latchno longer happens. The Simulator's "stop routing" is the shared route code, and W1's route memory clears on every read-back. The matrix's "every offered action, in every outcome" sweep checks that a reversal that succeeds hides the control and one that fails keeps it: 180 Simulator rows, green at 529113e.none. Close the roadmap row and cite the test.close
R10 · newOn a Mac, the certificate task reads "✓ done — installed and trusted" whenever a certificate named "Trawler Proxy CA" is in any keychain. It never checks trust. So a certificate that was added but not trusted, as in R8's failure, reads as done. security verify-cert -p basic tells the two apart: checked on this Mac, it passes for Trawler's trusted CA and fails with CSSMERR_TP_NOT_TRUSTED for a CA that is present but untrusted.The macOS probe reads trusted only when the installed copy verifies. It is the same check R8's script uses, so the probe and the action cannot disagree.take
