The screen a user watches traffic on: FlowList, the header/filter bar and the shell that holds them. One run, because they are one screen to a user and share its zoning.

1 · Frame

Purpose: a developer debugging their own client watches requests land in real time, and finds the one that went wrong. Given (functional input — received, not designed): live SSE flow stream · server-side filter on four keys · per-flow status, method, URI, start time, duration · the ring's capacity · a decrypted-HTTPS proof signal · connection count.

Not given (may not be assumed to exist): a request the proxy never saw · a flow the ring has dropped · why a request was made · pass/fail beyond the HTTP status · request ordering other than start time · any persisted selection or filter.

The one hard-rule collision — wrap-not-truncate vs. a fixed-height row

The ruleThe constraintVerdict
"Long values wrap — never truncate, never widen the column." Checked as: no truncate/ellipsis/nowrap on payload elements. Binds at Elements · Draft mockup. Rows are virtualized at a fixed 30px (Frame constraint rows are virtualized), and a path is unbounded. Wrapping requires variable row height; the two cannot both hold. violated, narrowly and on the record — truncate stays on host and path only.

What makes this narrow rather than convenient:

CellRule statusWhy
time · method · status · durationsatisfied, by the componentEach is a registry component that sets its own whitespace-nowrap (or min-w-verb) because its value has a known maximum width. Nothing is ever cut — the cell is sized to the widest possible value. The screen adds nothing.
host · pathviolatedUnbounded payload in a fixed-height row. Three ways out were considered and rejected: wrap breaks virtualization (and the Frame's watch it arrive goal — variable heights make arriving rows shift the read position); horizontal scroll on C pushes status and duration off-screen, inverting the top goal; a per-row expand is the detail pane (D) that already exists, one click away.

What the violation costs, and what pays it back: the full value is never lost — it is on the row's title, and D shows the whole URI on selection (progressive-disclosure: the scan level is clean, depth is one act away). The registry's own pattern is the precedent this follows: CopyText, TextRenderer and StepList all wrap because their surfaces have variable height; KeyValueRow's name cell and TimestampText both nowrap because they do not. A fixed-height log row is the second kind. Recorded as a finding for the rulebook, not fixed here: the rule reads as absolute and has no clause for a fixed-height virtualized row. Blocked-on carries it; the rulebook is frozen input for this run and grows at distillation (DEC-14).

The gap this stage found. Row selection has no keyboard path today — the row is a div with an onClick, unreachable by keyboard and unannounced to a screen reader. keyboard-parity binds per row, so the design names one: the row region is a single tab stop, ↑/↓ move the selection without wrapping (matching Select's option convention rather than inventing a second grammar), Enter or Space opens the pane. The rows carry aria-selected already; the region needs the listbox role and the tabindex that make it true. W4 builds this — it is the one interaction the current screen cannot perform at all.

6 · Tune

why — and which loop back to Layout
  • T1 — the Frame ranks find the failure first, and the shipped grid gives status 70px between a 180px host and a 1fr path. I tried widening it and it is wrong: StatusPill renders three characters, so extra width buys empty space, not weight. Weight here is tone — the only chromatic channel on the screen, against an otherwise neutral row — plus the right edge where the eye lands. The call is to change nothing and record why, because a reviewer comparing goal ranking to column width will otherwise read the narrow cell as a violation. Loops back to Layout: no.
  • T2 — a bare muted span made the count read as a label. As a TonedText at muted it reads as a value with a deliberately absent tone, which is what it is. No.
  • T3 — the real find of the run: one sentence served two causes, and the second one instructed the user to do something they had already done. Two sentences, and Field's @avoid had already said where the second belongs. No — same zone, same region, different content.
  • T4 — raised at review: the status codes looked adrift. Right-alignment was chosen so label and value share one edge, but the shared edge is also the duration column's, so a 3-digit code reads as that column's leading digit rather than as its own cell. Centring the values alone is worse — the label stays pinned right and the pair loses its edge entirely (checked in the browser, all three variants). Centring both restores one edge and detaches the column from its neighbour. Every status is three characters, so nothing ragged appears; the pending "…" centres under the codes. No.
  • T5 — surfaced by the Interaction stage's keyboard column, which is exactly what it is for. No — the zoning is unaffected; the row region gains a role and a tab stop.
  • No call loops back to Layout. The zoning survived Elements and Tune intact — the one thing that pressed on it, the unbounded path cell, was resolved inside zone C by the truncation verdict rather than by re-zoning.
