launch-guard — a slow-launch machine is named, not endured

Before Gate 0 pays for a suite run it proves the machine can run one: cargo-nextest present, and a freshly linked binary launching fast.

v1 · 2026-11-05 · Trawler · T3 WU plan · E-GATEPAR2.W3 · epic plan · push timing report

Requirement

When Gate 0 is about to run its checks (marker miss — in gate0, gate0 merge, gate0 push and the preflight), it first checks two prerequisites and refuses in seconds when either fails: cargo nextest --version must succeed (else the install line), and a freshly linked tiny binary must finish its first launch within 2 s (else the Developer Tools fix line). TRAWLER_ACCEPT_SLOW_LAUNCH=1 skips the launch probe. A fast verdict is cached per machine boot, so a fast machine pays the probe once; a slow verdict is never cached. The serial cargo test --all fallback is removed.

Cached per boot, not forever: the assessment backlog is machine state that can arrive later; a reboot re-measures. A slow verdict is not cached, so enabling Developer Tools takes effect on the next run with no cache to clear.
This machine has no cargo-nextest: once W3 lands, every suite-running gate here refuses until cargo install cargo-nextest --locked runs — that is the point of the WU.

Expected result

  • A marker miss without cargo-nextest exits non-zero naming cargo install cargo-nextest --locked; no fmt, clippy or test process runs.
  • A marker miss where the probe's first launch exceeds 2 s exits non-zero naming System Settings → Privacy & Security → Developer Tools and TRAWLER_ACCEPT_SLOW_LAUNCH=1; no check runs.
  • With the override set, no probe is linked and the checks run.
  • A fast probe stores the boot key; the next miss on the same boot links no probe.
  • A marker hit runs neither prerequisite.
  • The suite always runs through cargo nextest run --all.
