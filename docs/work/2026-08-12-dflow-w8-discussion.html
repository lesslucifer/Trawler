The forks

Six, in dependency order — plus D1a, which round 1 opened. chosen marks the ruling; the unmarked options are kept as the record of what was weighed against it. Summary table: where round 1 landed.

D1 · The unit of coupling — where the design sits relative to the build

OptionForAgainst
A · Design WU, then build WU, same epic chosen Tier-3 fires at the design WU's merge, so the gate is genuinely upstream — a FAIL costs a document, not built code. Docs-only design merges are now correctly gated rather than exempt (DEC-24), so a design-only WU is a fully evidenced unit, not a hole. The WU declares itself a design WU, and that declaration is what makes the design receipt mandatory on its merge two WUs per screen, two plans, two reports. A design can age between the two merges: if the rulebook moves in between, receipt·rulebook-stale re-opens the closed run's receipt — correct, and still rework
B · One WU, design commit first not a shape — an outcome, see D1a one plan, one report, one review pass; no aging window; the build's discoveries can amend the design inside the same unit, which is where they are cheapest to act on. It is also the shape the repo reached for unprompted: the one Working Unit that ever called itself a design WU — E-UISETUP.W1, "onboarding design + skeleton" — landed the design and 8 ui/src/ files in a single commit the verdict lands after the code is written — DEC-24's flagged dependency, in its own words. A FAIL then means reworking implementation, and the reviewer judges the design with the implementation in front of them, which is exactly the position that rationalises a weak design
C · Design epic ahead of build epics the shape E-DFLOW itself ran; batches a whole surface's design while the substrate is fresh the coarsest feedback loop available, and designs age across epic boundaries. The roadmap plans no further design epics — every remaining UI epic is a build epic
D · Per screen, not per WU — required whenever a screen is first built or materially re-shaped; WU boundaries free matches the artifact's real granularity (a run designs a screen, not a WU), and tolerates a build split across several WUs without demanding a design from each "materially re-shaped" is not mechanically decidable, so this option is only as good as D2's trigger — on its own it is a rule only a human can apply, and M3 says most UI work is re-shaping

D1a · When the build has to change the design — the exception, and what watches it

Your question: A is the shape, but discovery is real — a small UI change nobody foresaw, or a design WU whose build finds the design wrong. B does not need to be a second shape. Three cases, and the machinery already in flight covers all three; nothing new is built for any of them.

CaseWhat happensWhat controls itWhat monitors it
1 · Small unplanned UI change mid-WU — a tweak to an existing screen, no new surface nothing. No design is required, none is written D2·B's trigger does not fire: it fires on a new @tier component or a new screen, not on re-shapes. This case is designed out, not waived n/a — there is nothing to watch
2 · Build WU amends the design its design WU closed the build WU edits the design file in its own commit; its note's pointer cites the new blob DEC-24 already fires Tier-3 on the merge that lands a closed design — the amended design is landing on this merge, so the design dimension re-judges it here, automatically. No rule is added; the existing one simply applies twice the cited blob ≠ the blob the design WU closed. That difference is the signal — no new note field, one comparison over notes already written
3 · A genuinely new surface is discovered mid-build (a new @tier component) the trigger fires on the build WU's merge, so a design must land inside it — which is option B, arrived at mechanically gated identically to a design WU: same trigger, same receipt, same Tier-3 refusal. The cost B was rejected for is still paid (verdict lands with code written) — but only on the WUs where discovery actually happened, not by policy a build WU whose note carries a design of its own is the exception, and it is one grep. If that count climbs, planning is failing upstream — which is the thing worth watching, not the individual WU

So the control is not a new permission and not a waiver: an amended or late design is gated exactly like an on-time one, because the gate keys on the merge that lands a closed design, not on which WU it belongs to. The only thing W8 adds for this is the pointer it was adding anyway (D2·C) — the blob in it is what makes case 2 countable.

D2 · What makes the requirement fire — the trigger

The load-bearing fork, and the one with numbers. A trigger that reds nearly every UI Working Unit teaches agents to route around it — DEC-15 rejected "block on unimplemented predicates" for exactly that reason.

OptionWould have fired onForAgainst
A · Path trigger — the diff touches ui/src/** 10 of 11 landed UI WUs one predicate, no new vocabulary, nothing for an agent to declare or forget it would have demanded a design run from a scaffold WU and from WUs whose UI delta was a review fix. A gate that reds almost everything gets waived almost every time, and the waiver bill is already at 4 of 12
B · New-surface trigger — the diff adds a file under ui/src/components/ carrying @tier, or adds a screen chosen, with C 0 of 11 mechanically derivable from what already exists (--diff-filter=A plus the @tier membership tag the roster oracle reads). It matches the flow's own output: a propose verdict is a new component. And firing 0 times on landed history means it grandfathers itself — no waiver, no cutoff (D6) silent on re-shapes of an existing screen, which M3 says is where most UI work lives. A component added without @tier dodges it — though that tag is already the roster's own membership waiver, stated where it cannot drift
C · Declared coverage — the build WU's note names the design it implements (path + blob), the gate checks it resolves and is closed chosen, with B n/a — a carrier the only option that makes the link checkable rather than the mere existence of a design somewhere. It is what turns a packet into an address the review can follow a declaration is not a trigger: nothing demands it when the agent writes nothing. Must be paired with A, B or D
D · Judgment at plan time — the WU plan states whether a design is needed; the review judges the answer n/a — judgment no false reds, and "does this need a design" is genuinely a plan-time question a human or reviewer can answer well silence reads as "no design needed" — the defect class this epic keeps finding. E-DFLOW.W2 landed 14 component design files with no code review at all on precisely such a silence, and nothing noticed for five Working Units

D3 · Where the packet lives — the address problem dissolved by your rule

Your reading is right, and it is stronger than any of A–D: there is no address problem, because there is no artifact to address. The four homeless contracts (M4) only look homeless because DEC-16 said an unbuilt design "lives there and nowhere else" — i.e. it granted an unbuilt design the right to survive the epic. Take that right away and the intersection empties: at the epic tip, every design either has code (its contract is TSDoc, the file retires per DEC-16's order) or it has none (the merge is refused). Nothing is left needing a home. Gate check 6 was never wrong — DEC-16 was.
