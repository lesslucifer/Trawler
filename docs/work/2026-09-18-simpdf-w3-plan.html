E-SIMPDF.W3 — the commit hook stops re-proving a green tree

Gate 0's cache already knows when the tree is unchanged, and the pre-commit hook does not ask it. Worse, its key hashes HEAD, so every commit invalidates a proof the content never touched. Make the key the tree's content, give the lint pair its own green marker, and let the hook read both.

Draft v1 · 2026-09-18 · Trawler · T3 WU plan · E-SIMPDF.W3

Requirement

cargo fmt --check and cargo clippy run at commit time only when the working tree's content differs from the content last proven to pass them: the cache key is the bytes the compiler reads — every tracked and untracked non-ignored path, its contents, its executable bit, and the fact of a deletion — and no longer HEAD or git diff HEAD, so a commit that changes no content does not invalidate the proof and a WU's second commit pays nothing. A skip fires only when the recomputed key equals a stored one, never on a stored verdict, so a tree that was not verified can never report green; every invalidation xtask/tests/gate0_cache.rs pins today still fires, and a tracked deletion and a mode flip now fire too. The lint pair gets its own target/.lint-green marker, a matching target/.gate0-green counts as proof of it because Gate 0 caches only after fmt and clippy have both passed, and .cargo-husky/hooks/pre-commit asks one command — cargo xtask lint — instead of running the pair blind. DEC-6's refusal on main stays the hook's first act, before any cargo process starts, and the --workspace guarantee survives the move to gate0::CLIPPY's own test.

Maps to

E-SIMPDF — by the owner's call at this WU's open, not by the epic plan's expected results, which are the design flow's alone and which this WU neither advances nor touches. It extends DEC-11's principle — gate speed is bought by caching under DEC-2, never by relaxing it — from the review path to the commit path, and amends DEC-11's recorded key definition, which this WU makes false. The record is DEC-54, carried by this WU rather than a separate one. No UC-*: nothing a user can see moves.

Executable bitvia the diffhashedSame reason, and this repo's hook tests depend on modes — Gate 0 runs the suite on this key.
Index / staging statenot hashednot hashedUnchanged, and deliberate: fmt, clippy and the tests read the worktree, not the index. The key describes what the compiler sees.

Measured on this repo — 312 files, 4.0 MB: the content key costs 27 ms in one process against the old key's 42 ms (which forks git twice). The key gets cheaper, not dearer; the clippy it stands in for is 0.1 s at best and minutes at worst.

Why two markers and not one. A marker means "this exact content passed this exact check set". .gate0-green vouches for fmt + clippy + the whole suite; .lint-green for fmt + clippy alone. Collapsing them would either let a lint-only pass satisfy Gate 0 — a cache reporting green for tests it never ran, the one thing DEC-11 forbids — or make the hook pay for the test suite. The implication runs one way only, and the reader encodes that direction.

The four facts that shape this WU

FactWhat it means here
The key is Gate 0's too, not only the hook'sChanging worktree_key changes what the review preflight caches on. That is the point — its false miss re-runs the whole test suite, the expensive one — but it widens the blast radius past the hook, so the five pinned properties are the acceptance criteria, not a formality.
DEC-11 states the old key verbatim"key = full worktree hash (HEAD + git diff HEAD + untracked non-ignored contents)". This WU makes that sentence false, so the record is amended in the same diff — never left to a later pass.
The hook is installed by cargo-husky at build timeEditing .cargo-husky/hooks/pre-commit does not change the installed hook until a build runs. The result report states the reinstall, and the hook tests read the versioned file rather than the installed one.
A T1 doc is in the diffdocs/workflow.html is rule-bearing, so the commit carrying it needs a Reviewed-By trailer through cargo xtask mr commit — manual review, which is the user's to run. It is staged and the command printed; never run by the agent.
