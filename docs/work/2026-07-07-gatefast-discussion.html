E-GATEFAST — gate-speed discussion

Landing a Working Unit or epic is slow. This doc pins down why — and it is not the gate scripts. cargo xtask verify-dod is fast local Rust. What is slow is AI-agent time: the turns an agent burns resolving the gate. This maps where that time goes and lays out candidate cuts for the planning session to weigh.

Draft v1 · 2026-07-07 · Trawler · T3 solution discussion
What this doc is about. The cost we are attacking is agent wall-clock and token spend to get a green gate, not the milliseconds verify-dod takes to run. Every optimisation below is judged on one axis: does it remove agent turns from the land-a-change loop without weakening what the gate proves? No recommendation is locked here — that is the epic plan's job.

TL;DR

The gate is a fast script wrapped in an expensive resolution loop. The loop is expensive because (1) the code-review skill re-runs from scratch — full compile + test + 5 finders + N verifiers — on every attempt, and (2) the review is byte-exact diff-bound, so any commit after it (or main advancing underneath) invalidates it and forces a full re-review even when the reviewed code did not change. Those two facts create a cascade: one late fix ⇒ new commit ⇒ dead review ⇒ full re-review ⇒ possibly another fix. Hand-authored notes and governed plan docs add smaller, steadier round-trips on top.
Grounded in session data. A single gate-heavy epic in this repo ran ~700–1600 agent turns, invoking the code-review skill 1–4× and verify-dod 2–8× (sessions 478b7de4: 1602 turns / 4 reviews / 8 gate runs; 9989d9bb: 466 turns / 1 review / 4 gate runs; 3c88ccc5: 726 turns / 1 review / 2 gate runs). Each code-review invocation is itself an orchestrator + 5 finder subagents + N verifier subagents (7–15+ agents), each starting from a full cargo nextest run --all.

Three facts the numbers settle. (1) The gate script is provably not the cost — verify-dod is 4–19 s per epic, <0.5% of active time. The premise holds. (2) The single biggest bucket is main-loop model generation (32–56%), i.e. the turns themselves — every hand-authored note, doc-tag fix, and cascade re-prompt lands here. This is what C4 and cascade-elimination attack; the turn count in the evidence box is the proxy for this bucket. (3) The code-review fleet is a stable ~25%, and inside it finders cost ~2–4× the verifiers (finders 96–110 s avg vs verifiers 23–47 s) — so C5's leverage is on the finder count specifically. cargo builds are a hidden ~10% and are paid twice (main loop + each review's Gate 0), which is C1's double target.

Digging deeper — four review questions

Q: verify-dod is 4–19 s — why any time at all? Isn't it just git-notes + scripted work, no AI?
Correct, and confirmed in the source: gate.rs spawns only git and date as external processes — never cargo, never a compile, and zero AI. It recomputes the diff SHA-256, reads the test/cr/doc notes on the tip, parses their YAML, and checks identity/schema/base/binding/doc-accounting. The 4–19 s is pure git diff + git notes show + process startup. It scales with the epic gate re-walking every WU seam (check 7·walk) — 8 gate runs over more seams ⇒ 19 s; 2 runs ⇒ 4 s. Nothing here is worth optimising; the doc's whole premise stands.
Q: what is the difference between finders and verifiers — isn't a verifier just a finder on a later loop?
No — they are distinct roles in the same review run, both spawned in parallel (SKILL.md §3–4):
  • 5 finders, one per rubric dimension — correctness, reuse, simplification, efficiency, altitude. Each reads the rubric and hunts the whole diff for candidate findings. ~96–110 s each; correctness is the heavyweight (454–959 s aggregate, ~2–3× any other dimension, because it traces callers and data flow).
  • N verifiers, one per candidate finding. Each gets only the claim (never the finder's reasoning) and tries to refute it. ~23–47 s each. N = how many candidates the finders raised.
The "later loop" intuition is a different mechanism: when a gate goes red, the entire find→verify pair re-runs from scratch (the cascade, S3). Session 3c88ccc5 shows six full finder sweeps (30 finder-runs ÷ 5) inside a single epic — that is re-running both roles repeatedly, and it is the real cost, not the finder/verifier split within one run.

But 6 sweeps ≠ 6 × 10 min. The 5 finders in a sweep run in parallel, so one sweep is ~6–12 min of wall-clock (bounded by the slowest finder + its verifiers), and re-run sweeps after a small fix are often just the 5 finders again at 0.6–3 min. Across all six sweeps the epic's entire review time was ~21 min wall-clock (478b7de4, 8 sweeps: ~26 min) — the ~25% row in the budget, not 60 min. Parallelism and shrinking re-runs are why.
Q: is the build-time cost unavoidable?
A floor is unavoidable — you must compile + test to prove green at least once. The individual invocations are already incremental cargo (7–35 s each, not clean rebuilds). What is avoidable is the duplication: the main loop runs test/clippy/fmt, then every code-review Gate 0 re-runs the identical trio, then a red gate re-runs it again. That is where C1 (skip Gate 0 when the tip SHA is unchanged since last green) pays off — it collapses the repeats down toward the one-verify floor without weakening the proof.
Q: dig deeper on the numbers — is doc distillation costly?
Measured, yes — but not where you might expect. The mechanical cost is tiny: HTML Edit/Write ≈ 11–13 s total, htmldoc snapshot/diff curls ≈ 49–50 s, and only 5–9 verify-doc hook-block round-trips per epic (no runaway loop). The real cost is authoring reasoning — the model's own token-generation time spent deciding which tier a fact belongs in, structuring the sections, and writing the HTML prose (as opposed to the near-instant mechanical file-write). Contiguous doc-work windows total 6–13 min of active wall-clock per epic (~10–15%), and it is model generation — so it lives inside the top "main-loop" bucket, it is not additive to it. Plan/result docs get rewritten 2–5× as the agent iterates prose. This is a genuine mid-sized sink, attackable the same way as notes (C4): generate governed-doc skeletons from the diff and let the agent fill intent, rather than hand-authoring each plan/result from blank.

Candidate solution directions

Each targets a specific sink and carries a rough tradeoff. These are framing for the plan, not decisions — a real epic plan will pick, sequence, and defend a subset (and prove each with a test).

→ S1

Incremental Gate 0

Skip the fmt/clippy/nextest re-run when the tip SHA is unchanged since the last green Gate 0 (cache last-green SHA in a note or file). Tradeoff: must invalidate correctly on any tree change; a stale cache that says "green" is a real hazard — cache the SHA, not a verdict divorced from it.

→ S2 · S3

Cheaper re-review on trivial deltas

When the post-review commit is docs-only (or a provably safe subset), allow a scoped re-verify — re-bind the diff hash and re-run only the affected finders — instead of the full 5-finder + N-verifier sweep. Tradeoff: defining "provably safe" is the whole risk; too loose reopens the R2 hole the gate exists to close. Likely the highest-leverage and highest-care item.

→ S2

Stale-base tolerance

Distinguish "base advanced but the WU's own diff is byte-identical" from "the WU diff changed". Only the latter should force re-review; the former can re-anchor the review to the new merge-base without re-running it. Tradeoff: must be certain the interaction surface didn't change, not just the WU's own lines — a semantic conflict with newly-landed main code is exactly what a re-review would catch.

→ S4

Note-authoring assist

Generate test/v2 / doc/v1 from the diff via an xtask subcommand (it already knows the diff, the tiers, and the schemas) instead of hand-YAML. Kills the schema/accounting round-trips outright. Tradeoff: counts/waivers still need agent judgment — generate the skeleton + file accounting, let the agent fill intent. Low risk, steady win.

→ S1

Right-size the finder fleet

Scale finder/verifier count to diff size/shape instead of a flat 5 + N — a two-line docs tweak does not need five dimensions. Tradeoff: under-provisioning a large diff is a coverage regression; needs a floor and a clear size heuristic, and interacts with C2.

→ S1

Faster model for the review fleet

Run finders/verifiers on a faster model (e.g. Sonnet) instead of Opus. Reality check: a finder's wall-clock is mostly tool I/O (git diff, reading files across the repo), not pure generation, so the speedup is partial, not proportional to raw token speed. Tradeoff — this is the load-bearing one: the finders are the bug-catching layer; a weaker finder misses real findings (silent coverage loss) and a weaker verifier either over-refutes (drops real bugs) or under-refutes (leaks false positives into the fix loop, adding turns). Verifiers — narrow, single-claim, adversarial — are the safer place to try it than finders. Cheap to A/B: run one epic's review on each model and compare found/verified/escaped counts before committing.

Where the leverage is (re-weighted by the measured budget). The numbers put main-loop turns as the top bucket (32–56%), so anything that removes whole round-trips outranks anything that speeds one step. That reframes C4 from "small safe extra" to a primary target — it deletes the note-authoring round-trips that live in the largest bucket, and cascade-elimination (C2/C3) removes entire re-review turns, not just re-review seconds. The code-review fleet is the stable #2 (~25%); C1 (skip the from-scratch Gate 0 re-run) and C5 (right-size the finder count, since finders are 3× the verifier cost) attack it directly, and C1 also reclaims the ~10% cargo-build time that is paid twice. S1 × S2 × S3 remain the mechanism that makes each loop iteration both expensive and cheap-to-re-trigger — but the win is measured in turns removed, not script seconds. S6 is out of the agent-time fight by design.

Non-negotiable constraints

Any candidate must preserve what the gate proves — no shortcut may let ungated work reach main, and no cache may report green for a tree it did not actually verify. The gate's whole trust model (DEC-2) is that receipts are recomputed, never blind-trusted; every optimisation here is a caching/scoping problem under that invariant, not a relaxation of it. Correctness of the invalidation logic is the load-bearing requirement — a wrong cache is worse than a slow gate.

Open questions for the planning session

  • C2 scope definition. What is the precise, mechanical definition of a "trivial delta" that is safe to re-verify partially? Docs-only is the easy case; is there a safe code subset, or does any code change force a full sweep?
  • C1 cache location. — DECIDED: git note. Last-green SHA in a git note — it survives, is queryable, and matches the existing receipt model (composes with test/cr/doc notes) rather than a per-worktree local file. Remaining detail for the plan: which ref (e.g. refs/notes/greentip) and whether it syncs to origin like the other note refs.
  • C3 vs. C2 overlap. Stale-base tolerance is arguably a special case of trivial-delta re-verify (delta = empty). Fold into one mechanism, or keep separate because the base-advance case has a different risk profile?
  • Sequencing. C4 is independent and safe — take it first? The loop cuts (C1/C2/C3) are coupled and higher-risk; likely their own WUs with dedicated regression tests freezing the invariant.
