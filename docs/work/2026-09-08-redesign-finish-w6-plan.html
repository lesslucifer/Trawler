The one thing this WU decides: which failure is which

W4 designed two sentences for two causes and left the client no way to tell them apart — listFlows throws one untyped Error for a dead socket and for a refused query alike. The build decision is the discrimination, and it is the smallest one that serves the design.

flowchart TD
  F["GET /flows"] --> R{"did it answer?"}
  R -- "no — fetch rejects" --> U["unreachable<br/>A′ · 'trawler is not answering'"]
  R -- "yes, 400" --> J["rejected<br/>C · '4xz is not a status'"]
  R -- "yes, 2xx" --> OK["the list, and no band"]
  R -- "yes, anything else" --> U
  U --> RT["retry re-runs the fetch"]
  J --> T["more typing is the only correction"]
The API answers a /flows query two ways and only two: the listing, or W5's stated 400. Any other status is a core that is not behaving like the core, which is the same reader-facing fact as no answer at all — the rows cannot be trusted, and retry is the act.
api.ts gains one exported error type carrying the HTTP status, or null for no answer. That is the whole mechanism: useFlows maps 400 to rejected and everything else to unreachable. A rejected query carries the status text that was typed, because status is the only parameter on /flows with a grammar to violate — the sentence W4 wrote ("4xz is not a status") names the value, so the value has to travel with the failure.

Expected result

Checkable by a reader who was not here, at the WU tip:

  1. The detail pane renders at 520px and the app's window opens at 1440 — both values live in configuration, neither is written into a component.
  2. The status field's placeholder reads status — 404 or 4xx, it carries no inputMode, and it is w-field wide. Typing 4xx narrows the list to 4xx flows against W5's real core.
  3. Killing the core with rows on screen produces the band, above rows that do not move; killing it with nothing captured produces the same sentence in the row region and no band. The two are never on screen together.
  4. Typing a value that is not a status produces “4xz is not a status” in the row region and no band — the failure the API answered is not the failure it did not.
  5. Retry disables its button and shows trying 127.0.0.1:7421… for the whole in-flight window, then removes the band and puts focus on the list region.
  6. The detail pane no longer sits on “loading this flow…” after a failed fetch — its failure reaches the same band, said once.
  7. pnpm test, pnpm lint and cargo xtask ui e2e are green; onboarding.spec.ts is untouched and still passes, which is the check that the re-design really did leave.

What could go wrong, and what stops it

RiskWhat stops it
The band and the row-region statement both render, so the failure is said twice. The precedence rule is one expression with one source of truth — the band is rendered only when there are rows — and a unit test asserts the pair for both row counts.
A refused query is reported as an unreachable core, which would tell the user to retry a fetch that will be refused identically forever. ApiError.status is asserted at the api layer and mapped in one place; the rejected state renders no retry at all, because more typing is the only correction.
Fork D4 half-lands — the button greys out with no progress line, or the line appears while the button stays live. Both halves come from one retrying boolean, and the unit test asserts them together in one act rather than in two.
Widening the pane to 520px overflows the row grid at the shell's declared minimum window. It does, and W4 escalated it with the numbers rather than hiding it: the threshold moves 992 → 1132 and both available fixes are inside this epic's declared non-goals. This WU carries the finding forward unchanged; it does not quietly re-decide the row grammar to make it disappear.
Keeping stale rows behind a failure reads as the app lying. That is the design's explicit call — the band says the rows are the last it sent — and the e2e's control asserts the reader can tell it from a quiet proxy.
