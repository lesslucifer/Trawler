Six Working Units that replaced a wizard over a model that observes no per-step progress with a screen a first-time user can finish. The epic also became the first to bill the design flow it ran — and the number says the thing the cut that produced the flow could not have known.

Outcome

Delivered. The epic set out to land two things in order — reach, then the screen that needed it — and to end with a screen a first-time user can finish. Both hold, and the second is provable: the e2e drives the shipped screen from a fresh launch through a real decrypted flow to the list's first paint, and through an off-machine platform whose unmet precondition is stated once rather than three times.

The design flow's first bill

E-SIMPDF's expected result 6, left standing deliberately: no design round in the corpus had ever had a clock or a token count, so DEC-53's cut was argued from what the artifacts cost the review to re-edit, never from what a round costs to run. This epic ran the flow twice. One round is measured; the other is not, and is recorded as not.

W4 — the run re-opened, read, re-closednot measured. No clock and no token count was taken at the time, and none is reconstructible now
Why W4 is blank rather than filled. This project writes no estimates, and the entire value of a first bill is that the next cut to the flow is argued from a measurement. A plausible-looking second data point, reconstructed after the fact, would have destroyed exactly what the deliverable was for — and it would have been indistinguishable from the measured row beside it. The gap is the honest result, and it is also the process finding: a round that is not instrumented when it runs cannot be billed afterwards, so the instrumentation belongs in the flow rather than in the epic that remembers to do it.
ReadingWhat it means for the next cut
The human gate is the flow's dominant cost — 76% of elapsed time. The agent worked 19 minutes; the round took 79 a cut that saves agent effort saves almost nothing. DEC-53 cut the flow to six items and argued it from re-edit cost; this says the payoff to optimise next is how many times a human must read the mockup. Two rounds cost two reads, and a first draft good enough for one read would have halved this
"Token count" is not one number. Output is 145k; cache read is 19.2M, 132× larger a bill reporting a single total is reporting cache traffic and calling it design effort. Output tokens track work done; the cache figures track how much context the session carried, which is a property of the session and not of the flow. Any comparison across rounds must hold them apart
A review round is not cheap relative to the draft. Round 3 spent 38 turns and 68k output to change four things, against round 2's 81 turns and 77k to write the whole amendment three of the four calls needed a component contract re-read before they could be answered. Answering a call well costs about what writing the thing cost — so a flow that wants cheaper rounds has to make calls rarer, not faster
What it does not say: nothing here is a per-item cost the six items were not written serially and cannot be billed apart. A flow arguing which item to cut next needs per-item instrumentation this run did not have and did not invent after the fact
And what this epic adds to it: the flow's rounds are not the only design rounds four more readings happened outside the flow — the PO review, W4's end-user reading, and the owner's two readings at the window inside W5. None is billed here, because none is a run of the design flow. But they are where most of the epic's design change came from, which is itself a finding about a flow whose bill covers only the part that runs before a build

Deviations

#Deviation from the epic planWhy
1The e2e's journey 2 asserts the unarmed half only. The plan wrote it as turn reachability on through the confirm → a host, a port and a certificate URL render not drivable, for three independent reasons: arming opens a native message dialog WebDriver cannot reach from inside the WKWebView; App reads reach once on mount and re-reads it only from the two calls that change it, so an out-of-band POST /reach binds a listener the window never learns of; and the suite runs one core and one window, so nothing can launch already armed. Stubbing confirm_reach under the e2e feature was refused — that feature adds the wdio plugins and changes no behaviour, so a stub would be the first divergence between the e2e shell and the shipped one, and it would prove arming by removing the authorization DEC-55 exists to require. The armed rendering stays covered at integration and unit
2The epic has six WUs because a build was read as a product. The plan's own shape diagram shows it, but the PO review that forced it was not in the original plan W3 shipped a screen that passed its gate and its design review, and then failed a reading nobody had performed: 28 findings, 3 of them sentences that were not true. The design flow reviews a run as a design and never reads it as an end user reads it. W4 added that row to the run's own review item, which is the process change this epic made
3The design of record was amended twice more inside a build WU. The plan has it closing at W2 and re-closing at W4 rounds 5 and 6 are the owner reading the built screen at 1440×800. This is not an oversight in the earlier readings: a rhythm a 384px column hides cannot be found before the column is 864. The cost is that W5 carries three design blobs in its history and one in its note; the alternative was a W6 row describing a gap the owner had already asked to close
4Two P2 findings landed inside W5 instead of becoming W6 backlog rows — F25's column width and F8's collapsed undo both are what the owner asked for at the window, and each is one line of an edit round 5 was making anyway. Deferring them would have written two backlog rows describing work already done
5The registry gained two entries and lost one, where the plan predicted zero movement. TaskStep and CommandBlock were built; ChoiceTiles was built and withdrawn inside one WU the plan's prediction was that the run proposed zero components and mounted nine existing ones, so components·unbuilt would have nothing to resolve. The conclusion holds and the reason does not: the check has nothing to resolve because the two new entries' contracts live in their own TSDoc per DEC-16, not because nothing was built. The withdrawal is on the run's record as withdrawn, naming the round that proposed it and the round that took it back
6DEC-55's index row was verified rather than written. The plan assigns it to W6 it landed complete with the record at W1. W6 read it against what DEC-55 decides and changed nothing — a row written twice is worse than a row written once
7architecture.html's T1 edit is staged, not committed it is rule-bearing: per CLAUDE.md it commits through cargo xtask mr commit … --as <id> with a listed authoriser, which a human runs and an agent never does. See follow-ups
