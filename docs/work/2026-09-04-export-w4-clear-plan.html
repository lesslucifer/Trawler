E-EXPORT.W4 — the capture can be cleared

DELETE /flows and DELETE /flows/{id}, over the first removal the ring has ever had — announced on the bus, because an interface that learns about removal by refetching is not live.

v1 · 2026-09-04 · Trawler · T3 WU plan · E-EXPORT.W4 · epic plan · W1 result · W3 result

Requirement

DELETE /flows removes every flow the listing filters select — the whole capture when no filter is given — and DELETE /flows/{id} removes exactly one, 404 when that id is not in the ring. Both report how many flows were removed, leave total_bytes equal to the sum of what the ring still holds, and announce what left on /stream as one event per removal batch, so a subscriber learns of a clear without refetching. The connection tally is untouched. A filter that selects nothing succeeds reporting zero.

Mapping

E-EXPORT · the epic plan's W4 summary block · UC-7, new at this epic's close ("a client can delete the whole capture, or only what a filter selects, and every live subscriber learns of it on /stream rather than by polling. A cleared store is empty, not restarted: the connection tally and the running proxy are unaffected") · the roadmap's "DELETE /flows" line · the epic plan's expected result 4 and settled question 6 (an empty match succeeds; only DELETE /flows/{id} on an unknown id 404s). Reuses W1's FilterQuery extraction so removal selects by the same rule the listing and the export already share. Independent of W1–W3; the CORS widening this WU was scheduled to make already landed with W3's import — DEC-31 records it and says DELETE joins the same list, which is this WU's edit to that record.

The five things this WU has to decide

QuestionDecision, and why
One Store method or two? One — remove_matching(&FlowFilter) -> Vec<FlowId>. Deleting one id is deleting a selection of size one, and the ring's unlink-and-re-weigh logic must not exist twice. DELETE /flows/{id} needs the 404 that only it can raise, so the route distinguishes "removed nothing" from "removed one" by the returned vector's length, over Store::get-free logic.
Why does the id route not just build a filter? FlowFilter has no id field and gains none: it is the listing rule, and an id is not a listing predicate — adding one would make GET /flows?id=… a second, worse detail endpoint. So Store::remove(FlowId) -> bool sits beside remove_matching, both over one private Ring helper that does the unlinking.
One event per removed flow, or one per batch? One per batch, a new FlowEvent::FlowsCleared { flow_ids }. Clearing a full ring would otherwise emit thousands of events and lag every subscriber past the broadcast capacity — the exact failure sse_lagged exists to report. A batch event is also what the UI needs: one list mutation, not N.
Why not reuse FlowEvicted? Eviction is the ring protecting itself; a clear is a user acting. A client that cannot tell them apart cannot show "capture cleared" without also announcing it every time memory pressure drops a row. Same reasoning the event bus was built on — a single overloaded variant cannot express ordering or cause.
What does the response body say? { "removed": n } — the same shape W3's import chose ({ "imported": n }), so the two mutating endpoints answer alike. DELETE /flows/{id} returns the same envelope with 1, not 204: a caller that wants a count from one endpoint wants it from both.

The byte invariant, and where it can go wrong

evict already does exactly this arithmetic — total_bytes = total_bytes.saturating_sub(flow.retained_bytes()) after a flows.remove — but it pops only from the front of order. Removal by filter takes rows from the middle, so the VecDeque must be rebuilt by retaining the survivors rather than popped. The invariant the proptest asserts is unchanged and is the reason the two paths share a helper: the sum of retained_bytes() over what the ring holds equals total_bytes, after any sequence of inserts, imports, responses, evictions and removals.

The one guardrail worth stating: evict keeps the last row alive (order.len() > 1) so a single oversized flow is still inspectable. Removal has no such floor — a clear that leaves one row behind is not a clear.

Test plan

LevelWhat asserts what
unit src/store.rs
  • remove_matching removes exactly the filtered rows and leaves the others listable and gettable
  • it re-weighs: total_bytes after a partial clear equals the sum over survivors — and a subsequent insert evicts by the corrected weight, not the stale one
  • it clears the ring completely when the filter is default — no last-row floor, unlike evict
  • it emits one FlowsCleared carrying every removed id, and nothing when the selection is empty (a no-op is not news)
  • remove by id returns true once and false on the second call; the ring's order keeps the surviving rows newest-first
  • the connection tally is unchanged by both, extending the existing note_connection_counts_and_broadcasts_independently_of_flows assertion
  • proptest ring_accounting extended with interleaved removals (by filter and by id) — the same invariant, one more operation in the sequence, per the epic plan's instruction not to add a test beside it
unit src/api/
  • view::sse_event maps FlowsCleared to ("cleared", {"flow_ids":[…]}) — the wire shape asserted, not assumed
  • routes::clear_flows: the removed count, the filter honoured, a bad source refused with its reason, an empty selection answering 200 with zero
  • routes::delete_flow: 200+{"removed":1}, 404 on an unknown id, 400 on a malformed one
  • api::mod route table: /flows and /flows/{id} answer DELETE, /flows/export and /flows/import still do not; the preflight grant lists DELETE
integration tests/api.rs Against a running engine on ephemeral ports, over the real HTTP surface: clear-all empties the listing and the subscriber receives cleared; a filtered clear removes only its matches while a survivor stays readable at its detail and body endpoints; /stats is unchanged across both; the three refusal cases answer 200/404/400 as specified. This is the WU's bounded contract — the store's removal reached through the API a client actually speaks.
e2e waived to the epic's own step, on the same reasoning W1–W3 recorded: the epic's e2e (tests/e2e_export.rs, step 4 of the epic e2e plan) drives real proxied traffic then subscribes and deletes, and the app half rides the WebDriver suite after W6. A WU-level e2e here would boot the same engine to assert the same thing one epic step already owns.

Hermetic: ephemeral ports, a local test server, no public network — the standard the existing tests/api.rs already meets.
