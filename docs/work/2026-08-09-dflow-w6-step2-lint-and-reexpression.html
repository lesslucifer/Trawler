ESLint 9 and a local design/vocabulary rule land first; its first red list is the worklist. 142 violations across 58 classes, then zero — every dead class re-expressed as a token, MethodLabel's five hues moved into the palette at the same values, six template shapes pragma'd.

Verdict

②'s gate is met. npm run lint is green over all of ui/src/, and the rule's enumeration is reconciled against the built stylesheet: on all 205 non-arbitrary classes this tree authors, the rule's verdict and the CSS agree exactly. 467 tests green across 39 files (447 → 448 app tests, plus the rule's own 19), npx tsc -b clean, cargo xtask ui specimens --check green.

How the rule decides — one list, no prefix table

A class is legal iff Tailwind's own getClassList() for the closed config contains it. That list is 5,129 entries generated from the config, not transcribed from it. Requirement 1 falls out for free: the list holds whole class names, so classification is on the resolved (prefix, value) pair by construction. text-center is in it, text-body is in it, text-lg is not — and no hand-written table of overloaded prefixes exists to go stale.

What the rule reads — and the two things it deliberately does not

ScopeWhy
Seeds at className, then follows every identifier it references to that identifier's declaration, transitively, anywhere in the file Requirement 2. Anchoring on the attribute misses MethodLabel's METHOD_COLOR map entirely — and that map holds the five classes this WU exists to retire. A rule with that blind spot reports the WU's headline change as already done. Function declarations are followed too, not just const.
Value positions only — comparisons, call arguments, conditional tests, object keys and TS type nodes are not classes and are not walked Found empirically. Following const outcomeClass = state === "confirming" ? … : … into its test produced a red on the string "confirming". The first run had 19 such false positives across Button, CopyButton, CopyText and Onboarding; scoping to value positions removed all 19 and cost nothing real.
Not test files. src/**/*.test.{ts,tsx} has the rule off Tests assert on class names, including deliberate fragments — not.toContain("text-method-"), not.toContain("bg-"), /text-(ok|warn|ink-mute)/. Judging them would red the very assertions that hold the vocabulary in place. Stated here rather than buried: this is a real hole, and a class that exists only inside a test file is invisible to the rule.
Reported, never skipped: a class the rule cannot resolve A template quasi that runs into an interpolation holds half a class name, and half a class name is exactly how an off-list value would hide. {`text-${tone}`} reds as unresolvable. This tree has zero such sites today; the case is covered by a RuleTester pair so it stays that way.

The split is now measured: 161 scale-bearing / 47 structural, over 208 distinct classes. Not this plan's 103/77 and not ⓪'s provisional 144/56. The discriminator is mechanical and needs no allowlist: a class is structural iff Tailwind registers it whole (a static utility — absolute, truncate, text-center) rather than generating it from a theme key. Structural classes carry no value a scale could govern, so closing a scale can never reach them. This is the figure DEC-17 should quote.
The 3 remaining divergences are the point, not a leak. They are the pragma'd template shapes — Tailwind emits an arbitrary value whether or not the config is closed, so the CSS says "legal" and the rule says "declare your intent". Read the reconciliation as: on everything the config can govern, two independent instruments agree; on the 3 it cannot, the rule is the only instrument there is.

The chromatic set — extended by three, on review

①'s reading of the D3 ruling was too strong, and step ② corrected it on review. "Only listed tokens are allowed" is not "delete what the list cannot yet express" — a colour that a component needs and the palette lacks is a gap in the palette. Fork D1 stands: verbs stay colour-coded, at exactly the five hues W5 shipped. What changed is that no token is named after its consumer any more.

Two of the five needed no extension at all. method-get was #4cc38a and so is ok; method-delete was #e5484d and so is warn. W2's fork D1 said as much in prose — "GET shares the ok hue and DELETE the warn hue deliberately — same semantic family" — and nobody had noticed that made two of the eight deleted tokens pure aliases. Verified against the built stylesheet: all five selectors emit their original RGB.
What this costs the rulebook, stated plainly. zero-accent cannot become the one-sentence rule the discussion wanted — the chromatic set is five, not two. The difference from the pre-W6 state is not the count: it is that the list now lives in one place, is mechanically enforced against ui/src/, and is named for meaning rather than for a consumer. A sixth tint still requires a config edit under review — it cannot arrive as an arbitrary value or an inherited default, which is how the previous three did. ③ writes zero-accent as a five-member set with a chromatic-meanings row per member, and adds the three new rows.

Six pragmas — every one a template shape

SiteClass
BodyViewer · FlowDetail · Gallery · FormRenderergrid-cols-[auto_1fr] — a two-column shape with no size in it at all
StepListgrid-cols-[theme(spacing.step-marker)_1fr] — was [18px_1fr]; the 18px is now a token reference, so only the shape is suppressed
Selecttop-[calc(100%+theme(spacing.chrome-y))] — was calc(100%+4px); same treatment
The pragma cannot cover a size, and the rule enforces that three ways rather than trusting the author: the class must carry an arbitrary value at all · that value must not be a bare length (// design-allow: text-[11px] — … is rejected, not suppressed) · and the named class must appear on the line below, so an edited line stops matching and reds. A missing reason reds. Each path has its own RuleTester case.
The pragma lives inside the className expression, not above the element. className={ /* … */ "grid grid-cols-[auto_1fr]" }. JSX has no comment position inside an opening tag, and a {/* … */} sibling is only available when the element has a parent — the expression container works everywhere and keeps the pragma adjacent to the class it excuses.

What code review found — two defects in the rule itself

The gate above was green and the rule was still wrong twice. Both defects are in classify/collectClasses — the rule's own judgement, the one thing no test in the app can reach. Neither was findable by running the rule over ui/src/, because both are silences: the rule said nothing where it should have spoken.
DefectWhat it didWhy the gate missed itFix
Identifier map keyed by bare name Two functions in one file each holding const cls = … overwrote each other; only the last-declared binding's classes were ever checked, the earlier one dropped with no report. The shape occurs nowhere in ui/src/ — six names repeat in the tree (stored, res, mime, live, auto, at) and none hold a class string. A rule cannot red what nobody wrote. Every declaration of a name is kept, not just the last. False-negative only, so no site changed verdict.
/step checked against one global opacity list rounded-full/wash, z-popup/wash, border/hairline all classified legal while Tailwind emits nothing at all — not even the base utility. And text-body/loose, which is legal, was reported. All four live / sites are colour-bearing (bg-canvas-soft/wash, border-hairline/hairline, border-hairline/scrim ×2), so the correct and the broken rule agree on every class the app actually authors. Each base's modifier scale comes from getClassList({includeMetadata:true}) — Tailwind's own per-class list, so the check needs no colour-prefix table any more than the base check needed a prefix table.
The second defect falsifies a sentence the plan and this doc both wrote. Both said the split is "colour token + opacity modifier, each checked against its own scale". The code checked the base against the undifferentiated class list and the step against a global opacity set — so the modifier half was never checked against its own scale at all. text- is the prefix where that bites: it is a colour prefix and a size prefix at once, which is the same overload requirement 1 exists to handle, one level down. Fixing it turned out to widen the vocabulary as well as narrow it — text-body/loose sets a line height and was previously reported as a bad opacity step.
The honest lesson for ③. ①'s defects were found by diffing built CSS; ②'s were found only by an adversarial reader of the rule's source. Both of ②'s defects are invisible to every mechanism this WU built — the lint run, the reconciler, and the 467 tests all stayed green through both. The rule's own unit tests are the only surface that can hold them, which is why the fix for each landed as a failing RuleTester case first. The rule count is now 23.
