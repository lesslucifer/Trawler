The one thing being designed into existence

Everything else in this WU is a wiring. The listbox contract is the single interaction the screen has never had, and W3 flagged it as designed but unproven — no shipped list in this app has one, so the convention is borrowed from Select's options rather than from a precedent at list scale.

region  role="listbox"  aria-label="flows"  tabIndex=0        ← ONE tab stop
        aria-activedescendant → the selected row's id
  row   role="option"   aria-selected={selected}  id=…
        ↑ / ↓   move selection by one, NO wrap at either end
        ⏎ / ␣   open the detail pane for the selected row
        click   unchanged — selects and opens, as today

virtualization: the selected row must be scrolled into view when the keys move
  it past the window, or the contract is nominal — the design's own risk note
  ("if a windowed list makes ↑/↓ untenable, that is a W4 finding").

The rows already carry aria-selected — on nothing, since no ancestor gives it meaning. The region's role is what makes the attribute true.

What could go wrong

RiskHandling
The build makes a design decision. The design does not specify every pixel, and the gap between "wire this component" and "make it look right" is where an undesigned choice slips in — the failure this whole epic exists to prevent, landing in the first WU that could commit it. Every visible change in the diff must trace to a W3 verdict, a Tune row or an Interaction row. Where the design is genuinely silent, the build takes the smallest option and says so in the result rather than inventing. Tier-3 judges this against the cited design.
The listbox contract is nominal. Roles and handlers can be added without the keys actually working — a virtualized list only renders the window, so ↑/↓ past its edge moves selection to a row that does not exist in the DOM and nothing scrolls. The scroll-into-view is part of the requirement, not a polish item, and the e2e drives the real keys against the real window rather than trusting a jsdom handler. W3 pre-authorized the finding: "if a windowed list makes ↑/↓ untenable, that is a W4 finding" — so an honest partial lands as a recorded limitation, never as a silent one.
The truncation gets "fixed". A reviewer or a later pass reads truncate on a payload cell as the defect the rulebook says it is, and removes it — losing the argument W3 spent a stage on. The unit test asserts the truncation and the title that pays for it, so removing either fails. The result restates that this is a recorded violation escalated to W11, not an oversight.
The citation is refused. The epic names this WU the probe and expects sharp edges — built must name exactly the rendered set, and flow.ts sits on the boundary of what design-scope counts as a surface. Run design-scope before writing the note and cite what it lists. If the gate demands something the flow spec calls legal — or refuses something it calls legal — that is a finding for the gate, captured in the result, per the epic plan's standing instruction.
toRow's shrink breaks a consumer. FlowRow's time and duration strings may be read somewhere other than the list. Checked before the edit, not after: grep for toRow and FlowRow across ui/src/. If the detail panel reads them, the change is confined to the fields the list actually owns and the result says so — W6 owns the detail's own migration.
The e2e's UC-4 block is written against the testids it already has, asserting nothing this WU changed, and passes green while proving nothing. The new assertions are on what the design added: the reason phrase in the pill's accessible name, the filter absence's own sentence, and the keyboard path. Each fails against the pre-WU build — that is the check that they are real.
