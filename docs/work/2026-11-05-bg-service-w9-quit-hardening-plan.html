E-BGSVC.W9 — quit hardening

W3's quit path leaves two holes in the shell and two silent failures in the window; this closes them.

v1 · 2026-11-05 · Trawler · T3 (docs/work/) · WU plan · branch wu/bg-service/quit-hardening off epic/bg-service · epic plan: E-BGSVC.W9 · after W3's result

Requirement

A quit request that cannot open the main window never exits the app unchecked and never stays pending. A main window destroyed while a quit request is pending hands the request on, so no window opened later quits unasked. An answer to the once-question that cannot be stored is said so, in the question, which stays open. A failed quit_app is a recorded limit.

Shape

FindingDecisionWhy
1 · quit_in_window exits when reopen_main errs retry once after 150 ms; on a second failure log, do not exit, and clear the flag exiting skips DEC-64's check and can strand the proxy on a dead port. The flag is cleared, not kept: a kept flag is finding 2 again (a later Open quits unasked). The menu-bar Quit stays available to retry
2 · the flag outlives a dying window on_window_destroyed takes a pending flag and, when the app stays, re-issues request_quit clearing alone drops a request whose new window was built before the old window's Destroyed event ran; re-issuing sets the flag again and rebuilds or reuses the window, so the request is answered exactly once. When the app exits anyway nothing is re-issued
3 · rejected quit_app only logsrecorded as an accepted limit (comment on quitApp) quit_app is infallible (app.exit(0)); a rejection means the bridge to the shell is gone, which no dialog could report through
4 · a failed keep-capturing write looks like a cancel the question stays open and shows couldn't save — <reason> (W6's General wording); cancel clears it a vanishing dialog reads as a cancel; staying open lets the user retry or quit
