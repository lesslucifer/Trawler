E-UIINSPECT — Flow Inspector

Click a flow → inspect it: headers, timing, bodies (JSON tree · XML/HTML · image · form · hex · text), copy-as-curl, copy / save body. 3 WUs.

v1 · 2026-07-12 · Trawler · T3 epic plan · roadmap: E-UIINSPECT, Wave 2 · builds on E-UIFOUND

Intent

E-UIFOUND shipped the live flow list but left its detail region empty — a list you can't open into. E-UIINSPECT fills it: select a flow, inspect it. The API already serves everything (GET /flows/{id} + the body endpoints), so the epic adds no new endpoint. Its one backend change: finish the view-time decode chain (brotli · charset · XML), today stuck at gzip/deflate + JSON pretty. It's the next roadmap epic and the feature that turns the list into a usable debugger.

Use-case requirements

One new use case — UC-5 Inspect a captured flow in the native app — added by extending docs/use-cases/web-ui.html (same doc as UC-3/UC-4). Selecting a flow shows:

Metadatarequest line, status (2xx/4xx/5xx color), timing, HTTP versions, full request + response header lists — from GET /flows/{id}
Bodiesrendered by content type — JSON tree · XML/HTML text (XML pretty-printed) · image · form table · hex · text — over GET /flows/{id}/{leg}/body, with a raw / decoded toggle. Empty / streaming / too-large / read-error states show a notice, never blank
Copy / savecopy-as-curl (reproduce the request), copy body to the clipboard, and save body to a file — acting on the shown body, raw or decoded per the toggle
Boundarya pure cross-origin client of 127.0.0.1:7421; reaches no core internals

Contract change: ?decode=1 broadens to also do brotli, charset→UTF-8, and XML — server-side, so curl and the web shell gain it too. Other contracts (raw body, /stream) unchanged; UC-3 / UC-4 stay valid.

Q2 — Decode scope · plan implements all three

The problem, concretely. Trawler stores the raw bytes off the wire; ?decode=1 is meant to render them readable. Today it only un-gzips and pretty-prints JSON, so these common cases are broken in the inspector:

Real trafficToday (?decode=1)After
content-encoding: br — brotli, the default compression for most modern CDNs/APIs (Cloudflare, GitHub, …)compressed bytes → the body shows as hex garbagedecompressed → readable JSON/text
content-type: …; charset=Shift_JIS (or ISO-8859-1) — a non-UTF-8 pagebytes shown as UTF-8 → mojibake (garbled 文字化け, £, é)transcoded to UTF-8 → correct text
a SOAP / RSS / XML body — one long unbroken linean unreadable single lineindented, exactly like JSON already is

So Q2 is only "how many of these three to fix now":

OptionScopeProCon
All three proposedbrotli + charset + XML roadmap-backed; each small/additive; inspector correct for the full common set at once 2 new crates + a charset policy; charset/XML lower-frequency
Brotli onlydefer charset + XML fixes the real bug (br → garbage today); 1 crate; narrowest diverges from roadmap; reopens decode.rs soon

→ all three — marginal cost over brotli-only is small. Narrow to brotli-only if new deps / charset risk bind; charset/XML then go to the backlog.
