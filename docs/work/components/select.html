Select T1

The app's one dropdown — a compact trigger, a popup list, and type-to-filter above a threshold. Options come in; nothing is resolved inside.

Component design · draft — awaiting confirmation · 2026-07-27 · E-DFLOW.W5 · T3 (docs/work/components/) · proposed by run #3 (B1 · B2) · fixes finding 4 · generic per finding 10's review ruling

Identity & frame

Why it exists: the roster has no dropdown at all. SegmentedControl is its only mutually-exclusive switch and it forbids nothing that applies — an @avoid miss by scale, not by kind (finding 10). At 6–7 options its inline group of segments stops being a switch and becomes a toolbar, so the row read as a clean reuse right up to the mockup. Review then ruled the fix generic rather than local: not a setup-specific target picker but the app's one searchable select, which every future dropdown builds on. So this file claims the category — the gap is the dropdown, not this screen — and the trust-target list is just data a caller passes in.

Select vs SegmentedControl — the boundary finding 10 asked for

Two components now do mutually-exclusive selection, so the line between them must be drawn in both files. The axis is cardinality, and it is the first time this collection has needed one — which is finding 10's real point: the contract language had no way to say "correct in kind, wrong at this count".

SegmentedControl needs one line if this lands — W5's to make, not this file's: its @avoid should send lists of five or more here by name, which is the bound finding 10 says component files lack. Not a design change to that component; it is the registry closing a loop that let a reuse read as clean until the mockup. The 5-option boundary is the reviewable claim in this file — 4 fits inline, 5 is where a group starts becoming a toolbar.

4 the no-match line
spec"no match" in ink-mute italic Inter where the list would be. Not selectable, not focusable. The search text stays as typed and the current selection is untouched. whythe alternative is an empty popup, which reads as broken rather than as "nothing matched" — the same reasoning Notice encodes for a zone with nothing to show, at control scale. Italic and muted so it is unmistakably not an option: a plain-styled "no match" row is one Enter away from looking selectable. It is never a warn tone — mistyping a filter is not an error (zero-accent, driver ⑤).
Single-select only. No multi-select, no clear, no placeholder, no free text. Exactly one option is always selected (driver ③) — defaultTarget(hostOs()) always resolves, and the caller owns that default. Multi-select needs a different trigger (it must show "3 selected" or a chip row), different keyboard rules (Space toggles, Enter commits) and a notion of "none": that is a different component, and no tenant has asked for it. A Select that accepts typed values it cannot resolve is a combobox — also not this.
No option groups, no icons, no descriptions, no disabled options. Every real list here is flat and label-only. Groups would need a header row that is not selectable and must be skipped by ↓; a per-option description makes rows two lines and breaks the 24px rhythm; a disabled option is a choice shown and refused, which the caller should simply not pass. Each is a component's worth of rules, and none has a tenant.

Behavior — the keyboard contract

Anatomy is what you see; this is what it does. Every row is Tab-reachable behaviour a test asserts, because a dropdown that only works with a mouse is a dropdown that excludes a keyboard user from the setup screen entirely (driver ④).

KeyClosedOpen
Enter / Spaceopens, active row = the selected oneselects the active row, closes, focus returns to the trigger
↓opens, active = selectednext visible row; stops at the last (no wrap — wrapping loses your place in a filtered list)
↑opens, active = selectedprevious visible row; stops at the first
Esc—closes, selection unchanged, filter cleared, focus returns to the trigger
Tabmoves on normallycloses without selecting, then moves on — never traps focus
typing—filters (shows the search row if it was hidden); active resets to the first match
click outside—closes, selection unchanged
Two rules carry the whole feel. ① Closing always restores focus to the trigger — otherwise focus lands on <body> and a keyboard user's next Tab starts from the top of the screen, which on the setup screen means walking back through three preconditions. ② Esc and Tab never change the selection, and moving the active row is not selecting: a picker that commits on ↓ re-renders the StepList below it on every keypress, so the instructions flicker while you are looking for the right target.

Deliberately absent:
  • no empty state — a Select with no options is a caller error, not a state to design; the host renders nothing instead. Every real list is 6 or 7 and fixed at build time.
  • no loading state — options are data the caller already has, never fetched by the component. A picker whose contents arrive later is the caller's problem to sequence.
  • no "nothing selected" — driver ③: exactly one option is always selected, so there is no placeholder and no clear.
  • no error/invalid state — the value is always one of the options passed in, so it cannot be invalid. Validation belongs to a form, which the app does not have yet.
  • no open-upward variant — the popup always opens downward. Flip-on-collision is real layout work with no tenant: its host sits high in a zone with the StepList below it. Recorded as the open question, not designed.

Forks — settled here, confirm or push back

D1 · the trigger is CopyButton's box, not a text-field look

settled ✓
The shared small-control box. Its real host puts a Select and a Button side by side in one row — with one box, that row reads as two controls of the same weight, which is what they are. Button's fork D1 already made this call for the same reason; a third box would make the collection teach that picking and acting are different kinds of thing.
rejected
macOS▾ filled, like Field
A filled input look (the Field primitive's bg-canvas box), so it reads as data entry rather than as an action. Genuinely arguable — a Select is an input. Rejected: it puts a filled box next to a transparent Button in the same row at the same size, which reads as a hierarchy that does not exist, and data-ink-first prefers the hairline. Revisit if the app grows a real form, where every control is an input and the row has no buttons.

D2 · the search threshold is the component's (> 8), not a prop

settled ✓
✓macOS
Windows
Linux
6 options → no search row. Typing still filters.
> 8 shows the row; typing always filters. Today's lists are 6 and 7, so neither shows a search box it does not need — and both stay type-ahead-able. The threshold lives here so no call site has to notice its list grew (driver ②) and two callers cannot disagree about when a list is long. 8 ≈ the point where the list starts scrolling (7 rows visible), which is the moment scanning genuinely gets harder.
rejected

A prop. Explicit and flexible. Rejected: it makes "is this list long?" a call-site judgement, which is the exact failure mode of finding 10 — a contract that reads clean because nobody had to decide. Run #3's review also asked for this generic rather than per-screen: a threshold set per call site is a per-screen decision wearing a generic component's name.

One highlight that moves. Simpler, and how a native <select> feels. Rejected: after one ↓ the popup no longer shows what the current value is, so Esc looks like it will keep the highlighted row. Costs a tick column; buys an honest picker.

Second open item: whether the trigger should be a native <select> under the hood — rejected in practice because a native popup cannot carry the search row or the tick column, but it is the fallback if the keyboard contract proves hard to hold.

Use / avoid

✅ Use

Any single choice from five or more options: the setup screen's trust and proxy targets, and every dropdown the app grows after them — a filter, a saved view, an export format. Pass {id,label}[], the current value, and a handler; the caller resolves the default. This is the whole dropdown category (finding 10's review ruling), not a target picker.

🚫 Avoid

Two to four options — SegmentedControl, where all choices visible reads as a switch. Multi-select, a clear affordance, or a placeholder: exactly one option is always selected. Free text — that is a combobox. Option groups, icons, per-option descriptions or disabled rows: pass a flat label-only list, or you need a different component. Resolving or sorting options inside the component — that would make it a T2 about your domain. And never commit on ↑↓: moving the active row must not change the value, or every keypress re-renders whatever the selection drives.
