Select T1

The app's one dropdown — a compact trigger, a popup list, and type-to-filter above a threshold. Options come in; nothing is resolved inside.

Component design · draft — round 2, awaiting confirmation · 2026-07-27 · E-DFLOW.W5 · T3 (docs/work/components/) · proposed by run #3 (B1 · B2) · fixes finding 4 · generic per finding 10's review ruling

Identity & frame

Why it exists: the roster has no dropdown at all. SegmentedControl is its only mutually-exclusive switch and it forbids nothing that applies — an @avoid miss by scale, not by kind (finding 10). At 6–7 options its inline group of segments stops being a switch and becomes a toolbar, so the row read as a clean reuse right up to the mockup. Review then ruled the fix generic rather than local: not a setup-specific target picker but the app's one searchable select, which every future dropdown builds on. So this file claims the category — the gap is the dropdown, not this screen — and the trust-target list is just data a caller passes in.
Round 2 — the review widened the component's remit. Draft 1 designed against the two lists it could see (6 trust targets, 7 proxy targets): both hardcoded at build time, both always with a selection. Review rejected four of its "deliberately absent" calls, and they resolve to one direction — Select must also serve remotely-loaded options and an initially-empty value. What changed:

Select vs SegmentedControl — the boundary finding 10 asked for

Two components now do mutually-exclusive selection, so the line between them must be drawn in both files. The axis is cardinality, and it is the first time this collection has needed one — which is finding 10's real point: the contract language had no way to say "correct in kind, wrong at this count".

SegmentedControl needs one line if this lands — W5's to make, not this file's: its @avoid should send lists of five or more here by name, which is the bound finding 10 says component files lack. Not a design change to that component; it is the registry closing a loop that let a reuse read as clean until the mockup. The 5-option boundary is the reviewable claim in this file — 4 fits inline, 5 is where a group starts becoming a toolbar.

Three occupants, in precedence order: isLoading → a spinner + "loading…" (round 2) · no options at all → "nothing to choose from" (round 2) · a filter that matches none → "no match". Loading outranks empty, because an empty list mid-fetch is not yet a fact. whythe alternative is an empty popup, which reads as broken rather than as a stated outcome — the same reasoning Notice encodes for a zone with nothing to show, at control scale, and HeaderTable's pending fix is the same class of bug: rendering "none" for something that has not arrived is a false statement. Hence the precedence, and hence three distinct sentences rather than one shared "empty" — "loading…", "nothing to choose from" and "no match" are three different facts, and collapsing any two of them tells the user something untrue. All muted italic so none is mistakable for an option (a plain-styled row is one Enter away from looking selectable), and none is warn-toned: a slow fetch, an empty set and a mistyped filter are all ordinary (zero-accent, driver ⑤).
Single-select only. No multi-select, no clear affordance, no free text. At most one option is selected (driver ③, round 2): the value may be undefined, and then the trigger shows the placeholder — but there is never a second selection. Multi-select needs a different trigger (it must show "3 selected" or a chip row), different keyboard rules (Space toggles, Enter commits) and a notion of partial state: that is a different component, and no tenant has asked for it. A Select that accepts typed values it cannot resolve is a combobox — also not this. No clear affordance either, despite undefined now being representable: an × in the trigger is a second target inside a control whose whole job is one target, and no tenant needs to return to unselected once a choice is made. A caller that genuinely needs "none" offers it as an option.
No option groups, no disabled options — but a row may render its own content (round 2). Comment: "should allow optional item element". So an option carries an optional element, and what a row looks like becomes the caller's (a glyph beside a label, a two-tone pair, a mono value). What stays the component's is everything structural: groups would need a non-selectable header row that ↓ must skip, disabled options are a choice shown and refused — the caller should not pass one — and the 24px row floor plus single-line rhythm holds whatever the element draws, because it is the touch target (driver ⑦) and the scroll cap depends on it. An element that wants two lines is asking for a different component; the constraint is stated in @avoid rather than enforced, since a T1 cannot police what it renders in a slot.

Behavior — the keyboard contract

Anatomy is what you see; this is what it does. Every row is Tab-reachable behaviour a test asserts, because a dropdown that only works with a mouse is a dropdown that excludes a keyboard user from the setup screen entirely (driver ④).

KeyClosedOpen
Enter / Spaceopens, active row = the selected one, or the first row when nothing is selectedselects the active row, closes, focus returns to the trigger. A no-op while loading, empty, or filtered to nothing
↓opens, active = selected (or first)next visible row; stops at the last (no wrap — wrapping loses your place in a filtered list)
↑opens, active = selected (or first)previous visible row; stops at the first

Two rules carry the whole feel. ① Closing always restores focus to the trigger — otherwise focus lands on <body> and a keyboard user's next Tab starts from the top of the screen, which on the setup screen means walking back through three preconditions. ② Esc and Tab never change the selection, and moving the active row is not selecting: a picker that commits on ↓ re-renders the StepList below it on every keypress, so the instructions flicker while you are looking for the right target.

Deliberately absent — and three that draft 1 listed here have moved into the grid above (round 2):
  • no error/invalid state — the value is always one of the options passed in (or undefined), so it cannot be invalid. Validation belongs to a form, which the app does not have yet. A failed fetch is likewise not this component's: the caller stops passing isLoading and renders its own Notice, because a dropdown cannot explain a network error or offer a retry inside a 184px popup.
  • no clear affordance — undefined is now representable, but only as an initial state; nothing returns to it. See the single-select callout.
  • no open-upward variant — the popup always opens downward. Flip-on-collision is real layout work with no tenant, and review confirmed the defer ("ok, skip for now"). Recorded as the open question, not designed.
  • no partial/indeterminate selection — single-select, so a row is ticked or it is not.

Now designed instead: loading (isLoading), empty (loaded with no options) and nothing selected (value === undefined) — all three in the states grid. Draft 1 argued each away from the two build-time lists it could see; review's point is that the app will fetch options, and a primitive that cannot say "loading" honestly forces every caller to draw its own dropdown.

Forks — settled here, confirm or push back

D1 · the trigger is CopyButton's box, not a text-field look

settled ✓
The shared small-control box. Its real host puts a Select and a Button side by side in one row — with one box, that row reads as two controls of the same weight, which is what they are. Button's fork D1 already made this call for the same reason; a third box would make the collection teach that picking and acting are different kinds of thing.
rejected
macOS▾ filled, like Field
A filled input look (the Field primitive's bg-canvas box), so it reads as data entry rather than as an action. Genuinely arguable — a Select is an input. Rejected: it puts a filled box next to a transparent Button in the same row at the same size, which reads as a hierarchy that does not exist, and data-ink-first prefers the hairline. Revisit if the app grows a real form, where every control is an input and the row has no buttons.

A component-owned threshold (> 8), no prop. Draft 1 settled this to keep "is this list long?" out of every call site — the failure mode of finding 10, where a contract reads clean because nobody had to decide. Rejected at review. The threshold's real problem: it is a guess about scannability that varies by content — six near-identical mono strings are harder to scan than twelve distinct words — so a fixed number is wrong on both sides of itself, and a caller who disagrees has no recourse.
What survives from draft 1: typing filters even when searchable is false, and the row appears the moment it is used. Type-ahead is what a keyboard user reaches for regardless, so opting out of the chrome should not opt out of the capability — otherwise searchable={false} silently removes a keyboard affordance to save a line of pixels. Also unchanged: there is no searchThreshold prop. A boolean is a call-site statement about its own list; a number is a design decision leaking into call sites, which is the part finding 10 was actually about.

Use / avoid

✅ Use

Any single choice from five or more options — known at build time or fetched: the setup screen's trust and proxy targets, and every dropdown the app grows after them — a filter, a saved view, an export format. Pass {id,label,element?}[], the current value, and a handler; value may be undefined before a choice is made, and isLoading covers options still arriving. This is the whole dropdown category (finding 10's review ruling), not a target picker.

🚫 Avoid

Two to four options — SegmentedControl, where all choices visible reads as a switch. Multi-select or a clear affordance: at most one option is selected, and nothing returns to unselected once chosen. Free text — that is a combobox. Option groups or disabled rows. An option element that wants two lines or its own hit target — the row is one line at a 24px floor (D4) — or an element with no label, since the trigger and the filter both need text. Fetching or sorting options inside the component — that would make it a T2 about your domain. Explaining a failed fetch here: stop passing isLoading and render your own Notice, because a 184px popup cannot carry an error and a retry. And never commit on ↑↓: moving the active row must not change the value, or every keypress re-renders whatever the selection drives.
