BodyRenderer family T2

Six content-type-aware body renderers sharing one dispatch contract — BodyViewer picks one by type; the family never renders blank. Status: confirmed 2026-07-23.

Identity & frame

Why it exists: a plain <pre> fails for JSON (no structure), form-encoded (no decoding), image (wrong element), and binary (noise) — dispatching to a type-aware renderer is the unit that knows how to make a body readable, hence T2.

TenantsRequest body pane · response body pane (inside BodyViewer; extracted from inline functions in BodyViewer.tsx + hexDump in body.ts:47, W2 verdict)
Exists todayPartial — JsonTree/FormBody/ImageBody/TextBody in BodyViewer.tsx:16–99; hex is hexDump in body.ts:47; dispatch in body.ts:8 + BodyViewer.tsx:101–113 → extract + rename
Made ofJson/Xml → read-only CodeMirror 6 surface (→ DEC-13) · Image/Hex/Text — no sub-components (Text is a plain wrapping <pre>: no grammar, so no surface to navigate) · FormRenderer → KeyValueRow×
DriverDesign consequence
① content type determines readabilityone renderer per content type, dispatched by family contract
② trustworthy — never alters wire datano silent transform; truncation always visible with cut marker + total size
③ large bodies cap the DOM, not the datahex capped at 4 KiB (body.ts:40); JSON tree over 128 KiB renders as text (body.ts:44); both show a cut marker
④ never a blank paneunknown type or parse failure falls back to TextRenderer (readable bytes) or HexRenderer (unreadable ones) — never empty. This is what makes TextRenderer the family's floor as well as one of its members

TextRenderer T2 W5 · r2·2

The family was documented as five members and dispatched to six. bodyKind() returns "text" for text/*, application/javascript and application/ecmascript (body.ts:14–21), rawKind() returns it for every UTF-8 raw body (body.ts:25–32), and no file specified the component on the other end — the most common body kind in the app, plus every raw view, reached a renderer nobody had designed. It also ships already, as TextBody (BodyViewer.tsx:56–62), doing three jobs at once. This block is the missing specification, written to what ships plus the family contract the others obey.
inputUTF-8 text. Behavior — rules the family obeys

Anatomy = what is on screen. Behavior = what the family does — the dispatch rule, the cut marker rule, and the fallback chain.

Dispatch rule — content-type → member

BodyViewer calls bodyKind(contentType) (body.ts:8) when decode=true, or rawKind(bytes) when decode=false (BodyViewer.tsx:149). The dispatch is a pure function — the member is selected before render, not inside a member.

Raw mode dispatch: rawKind(bytes) returns only "text" or "hex" — no JSON tree, no form decode, no image in raw mode. The distinction is intentional: raw bytes may be compressed; treating them as JSON or form would produce garbage. BodyViewer.tsx:149: decode ? bodyKind(loaded.contentType) : rawKind(loaded.bytes). Every raw text body therefore lands on TextRenderer — which is the second reason it is the family's most-reached member and the one that had no file.
bodyKind does not make the XML/Text split the table above states W5 · for the build WU

The shipped function returns one flat "text" for text/*, application/xml, *+xml and application/javascript alike (body.ts:14–21), and the shipped BodyViewer renders all of them through TextBody (BodyViewer.tsx:109–110) — so XmlRenderer's own dispatch row has never been implemented either. Naming TextRenderer is what makes the gap visible: with six members, BodyKind needs six values ("xml" split from "text"), or the dispatch needs a second predicate over the mime. A dispatch contract that returns five kinds for six renderers cannot be satisfied, whatever the docs say. Recorded here for the build WU; it does not change any member's own contract.

Use / avoid

✅ Use

Inside a body pane (BodyViewer), dispatched by bodyKind or rawKind. Any context that needs to present wire body bytes in a type-appropriate, trust-preserving way. FormRenderer wherever URL-encoded pairs need to be presented — decode + display is its job.

🚫 Avoid

Outside of a body pane context — these are rendering leaves, not general-purpose widgets. Avoid using HexRenderer for non-body binary data (there is no such screen yet). Keep syntax color to the three muted tokens (key/string/number) — no full syntax-theme rainbow, and never in UI chrome. Never mount a member without letting BodyViewer handle the loading/empty/error states first.
