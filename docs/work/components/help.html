Help

A bare ? at the end of a line that opens what explains that line underneath it, and closes it again.

Component design · 2026-10-31 · draft — awaiting confirmation · Trawler · proposed by the setup design run, round 21 (E-ONBRVP.W13, H1) · drawn in context there · retires into the TSDoc on build (DEC-16)

Why this exists

A screen shows only what the user acts on; what explains it is one click away. Today every why line, note, caption and warning is small muted text that is always on screen, so the one thing to do next competes with four lines about it. Deleting them loses help a user sometimes needs. A collapsed details row per note adds a line for each one, which is the clutter this removes.

DriverDesign consequence
The owner's rule, 2026-10-31 (W13's R1)Closed by default. Its text is absent from the page until opened
The line it explains stays where it isIt wraps that line and adds one glyph at its end. Opening it pushes what follows down, never overlays it
keyboard-parityA real button: Tab reaches it, Enter or Space toggles it, Esc closes it while focus is inside
A screen reader must know it togglesaria-expanded and aria-controls on the trigger, and an accessible name that says what it explains (help: why this step)
A new state is a new screenThe host keys it on its state, so it closes when the state it explained changes
zero-accent · Button's contractNo colour or fill of its own. The glyph is ink-mute and lifts to ink on hover and while open

The contract

FacetDecision
tierT1: one boolean of its own, no business logic. It never reads what it shows.
anatomy① the line it explains, unchanged, in a baseline row · ② a 24×24 IconButton with the glyph ?, gap-chrome-gap after the line · ③ when open, the text under the line at pt-chrome-tight, in text-chrome text-ink-mute, the type every note uses today.
behaviourClick, Enter or Space toggles it. Esc closes it and returns focus to the ?. Focus does not move on opening. Several can be open at once: each line owns its own.
textA string, or a short node holding parts a step already uses (a value, a path). Never a button: an action is never hidden (R1).
accessible namehelp: <topic>, where the caller names the topic in a few words (why this step, on Ethernet, if it doesn't load).
colour · type · spacingNothing of its own: IconButton's chrome, ink-mute text, chrome type, the named chrome gaps.

States

StateShows
closedthe line and a muted ? after it
openthe ? in ink, the text under the line
hover · focusIconButton's wash and focus ring

Not states: empty (a line with nothing to explain gets no Help; the caller passes none) and disabled (help is never withheld).

Forks

settled: a button that wraps its line

The ? sits at the end of the line it explains and the text opens right under it, so the reader sees which line it belongs to.

rejected: Disclosure with a ? summary

A native summary must come before its content and is a whole row. The line would have to become the summary, which makes a title or a step sentence a toggle target, and adds a row where none was.

rejected: a tooltip or popover

A tooltip hides on hover-out and does not exist on touch. A popover overlays what follows it and needs focus trapping. Neither can hold a value the user copies.

rejected: one help panel per screen

The text moves away from the line it explains, and the reader has to match them up.

Use and avoid

Use

Why a task matters · a note true of a platform (On Ethernet, change Wi-Fi to Ethernet in the command) · what to check when something fails to load · what a control also does (other devices on Ethernet will be able to use this proxy…).

Avoid

The next action, a value or command to copy, a task's state line, an action's own outcome note: those stay on screen. A second route to the same end: that is other ways, a Disclosure.
