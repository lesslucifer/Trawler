StatusLine T2

A precondition's resolved verdict on one line — glyph, name, short message — where the verdict is what has actually been observed, not what was last clicked.

Component design · draft — awaiting confirmation · 2026-07-27 · E-DFLOW.W5 · T3 (docs/work/components/) · proposed by run #3 (×3, in PreconditionRow) · fixes findings 2 · 22 · @madeof TonedText

Identity & frame

Why it exists: nothing in the roster carries a non-HTTP status with a message. StatusPill is the only status component and its @avoid excludes exactly this case; Notice is one sentence about a zone's absence, not a per-item verdict; TonedText is a tone and some text with no notion of which verdict wins. Run #3's setup screen needed this three times in the one zone that carries the screen's whole meaning — is the certificate trusted, is the proxy set, is traffic arriving — and had to compose it from parts. The reason it is T2 and not a layout helper: which verdict is true is business logic the app already ships (trustStatus / proxyStatus / verifyStatus, setup.ts:206–262), and it is not obvious — an authoritative positive must beat a stale error.
TierT2 Widget — owns the verdict precedence (authoritative positive > in-flight > error > inference > unknown) and the glyph→tone pairing → in the collection
Tenantsthe setup screen's three preconditions — certificate · proxy · verify (run #3, inside PreconditionRow ×3) · any future checklist, health panel, or diagnostic where an item reports a resolved state with a reason
Exists todaythe logic ships and is unit-tested — StepStatusView {glyph, tone, message} (setup.ts:191) returned by three resolvers; the rendering is inline in Onboarding.tsx. This component is the render side, and it takes the shipped view struct as its input
Made ofTonedText — the glyph and, when present, the message tone. StatusLine adds the precedence, the name, and the in-flight case; TonedText adds the colour
DriverDesign consequence
① three of these are scanned together, top to bottomone line, fixed leading, and a short message — finding 22. A status line is scanned, not read; the elaboration belongs to the zone body below it, where there is room
② the verdict must never overstate (the epic's trust-critical rule)a resolved muted "can't check" is a first-class outcome, not a failure and not a blank. The component renders what it is handed and never infers a positive from silence
③ an authoritative positive outranks a stale errorthe precedence is inside the component's contract (and already inside the shipped resolvers): the CA is trusted whatever the last click did. This single rule is what makes it T2
④ the actions behind it take seconds and show an OS promptan explicit in-flight verdict (⟳, muted) that is a state of the line, not of the button beside it — the home Button's @states delegates to "the caller's zone" (finding 7)
⑤ colour is never the only channel (colour-plus-text)the glyph is required and distinct per verdict shape (✓ ⚠ ◐ ○ ⟳) — so the line reads correctly in greyscale. This is the obligation TonedText's D2 states and cannot enforce; StatusLine discharges it
⑥ zero chromatic accent (Warp DEC-11, zero-accent)three tones only, and they arrive already resolved. No fourth tone, no per-verdict hue — the glyph carries the distinction that colour cannot
⑦ never a checkbox — "a tick lies in most real states" (run #3's Frame)no box, no control affordance, no interactivity. A checkbox promises two states to something that has five, and promises the user can set it

The precedence — the business logic that makes this T2

Read top to bottom; the first row that matches is the verdict. This is not new logic — it is setup.ts:206–262 stated as a contract, so a second tenant inherits the reasoning instead of re-deriving it. A component that got this order wrong would be actively misleading, which is why it cannot be a T1.

#ConditionVerdictWhy it ranks here
1an action is running⟳ muted · "Installing…"the truest thing about right now is that we are working. Suppresses every stale reading beneath it, including a previous error (driver ④)
2the probe says yes✓ okan authoritative positive beats a stale error — the machine trusts the CA whatever the last click did (driver ③, setup.ts:214)
3observed evidence proves it✓ ok · "confirmed by captured traffic"a decrypted flow is proof the probe could not obtain — evidence outranks an unavailable check, and still outranks the error
4the last action failed⚠ warn · "Install failed — …"only reached when nothing above proved success. Below both positives by design: an error that has since been overtaken is noise
5partial evidence contradicts⚠ warn · "arriving but not decrypting"traffic without decryption points at the sending device — a warning, not a red error (setup.ts:219)
6the probe cannot run here◐ muted · "can't check automatically"a resolved verdict, not a failure and not a blank (driver ②). The half-glyph is the shape of "unknown", distinct from "no"
7nothing yet○ muted · "not … yet"the honest floor. "Yet" is load-bearing microcopy — the state is pending, not broken
Where the precedence lives. The resolvers stay in the domain (setup.ts) — they read probes, observations, and running flags this component has no business knowing. What StatusLine owns is the contract that a verdict is already resolved by this order, and the guarantee that it will render the result faithfully: it never re-ranks, never merges two verdicts, and never substitutes a friendlier one. Fork D1 settles the API that makes this true — the component takes one resolved verdict, never the raw inputs. So the T2 line is: StatusLine owns the shape of a verdict and the promise of the order; the domain owns which one is true.

Five verdict states × (with name · without) — and the states are verdict shapes, not tones: ◐ and ○ are both muted, ⚠ covers two precedence rows. Reading the tone alone loses information, which is the point of driver ⑤.

Deliberately absent:
  • no empty state — a precondition always has a verdict; the resolvers' floor is ○ … yet (precedence 7), never nothing. A host with no verdict to show renders no StatusLine.
  • no disabled state — run #3's Frame bans an unmet predecessor locking a successor. All three preconditions always report.
  • no interaction states — pure display (driver ⑦); the surrounding row owns the target.
  • no error state distinct from warn — a failed action is a warn verdict with a reason (precedence 4). A separate error tone would need a fourth colour, and DEC-11 has three.
  • no success animation — the verdict flipping to ✓ is the feedback. A celebration on a security precondition reads as reassurance the app cannot always justify (driver ②).

Forks — settled here, confirm or push back

D1 · API — take one resolved verdict, never the raw inputs

settled ✓
✓proxyreceiving traffic <StatusLine name="proxy" verdict={proxyStatus(…)} />
{glyph, tone, message} in — the shipped StepStatusView exactly (setup.ts:191). The resolvers are pure, unit-tested, and read probes plus observations this component must not know. StatusLine owns the shape and the promise of the order; the domain owns which verdict is true. Zero duplication: the struct already exists and already has tests.
rejected
<StatusLine probe="untrusted" seen={…} running={null} error={…} />
Raw inputs in, precedence inside the component. Symmetric with StatusPill's fork D4 (status-in, not tone-in), which is the real argument for it. Rejected: StatusPill's mapping is universal HTTP semantics, while this precedence reads capture observations and running flags — domain state a component would have to import. It would also duplicate three tested resolvers and let the two copies drift on the one rule that must not (driver ③).
The asymmetry is deliberate and worth naming, because a reviewer will read D1 against StatusPill's D4 and see a contradiction. Both put business logic where the inputs live: HTTP status → display is a pure total function of one number, so StatusPill absorbs it. Probe + observations + running + error → verdict is a function of app state, so the domain keeps it and StatusLine takes the result. The tier is the same (T2) because owning the verdict's form and guaranteeing its order is still business logic — it is just not the resolution step.

D2 · short message on the line, elaboration in the body below

settled ✓
⚠certificatenot decrypting …install the certificate on the device you're capturing from. ← the body's
A fragment, ≤ ~40 chars. Three lines are scanned as a column (driver ①); a sentence per line makes the column a paragraph and the glyphs stop lining up. The remedy belongs where the user acts on it. Cost, disclosed: the domain does not return the short form yet — hence the [UI_DEFER] marker, not a silent shortening.
rejected
⚠certificateTraffic is arriving but not decrypting — install the certificate on the device you're capturing from.
Render whatever the domain returns, full sentence and all. Honest today and needs no domain change. Rejected: it makes the component's spec "however long the caller's string is", so three preconditions become three wrapped paragraphs and the scan column is gone. The contract should describe the design, and the gap should be visible.

D3 · in-flight is a spinner in the glyph slot, not a static ⟳

settled ✓
certificateinstalling… domain sends glyph "⟳" → the component animates it
The ⟳ the resolvers return renders as BodyViewer's existing spinner (.spin, already in the sheet), same slot, same width. Motion is the one honest signal that a multi-second privileged action is still running (driver ④) — a static glyph beside "installing…" is indistinguishable from a hang. Reuses a drawing rather than adding one.
rejected
⟳certificateinstalling…
Static ⟳, verbatim. Simplest, and consistent with rendering the glyph as given. Rejected: DurationText's ban on live animation is about a scan column of resting values, and this is the opposite case — the only element on screen that is genuinely mid-flight, during an OS password prompt where the user needs to know we are still waiting too.
Open for review — announcement. A verdict flipping while the user watches (the proxy starts receiving traffic) is a meaningful change with no visual motion. An aria-live="polite" region would announce it; three of them announcing on every poll would be noise. Not settled here because the right answer depends on how PreconditionRow polls, which is screen work W5 does not do — and TonedText deliberately adds no semantics, so this component is the right owner when it is decided. Recorded, not designed.

The card this file compiles down to — carried verbatim as the component's TSDoc when built (code-as-truth):

/**
 * StatusLine — a precondition's resolved verdict on one line: glyph, name, short message.
 * @tier T2 — owns the verdict's form and the guarantee of its precedence (running > authoritative positive > observed proof > action error > partial evidence > can't-check > not-yet), plus the glyph→tone pairing. Takes a resolved StepStatusView; the domain resolvers own which verdict is true
 * @anatomy one baseline row: glyph as a TonedText in the verdict tone (✓ resolved · ⚠ attention · ◐ can't-determine · ○ not-yet · ⟳ in-flight, animated) · optional name in Inter ink-body, never toned, never truncated · short message in Inter ink-mute, a fragment not a sentence (≤ ~40 chars), wraps rather than truncates
 * @use any item that reports a resolved state with a reason — a setup precondition, a health check, a diagnostic row. Pass the resolver's StepStatusView through unchanged
 * @avoid an HTTP status (use StatusPill) · a zone-level absence or one-sentence outcome with an action (use Notice) · a bare toned value with no verdict semantics (use TonedText) · re-resolving or re-ranking the verdict at the call site — the order is the contract · shortening a domain message at the call site: the short form is the domain's to return (see the [UI_DEFER] marker in setup.ts) · rendering it as a checkbox or toggle: a tick lies in most real states, and it is pure display
 * @states ok (✓, resolved yes) · warn (⚠, needs attention) · muted·can't-determine (◐) · muted·not-yet (○) · in-flight (spinner, muted, outranks every other verdict including a stale error) — each with or without the name. No empty, disabled, interaction, or distinct-error state
 * @madeof TonedText
 */

Use / avoid

✅ Use

Any item that reports a resolved state plus a reason and will be scanned alongside its siblings: the setup screen's three preconditions, a future health panel, a diagnostics list. Pass the domain resolver's view struct straight through — the component's promise is that it renders the verdict you resolved, in a shape that survives greyscale and stacks into a scannable column.

🚫 Avoid

An HTTP status — StatusPill. A zone with nothing to show, or a one-sentence outcome with an action beside it — Notice (and it is a zone statement, not a per-item verdict). A toned value with no verdict semantics — TonedText. Re-resolving or re-ranking at the call site: the precedence is the contract, and a screen that reorders it can show a stale error over a proven success. Shortening a domain message locally — the short form is the domain's to return. And never draw it as a checkbox or toggle: a tick lies in most real states, and this component is pure display.
