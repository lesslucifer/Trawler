The fifth state — why fetch-failed is not one of the other four W5 fix

The four absences above all describe bytes that are not there, for reasons that are the store working as designed. Eviction is a different claim: the exchange happened, the bytes were captured, and the ring has since moved past the flow — the bytes are unreachable. Rendering "empty body" or "not captured" for that is the same class of false statement as HeaderTable's "none" for a pending response.
statethe claimtoneaction
emptythe leg carried no bytesmutenone possible
not-capturedbytes existed; the cap declined themmutenone possible
streamingbytes passed through uncaptured, by designmutenone possible
no-response-yetthe exchange is unfinishedmutewait — it resolves itself
fetch-failed newbytes were captured and are now unreachablewarnnone for eviction; retry only when the fetch itself failed

Warn rather than mute because this is the one case where what the user asked for existed and cannot be delivered. But it is not a fault — the ring moved on, which is the store working as specified — so the wording must not read as an error the tool committed (calm-microcopy). The term "no longer captured" is r2·31's lexicon proposal and belongs to W6; this file uses it and will follow whatever W6 settles.

Two failures, one state, distinguished by whether retry is offered: a transport failure against a live flow gets retry (the existing "failed to load body" swatch); an evicted flow gets no action at all, because empty-states-orient's instruction to offer a next step is a lie when none exists (r2·16). The caller supplies the sentence and the action slot; BodyViewer only decides that the region is warn-toned and the controls are gone.

Deliberate non-states. No "disabled" state on the whole component — a leg always has a body BodyView (even if empty). No hover state on the pane itself — chrome interaction lives in the switch and icon buttons; the in-pane cursor, selection and fold gutter of the Json/Xml CodeMirror surface are the renderer's states (body-renderer.html DEC-13), not BodyViewer's. No "loading" skeleton/shimmer — a single small animated spinner, no text (manager 2026-07-23). The chrome bar has no loading state of its own; the pane carries it.

D4 · view default + segment naming — pretty by default, segments raw | pretty settled — manager 2026-07-23

Manager decision (comment round 1): "decoded + prettified by default; hex raw doesn't matter much. raw = decoded raw, pretty = prettified." This supersedes the doc's earlier raw-first stance and reshapes the whole switch, not just its default:

  • pretty (default) = full decode chain: decompress → charset → pretty-print (decode.rs:13). Matches the shipped default (BodyViewer.tsx:141).
  • raw = decoded raw: transport decode only, no pretty-print — minified JSON stays one line. Not wire hex.
  • wire-level bytes are dropped as a view; hex remains only the fallback renderer for non-text bytes (either view); save delivers the decoded-raw file.
  • API implication (build WU owns): the API today serves only wire bytes (no param) or the full chain (?decode=1); raw needs a decompress+charset-only level — a decode.rs split plus a query-param value.
Option A — raw-bytes default rejected

This doc's original stance + the W2 seed card: wire bytes as the trust default; decode always explicit. Rejected: costs one click per body in the common debugging read, and the always-visible active segment already names the view — trust holds without it.

Option B — decoded default chosen — extended

The shipped code (BodyViewer.tsx:141 useState(true)) and the DecodeToggle draft. Chosen, and extended by the manager: the non-default segment is renamed from "raw = wire bytes" to raw = decoded raw, so both segments show the logical body — one as sent, one prettified.

D5 · view-switch visibility when raw and pretty are identical OPEN — needs an API decision before the build WU

Inherited from the DecodeToggle draft, reframed under D4: the switch is a no-op exactly when pretty-printing changes nothing. The problem by example:

Option A — always show the switch

Simplest, no API change; honest for JSON/XML (pretty-print differs). On a plain-text or image body both views are identical and the user wastes a click discovering it.

Use / avoid

✅ Use

Any body pane in the FlowDetail panel — one instance for the request body section, one for the response body section (D3). BodyViewer is the only component that knows how to fetch, dispatch, and render a Trawler body with its full state machine.

🚫 Avoid

Using BodyViewer as a generic file/body previewer outside the FlowDetail context — it is bound to TrawlerApi and the BodyView state contract. For a generic body preview without fetch, use the BodyRenderer members directly. Do not add a third "wire hex" segment to the view switch — wire bytes are not a view (D4); hex is only the fallback renderer for non-text bytes.
