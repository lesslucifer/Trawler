Identity & frame

Why it exists: IconButton's @avoid redirects word-labelled actions to "CopyButton or a plain button" — naming a component the roster does not contain. CopyButton's @avoid rules out "anything that is not a copy action". So the first non-copy, non-glyph action the collection met (retry) had nowhere to land. It stayed invisible for four zones because a read-only detail panel has almost no actions that are not copies — the gap is structural, not incidental.

The three customization axes — how one shell serves all three buttons W5 · reviewer call: all three compose Button

Button owns the only <button> element in the collection. Its siblings differ on exactly three visual axes, so those three become props whose defaults are Button's own values — a sibling passes only what it changes and inherits everything it does not.

Everything else is inherited and can no longer drift: the focus ring (1 px ink-mute outline at 2 px offset), the disabled treatment, the 24 px hit floor, the radius, the hover/active transition, the aria plumbing and the keyboard behaviour. Those are exactly the values the three files had been restating independently — and three of them had already diverged between Button and CopyButton alone (§ tokens). One element, one place the shared half lives.

Why props rather than three implementations: the axes are orthogonal, each has two settings, and four of the six combinations are already in use. frame="bare" + square is IconButton; frame="border" + square is CopyButton's icon form; frame="border" + label is Button and CopyButton's labelled form. Adding a variant later means adding a setting, not another button.

Button is the collection's only <button> element. W5 · reviewer call: all three compose it

CopyButton renders a Button and adds the clipboard write, the copied/failed vocabulary, and the payload-transparency rules — labelled form on the defaults plus tone="mute", icon form adding shape="square" (its fork D2b). IconButton renders a Button with frame="bare" shape="square" size={28} tone="mute" and adds the named-glyph registry. Neither declares a border, a focus ring, a radius or a hit floor of its own.

Button's contract is therefore narrower than its appearance: the element, its accessibility and keyboard behaviour, and the three axes on which a button may legitimately differ. What a copy needs beyond that lives in CopyButton; what a glyph-only trigger needs lives in IconButton. The default rendering — bordered, label-width, ink-body — is just the setting a plain action uses.
No primary variant, no filled style. zero-accent leaves nothing to fill a button with — ok and warn are status colours, and a warn-filled "retry" would state that retrying is the danger. Emphasis comes from which actions are offered at all: zone E's eviction case shows only close precisely because retry can never succeed there. Choosing the actions is the hierarchy; painting one of them is not.
No confirming state, no loading state. CopyButton confirms because it owns the clipboard write and nothing else on screen changes. A Button's handler changes the zone — a successful retry replaces the Notice with content, which is the confirmation. A spinner belongs to the zone doing the work, not to the button that started it. Adding either would make this T2.

Each swatch is a real Button. rest and disabled are the component's own output; the middle three are the same component with its :hover/:focus-visible/:active rules forced on by the doc (see the .force-* block in <head>) — so what you see is the component's real interaction CSS, not a static imitation of it. Before this file was migrated, hover was a fourth hand-written button carrying text-ink border-ink-mute directly: a drawing of a state rather than the state.

Five states, and they are CopyButton's five minus confirming and error — the two it owns because it owns the clipboard. Same values throughout; the only deliberate divergence is the rest label tone (ink-body vs CopyButton's ink-mute), argued in anatomy ②.

The in-flight window is disabled — there is no sixth state. A slow action reuses the swatch above rather than adding one, and the zone carries the progress sentence beside it. That split is fork D4, and it is a contract obligation on the caller, not an optional pattern: disabled without a progress line is a dead control; a live button during an in-flight write invites a double-press.

Forks — settled here, confirm or push back

D1 · chrome — one box for the family, not a second one W5: from "clone CopyButton's box" to "be the box"

settled ✓
Identical border, radius, padding, family and size — and since W5, identical by composition. Side by side, the only difference is the word, which is correct, because the only difference is the word. A second button box would teach that copies and non-copies are different kinds of thing.

W4 settled this as "clone CopyButton's box". W5 finished it: CopyButton renders a Button, so there is one box and one token table. The reason the wording had to change is that cloning did not hold — three values had already drifted while both files claimed identity (see § tokens). A rule that two files must match is only as good as the next edit; a shared shell needs no rule.
rejected · drawn, not built
A distinct, slightly heavier box so actions read as more consequential than copies. Rejected: it invents a weight hierarchy the rulebook does not have, and every screen would then need to decide which of two boxes an action deserves.

D2 · a button inside a warn Notice stays ink-toned

settled ✓
⚠ trawler is not responding
Ink-toned, unchanged. The warn belongs to the message; the button is the way out, not part of the problem. Keeping exactly one warn element per failure means the eye lands on the sentence first — which is the one that says what happened.
rejected · drawn, not built
⚠ trawler is not responding
Warn-toned inside a warn Notice. Tempting for cohesion, but it doubles the alarm and reads as "retrying is dangerous". Also collides with CopyButton's s-error, where warn on a button genuinely means this button failed.

D3 · label tone at rest — ink-body, one notch above CopyButton

settled ✓
ink-body
ink-body. A Button is usually the only way out of the zone it sits in; CopyButton is a convenience beside content that is already readable. visual-weight-follows-goals — weight follows what the zone is for.
rejected · drawn, not built
ink-mute
ink-mute, exact CopyButton parity. Simpler rule, and one fewer divergence to remember. Rejected because the panel's only recovery action would then be the quietest text in the zone.

D4 · the in-flight state — Button stays stateless, but the contract names who renders what W5 · r3·7 · r3·1

settled ✓
⟳ waiting for the system prompt…
The button goes disabled; the zone renders the progress sentence. Button gains no loading prop and no spinner — but the delegation is no longer open-ended. The caller must render both halves: ① the Button disabled for the whole in-flight window, so it cannot be pressed twice, and ② a progress line in the same zone, adjacent to the button, naming what is being waited on. Neither half is optional: a disabled button with no sentence is a dead control, and a sentence with a live button invites a double-press.
rejected · drawn, not built
A loading prop with an in-button spinner (what CopyButton does in spirit — it owns its own confirm). Rejected: the label would have to change to a progress word, so the caller supplies two strings for one action; the box would resize; and the button becomes the only place the progress is stated, which fails as soon as the action takes long enough that the user has looked elsewhere. A zone-level line survives that; a glyph inside a disabled control does not.
Why "the caller's zone owns the outcome" was not enough W5 fix · r3·7

Delegating the lifecycle is the right T1 boundary — a primitive cannot know whether an elevation was declined, a write partially applied, or a prompt dismissed. But the old contract stopped at the delegation: it said the zone owns the outcome and never said what the zone must render. So every screen with a slow action invents its own answer, and the two components that already exist disagree in spirit — CopyButton confirms inline, Button pushes out. Run #3's setup screen, where every write takes seconds and shows an OS prompt, had to resolve it as a screen decision standing in for a vocabulary one.
phaseButton rendersthe zone renders
at restthe label, enabledwhatever the zone's standing state is
in flightthe same label, disabled — no spinner, no label changerequired: a progress line naming what is awaited ("⟳ waiting for the system prompt…")
succeededenabled again, or removed if the action no longer appliesthe new standing state — a Notice at tone="ok" when the outcome is the zone's content (Notice D4)
failed / declinedenabled again — the way out must come backa warn Notice saying what happened, with this Button in its action slot if a retry can succeed

This is still a delegation — Button holds no lifecycle state and takes no new prop. What changed is that the contract now says which two things the caller renders, so the next screen cites this table instead of deciding again. The progress line's shape (glyph · sentence) and its precedence rules are StatusLine's (T2 — the precedence is business logic); a zone with no status line of its own uses a mute Notice.

Not fixed here: r3·7 also asks whether the rulebook should carry this as a rule so it binds screens that never touch this file. That is W6's; this file states the component-side half.

Open for W5: whether a destructive tone is needed later (clear the capture ring, delete a flow). Deliberately not designed here — the app has no destructive action today, and zero-accent means the answer would have to be a word ("clear all"), a confirm step, or a warn carve-out. Designing it against a hypothetical would settle it wrong; recorded so the first real tenant reopens it rather than inventing a variant.

Use / avoid

✅ Use

Any action that needs a word and is not a copy — retry, close, save, submit, and every form or dialog the app grows. This is the primitive IconButton's @avoid already sends you to. Prefer one lowercase verb; the label is the accessible name.

🚫 Avoid

Copy actions — CopyButton owns the clipboard write and the confirm that follows it. Actions whose glyph is unambiguous in place (close ×, save ↓ in a dense bar) — IconButton is more compact and already the convention there. Reaching for emphasis: there is no primary variant, so express importance by offering fewer actions, not louder ones. And never warn-tone it inside a warn Notice (D2).
