A11y — radiogroup pattern
specrole="radiogroup" on the container · aria-label from the ariaLabel prop · each segment role="radio" with aria-checked · roving tabindex (active segment holds the tab stop) · arrow keys move focus · Space/Enter selects whyradiogroup is the correct ARIA pattern for mutually exclusive options — it gives screen readers the "1 of N" positional context (Fork D3 rationale)

specoptional disabled prop mutes and inerts the whole group (native disabled on every segment); the current value stays visible. No per-segment disabled whya single unclickable option in a 2-option group reads as broken; if one option can't be chosen, the tenant removes it or hides the control — that judgment is domain logic (see body-viewer.html fork D5)

States

value-active — exactly one segment filled at all times; which one is purely the value prop
hover (inactive segment) — muted → ink; fill does not appear until clicked
focus — 1 px mute outline on the focused segment. Zero-chromatic-accent rule: never colored
disabled (whole group) — muted, non-interactive, value still visible. E.g. BodyViewer while the body is absent/loading
Deliberate non-states. No per-segment disabled — reads as broken on a small group; the tenant removes the option or hides the control instead. No empty / no-selection state — value must always match one option; a segmented control with nothing selected is a different (worse) component. No loading or error states — the control is synchronous display; anything asynchronous belongs to the tenant.

Forks — settled here, confirm or push back

D1 · control form settled: segment group
← settled

All options visible in a single group makes the choice structurally explicit — the current state is unambiguous at a glance (driver ①). A cycling button only names one side and forces the user to read the label to infer the state.

alt: single cycling button rejected

One touch target, but "show decoded" implies decoded is not current while "decoded" implies it is — either reading is ambiguous. Driver ① rules it out.

D2 · selection model settled: single-select only

Both known tenants (decode, leg) are mutually exclusive views. Single-select is what "one segment always filled" and the radiogroup pattern mean; the contract stays one prop (value), one event (onChange).

alt: multi-select variant rejected — no tenant

A type="multiple" mode (as Radix ToggleGroup offers) would change the value shape to a set and the ARIA pattern to independent aria-pressed toggles — a different component wearing the same clothes. Add as a sibling when a real tenant appears, not before.

D3 · ARIA pattern settled: radiogroup
tab ▸ "body view, group" → ▸ "decoded, radio, 2 of 2" space ▸ selects decoded

role="radiogroup" + role="radio" gives the 1-of-N positional context and the roving tabindex model. Screen readers announce selection without extra markup.

alt: aria-pressed on each segment rejected

aria-pressed implies independent toggles — a screen reader would not convey that selecting one deselects the others. The radiogroup pattern exists precisely for this case.

Where the decode forks went. The DecodeToggle draft's domain decisions were never this control's to make: default mode and reset-on-flow-change (was D2) and visibility when there is nothing to decode (was D3) are BodyViewer rules — now body-viewer.html forks D4 and D5, both open.

Use / avoid

✅ Use

Any mutually exclusive view/mode switch whose state must stay visible: BodyViewer's decode switch and leg switch today; any 2–4-way mode choice tomorrow. The tenant owns the value, the side effects, and the decision to render the control at all.

🚫 Avoid

Actions — a segment selects a mode, it never does something (that is CopyButton/IconButton). Multi-select (fork D2). Tab navigation that owns panels — that is a tablist, a different ARIA pattern. More than 4 options — use a select. Encoding domain rules in the control: what "decoded" means, which mode is default, when the switch is hidden — all tenant logic.
