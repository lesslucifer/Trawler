Why pending exists — the contract used to state something false W5 fix · r2·1

An in-flight response has no headers yet. Before this fix the file declared "no loading / in-flight state" and advised the caller not to render the Section at all — so a screen that did render it (as the shipped panel does, and as no-layout-jump requires) fell through to empty and printed "none". The lexicon reserves "none" for the empty set: the response arrived and carried no headers. Rendering it for a response that has not arrived is a false statement about the wire, in a tool whose only value is being trustworthy about the wire.
caller passesstaterendersmeans
nullpending"awaiting response…"the exchange is unfinished; ask again later
[]empty"none"the exchange is finished and this leg carried no headers
[…]populatedthe gridthese are the headers, in wire order

The distinction is the caller's to make — HeaderTable only renders what the shape of headers tells it. The two sentences must never collapse into one (absence-names-itself, the rule candidate r2·13 proposes from this same finding). Not rendering the Section is also not an option: the zone would appear when the response lands and shift every zone below it.

Deliberate non-states:
  • No spinner. pending is a sentence, not a progress indicator — see the state above. What HeaderTable still does not do is decide it is pending: the caller passes headers={null}, because only the screen knows whether a response is in flight, evicted, or simply absent.
  • No collapsed state. Fork D1 settles this: a scroll cap is used instead of a collapsible disclosure. HeaderTable has no open/closed state; it is always fully expanded.
  • No hover / focus state on the composition. These belong to KeyValueRow (value cell: CopyText's hover/focus/confirming — review 2026-07-23) and the copy-all CopyButton (its own states, incl. the error state); HeaderTable itself has no interactive states of its own.

D4 · copy-all payload format settled: wire format, trailing \n
accept: application/json authorization: Bearer eyJhbG… content-type: application/json (single trailing newline)

Wire format wins (moved here from the dissolved CopyAllHeadersButton — HeaderTable owns the serialisation): name: value\n per pair is paste-ready everywhere (tickets, specs, curl), human-readable, and represents duplicates + order faithfully. The trailing newline lands the paste cursor on a fresh line — join('\n') + '\n', one character.

alts: JSON · curl -H · tab-separated rejected

JSON object — needs transformation before use; cannot represent duplicate header names; key order implementation-dependent. curl -H flags — curl-only syntax; the full-request case is already served by copy-as-curl (FlowDetail.tsx:51 / toCurl). Tab-separated — no ecosystem reads tabs as headers; pastes as broken text in most editors.

 * owns the copy-all serialisation (name: value\n per pair, wire order, trailing \n).

Use / avoid

✅ Use

Exactly two call sites: "Request headers" (panel zone C) and "Response headers" (panel zone D) in FlowDetail.tsx. Any future leg that exposes a named header set with a copy-all action follows the same pattern.

🚫 Avoid

Passing a pre-sorted or pre-filtered array — the composition contract requires the raw captured order. Passing [] for a response that has not arrived — that renders "none", which says the leg carried no headers; pass null and get "awaiting response…" instead. Rendering KeyValueRow× directly without HeaderTable when a copy-all action is also needed — that duplicates the sub-bar placement logic. Using HeaderTable for non-header name/value data that doesn't warrant a copy-all (a single decoded form field, for example — a bare KeyValueRow is sufficient).
