Behavior — the rules the parts obey

Anatomy is what is on screen; behavior is what it does. StatusPill is purely display — it owns no interaction. Its "behavior" is the resolution rule: status in → tone, text, and alt text out.

The mapping in full (flow.ts:7–13): status == null → muted · floor(status/100) === 2 → ok · floor(status/100) === 4 || 5 → warn · everything else → muted. That means 1xx, 3xx, and any out-of-range code are all muted. 3xx being muted (not ok) is an intentional product call: a redirect is not a success outcome for the intercepted exchange. The build WU moves this mapping inside StatusPill (fork D4); the rule itself is unchanged.
No interactive states. StatusPill is a pure display component — no hover, no focus, no click. It carries no interaction of its own; the row that contains it owns selection/hover.

D2 · 3xx treatment — muted vs ok settled: muted
settled: muted
301 302

A — muted (shipped). A redirect means the exchange didn't complete at this URL; calling it "ok" would mislead a developer checking why their API call bounced. Muted reads "informational / non-terminal".

rejected: ok-tinted
301 302

B — ok (rejected). HTTP spec calls 3xx "successful redirection" — but from the proxy's perspective the intercepted request was redirected, not served. ok would obscure infinite-redirect bugs.

D3 · StatusPill vs StatusDot — relationship settled: two components, different concerns
StatusPill — HTTP outcome
200 404 …

StatusPill shows the HTTP result of a single flow. Its tone comes from statusTone(). It is the per-row / per-flow status token. No interaction.

StatusDot — capture connection
connected broken checking

StatusDot (components.tsx:38) shows the proxy's capture connection health — a single persistent indicator in the header. It is a <button> (tap re-invokes onboarding). Different shape (circle vs text), different domain (infra health vs HTTP outcome). They share the ok/warn/muted tone vocabulary but are not the same component and do not compose.

No unification proposed. checking has no chromatic token (DEC-11, per components.tsx:31) — so it reads muted; broken/connected reuse warn/ok. StatusPill has no "checking" state because HTTP flows either complete or are pending.

D5 · reason-phrase source — lib vs hardcoded map settled: statuses lib

A — statuses (jshttp), settled. Zero-dependency, ~2 kB, IANA-sourced: statuses.message[404] → "Not Found". Maintained upstream (the map Express itself uses) — nothing to keep in sync in this repo. New dep in ui/package.json at the build WU.

B — hardcoded map (rejected). ~60 lines of copied IANA table that drifts as codes are added. No stdlib alternative exists in the browser (http.STATUS_CODES is Node-only, unavailable in the Tauri webview bundle).

Open question for the reviewer (gap): the shipped statusTone() handles only null (pending) and numeric HTTP codes. Trawler's flow model may eventually surface flows that are aborted before any response (connection reset, TLS error, proxy error) — distinct from "no status yet" (null). The current code folds these into null → muted "…". Is a distinct "aborted" / "failed" state needed — e.g. a warn-toned "✕" or "ERR"? If so, that is a new tone in StatusTone and a new branch in statusTone(). Confirm or propose here before the build WU.

The card this file compiles down to — carried verbatim as the component's TSDoc when built (code-as-truth):

/**
 * StatusPill — HTTP status value tinted by outcome tone; the sanctioned chromatic exception in Warp's zero-accent scheme.
 * @tier T2 — owns the status→tone mapping (2xx=ok, 4xx/5xx=warn, else muted) and the reason-phrase alt text; status in, full display out
 * @anatomy TonedText carrying the status code ("…" when null); title + aria-label = "<code> <reason phrase>" via the statuses lib
 * @use anywhere a flow's HTTP outcome is shown — pass the raw status (number | null), nothing else to resolve or format
 * @avoid pre-resolving tone or formatting at the call site — that is this component's job · a toned value that is not an HTTP status — use TonedText (T1) · proxy connection health — StatusDot
 * @states tone:ok (2xx) · tone:warn (4xx/5xx) · tone:muted (3xx, 1xx, unknown, null/pending → "…") · no interaction states (pure display)
 * @madeof TonedText
 */

Use / avoid

✅ Use

Any place an HTTP outcome needs a color signal: the flow list status column, the detail panel identity bar, any future flow summary card. Pass the flow's raw status — nothing to resolve or format first.

🚫 Avoid

Raw hex colors — tones come from tokens, never hard-coded. Pre-resolving the tone or formatting the value at the call site — that duplicates the business logic StatusPill centralises. A toned value that is not an HTTP status — that is TonedText (T1), not StatusPill. Proxy connection health — that is StatusDot, not StatusPill.
