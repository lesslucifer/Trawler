E-DFLOW.W4 Run #3 — the setup screen, against the substrate

A third integrated run, on a screen the substrate has never seen. Runs #1 and #2 both designed the flow detail panel — the registry and rulebook were extracted from that panel, so they were being asked to fit their own source. The setup screen shares no element with it. This run is the generalization test.

How to read this

Each stage carries its artifact and nothing else — every place the substrate is wrong, missing or ambiguous is a row in the one findings table, tagged by owner: W5 registry W6 rulebook W7 harness flow. The screen is designed fresh: the shipped onboarding stepper exists but is not an input — it was built by E-UISETUP before this flow existed, and reading it first would anchor the design to a layout nobody derived. It is compared against the result at the end (cross-check). The registry and rulebook were read once, before stage 1, and are not edited during the run.

1 · Frame

Not given: firing the prove-it request (epic non-goal) · any remote-device probe · per-device attribution (a bare u64) · why a handshake failed · undoing an install from the app.

Three structural calls, each traceable to a Frame row. (1) No mode picker. "Three cases, one screen" forbids asking; the case is read off the probes and the observed traffic. This machine = probes answer; remote = probes say unknown and a target is picked; return visit = C is already true on paint, so B collapses to status lines. The zones do not change — only which one is loud. (2) Weight is dynamic, order is static. "Preconditions order weakly" bans disabling and bans a fixed 1-2-3 emphasis, so B renders in a stable reading order while open-at-rest follows the highest-ranked unmet one. A user landing with a trusted CA and no proxy sees B2 open and B1 as a satisfied line. (3) Reversal is a zone, not a disclosure. Putting D inside each precondition's body would hide it exactly when it matters most (after a successful install, when the body is collapsed) — so the undo appears in both places: inline with its command as the instruction's last line, and collected in D as the standing answer to "what did this app do to my machine".

Loop back to Frame: none. Every zone traces to a driver, and the Frame's two substrate constraints both landed structurally — Section-no-nesting forced B's sub-grouping onto a lighter device (the status row + hairline, drawn above), and the absent action-lifecycle state is what makes "install for me" a designed control rather than a cited one. Both resolve at Elements.

Two T1 proposals are wider than this screen. Review pushed both up a level: TonedText is the base StatusPill already declares, and Select claims the whole dropdown category rather than this screen's target picker. Neither is a setup component — the setup screen is just the first tenant, which is the right way for a registry to grow (a component earns its file by being needed twice, and both are already cited twice). It does mean W5's scope grows: these two land as vocabulary, not as screen parts.

The result is the finding. Four of eleven placed components are reuses and four are proposals — against run #2's twelve reuses and two proposals on the same substrate. That ratio is the generalization test's answer: the registry covers showing captured data and does not cover telling a user to do something. Every proposal here is in the second category (a status that is not an HTTP status, an instruction list, a target picker), and every reuse is a component whose job is rendering a value or a label. This is a breadth result about the registry, not a failure of the run — but it does mean a screen outside the flow-detail family currently costs four design files before it can be built.

Findings

#StageFindingOwner
1Frame The registry holds no component with an action lifecycle — nothing can be pending, in-flight, or refused. Button and IconButton both assume an act that completes instantly (a copy). Every write on this screen takes seconds and shows an OS prompt, so the state has to be designed rather than cited. Narrowed at Elements: Button's @states does not omit the lifecycle, it delegates it ("the caller's zone owns the outcome") — see finding 7. The Frame overstated this by reading the roster, not the file. W5 registry
2Frame The rulebook's chromatic vocabulary is binary — ok = success, warn = failure. This screen's most common status is neither: unknown is a permanent, supported state in the remote case. The Frame resolves it to the neutral channel as a case-specific quality, but a screen whose dominant status has no vocabulary entry suggests the fixed-meanings table needs a third. W6 rulebook
3Frame Nothing in the rulebook binds a design that modifies the user's machine — no rule about announcing an effect before invoking it, about surviving a declined elevation, or about publishing a reversal. Three of this screen's drivers had to be written from scratch where a rule should have carried them. The flow-detail panel was read-only, so the gap was invisible until now. W6 rulebook
4Frame The Frame template asked for "given capabilities" with no slot for explicit non-capabilities — half this screen's design pressure comes from what it cannot observe. Fixed mid-run: Not given is now a named template line, and frame·prose-blocks allows 3. flow
5Frame The Frame's form rule ("every cell is a clause, never a paragraph") was written and ignored — this run's first Frame came in at mean 17.9 words per cell against run #2's 9.0, plus two commentary blocks that were not artifacts. Fixed mid-run: six Tier-1 predicates now check Frame density on every write. W7 harness
6Frame A Frame at legal density was still hard to read: three abstraction columns in a row (driver · therefore · why) gave a reviewer nothing concrete to judge, and checked by stated the test abstractly rather than showing it. Fixed mid-run: the column order is now driver → why → therefore → on this screen, and the last column is a ✓/✗ pair — the rulebook's own DO/DON'T pattern, which has held across 14 soft rules. The ✗ does work the criterion never did: it names the plausible failure the design is at risk of. flow
7Elements "The caller's zone owns the outcome" names no owner. Button declares no loading and no confirming state and delegates both to the caller — a reasonable T1 boundary, but the contract stops at the delegation. Nothing says what the caller must render, so every screen with a slow action invents its own answer, and the two that exist already disagree in spirit (CopyButton owns its confirm inline; Button pushes it out). This screen resolves it as Button disabled + the zone's status line carries ⟳, which is a screen decision standing in for a vocabulary one. W6 rulebook
8Elements TonedText is cited by contract and does not exist — second sighting. StatusPill's @madeof is TonedText and its @avoid redirects non-HTTP toned values to it by name and tier, but the roster has no row and there is no design file. Run #2 found it by reading StatusPill and never needed to place it; this run needs it three times in the one zone that carries the screen's whole verdict. A contract that names a component the vocabulary lacks is worse than a gap — it reads as available. W5 registry
9Elements The registry has no instructional component. Nothing renders an ordered list of things for the user to do — KeyValueRow is wire data, CopyText @avoids prose outright, Notice is one sentence with at most one action. This is structural, not incidental: all 16 files were extracted from a read-only panel that never asked the user for anything. Any screen that instructs — setup, an error with a remedy, a migration — starts from zero. W5 registry
10Elements An @avoid miss by scale, not by kind. SegmentedControl is the roster's only mutually-exclusive switch and forbids nothing that applies here, yet at 6–7 targets its inline-group anatomy stops being a switch and becomes a toolbar. The contract language has no way to express "correct in kind, wrong at this cardinality", so the row reads as a clean reuse right up until the mockup. Component files may need a bound on their option count where one exists. Resolved at review as a generic Select (T1) rather than a setup-specific picker — the roster has no dropdown at all, so the gap is the category, not this screen. W6 rulebook
11Elements The generalization test has its answer, and it is a breadth result. Same substrate as run #2, different screen: 12 reuses / 2 proposals there, 4 reuses / 4 proposals here. The split is clean along one line — the registry covers showing captured data and not telling a user to do something. Every reuse this run is a value-or-label renderer; every proposal is instructional or status-with-a-message. The vocabulary is sound within its family and thin one step outside it. Review widened two of the four: TonedText and Select are proposed as general vocabulary, not setup parts — so the registry gains a status base and a dropdown it lacked entirely, and only StatusLine and StepList are really this screen's. W5 registry
12Elements The element map shipped inert, and two gates missed it. The Elements stage was written keyed and correct, but the run doc never linked specimen.css — which is where .hl lives. Every click fired and toggled a class that styled nothing. verify-doc did catch it as assets·specimen, and the run read that failure as "a downstream stage is still pending" and moved on: a checker is only as good as the reading of its output, and a red that names an asset is indistinguishable, at a glance, from a red that names a missing section. Separately, elements·map itself was too weak — it passed on data-map plus any single data-key, so a keyed tree over an unkeyed catalog (half the map dead) read as green; the flow's own green test fixture was exactly that shape. Fixed mid-run: the check now requires a key in both halves and reds any component placed in the tree with no catalog row — the last one is the valuable half, since a placed component with no row never faced the reuse-or-propose pass at all.
