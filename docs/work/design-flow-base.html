Design flow — base spec & templates

The staged flow an AI agent follows to design a screen, with a copy-paste artifact template per stage. Screen-agnostic: the reusable method, not one design. Worked example: the flow-detail panel in dflow-run-1.html.

Base flow · 2026-07-19 · Trawler · T3 (docs/work/) → promoted to a T1 process doc after W4 · from E-DFLOW.W1

What this is

The written base flow produced by E-DFLOW.W1: six stages, each with the concrete artifact template the hand-run converged on, plus the conventions that make an artifact reviewable. It is a first cut hardened by one real run — W4 re-runs it against the seeded registry (W2) + rulebook (W3) and revises; only then is it distilled into the T1 process doc. Until then it lives here in T3.

Principles (apply to every stage)

  • Representation is load-bearing — optimize for human perception. The reviewer is the bottleneck. Every artifact is picture- or table-first; prose is demoted to a compact reference. Walls of text and over-dense diagrams (mindmaps) failed review in the run. When a form isn't obvious, pick it by comparison (a throwaway side-by-side doc), don't assume.
  • Cite by name, not coded ids. Drivers, rules, and components are referenced by name; the harness coverage-checks the named rows. Coded ids (G1/C2/…) were tried and dropped as noise.
  • Reuse-or-propose. A design either reuses a registry component or proposes a new one — passing with a spec now, built + human-approved later. It never silently reinvents.
  • One artifact per stage, cheapest commitment first. Each stage's artifact is the next stage's input. A stage may loop back (Tune → Layout); the loop is real, not decorative.

The stages

1 · Frame

Question: who reads this screen and in what context, what job does it do, what are its ranked goals, hard constraints, and experience qualities? (The screen's functional capabilities — what it must be able to do — are an input, not the output.)

Form: a driver table — each driver forces a design consequence; the row is the reasoning. Grouped Goals / Constraints / Qualities; no coded ids.

Purpose: <one paragraph — user, context, the job this screen does>

Given capabilities (functional input — received, not designed):
  <capability> · <capability> · …
Driver…therefore (design consequence)whychecked by
Goals — the ranking is the visual hierarchy
<goal><what it forces><why it ranks here><observable criterion, or —>
Constraints — hard boundaries
<constraint><consequence><why><criterion>
Qualities — Tune's yardstick (drive the feel)
<quality><consequence><why><criterion>
Non-goals: <explicitly out of scope>

Key distinctions: functional requirements are the input; the Frame's output is the design lens (goals become hierarchy, qualities become Tune's yardstick). Each success criterion rides in the driver's "checked by" cell — it verifies that driver's consequence — rather than living in a separate list. General principles (a11y, spacing, state-handling) live in the rulebook, not here; the Frame holds only what is case-specific.

2 · Layout

Question: how is the frame divided into regions, and what is their priority/hierarchy? (Zones only — no content yet.)

Form: an annotated ASCII region sketch — labelled boxes with a one-line priority/behavior note per zone.

┌───────────────────────────────┐
│ A  <zone name>                 │  ← <priority / behavior note>
├───────────────────────────────┤
│ B  <zone name>                 │  ← <note>
│                               │
├───────────────────────────────┤
│ C  <zone name>                 │  ← <note>
└───────────────────────────────┘

Key distinctions: draw.io was trialled and dropped — it added no value over ASCII for a region sketch (light-canvas island, static, poor diffs). Keep the sketch compact; a derived structural decision (e.g. "headers collapse") can ride as an annotation or a short callout.

3 · Elements

Question: what concrete components fill each region, which are shared, and what is each one's reusability tier?

Form: a tiered component catalog — a placement/composition tree (ties back to Layout zones) plus a one-row-per-distinct-component table. Interactive linking (click a node → highlight its row) is nice-to-have; the columns are the substance.

Tree (placement + composition; mark recurring components):
  panel
  ├─ <zone A> ── <component> · <component>
  └─ <zone B> ── <shared component ◆> · <composition ▣>
        <▣ composition> = <part> · <part> · <shared component ◆>
ComponentWhat it isUsed inTier
<name><role><zone(s) — two = shared><T0–T4> — <reuse note / customization / propose-new>

T4 break-down (per composition): <composition> → <lower-tier part (tier)> · <part (tier)> …

Key distinctions: the T1↔T2 split is exactly business logic (primitive = presentation only; widget = carries logic). A component in two zones is a reuse; "used in" surfaces it. A T4 composition is built local and broken down — its lower-tier parts are the real registry seeds. With the collection empty (W1), every T1/T2 verdict is a propose-new proposal, not a lookup.

4 · Interaction

Question: what does the user actually do with this screen? (The use-cases — not each element's default states.)

Form: a use-case table, each row grounded in a Frame goal, giving the user's action and the screen's response.

Use caseGoalUser doesScreen responds
<task><Frame goal><trigger / action><coordinated response across elements>

Key distinctions: per-element default interaction (hover/focus/confirm/tones) belongs to the component (the registry), not here — do not re-list it. State handling folds in as use-cases ("watch a live call" is the in-flight state); a state with no defined screen response (e.g. an error the domain never designed) surfaces as a use-case gap — a real finding, not something to invent.

5 · Draft mockup

Question: assembled, does it hold together as one screen?

Form: a native HTML/CSS build — dark tokens, real widgets, and stateful (a toggle to show empty / in-flight / error). The finish line: lo-fi and structural, not hi-fi. It is a real build, so it is a truer test than a picture of one.

<div class="mock">
  <div class="bar"><!-- identity zone: primary outcome, fixed --></div>
  <div class="sec"><!-- zone: label + content --></div>
  <div class="sec">
    <!-- use .complete-only / .inflight-only for state variants -->
  </div>
</div>
<button class="statebtn">toggle state</button>
<!-- styles: var(--paper/--line/--ink/--muted/--ok); ~15-line JS toggles a class -->

Key distinctions: the mockup is a decision stage, not mere assembly — building it in real HTML forces details the earlier stages never surfaced (e.g. click-to-copy on long values, per-body copy affordances, raw-vs-decoded semantics, collapsible sections). A static picture (ASCII / draw.io) lets those slide. Prefer native <details>/inputs over hand-rolled widgets.

6 · Tune

Question: stepping back from the whole, what grouping, hierarchy, or redundancy is off — and why?

Form: a short before/after list; may loop back to Layout.

<aspect>. Before: <what it was>. After: <the change> — <why>.
<aspect>. Before: … After: … (loops back to Layout: <yes/no>)

Key distinctions: Tune is load-bearing — in the run it genuinely sent design back to Layout, so it earns a distinct stage. Every tune call ("hero", "weight", "proximity") is a soft judgment that should cite a rulebook soft-rule, or it is pure vibes.

Provenance & what feeds the rest of the epic

This spec was distilled from a single hand-run (dflow-run-1.html, the flow-detail panel). That run also produced two seed lists this doc deliberately does not hold — they belong downstream:

  • Component candidates → W2 registry (the tiered catalog's rows + T4 break-downs).
  • Rule candidates → W3 rulebook (hard: state declarations, mono-for-wire-data, tokens-not-hex, spacing scale; soft: wording, visual-weight, grouping, ordering).
  • Open flow gaps → W4 (Layout/Elements boundary; no escalation path for upstream-undefined states).

After W4 validates the flow against the seeded substrate, this becomes the T1 design-flow process doc (sibling to workflow.html / testing-strategy.html).
