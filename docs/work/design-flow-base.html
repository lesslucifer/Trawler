Design flow — base spec & templates

The staged flow an AI agent follows to design a screen, with a copy-paste artifact template per stage. Screen-agnostic: the reusable method, not one design. Worked examples: run #1 (bare flow, W1) · run #2 (against the registry + rulebook, W4).

What this is

The written base flow: six stages, each with the concrete artifact template a real run converged on, plus the conventions that make an artifact reviewable. W1 produced the first cut from a bare hand-run; W4 wired it to the substrate — the design now consumes the component registry (reuse-or-propose per element) and the design rulebook (rules cited per stage, all slugs receipted at the end) — and re-ran it on the flow detail panel (run #2). It is distilled into the T1 process doc at epic distillation; until then it lives here in T3.

Principles (apply to every stage)

  • Load the substrate before stage 1. The registry index (the whole component vocabulary in one file) and the rulebook are inputs, read once at the start and never edited mid-run — a run that changes the rules it is judged by proves nothing. The versions read are named in the receipt.
  • Representation is load-bearing — optimize for human perception. The reviewer is the bottleneck. Every artifact is picture- or table-first; prose is demoted to a compact reference. Walls of text and over-dense diagrams (mindmaps) failed review in the run. When a form isn't obvious, pick it by comparison (a throwaway side-by-side doc), don't assume.
  • Cite by name, not coded ids. Drivers are cited by driver name, rules by slug, components by component name; the harness coverage-checks the named rows. Coded ids (G1/C2/…) were tried and dropped as noise.
  • Reuse-or-propose, fit-first. Every element resolves to reuse (cite the component), extend (the component grows — never fork a copy), or propose (a new design file, tiered). Fit is judged against the entry's @use/@avoid: forcing a component past its @avoid line is a propose, not a reuse.
  • Never re-decide what a component owns. A component's states, tones, hover/focus, microcopy and internal layout are its design file's truth; the screen cites them and never restates them (restating is duplication down a tier — the doc-system rule). The screen decides only placement, composition, and the coordinated response across components.
  • Compose the artifacts, not just the components. A design file's specimen CSS is the component's rendering, and a run doc links it (components/specimen.css) instead of re-typing its values; the doc behaviours a run needs — the keyed element map, the mockup's state switch — come from components/specimen.js instead of a fresh script per doc. Re-typing either is how a run silently forks the registry while claiming to reuse it, and it is invisible at review time because the copy looks deliberate.
  • Every convention here is machine-checked — the checker is the truth, this page is the reading copy. A run doc declares data-artifact="design-run" and tags its nine items; cargo xtask verify-doc then reds it on every write (PostToolUse) and at every turn end (Stop). What it checks: the nine items non-empty · the receipt's soft-rule coverage against the live rulebook, verdict enum and citations · a keyed data-map at Elements · a state toggle in the mockup · both shared specimens linked · zero colour literals in the doc's own CSS · the Frame's density. A rule an agent must remember is a rule an agent forgets — the three defects this flow has actually shipped (a lost element map, a re-typed component sheet, a Frame of paragraphs) all happened after the wording existed.
  • Findings live in one table, tagged by stage — never as prose inside a stage. A stage carries its artifact and stops. Per-stage commentary duplicates the findings roll-up in the most verbose form available, and the reviewer reads the same thing twice.
  • Nothing rides on taste alone. Every structural call cites a Frame driver; every judgment call ("weight", "grouping", "hero") cites a soft-rule slug. A call that can cite neither is a finding — either the design is arbitrary or the rulebook has a hole.
  • One artifact per stage, cheapest commitment first. Each stage's artifact is the next stage's input. Stages loop back — Elements → Layout (a component contract breaks the zoning) and Tune → Layout (the assembled whole reads wrong); both loops are real, not decorative.
  • Gaps escalate, they are never invented. Anything the design cannot decide because something upstream is missing — an undesigned domain state, a token that does not exist, a capability the API lacks — goes on the run's blocked-on list with its owner. The flow never quietly fills an upstream hole.

The stages

Which rules bind where is the rulebook's own Binds at column — read it there, per stage, and never copy the list into a run or into this spec (one fact, one home). Each stage below names only how it consumes the substrate.

1 · Frame

data-item="frame"

Question: who reads this screen and in what context, what job does it do, what are its ranked goals, hard constraints, and experience qualities? (The screen's functional capabilities — what it must be able to do — are an input, not the output.)

Form: a driver table — driver → why → therefore → on this screen; the row is the reasoning, and it lands on a concrete ✓/✗ pair. Grouped Goals / Constraints / Qualities; no coded ids. Every cell is a clause, not a sentence, and never a paragraph: a Frame that reads as prose has stopped being a table and nobody reads it. The purpose line is one sentence; each capability list is one ·-separated line.

Why the row ends in an example (revised at run #3). The first three cells are all abstractions, and three abstractions in a row do not tell a reviewer whether the design is right — run #3's Frame was rewritten to clause density, passed every predicate, and was still hard to read. The on this screen cell is the row's only concrete artifact: the ✓ names the thing that honours the driver, the ✗ names the plausible thing that breaks it. It replaces the old checked by column (an observable criterion), which stated the test abstractly where the pair now shows it — and the ✗ does work the criterion never did, by naming the failure the design is actually at risk of. The pattern is the rulebook's own DO/DON'T cell, which has held up across 14 soft rules.

Density is machine-checked — run #3 wrote a Frame at 2.5× the accepted density (mean 17.9 words per cell against run #2's 9.0, plus two commentary blocks that were not artifacts) with every word of the rule above already on this page. Six predicates, on two budgets: the three reasoning columns are held to one clause, the ✓/✗ pair to two.

Key distinctions: Not given is a first-class line, not an omission — a screen is shaped as hard by what it cannot observe as by what it can (run #3: no remote probe, no per-device attribution, no reason for a failed handshake), and an absence left unwritten gets silently invented downstream. Functional requirements are the input; the Frame's output is the design lens (goals become hierarchy, qualities become Tune's yardstick). The on this screen pair is screen-specific and falsifiable, never a restatement: "✓ clear hierarchy / ✗ unclear hierarchy" is noise, and a ✗ nobody would plausibly build is a strawman that makes a weak driver look tested. Write the ✗ someone would ship. Anything the rulebook already binds is not a driver (a11y, spacing, wrapping, state handling, calm microcopy, zero accent): the Frame holds only what is case-specific, and a quality that merely restates a soft rule is deleted, not written. A quality survives when it says which instance of a generic rule matters most here ("the leg boundary is this panel's strongest seam"). A substrate constraint is a first-class constraint row: a component contract the screen must design around (e.g. "Section must not nest") belongs in the table with the registry file as its "why".

2 · Layout

data-item="layout"

Question: how is the frame divided into regions, and what is their priority/hierarchy? (Zones only — no content yet.)

Form: an annotated ASCII region sketch — labelled boxes with a one-line priority/behavior note per zone.

┌───────────────────────────────┐
│ A  <zone name>                 │  ← <priority / behavior note>
├───────────────────────────────┤
│ B  <zone name>                 │  ← <note>
│                               │
├───────────────────────────────┤
│ C  <zone name>                 │  ← <note>
└───────────────────────────────┘

scroll / overflow: <which zone is pinned · which region scrolls · every
                   unbounded zone's cap and who owns it>

Key distinctions: draw.io was trialled and dropped — it added no value over ASCII for a region sketch (light-canvas island, static, poor diffs). Keep the sketch compact; a derived structural decision (e.g. "headers scroll-cap so the body stays reachable") rides as an annotation or a short callout. The overflow line under the sketch is not decoration — it is what overflow-declared checks, and a cap owned by a component is declared here by reference ("HeaderTable's rows cap").

3 · Elements

data-item="elements" — the same element carries data-map

Question: what concrete components fill each region, and for each one — does the registry already have it?

Form: a tiered component catalog — a placement/composition tree (ties back to Layout zones) plus a one-row-per-distinct-component table whose load-bearing column is the registry verdict: reuse · extend · propose. This is the reuse-or-propose pass; the registry index is read here, once, and every row resolves against it. The tree and the table are one keyed artifact, not two: wrap both in data-map and give every component mention data-key="<component-file-slug>", so one click lights every appearance and a reuse is visible rather than asserted. Both halves are checked (tightened at run #3, which shipped an inert map): a key must appear in the tree and in the catalog, and a component placed in the tree with no catalog row is red — it never faced the reuse-or-propose pass. The highlight styling lives in specimen.css, so a run that loads specimen.js alone is clickable and dead. The behaviour comes from components/specimen.js — never re-implemented per doc.

Key distinctions: the T1↔T2 split is exactly business logic (primitive = presentation only; widget = carries logic). A component in two zones is a reuse; the placement line surfaces it. Tier · verdict · placement share one cell — three one-token columns cost more width than they carry, and the verdict reads better against its tier. Colour @use and @avoid in the Fit column (ok / warn): the whole column is contract quotation, and which side a quote is on is the fastest thing a reviewer needs. A T4 composition is built local and broken down — its lower-tier parts are the real registry entries. The Shape sketch is reference only (added at run #3): a few lines of ASCII so a reader can tell what a row is without opening its file — it binds nothing, and the component's design file wins any disagreement. For a proposal that file does not exist yet, so the sketch is the reviewer's only picture and is worth the most there. The States column is filled by reference, never by re-listing what the component's design file already owns — a bare citation is a complete cell, and the screen writes states only for a proposed component or for a state the screen itself coordinates. An @avoid hit is the stage's most valuable output: it means the design wants something the vocabulary does not have, so the verdict flips to extend/propose and the row carries the reason. This stage is also the most common source of a loop back to Layout — a component contract (nesting, self-labelling, an absent state) can make the zoning unbuildable, and the honest move is to re-zone, not to bend the contract silently.

4 · Interaction

data-item="interaction"

Question: what does the user actually do with this screen? (The use-cases — not each element's default states.)

Form: a use-case table, each row grounded in a Frame goal, giving the user's action and the screen's response.

Use caseGoalUser doesScreen respondsKeyboard path
<task><Frame goal><trigger / action><coordinated response across elements><the keys, from the rulebook's keyboard conventions — or "proposed: <keys>" when the vocabulary has no entry>

Key distinctions: per-element default interaction (hover/focus/confirm/tones) belongs to the component (the registry), not here — do not re-list it. State handling folds in as use-cases ("watch a live call" is the in-flight state); a state with no defined screen response (e.g. an error the domain never designed) is a blocked-on entry, never something to invent. The keyboard column exists because keyboard-parity is checked per row: a pointer-only row is a red row, and a key that the conventions vocabulary does not yet hold is a proposal — a design that silently coins a binding is exactly what the vocabulary exists to stop.

5 · Draft mockup

data-item="mockup" — the tagged element contains the state toggle

Question: assembled, does it hold together as one screen?

Form: a native HTML/CSS build assembled from the component design files' own specimen CSS — link components/specimen.css (the single extraction of every design file: app tokens plus one block per component) and mark the build up with their class names. Real widgets, and stateful (a toggle across the states the Interaction table named, from components/specimen.js). The finish line: lo-fi and structural, not hi-fi. It is a real build, so it is a truer test than a picture of one.

Key distinctions: the mockup is a decision stage, not mere assembly — building it in real HTML forces details the earlier stages never surfaced (click-to-copy on long values, per-body copy affordances, raw-vs-decoded semantics, where a cap bites). A static picture (ASCII / draw.io) lets those slide. Prefer native <details>/inputs over hand-rolled widgets. The hard token rules are checked here, which is why no value is ever typed twice: the tokens live in specimen.css and the mockup only ever writes var(--a-…). Re-typing a component's values is not a shortcut, it is a silent fork — the mockup then looks compliant while rendering something the registry never agreed to, and a rule the component breaks turns green because the mockup quietly fixed it on the way in (both happened, once each, before this rule existed). When a component's specimen CSS contradicts its own token table, or two files draw the same thing differently, compose it as drawn and file the conflict — the mockup is not the place to pick a winner. A component whose design file demands a token that does not exist yet cannot be mocked honestly — render its documented fallback and put the missing token on the blocked-on list. Build what the screen decides, stub what a component owns: zones, seams, labels, caps and every state the Interaction table named are real in the mockup; a component's internals (a code surface, a live clipboard, a renderer family) are a static stand-in — the same scale-down rule the component design format uses for its specimens. Reimplementing a component in the mockup wastes the run and invites the mockup to contradict the registry.

6 · Tune

data-item="tune"

Question: stepping back from the whole, what grouping, hierarchy, or redundancy is off — and why?

Form: a short before/after list; may loop back to Layout.

<aspect>. Before: <what it was>. After: <the change> — <why>. [<soft-rule slug>]
<aspect>. Before: … After: … [<slug>] (loops back to Layout: <yes/no>)

Key distinctions: Tune is load-bearing — it has genuinely sent design back to Layout, so it earns a distinct stage. Every tune call cites a soft-rule slug ("hero", "weight", "proximity" are not reasons); a call with no slug to cite is a rulebook hole and goes to the findings, not into the design. Conversely a soft rule that never gets cited across a whole run is a kill candidate — the receipt makes that visible.

Closing artifacts — receipt · proposals · blocked-on

A run ends with three lists, not with the mockup. They are what a reviewer and (from W7) the harness consume; the design itself is only the first half of the deliverable.

ListOne row per…Row shape
Receipt — data-item="receipt", a <pre> of YAML, machine-readevery soft slug in the rulebook, in rulebook order. Hard rules are never receipted — a rule with a Tier-1 predicate is judged by the predicate; a hand verdict on it is the one row that can be wrong for free, and a hard slug in the receipt is a red
rulebook: <blob sha>
soft:
  <slug>: <verdict> — <one clause of evidence>
verdict ∈ satisfied · inherited (a component owns it — the citation is the proof) · satisfied-via-proposal (only an entry that does not exist yet closes it) · n/a · blocked (unsatisfiable as specified — name what is missing) · violated · violated-inherited (a component the screen composes and may not re-author breaks it). One line per slug; the why is a clause, and the tally is computed, never typed
Proposalsevery entry the design needed and the vocabulary lackedkind (component · component extension · token · lexicon term · key binding) · what · why nothing existing fits · owner
Blocked-onevery decision the design could not make because something upstream is missingwhat is missing · which stage hit it · whose call it is (domain/UX · API · build WU) · what the run did meanwhile

Why forced coverage: a receipt that only lists the rules the design happened to think about proves nothing — the value is the row that reads n/a or violated, because that is where the rulebook is wrong or the design is. inherited is a first-class verdict, not a dodge: most component-level rules are satisfied by reusing the component, and the citation is the proof. Coverage is checked against the rulebook on disk, so adding or killing a rule re-opens every receipt; a receipt that cannot be checked (unreadable rulebook) is red, never silently green.

Why the hard/soft split: the receipt exists for what a machine cannot judge. Run #2 wrote satisfied against spacing-scale while its mockup re-typed three components' padding on-scale — the claim was false, the citation was fluent, and only composing the real CSS caught it. Hard rules therefore leave the receipt and become predicates; each one still unimplemented is printed on every verify (hard rules: n/13 machine-checked) so the gap stays visible instead of becoming a forgotten follow-up.
