Design flow — base spec & templates

The staged flow an AI agent follows to design a screen, with a copy-paste artifact template per stage. Screen-agnostic: the reusable method, not one design. Worked examples: run #1 (bare flow, W1) · run #2 (against the registry + rulebook, W4).

What this is

The written base flow: six stages, a close and an independent review, each with the concrete artifact template a real run converged on, plus the conventions that make an artifact reviewable. W1 produced the first cut from a bare hand-run; W4 wired it to the substrate — the design now consumes the component registry (reuse-or-propose per element) and the design rulebook (rules cited per stage, all slugs receipted at the end) — and re-ran it on the flow detail panel (run #2). It is distilled into the T1 process doc at epic distillation; until then it lives here in T3.

A flow only its author can drive is not a flow. Each command below is named again at the stage that needs it; this table is the single place they are all together, so a run can be started from here without reading the rest first.

Principles (apply to every stage)

  • Load the substrate before stage 1. The registry index (the whole component vocabulary in one file) and the rulebook are inputs, read once at the start and never edited mid-run — a run that changes the rules it is judged by proves nothing. The versions read are named in the receipt.
  • Representation is load-bearing — optimize for human perception. The reviewer is the bottleneck. Every artifact is picture- or table-first; prose is demoted to a compact reference. Walls of text and over-dense diagrams (mindmaps) failed review in the run. When a form isn't obvious, pick it by comparison (a throwaway side-by-side doc), don't assume.
  • State the conclusion, collapse the proof. A run doc has two readers — an agent that needs the whole trace, and a human who needs the verdict — and the trace is attestation, not communication. Run #3's reviewer said it of three sections at once: "we just need to write it so the AI agent considers it… I rarely read it." So every dense cell is a one-line <div class="gist"> with the reasoning behind <details class="why">: the Elements @use/@avoid trace, the Interaction per-zone deltas, the receipt, the hard-rules table. Nothing is deleted — the reuse-or-propose pass is worthless unattested and the receipt is machine-parsed — it just stops being the reading surface. Checked: elements·gist and interaction·gist red a row with no gist, a row that collapses nothing, and a gist over 14 words (the regression: the trace written straight into the visible column). A defect that lives only in collapsed evidence is a defect nobody reads — promote it to a finding, as run #3 had to for its spacing-scale breach.
  • Cite by name, not coded ids. Drivers are cited by driver name, rules by slug, components by component name; the harness coverage-checks the named rows. Coded ids (G1/C2/…) were tried and dropped as noise.
  • Reuse-or-propose, fit-first. Every element resolves to reuse (cite the component), extend (the component grows — never fork a copy), or propose (a new design file, tiered). Fit is judged against the entry's @use/@avoid: forcing a component past its @avoid line is a propose, not a reuse. Read @avoid first (added at run #3, which shipped a wrong reuse for a whole stage): the pass is a rejection test, not a matching test. A @use line describes the action and matches easily — run #3 cited CopyButton's "any one-click copy affordance" correctly while both CopyButton's and CopyText's @avoid lines partitioned the space against it. Where two components name each other in their @avoids, that pair is the discriminator, and a fluent @use citation is not evidence of fit.
  • Never re-decide what a component owns. A component's states, tones, hover/focus, microcopy and internal layout are its design file's truth; the screen cites them and never restates them (restating is duplication down a tier — the doc-system rule). The screen decides only placement, composition, and the coordinated response across components.
  • Compose the artifacts, not just the components. A design file's specimen is written in the app's own Tailwind utilities, and a run doc loads the same theme (doc-assets/components/tw-config.js, importing the app config) and reuses those class strings instead of re-typing values; the doc behaviours a run needs — the keyed element map, the mockup's state switch — come from doc-assets/components/specimen.js instead of a fresh script per doc. Re-typing either is how a run silently forks the registry while claiming to reuse it, and it is invisible at review time because the copy looks deliberate.
  • Every convention here is machine-checked — the checker is the truth, this page is the reading copy. A run doc declares data-artifact="design-run" and tags its eleven items; cargo xtask verify-doc then reds it on every write (PostToolUse) and at every turn end (Stop). What it checks: the eleven items non-empty · the receipt's soft-rule coverage against the live rulebook, verdict enum and citations · the rulebook pin against the rulebook on disk · every reviewer instruction naming what it moved and the contract it hit · a keyed data-map at Elements · every reuse citing an @avoid · a gist + collapsed trace per catalog and use-case row · Tune drawn and slug-cited · every Given capability answered · a state toggle in the mockup · both shared specimens linked · zero colour literals in the doc's own CSS · the Frame's density. A rule an agent must remember is a rule an agent forgets — the three defects this flow has actually shipped (a lost element map, a re-typed component sheet, a Frame of paragraphs) all happened after the wording existed. Every predicate reads the live rule set, so tightening a stage's form re-opens closed runs — run #3's checks red runs #1 and #2, which are records of what the flow was rather than work anyone will redo. A finished run therefore carries data-status="archived", which exempts it for the opposite reason to draft: finished under an older contract, not unfinished. A run still open is never archived — that hides exactly the reds the flow exists to surface. A finished one is archived when it finishes, newest included: waiting for a later run to replace it as the reference is what left run #3 red in the tree for two Working Units, because closing a run was nobody's step. It is step 7 now, and 6·run-closed refuses the merge of a Working Unit that carried a run it never closed. The pins that read a real artifact lift the flag themselves and assert the lift changed something, so an archived run cannot make them pass vacuously — the day one stops being archived, the pin fails instead of going quiet.
  • Findings live in one table, tagged by stage — never as prose inside a stage. A stage carries its artifact and stops. Per-stage commentary duplicates the findings roll-up in the most verbose form available, and the reviewer reads the same thing twice.
  • Nothing rides on taste alone. Every structural call cites a Frame driver; every judgment call ("weight", "grouping", "hero") cites a soft-rule slug. A call that can cite neither is a finding — either the design is arbitrary or the rulebook has a hole.
  • One artifact per stage, cheapest commitment first. Each stage's artifact is the next stage's input. Stages loop back — Elements → Layout (a component contract breaks the zoning) and Tune → Layout (the assembled whole reads wrong); both loops are real, not decorative.
  • Gaps escalate, they are never invented. Anything the design cannot decide because something upstream is missing — an undesigned domain state, a token that does not exist, a capability the API lacks — goes on the run's blocked-on list with its owner. The flow never quietly fills an upstream hole.

The stages

Which rules bind where is the rulebook's own Binds at column — read it there, per stage, and never copy the list into a run or into this spec (one fact, one home). Each stage below names only how it consumes the substrate.

1 · Frame

data-item="frame"

Question: who reads this screen and in what context, what job does it do, what are its ranked goals, hard constraints, and experience qualities? (The screen's functional capabilities — what it must be able to do — are an input, not the output.)

Form: a driver table — driver → why → therefore → on this screen; the row is the reasoning, and it lands on a concrete ✓/✗ pair. Grouped Goals / Constraints / Qualities; no coded ids. Every cell is a clause, not a sentence, and never a paragraph: a Frame that reads as prose has stopped being a table and nobody reads it. The purpose line is one sentence; each capability list is one ·-separated line.

Why the row ends in an example (revised at run #3). The first three cells are all abstractions, and three abstractions in a row do not tell a reviewer whether the design is right — run #3's Frame was rewritten to clause density, passed every predicate, and was still hard to read. The on this screen cell is the row's only concrete artifact: the ✓ names the thing that honours the driver, the ✗ names the plausible thing that breaks it. It replaces the old checked by column (an observable criterion), which stated the test abstractly where the pair now shows it — and the ✗ does work the criterion never did, by naming the failure the design is actually at risk of. The pattern is the rulebook's own DO/DON'T cell, which has held up across 14 soft rules.

Density is machine-checked — run #3 wrote a Frame at 2.5× the accepted density (mean 17.9 words per cell against run #2's 9.0, plus two commentary blocks that were not artifacts) with every word of the rule above already on this page. Six predicates, on two budgets: the three reasoning columns are held to one clause, the ✓/✗ pair to two.

The other stage tables drift the same way and are candidates for the same treatment once there is an accepted run to calibrate each against — a threshold picked without one is the checker's taste, not the flow's rule.

Key distinctions: Not given is a first-class line, not an omission — a screen is shaped as hard by what it cannot observe as by what it can (run #3: no remote probe, no per-device attribution, no reason for a failed handshake), and an absence left unwritten gets silently invented downstream. Functional requirements are the input; the Frame's output is the design lens (goals become hierarchy, qualities become Tune's yardstick). The on this screen pair is screen-specific and falsifiable, never a restatement: "✓ clear hierarchy / ✗ unclear hierarchy" is noise, and a ✗ nobody would plausibly build is a strawman that makes a weak driver look tested. Write the ✗ someone would ship. Anything the rulebook already binds is not a driver (a11y, spacing, wrapping, state handling, calm microcopy, zero accent): the Frame holds only what is case-specific, and a quality that merely restates a soft rule is deleted, not written. A quality survives when it says which instance of a generic rule matters most here ("the leg boundary is this panel's strongest seam"). A substrate constraint is a first-class constraint row: a component contract the screen must design around (e.g. "Section must not nest") belongs in the table with the registry file as its "why".

Every Given capability is answered by the end of the run (added at run #3, which lost one). A capability received at the Frame can be written down and then silently dropped two stages later with every gate green: run #3 listed proxy unset as an elevated app action, then designed its undo zone as copyable commands only and filed a blocked-on entry claiming the app cannot reverse its own writes — which the shipped code disproved. The receipt forces coverage of rules; nothing forced coverage of capabilities. So each Given item ends the run in one of three states: used (name where), deliberately unused (say why — a non-goal, a case the screen does not serve), or blocked. An unmentioned Given is the same defect class as an unreceipted rule, and it is worse in one way: a dropped capability makes the design look correctly constrained rather than under-designed.

2 · Layout

data-item="layout"

Question: how is the frame divided into regions, and what is their priority/hierarchy? (Zones only — no content yet.)

Form: an annotated ASCII region sketch — labelled boxes with a one-line priority/behavior note per zone.

┌───────────────────────────────┐
│ A  <zone name>                 │  ← <priority / behavior note>
├───────────────────────────────┤
│ B  <zone name>                 │  ← <note>
│                               │
├───────────────────────────────┤
│ C  <zone name>                 │  ← <note>
└───────────────────────────────┘

scroll / overflow: <which zone is pinned · which region scrolls · every
                   unbounded zone's cap and who owns it>

Key distinctions: draw.io was trialled and dropped — it added no value over ASCII for a region sketch (light-canvas island, static, poor diffs). Keep the sketch compact; a derived structural decision (e.g. "headers scroll-cap so the body stays reachable") rides as an annotation or a short callout. The overflow line under the sketch is not decoration — it is what overflow-declared checks, and a cap owned by a component is declared here by reference ("HeaderTable's rows cap").

3 · Elements

data-item="elements" — the same element carries data-map

Question: what concrete components fill each region, and for each one — does the registry already have it?

Form: a tiered component catalog — a placement/composition tree (ties back to Layout zones) plus a one-row-per-distinct-component table whose load-bearing column is the registry verdict: reuse · extend · propose. This is the reuse-or-propose pass; the registry index is read here, once, and every row resolves against it. The tree and the table are one keyed artifact, not two: wrap both in data-map and give every component mention data-key="<component-file-slug>", so one click lights every appearance and a reuse is visible rather than asserted. Both halves are checked (tightened at run #3, which shipped an inert map): a key must appear in the tree and in the catalog, and a component placed in the tree with no catalog row is red — it never faced the reuse-or-propose pass. The highlight styling ships inside specimen.js itself, so loading the behaviour is enough. The behaviour comes from doc-assets/components/specimen.js — never re-implemented per doc.

Key distinctions: the T1↔T2 split is exactly business logic (primitive = presentation only; widget = carries logic). A component in two zones is a reuse; the placement line surfaces it. Tier · verdict · placement share one cell — three one-token columns cost more width than they carry, and the verdict reads better against its tier. Colour @use and @avoid in the Fit column (ok / warn): the whole column is contract quotation, and which side a quote is on is the fastest thing a reviewer needs. A T4 composition is built local and broken down — its lower-tier parts are the real registry entries. The Shape sketch is reference only (added at run #3): a few lines of ASCII so a reader can tell what a row is without opening its file — it binds nothing, and the component's design file wins any disagreement. For a proposal that file does not exist yet, so the sketch is the reviewer's only picture and is worth the most there. The States column is filled by reference, never by re-listing what the component's design file already owns — a bare citation is a complete cell, and the screen writes states only for a proposed component or for a state the screen itself coordinates. An @avoid hit is the stage's most valuable output: it means the design wants something the vocabulary does not have, so the verdict flips to extend/propose and the row carries the reason. This stage is also the most common source of a loop back to Layout — a component contract (nesting, self-labelling, an absent state) can make the zoning unbuildable, and the honest move is to re-zone, not to bend the contract silently.

4 · Interaction

data-item="interaction"

Question: what does the user actually do with this screen? (The use-cases — not each element's default states.)

Form: a use-case table, each row grounded in a Frame goal, giving the user's action and the screen's response. The response is zone → delta lines, never prose (added at run #3, whose prose version hid the coordination): the column exists to show which zones change together, and a paragraph buries exactly that. One line per affected zone, UNCHANGED spelled out where not-changing is the decision, and a trailing ← note only where the delta carries a judgment. Prose after the block is fine for the one clause a reader cannot infer.

Use caseGoalUser doesScreen respondsKeyboard path
<task><Frame goal><trigger / action>
<zone> → <delta>
<zone> → <delta>   ← <why, only where it is a decision>
<zone> → UNCHANGED  <when that is the point>
<the keys, from the rulebook's keyboard conventions — or "proposed: <keys>" when the vocabulary has no entry>

Key distinctions: per-element default interaction (hover/focus/confirm/tones) belongs to the component (the registry), not here — do not re-list it. State handling folds in as use-cases ("watch a live call" is the in-flight state); a state with no defined screen response (e.g. an error the domain never designed) is a blocked-on entry, never something to invent. The keyboard column exists because keyboard-parity is checked per row: a pointer-only row is a red row, and a key that the conventions vocabulary does not yet hold is a proposal — a design that silently coins a binding is exactly what the vocabulary exists to stop.

5 · Draft mockup

data-item="mockup" — the tagged element contains the state toggle

Question: assembled, does it hold together as one screen?

Form: a native HTML build assembled in the app's own Tailwind — load the CDN plus doc-assets/components/tw-config.js (which imports ui/tailwind.config.js directly, so a specimen and its component are written in the same class names) and mark the build up with the utility strings the component design files draw. Real widgets, and stateful (a toggle across the states the Interaction table named, from doc-assets/components/specimen.js). The finish line: lo-fi and structural, not hi-fi. It is a real build, so it is a truer test than a picture of one.

Key distinctions: the mockup is a decision stage, not mere assembly — building it in real HTML forces details the earlier stages never surfaced (click-to-copy on long values, per-body copy affordances, raw-vs-decoded semantics, where a cap bites). A static picture (ASCII / draw.io) lets those slide. Prefer native <details>/inputs over hand-rolled widgets. The hard token rules are checked here, which is why no value is ever typed twice: the tokens live in ui/tailwind.config.js and the mockup only ever writes their utility names. Re-typing a component's values is not a shortcut, it is a silent fork — the mockup then looks compliant while rendering something the registry never agreed to, and a rule the component breaks turns green because the mockup quietly fixed it on the way in (both happened, once each, before this rule existed). When a component's specimen contradicts its own token table, or two files draw the same thing differently, compose it as drawn and file the conflict — the mockup is not the place to pick a winner. A component whose design file demands a token that does not exist yet cannot be mocked honestly — render its documented fallback and put the missing token on the blocked-on list. Build what the screen decides, stub what a component owns: zones, seams, labels, caps and every state the Interaction table named are real in the mockup; a component's internals (a code surface, a live clipboard, a renderer family) are a static stand-in — the same scale-down rule the component design format uses for its specimens. Reimplementing a component in the mockup wastes the run and invites the mockup to contradict the registry.

6 · Tune

data-item="tune"

Question: stepping back from the whole, what grouping, hierarchy, or redundancy is off — and why?

Form: a short before/after list; may loop back to Layout.

<table data-item="tune">   one row per call — before and after are DRAWN
| Call        | Before                | After                 | Slug        |
| <aspect>    | <pre class="tb">      | <pre class="tb">      | <code>slug |
|             |  the old rendering  ‾ |  the new rendering  ‾ |  <code>slug |

<details class="why"> one <li> per call: why, and loops back to Layout: yes/no

Form: before and after are drawn, never described (added at run #3, whose prose version needed three sentences to say what a ragged column and an aligned one show at a glance). Tune judges how the screen looks; ASCII in two adjacent <pre class="tb"> cells makes the change the content. The reasoning collapses behind one ▸ why. Checked: tune·drawn reds a row with fewer than two drawn cells, a row citing no slug, and a Tune stage that is prose instead of a table.

Key distinctions: Tune is load-bearing — it has genuinely sent design back to Layout, so it earns a distinct stage. Every tune call cites a soft-rule slug ("hero", "weight", "proximity" are not reasons); a call with no slug to cite is a rulebook hole and goes to the findings, not into the design. Conversely a soft rule that never gets cited across a whole run is a kill candidate — the receipt makes that visible.

Closing artifacts — receipt · capabilities · proposals · blocked-on · review

Why forced coverage: a receipt that only lists the rules the design happened to think about proves nothing — the value is the row that reads n/a or violated, because that is where the rulebook is wrong or the design is. inherited is a first-class verdict, not a dodge: most component-level rules are satisfied by reusing the component, and the citation is the proof. Coverage is checked against the rulebook on disk, so adding or killing a rule re-opens every receipt; a receipt that cannot be checked (unreadable rulebook) is red, never silently green.

Why the hard/soft split: the receipt exists for what a machine cannot judge. Run #2 wrote satisfied against spacing-scale while its mockup re-typed three components' padding on-scale — the claim was false, the citation was fluent, and only composing the real CSS caught it. Hard rules therefore leave the receipt and become predicates; each one still unimplemented is printed on every verify (hard rules: n/m machine-checked, counted off the rulebook) so the gap stays visible instead of becoming a forgotten follow-up.

When a new predicate reds an artifact, the artifact is the suspect (added at run #3, which did the opposite). This run ended one capability "dropped, then recovered", the three-state check went red, and a fourth state was added to the checker in the same commit that introduced the rule — so the code disagreed with this spec and the gate rubber-stamped the exact defect it existed to catch. Code review caught it, the author did not. A predicate's vocabulary is closed on purpose: an outcome that does not fit is the run reporting something under-designed, and widening the check deletes that signal while leaving the gate green. Loosening a predicate is a rulebook change — it needs its own reasoning, never a same-commit accommodation of the artifact that tripped it.

7 · Close the run a step, not a side effect

Run #3 sat open and red in the tree for two Working Units because archiving happened as a side effect of the next run being written — and run #3 had no next run. Closing is therefore its own step, with its own gate.

#DoWhat refuses it
①Re-pin the rulebook. git hash-object docs/design-rules/design-rules-index.html; if it no longer matches the receipt's rulebook:, the rulebook moved under the run — re-judge every soft row against the current one before re-pinningreceipt·rulebook-stale names both versions. ②Fill the review item — one row per reviewer instruction, what it moved, the contract it hititem·review · review·recorded

④Archive it: data-status="archived" beside its data-artifact, in the commit that finishes the run — newest included, never waiting for a successor6·run-closed refuses the merge of any tip whose diff carries a run still open. A run genuinely mid-design across a merge declares data-status="draft" instead, which says unfinished rather than closed

Why the merge and not the working tree. A run mid-design is legitimately red for days, so a sweep asserting "every run is archived or green" would hold the suite hostage to work in progress. The merge is the first moment the tree is answerable for the run: the Working Unit that carried it is ending. archived then exempts the run from every later rule — finished under an older contract, not unfinished — which is why ③ has to happen before ④ and not after.

8 · The design review Tier-3 — the reviewer is not the author

Everything up to ⑦ is the designing agent judging its own work: the stages are its design, the receipt is its claim about that design, and the predicates check the claim's shape. The one thing missing is the rule the dev workflow has always had — never judge your own diff. So the closed run goes through the same door code goes through: the design dimension of the code review, which fires on the merge that lands it.

How
What activates it cargo xtask design-scope <base> <head> — a closed run (data-status="archived") or a component design file in the diff. A draft run is unfinished and is judged by the merge that closes it, so ⑦ and ⑧ are one motion
What it judges soft rules and the new-component warrant, on the artifact — not the built code, and not the thirteen hard rules Tier-1 already owns. The rubric is .claude/skills/code-review/design-rubric.md
What it catches that ⑦ cannot a receipt that is complete, fluent and false — a satisfied the design does not earn — and a component invented while an existing one fit. Both are defects the author wrote and then attested
Where the verdict lives the tip's cr/v3 note, in a design: section naming every artifact judged and pinning the rulebook blob. Not in the run doc: the run is retired under DEC-16 and the commit is not
What refuses it 9·design at the merge — a design-bearing tip whose note has no design section, skips an artifact, pins another rulebook, or carries a failing design verdict. A design-bearing diff is never docs-only-exempt: a design is a docs-only deliverable, and the exemption was handing this check exactly the diffs it exists to judge — W2 landed 14 component design files with no code review at all (found by the flow e2e)

Tier-2's receipt stays inline and Tier-3's verdict does not, and the asymmetry is the point: a self-claim is part of the artifact and dies with it, while an independent judgment is about a commit — and commits outlive the files they carry.

9 · Hand over to the build Tier-3 passed — now something gets built

A judged design is still nothing but a file. The hand-over is the step that makes it consumable, and it is short because everything it needs already exists: the closed run (or component design) is the artifact, its path and blob are the address, and the Working Unit that builds from it writes both into its own review note. One rule, three halves, and a life that ends at the epic.

HalfWhat it saysWhat refuses it
The build names its design a Working Unit whose diff adds a registry component (a file under ui/src/components/ carrying @tier) or a screen (a non-test .tsx under ui/src/ outside the collection, at any depth) cites what it built from: design.implements: [{path, blob, built}] in its cr/v3 note. The path resolves at the tip, the blob is the bytes the tip ships, the doc is a design artifact, a run it names is archived — an open run cannot be handed to anyone — and built names the files it produced, so a citation covers what it claims and no more 9·design at the WU merge
An edit answers for itself every other UI-rendering file the diff touches — any non-test .tsx under ui/src/ — is cited the same way or declared: design.undesigned: [{path, why}], an empty reason being no reason. This half demands a sentence, never a run: most UI work re-shapes what exists, and a gate that answered that with "go design it" would be routed around by lunchtime. What it refuses is the silence, which is the defect this flow keeps finding 9·design at the WU merge
No unbuilt design survives its epic every component design the epic added resolves to a roster entry at the epic tip — screens count, not only @tier components, so a screen design resolves where it was built — or the epic's note records design.dropped: [{path, why}]. This is DEC-16's retirement rule with its survival clause removed: a design file is retired into the code's TSDoc when built, dropped on the record when not, and never simply left standing components·unbuilt at the epic merge

The design is not the only thing that has to reach the build. A design run designs a screen, and a screen is where the flow's own screen-bound rules live — layout, grouping, ordering, disclosure. The hand-over therefore reaches every rendered file, not only the ones the collection knows about, and it reaches them whether they are new or being re-shaped.

Why the blob and not just the path. A path proves a file was named; a blob proves which bytes were read. It costs one field and buys the drift count for free — a build whose cited blob differs from the one its design Working Unit closed is a build that amended its design, countable over notes already written. The field is the monitor; no monitoring machinery exists.

When the build and its design come apartWhat is owed
an unforeseen small change while building one sentence. No run, no artifact, no stage: the file is named under design.undesigned with why it needed no design. The reviewer writes it, bound to the diff — it is a statement of fact, not a permission the build grants itself
the build amends the design it was handed nothing to remember. The amended file is a design artifact in that Working Unit's diff, so Tier-3 re-fires on the merge that lands it and the cited blob is the amended one. The re-judgment is automatic, not a rule anyone has to recall
a surface nobody designed, discovered mid-build the build Working Unit carries its own design, gated identically — it is a design WU and a build WU at once
Nothing judges the build against its design. The gate answers is there a design, and is it this one — never whether the code honoured it. The pointer is a mechanical check, not a judgment, and why — plus the one piece of evidence that would reopen it — is DEC-25's, not this spec's.

What proves the harness — the flow e2e xtask/tests/e2e_design_flow.rs

Every stage above is a rule an agent must follow and a predicate that refuses it, and the whole point is the sequence: no unit test can tell whether a run can be driven from a blank page to a landed merge. A fake designing agent emits one artifact at a time and a fake human answers each with a taste instruction; all three tiers then judge the result over a real git tree, real node oracles and the real merge hook. Feature-gated (--features design-e2e) out of the default suite — re-run it when the flow or the harness changes.
