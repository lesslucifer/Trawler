Review — when and where the setup instructions show

The setup screen that E-ONBOARD shipped, read for timing and placement: at which moments the screen appears, which instructions open, and which platforms get which steps. Twenty-two findings: seventeen reproduced against the real components, five traced in the code.

v3 · 2026-09-25 · R12 from the owner's report · R13–R22 from the state sweep · Trawler · T3 (docs/work/) · reviews main @ 1ec6f07 · input to the E-ONBREV plan · contract under review: UC-ONBOARD in web-ui.html

Verdict

The screen's content is right: truthful per platform, and the design of record holds. Its timing was designed for one moment only, a first run on a working core with an empty capture. Every other way in breaks at least one promise UC-ONBOARD makes. Those other ways in are a launch that is still checking, a core that is down, a capture holding imported or sent rows, coming back to set up a second device, and any state where a task's reading and the action offered for it disagree. Five root causes explain twenty of the twenty-two findings.

How the state sweep was run

After the owner's example (R12), every state the screen can be in was rendered and flattened into an outline: each task's state line, its buttons, its open or closed guides, and every block drawn between tasks. Each outline was then read against three rules. Place: an instruction sits inside the task it is for. Time: an action or step is offered only while its task is not read as done. Truth: no sentence contradicts a reading on the same screen.

Findings

Severity: High means the screen shows wrong or missing instructions to a user on a common path, or breaks a UC-ONBOARD guarantee. Medium means it misleads on a reachable path. Low is polish or a question about the rule itself. Reproduced means a throwaway Vitest probe against App asserted the defect and passed; code-read means it was traced in the code but not run.

R1High Setup flashes on every launch, including for users whose capture already works. The title, the platform question and every task render while the launch self-test is still reading /flows. On a slow core the flash lasts as long as the request takes. The task states during the flash are placeholders ("we'll confirm this on this Mac's first request"), because the probes only start once the phase is onboarding. Root A. checking falls into the setup branch, and only the dot knows it is checking. The existing test "on mount shows the onboarding surface" uses findByText, so it passes whether or not the screen flashed first. reproduced: with listFlows pending, the question renders synchronously and the dot reads checking
R2High A core that is down gets setup instructions instead of "not answering". If /flows fails at launch, the app dispatches not-detected, and the user is told to trust a certificate and set a proxy. The actual problem is that Trawler's core is not running. The "no answer from …" band exists only in the list branch, so the setup screen never says it. When the core returns holding older https rows, the live check flips to the list with the "You're set up" banner. That is news for a success that happened before this session. Root A. The catch handler dispatches not-detected, and NotAnswering is not mounted in the setup branch. reproduced (no band on the setup screen) · the banner half is code-read
R3High Imported and sent rows count as proof of capture. Launching with only an imported HAR row, or only a request Trawler replayed itself, skips setup entirely. On the setup screen, a replay sent a moment ago makes the try task read capturing traffic ✓, although no device routed anything. This breaks UC-ONBOARD's "only a decrypted flow reveals the list" and "the first https:// flow the MITM rewrote". Root B. Neither helper reads source. It is a seam regression: E-EXPORT and E-REPLAY added the provenances after the proof rule was written, and neither re-checked it. reproduced for imported and sent
R4High Setting up a second device opens no instructions and says "You're set up" at once. After the first device is proven, re-entering setup shows three things from the old device's traffic. (a) Every guide is collapsed, on every platform, because "one guide open, none once a request has decrypted" reads a decryption from the previous device. (b) If that decryption was in the last 30 s, the screen already says "You're set up — Trawler is capturing traffic from this machine" before the user has done anything. (c) The try task reads capturing traffic from the old device. Root C. everDecrypted = traffic.lastDecryptedAt !== null has no baseline for when this setup started. What holds

Probes stay on this machine

probesTrust and probesRoute gate every probed state per platform. The Simulator's trust is never read from the host keychain.

Dimming before reach

Off-machine tasks stay numbered and dimmed until reach is armed, and they say "after step 1". No step is given that cannot work.

One primary action

macOS and Windows get one combined button and one prompt. What it offers once a half is done, or after it fails, is R12 – R16.

The per-task layout

Where no combined action exists (Linux, Android emulator, off-machine), each task carries its own steps. A done task's steps collapse and the next task's steps open. It is the layout R12 – R16 should fall back to.

First run on a working core

Launch → setup → the first live https row → the list with the banner. The path the epic's e2e walks behaves as specified.
