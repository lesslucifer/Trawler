Requirement

A navigable onboarding surface renders in the native app until capture is proven by a live decrypted HTTPS flow, and gives way to the flow list once it is — a three-step stepper (trust the CA · set the proxy · verify) with placeholder step bodies and a persistent verify status, fronted by a 3-state capture-status dot that always re-opens setup, all driven by a pure onboarding state machine wired into UC-4's Layout. This WU ships the shell and the state machine only: step actions are inert placeholders (W2/W3) and the captured proof signal is dispatched by a test, not yet by a live detector (W4).

Onboarding UX & state machine

Entry is state-driven, never a popup. The machine is a pure reducer so its transitions are unit-testable with no network (W1's "done when").

What proves "working" — live capture, not a /flows count. A non-empty /flows is not proof the connection works now: it counts plain HTTP, and the moment we add persistence (a future epic) it would count stale history and lie. So proof is a fresh decrypted HTTPS flow — obtained reliably by W4's active self-test (the app fires its own test HTTPS request through the proxy and confirms it returns decrypted) and by watching /stream for a new decrypted HTTPS flow after Verify. Stale/historical flows never count — that is exactly what makes it persistence-proof. Launch is therefore always checking, never "proven because rows exist".

Broken setup, and the status dot. The header dot is the one indicator + control: broken (capture not working — fresh & broken both read red), checking (self-test running), connected (working). Tapping it always opens setup (re-invoke). W4 runs the self-test on a schedule so the dot flips to red on its own when setup breaks mid-use (CA removed, proxy changed) — the liveness proof is the detector, since a broken setup stops producing fresh decrypted flows. Passive detection (HTTPS connections arriving but failing to decrypt) is not possible on today's API — /stream emits only request/response/evicted, no failed-handshake event — so it needs a new core signal and is a future enhancement (out of "no new backend" scope). W1 builds the dot + tap→re-invoke; the scheduled detector is W4.

Wireframes

Surface — centered panel · minimal header · stepper

Onboarding fills the main area in a centered panel; the header shrinks to the status dot + wordmark (no filter fields — inert with zero flows). Reuses Layout's header prop, so no Layout change: App passes a minimal header while unproven and the full filter header once proven. Steps use the stepper (all three visible; active expands, done ticks; Verify pinned) — the epic's persistent red→green verify. Considered a one-step wizard and modal/full-filter surfaces; declined.

State-machine contract (the shape the tests pin):

type Step  = 'trust-ca' | 'set-proxy' | 'verify';
type Phase = 'checking' | 'onboarding' | 'proven';
interface OnbState { phase: Phase; step: Step; everProven: boolean; }

type OnbEvent =
  | { t: 'next' } | { t: 'back' } | { t: 'goto'; step: Step }
  | { t: 'captured' }       // fresh decrypted HTTPS flow — W4 detector dispatches
  | { t: 'not-detected' }   // launch self-test found nothing — W4 dispatches (W1: on mount)
  | { t: 're-invoke' }      // tap status dot / W4 health-check fails → re-setup
  | { t: 'exit' };          // Back to flows — returns to proven iff everProven, else no-op

initial(): OnbState                        // { phase:'checking', step:'trust-ca', everProven:false }
reduce(s: OnbState, e: OnbEvent): OnbState
dotStatus(s: OnbState): 'broken' | 'checking' | 'connected'   // onboarding→broken, checking→checking, proven→connected

Step status in the UI is derived from step order + phase (before = done, current = active, after = pending) — no separate done-tracking, because "done" is proven by capture, not self-reported. everProven gates the Back control and lets the dot tell "broke mid-use" from first-run (both red, different tooltip).

Expected (done when)

  • Launch → onboarding surface shows (W1 falls checking→onboarding immediately, real self-test is W4), not the bare "no flows yet" empty list.
  • Navigable stepper: next/back (or step click) walk the three steps; active body visible; Verify shows waiting.
  • Step actions are inert placeholders — no CA install, no proxy set, no snippet.
  • Header StatusDot renders 3 states from dotStatus and, when tapped, dispatches re-invoke to open setup.
  • A forced proven state shows the flow list; re-opening setup from it shows the Back to flows control, and Back returns to the list; first-run hides Back.
  • All reduce transitions + dotStatus unit-tested; render smoke + entry integration green; cargo xtask ui build (tsc) clean. (Live/scheduled proof is W4.)
