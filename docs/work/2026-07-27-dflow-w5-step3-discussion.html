Why the sheet is off-scale in the first place

Not an accident, and worth stating before proposing to change it — the values were reasoned about.

The components are chrome, not layout

Tailwind's 8px-step scale is a layout scale. A 24px-tall button with a 1px border and 11.5px text lives below its first step. The sheet's 1–5px paddings are the interior of controls; the config's 8/12/16 are the gaps between them. Two different problems, and the config only ever solved one — it was written for the flow-list screen, before a component collection existed.

The density is the product

A debugging proxy panel shows a request, its headers and its body at once. The sheet's 11px/10px type and 2–4px gutters are what make that fit. Rounding every value up to the nearest Tailwind step would visibly loosen the panel — a design regression introduced by a tooling decision, which is precisely backwards.

The rulebook already has an opinion — and it is W6's

spacing-scale declares an 8px floor. Two sheet values already violate it (.ht-grid's 4px row gap, .btn-copyall's 2px padding) and both are marked → W6, deliberately unresolved. So "make everything scale-conformant" is not W5's call to make; W6 owns whether the floor stands, moves, or gains a chrome exception.

The keyed-highlight and state-toggle CSS at the bottom of the sheet? Doc interaction, pairs with specimen.js. Moves into specimen.js's own injected style or the doc chrome — not deleted, just not pretending to be a component.
--a-key / --a-str / --a-num (syntax colours) and the 4 raw rgba() washes? They are not in tailwind.config.js today — which is exactly why colour-tokens-only is unsatisfiable for a rendered JSON body (an existing → W6 marker). Under E they must be added to the config to be drawable at all. this forces a W6 question early — see the boundary note below.
Is tw-config.js gitignored? round-2 comment Moot — there is no generated file. The comment asked the right question ("don't hand-maintain a duplicate") and the follow-up asked the better one: why generate at all? ui/tailwind.config.js is an ES module, so a <script type="module"> imports it directly over file:// — verified in headless Chrome, including a relative path across directories and the function-valued backgroundColor key. tw-config.js is now a 30-line module that imports the config and sets tailwind.config; it holds no values. No generator, no staleness gate, no regeneration step — nothing can drift because there is no second copy.
Does the CDN's JIT catch classes added by specimen.js at runtime? Yes — the Play CDN observes the DOM and generates on mutation. State classes toggled by the switch (.s-hover, .inflight) are fine. Caveat: classes assembled from string fragments in JS are not statically visible; the specimens don't do that, and shouldn't start.
The one real cost: docs now need the network to look right. Today a design file renders fully offline from its own <style>. Under E, no CDN means unstyled specimens — the prose, tables and diagrams still read (Mermaid is already a CDN dependency, so the docs are already network-dependent for their diagrams). Accepted: these are T3 working docs read by agents and the reviewer on a connected machine, and Q1 retires them once code is truth. If it ever bites, the fix is one vendored tailwind.js next to specimen.js — same shape, no redesign.
A W6 boundary just moved, and it should be named. Under C, an unnameable colour (the syntax tokens, the hover washes) could keep sitting in the sheet as a raw literal with a → W6 marker on it. Under E there is no sheet to hide in: every colour a specimen draws must exist in the config. That does not decide W6's rule — but it does force the vocabulary to be complete now, so W5 adds syn-key/str/num and names the two washes. W6 still rules on whether they are permissible; W5 only makes them expressible. Flagging it because it is a real widening of step 3 that the round-1 doc did not carry.
Why C and not D, stated once. D is correct about the destination and wrong about the sequence. The six conflicts are contradictions, not gaps — a builder reading section.html today finds 10/14px in the specimen and px-4 py-3 in the token table and has no way to know which is the contract. C resolves each contradiction by making the config the tiebreaker, which is the same authority D would eventually appeal to — just applied before 22 components are written against the ambiguity instead of after.

D2 · If C — what do the new config keys look like?

This is the fork that decides whether C is an improvement or just a relocation. Adding spacing: {0.5: "2px", 1: "4px", …} would make every value expressible and mean nothing — an unconstrained scale is not a scale. Two shapes:

The button box becomes one shared token instead of three files agreeing by luck — which is the exact class of bug W5 is fixing.

Named tokens also give the rulebook something to cite. colour-tokens-only works today because colours have names; spacing-scale is unenforceable against padding:3px 9px and becomes enforceable against py-control-y. That is W7's predicate turning from impossible to trivial — and it is a side effect of D2, not extra work.

Boundary — this does not pre-empt W6. Naming control-y: 3px records what the components draw; it does not rule that 3px is permissible. The 8px floor and its chrome exception stay W6's, and the four → W6 markers stay in the sheet untouched. If W6 later rules the floor absolute, it changes one config value and every specimen and component follows — which is the entire argument for doing this.
