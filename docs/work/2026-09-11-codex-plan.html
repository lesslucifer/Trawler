E-CODEX — one source, two harnesses

A Codex session in this repo reads the same T0 rules, loads the same code-review skill, and runs the same verify-doc hooks a Claude session does — through symlinks, with one payload-tolerant hook script.

Draft v1 · 2026-09-11 · Trawler · T3 epic plan · E-CODEX

Intent

The workflow's authoring-time guarantees are harness guarantees. The PostToolUse hook is what feeds a red doc back while it is being written, the Stop hook is the backstop that refuses to end a turn with one red, and the cr/v3 evidence note names a skill run from .claude/skills/code-review/. The standard states the premise in one line: hooks are "versioned in .claude/settings.json — the harness executes them, not the agent, and in an AI-first repo every author is a harness session, so authoring-time coverage is total" (work-planning). In a Codex session, none of those three happens, and nothing fails loudly: T0 is not read (Codex looks for AGENTS.md), the code-review skill is not discovered (Codex scans .agents/skills/, which is empty), and the doc-feedback hook exits 0 without looking at the file it was handed (the payload shape it parses is Claude's, not Codex's). Every doc and every commit written in such a session lands outside every check the workflow claims is total — and the session cannot tell, because a silent hook and a green hook look identical. Why now: agents already run in this repo as Codex sessions, so the gap is being paid today — this plan is one such session. The fix is single-sourcing: keep CLAUDE.md and .claude/ canonical, and give Codex the paths it actually reads, as symlinks over those exact bytes.

What already works, and why it is not enough. The Stop backstop reads nothing from stdin, so it behaves identically under both harnesses — but only once the Codex hook layer loads at all, and today .codex/ is untracked: a fresh clone has no Codex hooks, and Codex only loads project hooks from a .codex/ layer the user has reviewed and trusted (/hooks). A missing payload field also fails open: the script's only guard is the path it parses, so an empty one is a silent success.

Four links, no second copy. Three of them are pure symlinks; the hook entry additionally needs one harness-neutral command string and a payload-tolerant script, because the two harnesses name the edited file differently.

Use-case requirements

A process epic — it delivers no UC-* behaviour and changes none. Nothing user-visible in the proxy or the UI moves. What changes is which harness the workflow's own rules hold for, so the truth lands in T2 and T1: a new decision record fixing the canonical/alias arrangement and the hook payload contract, plus the wording in the T1 process docs that today names one harness and one payload shape (workflow's hook table, work-planning's authoring-time trigger section, and documentation-system's T0 row). Those three are rule-bearing, so the edits land under a Reviewed-By trailer.

Non-goals

  • Not a reverse port. Nothing becomes canonical under .codex/ or AGENTS.md. CLAUDE.md and .claude/ stay the sources the gate, the husky hooks, the T1 docs and the mr rules already name; the Codex paths are aliases.
  • Not T0 content. The symlink makes both names the same bytes, so the T0 text is not edited — including line 80's self-reference, which stays accurate: the real file is CLAUDE.md.
  • Not a harness feature-parity project. Models, sandboxing, subagents, plugins and MCP are Codex's business; only the three things the workflow depends on are in scope.
  • Not a general "make Claude files work for Codex" sweep. A second copy of any skill, hook or rule is refused here; if a future Claude-only artifact needs a Codex door, that is its own decision.
  • Not a change to how checks behave. The verdicts, problem blocks and gate semantics stay identical — this epic moves the door, not the room.

E2E test plan

The epic's user is an agent session, so the end-to-end flow is configuration as Codex reads it → the same verdict the Claude path gives, driven from the committed files rather than from hand-typed paths. No waiver: this is one hermetic test, plus the parity assertions it shares with the WU tests.

StepWhat it doesAsserts
1 Resolve the T0 door: read AGENTS.md at the repository root and CLAUDE.md through git. Same bytes, link mode 120000 — the text a Codex session loads is the tracked T0 blob, not a copy of it.
2 Resolve the skills door: enumerate .claude/skills/*/SKILL.md and read each through .agents/skills/. Every skill resolves byte-identically and carries name + description.
3 Read the hook definitions out of .codex/hooks.json as Codex would, and run the PostToolUse command string in a temp repo that shares the repository's .claude/ — a stand-in for a second worktree — with a Codex apply_patch payload writing a red ready doc. Exit 2, and the problem blocks name the missing checklist items — the identical verdict the Claude payload produces.
4 Repeat step 3 for a green ready doc and for a patch touching no HTML. Exit 0 with empty stderr — no false red, no noise.
5 Run the Stop command string in that temp repo holding a tracked red doc. Exit 2 with the refusal text: the backstop survives the shared config.

Steps 1–2 read the real repository (the symlinks are the artifact); steps 3–5 are hermetic temp repos with the real xtask binary, in the style of the existing doc_hooks suite. What is deliberately not asserted: Codex's hook-trust store and its own discovery pass — a test cannot review a per-machine trust prompt, so that is step 6 of the expected results and a documented operator step.

Open questions

#QuestionProposed default
1 Does Codex follow a symlinked skill root, not just a symlinked skill folder? Assume yes — the docs promise symlinked skill folders are followed, and a repository-root link is the only form that keeps a future skill from needing a second step. W2 verifies it in a live session; if the link is missed, the fallback is one link per skill (.agents/skills/<name> → ../../.claude/skills/<name>), and the parity test enumerates .claude/skills/* either way.
2 Does Codex accept a symlinked .codex/hooks.json, and does its trust hash follow the target? Assume yes, and assert the contract, not the mechanism: the parity test requires both harnesses to resolve to the same command set, so a small real .codex/hooks.json is an acceptable fallback if the link misbehaves. Observed consequence to record in DEC-42: an edit to the shared config re-prompts trust, which is the intended review point, not a defect.
3 What if a future committed setting is Claude-only? Keep the shared file hooks-only (enforced by the parity test) and put local Claude settings in the untracked .claude/settings.local.json. A genuinely committed Claude-only section forces the split: a real .codex/hooks.json carrying the same definitions, with the parity test as the drift alarm.
4 Is the /hooks trust step a gap in the epic's evidence? Accepted and named. Trust is a per-machine store Codex manages; the epic proves the configuration contract and records the operator step in DEC-42, exactly as .mr-allowed is provisioned per machine and never asserted by a test.
