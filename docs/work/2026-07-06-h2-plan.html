E-H2 — HTTP/2 end-to-end

Collapsed epic + WU plan: enable HTTP/2 on both proxy legs and record the true protocol version per leg.

v2 · 2026-07-06 · Trawler · T3 · epic E-H2 (one WU: E-H2.W1)

Intent

Today every client is silently downgraded to HTTP/1.1 on both legs: hudsucker is built without its http2 feature and the upstream connector only advertises http/1.1 in ALPN (src/lib.rs, enable_http1()). Modern clients (browsers, gRPC-adjacent tooling, most CLIs against CDNs) speak HTTP/2 by default, so Trawler both distorts the traffic it claims to observe and records a misleading version. This epic — Wave 1, Function pillar of DEC-5 — turns on HTTP/2 across the MITM path so clients negotiate h2 with the proxy, the proxy negotiates h2 with upstreams that support it, and each flow records the version actually spoken on each leg.

Why the design doc's "ALPN-accept + HTTP/1.1 normalization, not true end-to-end h2" claim is stale: hudsucker's normalize_request does mark every forwarded request HTTP/1.1, but that field never forces the wire — hyper-util's legacy client speaks whatever ALPN negotiated on the pooled upstream connection, and the recorded response.version comes back from that actual connection. So end-to-end h2 and truthful per-leg recording both hold; the e2e tests are the proof, and correcting the stale T1 statements is part of distillation.

Use-case requirements

No UC-* records exist yet (docs/use-cases/ is empty); this epic changes the core capture contract and will seed the first T2 use-case doc. Contract-level:

  • Intercept HTTPS without protocol distortion — an h2-capable client connecting through the proxy negotiates HTTP/2 with the MITM endpoint instead of being forced down to HTTP/1.1; an h1-only client keeps working unchanged.
  • Inspect a flow's true protocol versions — GET /flows and SSE payloads report, per flow, the version actually spoken on the client leg (request.version) and on the upstream leg (response.version); mixed-version flows (h2 client, h1-only upstream) show the mismatch honestly.

Expected result

Observable after the epic, checkable by anyone with curl:

  • An HTTPS request sent through the proxy by an h2-capable client to an h2-capable origin produces a flow whose request.version and response.version are both HTTP/2.0 on GET /flows.
  • The same client against an h1-only origin produces request.version = HTTP/2.0, response.version = HTTP/1.1 — legs are independent and truthfully recorded.
  • Plain-HTTP and h1-only-client traffic behaves exactly as before (bodies captured, headers preserved, HTTP/1.1 recorded) — no regression.

Non-goals

  • h2c (cleartext HTTP/2) on either leg — h2 arrives via ALPN on TLS only.
  • HTTP/3 / QUIC.
  • Per-host protocol-version overrides or any new config surface.
  • UI work — the existing version fields on the API simply become truthful; surfacing them richly belongs to the UI epics.
  • WebSockets (own epic E-WS), gRPC-specific decoding.

E2E test plan

Extends tests/e2e_capture.rs (or a sibling e2e_h2.rs) using the existing hermetic harness: trust the generated CA, local TLS upstream on an ephemeral port.

  1. h2 end-to-end: reqwest client (rustls, h2 enabled) → CONNECT → MITM TLS with ALPN h2 → local axum-server upstream with ALPN h2, http/1.1. Assert the exchange succeeds, body round-trips intact, and the flow on GET /flows shows HTTP/2.0 on both legs.
  2. Mixed legs, both directions: h2 client → upstream restricted to http/1.1 ALPN: assert request.version = HTTP/2.0, response.version = HTTP/1.1. And an http1_only client → h2 upstream: assert request.version = HTTP/1.1, response.version = HTTP/2.0. The legs negotiate independently, and the h1↔h2 adaptation must not corrupt traffic (echo body round-trip asserted both ways).
  3. Concurrent streams, one connection: N concurrent requests with distinct bodies from one h2 client (reqwest multiplexes them over a single MITM'd connection). Assert N flows, each pairing its own request body with its own response, all HTTP/2.0 — pins the recorder's per-exchange request↔response correlation under multiplexing, the one h2-specific regression risk in the capture path.
  4. h1 regression: the existing plain-HTTP and h1 HTTPS e2e capture tests stay green unmodified — proof of no regression for h1-only clients.

Open questions

None — v1's three questions were closed by source-level verification before code:

  • reqwest dev-dependency: yes, it needs its http2 feature for the e2e client (it is default-features = false today); dev-only, no runtime cost.
  • hudsucker MITM ALPN: the http2 feature alone is sufficient — verified in 0.24.1 source (rcgen_authority.rs offers h2, http/1.1; hyper-util/http2 enables the auto server's h2 path). No builder call needed.
  • Upstream ALPN order: enable_all_versions() offers h2 first and the origin decides — matches what real clients send.
