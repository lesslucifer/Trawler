E-RELFIX.W2 — headers and a URI read as the form they are

The data window reads a header block as text, and its form view reads every text as a=b&c=d.

v1 · 2026-11-06 · Trawler · T3 WU plan · E-RELFIX.W2 · branch wu/release-fixes/inspect-form-parse off epic/release-fixes · epic plan E-RELFIX · owner-named 2026-11-06

Requirement

A leg's headers opened in a data window read as form: one row per name: value line, repeats kept. A URI opened there reads as form: its scheme, user, host, port, path and fragment as labelled read-only rows, then its query's pairs percent-decoded. Picking form on either from text gives the same rows; picking it on text that is none of the three shapes says why and shows the text.

Decisions

#DecisionEvidence / why
D1The openers name their data with registered media types: headers text/rfc822-headers (RFC 6522: a message's header portion), a URI text/uri-list (RFC 2483). labelKind maps both to form.DEC-76 rule 1: typeHint is a media type and the window learns no source kind; DEC-79 rule 4: form is named by a label or the picker, never guessed from bytes. Both stay true.
D2Inside form, the shape is read from the bytes handed in (the original), as the kind is: url (one line, no whitespace, scheme:// or a leading /), headers (every line token: value, a leading : for a pseudo-header, an indented line folds into the one above), query (any other single line), or none.No new kind, so the picker's nine rows (E-INSPWIN2 E6) and the window's look stay. A whole parse, not a guess: each shape's grammar accepts the whole text or the shape is not taken.
D3none: text with a raw ", <, > or a line break that is not a header block. The window shows the text surface under a warn notice; no form tools.WHATWG URL's query percent-encode set always encodes " < >, and the urlencoded serializer every one of them and line breaks: a form never carries them raw. JSON, XML, HTML and prose are refused; a sloppy a=hello world still parses.
D4A + is a space in a URL's query as in a form body; a path, user and fragment are percent-decoded only. A bad escape keeps that part as sent (the existing kept note).WHATWG URLSearchParams (and so url.searchParams) parse a query with the urlencoded parser (+ → space), as the pane's formEntries already does for bodies; RFC 3986 gives + no meaning in a path.
D5URL parts are labelled, read-only rows above the pairs (no number, no add/remove; find marks their values; copy and decode work). Edits, add, remove and sort touch only the query (url) or the lines (headers); the rest of the text is kept byte for byte.The owner asked to read the parts; editing a host is not asked. Path segments get no rows: the path row wraps whole.
D6Headers values are verbatim (no percent-decoding); an edited value's line breaks become spaces.A header value has no escape grammar and no line breaks.
D7A long JWT/base64 value (efg=eyJ…) stays a value; the existing row decode (⌘⇧D) reads it.No new decode affordance (brief: do not invent).
D8The pane's FormRenderer reads the same shapes so a body served text/uri-list or text/rfc822-headers is not split on &; a URL-encoded body keeps formEntries unchanged.The label map is shared (DEC-79: one detector); the pane must not regress.
