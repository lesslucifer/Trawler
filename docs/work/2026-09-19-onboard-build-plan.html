The shape of the build

One screen file, three data modules, one component extension. The rule that decides where a fact goes: what a platform is is the axis module, what a reading means is the verdict module, and what the screen draws is the screen.

  C["preconditions — Section variant=band 'what has to be true'\nreach (off-machine only) · trust · route"]

The eight platforms — the content this WU owes

The run's blocked-on row 3 handed the build the instruction content: TrustTarget has no iPhone or iPad member and no another machine member, and its single android entry conflates the emulator with a device. The matrix below is what replaces it. Reach says whether the platform's instructions depend on an armed reach; probed says whether this machine's two probes are about the platform the user named.

PlatformReachProbedTrust routeRouting route
This machine — the detected OS, the defaultnoyes one-click install on macOS and Windows, plus the host OS's own steps and its removal one-click set on macOS and Windows, plus the host OS's steps; stop routing only once the proxy is ours
Another Mac · Another Windows PC · Another Ubuntu machineyesno fetch the certificate from the URL reach reports, then that OS's trust command — no one-click, it would be a lie about the wrong host that OS's proxy command, built from the reach host and port
iOS Simulatornoyes shares this Mac's certificate store — installing here covers it; restart the Simulator if it was running shares this Mac's system proxy — setting it here covers it
Android emulatornono its own user store, not this Mac's: adb push then install, with the Android 7+ network-security-config caveat 10.0.2.2 — the emulator's alias for the host it runs on — with the real port. A constant, not an address anyone must arm
iPhone or iPadyesno open the certificate URL on the device, install the profile, then turn it on in Certificate Trust Settings; the saved file is the no-browser fallback Wi-Fi → the network → Configure Proxy → Manual, with the server and port as copyable values
Android deviceyesno open the certificate URL on the device, install it as a CA certificate, same Android 7+ caveat Wi-Fi → the network → Proxy → Manual, with the server and port as copyable values

The emulator is the one call the mockup did not render. Its guide is reach-free because 10.0.2.2 reaches the host's loopback from inside the AVD, so an armed reach would be an exposure the platform does not need. That is the split the run asked for — the emulator and the device stop sharing one answer — taken to its conclusion: they differ in whether reach is needed at all, not only in their steps.

Integration — the WU's contract

The screen inside App, against the API stub and a mocked invoke: the seam this WU owns is the screen's contract with the machine and the API, and neither half is observable from a unit test of the screen alone.

ContractAsserted
reach is read, not assumed entering onboarding calls GET /reach once; an unarmed answer renders the reach precondition and no address anywhere on the screen
arming costs one confirm, and a refusal costs nothing pressing the arm action invokes confirm_reach with the selected address; a false answer makes no POST /reach and leaves the screen unarmed; a true answer POSTs that address and the screen renders the addresses the response carried
disarming is offered only while armed and needs no confirm stop listening calls DELETE /reach and the screen returns to the unarmed rendering — no second dialog, because nothing new is being exposed
the probes still reach the two steps they belong to with the platform on this machine, ca_trusted and proxy_status drive the trust and routing verdicts and check again re-reads both — DEC-33's layer, unchanged by the move
the one-click actions still work end to end install fetches the PEM and invokes install_ca; set proxy invokes set_proxy with the split address; both re-probe afterwards; neither transitions the machine — capture is still proven only by a decrypted flow

What could go wrong, and the answer

RiskThe answer
The move commits and the rebuild commit blur together, and the review cannot see which lines are new behaviour Step 1 is a pure move: no signature changes, no renamed exports, the existing tests follow their code and stay green. If a test has to change to survive the move, that is a sign the move was not pure and it stops being a move
The e2e spec goes red on this tip and the WU gate reads it as a regression Stated here and in the result: the suite the WU runs is the Vitest suite; the e2e is rewritten in W4 against the screen this WU builds, with a coverage map. The alternative — editing the old assertions here — would land a spec that asserts a screen nobody designed
A UC-ONBOARD promise quietly disappears in the rewrite, and the run's audit is trusted instead of the tree The re-check is done against the built screen's tests, promise by promise, and the result reports each one as standing or lost. The run's audit is an input, not evidence
The build finds the run wrong somewhere An amendment is allowed and carries itself: the amended run is a design artifact in this WU's diff, so check 9 re-judges it on this merge and the cited blob is the amended one. What is not allowed is building something else and citing the old bytes
Notice tone="pending" turns out to need more than a glyph-column spinner Then it is not the delta the run proposed, and the screen keeps the screen-owned composition the mockup renders while the extension is re-proposed. The proposal is a claim about the component's anatomy, and a build that has to widen it has falsified it
The emulator's reach-free call is wrong for some AVD configuration It is written as the platform's own instruction set, not as a special case inside another platform's — so it is one table row to change, and the run's blocked-on row 3 named this content as the build's to confirm
