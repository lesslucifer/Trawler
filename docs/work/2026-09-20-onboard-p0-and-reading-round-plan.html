The reading round — what it decides

Round 4 of the run, and the first one read as an end user reads it rather than as a designer reviews it. Three rules are re-opened; the row records the call, the mockup renders it, and W5 builds it.

Re-openedThe callWhat the amended mockup renders
Not a wizard: no stepper, no numbering, because nothing observes per-step progress (round 1) Split. The right half holds — no step ever self-reports ✓. The wrong half goes: order is a reading aid, not a claim about progress Preconditions rendered as numbered steps whose state comes only from a probe or the traffic reading; an unmet step is greyed and still numbered; nothing carries a cursor, a current step or a progress count
One Select as the screen's only axis (round 1) Axis kept, control changed. One choice, seen rather than discovered The platform question as tiles — every option visible without opening anything, the answer still exactly one
The verdict zone leads the screen (round 3) Reversed. A verdict is status; a first screen owes orientation above status A title and one sentence of purpose lead; the status sentence follows them, unchanged in what it says
DEC-33 · DEC-13 · DEC-55, and StatusLine's @avoid Kept, all four. The review says so itself Nothing. They are re-asserted by the round's row, not re-argued — and F16 is not a blend: the lead sentence may read both layers as long as each fact keeps its source

The round also carries the review's copy table into the mockup's sentences, so W5 has one artifact to build from rather than a design and a review to reconcile. The two wireframes in the review are wireframes — the amended mockup owns the real shape, mounted from the real collection.

What could go wrong, and the answer

RiskAnswer
The reading round quietly becomes the P1 build — a mockup amendment is one edit away from an Onboarding.tsx rewrite The WU's diff is allowed to change the screen only where a P0 finding names it. Anything the amended mockup renders that no P0 finding asks for ships as design and waits for W5; the result report lists what the mockup gained against what the code gained
The ordering rule needs a fact the host will not give — which address is active The host answers it by routing: the source address the OS picks for an unroutable test destination, resolved without sending a packet. No route, no answer, and the rule falls through to IPv4-before-IPv6 — which is still a better default than the one shipped
A temporary IPv6 cannot be told from a stable one through if_addrs Read from the host where it says so and sink it; where it does not, the address stays where the rest of the rule puts it — below every IPv4. The failure the review reported (a rotating address offered first) cannot survive either way
The chip lives in the app shell, which the design of record does not design Declared undesigned in the design/v1 note with the reason — the run designs the setup screen, and the chip is the shell's. F20 is its source, and W6's restatement is where it becomes a promise
A P0 fix contradicts a decision the review said to keep Three are load-bearing here: DEC-33 (F16 reads both layers and each fact keeps its source), DEC-13 (F13 changes what a refusal says, never that arming asks), DEC-55 (F11 and F20 change the address offered and its visibility, never the rules). Each is re-asserted by a test, not by a sentence
