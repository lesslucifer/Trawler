E-UISHELL — Embedded Web UI Shell

Epic plan (collapsed: one WU) — live, filterable flow list in the browser, served from the binary, zero setup.

v1 · 2026-07-06 · Trawler · T3 epic plan + WU plan · roadmap: DEC-5, Wave 1, GUI pillar

Intent

Trawler today is API-only: seeing captured traffic means curl :3001/flows. E-UISHELL ships the first user-visible surface — open http://127.0.0.1:3001/ in a browser and watch flows appear live as traffic passes the proxy, with a filter bar to narrow them. It is Wave 1 of the GUI pillar (DEC-5): visible traffic first, deliberately before the UI foundation epic — the shell's minimal chrome is a priced-in rework that migrates onto E-UIFOUND's layout as its first tenant. Everything rides on the existing control API; the epic adds no new capture capability.

Use-case requirements

No docs/use-cases/ topic exists yet; this epic introduces the first UC. Contract-level behavior delivered:

UCContract
UC-UI1 Watch live traffic in the browser With Trawler running, GET / on the control API port serves a self-contained HTML page (no external app assets, no install/build step). The page shows the captured flows (method, host, path, status, duration, size) and updates live via the existing SSE stream as new traffic passes the proxy. A filter bar narrows the list by host, method, status and free text — the same semantics as the GET /flows query parameters, because the page delegates filtering to them. Works against a fresh binary with zero configuration.

Existing API contracts (GET /flows, GET /stream) are consumed unchanged — no behavior change to them.

Expected result (epic = WU, collapsed)

Observable after the epic lands, checkable by anyone with the binary:

  • cargo run, then open http://127.0.0.1:3001/ → an HTML page renders titled as Trawler with an (initially empty) flow list and a filter bar.
  • curl -x http://127.0.0.1:3000 http://example.com/ → the flow appears in the open page without a manual refresh (SSE-driven).
  • Typing example.com in the host filter shows the flow; a non-matching filter hides it.
  • curl :3001/ returns 200 text/html; the page is one embedded asset — no file paths, no CDN dependency required for the list to function.
  • All pre-existing API routes behave exactly as before.

Approach

One embedded page over the existing API. Filtering stays server-side: the page refetches /flows with the current filter; SSE events only trigger a debounced refetch, so no filter logic is duplicated in JS.
Lazy by design: a single ui.html (vanilla JS + inline CSS) embedded with include_str! and served by one new axum route. No npm, no bundler, no new crate, no framework — E-UIFOUND owns the real UI stack decision; anything heavier built now is rework guaranteed by DEC-5.

Non-goals

  • Flow detail / inspector views, body rendering, copy-as-curl — E-UIINSPECT.
  • UI tech-stack decision, design system, app layout, UI build tooling — E-UIFOUND (the shell migrates onto it later; its chrome is intentionally throwaway-minimal).
  • Onboarding, CA-trust guidance in the UI — E-UISETUP.
  • Pagination, delete/clear — E-EXPORT; persistence — E-PERSIST.
  • Authentication / remote access hardening — the UI binds where the API binds (loopback by default), nothing more.
  • New API endpoints or changes to existing ones.

E2E test plan

One hermetic e2e (tests/, ephemeral ports, local origin server — per the testing standard) proving the full flow:

  1. Start the full app via run(Config) with ephemeral ports + a local HTTP origin.
  2. Send a request through the proxy at the origin.
  3. GET / → 200 text/html, body contains the shell's flow-list and filter markup and wires /flows + /stream.
  4. GET /flows?host=<origin-host> → the proxied flow; a non-matching filter → empty list.
  5. Open /stream, send a second proxied request → its SSE event arrives.

This covers the epic end to end at the HTTP layer. In-browser rendering is the waived layer (reason above, judged at review); the compensating manual check is part of the WU result evidence.

Open questions

QuestionProposed default
Serve the UI from the API port or a separate one? Same port/origin (:3001, GET /) — zero CORS, zero config, one listener. A dedicated UI port is an E-UIFOUND question if ever.
SSE handling: client-side merge of events into the list, or refetch? Debounced refetch of /flows with the current filter — the server stays the single source of filter truth; no duplicated filter logic in JS.
Is HTTP-level e2e enough for a UI epic? Yes for the shell: browser automation is stack tooling E-UIFOUND owns; waiver recorded in test/v2, manual browser check in the WU result. Review judges it.
