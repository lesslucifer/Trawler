E-REPLAY — epic plan

Send a request again, edited or written from scratch, and see what happens. The result lands as a new flow, and the app gets a composer to drive it.

v2 · opened 2026-09-23 · open questions answered by the owner 2026-09-25 · Trawler · T3 (docs/work/) · branch epic/replay · WU branches wu/replay/<slug>

Intent

Trawler shows a developer what their client sent, but it cannot answer the question that usually comes next: what if it had sent something else? Today the only way to find out is to copy the request as curl, edit it in a terminal and send it outside Trawler, where the answer is never captured. This epic adds that capability to the core first. Two POST endpoints are added: one re-sends a captured flow with any of its method, URL, headers or body overridden, and one sends a request written from scratch. Each result lands in the ring as an ordinary flow, marked with where it came from. The native app then gets the composer that design run #7 already drew: seed a draft from a flow, change one thing, send it, and read the outcome under the button that sent it. It is the roadmap's wave-3 functional epic. The differentiators in wave 4 (E-LLM, E-MCP, E-OAS) need this send machinery, and building it here means it is built once.

Use-case requirements

One new use case, UC-8, and one amended one, UC-5. Contract level:

UCChangeContract after this epic
UC-8 new replay a flow any flow in the ring can be sent again, with its method, URL, headers or body overridden. An absent override means the seed's own value. The answer is the new flow. A seed whose body was never captured (streamed, too large, read error) is refused, naming which absence, unless the caller supplies a body. A missing body is never sent as an empty one, which is the principle UC-6 already holds for export and import
UC-8 compose a request a request written from scratch (method and URL required; headers and body optional) is sent the same way and lands the same way. Replay and compose use one sender, so the only difference is where the starting values come from
UC-8 the result is a flow the sent exchange is an ordinary flow: same ring, same eviction, same detail and body endpoints, announced on /stream. It is marked source: "sent" and names its seed when it had one. It is selectable by ?source=sent. Its versions are the ones actually negotiated (UC-2), and its bodies obey the capture cap like captured traffic
UC-8 a send that fails a transport failure (refused, unresolvable, TLS rejected, timed out) is an answer with the reason in words, and no flow lands. A flow asserts that an exchange happened, and none did
UC-8 the app's composer a draft is seeded from the flow open in the inspector, or started empty. Every field is editable on one surface. An edited header row marks itself and its neighbours do not. Send is one act, disabled while in flight with the wait named beside it. The outcome (status, duration, the new flow) lands beside the send button. The draft survives its own send
UC-5 amended the inspector gains an entry the inspector opens a replay draft seeded from the flow it shows. Nothing it does today changes
UC-4 · UC-6 unchanged in contract the list marks a sent flow the way it marks an imported one, and the ?source= set the listing and the export accept widens by one value. Neither use case gains or loses a promise

The contract

sequenceDiagram
  participant C as client (app · curl · agent)
  participant A as control API :7421
  participant S as sender
  participant U as upstream
  participant R as ring + /stream
  C->>A: POST /flows/{id}/replay { method?, url?, headers?, body? }
  A->>A: seed + overrides → request (uncaptured seed body, no override → 422)
  A->>S: send
  S->>U: request (ALPN: h2 or http/1.1, verified TLS)
  alt response
    U-->>S: status · headers · body
    S->>R: insert(flow, source = sent, seed = id) · capped like capture
    R-->>C: SSE request + response
    A-->>C: 201 FlowView
  else transport failure
    S-->>A: reason
    A-->>C: 502 / 504 plain-text reason · nothing inserted
  end
One sender, two doors: POST /flows/{id}/replay merges overrides onto a seed, and POST /flows takes a whole request. Error bodies are plain text, the API's existing shape. Every detail is decided on the decisions list below; W1 builds it and writes it into DEC-58.

Decisions (were open questions)

No question is left open. On 2026-09-25 the owner accepted the recommendation on eight of them (#4 confirmed 30 s) and asked for #3 to be explained. #3 was W1's call, so its recommendation stands, and its example is rewritten below as a timeline. Each row keeps its example, because the example is what W1 and W2 build against. The running case: flow 42 is a captured POST https://a.test/users with body {"name":"a"}.

#The question, plainlyExample: what actually happensDecision, and the alternative it beat
1 What does a call to Trawler look like? The endpoint and its JSON body
decided W1		 Replay 42 with new headers: 
POST /flows/42/replay
{ "headers": [
    {"name":"Authorization","value":"Bearer NEW"},
    {"name":"Content-Type","value":"application/json"} ] }
Method, URL and body come from 42, and these two headers are the whole header list sent. Compose from scratch: 
POST /flows
{ "method":"GET", "url":"https://a.test/users" }
 Decided: the two endpoints above. A given headers list replaces the seed's list whole, because the composer always has the full edited list to send.
Alternative: a patch language ({"set":{…},"remove":["Cookie"]}). It is shorter for curl users, but it is a second syntax to learn and test
2 What label does the new flow carry? The source value in the API and the list
decided W1 · DEC-58		 Replay 42 and you get flow 43: {"id":43, "source":"sent", "seed":42}. Compose from scratch and you get flow 44: {"id":44, "source":"sent", "seed":null}. Later 42 is evicted from the ring: GET /flows/42 is a 404 while 43 still says seed: 42 Decided: sent, meaning Trawler itself sent it (the other two are captured, which the proxy saw, and imported, which a file carried). A dangling seed id is stated, not prevented.
Alternative: replayed. But flow 44 is a replay of nothing, so the label would be false for every composed request
3 Does the call return at once, or when the server has answered?
decided W1		 You press send in the app. The app asks Trawler to send the request, Trawler sends it to a.test, and a.test takes 3 s to reply. The question is only when Trawler answers the app:
momentA · decided: answer when the server has repliedB · answer at once
0 s, send pressedcomposer: "sending…" · list: unchangedTrawler says "it is flow 43" · list: row 43 appears, with no status yet
3 s, a.test replies 200Trawler hands the app the finished flow 43 · composer: 200 · 3.0 s · list: row 43 appears, complete row 43 fills in 200 · the app must watch for that to happen
if a.test is downcomposer: ⚠ connection refused · list: unchanged, because nothing was exchangedrow 43 is already in the list and describes a request that never got a reply, so it stays pending forever or has to be deleted
 Decided: A. Trawler answers once a reply exists, and only then adds the flow to the list. The waiting is shown in the composer as "sending…".
Alternative: B. The list would show the request the instant it leaves, at the cost of rows describing exchanges that never happened
4 How long do we wait for a server that never answers?
decided W1		 Compose to a server that accepts the connection and then says nothing. After 30 s the call returns 504 no response within 30 s, and the composer shows ⚠ with that sentence and re-enables send. With no timeout, send would stay disabled until the app quits Decided: 30 s until the response starts (owner: "yes, 30s"). The body read is limited by the same capture cap the proxy uses.
Alternative: a configurable timeout now. Nothing asks for one yet, so it can be added later
5 Which headers does Trawler fix up, rather than send as typed?
decided W1		 Flow 42 carried Host: a.test and Content-Length: 12. The user changes the URL to https://b.test/users and the body to {"name":"alice"} (16 bytes). Decided: the request goes out with Host: b.test and Content-Length: 16. Sent verbatim instead: b.test receives Host: a.test and may route to the wrong site, and Content-Length: 12 cuts the body to {"name":"ali Decided: Content-Length is always recomputed. Host follows the URL unless the user typed a Host header themselves. Connection-level headers (Connection, Transfer-Encoding) are the client's to set.
Alternative: send every header exactly as given. That is honest to the letter, and it breaks the most common edit, a changed URL or body
6 When reach is on, can another device on the network use the send endpoints?
decided built in W1		 Reach is armed on 192.168.1.5. A phone on the same Wi-Fi calls POST http://192.168.1.5:7421/flows with "url":"http://192.168.1.1/admin", and Trawler sends it. That phone could already do the same today through the proxy reach opens: curl -x 192.168.1.5:7420 http://192.168.1.1/admin Decided: yes, with no extra gate. The endpoints add nothing the armed proxy does not already allow, and DEC-58 writes that argument down.
Alternative: refuse the send endpoints with 403 on the reach address. It is safer-looking, but it guards a door whose neighbour is open
7 Where does the composer open on screen?
decided W2 renders it		 The list is on the left and the inspector on the right shows flow 42. The user clicks replay. Decided: the right-hand pane turns into the composer, filled from 42, and the list stays visible. After send, row 43 appears in the list while the user watches, and back returns to 42's inspector. Modal: a dialog covers the list, so row 43 lands where nobody can see it Decided: in the detail pane, in place of the inspector, which fits DEC-36's 520 px pane.
Alternative: a modal, which gives more room and hides the list the result lands in
8 Are the user's edits kept if they look away?
decided W2 renders it		 The user edits the Authorization header in 42's draft, clicks flow 50 in the list to check something, then goes back. Decided: the edited header is still there. Clicking replay on flow 50 starts a new draft and replaces the old one. Quitting the app loses it Decided: one draft, kept until a new one replaces it or the app quits. It is held in the app, not the core.
Alternative: the draft is discarded the moment the composer closes. That is simpler, and one mis-click loses the edits
9 How does the text box get a multi-line form? Field is one line today
decided W2 proposes · W3 builds		 The body is several lines of JSON. Decided: <Field multiline …/>, with the same border, padding and states as the one-line box, and the import dialog's hand-made <textarea> moves onto it too. The edited mark is drawn by the composer's header row, not the box. A mistyped URL such as htp:/x gets no red border: on send, the core answers 400 url must be absolute http(s), shown in the send zone Decided: one component with a multiline option. It gains no edited and no invalid state, because DEC-19 has no colour for either.
Alternative: a separate TextArea entry. That makes two boxes that must be kept identical, which is the drift DEC-30 was written to end
