E-UIFOUND — Native UI Foundation

Epic plan (3 WUs) — decide + establish the native desktop UI stack, build integration, design system, and base app layout, with the live flow list as its first tenant.

v1 · 2026-07-12 · Trawler · T3 epic plan · discussion: uifound-discussion.html · roadmap: E-UIFOUND, Wave 2, GUI pillar

Intent

Trawler's only UI today is the minimal web shell (E-UISHELL: vanilla JS at GET /). E-UIFOUND establishes the native desktop app as the primary UI surface and the designed foundation every later UI epic (E-UIINSPECT inspector, E-UISETUP onboarding) builds on. Per the discussion and its Owner decisions, the stack is Tauri 2 + Vite + TypeScript + React + Tailwind (mirroring the sibling Strata app), the app is an out-of-process client of the existing control API (127.0.0.1:7421, REST + SSE), and the design system is seeded from Warp's DESIGN.md. This is a strategic reversal of the roadmap's web-primary framing — recorded here as DEC-11. The epic adds no capture capability and no new API; it rides entirely on the API that already exists. The web shell is kept alongside (a second client), to be retired later at parity.

Use-case requirements

Most of the epic is foundation (stack, build, design system, layout) with no user-facing contract. The one lasting behavior it delivers — its demoable first tenant — is a new use case, the native counterpart to the web shell's UC-3:

UCContract
UC-4 Watch live traffic in the native app With Trawler running, launching the native app shows the captured flows (method, host, path, status, duration) and updates live as new traffic passes the proxy, via the existing SSE stream. A filter bar narrows the list by host, method, status and free text — the same semantics as the GET /flows query parameters, because the app delegates filtering to them. The app is a pure client of 127.0.0.1:7421; it reaches no core internals.

Existing API contracts (GET /flows, GET /stream) are consumed unchanged. UC-3 (web shell) stays valid — both surfaces are clients of the same API.

Expected result

Observable after the epic lands, checkable by anyone with the repo:

  • cargo xtask ui build produces a front-end bundle under ui/dist/; the command wires pnpm install/build with no manual steps.
  • cargo xtask ui dev launches the native app window (Tauri) against a running core; the window renders the Warp-styled base layout with the live flow list.
  • Send traffic through the proxy (curl -x http://127.0.0.1:7420 http://example.com/) → the flow appears in the app without a manual refresh (SSE-driven); the filter bar narrows it.
  • cargo build and cargo test of the core resolve without pulling the GUI toolchain — the ui/src-tauri crate is outside the core workspace.
  • The design system exposes Warp tokens as the Tailwind theme + a base component kit reused by later epics; 2xx/4xx/5xx flow status keeps functional color.
  • The web shell (GET /) still works, unchanged.

Three WUs build up the ui/ project in sequence on one layout. All data access is the React frontend calling the existing API over loopback — the Tauri Rust side stays a thin window shell (no core logic), preserving the API-first invariant.
Mirror Strata's proven stack rather than re-deriving it; add only @tanstack/react-virtual for the long streaming flow list (Strata has no such list). The flow-list logic is ported from the web shell (src/api/ui.html) — same server-side filtering, same debounced SSE refetch — not reinvented. This epic also establishes the front-end test stack (Vitest + Playwright), discharging the browser-assertion waiver E-UISHELL deferred to E-UIFOUND.

Non-goals

  • Flow detail / inspector, body rendering (JSON tree, hex, image), copy-as-curl — E-UIINSPECT.
  • Guided onboarding, CA-trust UX, live "interception works" check in the app — E-UISETUP.
  • Retiring the web shell — kept this epic; a later step at native-UI parity (per the discussion).
  • The Tauri app auto-spawning / supervising the core process — this epic assumes the core runs alongside (the xtask ui dev task runs both); lifecycle supervision is deferred.
  • Pagination, delete/clear, HAR — E-EXPORT; persistence — E-PERSIST.
  • Any new API endpoint or change to an existing one; any capture/protocol change.
  • Windows/Linux packaging polish — macOS-primary this epic; the stack is cross-platform but only macOS is a gate target here.

WU summaries

Three WUs — three bounded contracts (build · design system · layout+flow-list), each landing on the same ui/ project in sequence, each with its own integration test at its seam.

W1 · Project scaffold & build integration

BuildsRequirement: a ui/ front-end project (Tauri 2 + Vite + TypeScript + React + Tailwind, mirroring Strata's layout) builds to ui/dist/ and launches a native window via cargo xtask ui, with ui/src-tauri a standalone crate outside the core Cargo workspace so a headless cargo build/cargo test of the proxy stays GUI-free. Establishes the front-end test runner (Vitest). App boots to a placeholder view (real content is W3).
Maps toEpic requirement "codebase in the build" + the project layout and thin-shell decisions. No UC (infrastructure).
Expectedcargo xtask ui build → a bundle in ui/dist/; cargo xtask ui dev → a Tauri window opens. Test — unit (commit): xtask ui subcommand wiring (Rust unit in xtask/); a Vitest smoke test that the React root mounts. Test — integration (WU seam): cargo xtask ui build runs the real pnpm pipeline and emits ui/dist/index.html (build works end to end); an assertion that cargo metadata for the core workspace does not include the ui/src-tauri crate (isolation holds).
DepsNone beyond a working pnpm + Rust toolchain. First WU; nothing else in the epic depends-before it.

W2 · Design system

BuildsRequirement: Warp's design tokens (warm-dark canvas #2b2622, off-white ink #f7f5f0, hairline borders, Inter/DM Mono/Instrument Serif type, 4px spacing scale, tight 3–4px radii) encoded as the Tailwind theme plus a small base component kit (the primitives the layout needs — surface/card, text tiers, input, badge/status chip), with functional 2xx/4xx/5xx status colors retained as the one deliberate exception to Warp's no-accent rule.
Maps toEpic requirement "design system"; the Warp design + status-color decisions. Horizontal contract reused by E-UIINSPECT / E-UISETUP. No UC.
ExpectedTailwind config carries the Warp tokens; components render with them. Test — unit (commit): the status-color mapping (2xx→ok, 4xx/5xx→warn, pending→muted) is a pure function, unit-tested at boundaries; each base component renders (Vitest + Testing Library). Test — integration (WU seam): a composed sample view asserts the resolved theme tokens are applied (class/computed-style checks) — the design system's contract is "these tokens, these components," verified as a unit of rendered output.
DepsW1 (the project + test runner must exist to build/test components).

W3 · Base app layout + live flow list (first tenant)

BuildsRequirement: a base app layout (named regions later UI epics slot into — header/filter bar, main content, a reserved detail region) hosts a live, filterable flow list ported from the web shell's logic, built on a typed API client that reads GET /flows and subscribes to GET /stream (SSE) on 127.0.0.1:7421, virtualized with @tanstack/react-virtual. This is the epic's demoable tenant (UC-4).
Maps toEpic requirement "base app layout; shell migrated onto it" + UC-4. Consumes W1 (project) + W2 (design system).
ExpectedThe app window shows the Warp-styled layout with the live flow list; a proxied request appears without refresh; the filter narrows it. Test — unit (commit): the API client parses /flows JSON into typed flow models; filter state → correct query params; the flow-list row renders from a fixture. Test — integration (WU seam): the flow list mounted against a mock API (or a real ephemeral core) renders a flow, hides it under a non-matching filter, and appends a new row on an injected SSE event — the exact request sequence UC-4 performs. Test — e2e (epic): see the e2e plan.
DepsW1 + W2. Last WU; carries the epic's e2e.

E2E test plan

One hermetic epic e2e proving UC-4 end to end (per the testing standard — ephemeral ports, local origin, no public network). Harness: Playwright drives the built front-end (Vite preview) pointed at a real ephemeral core started via run(Config) with a local HTTP origin:

  1. Start the full core (run(Config)) on ephemeral proxy + API ports with a local origin server; serve the built UI via vite preview, configured to reach the ephemeral API port.
  2. Open the app; assert the base layout + (empty) flow list + filter bar render.
  3. Send a request through the proxy to the origin → the flow row appears in the list live (SSE), with method/host/path/status.
  4. Type the origin host in the filter → the flow stays; a non-matching filter → the list empties.
  5. Send a second proxied request → its row appears without a manual refresh.

Why Playwright-against-preview, not the Tauri window: the flow-list contract is fully exercised by the real React app + real API in a browser context; driving the actual Tauri window (tauri-driver/WebDriver) adds a heavy platform harness for no extra coverage of UC-4. W1 carries a boot-smoke check that the Tauri shell loads the UI; tauri-driver is the recorded escalation if window-level behavior ever needs a gate. This choice discharges the E-UISHELL browser-assertion waiver.
