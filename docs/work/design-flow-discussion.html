Design System & Harness — epic direction

Give AI agents a way to design app UI that is consistent and verifiable, and wire it into the dev lifecycle. This doc sets the epic's direction and surfaces the hard problems — it does not execute any design.

Draft v4 · 2026-07-15 · Trawler · T3 scratch (docs/work/) · epic/design-flow

What this epic is

A design system + harness so any UI a Trawler agent designs is (a) composed from a shared component vocabulary, (b) bound by shared rules/tokens, (c) produced by a repeatable flow, and (d) gated to a minimum bar before it can proceed — then connected to the dev workflow.

The animating problem, in your words: raw instruction is not reliable — agents hallucinate and forget. So consistency can't rest on instruction; it needs a gate, the same way code quality rests on clippy + tests + verify-dod, not on "please write good code."

This is an epic discussion — direction only. Each requirement becomes its own Working Unit. We do not run a design in this doc.

The gate defines "done": a design is finished when it passes with a receipt, not when it looks nice. Reliability lives in the gate, not the agent.

The enforcement model (settled)

We can't programmatically verify design quality. What we can verify is that every rule was considered, with a citation-backed verdict — that's how "the agent didn't forget" becomes mechanically true. Three tiers, cheapest first:

Tier 1 · Mechanical gate

Deterministic, no judgment. Checks completeness (required sections + per-step artifacts exist), fixed rules (only tokens, only registry components or a declared new-component request, spacing scale…), and receipt coverage (every rule id has a verdict). Like clippy.

Tier 2 · Self-reflex receipt

The designing agent emits its own verifiable receipt: per rule id → considered / verdict / citation. Cheap, catches forgetting. Can be hallucinated — but cheaply reduces the odds, and Tier 1 checks it's complete.

Tier 3 · Adversarial review

Independent agents (the CR-skill model) review, cite the exact rule/inconsistency violated, or pass. Scoped to what mechanics can't judge — soft rules + new-component warrant.

Tier 1 polices the receipts of Tiers 2 & 3: it can't judge the design, but it can refuse a receipt that skipped a rule id. That is the whole trick.

The component registry (settled shape)

Code is the source of truth. Each registry component carries a structured usage doc-comment (when to use / when not / tier). An index file is the single thing an agent loads to know the whole vocabulary (so it needn't open every component file); sync is a Tier-1 check that the index lists every file in the collection folder (unless a file carries a waiver directive). A design either reuses a registry component or proposes a new one — passing with a spec, not built yet; the build happens later in the dev phase, and a human approves the addition after all gates pass. The collection grows over time.

Hard vs. soft rules — the examples you asked for

The confusion was fair. "Rules" span a spectrum of enforceability. Same rulebook, but each rule is tagged so the harness knows how to enforce it:

Hard — Tier-1 mechanical (grep/parse, pass/fail)Soft — Tier-3 judged (LLM, best-effort)
Only colour tokens, never raw hexWording is professional & consistent with app voice
Only Primitives/Widgets, or a declared new-component requestLayout groups related things sensibly
Spacing uses the 8/12/16… scaleVisual hierarchy makes the primary action obvious
Every interactive element lists its states (hover/focus/disabled)This new component is genuinely warranted, not needless

The problem I was flagging: if you write all of these in one flat list and tell the harness "verify the design follows the rules," it can truly check the left column but only pretend to check the right. The fix (per your enforcement model): tag each rule hard/soft. Hard → Tier 1 mechanically. Soft → Tier 3 judged. Both still require a receipt verdict — the tag only decides whether Tier 1 also checks it mechanically.

Decided (from your feedback)

  • Enforcement = 3 tiers + receipts (mechanical / self-reflex / adversarial); the gate guarantees consideration, not quality.
  • Registry: code is truth, usage in structured doc-comments + an index file agents load (Tier-1 check: index covers the folder unless waived), reuse-or-propose (pass with a spec, build later, human approves), five tiers (Foundation → Compositions), collection = Primitives + Widgets.
  • Draft mockup is the finish line — lo-fi structural, no hi-fi visual.
  • Fresh artifact per stage, distilled on epic merge.
  • Guinea-pig = the flow detail panel (inspector), executed in a WU.
  • Flow e2e = scripted run with both a fake user and a fake AI agent, proving the harness/flow plumbing works end-to-end (never stuck / misleading, yields output) — not real design quality. Not part of app e2e — run once, re-run manually on change (like the workflow e2e).
  • Rulebook = a T1 doc, enumerable with stable rule ids so receipts can be coverage-checked.
  • Reuse is fit-first: don't rebuild what exists at any tier; tier order is only a tiebreaker.
  • Adversarial review scoped to soft rules + new-component warrant (Tier 1 owns the hard rules).
  • Design→dev integration (#4) deferred to its own WU (W8).
