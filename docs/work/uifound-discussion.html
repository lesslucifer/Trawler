E-UIFOUND — Native UI Stack (Discussion)

The foundation epic pivots to a native Rust desktop app. This doc lays out the fork, the researched options, and the two decisions the Owner must make before planning.

Draft v1 · 2026-07-11 · Trawler · T3 discussion · roadmap · decisions

TL;DR — what this doc decides

E-UIFOUND's requirement is "UI tech stack decided (as a DEC), codebase in cargo/xtask build, design system + base app layout; shell migrated onto it." The Owner has set a new direction: the UI is a native app built in Rust, not browser-based. That reverses the roadmap's embedded-web-UI assumption, so it needs a recorded decision — this doc is the pre-decision discussion. Two choices come out of it, both the Owner's to make:

Q1 · GUI framework

Which Rust native GUI toolkit the foundation adopts. Top realistic picks: egui, Iced, Slint. Webview toolkits (Tauri, Dioxus-desktop) are disqualified by "not browser-based".

Q2 · Embedding / topology

How the native app relates to the existing API-first core: in-process, out-of-process over the local HTTP API, or hybrid (one binary, still routed through the loopback API). This is the "how do we embed it" question.

My recommendation, up front: egui/eframe for Q1 (fastest path, built-in virtualized tables for thousands of streaming rows, permissive license, single binary) and Hybrid (Topology 3) for Q2 (keeps the API-first invariant intact and ships one binary). Everything below is the evidence. Pick from the option tables and I'll write the epic plan + the DEC.

The pivot — and why it needs a decision

The roadmap frames every UI epic around the API-first web UI: "every GUI capability is a call on the public API, so the GUI never forks the feature surface," and E-UISHELL already shipped an embedded single-binary web UI (vanilla JS at GET /, served via include_str!). E-UIFOUND was scoped to migrate that shell onto a designed layout. Going native instead of web is a strategic reversal of a pillar's delivery mechanism. The roadmap explicitly says such reversals are "recorded as a decision and then reflected here" — so this discussion feeds a DEC, and the roadmap's E-UIFOUND row + the "browser-based" framing get updated when it lands.

What the pivot must resolve: the API-first invariant is a core design decision (core-technical-design.html: "trawler-core is UI-agnostic… any UI is a client"). A native app can honour it or break it depending on how it embeds — which is exactly why Q2 (topology) matters as much as Q1 (framework). The existing web shell doesn't disappear for free either: see the shell's fate.

Q1 · GUI framework re-scoped to RN-like

Owner comment: "I want a react-native-like GUI lib, try again." Re-scoped: the app must give the React-Native developer model — a declarative component tree (JSX/RSX), hooks-style reactive state, flexbox layout — while still rendering natively (no webview). That rules out my earlier picks: egui is immediate-mode, Iced is Elm, Slint is a DSL — none are React-like. It also re-opens the Dioxus family, which is the most React-like Rust option. The realistic RN-like-and-native contenders are below.

One tension only the Owner can settle: the direction so far was "native app, built in Rust." "React-Native-like" + "truly native (not webview)" + "production-ready" don't all hold in one Rust library today. So there are two readings:
(a) Rust-first — accept a young Rust framework (Freya) that has the RN ergonomics + native Skia render now, at pre-1.0 / solo-maintainer risk.
(b) RN-first — use literal React Native for desktop (react-native-macos, JS/TS), which is production-proven and truly native, but the frontend is no longer Rust. The core stays Rust; the UI talks to it over HTTP.

My read: if "in Rust" is the hard constraint → Freya 0.3.4: it's the only Rust lib with RSX+hooks, a native Skia renderer, and a built-in VirtualScrollView for the streaming flow list — but treat it as a calculated bet (do a 5K-row spike first, plan to build the tree/hex panels yourself, track the 0.4 rewrite). If "react-native" is the hard constraint and production-readiness matters more than a single-language stack → react-native-macos: it's literally React, truly native (AppKit), and FlashList solves the thousands-of-streaming-rows problem that no Rust-native lib has proven yet — at the cost of a JS/TS frontend over the Rust core. Dioxus-native is the ideal on paper but pre-alpha with no list virtualization — not buildable today. This is the one call I need from you before planning.

Q2 · Embedding / topology DECIDED · out-of-process

Owner decision: "go with opt 2" → Topology 2, out-of-process. The native app is a separate binary that drives 127.0.0.1:7421 (REST + SSE), exactly like a browser or curl would. This keeps API-first fidelity fully intact (the GUI can only do what the public API exposes) and lets the core run headless for CI/scripting/remote-tunnel use. It also fits the RN-first reading of Q1 cleanly: a JS/TS react-native-macos frontend is necessarily out-of-process. The comparison that led here is kept below for the record.

The native app has to get flows + live events from the core. Three topologies, scored against the one invariant that matters here — does the GUI stay a pure client of the public API, or does it reach behind it and fork the feature surface?

Why Hybrid: it's the only option that keeps API-first fidelity and ships a single binary. The cost over out-of-process is ~20 lines of "wait for :7421 to bind before the GUI opens its SSE stream"; the cost over in-process is one loopback TCP hop, imperceptible at UI refresh rates. This is the standard pattern for Charles / Proxyman / Wireshark (one app bundle, internal API). Deviate to Topology 2 only if the core must run on a remote host (SSH-tunnel use case) or you want independently-versioned GUI and core. Avoid Topology 1 — it permanently breaks the invariant the design makes a first-class decision, for a performance win we don't need.

The web shell's fate DECIDED · keep for now, drop later

Owner decision: "keep it for now, we'll drop when the new UI is ready." The E-UISHELL web UI (GET /, ui.html) stays untouched through this epic — both surfaces are clients of the same API, so there's no conflict. E-UIFOUND does not migrate or retire it; the native app is built alongside. Retiring the web shell (drop GET / + ui.html, rewrite UC-3) becomes a later step, triggered once the native UI reaches parity — tracked as a follow-up, not in this epic's scope.

What the epic becomes (once Q1 is picked)

Q2 (out-of-process) and the shell (keep for now) are settled. With Q1 answered, E-UIFOUND's plan writes into these Working Units (illustrative — finalized in the T3 plan):

  • The DEC — record the framework choice + out-of-process topology as a T2 decision; update the roadmap's E-UIFOUND row and its "browser-based" / single-binary framing; note the reversal.
  • Project + build integration — the GUI project set up (a Rust crate in the workspace if Freya; a JS/TS react-native-macos project if RN); xtask builds/runs it and the core together.
  • Design system — tokens seeded from the existing ui.html palette (--bg #181b22, --accent #5ab0f7, etc.) + base components in the chosen framework.
  • Base app layout — the shell later epics (E-UIINSPECT inspector, E-UISETUP onboarding) slot into; the live flow list (over /flows + /stream) is its first tenant.

If the pick is Freya, WU-1 should be a spike: 5K streaming rows through VirtualScrollView to confirm perf before the design system is built on it.
