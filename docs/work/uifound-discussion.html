The pivot — why this needs a recorded decision

The roadmap frames every UI epic around the API-first web UI, and E-UISHELL already shipped an embedded web shell (vanilla JS at GET /). The Owner's direction moved the primary UI to a standalone Tauri desktop app. That's a strategic reversal of a pillar's delivery mechanism, which the roadmap says must be "recorded as a decision and then reflected here" — so this feeds a DEC, and the roadmap's E-UIFOUND row + its "browser-based" / single-binary framing get updated when it lands. (Tauri does render UI in the OS webview, so "not a bundled browser" is the honest framing, not "not browser-based" — noted in Q1.)

The invariant that survives the pivot: the core stays UI-agnostic (core-technical-design.html: "any UI is a client"). The out-of-process topology keeps that true by construction — the React UI is a pure API client, the Tauri process holds no core logic. The existing web shell stays as a second client (shell's fate).

Q2 · Embedding / topology DECIDED · out-of-process

Owner decision: "go with opt 2" → Topology 2, out-of-process. The React frontend (in the thin Tauri shell) drives 127.0.0.1:7421 (REST + SSE) via fetch + EventSource, exactly like a browser or curl would. This keeps API-first fidelity fully intact (the UI can only do what the public API exposes) and lets the core run headless for CI/scripting/remote-tunnel use. It fits the Tauri choice cleanly: the Tauri Rust process stays a window shell and holds no core logic. The comparison that led here is kept below for the record.

The native app has to get flows + live events from the core. Three topologies, scored against the one invariant that matters here — does the GUI stay a pure client of the public API, or does it reach behind it and fork the feature surface?

Dimension1 · In-process (direct)2 · Out-of-process (HTTP) chosen3 · Hybrid
HowGUI compiled in; reads Arc<Store> + broadcast::Receiver directly, no HTTP hopSeparate binary; drives 127.0.0.1:7421 REST+SSE like the web UI / curlOne binary; starts trawler::run() in-process but GUI still talks to it over loopback :7421
API-first fidelityVIOLATED — imports internal types; two feature surfaces emergeFULL — GUI can only do what the API exposesFULL — same as 2; no Store ref leaks into GUI
Single binaryYesNo — two binaries, must ship togetherYes
Streaming pathDirect broadcast::Receiver, zero overheadSSE over TCP + reconnect logic; ~0.5 ms loopbackSSE over loopback (same as 2), server end same process
LifecycleOne process, simplestSpawn/kill child, port coordinationOne process; ~20 lines startup sequencing (wait for API ready)
TestabilityPoor — GUI couples to internals; no contractBest — testable vs real/mock API serverGood — GUI decoupled; one startup seam to test
Headless coreNo — GUI drags in at compile timeYesYes — --headless flag skips GUI
Matches design docNo (breaks the stated invariant)YesYes

Why Hybrid: it's the only option that keeps API-first fidelity and ships a single binary. The cost over out-of-process is ~20 lines of "wait for :7421 to bind before the GUI opens its SSE stream"; the cost over in-process is one loopback TCP hop, imperceptible at UI refresh rates. This is the standard pattern for Charles / Proxyman / Wireshark (one app bundle, internal API). Deviate to Topology 2 only if the core must run on a remote host (SSH-tunnel use case) or you want independently-versioned GUI and core. Avoid Topology 1 — it permanently breaks the invariant the design makes a first-class decision, for a performance win we don't need.

Supporting pieces — how the React UI reaches the API

With Tauri, the frontend is a webview, so the data path uses the same web primitives the existing shell already uses — no extra crates, no Tauri command bridge:

Live events (/stream)native EventSourceBuilt into the webview runtime — new EventSource('http://127.0.0.1:7421/stream'), with request/response/lagged listeners. Zero dep, auto-reconnect. Same pattern the existing web shell already uses.
REST (/flows, …)native fetchStandard fetch to 127.0.0.1:7421. No Tauri command bridge — the Tauri Rust process is not in the data path.

The web shell's fate DECIDED · keep for now, drop later

Owner decision: "keep it for now, we'll drop when the new UI is ready." The E-UISHELL web UI (GET /, ui.html) stays untouched through this epic — both surfaces are clients of the same API, so there's no conflict. E-UIFOUND does not migrate or retire it; the native app is built alongside. Retiring the web shell (drop GET / + ui.html, rewrite UC-3) becomes a later step, triggered once the native UI reaches parity — tracked as a follow-up, not in this epic's scope.

Tension to flag: Warp's palette is warm-dark + off-white, zero chromatic accent; the current ui.html uses a cool-dark blue-accent scheme (--bg #181b22, --accent #5ab0f7, green/red status). Adopting Warp means status colors (2xx ok / 4xx-5xx error) need a deliberate exception to the "no chromatic accent" rule — a debugging proxy genuinely needs to distinguish success/error at a glance. The design-system WU resolves how far to follow Warp vs. keep functional status color. I'll default to Warp for chrome/typography, keep functional status colors unless you say otherwise.
