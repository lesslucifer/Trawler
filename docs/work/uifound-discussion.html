E-UIFOUND — Native UI Stack (Discussion)

The foundation epic pivots to a native Rust desktop app. This doc lays out the fork, the researched options, and the two decisions the Owner must make before planning.

Draft v1 · 2026-07-11 · Trawler · T3 discussion · roadmap · decisions

TL;DR — what this doc decides

E-UIFOUND's requirement is "UI tech stack decided (as a DEC), codebase in cargo/xtask build, design system + base app layout; shell migrated onto it." The Owner has set a new direction: the UI is a native app built in Rust, not browser-based. That reverses the roadmap's embedded-web-UI assumption, so it needs a recorded decision — this doc is the pre-decision discussion. Two choices come out of it, both the Owner's to make:

Q1 · GUI framework

Which Rust native GUI toolkit the foundation adopts. Top realistic picks: egui, Iced, Slint. Webview toolkits (Tauri, Dioxus-desktop) are disqualified by "not browser-based".

Q2 · Embedding / topology

How the native app relates to the existing API-first core: in-process, out-of-process over the local HTTP API, or hybrid (one binary, still routed through the loopback API). This is the "how do we embed it" question.

My recommendation, up front: egui/eframe for Q1 (fastest path, built-in virtualized tables for thousands of streaming rows, permissive license, single binary) and Hybrid (Topology 3) for Q2 (keeps the API-first invariant intact and ships one binary). Everything below is the evidence. Pick from the option tables and I'll write the epic plan + the DEC.

The pivot — and why it needs a decision

The roadmap frames every UI epic around the API-first web UI: "every GUI capability is a call on the public API, so the GUI never forks the feature surface," and E-UISHELL already shipped an embedded single-binary web UI (vanilla JS at GET /, served via include_str!). E-UIFOUND was scoped to migrate that shell onto a designed layout. Going native instead of web is a strategic reversal of a pillar's delivery mechanism. The roadmap explicitly says such reversals are "recorded as a decision and then reflected here" — so this discussion feeds a DEC, and the roadmap's E-UIFOUND row + the "browser-based" framing get updated when it lands.

What the pivot must resolve: the API-first invariant is a core design decision (core-technical-design.html: "trawler-core is UI-agnostic… any UI is a client"). A native app can honour it or break it depending on how it embeds — which is exactly why Q2 (topology) matters as much as Q1 (framework). The existing web shell doesn't disappear for free either: see the shell's fate.

Q1 · GUI framework

App needs: a live-updating filterable flow list (thousands of rows, streaming), inspector panels (headers, JSON trees, hex, images), macOS-primary but cross-platform, single-binary. Research covered the full 2026 landscape; below are only the realistic, non-webview contenders. disqualified Tauri and Dioxus-desktop are webview-based (WKWebView/WebView2) — they render HTML/CSS, i.e. browser-based, which the Owner ruled out. xilem (alpha, no table widget), Dioxus-native/Blitz (pre-alpha), and gtk-rs (non-native macOS look, LGPL) are also out for this app.

Why egui is the default: the app is a real-time data inspector — immediate-mode maps directly onto "repaint when a new flow arrives over SSE," with no retained-state sync. It's the only realistic pick with built-in virtualized tables for the thousands-of-rows flow list (the exact Rerun.io workload), the smallest binary, and a permissive license with zero cost. The ceiling is aesthetics (not native chrome) and a hand-built tree view — acceptable for a devtool. Choose Iced if you want a cleaner retained architecture and can accept the accessibility gap; Slint if native polish is worth the DSL and the license question; gpui only if you'll accept living on an unmaintained-for-community pre-1.0 framework for its superior components.

This is the tech the Owner asked me to research and compare. The native app has to get flows + live events from the core. Why Hybrid: it's the only option that keeps API-first fidelity and ships a single binary. The cost over out-of-process is ~20 lines of "wait for :7421 to bind before the GUI opens its SSE stream"; the cost over in-process is one loopback TCP hop, imperceptible at UI refresh rates. This is the standard pattern for Charles / Proxyman / Wireshark (one app bundle, internal API). Deviate to Topology 2 only if the core must run on a remote host (SSH-tunnel use case) or you want independently-versioned GUI and core. Avoid Topology 1 — it permanently breaks the invariant the design makes a first-class decision, for a performance win we don't need.

The web shell's fate

E-UISHELL shipped the vanilla-JS web UI at GET /, and the roadmap priced in "migrated onto the foundation's layout as its first tenant." With a native pivot the honest options are:

A · Keep the web shell, add native alongside

Both are clients of the same API. Web UI stays the zero-install / remote-access surface; native becomes the primary desktop experience. Nothing thrown away. recommended

B · Retire the web shell

Native replaces it; drop GET / and ui.html. Simpler surface, but loses the zero-setup browser view (and UC-3 needs rewriting).

The "shell migrated onto the foundation" clause in the requirement was written for a web foundation. Under a native pivot it either becomes "native app built on the foundation layout" (the web shell staying as-is, option A) or "web shell retired" (option B). This is a smaller call than Q1/Q2 but the plan needs it pinned. I lean A — keeping a browser view costs nothing and preserves the zero-install adoption path E-UISHELL was built for.

What the epic becomes (once decided)

With Q1 + Q2 answered, E-UIFOUND's plan writes itself into these Working Units (illustrative — finalized in the T3 plan after the Owner picks):

  • The DEC — record the stack + topology choice as a T2 decision; update the roadmap's E-UIFOUND row and "browser-based" framing; note the reversal.
  • Build integration — the GUI crate in the cargo workspace; xtask builds/runs it; single-binary output with --headless.
  • Design system — tokens (the existing ui.html palette is a starting point: --bg #181b22, --accent #5ab0f7, etc.) + base components in the chosen framework.
  • Base app layout — the shell that later epics (E-UIINSPECT inspector, E-UISETUP onboarding) slot into; the live flow list is its first tenant.
  • Shell resolution — per option A or B.
