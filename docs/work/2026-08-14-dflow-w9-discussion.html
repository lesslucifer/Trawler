D3 · Which gate leg fires — and does W9 need both?

W8 built two legs. new_surface fires on an added registry component or screen; the edit leg fires on a modified rendered file. Rebuilding Onboarding.tsx modifies — so by default only the edit leg fires.

This is the leg that matters. W8 step ⑥ measured the added-only trigger's whole population as already built — "every UI change it could ever see was one nobody was going to make". The edit leg is the one a repo where everything is built actually exercises, and it has never fired on a real edit. If the redesign also proposes a new component, both legs fire from one run and no scope is added to force it.
Ruled · both fire. W9 exercises both legs, not just one.

What that means in practice. The two legs fire on different things:

D5 · Why Tier-3 needs a design it is supposed to fail

Restated — round 1 said "I dont get this", so here it is from the beginning.

What Tier-3 is. An AI reviewer that reads a finished design and judges it against the 17 soft rules — the ones no program can check. Is the wording calm? Does the grouping follow relatedness? When the design quotes a component's @avoid, did it quote it honestly? It writes PASS or FAIL into the review note, and a FAIL refuses the merge.

What has never happened. It has never judged a real design. W7 proved it runs — over the right files, against the right rulebook, and that its silence is loud. W7 never proved it judges. That is the whole of debt D1.

So why isn't running it on W9's design enough? Suppose we run it and it says PASS. Two different worlds produce exactly that output:

WorldWhat it outputs on W9's designWhat we learn
The finder works, and the design really is cleanPASS The tier is good
The finder is broken and says PASS to everythingPASS Nothing — and we would ship believing the tier is good

From one PASS you cannot tell those apart. A gate that has only ever been shown green is indistinguishable from a gate that cannot go red — which is the same bet DEC-15 records this project losing eleven separate times.

The fix, in one sentence: also hand it a copy of the same design with one deliberate, known break in it, and require it to say FAIL.

flowchart LR
    A["run #4's real design"] --> T{"Tier-3 finder
same run, same rulebook pin"}
    B["a doctored copy —
one @avoid paraphrased dishonestly"] --> T
    T -->|"must be PASS"| P["✓ the tier can pass a good design"]
    T -->|"must be FAIL"| F["✓ the tier can catch the defect it solely owns"]
    P --> ACC["accepted"]
    F --> ACC
Two inputs, two required outputs. Either result alone is unfalsifiable; together they are a test the finder cannot pass by accident.

Which break, concretely. The one defect class Tier-3 solely owns (D2 in the debts table): a design that cites a component and paraphrases its @avoid as something the TSDoc does not say. It is mechanically undecidable — W7 ② measured that, which is why no hard rule can catch it — and it is the defect run #3 actually shipped. If Tier-3 misses it, nothing in the harness catches it.

The doctored copy is scratch input: it never lands in the tree, never enters design-scope's output, and never appears in the review note. It exists for the length of one check.

Ruled · yes, and the broken one goes first. "Let's deliver the first version that fail before apply the real version." So it is a sequence, not two checks run side by side:
① submit the doctored design → Tier-3 must return FAIL. If it passes, the tier is broken and W9 stops there — nothing downstream is worth running.
② only then submit the real design → Tier-3 must return PASS, and that PASS is now worth something, because the same finder was just shown able to say FAIL.
Why the order matters: run them together and a convenient result can be chosen after the fact. Red first, green second, makes the FAIL a precondition — the same shape as writing a failing test before the code that satisfies it.

D6 · The regression floor

28 unit tests and an 86-line e2e guard the shipped screen. Fork: the rebuild keeps them green unchanged (they become the conformance oracle), or they are rewritten alongside the build?

Round 1 · "keep them unchanged" → round 2 · retire them. The first instinct was right about the risk (a rebuild that rewrites its own oracle proves nothing) but could not coexist with D2. Round 2 resolved it the other way: the suite is retired with the design it was written against. Both rounds are kept — the reasoning is below.

The clash round 1 created — D2 against D6

These two rulings arrived in the same pass and cannot both hold as written.

RulingSays
D2"We will redesign the full flow, UI / UX here" — and UC-ONBOARD may be amended to match
D6"Keep them unchanged" — the 28 unit tests and the 86-line e2e stay as they are

Why they collide. The suite does not assert what onboarding does. It asserts how the current design does it — verbatim:

What the test saysDesign decision it has hard-coded
getByText(/Trust the CA/)this exact wording — and calm-microcopy + one-term-per-concept are soft rules a redesign will read
getByTestId("step-trust-ca") has data-status="active"three named steps, one active at a time

fireEvent.change(getByTestId("trust-target"), {value:"windows"}) a <select> the user must operate to pick an OS

The worked case. Suppose run #4 concludes the OS should be auto-detected with a "not my OS?" escape hatch instead of a dropdown — an ordinary conclusion, with progressive-disclosure and generous-targets both in the rulebook. getByTestId("trust-target") then matches nothing and the test is red. To keep it green you keep the dropdown; to keep the dropdown you do not redesign. D6 read literally is a veto on D2.

What untangles it is that those tests are doing two jobs at once:

JobExampleSurvives a redesign?
Capability"a failed CA install shows the error and does not claim Trusted"Must — losing it is a regression whatever the UI looks like
Design"there is a step-trust-ca element and onb-next advances it"No — that is the old design describing itself

D6 protected both. Only the first was worth protecting, and the second is exactly what D2 licensed changing.

ReadingWhat it means in practiceCost
R1 · coverage frozen, assertions may move Every capability the current tests assert must still be asserted after the rebuild. The assertions may be rewritten to match the new UI; none may disappear. A test that must be dropped rather than rewritten is a finding, and requires the matching UC-ONBOARD / DEC-13 amendment to say so out loud Bookkeeping: the WU owes an explicit before/after coverage map, so a silent deletion cannot hide inside a rewrite

Ruled · R3 — the old suite is retired, not preserved. "The tests should be renewed as well, drop them." The 28 unit tests and the 86-line e2e were written against a design W9 is replacing; they go with it, and W9 writes the suite its own design needs. The mandatory levels are unaffected and still owed in full: a Working Unit owes its integration test, every commit owes unit tests for what it changes, and the epic owes its e2e.
What R3 gives up — recorded once here so the result report does not have to discover it. W9 keeps no independent regression evidence. The run that changes the UI also writes the tests that judge it, so a green suite proves the new build matches the new design and nothing more. The moment the old suite is deleted, UC-ONBOARD's shipped capabilities have no guard except the new design's own idea of them.
The receipt that costs one table (default; say so if you want it gone): W9's result carries a coverage map — what each retired test asserted, and either where that assertion landed in the new suite or why it was deliberately dropped, with the matching UC-ONBOARD / DEC-13 amendment. Q1 · What if the redesign needs no new component? ruled: no

The setup. You ruled that both gate legs must fire (D3). The edit leg is guaranteed — W9 rewrites a file that exists. new_surface fires only if W9 adds a file that did not exist before: a new component in the collection, or a new screen.

The situation that might arise. Run #4 designs the new onboarding, and it turns out everything it needs is already in the registry — StepList for the manual steps, Notice for the capture-is-working zone, Select for the OS picker, the Button trio for the actions. Nothing new is added. So new_surface never fires, and "both fire" cannot be satisfied.

The question is simply: do we invent a component so the predicate fires?

AnswerWhat happensWhat it costs
Yes — force it Add a component the design did not ask for, so new_surface is guaranteed to be exercised The component exists to satisfy a gate, not to serve a design. That is a fake surface — a miniature of the exact "fake build" sin W9 exists to pay off
No — report it (default) Write down that the design honestly proposed nothing new and that new_surface stayed unexercised, and carry it as a named gap new_surface remains unproven by real work. But the report is itself a finding worth having: a full redesign of the app's largest screen needed zero new components is a real statement about how well the registry covers the app
Ruled · no. If the design honestly proposes nothing new, that is written down as a named gap and no component is manufactured to trip the predicate. Carried into the plan at step ④.
Likelihood, for calibration: low. A greenfield redesign of a 464-line screen probably does want something the collection lacks — and the registry currently has no T3/T4/T5 entries at all (24 components, 13 T1 + 11 T2), so anything screen-shaped the design proposes is new by definition. Q1 most likely never fires. It was asked anyway because a rule invented after seeing the result is not a rule.

Also carried into the plan, not questions: DEC-13 is in scope alongside UC-ONBOARD (D2) · the epic plan's two non-goals get struck in writing on DEC-25's authority, with the reason recorded (D4) · run #4 against run #3 is measured as a repeatability read after #4 closes, never as an input to it (D1) · DEC-17's 7-of-13 never-red figure is re-taken before any plan row rests on it · the retired suite's coverage map is an output of the WU (R3).

Scope — round 0's Q5 got no answer, so its default is still only a default. The question was whether to split the build into its own Working Unit. Round 1's answer to D2 made it heavier, not lighter. Standing default: one Working Unit, because splitting re-opens the exact gap DEC-25 exists to close. It becomes a ruling the moment you say so — or the moment W9's plan lands on it unchallenged.
