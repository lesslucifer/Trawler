1 · Frame

Purpose: a first-run operator, on the machine Trawler runs on or pointing a second device at it, gets from a fresh install to one decrypted request.

Given (received, not designed): trust probe · proxy probe · observed traffic · observed decrypt · one-click install, set and unset on macOS/Windows · per-target instructions · copyable commands · the configured address · host OS · the proven latch

Not given (may not be assumed): a remote trust probe · per-device attribution · a reason for a failed handshake · firing the request itself · progress inside an elevated action · any confirmation that a manual install worked

2 · Layout

┌──────────────────────────────────────────────┐
│ A  outcome                                   │  ← the whole screen's answer, one sentence
├──────────────────────────────────────────────┤
│ B  preconditions                             │  ← two, each verdict + action + its guide
│                                              │
│                                              │
├──────────────────────────────────────────────┤
│ C  first flow                                │  ← the command that causes one, copyable
├──────────────────────────────────────────────┤
│ D  way out                                   │  ← present only once ever proven
└──────────────────────────────────────────────┘

overflow: A is one sentence and C is one command, so neither can grow; a long
          command wraps rather than clips, which is wrap-not-truncate and not a
          cap. D is one control. B is the only unbounded zone — an instruction
          list grows with the target — and it is not capped internally: each
          StepList's own no-truncate-and-no-scroll rule is StepList's, cited not
          re-annotated. The whole column is capped at the dialog-max token and
          centred; the page behind it scrolls.

Why four zones and not three steps. A stepper needs a cursor, and a cursor is a claim about progress the app cannot observe — StepList's @avoid refuses to draw one and StatusLine owns the verdict instead. So the screen zones by what is true (A), what must become true (B) and what proves it (C), and the boundary between B and C is the seam between things the user does and the thing that judges them.

What the build forced that the earlier stages had not. Three things. The verdict cannot sit under the precondition's name without the row reading as two unrelated lines, so the name and the verdict share one row and the action drops below — which is what makes fork D4's "in the same zone" true rather than asserted. The seam has to be a bottom hairline on each precondition rather than a divider between them, or the last precondition loses its floor and the zone below it reads as part of it. And the guide's picker had to move above the steps: a selector after what it selects reads as a filter on a result.
