E3 · work-planning — plan outputs & result reports, checklist-verified

T3 plan: define what the planning phase of an epic/WU must output and what the result report after the work must contain — as minimum-content checklists verified by a script that the existing hooks trigger mechanically, never as fixed templates.

Draft v3 · 2026-07-05 · Trawler · T3 work doc · epic/work-planning

Epic requirement

Planning and result-reporting get defined outputs. For each output the T1 standard gives a checklist of what must at least be in it and a mechanical check — a script in the verify-dod family that verifies a doc against its checklist and prints the problems when it falls short — while the form stays free: a plan or report may be prose, tables, diagrams or widgets, shaped creatively to fit its task. Nobody remembers to run the script: the existing git hooks trigger it, so forgetting is not a failure mode any more than forgetting clippy is.

Expected result — observable

  • docs/work-planning.html (T1) exists and owns: the planning outputs of an epic and of a WU, the result-report outputs of an epic and of a WU, one minimum-content checklist per output, the markup contract that makes the items machine-findable, and the trigger points where the check runs.
  • An agent starting any epic can produce a conforming plan — and close any epic/WU with a conforming result report — from the standard alone, without copying a skeleton.
  • cargo xtask verify-doc <path> verifies any governed doc against its checklist: exit 0, or exit 1 with one problem block per missing/weak item in the house red style (item, expected vs found, fix →).
  • The check is impossible to forget: the hooks that already gate the repo invoke it — a commit touching a governed doc, a WU merge, an epic merge each fail while a required doc is absent or red.
  • workflow.html's plan-artifact cells link to the standard instead of half-defining it.

Non-goals

  • No fixed templates. The standard constrains substance (items that must exist), never form. A skeleton to copy-paste is explicitly what we don't want.
  • No new evidence machinery. No new note schemas, no receipts — the check is re-runnable on any doc at any time, its verdict is never stored. Triggering reuses the hooks that already exist (pre-commit, pre-merge-commit); no new hook types.
  • No tracker files or dashboards.
  • No work estimates anywhere in plans or reports (AI-first rule).

The gap

workflow.html mandates "one T3 work doc listing its WUs, each with requirement sentence + detailed test plan" — and stops there. E1's brainstorm and E2's plan already diverge in what they contain; nothing says what a complete plan holds, and nothing at all defines what to produce after the work: today an epic ends with evidence notes and distilled T2 docs, but no result report states what was delivered against what was planned, what deviated and why. Quality of plans and reports is judged by taste, per-session, with no checklist to judge against.

Every artifact is checked mechanically at a point git already controls: committing a governed doc verifies it on the spot; the merges refuse to happen while a required doc is absent or red.

The four outputs. Planning phase: the epic plan (one T3 doc per epic) containing a plan entry per WU. After the work: a result report per WU (written when the WU completes) and an epic result report (at epic close) — each result report is its own separate T3 doc under the normal naming rule (docs/work/YYYY-MM-DD-<wu-or-epic-slug>-result.html). All T3 lifecycle rules (distill, then archive) apply unchanged.

The mechanical check. Free form and a mechanical check coexist through a minimal markup contract: a governed doc declares what it is (data-artifact="epic-plan | wu-result | epic-result", WU plan entries marked inside the epic plan) and each checklist item is tagged where it lives (data-item="intent", data-item="expected", …) — any element, any order, any form around it. cargo xtask verify-doc <path> reads the artifact type, selects its checklist, and checks every item: present, non-empty above a substance floor, no placeholders (TBD/TODO), no estimate language (AI-first rule), plus per-type consistency (an epic plan must hold ≥ 1 WU entry, each complete). Anything red prints as one problem block per item — check id, expected vs found, fix → — exit 1.

Who triggers it — nobody, by design. An agent that must remember a check will eventually forget it, so the script rides the hooks that already refuse bad git actions: pre-commit runs verify-doc on every governed doc in the commit's diff (instant feedback, the red doc never enters history); the wu merge gate refuses the merge while the epic plan or the WU's result doc is absent or red; the epic merge gate does the same for the epic result doc. Manual runs work anytime for feedback, but no workflow step depends on an agent remembering one — exactly the fmt/clippy/verify-dod trust boundary.

Design notes

Checklists over templates. A fixed template optimizes for uniformity and rots into cargo-cult sections; a checklist optimizes for completeness while letting each task pick the form that carries it best (E2's plan was right to be 57 terse lines; a protocol-heavy epic may need diagrams and a widget). The standard therefore never prescribes headings or order — only items, their meaning, and the quality bar.

How far the mechanical check reaches. The markup contract is what lets a script verify substance without a rigid template: items are addressable wherever the author put them, so the script checks presence, floors and red-flag content — the minimum quality the manager's checklist demands. Whether an "observable expected result" is truly observable stays a semantic call: that lives where judgment already lives (the code review that reads the plan, the user's comment round), on top of — never instead of — the script.

Relation to the DoD gates. Additive, not entangled: verify-doc is its own subcommand with its own checklist logic; the existing hooks and merge gates gain one more call site, and no evidence note or receipt schema changes. The docs-only exemption keeps meaning "no test/review evidence demanded" — it does not exempt a WU or epic from having its plan and result docs, since those exist precisely when code doesn't.

Open questions

  • How aggressive are the substance rules? Proposed start: non-empty, a small per-item character floor, placeholder words, estimate language — tuned against real docs during W2's dry-run. Too-strict heuristics would push authors into padding, which is boilerplate by another name.
  • Pre-standard docs. E1's brainstorm and E2's plan predate the markup contract. Proposed: grandfathered exactly like v1 notes — ungoverned docs are ignored; only docs declaring data-artifact are checked, and everything from E3 on must declare it (the merge gates enforce that from E3's WUs onward).
  • Result doc for a collapsed epic. A one-WU epic writes one combined result doc proposed (data-artifact declares both roles) rather than two near-identical files.
