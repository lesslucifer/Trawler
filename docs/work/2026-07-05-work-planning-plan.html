E3 · work-planning — plan the work, gate the result

T3 plan: standardize what an epic/WU plan must state before work starts, and close the loop with a result report the epic gate verifies against what actually landed.

Draft v1 · 2026-07-05 · Trawler · T3 work doc · epic/work-planning

Epic requirement

Planning and result-reporting become checkable structure instead of convention. A T1 standard defines what every epic and working-unit plan must state before work starts — requirement, expected result, test plan — and every epic closes with a result report on its tip (a report/v1 git note, the fifth evidence note) that verify-dod cross-checks against the work that actually merged. Deviations from the plan surface in evidence, never only in an agent's word.

Expected result — observable

  • docs/work-planning.html (T1) exists and is the single owner of the plan shape and the report/v1 schema; workflow.html links to it (plan-artifact cells, evidence table, DoD-E row) instead of restating it.
  • cargo xtask verify-dod epic goes red when the epic tip lacks a valid report/v1 note, or when the report disagrees with the epic walk — a merged WU seam missing from the report, or a WU reported delivered that never merged.
  • The green path is unchanged except the receipt's checks list appends report.
  • E3's own merge into main is the first demonstration: it carries the first report/v1, written against this plan.

Non-goals

  • No per-WU report notes — the epic report carries one entry per WU; a WU tip already holds test/v2 + cr/v2 + dod/v1. Upgrade only if an epic report proves too coarse in practice.
  • No tracker files, dashboards, or tooling beyond git notes and verify-dod.
  • No changes to the test/v2, cr/v2, doc/v1 schemas.
  • No work estimates anywhere in plans or reports (AI-first rule).

The gap

workflow.html mandates "one T3 work doc listing its WUs, each with requirement sentence + detailed test plan" but nothing owns the plan's required shape — E1's brainstorm and E2's plan already diverge. DoD-W's "requirement recorded before the code" is a judgment with no standard to judge against. And the gates prove tests ran, review passed and docs distilled — but nothing proves we delivered what we planned: a silently dropped WU or a scope swap leaves no evidence anywhere.

The loop this epic closes: expectation stated before work, outcome verified after, both as evidence.

The plan (one T3 doc per epic, written before the epic branch does work; this document follows the shape it proposes): epic intent as one requirement paragraph · expected result as observable acceptance, not intention · non-goals · one section per WU with its requirement sentence, expected result and detailed test plan · design notes and open questions as needed. The plan is living during the epic — amended in place, snapshots keep evolution reviewable — but every deviation from the original expectation must resurface in the result report.

The report (at epic close, before the merge into main): a report/v1 YAML note on the epic tip. Identity block like every note schema · plan path · the epic's expected result restated in one line (evidence stays self-describing after the plan is archived) · epic outcome · one entry per planned WU (delivered | deviated | dropped, one line of what/why + evidence pointer) · unplanned work accounted. Existence and consistency with git are mechanical; adequacy and honesty of the prose are judged by the epic review, whose finders read plan and report.

Design notes

Why a note, not a report section in the plan doc. E2 (doc-archive, in flight) removes archived docs from the tracked tree — at the epic tip the plan file no longer exists, so a file-content check would be inspecting deleted content. Notes are the house evidence channel: tamper-evident (they orphan on rewrite), queryable by identity (cargo xtask dod list), and the epic walk already enumerates WU seams to reconcile against. The report is evidence, not documentation — durable knowledge still distills to T2 exactly as before; the report proves the plan→result loop closed.

WU-level expectations without WU-level reports. A WU's expectation lives in its plan section; its result is one entry in the epic report. The collapse rule carries over: a one-WU epic still reports, with one entry.

E2 interaction. E3 branches off main, which does not yet carry E2's absolute tracked-docs check; the two are independent — the plan-existence check at the wu gate looks at merge-time trees (plan tracked while the epic is live), E2's check looks at epic tips (plan archived by then). Whichever lands second rebases nothing.

Open questions

  • Report granularity — epic-only is proposed. Want per-WU report notes anyway (heavier, but each WU merge would self-report)?
  • Restating expected in the note — proposed yes (one line), so the evidence is self-describing after the plan leaves the tree; the alternative is a bare plan path and a trip through git history.
  • Plan-existence check at the wu gate — proposed in. Drop it if plan-before-code should stay pure judgment.
