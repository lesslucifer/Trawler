E3 · work-planning — plan outputs & result reports, checklist-verified

T3 plan: define what the planning phase of an epic/WU must output and what the result report after the work must contain — as minimum-content checklists verified by a script the agent harness triggers at authoring time, never as fixed templates, never as git hooks.

Draft v5 · 2026-07-05 · Trawler · T3 work doc · epic/work-planning

Epic requirement

Planning and result-reporting get defined outputs. For each output the T1 standard gives a checklist of what must at least be in it and a mechanical check — a script in the verify-dod family that verifies a doc against its checklist and prints the problems when it falls short — while the form stays free: a plan or report may be prose, tables, diagrams or widgets, shaped creatively to fit its task. Nobody remembers to run the script and nothing waits for git: the agent harness triggers it the moment a governed doc is declared ready — and on every edit after — so a low-quality plan is caught while it is being authored, before any work is built on it, and forgetting is not a failure mode because no one has to remember.

Expected result — observable

  • docs/work-planning.html (T1) exists and owns: the planning outputs of an epic and of a WU, the result-report outputs of an epic and of a WU, one minimum-content checklist per output, the markup contract that makes the items machine-findable, and the harness trigger points where the check runs.
  • An agent starting any epic can produce a conforming plan — and close any epic/WU with a conforming result report — from the standard alone, without copying a skeleton.
  • cargo xtask verify-doc <path> verifies any governed doc against its checklist: exit 0, or exit 1 with one problem block per missing/weak item in the house red style (item, expected vs found, fix →).
  • The check is impossible to forget, never late, and never noisy: a harness hook in the project's .claude/settings.json runs verify-doc on every Write/Edit of a ready governed doc and feeds the problems straight back into the authoring session — drafts iterate in silence; a turn-end backstop refuses to conclude while a ready governed doc in the tree is red.
  • workflow.html's plan-artifact cells link to the standard instead of half-defining it.

Non-goals

  • No fixed templates. The standard constrains substance (items that must exist), never form. A skeleton to copy-paste is explicitly what we don't want.
  • No git machinery. No git hooks — commit/merge time is too late for a doc check: the work would already stand on a low-quality doc. No new note schemas, no receipts — the check is re-runnable on any doc at any time, its verdict never stored. The DoD gates are untouched.
  • No tracker files or dashboards.
  • No work estimates anywhere in plans or reports (AI-first rule).

The gap

workflow.html mandates "one T3 work doc listing its WUs, each with requirement sentence + detailed test plan" — and stops there. E1's brainstorm and E2's plan already diverge in what they contain; nothing says what a complete plan holds, and nothing at all defines what to produce after the work: today an epic ends with evidence notes and distilled T2 docs, but no result report states what was delivered against what was planned, what deviated and why. Quality of plans and reports is judged by taste, per-session, with no checklist to judge against.

Drafts iterate in silence — no false positives mid-authoring. Declaring the doc ready is the checkpoint; from there every edit re-verifies, and red never survives a turn. The backstop also catches docs edited around the file tools (e.g. via shell).

The four outputs — each its own T3 doc. Planning phase: the epic plan (one doc per epic, carrying only a summary per WU — what it builds, what it maps to, expected outcomes, dependencies) and a WU plan per WU (its own doc, written before that WU's code, where the full WU planning lives). After the work: a WU result report (when the WU completes) and an epic result report (at epic close). Naming follows the normal T3 rule (docs/work/YYYY-MM-DD-<slug>-plan.html / …-result.html); a collapsed one-WU epic may combine the two plans in one doc and the two results in one doc, each declaring both roles. All T3 lifecycle rules (distill, then archive) apply unchanged.

Draft checklists — v0, to be refined and owned by the T1. Every item has an exact, normative tag; the script verifies each tagged section exists with content. Tagging is strict by design: content sitting under a wrong or missing tag is red — the tag is the contract — and the verifier reports unknown tags by name next to the missing item, so a typo reads as "unknown tag expcted / missing item expected" and the fix is obvious. Whether the content is substantive — task-specific, observable where it claims to be, never boilerplate — is the quality bar the standard states and the existing reviews judge.

The mechanical check — strict tag verification. Free form and a mechanical check coexist through a minimal markup contract: a governed doc declares what it is (data-artifact="epic-plan | wu-plan | wu-result | epic-result"), declares its state (data-status="draft" while authoring; absent or ready = ready), and tags the section holding each checklist item with that item's exact tag from the tables above — any element, any order, any form around it; the standard instructs authors to tag as they write, and to tag precisely. cargo xtask verify-doc <path> reads the artifact type, selects its checklist, and checks exactly this: every item's tagged section is present with non-empty content, the type's structure holds (an epic plan carries ≥ 1 data-wu block, each with its four sub-tags), and no unknown tags exist for the type — the typo guard that turns "content there, tag wrong" into a named, fixable problem instead of a mystery. Nothing cleverer — depth of content is review territory. Anything red prints as one problem block per item — check id, expected vs found, fix → — exit 1. Docs that declare no data-artifact are not governed and are ignored — pre-existing docs (E1's brainstorm, E2's plan) are simply skipped, never retrofitted.

Who triggers it — the harness, at authoring time. Git hooks are the wrong point: by commit or merge the work already stands on the low-quality doc. An agent that must remember a check will eventually forget it. So the trigger is the agent harness itself, via hooks versioned in the project's .claude/settings.json — the harness executes them, not the agent, and in an AI-first repo every author is a harness session, so authoring-time coverage is total: a PostToolUse hook fires on every Write/Edit whose target is a ready governed doc, runs verify-doc on it, and on red injects the problem blocks straight back into the session as feedback — the authoring agent must fix the doc now, before anything is built on it; and a Stop hook backstops the loop — a turn is refused to end while any ready governed doc in the working tree is red, which also catches docs edited around the file tools (shell, scripts). Drafts (data-status="draft") are exempt from both, so a doc under construction never spams false positives — it iterates silently, across turns and review rounds if needed, and the flip to ready is the moment it gets checked. A doc left draft while work proceeds on it is exactly the kind of finding the reviews that read these docs exist to catch. Manual runs work anytime for feedback; no workflow step depends on anyone remembering one.

Design notes

Checklists over templates. A fixed template optimizes for uniformity and rots into cargo-cult sections; a checklist optimizes for completeness while letting each task pick the form that carries it best (E2's plan was right to be 57 terse lines; a protocol-heavy epic may need diagrams and a widget). The standard therefore never prescribes headings or order — only items, their meaning, and the quality bar.

How far the mechanical check reaches. Deliberately simple: the markup contract makes every checklist item addressable wherever the author put it, and the script verifies the tagged sections exist with content — no heuristics about how the content reads. That keeps false positives near zero and the contract easy to satisfy honestly. Whether an "observable expected result" is truly observable stays a semantic call: that lives where judgment already lives (the code review that reads the plan, the user's comment round), on top of — never instead of — the script.

Relation to the DoD gates. None mechanically — no git hook, no gate, no note schema changes; commit/merge time is exactly the "too late" this design avoids. The lifecycle duties (plan before work, WU result at WU close, epic result at epic close) are stated by the standard, kept honest at authoring time by the harness hooks, and judged like every other judgment: the existing reviews read the plan and result docs as inputs. A WU or epic being docs-only exempts it from test evidence, never from its plan and result docs — those exist precisely when code doesn't.

Open questions
