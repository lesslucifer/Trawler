Design run #9 — the body viewer

The pane that shows what actually crossed the wire. Six body kinds, nine family members, two mutually exclusive switches and seven ways to have nothing to show — designed so a body states its truncation instead of silently swallowing it.

Design run · 2026-09-04 · Trawler · T3 (docs/work/) · rulebook aeff5b0f · registry 27 entries · the flow it follows · W7 plan · built by W8

The shipped BodyViewer.tsx hand-rolls six renderers and a ModeButton, and its own marker at line 112 assigns this rewiring to a later WU. This run is that design. The registry already holds every member it needs, so nothing here is invented — the work is resolving what the pane owns against what nine components already own, and finding the places they refuse.

1 · Frame

Purpose: a developer reads the exact bytes one leg of one flow carried, to decide whether the payload is the bug. Given (functional input — received, not designed): the leg to show (from the panel) · fetch that leg's body decoded · fetch it raw · dispatch on content type · sniff raw bytes · decoded pretty-print from the server · the five capture states · save bytes to a file · read total byte length Not given (may not be assumed to exist): a byte range or paging · re-fetch of a body the ring dropped · a diff against another body · search inside a body · the encoding a charset-less body used · the other leg (the panel renders its own instance)

scroll / overflow: A is fixed and never scrolls. B is the single scroll container — it
owns both axes (long lines wrap per wrap-not-truncate, so the x-axis carries only the
hex dump's fixed-width rows and an oversized image). B's content is capped BEFORE it is
rendered, by the member: TEXT_MAX 128 KiB (text · xml · form), TREE_MAX 128 KiB (json,
which falls back to TextRenderer over cap), HEX_MAX 4 KiB (hex). ImageRenderer is the
one uncapped member — it letterboxes to the zone's width instead, so the DOM cost is one
element whatever the byte count. C does not scroll: it is pinned to B's foot, because a
statement that scrolls out of sight is one nobody reads (Tune's third call, which loops
back here). B caps its own height so two stacked instances both stay reachable —
whichever leg the reader wants is never a full pane-scroll away. Every cap is the
member's own, and the caller sets none of them.

The leg is the panel's, not the pane's. The panel already splits headers into Request headers and Response headers; a single Body section that switched legs inside itself was the odd one out — the same fact expressed two ways on one screen (grouping-by-relatedness). Mounting one instance per leg makes body follow headers, and deletes a control, a piece of state and a whole class of question (which leg am I looking at?) from this screen. Each instance keeps its own mode, because raw-ness is a property of the body being read, not of the flow.

HexRenderer T2 reuse
B, kind=hex
Toned offset·hex·ascii columns, and a marker that is not an ellipsis.
▸ why@use: "anything not json / xml / image / form / text — and every raw-mode body that is not valid UTF-8 or carries control characters", which is both of rawKind's hex outcomes. @avoid clears: no non-body binary (no such screen), and — load-bearing here — "the muted '… N more bytes' ellipsis hexDump appends by default: it is easy to miss". ▸ why
  • Save loses its word. Two worded actions at the row's end read as equals, and they are not — copy is the frequent one, save the occasional. Demoting save to its glyph lets copy carry the text weight alone. Loops back to Layout: no.
  • The row closes up. With one switch instead of two, zone A holds far less, and a row sized for the old pair leaves the actions stranded on a second line at narrow widths. One row, chooser left and actions right, is now the whole of A — and the shipped · separator between the two switch groups goes with the switch it separated. Loops back to Layout: no.
  • The marker must not scroll away.
