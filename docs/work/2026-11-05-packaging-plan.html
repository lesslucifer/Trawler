Intent

Trawler only runs from a clone today, through cargo run, and only on macOS has it ever run. This epic makes it installable and self-updating on all three desktop platforms, the way Strata ships. Pushing a v<version> tag runs a GitHub Actions matrix. It builds the macOS universal .dmg, the Windows .msi and NSIS -setup.exe, and the Linux .deb, .rpm and .AppImage, plus the signed updater archives and latest.json. Each job smoke-tests its own bundle, and the run creates a draft release that the owner publishes. Without a paid signing certificate the installers are unsigned (ad-hoc on macOS), so the first open shows the OS's prompt and the release notes say how to pass it. Updates fetched by the app itself are verified by the updater's own signature. Why now: E-ONEAPP made the app one workspace with one self-spawning binary (DEC-69), and the repo is going public. E-BGSVC lands first, and this epic packages what it adds.

Use-case requirements

UCChangeContract after this epic
UC-INSTALLnewA user installs Trawler from the published release with their OS's own artifact. The first open shows that OS's prompt for an unsigned app, and the release notes name the one way past it. From then on the app behaves as cargo run does under UC-4: one launch, an owned core, and the CA in the platform's app data directory (dev.trawler.app).
UC-UPDATEnewThe app checks the release channel at launch (at most once a day) and on Check for Updates…. For a newer version, a native dialog names the old and new versions and asks first. It never installs silently. Installing verifies the update's signature, goes through the DEC-64 quit check, says that the captured list is cleared, replaces the app and relaunches. The CA and settings survive. On a deb or rpm install the dialog opens the release page instead. A bad signature or an unreachable channel changes nothing, and the app says why only when the user asked to check.

Non-goals

Out of scopeWhy / where it goes
Developer ID signing, notarization, AuthenticodeThere is no paid certificate (Q3). Ad-hoc signing on macOS keeps arm64 from being killed on launch.
Mac App Store, Microsoft Store, Flathub, SnapThe macOS sandbox forbids setup's elevation, trust and proxy writes (Q11). The other stores are later rows if asked for.
.pkg, Homebrew cask, winget, apt repositoryThe release's artifacts are enough (Q10). Each can later point at a published release.
A standalone headless trawler CLI downloadThe app's binary already runs --core (Q12).
CI as a merge gateGates stay local (DEC-42, DEC-74). The CI workflow is a cross-platform signal, and the release workflow is what builds.
Silent, forced or delta updates; a release-notes UI beyond the dialog's textAn update always asks (UC-UPDATE).
Any API, route or port changePackaging wraps the app. W2 changes app or core code only where a platform breaks it.

moved to E-PKG2 W4 · release workflow — a tag builds every installer and a draft release

Adds .github/workflows/release.yml, modelled on Strata's. It triggers on a v* tag and runs a matrix over macOS universal, Windows x64 and arm64, and Linux x64 and arm64 (Q16). It fails when the tag differs from the workspace version (Q18), and signs ad-hoc on macOS through tauri-action with the updater secrets. Each job runs the e2e smoke (J1, J4) on the bundle it built before uploading. A final job creates a draft release with every artifact, the .sig files, a merged latest.json, and generated notes headed by the first-open steps per OS.

E2E test plan

At this close. The epic's e2e is xtask/tests/package_bundle.rs, run at the epic tip. It covers W1's whole flow: a real cargo xtask package with VITE_E2E set, a release-flavoured bundle, an .app green under codesign --verify --deep --strict, and the packaged binary capturing a request under a launcher's environment. e2e_packaging and its journeys below move to E-PKG2.

One hermetic Rust e2e, e2e_packaging, built from the real cargo xtask package with the package-test profile (Q15). HOME (%APPDATA% on Windows) is a tempdir, and every origin and manifest is a local server. It runs in the local gate on macOS and in ci.yml on all three OSes. Each release job runs J1 and J4 on the real artifact it is about to upload. J2 and J3 need a test-key build with an update-consent feature that answers the dialog yes. A unit guard proves that the release package carries neither, mirroring the scenario feature's rule.
