E-BGSVC — epic plan

Capture with no window open: the app outlives its window behind a menu-bar icon, and can start at login with no window at all.

v3 · opened 2026-11-05 · owner rulings 2026-11-05 on Q1–Q14 · Trawler · T3 (docs/work/) · branch epic/bg-service · WU branches wu/bg-service/<slug>

Intent

Today the main window is the app: closing it quits, and quitting stops the capture service (DEC-69 rule 14, E-ONEAPP's Q7). A user who wants traffic recorded while they work elsewhere must keep a window open, and Trawler cannot be running before they think to open it. This epic lets the app run with no window: a menu-bar icon shows the service's state and reopens the window, a switch keeps capture running when the window closes, and another starts Trawler at login with no window. The app still supervises its core — the background service is the app process without a window (Q1), so the lifeline, the single instance, the CA location and every API stay as they are. Now, because it is the roadmap's next user-facing row and E-PACKAGING (in flight beside it) makes an installed app — the thing a login item points at — real.

Before: only Windowed and Asking exist, and ✕ always asks-then-quits. The core lives exactly as long as the app process in every state; only the window comes and goes.

One invariant rides on all of it: the app is never windowless without a menu-bar icon. A host that cannot show one never hides the window.

E-BGSVC.W1 — the app outlives its main window

What it buildsThe decision record DEC-next (the app outlives its window), amending DEC-69 rule 14. A shell preference keep_capturing in its config dir (read/write commands, a corrupt file reads off). With it on, the main window's destruction no longer exits the app; with it off, nothing changes (settings.rs ends_the_app becomes a decision over label + preference + tray availability). Reopening the main window — a second launch (single-instance), macOS RunEvent::Reopen — rebuilds it if destroyed, through the same builder setup uses (init script with the core address, geometry restore). macOS activation policy: Regular while a window is open, Accessory while none is. A --background launch flag skips building the main window.
Maps toUC-BG, UC-4. Expected #1, #3 (Dock, second launch), #8, #10. Q2, Q3, Q11.
Expected outcomeShell integration tests (Tauri MockRuntime): with the preference off, destroying main exits; with it on, the app and its core survive, and a reopen builds a main window carrying the core-address init script. Unit tests cover the exit decision table, the preference file's round trip and corrupt read, and the flag parse beside --core. The lifeline integration test is re-run windowless.
Dependenciesnone — the first shell WU

E-BGSVC.W2 — the menu-bar icon

What it buildsA tray module (Tauri's tray-icon feature): a template icon with a running and a stopped variant, driven by the supervisor's CoreEvent::State observer. Menu: a status line (Capturing · Capture service stopped · Attached), Open Trawler, Settings…, Restart capture service (only when stopped, the same restart path the Capture service page uses), Quit Trawler. Tray creation failure is recorded as the host's tray availability, which W1's exit decision and W6's switch read — so the window is never hidden on a host that cannot show the icon. Native menu, no ui/src file: outside the design gate, its wording follows the closed vocabulary.
Maps toUC-BG. Expected #3 (menu Open), #4, #9.
Expected outcomeUnit tests: menu items per core state (running · exited · attached), the menu-action table, icon variant per state. Shell integration test: a state change through the supervisor's observer updates the menu; Restart from the menu round-trips to running on the same ports; a failed tray build marks the host trayless.
DependenciesW1 — Open needs the rebuild path, and the exit decision consumes tray availability

E-BGSVC.W3 — every quit Trawler can hold asks the same

What it buildsThe close request and the quit request come apart. The first ✕ that would quit, while the switch is unanswered and a tray exists, shows the once-question as W5 designed it (Keep capturing · Quit) and stores the answer as the switch. ⌘Q and the menu-bar's Quit emit a quit request and never show it; the shell opens (or rebuilds) the main window and the window runs DEC-64's check, then asks the shell to exit — one dialog, one copy of each reversal (DEC-64 rule 7). ✕ runs the check only when it quits; in background mode it closes at once. closeConfirm.ts gains the request kind; DEC-64 rules 1 and 6 are amended. The once-question cites W5's design; any other .tsx it touches is declared design.undesigned — DEC-64's dialog is reused as is.
Maps toUC-ONBOARD (quit), UC-BG. Expected #1, #5, #6, #11. Q3, Q9.
Expected outcomeVitest: the decision per (request kind × keep_capturing unanswered/on/off × tray × proxy reading) — the once-question only on an unanswered ✕ with a tray, its answer persisted, Quit then running DEC-64's check; ✕ in background mode never reads the proxy; ⌘Q always runs the check and never the once-question; a cancelled quit leaves the window open. Shell integration test: a quit request with no window builds one and emits to it; the menu's Quit maps to the quit request; the Dock's terminate path still stops the core.
DependenciesW1 (rebuild the window to ask) · W2 (the menu's Quit, tray availability) · W5 (the once-question's design)

E-BGSVC.W4 — Trawler at login

What it buildsA login_item module with one writer per platform, each rooted in a directory the caller passes: macOS $HOME/Library/LaunchAgents/dev.trawler.app.plist (RunAtLoad, ProgramArguments = [current_exe, --background]), Linux $XDG_CONFIG_HOME/autostart/dev.trawler.app.desktop, Windows the HKCU\…\Run value. Commands login_item_read (on when an entry exists, with the path it starts) and login_item_write (on overwrites any entry with this binary — the last write wins, Q8). No launchctl call: the item takes effect at the next login, the way macOS login items do.
Maps toUC-BG. Expected #7, #8. Q6, Q7, Q8.
Expected outcomeIntegration tests in a tempdir: on writes a plist that plutil -lint accepts (macOS) and a desktop entry with the exact Exec line (Linux); read reports off, or on with the entry's path; off removes it; on over an entry naming another binary replaces it with this one. Unit tests: the plist and desktop renderings, path quoting with spaces. Windows writer: unit-tested rendering only, its real check owed.
DependenciesW1 — the --background flag the item launches

E-BGSVC.W9 — quit hardening

Open questions

#QuestionAnswer
Q1What is the "background service" — the app process with no window, or a core running as its own login/system service that the app attaches to? owner ruling 2026-11-05 The app process with no window. It keeps DEC-69 whole: one supervisor, the stdin lifeline, one CA dir, single instance. A separate service would make every launch an attach, orphan the Capture service page's Restart and log, and need its own install/uninstall story.
Q2✕ in background mode: destroy the main webview or hide it? owner ruling 2026-11-05 Destroy, rebuild on reopen. No webview rendering a live list for hours unseen; the list reloads from the core, chips and geometry from their files. Cost: a reopen paints a fresh window (~a cold window's time).
Q3How does the user decide what ✕ does — the switch only, or a question the first time they close the window?
OptionThe user seesCosts
(a) switch only✕ quits, as today, until they find Keep capturing when the window closes in Settings → General and turn it on. Never asked. nothing new; the feature is easy to miss
(b) ask onceThe first ✕ that would quit asks: "Keep capturing in the menu bar after the window closes?" — Keep capturing · Quit. The answer becomes the switch; never asked again; changeable in Settings → General. a new dialog (W3 shows it, W5 designs it). Answering Quit while this machine routes through Trawler is followed by DEC-64's dialog — two questions, on that one close only
 owner ruling 2026-11-05 (b) ask once — the choice is offered at the one moment it matters, and nothing changes until the user picks it. A host with no menu-bar icon never asks and just quits.
Q4Menu-bar icon always, or only while windowless / background mode is on? owner ruling 2026-11-05 Always while the app runs. One place that says the service is running and reaches the window, and the icon is already there the moment the window goes.
Q5Where do the two switches — Keep capturing when the window closes and Open Trawler at login — live? owner ruling 2026-11-05 Settings → a new General page (designed, W5), and only there — one control per setting, as DEC-61 rejected two controls for one. The menu-bar menu offers Settings… to reach it; it carries no switches itself.
Q6Does a login launch open a window? owner ruling 2026-11-05 No — it starts with --background. Opening a window at every login is what users turn login items off for.
Q7To start at login, Trawler must register itself with the OS. Which way?
WayWhat it isTrade-off
(a) write the entry ourselvesOne small file per OS: macOS ~/Library/LaunchAgents/dev.trawler.app.plist, Linux an autostart .desktop file, Windows a registry value works for any build, tests write into a temp folder. On macOS 13+ the entry appears under System Settings → Login Items → "Allow in the Background", and macOS posts a one-time "Background Items Added" notice
(b) tauri-plugin-autostarta ready-made plugin that writes the same kind of entryalways writes into the real home folder, so a test would register the test build on this machine
(c) Apple's SMAppServicethe modern macOS API — Trawler shows by name in Login Itemsneeds macOS 13 and a signed app installed in /Applications, which only E-PACKAGING brings
 owner ruling 2026-11-05 (a) now; E-PACKAGING may move the macOS entry to (c) once the app is signed.
Q8The login entry stores the path of the Trawler program to start. If that path is not the Trawler now open — e.g. it was turned on from a cargo run build in target/debug/ and this is /Applications/Trawler.app, or the app was moved — what does the Open Trawler at login switch show? owner ruling 2026-11-05 The last write wins. The switch reads on whenever an entry exists, whatever copy it names; turning it on (or off and on) points it at the copy now open. Hovering the switch shows the entry's path, for debugging — a mismatch is not a real-use case, so it gets no state of its own.
Q9Menu-bar Quit with no window open: how does DEC-64's check ask? owner ruling 2026-11-05 Open the main window and ask there. A native shell dialog would be a second copy of every case and reversal (DEC-64 rule 7).
