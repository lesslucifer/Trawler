E-DFLOW.W10 — the flow costs what a real run needs

An audited design run spends 43% of its prompt tokens re-reading four files. W10 compacts the flow spec and the rulebook to real-run value, makes the checker's failure output the oracle instead of its source, and batches the fix loop — measured against run #6's numbers.

Requirement

A real design run must read each reusable artifact once, in the smallest slice that answers the question. The audit of run #6 (session session-1508a59f, turn 3) attributes 4.87M of 11.4M prompt tokens to four files re-read in slices: xtask/src/doc.rs (1.49M), docs/work/design-flow-base.html (1.42M), docs/design-rules/design-rules-index.html (1.14M), ui/src/setup.ts (0.83M). The same session's 13 full-price cache misses (1.58M billed input, 55% of the turn) follow any new tool result landing in the conversation. W10 makes each of these measurable cheaper:
  • design-flow-base.html compacted — only what a real run uses: the six stages' tags, the receipt contract, the close ritual. History, worked examples and prose that a run never reads are cut.
  • design-rules-index.html distilled — machine-readable rule rows (slug + verdict enum + one-sentence guidance) plus the receipt contract; the prose that exists to explain rather than to judge is dropped. Structural rows must survive byte-faithful — the checker reads slugs out of data-c="hard-rules-table" / soft-rules-table, and the receipt must pin the live blob.
  • The agent stops reading the checker source. verify-doc's failure output already names each check and its fix; the flow spec (compacted) enumerates the machine-checked conventions. A run therefore never reads xtask/src/doc.rs — the rule is stated in the flow spec, and the agent is directed to verify-doc's output and the rulebook rows instead.
  • Batched fix loop. Edits are applied in one pass, verified once, residuals batched again — never the twelve edit→verify cycles run #6 took. The flow spec's close step states "edit twice, verify twice" as the norm.
UC-DFLOW unchanged; this is flow cost, not flow behaviour.

A run-6-class task (setup-screen redesign) measures ~65–70% fewer prompt tokens than run #6's turn-3 baseline (11.4M → ~3.4M), through: reading each of the four files at most once (never in slices), reading neither the checker source nor ui/src/setup.ts, batching the fix loop to two passes, and splitting research from authoring across turns so the checkpoint resets context.
