Design rules — the KB, one file

The enumerable, slug-id'd design rules every Trawler screen design must satisfy, and the vocabularies every screen must agree on. Every rule is a one-liner carried by its Tier-1 predicate, read on the mockup doc; what a predicate cannot judge is the human's reading of the mockup.

Living T2 · the design-rules KB's single file (index = rulebook) · Trawler · rationale: DEC-14 · tokens: DEC-11 · closed vocabulary: DEC-17 · truncation escape: DEC-34 · the cut: DEC-53

What this is

Most rules are extracted — the codebase or a design run already made the decision and this is where it was written down. A marked minority are principle imports. Rules are cited by slug (stable kebab name, never renamed once a run or a review row cites it — deprecate instead).

One list, two surfaces. A design can pick an illegal value and so can a built component — binds says which. Every rule in this book has a predicate; there is no receipt and no coverage list — a run cites a slug only where a review row hits one (DEC-53).
binds — where a rule can be violated. It decides which surface judges the rule, and whether a screen must answer for it at all.
bindsViolated inJudged by

The litmus is the predicate. If a mechanical predicate exists the rule is hard and lives here. If the check is a reviewer's question it is judgment, not a rule of this book — the human reads it on the mockup and the run's review item records the call (DEC-53). If neither can be written, it stays out.
Consistency is vocabulary, not vigilance. Anywhere designs must agree across screens — colours, spacing, key bindings, words — a vocabulary fixes the options in one place. A screen never re-decides what warn means — it reuses the entry or proposes a new one.

Vocabularies

The fixed sets rules force designs to pick from. This section names the sets and their governing rules; it never lists their members — the member list is ui/tailwind.config.js.

The one thing a mockup must declare: data-wire. Three hard rules turn on which elements render a verbatim payload. The mockup says so: data-wire="<what it is>" on every payload element, data-wire="collection" on a zone host element that renders a captured collection, and data-wire="none" once when the screen renders no payload at all.

A collection host carries data-order beside it — "wire", or the sort and why.
A rule this codebase currently breaks is not recorded here. It goes to the deferred backlog. A rulebook that lists its own live exceptions teaches that the rules are negotiable.

Lifecycle

This doc is never finished — it is a living rulebook, the fourth T2 KB docs/design-rules/. Rules grow in place with the codebase (DEC-14).

The sanctioned escapes

Exactly two narrow escapes: a raw CSS block whose colours are still checked — and the pragma below for a template shape.

Rule of the escapeWhy
Form is design-allow: <class> — <reason> in a comment, applying to the next line only. The comment is the host language's: // design-allow: … in JSX, <!-- design-allow: … --> in HTML mockupSame granularity as eslint-disable-next-line
The named class must appear on the line belowAn edited line stops matching — stale pragma cannot protect silently
The reason must be non-emptyMirrors the merge gate's waived: rule
A pragma over a size value is rejectedExists for template shapes; the moment it could excuse text-[11px], the vocabulary is advisory
The live count is printed on every runSuppressions are visible debt
