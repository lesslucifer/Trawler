Design rules — the KB, one file

The enumerable, slug-id'd design rules every Trawler screen design must consider. Hard rules are one-liners — their Tier-1 predicate carries them; soft rules carry the judgment guidance a Tier-3 reviewer needs.

Living T2 · the design-rules KB's single file (index = rulebook) · Trawler · rationale: DEC-14 · tokens: DEC-11 · closed vocabulary: DEC-17

What this is

Most rules are extracted — the codebase or a design run already made the decision and this is where it was written down. A marked minority are principle imports: established design principles admitted on faith, promoted or killed once runs have judged them. Rules are cited by slug (stable kebab name, never renamed once a receipt cites it — deprecate instead). A rule belongs here only if it binds any screen design; facts with a narrower home live there:

This file is the rules, not the case history. Why a rule says what it says — the run that produced it, the defect that sharpened it, the counts that proved it — belongs with that work in docs/work/ and is not repeated here. A rule that needs its war story told to be understood is a rule that is not yet written clearly enough.

One list, two surfaces. A design can pick an illegal value and so can a built component — binds says which. The coverage list = every slug in the hard + soft tables; a design receipt must cite them all.
binds — where a rule can be violated. It decides which surface judges the rule, and whether a screen must answer for it at all.
bindsViolated inJudged by
screena screen's layout / composition decisionsthe design run and its receipt
componenta built component's own markupthe lint rule and the component's design file — checked on every component change, not only on a design run
botheither — a screen can pick an illegal value, so can a componentboth surfaces, each at its own level
A screen rule stops asking components to answer it; a component rule stops filling design receipts with n/a.
The hard/soft litmus is the check. If a mechanical predicate exists (grep the mockup, a non-empty table cell, a value ∈ a vocabulary) the rule is hard. If the check is a reviewer's question, it is soft. If neither can be written, it is not a rule yet — it stays out.
Consistency is vocabulary, not vigilance. Anywhere designs must agree across screens — colours, spacing, key bindings, words — a vocabulary fixes the options in one place and a rule forces every design to pick from it. A screen never re-decides what warn means, what Enter does, or what "decode" is called — it reuses the entry or proposes a new one (the same reuse-or-propose contract the registry uses for components).

Vocabularies

The fixed sets rules force designs to pick from. This section names the sets and their governing rules; it never lists their members — the member list is ui/tailwind.config.js, read directly by the predicates and by the lint rule. A rulebook that re-states the config is a second copy of it, and a copy drifts.

The vocabulary is closed, and "closed" is a property of each scale — checked per scale, never asserted once. Every scale replaces Tailwind's rather than extending it, so an off-list value emits no CSS at all. Tailwind drops an unknown utility silently, so the config is the definition and npm run lint (design/vocabulary) is the alarm (DEC-17).
How a closed vocabulary leaksWhat holds it shut
A scale left undeclared inherits Tailwind's whole ladder. Every member of it emits, so nothing drawn from it can ever red — the leak is invisible by construction, and no amount of linting finds itLegality is membership of a scale the config declares, not merely one Tailwind can emit. So the config names every scale the code draws from, at exactly the members it uses, and a class from any other scale reds on sight
One token name living in two scales that share a class prefix — the class then sets both properties at once, changing one silentlyA unit test asserts no duplicate in the generated class list
Arbitrary […] values, which emit whether or not a scale is closed — closing the config cannot reach them at allThe lint rule reds every one, unless a pragma excuses a template shape carrying no size
Out of scope by nature: structural classes (flex, absolute, truncate). Tailwind registers them whole rather than generating them from a theme key, so no scale could govern them and the rule has nothing to judge.
The second sanctioned escape: a component may write raw CSS when it is configuring something that cannot take a class. A third-party styling API — an editor's theme object, a stylesheet — has no className to give it. Such a block is accepted, not excused, on three conditions.
ConditionWhy
It covers the styling API, never a plain element. Anything with a className uses tokensOtherwise it is a general way out, and the vocabulary is advisory
Every colour in it must still be a palette value — asserted mechanically over all of ui/src/A literal that is a token renders the vocabulary; a literal that is not is a second copy of it, and a copy drifts — silently, because no class-reading check can see either one
Sizes and radii inside such a block are the author's to justify, and are not mechanically checkedStated rather than implied — extracting lengths from arbitrary CSS-in-JS is noisy enough to be worse than honest silence
The shape worth remembering: the lint rule reads class names and the Tier-1 predicates read the design doc, so a value that is never a class is invisible to both. The colour guard is what makes this escape safe rather than a hole.

Chromatic meanings

Every chromatic token is named for what a colour means, never for who uses it — and its meaning is fixed here while its membership is fixed in the config. A tint stays consistent because its mapping lives in exactly one component: screens reuse the component, never re-map the colour. A new tint is a config edit under review, which is the only way one can arrive.

TokenFixed meaningMapping owned by
oksuccess outcome (2xx) · confirmation of a completed action · a request that only reads (GET)StatusPill status→tone · CopyText/CopyButton confirm · MethodLabel verb→tone
warnfailure outcome (4xx/5xx) · error states · a request that destroys (DELETE)StatusPill · MethodLabel
createa request that brings a resource into being (POST)MethodLabel verb→tone
replacea request that overwrites a resource whole (PUT)MethodLabel verb→tone
amenda request that alters part of a resource (PATCH)MethodLabel verb→tone
syn-key · syn-str · syn-numthe three body-pane syntax roles — a key, a string, a number inside a rendered payload. Three roles and no more: a full syntax theme is what the renderer family forbids, and punctuation stays ink-mute (DEC-11)SourceSurface — the pane JsonRenderer and XmlRenderer share
unknown — an outcome that is neither success nor failureno tint. The neutral ink channel is the answer — a probe that fails and a probe that shrugs are both unknown, and on some screens that is the permanent case rather than an edge one. colour-plus-text already guarantees the text channel carries the meaning, so a third status hue would add nothing a reader needs— (ink, never a colour)

Two tokens carry double duty on purpose: GET shares the ok hue and DELETE the warn hue because reads succeed and destruction warns are the same semantic family — which is why they need no token of their own. Hover and press feedback is not chromatic: the washes are ink-toned and live in theme.backgroundColor.

prettythe re-indented view of those same bytes — a rendering, always named on screen and one act from rawprettify · format · beautify · pretty-print
nonethe empty-set microcopy for an absent value — the value is emptyempty · no data · nothing here

first flowthe proven-decrypted milestone — the moment traffic is being captured and readverify · test · done · working

The three body terms are one ladder, not three synonyms: wire bytes → decode (transport off) → raw (no indenting) → pretty (re-indented). Two different switches can sit on that ladder, so a screen must name which one it offers.

The one thing a mockup must declare: data-wire. Three hard rules turn on which elements render a verbatim payload, and no static reader can tell a wire value from a label by looking at it. So the mockup says so: data-wire="<what it is>" on every payload element, data-wire="collection" on a catalog row that renders a captured collection, and data-wire="none" once when the screen renders no payload at all. The n/a path is an answer; leaving the question unanswered is not one.

A collection row carries data-order beside it — "wire", or the sort and why. Same reason, one step further in: a declaration is a fact the run states, and prose about ordering is not a declaration. Judging it by keyword fails in both directions at once.

A new rule enters as soft unless a predicate for it can be written — an unchecked hard rule is a soft rule that lies about itself. Every rule in this table has one.

Lifecycle

This doc is never finished — it is a living rulebook, and it IS the fourth T2 KB docs/design-rules/ — a single file (the index carries the rulebook; it splits into topic files only if it ever outgrows one comfortable read) (design contracts — "what must every design satisfy"), sibling to use-cases/decisions/backlog: T1 is for shape that rarely changes, decisions/ is append-only (the DEC-5 precedent), and rules grow in place with the codebase. Why this home, and the wiring that makes growth stick, is DEC-14.

EventWhat happens to this doc
a design runconsumes this list frozen. Findings are recorded against it, nothing is edited mid-run — a rulebook that moves while a run cites it invalidates the receipt
a revision, after a runrules added, retagged or sharpened in place from that run's findings. A cited slug is never renamed — deprecate with a pointer, so every past receipt stays valid
promotion — an import proves itselfa rule marked import becomes extracted once the codebase or a run has made the decision for real: two independent sightings, or one sighting plus a finding it caught. Without this step an import stays a kill candidate forever, however much weight it pulls

The sanctioned escapes

A closed vocabulary needs a way out, or the way out becomes "stop running the check". There are exactly two, both narrow: a raw CSS block configuring a third-party styling API, whose colours are still checked against the palette — and the pragma below, for a class carrying a template shape. Neither can excuse the thing the vocabulary exists to govern.

Rule of the escapeWhy
Form is design-allow: <class> — <reason> in a comment, applying to the next line only. The comment is the host language's: // design-allow: … inside the className expression in ui/src/, and <!-- design-allow: … --> in a design run's mockup. The same rules either way, and one implementation of “is this a size”; only the comment syntax differs, because HTML has no // and JSX has no <!-- --> where it is needed. The class is a token and the separator is the rightmost one in it, so a class carrying its own -- (a custom property) spells its reason after a space — glued, the class's own dashes are the split. The printed count is the design surface's — verify-doc tallies live suppressions per run; the lint rule reports per file and has no run to totalSame granularity as eslint-disable-next-line. JSX has no comment position inside an opening tag, so the expression container is the one place that works everywhere and keeps the pragma beside the class it excuses
The named class must appear on the line belowAn edited line stops matching and reds again — a stale pragma cannot go on protecting code it no longer describes
The reason must be non-emptyMirrors the merge gate's waived: rule — a suppression with no argument is not a decision
A pragma over a size value is rejected, never honouredIt exists for template shapes — grid-cols-[auto_1fr], a two-column layout with no size in it. The moment it could excuse text-[11px], the vocabulary is advisory
The live count is printed on every runSuppressions are visible debt, not a silent hole
A rule this codebase currently breaks is not recorded here. It goes to the deferred backlog with the ruling on which side is right, and the soft rule that catches it meanwhile keeps catching it. A rulebook that lists its own live exceptions teaches that the rules are negotiable — and the list is never pruned once the fix lands.
