Design rules — the KB, one file

The enumerable, slug-id'd design rules every Trawler screen design must consider. Hard rules are one-liners — their Tier-1 predicate carries them; soft rules carry the judgment guidance a Tier-3 reviewer needs.

Living T2 · the design-rules KB's single file (index = rulebook) · Trawler · seeded 2026-07-24, homed by E-DFLOW.W3 · seed frozen through the W4 integrated run, revised in W6 · sources: W1 run · W2 design files · DEC-11 (Warp tokens) · marked principle imports · rationale: DEC-14

What this is

Most rules were extracted from decisions the W1 hand-run or a W2 design file already made; a marked minority are principle imports (established design principles with at most one Trawler sighting) that W4's integrated run must validate or kill. Rules are cited by slug (stable kebab name, never renamed once a receipt cites it — deprecate instead). A rule belongs here only if it binds any screen design; facts with a narrower home live there:

How a rule is enforced

flowchart LR
  H[hard rules] --> T1["Tier-1 · mechanical check\n(a predicate over the artifacts)"]
  A[ALL rules] --> T2["Tier-2 · receipt coverage\n(every slug cited, verdict + citation)"]
  S[soft rules] --> T3["Tier-3 · adversarial review\n(judged against the artifacts)"]
One list, three tiers. The coverage list = every slug in the hard + soft tables; a design receipt must cite them all.
The hard/soft litmus is the check. If a mechanical predicate exists (grep the mockup, a non-empty table cell, a value ∈ a vocabulary) the rule is hard. If the check is a reviewer's question, it is soft. If neither can be written, it is not a rule yet — it stays out.
Consistency is vocabulary, not vigilance. Anywhere designs must agree across screens — colours, spacing, key bindings, words — a vocabulary fixes the options in one place and a rule forces every design to pick from it. A screen never re-decides what warn means, what Enter does, or what "decode" is called — it reuses the entry or proposes a new one (the same reuse-or-propose contract the registry uses for components).

Soft rules Tier-3

Principles a reviewer judges — each with its DO/DON'T pair and the question the adversarial reviewer asks. Seed column: a W1/W2 citation = extracted; import = an established principle W4 must validate or kill.

SlugPrincipleDO · DON'TReviewer asksSeed
visual-weight-follows-goals The visual hierarchy matches the Frame's goal ranking — the top goal owns the most visual weight. The ranking is the hierarchy. ✓ top goal "scan failures" → status column carries the most weight
✗ timestamps heavier than statuses		 Compare the Layout/mockup hierarchy against the Frame goal table, top to bottom — where do they diverge? W1 Frame stage
grouping-by-relatedness Visual proximity mirrors semantic relatedness; every separator marks a real boundary — decoration never separates. Gestalt proximity. ✓ hairline between request and response legs
✗ a divider inside one header set		 For each separator and cluster: does the visual boundary match a semantic one? W1 seed · Section ("the seam, not a card frame")
ordering-by-priority Within a zone, order follows the user's scan priority — never alphabet or implementation order. Captured collections are exempt (wire-order-preserved owns them). ✓ identity → request → response, the debugging read order
✗ zones ordered by build convenience		 Read each sequence aloud: whose priority does this order serve? W1 seed · FlowDetail zone order
progressive-disclosure The default view is the scan level; depth is one explicit, invited act away — never everything at once, never buried deeper. ✓ list row → detail panel · raw body → decode toggle
✗ full bodies inline in the list		 At rest, is the scan clean? After one act, is the depth there? Anything need two? import · FlowList → FlowDetail
data-ink-first Every non-data pixel earns its place — backgrounds, borders, icons, badges only when they inform. Tufte's data-ink ratio. ✓ tinted text is the whole StatusPill
✗ a bordered badge around every status		 Strip each piece of chrome in imagination: is any information lost? import · StatusPill driver ④
generous-targets A hit target is the largest natural area — never a small glyph beside the thing it acts on. Fitts's law. ✓ the whole value copies on click
✗ a 12px icon as the only target		 For each interaction: could the target be bigger for free? import · CopyText whole-text target
motion-informs Motion and transience only communicate state change; nothing animates for decoration; transient feedback expires (~2 s). ✓ confirm chip appears, expires
✗ hover glow, panels sliding for style		 For each animation: what does it tell the user? "Nothing" fails. import · CopyText confirm
empty-states-orient A zone's empty state says what will appear and how to cause it; a value-level absence stays a calm "none". ✓ "waiting for traffic — point a client at :7420"
✗ a blank panel		 Land on each empty state cold: do you know what to do next? import · E-UISETUP onboarding · HeaderTable "none"
familiar-idioms When a devtools convention exists for the job, prefer it; novelty needs a driver in the Frame. Least surprise. ✓ network-table row grammar (method · path · status · time)
✗ a novel traffic viz with no driver		 Name the idiom this follows — or the Frame driver that justifies departing from it. import · FlowList mirrors devtools
display-equals-payload A displayed wire value is the payload, verbatim — no rewriting or shortening at rest; a transformed view (decode) is explicit and reversible. The trust contract of a debugging proxy. ✓ raw body at rest, decode is a toggle
✗ silently pretty-printed JSON		 Hunt every displayed wire value for a silent transformation. CopyText driver ② · BodyViewer decode
labels-add-context A label carries only the fact its context doesn't already state. Repeated context is noise in a dense panel. ✓ "copy all"
✗ "copy request headers" (under that heading)		 Read each label in situ: does any word repeat its surroundings? HeaderTable sub-bar verdict
calm-microcopy Microcopy is lowercase, terse, unexcited. A tool for reading traffic keeps its own voice quiet. ✓ "copied" · "none"
✗ "Copied!" · "No headers found."		 Scan all microcopy for case, length, exclamation. CopyText · HeaderTable
one-term-per-concept Every user-facing term comes from the lexicon — one term per concept, one concept per term; new terms are proposed, never coined ad hoc. Reuse-or-propose, for words. ✓ "decode" everywhere
✗ "decode" here, "prettify" there		 Check each label/microcopy term against the lexicon; unknown terms need a proposal entry. HeaderTable "copy all" · BodyViewer decode
confirm-at-point Feedback for a user action lands at the interaction point, inline and transient — never a toast across the screen. Verify without looking away. ✓ inline "copied" chip at the value
✗ a corner toast		 Trace each use-case's feedback: where does the eye have to go? CopyText confirm chip

Lifecycle

This doc is never finished — it is a living rulebook, and it IS the fourth T2 KB docs/design-rules/ — a single file (the index carries the rulebook; it splits into topic files only if it ever outgrows one comfortable read) (design contracts — "what must every design satisfy"), sibling to use-cases/decisions/backlog: T1 is for shape that rarely changes, decisions/ is append-only (the DEC-5 precedent), and rules grow in place with the codebase. Why this home, and the wiring that makes growth stick, is DEC-14.

EventWhat happens to this doc
W4 integrated runthe flow consumes this list frozen; findings recorded, nothing edited mid-run — imports that pull no weight are W6 kill candidates
W6 revisionrules added/removed/retagged/sharpened in place from W4 findings; a cited slug is never renamed — deprecated with a pointer
W7 harnesshard checks become the Tier-1 predicates; the two rule tables become the receipt-coverage list; the receipt pins the rulebook version (git blob hash) it ran against
epic distillationlinks into docs/work/ (the W1/W2 groundings) re-point to the components' post-epic home when those T3 docs distil and archive
