DEC-71 — a filter is a chip, the core stays keyed

The app's four filter controls become one typed query bar. Each accepted filter is a chip, the app parses the grammar, and the core keeps keyed query parameters, now with lists, negation and is.

v3 · 2026-11-05 · Trawler · T2 decision · minted by E-QUERY before W1 and W2, from the owner's rulings on Q1–Q10 (2026-11-04) · reverses UC-4's “an exactly-matched filter is chosen rather than typed” · UC-3 · UC-4 · UC-6 · UC-7 · built by E-QUERY.W1–W3, walked end to end by W4 · active

Why this record exists

Before (UC-4, E-RFINISH)What went wrongRuling
four controls: free text (URI only), a host dropdown, a method dropdown, a status field four rules to learn. content_type and source existed in the core with no control in the appone typed bar, every filter a chip
method and host chosen, not typed, so a partial verb like GE could not be writtenthe dropdowns fixed one failure (a query that cannot be satisfied) by removing typing altogethertyping returns. An unparseable draft stays a draft and says why, so that failure stays fixed
the host dropdown offered new URL().host (port kept); the core matched Uri::host() (port dropped)picking localhost:8080 listed nothing the host filter matches host or host:port

Decision. A filter is a chip, and only a chip filters. The app parses a typed draft into a chip and refetches only when a chip is added or removed. The grammar belongs to the app. The core parses no query string and keeps keyed parameters, which an API client writes directly.

The rules

#RuleWhy
1The core takes host method status content_type source q is, each repeatable, and a not_<key> form of eachQ1, Q9: no ?query= grammar in the core. Negation and lists are the two things the chips need that keyed parameters lacked
2A repeated q matches all of its values. Any other repeated key matches any of its values. Different keys combine as all ofQ10: each text chip narrows. Q2: host:a host:b means either host, so there is no OR syntax
3not_<key>=v excludes every flow that <key>=v would select. Repeated, it excludes flows matching any of the values“matches none of them”, whatever the key
4is=pending means no response yet. is=https means the request scheme is httpsQ2: the two states the bar offers that no key covered
5A single parameter behaves exactly as it did before this recordno existing client (the web shell, scripts, the app before W3) breaks
6A value the core cannot read is refused 400 with a reason naming the parameter as sent (not_status, not status). The listing, export and clear share that one refusalthe app marks the chip that produced the refusal. A silently empty list reads like “nothing matched”
7The host filter is a substring of host or host:portthe app's host values carry the port
8A draft that does not parse never reaches the core. It stays in the bar and names its fault this keeps the protection the dropdowns gave, without the dropdowns
9Actions (export, clear, settings) stay out of the bar. ⌘F focuses it. The chips survive a relaunch through E-STICKY's storeQ3, Q4, Q8
