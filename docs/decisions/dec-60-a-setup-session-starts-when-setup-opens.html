DEC-60 — a setup session starts when setup opens

Setup is opened once per device, and each opening is its own session. The screen reads only what that session produced, since nothing can say which device a request came from.

Decision. Opening setup starts a session at the moment it records (since). Every reading the setup screen takes from traffic counts only captured rows and tunnels that started at or after since, listed unfiltered. The capture indicator keeps saying capture works once it has been proven. "Set up another device" never answers the device already set up.

The rules

#RuleWhy
1Each opening records since: the launch read's send time on a first run, the click on every re-entrytime is the only boundary available. The core cannot attribute a request to a device (DEC-13's blocked-on row)
2The try task, every task read from traffic, the one-open-guide rule and the success line read only captured rows and tunnels at or after sinceevidence from an earlier session is another device's (DEC-33: a verdict never borrows from outside its own reading)
3The session's rows are listed unfiltered. The list keeps its own filtered rows for when the user comes backa filter is the list's question. The setup screen never asked it
4A count with no time (the core's /stats tally) feeds no sessionit cannot be placed after since. Inside a session every row and tunnel carries its own time
5Once capture has been proven, the dot reads connected in setup toosetting up another device is not capture breaking on the first
6"Set up another device" opens on the last device chosen in this app session when that was not This machine. Otherwise it leaves the question unanswered, and no task is drawn until it is answered. The dot opens on the last device chosen, This machine includedthe button names another device. The dot says "run setup again"

Rejected

AlternativeWhy not
Attribute each request to a device and read that device's rowsthe core cannot tell a phone's request from this machine's. A new reading is its own epic
Clear the list's filter when setup opensit takes away a choice the user made about the list, to answer a question the list never asked
Keep the /stats tally as "something reached Trawler"a first launch would read "nothing arriving right now" from traffic before the session, which is the borrowing rule 2 forbids
Preselect the first device that is not This machinea guess dressed as an answer. The user knows which device, and the screen does not
Restart the session when the platform changesthe session is the opening. A change of mind inside it would discard the evidence the user just produced
