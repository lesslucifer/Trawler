DEC-13 — Onboarding's local-OS actions & the core connection signal

Why the native app may change the machine, and why the core grew a pre-decrypt "connection seen" signal.

v1 · 2026-07-15 · Trawler · T2 decision · minted by E-UISETUP · relates to DEC-12 · UC-ONBOARD

DEC-13 · What onboarding is allowed to touch

E-UISETUP added guided onboarding (UC-ONBOARD): walk a fresh machine from an untrusted CA and an unconfigured client to its first decrypted HTTPS flow. Two of its choices overturn boundaries written earlier in the epic's own plan and one of its WUs. This record is their durable home — the plan that named the non-goals is archived out of git (DEC-3), so the reversal lives here, not there.

Decision. The native app performs two classes of action a pure API client would not: (1) it reads and writes OS state — installs the CA into the trust store, sets/unsets the system proxy, and probes both — all in the Tauri process, gated on an explicit confirm + OS elevation; (2) the core emits a pre-decrypt "connection seen" signal (GET /stats + a connection SSE event) so the proxy step can go green on any tunnel, even an HTTPS attempt Trawler can't yet decrypt. Both were owner-approved during the epic.

Local-OS actions in the Tauri process

The core stays a pure MITM proxy + read-only control API — it never touches the host's trust store or proxy settings. Onboarding's "do the work for the user" rule (UC-ONBOARD) needs exactly those writes, so they live in the native app (ui/src-tauri), never in the core:

  • CA install — security add-trusted-cert (macOS) / certutil -addstore (Windows); guided text elsewhere.
  • Proxy set/unset — networksetup (macOS) / WinINET (Windows); symmetric revert on clean quit and crash-reconciliation at launch.
  • Read-only probes — "does this machine trust the CA / route its proxy at Trawler?", used for the ~90% single-machine case.

Every write is one explicit confirm + an OS elevation prompt away; decline ⇒ guided steps. This is consistent with DEC-12 (the native app is an out-of-process client of the API) — the API contract is unchanged; the OS-touching capability is a property of the desktop shell alone.

Reverses W2's "no trust-store inspection". W2 built CA install with the rule "trust is proven by capture, not by reading the store." W6 added a read-only trust probe (ca_trusted) for an honest instant per-step status. Reading the store to report status is now allowed; revealing the flow list is still capture-only — a probe-green step never ends onboarding. The narrow invariant that survives: done = a real decrypted flow, never a self-reported or probe-reported checkbox.

The core connection signal

An HTTPS client that doesn't yet trust the CA fails its TLS handshake and produces no flow — so "is my traffic even routing through Trawler?" had no observable answer before decryption worked. The core now counts the tunnel itself:

  • recorder calls store.note_connection(authority) on the CONNECT authority;
  • store holds a monotonic connections: AtomicU64 and broadcasts FlowEvent::ConnectionSeen { authority } (event);
  • api exposes GET /stats → { connections } (one-shot seed) and maps the event to a connection SSE event (live bump).
Reverses the epic's "no new backend / API endpoint" non-goal. The epic plan promised onboarding would add no core/API surface. It added the smallest possible one: a read-only counter + one SSE event kind, no new capture behaviour, no config. The tally is a monotonic u64 (no unbounded growth, no per-authority map). It exists solely so the proxy step is observable pre-decrypt — it never reveals the flow list (that stays gated on a decrypted https:// flow). curl-reachability (UC-3) is preserved: /stats is a plain GET like every other route.

Alternatives rejected

Instead of…Rejected because
Keep "prove by capture only", no probe, no signal Left the honest 90% case ("I'm on this machine, is it set up?") with a "Waiting…" dead-end and a false "not set up" when a device was routing but not decrypting. The whole epic's UX rule is "tell the truth in every case".
Per-authority connection map / rich stats Onboarding needs one bit — "has anything arrived?". A monotonic counter answers it with zero growth risk; a map is speculative surface (YAGNI).
Infer connections client-side from failed fetches A remote device's failed TLS handshake is invisible to the app; only the proxy sees the tunnel. The signal has to come from the core.
CA/proxy writes in the core The core is API-first and headless; touching the host trust store / proxy from it breaks that and has no API justification. The desktop shell is the right owner (DEC-12).

Status: active. Supersedes the epic-plan non-goal "no new backend/API endpoint" and W2's "no trust-store inspection", both for onboarding's scope only; the core's API-first, capture-proves-done invariants otherwise stand.
