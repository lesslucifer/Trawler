DEC-18 — the collection has one small-control box, and a new control composes it

Copying, acting and picking are the same weight of thing, so they are the same box. A second box would teach a hierarchy the rulebook does not have — and a rule that two files must match is only as good as the next edit.

DEC-18 · 2026-08-12 · Trawler · E-DFLOW.W7 · distilled from Button D1/D3 · CopyButton D4 · Select D1 · IconButton D2 · status: active

Context

Four components in the collection draw a small control: CopyButton, Button, IconButton, Select. Each was designed on its own file, and each fork reached the same question independently — does this one get its own box? The first answer, in W4, was "clone CopyButton's box". W5 built the collection and found the clone had already failed.

Three token values had drifted while both files still claimed identity. Nothing compared them: the rule lived in prose in two design files, and prose is not a comparison. This is the whole argument — a rule that two files must match is only as good as the next edit.

One box, one token table. The differences between these four are the word, the tone and the affordance — never the shape.
What is sharedWhat each still owns
The shell — border, radius, padding, font family, min-height. Shared by composition, not by a matching rule: CopyButton renders a Button, Select's trigger is the same box CopyButton: the clipboard write, the confirm, the timer hook
The weight. Side by side the only difference is the word, because the only difference is the word Button: label tone ink-body, one notch above CopyButton's ink-mute — a Button is usually the only way out of its zone, a CopyButton is a convenience beside content already readable
The refusal: no primary/filled variant anywhere in the family. Emphasis is expressed by which actions are offered, never by button weight IconButton: borderless at rest — its glyph is self-contained, so the frame adds chrome without aiding recognition

Options rejected

OptionWhy not
A distinct, heavier box for actions so they read as more consequential than copies It invents a weight hierarchy the rulebook does not have, and every screen would then have to decide which of two boxes an action deserves. Drawn, then rejected
A filled input look for Select, so picking reads as data entry rather than as an action Genuinely arguable — a Select is an input. Rejected because its real host puts a Select and a Button side by side in one row: a filled box beside a transparent one at the same size reads as a hierarchy that does not exist, and data-ink-first prefers the hairline. Revisit if the app grows a real form, where every control is an input and the row has no buttons
ink-mute label on Button, exact CopyButton parity Simpler rule, one fewer divergence to remember — but a panel's only recovery action would then be the quietest text in the zone
A hairline border on IconButton at rest, CopyButton style CopyButton carries a border because its label needs the frame to read as a button; a glyph does not
Keep "clone CopyButton's box" as a written rule Measured and failed: three values drifted while both files claimed identity. A shared shell needs no rule

Consequences

  • A new small control composes the shell; it does not redraw it. A design run proposing a control with its own box is proposing a second box, and the burden is on the proposal.
  • The generic FlashButton this family once deferred is resolved, not pending: the shared piece turned out to be the shell, not a flash mechanic. Button carries no timer and never flashes — the confirm hook stayed with CopyButton.
  • Weight differences are expressed in tone (ink-body vs ink-mute) and in which actions exist — never in a second shape.
  • The one open door is named above: a real form, where the whole row is inputs, may reopen Select's box.
