DEC-70 — a choice belongs to the user, not the flow

A view choice made on one flow carries to the next flow and across a relaunch. The detail's leg, the body mode and setup's last platform live in one record, held by Shell and kept by the shell in view-prefs.json.

v1 · 2026-11-04 · Trawler · T2 decision · minted by E-STICKY from the epic plan's rulings Q1–Q6 · amends DEC-31 (who holds the body view) and DEC-60 rule 6 (the last device outlives the app session) · relates to DEC-67 · UC-5 · UC-ONBOARD · UC-SVC · active

Why this record exists

BeforeWhat changed
FlowDetail was keyed by the flow, so each flow remounted the pane and reset its leg and the body's raw | pretty; a relaunch forgot both, and setup's last platform ended with the app session the owner, 2026-11-04: "select once". A choice states what the user wants to read, which does not change with the row they click

Decision. The leg (request | response), the body mode (pretty | raw, one setting for both legs) and setup's lastPlatform are one record, held by Shell, read once at launch and written whole on every choice to view-prefs.json in the shell's config dir (view_prefs_read / view_prefs_write). The Settings window reopens where it was left, as every window does under DEC-67.

The contract

#RuleWhy
1One writer: Shell holds the only record. Every field — E-QUERY's query text included — goes through it; the Settings page never mounts ittwo writers of one file overwrite each other's fields
2Each field is read on its own: missing, mistyped or unknown values read as that field's default (Request, pretty, none), never as an errorlosing one choice costs a click; losing all of them for one bad field costs every click
3Fields the app does not know are kept: a write merges the file's unknown fields under the ones it sendsan older and a newer app share the file; neither erases the other's choices
4A choice made before the launch read lands wins; no write happens until that read settles an early click is the user's latest word, and an early write would erase the saved fields
5Each choice is written the moment it is made, staged then renamed (DEC-67 rule 5)⌘Q, the Dock's Quit and the last window closing end the process without unmounting the app, so a timer loses the last choice
6lastPlatform seeds only setup the user opens (the dot, "set up capture", "set up another device", DEC-60 rule 6 still applied). The launch check's own setup and the session's chosen start on This machine every launchchosen decides whether adb runs, in setup and at quit; no launch should run it before the user opens setup
7A flow with no response yet, opened on Response, shows Response with its own "no response yet" statethe choice stays put; the flow says what it lacks
