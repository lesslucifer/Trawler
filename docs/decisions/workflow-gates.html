DEC-2 DoD evidence is four per-tip git notes, judged by a recomputing gate

Statusaccepted · 2026-07-05
OriginEpic E1 (workflow standard) — manager decisions D1–D13 in the archived brainstorm (docs/.archive/2026-07-05-workflow-brainstorm.html, untracked; content in git history before E2)
Wherextask/src/gate.rs · .cargo-husky/hooks/pre-merge-commit · workflow.html

Context

Every line is AI-written and merges are unattended; agents cannot be trusted to remember ritual steps or honestly self-report completion. Evidence must be mechanical, queryable after branches are deleted, and tamper-evident against amend/rebase.

Choices (each looks "fixable" — it isn't)

ChoiceWhy — do not "simplify" it away
Four notes (test/cr/doc/dod), not one blobEach has one writer and one lifecycle: manifests and doc notes are authored during work, the review note by a review run, the receipt only by the gate on green. Merging them would let one writer forge another's evidence.
The dod/v1 receipt exists although it is recomputableManager decision (brainstorm Q4): a queryable index of completed work. It is safe because it is never blind-trusted — any tip can be re-verified offline; a hand-minted receipt fails recomputation.
merge.ff = false everywhereThe epic walk recovers WU tips as merge^2; a fast-forward erases the seam and hides evidence. The post-checkout hook re-heals the config.
The walk skips the epic tip when it is a non-merge commitOne commit cannot carry both an epic-level and a commit-level test note (one note body per ref per commit). The tip's own diff is covered by the epic gate itself.
Diff hashing uses git diff --no-color --no-ext-diffThe review-time hash and the gate-time recomputation must be byte-identical across user configs; bare git diff respects local color/ext-diff settings.
waived (judgment, with reason) vs exempt (rule: docs/infra-only)Waivers stay visible and reviewable — an unjustified one is a review finding; exemptions are mechanical and carry no note at all. Collapsing the two would either bury judgments or demand ceremony for prose fixes.
Code paths are src/, xtask/, tests/The gate itself is code; scoping "code" to src/ alone would have exempted the tool that enforces the rules.
Hook mode resolves the merged tip from GIT_REFLOG_ACTION, with the MERGE_HEAD file as the first choiceDiscovered live on E1's first gated merge, which failed open: pre-merge-commit fires before git materializes MERGE_HEAD for automatic (ort) merges — the merged revs exist only in the reflog action then. MERGE_HEAD is on disk only for conflicted/--no-commit merges, whose completion pre-commit gates through the same path.
Every spawned git scrubs inherited GIT_* env (xtask/src/git.rs · cmd; local copies in the hook-test helpers)Discovered live when the pre-push suite trashed the enclosing repository: git exports GIT_DIR to hook processes, and inherited it overrides -C/current_dir, silently redirecting every "hermetic" temp-repo call to the real repo. Regression tests in dod_gate and dod_hooks run the helpers with a poisoned GIT_DIR.

Consequences

Hooks can be bypassed (--no-verify, ff-merge) but not the epic walk — smuggled content turns the next gate red. Deferred: verify-dod --remote (assert origin has the notes refs) once a second machine or CI consumes them.

DEC-3 Archived docs leave git; the epic gate enforces the tracked-doc layout absolutely

Statusaccepted · 2026-07-05
OriginEpic E2 (doc-archive) — user direction: archives must not be tracked
Wherextask/src/gate.rs · check_tracked_docs · xtask/src/notes.rs · is_expected_tracked_doc · documentation-system.html

Context

Archived T3 docs were tracked under docs/work/archive/. Sessions must never read archives, yet tracked files invite reads, bloat the tree, and make "what docs exist" ambiguous. Archiving already requires distillation, so the tracked copy carries no information the tiers and git history don't.

Choices

ChoiceWhy — do not "simplify" it away
Archiving = git rm + move to gitignored docs/.archive/The archive stays greppable locally for forensics, but git carries only living docs; the pre-archive content remains addressable in history via the commits that added it.
The epic gate checks the whole docs/ tree at the tip (flat T1 files, use-cases/, decisions/), not just paths added since baseA base-relative check fails open: junk landed through an ungated path (or grandfathered before the rule) never turns any gate red. The absolute check makes every epic re-assert repo-wide doc hygiene; main was migrated clean in E2 so any hit is real.
archived doc-note entries keep requiring distilled_to, judged wherever the deletion appears in a gated diffA work doc created and archived inside one epic nets out of the epic diff — its lineage evidence lives at the WU seam that deleted it, so the requirement cannot be re-hung on the epic note.

Consequences

Archives don't replicate through clones — a fresh clone starts with an empty docs/.archive/, which is by design: nothing citable may live there. Any doc path outside the tier layout (a stray docs/<dir>/) now blocks the next epic merge until it is moved into a tier folder or archived. The layout check runs before the docs-only exemption, so even an exempt (docs-only) epic merge re-asserts hygiene — a stray doc cannot ride an ungated merge into main.

DEC-6 main is merge-only — the pre-commit hook refuses direct commits with branch guidance

Statusaccepted · 2026-07-06
OriginEpic E-MAINLOCK — user direction after auditing the direct-to-main path used by the port-change commit
Where.cargo-husky/hooks/pre-commit · tests/dod_hooks.rs · workflow.html

Context

The original workflow allowed standalone commits directly on main: docs/infra-only ungated, code commits with a test/v2 · level: commit note checked by the pre-push range walk. Audit showed that path never requires a code review (check_review is skipped at commit level) and is never revisited — epic gates walk only their own branch range, so main-side history stays behind every future merge-base. Unreviewed code could land on main permanently, gated only by fmt/clippy/tests and a self-attested note.

Choices

ChoiceWhy — do not "simplify" it away
Remove the path (refuse the commit) instead of patching it (requiring cr/v2 at commit level)One uniform rule for an AI committer beats a second evidence contract: any work ⇒ branch ⇒ gated merge. The refusal message teaches the correct move at the exact moment of the mistake.
The guard sits first in pre-commit, before fmt/clippyThe refusal must be instant and unambiguous — not buried after a minutes-long clippy run, and never masked by an earlier failure.
Docs-only commits are refused tooUser decision: "any works". Carve-outs re-open judgment calls the rule exists to remove; the merge gate already exempts docs/infra-only diffs, so the added ceremony is one branch and one --no-ff merge.
Merge completions (MERGE_HEAD on disk) pass the guardConflicted merges into main complete through pre-commit — they are the gated path, not a bypass; the existing MERGE_HEAD block in the same hook runs the epic gate on them.
No pre-push backstop against --no-verify commits on main--no-verify defeats pre-push equally, so a backstop there adds no real enforcement (DEC-2 already accepts hooks-can-be-bypassed); the workflow forbids bypassing gates outright.
epic/* branches keep allowing standalone commitsPlan docs, epic-level notes and small fixes legitimately land there, and the epic walk gates every one of them at merge time — the hole existed only where no later walk ever looks.

Consequences

Every change, including T0/CLAUDE.md edits and doc snapshot bookkeeping, now needs a branch and a --no-ff merge. Post-epic cleanup that used to land directly on main (e.g. archiving a distilled doc) must happen on the epic branch before its merge — which the tracked-doc layout check (DEC-3) already forces. The commit-level rows of the DoD table now apply only to standalone commits on epic/* branches.

DEC-7 Manual review is a fifth note, required by path + level, with identity-only auth deferring the cryptographic form to E-MRSIG

Statusaccepted · 2026-07-06
OriginEpic E-NMWF (manual review) — user direction; plan archived at docs/.archive/2026-07-06-manual-review-plan.html (untracked)
Wherextask/src/mr.rs · xtask/src/gate.rs · check_manual_review/check_commit_trailer · xtask/src/notes.rs · is_doc/is_ui · .cargo-husky/hooks/commit-msg · .mr-allowed · workflow.html · roadmap (E-MRSIG)

Context

Human-facing surfaces must not land silently, yet every line is AI-written and merges are unattended. A sign-off gate has to be as mechanical and un-agent-trustable as the rest of the DoD: whether review is required cannot be an agent's judgment, and the record of who signed must be verifiable. The strong version — a signature no agent can produce — needs its own design and is deliberately split out; this epic builds the whole surrounding gate and leaves one swappable seam for it.

Choices (each looks "fixable" — it isn't)

ChoiceWhy — do not "simplify" it away
Requirement is derived from diff paths + level, never a flag — docs⇒commit, UI⇒WU, epic⇒alwaysAnything an agent asserts about necessity is forgeable; a path predicate (is_doc/is_ui) is not. Same principle as the docs/infra exemption and the code-path definition (DEC-2).
Docs are gated at commit time via a Reviewed-By message trailer, not a noteReviewing after the commit exists is too late — the point is to prevent the commit — and a git note cannot hang on a commit that does not exist yet. The trailer rides in the message; the commit-msg hook enforces it against the staged diff. The change hash needed for the future signature exists pre-commit as git diff --cached and recomputes as parent..commit, so the carrier is already the right shape for E-MRSIG.
Not waivableA waivable human-sign-off is not a sign-off. Unlike a test layer (DEC-2's waived), "required" means a listed authoriser is recorded — nothing to skip.
The check runs before the docs/infra exemptionAn always-required epic (or a docs-only one) must still carry its note even when exempt from test/cr/doc — exactly like the epic tracked-doc check (DEC-3). Path lists use --no-renames so a rename out of docs/ or ui/ can't mask the requirement.
Identity-only auth this epic; the crypto signature is E-MRSIGAn identity in .mr-allowed is agent-forgeable, so today's guarantee is a forced stop + an audit trail of who signed, not proof. This is stated wherever the mechanism is documented, never blurred. E-MRSIG swaps only the auth predicate (identity-match → signature-verify); the rules, carriers, hook, gate check and walk all stay. The seam is a single function — mr::message_authorised / tip_authorised.
The UI path set is provisional (ui/) until E-UIFOUND fixes itThe UI-WU rule needs a predicate now to be built and tested; the real asset paths are unknown until the UI stack is chosen. E-UIFOUND owns the final is_ui (recorded in the roadmap).

Consequences

The gate now honestly enforces a human pause and records an accountable signer. The cryptographic form this DEC deferred has since landed: E-MRSIG swapped the auth predicate to signature-verify for key-backed identities through exactly the seam named here (DEC-9); identity-only entries keep this DEC's audit-trail-not-proof guarantee. Until E-UIFOUND lands, the UI-WU rule matches only ui/ paths, so no current WU triggers it; epics and doc commits are live immediately. Adding a person to .mr-allowed is itself a tracked, reviewable diff. (Superseded by DEC-10: the list is a gitignored local trust store, and the UI-path WU rule is replaced by mr-always.)

DEC-8 The epic walk skips history already on the gate target; a per-seam walk waiver on the cr/v2 note is the only recorded override

Statusaccepted · 2026-07-07
OriginEpic E-GATEBM — the walk's three-parent arm mis-gated a back-merge of already-gated history, which already forced a blanket --no-verify onto main (E-NMWF landed at 8871d7b with no receipt on the back-merged tip). Plan/discussion archived under docs/.archive/ (untracked)
Wherextask/src/gate.rs · is_landed_history/record_seam/tip_walk_waivers · xtask/src/notes.rs · CrNote.walk_waivers/walk_waiver_for · workflow.html

Context

The epic gate's seam walk (check 7) is the one place that re-inspects every first-parent seam, and it is the unbypassable backstop against a fail-open or bypassed sub-gate — so it cannot be removed. But it answered only one classification question: "is the merged-in parent already reachable from the epic mainline?" That misses the normal shape of a stale epic that back-merges an advanced main — the two lineages have diverged, so neither contains the other, yet the merged-in tip is already on main and was gated by main's own history. The walk mis-read that integration as a net-new, ungated WU seam and turned the epic gate red on a legitimate merge.

Choices (each looks "fixable" — it isn't)

ChoiceWhy — do not "simplify" it away
Discriminator #2: skip a seam when its merged-in parent is an ancestor of the gate target (p2 ⊑ main), kept alongside the existing p2 ⊑ mainline checkContent already on main was gated by main's own history — there is nothing to re-gate. It is R2-safe by construction: a genuine forward WU seam always carries commits absent from main, so it can never be an ancestor of the target and the skip can never swallow it. The regression test freezes that property rather than hoping for it.
Rejected #1 (symmetric ancestry: also skip if mainline ⊑ wu_tip)Verified against the real E-NMWF back-merge: the diverged lineages mean neither tip contains the other, so #1 does not fix the reported case. The intuition "a back-merge means one side contains the other" is false once both sides advance — the normal state of a stale epic.
Rejected: removing the walkIt is the only re-inspection of seams and the only backstop that a fast-forward or --no-verify can't defeat (DEC-2). Removing it trades a false positive for a permanent hole.
Deferred #3′ (gated-lineage: skip if the merged-in tip's own chain is fully receipted)The fully-general answer — it also covers unlanded cross-epic siblings — but it re-derives the gate recursively and is costlier. No unlanded cross-epic integration has ever occurred; the standing rule is to serialize cross-epic dependencies through main (land one, back-merge, build the next), which turns that case into a plain back-merge #2 already handles. Build #3′ only if live integrations ever become frequent enough that per-seam waivers turn noisy.
R5 waiver valve: a walk seam failure is suppressable only by a walk_waivers: [{seam, why}] entry on the epic tip's cr/v2 note, per-seam, mandatory non-empty why#2 fixes the known misfire; the walk is subtle enough that the next one needs a surgical, recorded override — never the blanket --no-verify, which skips every gate and already defeated the gate once. The waiver waives exactly one named seam; every other seam and every non-walk check still runs.
The waiver rides cr/v2 — not test/v2, not dod/v1A walk waiver is a review judgment ("I looked at this seam the walk can't classify and skipping its re-check is acceptable"), not test coverage (test) and not the gate's own green-only output (dod, which can't authorise its own pass — DEC-2). And cr/v2 is diff-bound (base + diff_sha256): if main moves and the epic's effective diff changes, the review — and the waiver riding it — is forced to be re-validated, so a waiver can't silently outlive the diff it was judged against. An unjustified waiver is a review finding, the same trust model as every other waived (DEC-2).
Manual review (check 8) stays outside the waiver pathThe walk_waivers valve suppresses walk-classification failures only; a doc commit's missing Reviewed-By trailer is a correctly-detected manual-review gap, and manual review is not waivable (DEC-7). Routing check 8 through the valve would make a human sign-off skippable — the opposite of its point. (Since DEC-9 the walk no longer emits doc-commit manual-review failures at all — authorisation is boundary-only; the tip-note check 8 remains, and remains unwaivable.)
Waivers key on the whole seam sha (prefix-tolerant), not per sub-checkThe agent copies the abbreviated sha the walk prints straight into the waiver; per-check granularity is deferred unless it proves too coarse. One named seam, one waiver.

Consequences

A stale epic can back-merge main (or a landed sibling) and walk clean, so the tooling/binary mismatch that forced the bypass self-resolves once a branch is current. The walk's backstop value is intact — genuine ungated seams still turn it red — but its blast radius is defused: a misfire is now a logged, per-seam door on the cr/v2 note, not a blanket --no-verify wall. The standing workflow rule "cross-epic dependencies serialize through main" is now explicit; unlanded live integration has a recorded escape (the waiver) rather than needing #3′.

DEC-9 Manual-review auth is an SSH signature verified against a key entry — native gpgsig for doc commits, note-carried for WU/epic tips

Statusaccepted · 2026-07-11
OriginEpic E-MRSIG — the cryptographic form DEC-7 deferred; plan archived at docs/.archive/ (untracked)
Wherextask/src/mr.rs · signature_authorised/commit_signed/trailer_key_backed · xtask/src/gate.rs · check_manual_review/check_commit_trailer · xtask/src/lib.rs · range · xtask/src/trawler_signer.swift · .mr-allowed · workflow.html

Context

DEC-7's identity-only auth is agent-forgeable by design — the agent knows the user's identity and can emit it. Unforgeability requires the sign-off to be something only the human's hardware can produce: a signature over the exact change, made with a private key the agent can neither read nor operate, verified offline against a public key listed in the repo.

Choices (each looks "fixable" — it isn't)

ChoiceWhy — do not "simplify" it away
SSH signatures (ssh-keygen -Y / git's gpg.format=ssh), not GPG or sigstoreVerification is fully offline with tools already present (git ≥ 2.34, OpenSSH ≥ 8.0); no keyserver, no network trust root. The key type is whatever .mr-allowed lists — FIDO2 sk- keys and Secure-Enclave ECDSA verify identically stock.
Doc commits sign git-natively (gpgsig header), verified at pre-push — not at commit-msgForced by hook timing: git signs after commit-msg runs, so that hook can only presence-check the trailer. An armored SSH signature (~232 chars) in the message body was rejected — the signature rides the commit object header and the message stays clean. The full check lives in one function (check_commit_trailer), shared by the pre-push range check and verify-dod commit.
Enforcement is boundary-only: the epic walk never re-judges doc commits (user decision, W3 review)A commit is immutable but .mr-allowed is mutable — retroactive re-verification would redden legitimately authorised history the moment a key rotates or a tier is delisted, blocking every future epic merge with nothing amendable (rewriting a gated branch orphans its notes). So authorisation is judged once, at the boundary, while the commit and the key list are contemporaries: commit-msg (presence) and the pre-push range check / verify-dod commit (full check incl. gpgsig). Accepted trade-off, same shape as DEC-6: a --no-verify push is never re-checked — the workflow forbids bypassing hooks outright, and the walk still gates every seam, note and manifest. (DEC-10 extends the same boundary-only rule to WU tips' mr/v1 notes at walk seams.)
WU/epic tips carry the signature in the mr/v1 note (base + sig over the base..tip change-hash), verified at gate check 8A merge tip needs authorising before the merge exists, so nothing git-native can carry it; the note already rode the tip (DEC-7). Signing the recomputed change-hash makes it tamper-evident: amend/rebase changes the hash and the signature stops verifying.
The guarantee is per-entry: key entries must verify; email/username entries stay listed-authorisedCoexistence is a migration convenience the user accepted knowingly — an identity-only entry remains agent-forgeable the moment it is listed, so unforgeability holds only for an all-key allow-list. A trailer claiming a weaker tier for a key-backed identity does not dodge the signature requirement (trailer_key_backed matches by identity, not claimed tier).
On a Secure-Enclave Mac, mr setup compiles and installs the bundled trawler-signer (CryptoKit) as gpg.ssh.programThe "no extra apps" requirement: sc_auth cannot produce SSHSIG, and Secretive is an extra app. Rebuilding its core (Enclave key + SSHSIG emission, per-signature Touch ID) is ~200 lines of Swift compiled with the system swiftc; both signing call sites are ours, so no ssh-agent is needed. TRAWLER_SIGN_REASON names the authorised action on the Touch ID sheet so the human knows what they are approving. Verification stays stock ssh-keygen -Y verify.

Consequences

For key-backed identities the sign-off is now proof, not audit trail: the agent cannot self-authorise a doc commit at the push boundary or a WU/epic tip at check 8, and amending a confirmed tip goes red at the next gate. With the identity tiers since delisted from .mr-allowed (all-key allow-list, the steady state this DEC's coexistence caveat anticipated), every doc commit required a Touch ID at commit/push time — a per-commit cost DEC-10 has since rebalanced: the commit gate now covers only rule-bearing files (T0 CLAUDE.md / flat T1 docs/), T2/T3 doc commits pass unsigned, and the human signature moved to the WU/epic boundary where it attests the result report; .mr-allowed itself became a gitignored local trust store. The rules, carriers, hook and check numbering of DEC-7 are unchanged — only the auth predicate deepened. The rule applies forward; pre-existing history is not re-signed. Hardware presence (the Touch ID prompt) is a deployment property: hermetic tests prove the crypto half with software keys, and the e2e (e2e_signed_manual_review_flow_with_a_software_key) drives setup → signed doc commit → signed confirm → tamper → rejection.

DEC-10 Human authority moves to the boundaries: WU/epic mr always attests a result report; commit signatures narrow to rule-bearing files (T0/T1); .mr-allowed leaves git

Statusaccepted · 2026-07-11 · enforced by E-MRSIG.W9 in the same WU that decided it (manager direction at the result-report review: implement with tests, don't defer)
OriginEpic E-MRSIG.W9 — manager-directed brainstorm at epic close (docs/work/2026-07-11-mrsig-w9-check-levels-brainstorm.html, T3, archived with the epic); manager comment rounds decided the open points and pulled the enforcement into the WU
Wherextask/src/notes.rs · is_rule_bearing (replaces is_ui) · xtask/src/gate.rs · check_manual_review/check_attested_report/check_commit_trailer (check 8) + the walk's check-8 filter (check 7) · xtask/src/mr.rs · resolve_report/report_sha/signed_payload/commit_msg_hook · xtask/src/notes.rs · MrNote.report/report_sha256 · .gitignore (.mr-allowed) · workflow.html · work-planning.html

Context

The all-key allow-list (DEC-9's steady state) made every docs/-touching commit cost a Touch ID — including T3 scratch — while a WU merge needs no human at all unless it touches UI, and the result reports the work-planning standard demands are invisible to the gate ("relation to the DoD gates: none mechanically"). The epic result report can't even be tracked at gate time: check 6 (DEC-3) refuses tracked docs/work/ files at the epic tip and T3 archival precedes the merge. Human attention was being spent where nothing meaningful is read and missing where something is.

Choices (each looks "fixable" — it isn't)

ChoiceWhy — do not "simplify" it away
mr/v1 becomes always required at WU tips, like epic tips; the UI-only path derivation is droppedThe WU merge is the first boundary where a human has a readable deliverable (the wu-result report). Supersedes DEC-7's UI⇒WU path rule; the is_ui predicate is no longer needed for manual review (E-UIFOUND's ownership of it lapses unless another check adopts it). Stays not-waivable — a waivable sign-off is not a sign-off (DEC-7).
Sign-what-you-read: mr confirm names the level's result report, records its path + sha256 in the mr/v1 note, and the key-backed signature covers the base..tip change-hash plus the report hash; check 8 verifies bothThis is what makes "mr always" worth its touch — otherwise the WU mr is a blind tap. For the epic it is the only shape that survives archival: the proof is the hash, not the file's git status, so DEC-3's tracked-layout rule keeps holding while the archive copy re-hashes offline forever. Chosen over lineage-only (proves a note claims a report) and over tracking the report on main (T3 on main rots by definition; rejected).
Commit-level signatures narrow to rule-bearing files: T0 (CLAUDE.md) and T1 (flat docs/*.html); T2/T3 doc commits go unsignedT0/T1 configure the workflow the agent runs under — an unsigned edit there lets an agent weaken its own gates, and post-hoc review of a rule change is too late (DEC-7's commit-time argument, kept). T2/T3 are agent-synthesized records whose substance the WU/epic reviews judge, and with WU mr always, every one now passes a human boundary. Also plugs a real gap: CLAUDE.md sits at the repo root and today's docs/-keyed rule never covered it. decisions/ stays unsigned: enforcement lives in T1 + gate code, a reworded DEC changes nothing a hook refuses.
.mr-allowed is gitignored — a local trust store provisioned by mr setup, never committed (manager decision)Signature verification is a local-machine concern: hooks and gates all run on the machine holding the list, so versioning it adds no enforcement — and the tracked file was itself an unsigned seam (neither code path nor docs/: an agent could append a key it controls through an ordinary infra commit and self-sign for the rest of the epic). Local-file tampering remains possible but is the same trust boundary as editing a hook — forbidden by the workflow, accepted shape per DEC-2/DEC-6. Supersedes DEC-7's consequence "adding a person to .mr-allowed is itself a tracked, reviewable diff".
T1 flips in the same change as the enforcement, never earlierT1 states what the hooks enforce now — a T1 claiming the new rule while the old hook still refused unsigned T2/T3 doc commits would steer agents into refused commits (code wins conflicts — the documentation system's own rule). Held: docs and code landed together in W9.
The epic walk never re-judges a WU tip's mr/v1 — manual review is boundary-only at seams, enforced by the WU merge hook when the seam is madeSame argument as DEC-9's doc-commit rule, made acute by the gitignored list: mr/v1 verifies against the mutable, local .mr-allowed, so a walk re-judgment would redden authorised history after key rotation — and on any fresh clone, where the list is empty. It also grandfathers pre-DEC-10 WUs (W1–W8 carry no mr notes). The epic tip's own check 8 always runs.

Consequences

T2/T3 doc commits cost no Touch ID; every WU merge costs exactly one, attached to a result report the human read (the signed payload is change-hash\nreport-sha256); epic touches are unchanged in count but attest the epic report's bytes; CLAUDE.md gains the commit-time signature it never had. A fresh clone verifies no signatures until mr setup recreates the local list — by design, like hooks needing installation. The result reports the work-planning standard demands stop being gate-invisible: existence and exact content are part of check 8. The is_ui predicate is deleted — nothing derives from UI paths any more; if a future check needs one, E-UIFOUND still owns the path set. The rule applies forward: pre-DEC-10 seams walk clean (boundary-only), and E-MRSIG's own epic confirm is the first production mr confirm --report.

Because the roster is local while notes are repo-wide, a valid signature and an unlisted signer are routinely the same tip read from two checkouts — so check 8 names which of the two it found: the signer and the roster path it read, distinct from a signature that fails against a listed key (E-GATETRUTH.W3). Deciding that from one sentence cost two wrong diagnoses on a merge whose signature was valid. The predicate is unchanged; only the account of a refusal is new.

DEC-11 Gate speed is bought by caching under DEC-2, never by relaxing it — incremental Gate 0 is the one cut that survived measurement

Statusaccepted · 2026-07-11
OriginMinted as DEC-9 on the parallel E-GATEFAST branch; renumbered DEC-11 at the E-MRSIG merge — an id race between concurrent epics, and E-MRSIG's DEC-9 carried the wider cross-reference web. Epic E-GATEFAST — six candidates measured, one adopted (owner verdict at epic close); plan, discussion and WU/A-B reports archived under docs/.archive/ (untracked)
Wherextask/src/gate0.rs · xtask/src/git.rs · worktree_key · code-review skill §Gate 0 (infra markdown)

Context

Landing a change measured 45–106 min of active agent time per gate-heavy epic, and the transcripts located it: main-loop generation 32–56%, the code-review fleet a stable ~25% re-run from scratch on every delta — while verify-dod itself is <0.5%. Every speed candidate is therefore a caching/scoping problem under DEC-2's recompute-don't-trust invariant: a cache that reports green for a tree it did not verify is worse than a slow gate.

Choices (every rejection is a measured A/B, not a hunch)

ChoiceWhy — do not "simplify" it away / do not retry without new leverage
Adopted: Gate 0 (fmt+clippy+tests) skips when the working tree is byte-identical to the last green run — key = full worktree hash (HEAD + git diff HEAD + untracked non-ignored contents), cached in a local target/.gate0-green file (key definition superseded by DEC-54, which drops HEAD and the diff for the tree's content; the cache's shape and its store-the-key rule are unchanged)The cache stores the key it vouches for, never a bare verdict, so a skip fires only when the recomputed key matches — DEC-2 applied to a cache. A file under target/, deliberately not a git note: the fact is ephemeral and per-checkout, cargo clean co-invalidates it, and it never syncs (another machine has not run this build). Recovers the cargo bucket previously paid 2–3× per review.
Rejected: note/doc skeleton generation (W1, C4)A/B (n=3/arm): on a capable model the hand-authored arm passed the gate first try, so the round-trip saving never reproduced — ~31% fewer tokens but ~1.9× wall-clock in print-only form. The win is contingent on weaker models or harder diffs; not adopted.
Rejected: faster review model (W3, C6)A/B on a labeled diff: Sonnet finders 2/2 known-real, ~25% faster — but Sonnet verifiers flipped 3/9 verdicts vs ground truth (a spurious PASS→FAIL), and the verify phase had no wall-clock headroom (47s vs 50s). Verifier quality is the binding constraint; owner closed the epic without adopting the switch for either role.
Rejected: context-pack for finders (W6)A known-real finding escaped and the critical path grew +63%. Failed on both axes.
Rejected: sharded correctness finder (W7)Parity and recall held but the critical path grew +11% — restructuring cost exceeded the parallelism it bought.

The "provably-safe delta" definition — the piece that would let a trailing docs-only fix skip the full sweep — remains open; it is the epic's one unexplored lever and was always flagged as its highest-care call (too-loose reopens the R2 hole).

Consequences

Gate 0 is paid once per green tree instead of 2–3×; any tree change — code, test, whitespace, a new untracked source file — re-runs the full trio, pinned by regression tests. The review fleet's critical path is empirically floored by the slowest finder plus Opus verification: three independent restructurings (pack, shard, stream) all lost their A/Bs against that floor, so do not retry them without changing the floor itself (a faster trustworthy verifier, or W4's safe-delta scoping).

DEC-27 The human signature goes last — mr confirm refuses a tip whose tree can still move

Statusaccepted · 2026-09-02
OriginE-DFLOW.W11 — committed the defect against itself: the sign-off was taken before the review ran, and the review then found the attested report's cost section stated a backwards conclusion. Found by the WU's own cr/v3, fixed in it rather than filed
Wherextask/src/mr.rs · unready_reasons · tip_unready · workflow.html §sign-last

Context

Every binding on a tip pins the diff it was made against — cr/v3 its diff_sha256, mr/v1 the result report's bytes (DEC-10). So any tree change after a binding orphans it, and a signature taken early is spent twice. The gate already refuses a stale review at merge time (checks 3–5), so nothing false can land; what was unguarded is the human's time and the meaning of their attestation. mr confirm would sign a tip with no review at all, or one whose review said FAIL.

A circularity makes the order strict rather than merely preferable: a test/v2 receipt that honestly reports a missing test can only be acted on by adding the test — a tree change, which invalidates a signature already given. Receipts therefore precede the signature; they cannot follow it.

Choices

ChoiceWhy — do not "simplify" it away
Adopted: mr confirm refuses unless test/v2, doc/v1 and a diff-bound cr/v3 PASS are already on the tip, refusing before the signing promptWriting a receipt is the act that carries settling the thing it attests, so a missing receipt means the tree may still move. Refusing before the prompt is the point: a passphrase or Touch ID spent on a doomed tip is the cost being prevented
Rejected: fold the cr hash into the signed payloadWould make the signature attest the verdict too — strictly stronger, and it breaks every existing mr/v1 note, needing an mr/v2 migration. The precondition buys the ordering with no compatibility break; revisit only if a signature over an unreviewed diff is ever observed
Rejected: verify the test/v2 claim against the diffThe receipt is written by the agent that adds the test; the two travel together. A gate reading the diff for test files would fire on honest multi-commit WUs and does not address the ordering defect this record is about
Rejected: warn instead of refuseWould not have stopped the founding instance — the warning would have been read and passed
Rejected: a new numbered gate checkThe merge gate already re-verifies the review (checks 3–5). A second check there would duplicate it; the gap was at the point of signing, so the guard belongs there

Consequences

The order is now tree-changing work → test/v2 + doc/v1 → cr/v3 PASS → mr confirm → merge, and it is machine-refused rather than remembered. One hole stays open by design: when no merge target resolves, the diff-binding half is skipped rather than guessed — check 5 still refuses a stale review at the merge, so the failure mode is a wasted signature, never a bad landing. Existing mr/v1 notes verify unchanged; the signed payload is untouched.

DEC-54 The cache key is the tree's content, not its history — and the commit hook reads a cache of its own

Statusaccepted · 2026-09-18
OriginE-SIMPDF.W3 — the owner asked why cargo xtask mr commit waits minutes before the signing passphrase. It does not: mr_commit spends microseconds and then calls git commit -S, whose pre-commit hook ran cargo fmt --check and cargo clippy --workspace --all-targets --all-features blind, ahead of the signature git can only take afterwards. Admitted into E-SIMPDF by the owner's call; its lineage is DEC-11 / E-GATEFAST
Wherextask/src/git.rs · worktree_key · xtask/src/gate0.rs · lint · .cargo-husky/hooks/pre-commit · xtask/tests/gate0_cache.rs · tests/dod_hooks.rs

Context

DEC-11 built the cache that answers "has this tree already been proven green?" and wired it to the review preflight alone. The commit hook — the gate an agent crosses most often — never asked it. Two facts made simply wiring it up insufficient:

FactMeasured
The old key hashed HEAD, so a commit invalidated a proof its content never touched — and a Working Unit is many commitsAcross a content-neutral commit in a scratch repo the key moved ca92183e… → 847a2513…; a content key held at b824d8cf…
Clippy's cost is bimodal, not small: it is near-free warm, but cargo clippy and cargo test invalidate each other's fingerprints, so any hook run following the suite recompiles the graph0.1 s warm · 11 s after a test run · minutes cold. DEC-6 already called it "a minutes-long clippy run" when it put the main refusal first
Reading the worktree is cheaper than the git diff it replaces312 files / 4.0 MB: 27 ms for the content key against 42 ms for the old one, which forks git twice

Choices

ChoiceWhy — do not "simplify" it away
Adopted: worktree_key hashes content — every tracked and untracked non-ignored path, its bytes, its executable bit, and the fact of a deletion — and neither HEAD nor git diff HEADIdentical content under a new commit is the same tree to every compiler, so hashing history bought nothing and cost a false miss per commit. It is DEC-11's own invariant read strictly: the key must describe what the build reads. Every invalidation DEC-11 pinned still fires, which is the acceptance criterion rather than a formality — the deletion and the mode bit came free from git diff HEAD and are now recorded as themselves, or they would have gone invisible.
Adopted: two markers — .gate0-green (fmt+clippy+tests) and .lint-green (fmt+clippy) — with a matching .gate0-green accepted as proof at the lint level and never the reverseA marker means "this content passed this check set". One file with a level in it would either let a lint-only pass answer for tests that never ran — a cache reporting green for work it did not do, the one thing DEC-11 forbids — or make every commit pay for the suite. The implication runs one way, and the reader encodes that direction rather than leaving it to a caller.
Adopted: the hook calls one command, cargo xtask lintThe skip rule, the marker paths and the --workspace scoping then live in tested Rust instead of shell. Moving it costs a test: before, the hook's own text was the executed command, so reading the file pinned what ran. A unit test on the CLIPPY constant does not replace that — it pins the constant's contents, not that run_lints forwards it to a real process, and this record claimed otherwise until the review that judged this diff refuted the claim by dropping --workspace from run_lints and watching every test stay green. xtask/tests/lint_spawn.rs closes it: it runs the real binary against a fake cargo on PATH and asserts the spawned argv. A guarantee that moves layers is not pinned until a test reads it at the new layer.
Rejected: prompt for the signature first, then checkWhat the owner asked for, and git cannot do it. pre-commit → commit-msg → write and sign the commit object is git's fixed order, and no hook runs after signing that can still refuse. The only way to put the prompt first is --no-verify plus a post-commit check that resets on red, which the workflow forbids outright.
Rejected: move the lint pair to pre-push, where the suite already runsDefensible under "the merge is the gate", but it lets a red tree sit in local history and it relaxes a gate rather than caching it — DEC-11's standing rule. Caching reaches the same speed with no rule changed.
Rejected: narrow the hook's clippy (drop --all-targets/--all-features, or scope it to staged packages)Same objection: it buys speed by checking less. The scoping is load-bearing — without --workspace the xtask member, where every gate and hook lives, goes unlinted by the gate that proves the tree green.
Rejected: reuse .gate0-green alone, without a lint markerA miss would then run the whole test suite at commit time — worse than the pair it replaced. The weaker marker exists precisely so a miss costs only what the hook always cost.
Not hashed: the indexDeliberate, and unchanged from DEC-11: fmt, clippy and the tests read the worktree, so the key describes what the compiler sees. A tree staged differently from disk was never covered by either key.
Not adopted here: the signing prompt itselfThe wait and the prompt are separable. user.signingkey pointing at an encrypted private key makes ssh-keygen -Y sign decrypt it on every signature; pointing it at the .pub with the key in an agent removes the prompt entirely. That is local configuration, not a repo rule, so it is recorded here and not enforced.

Consequences

A commit on a tree already proven green runs no fmt and no clippy, including the second and every later commit of a Working Unit, where only HEAD moves. The review preflight gains the same relief for free, and its miss was the expensive one — it re-ran the whole suite. A key that no longer mentions HEAD also works on an unborn branch, where rev-parse HEAD used to error. The blast radius is wider than the hook: every caller of worktree_key now keys on content, so the five invalidation properties gate0_cache.rs pins are the contract, joined by a content-neutral commit holding the key, a tracked deletion changing it, and an executable-bit flip changing it. The hook is installed by cargo-husky at build time, so the new one takes effect after this lands and a build runs — until then a checkout keeps the blind pair. (Superseded by DEC-72: the copy never re-installed, so this hook never ran until git was pointed at the tracked hooks. The markers live in each worktree's own target/ since DEC-73.) Because the hook no longer carries the command it runs, xtask/tests/lint_spawn.rs is now the only thing standing between a run_lints edit and a silently narrowed lint; delete it and the scoping goes unpinned again.
