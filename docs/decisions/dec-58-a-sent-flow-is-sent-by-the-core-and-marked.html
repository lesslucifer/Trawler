DEC-58 — a sent flow is sent by the core's own client, and marked

Trawler can send a request itself. The exchange lands as an ordinary flow with a third provenance, sent, and a link to the flow it came from. An exchange that never happened lands nothing.

v1 · 2026-09-25 · Trawler · T2 decision · minted by E-REPLAY.W1 · extends DEC-38 · re-argues DEC-55 · UC-8

Why this record exists

DEC-38 made an imported flow "inspectable, never executable" and left firing one at a server to "a different capability with its own decision". This is that decision. Until now the core had one outbound path, the proxy, and every flow either passed through it or came out of a file.

Decision. The core sends through a Sender of its own, which connects through the proxy's upstream_connector. Two doors reach it: POST /flows/{id}/replay (a seed plus overrides) and POST /flows (a request from scratch). The call answers once a reply exists, and only then does the flow land, marked source: sent with seed naming its origin or null.

What it rules

RulingWhy this wayRejected
sent, not replayed a composed request replays nothing, so replayed would be false for every flow the compose door makes. sent is true of both doors: Trawler's own client made this exchange replayed · two values (replayed / composed), which split one mechanism into two filters
A seed link, dangling by design the link records where the request came from. The ring may evict the seed, and the sent flow keeps naming an id that now 404s. Keeping the seed alive would let a replay pin memory the ring exists to bound clearing the link on eviction, which rewrites a recorded fact · pinning the seed
No flow for an exchange that never happened a flow asserts that an exchange happened. Refused, unresolvable, TLS rejected, or no reply head within 30 s: the caller gets 502 / 504 with the reason in words, and the ring is untouched. A reply whose body stalls is still an exchange, so it lands with a read_error body a pending row inserted at send time, which either stays pending forever or has to be deleted, and makes the list describe traffic that did not occur
Verified exactly as the proxy verifies the sender is built on the same upstream_connector function (webpki roots plus upstream_extra_root_pems, ALPN h2 / http/1.1), so the two outbound paths cannot come to trust different upstreams an insecure-TLS toggle, per-send CAs, client certificates. Loosening verification needs its own decision
Not through the proxy port a request looped through :7420 would land as captured, with no seed and no id to hand the caller sending via the proxy

The header rules, and why they are rules

RuleWhy
Content-Length is the body's the most common edit is the body, and a stale length cuts it short on the wire
Host follows the URL unless the caller typed one a changed URL with the seed's Host routes to the wrong site. The seed's own Host is not "typed". Only one in a header list the caller gave is
connection headers are the client's HTTP/2 refuses Connection, Keep-Alive, Proxy-Connection, Transfer-Encoding, Upgrade and TE outright, and a seed captured through the proxy routinely carries one
several Cookie headers join into one the proxy's own normalization. An h2 seed may split cookies and an HTTP/1.1 server takes one

Everything else goes as given, in order, duplicates kept. A given header list replaces the seed's whole rather than patching it, because the composer always holds the full edited list. A patch language would be a second syntax to learn and to test.

400 and 422 mean different things

StatusMeansExample
400the caller's request is malformed url must be absolute http(s) · method is required · an unknown field, refused rather than ignored, because a typo'd header would silently send the seed's headers
422the request is well-formed, but the seed lacks what must be supplied the seed's request body was not captured (too_large); give a body to replace it. A missing body is never sent as an empty one, the principle UC-6 holds for export and import

Reach: why the doors add no exposure

When reach is armed (DEC-55), a device on that network can call the send doors and make Trawler issue a request, for example to http://192.168.1.1/admin. The same device could already do exactly that through the proxy reach opens: curl -x 192.168.1.5:7420 http://192.168.1.1/admin. The send doors reach the same upstreams, with the same verification, from the same host. They add no reach the armed proxy does not already grant, so they take no gate of their own. A 403 on the reach address would guard a door whose neighbour is open. What DEC-55's confirm buys is still the whole boundary.
