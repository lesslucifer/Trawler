DEC-45 — the review binds the code it judged

E-SIMPWF.W4 makes the code review's subject, binding and inputs the code paths: the note is cr/v4, its diff_sha256 covers is_code and nothing else, and a diff that changes no code path is asked for no review at all.

Decided 2026-09-12 · E-SIMPWF.W4 · active

The decision

The code review binds the bytes of the code paths it judged. The note is cr/v4, and its diff_sha256 is the hash of git diff --no-color --no-ext-diff BASE..HEAD -- <the paths notes::is_code names> — src/, xtask/, tests/, ui/src/, ui/e2e/. A document the review never opened cannot move it, so a docs-only commit landing after a PASS neither voids the verdict nor re-buys the fleet; a code edit still voids it, and the note the gate wants is written by the same command that printed the range, under the same flags.

A cr note is demanded iff the diff touches a code path. A diff that changes no code is not asked for one, and a review dropped on such a tip anyway refuses nothing and proves nothing — there is no code subset its verdict could be about.

The schemas before it keep their own meaning: a cr/v2 or cr/v3 note is judged against the whole-diff hash it was written about, so every tip merged before this change — including this epic's own seams — re-verifies exactly as it did.

The preflight drops doc/v1 from what it stops on. The review no longer reads it, and a doc note can no longer orphan the PASS, which was DEC-43's whole criterion for what a preflight may refuse.

Why it needed deciding

The PASS was bound to the whole diff. That made a document part of the review's blast radius twice over: the finders were handed docs to judge, and any later doc commit moved the hash the gate recomputed, so the fleet ran again to re-judge code that had not changed. E-SIMPWF measured the shape of that waste (DEC-42) and the plan ruled the review code-only. The binding is the piece that makes the rule real: without it, "the review judges code" would be a statement about its prompts while its evidence still died of a README edit.

What binds, and what does not

ThingWhat happens to itWhy
A code path changes The subset hash moves; 5·diff-binding refuses until a review of this exact tip lands the verdict is a claim about these bytes, and code is what it judged
A document changes Nothing: the subset hash is unchanged, and the PASS stands on the new tip no finder read it, no check of the review's compares it; the authoring-time doc checks and the human sign-off are its gate
A diff changes no code path No cr note is demanded or read; the gate asks for what the diff does owe the review has no subject on such a diff, and a note about nothing is not evidence
A cr/v2/cr/v3 tip Compared against the whole-diff hash, as its schema says a note is immutable evidence; re-reading it under a binding it never made would redden history the walk is supposed to re-verify
The subset is empty but a note is present The note is ignored: no verdict, no refusal a claim about no code is not a claim this gate can check, and refusing it would demand a review the workflow does not ask for
