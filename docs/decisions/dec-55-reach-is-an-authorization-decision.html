DEC-55 — reach beyond loopback is an authorization decision

Trawler may listen where another device can reach it. That is not a configuration flag: it is off by default, it costs one explicit confirm, it dies with the process, and it binds one address the user named — never every address the host holds.

v1 · 2026-09-19 · Trawler · T2 decision · minted by E-ONBOARD.W1 · relates to DEC-13, DEC-12 · UC-ONBOARD

Why this record exists

Trawler bound 127.0.0.1 for both servers since the first commit, and the rest of the system quietly leaned on it — most visibly the control API's open CORS grant, which architecture.html justified with "adding no exposure beyond the bind address". The onboarding redesign broke that silence: once the setup screen makes the user name a platform, five of the eight it offers — another machine, an iPhone, an Android device, and the two emulators that are only sometimes local — have no address to point at and no route to fetch the certificate. The screen could either apologise to five of eight platforms, or Trawler could answer off this machine.

Decision. The core gains a reach choice. By default both servers bind loopback and nothing outside the machine can connect. A user may arm reach on one interface address, at which point the proxy and the control API also listen there and /ca.crt is fetchable over it. Arming is an authorization act, not a setting: the native shell asks first, the answer is not written down, and it lasts exactly as long as the process. Nothing finer — no token, no TLS, no per-origin CORS — is added, and the grant does not widen with the bind.

The four rules

RuleWhat it means in the treeWhy this way
Off by default Config::default() is Reach::Local; loopback is the only bind until something arms it. Arming adds a second pair of listeners and never moves the first Every install that does not need reach pays nothing for it, and the loopback path — the ~90% single-machine case — cannot regress by accident
One named address The unspecified address (0.0.0.0, ::) is refused with a reason. Any other address is adjudicated by the bind: one the host does not hold fails, in the OS's own words The screen has to print an address anyway, so nothing is gained by listening on all of them — and a mistaken confirm then costs one network instead of every network the host is attached to. The control API enumerates the routable interfaces so the user picks from what exists rather than typing
One explicit confirm The Tauri shell owns the ask (confirm_reach), the same place the CA install and the system-proxy write already live per DEC-13. The dialog names the address and what becomes reachable through it DEC-13's rule is that an action changing what the host exposes costs one explicit confirm. This changes what the host exposes
Re-armed per launch Nothing persists. The listeners live in the process; shutdown takes them with it The revert-on-quit symmetry DEC-13 requires of the system proxy, got for free by never writing the state down. A host-affecting state Trawler set does not outlive the session that confirmed it

What arming actually exposes — stated, not implied

Arming reach exposes the proxy and the whole control API on the chosen address. The control API serves the captured flows, their bodies and their headers, so anything on that network can read the traffic Trawler has captured, clear it, or route its own traffic through the proxy. That is what the confirm buys, and the dialog says so.

This is a deliberate boundary, not an oversight. Splitting the surface — a remote route for /ca.crt alone, a token, TLS on the control API, a per-origin CORS policy — is real work with its own design, and E-ONBOARD explicitly does not take it. The residue leaves as a backlog row rather than as an unstated assumption.

What the confirm is, and is not

It isIt is not
The record that a user decided to expose this machine — the difference between Trawler being reachable and Trawler having been made reachable An access control against a process that already holds loopback. Anything that can reach the control API can arm reach, exactly as it can already clear the capture or read every flow. The trust boundary is unchanged; what changed is that the default is no longer the only possibility
Unavoidable in the product path: the screen's only route to reach runs through the shell's dialog Unforgeable. A local script may drive the API directly, and always could

The CORS grant does not widen

The control API answers every request with Access-Control-Allow-Origin: *, because the native app is a cross-origin client of it (DEC-12). That grant is unchanged by this record and unchanged by arming: the same middleware, the same headers, over both addresses. What is retired is the sentence that justified it — "the surface is loopback-only" is no longer true of an armed process, and the honest justification is the one above: the grant permits nothing the bind does not already permit, and the bind is now a confirmed decision rather than a constant.

Rejected

AlternativeWhy not
A CLI flag or config file entry — --listen 0.0.0.0 It makes exposure a default someone can inherit. A flag in a shell profile or a checked-in config outlives every session and asks nobody. The whole point is that the decision is taken by a person, for a session
Binding 0.0.0.0 and letting the screen pick which address to print It listens on networks the user never named — a VPN, a bridged container network, a conference Wi-Fi — to render one address. The blast radius of a mistaken confirm should be the network the user was thinking about
Persisting the opt-in so setup is not repeated It converts a session decision into a standing one, and it would have to be reverted on quit to keep DEC-13's symmetry — which is the same work as re-arming, with a file to get wrong
Shipping a token or TLS with the bind Worth doing, and too big to ride along. Bundling it would make this record about authentication rather than about the decision to expose, and would have stalled the screen that needed the address
Putting the bind in the core's startup and restarting the core to arm The shell is an out-of-process client (DEC-12) and does not own the core's lifetime; a restart would drop every captured flow to turn a listener on
