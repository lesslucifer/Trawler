DEC-50 — the fleet carries only the dimensions that pay

198 recorded rounds say two of the five finder dimensions never produced a severe code finding and a third produced at most one. They are retired and made conditional, each beside the number that retired it, and the verifier stage is grouped by the code a verifier must read — with the one severity that decides a verdict kept out of every group.

Decided 2026-09-16 · E-SIMPWF.W9 · active · supersedes part of DEC-48

The decision

The rule. The fleet carries only the dimensions that produce severe code findings. correctness and efficiency always; altitude only where the diff's code paths resolve to more than one module; simplification and reuse are retired. The verifier stage batches by relevance — candidates sharing the code a verifier must read go to one agent — except that a candidate proposed blocker never joins a batch.

Each retirement is recorded in rubric.md beside the corpus number that retired it, so a later reading of "more coverage" cannot re-buy a dimension without new evidence.

The first reading, taken by E-SIMPWF.W9's own review: 934k tokens, not ~410k. 3 finders (500k) and 3 relevance batches over 5 claims (434k), against a ~1.05M baseline — an 11% saving, not the 61% projected. The projection is wrong because of the arithmetic above it: it priced a finder at W6's 98.6k mean and a verifier at 52k, and this round's agents cost 102k–202k and 126k–157k because they reproduced their findings — building the binary, driving scratch repos, shimming git — rather than reading and reasoning.

The cut is real; its size was overstated. A round's cost is set at least as much by how hard its agents work as by how many there are, which is the token-axis companion to DEC-49's rule about the clock, and which no cut priced per-agent can predict. One round is one reading — but every future proposal priced off W6's means owes this correction first.

Four rounds now exist, and they are the argument for this shape rather than against it. 934k, 716k, 522k and 653k tokens; 2 or 3 finders and 2 or 3 relevance batches each. Across them the fleet raised 14 candidates, refuted 1, and found 4 verified blockers — every one of them in the other half of the Working Unit that proposed it, which was withdrawn as a result (DEC-51). A two-finder fleet judged against the bar no verified blocker or important is lost caught four blockers in the diff it was reviewing. The blocker guardrail — a proposed blocker never joins a batch — was exercised on all four.

Why batching is not the batching DEC-48 refused

W6's reasonDoes relevance-grouping answer it?
"A batched judge reads every claim's surrounding code in one context instead of several in parallel" Yes — this is the whole point. W6 batched the whole pool, undifferentiated, so one agent serially read every region the pool touched. A batch grouped by shared code reads that region once for all its claims. The cost W6 measured (4.6× the stage, +398s) is the cost this shape removes
"A verifier that has already confirmed one claim is no longer a fresh adversary for the next" No — and grouping makes it worse. Relevance-grouping puts the most correlated claims in one context, which is exactly where a confirmation carries over. This is the risk the record accepts, and why the blocker guardrail is part of the rule rather than advice

Why the bar moved

W6 pre-registered its bar as every known-real finding in the corpus is raised by the new fleet. No cut that removes scope can pass that bar — by construction, removing a dimension loses that dimension's findings. So the epic could adopt only cuts that lose literally nothing, and exactly one such cut exists: Gate 0's ordering. That is the mechanism by which three Working Units of measurement produced 60 seconds.

This record is judged on no verified blocker or important is lost.
