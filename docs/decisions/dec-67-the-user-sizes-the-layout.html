DEC-67 — the user sizes the layout

The list/pane split, the headers/body split, the flow list's fixed columns and every window are sized by the user within designed bounds, and come back the way they were left. The designed values become the defaults a reset returns to.

v1 · 2026-11-03 · Trawler · T2 decision · minted by E-PANELS.W1 from the epic plan's rulings Q1–Q9 · supersedes in part DEC-36 (its rejection of a draggable split) · UC-4 · UC-5 · active

Why this record exists

BeforeWhat changed
DEC-36 fixed the pane at 520 px and rejected a draggable split: three things the shell lacked (a stored preference, a drag affordance, a minimum on both sides) for a gain its run could not showthe owner asked for the capability, 2026-11-03: a reader with a long cookie wants a wider pane, one scanning paths a narrower one, and every relaunch forgot the window. The gain is now the requirement, and E-PANELS builds all three

Decision. Each split and each fixed flow-list column is draggable and keyboard-resizable between a minimum and a maximum; nothing collapses to zero. Sizes persist in the shell, in layout.json in the app config directory: pane width, headers share and the column widths once for the whole app, window geometry once per window label. A saved layout is restored whole or not at all.

The persistence contract

#RuleWhy
1The shell owns the file, beside the dismissed-notice markers; the app reaches it through layout_read / layout_write. No layout state passes through the core or the control APIone home for the app's remembered choices (as DEC-66); curl keeps seeing everything the app does (DEC-12)
2Pane width, headers share and each column width are one value for the whole app; window size, position and maximized state are one record per window labelevery flow opens at the same pane, an inspector window reads the same headers share as the main one, and each window reopens where it was
3No version field. A file that does not parse into exactly the current shape (missing, extra or mistyped field, not JSON) reads as no saved layout: the whole default, never a partial restorea part of a layout restored beside defaults is a layout nobody chose
4The store checks shape, never bounds; the app clamps a restored value to the live boundsthe bounds are tokens and the window's size, both of which can change under a saved value
5A write replaces the file whole, through a staged sibling and a renamea crash mid-write leaves the old layout or the new one, never a torn file

Rejected

AlternativeWhy not
The window's localStorageper origin: the dev server and the bundle would keep separate layouts, and the e2e could not clear it from outside
A version field with migrationsa layout is cheap to lose and costly to restore wrong; the default is always a valid answer
Saving sizes per windowthe pane and the headers share would differ between windows showing the same flow
Storing layout in the corethe core has no window; layout is the shell's
Collapsing a panel to zeroclosing the pane stays deselect the flow
Reordering or hiding columnschanges the arrangement, which this record keeps fixed
