DEC-56 — the app may prove capture with a request of its own

The last task of setup asks the user to produce traffic. Today it asks them to open a website or run a curl command. A user who does neither has no way forward — so the app may fire one request through the system proxy itself, and that is a capability decision, not a button.

v2 · 2026-09-28 · Trawler · T2 decision · minted by E-ONBOARD.W6 from the PO review's F24 · relates to DEC-13, DEC-33 · UC-ONBOARD · built by E-ONBRVP.W2

Why this record exists

Setup ends on evidence, never on assertion: only a decrypted flow reveals the list (DEC-13). The user therefore has to make one request happen. The screen offers two routes — open any website, or run the copyable curl -x … — and the PO review found that the second is written for someone who already knows what curl is, while the first silently assumes the browser on this machine uses the system proxy.

An in-app Test now closes that gap in the strongest possible way: it proves the certificate and the proxy at once, because a request the app makes through the system proxy can only be decrypted if both are in place. But it makes Trawler a client of its own proxy, and that is a new thing for this app to be.

Decision. The app may fire one HTTPS request through the system proxy to prove setup, on the user's explicit click and never on its own. The request is the user's act, and the screen still reports only what the traffic layer observed — the button produces evidence, it never produces a verdict. It costs no confirm: unlike the trust store and the system proxy, one outbound request changes nothing about this host.

The rules a build owes

#RuleWhy
1The button produces traffic; it never produces a state. The task's reading stays the traffic layer's, judged against its clockDEC-33 — a ✓ the user clicked into existence is the one thing this screen has never done
2It goes to a destination the user can see in the sentence, and one Trawler does not owna request to an address the app chose in secret is a fact the user cannot check, and the whole screen is built on checkable facts
3It is not run automatically, on mount, on a timer, or as part of the set-up actionan app that reaches the network because it was opened is doing something its user did not ask for. It is also what would make this a privacy question rather than a convenience
4A request that fails says what failed, in the user's words, and leaves the manual routes standingthe failure is informative — a refused connection through the proxy is itself a reading — but it is never the app blaming the user
5The two manual routes stay. The button is a third, not a replacementa developer who wants the curl is the audience the screen started with, and the epic's rebuild never removed a route

What this does not decide

Which destination the request goes to, and whether it is configurablethe build. Rule 2 constrains it: visible in the sentence, not owned by Trawler
Whether the request is made by the core or by the shellthe build. Either satisfies the rules; the shell is the natural home because the system proxy is the host's and DEC-13 keeps host-reading out of the core
Whether an off-machine platform gets one toonothing here can prove a phone's setup from this machine — a request this app makes travels through this host. The button is the host platforms', and the record says so rather than leaving it to be discovered
