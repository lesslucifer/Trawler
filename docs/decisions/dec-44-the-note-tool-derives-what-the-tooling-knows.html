DEC-44 — the note tool derives what the tooling knows

E-SIMPWF.W3 puts one command in front of the two notes a review reads: it computes every field git can answer, writes both notes from one judgment, and refuses — writing nothing — when the judgment and the range disagree.

Decided 2026-09-12 · E-SIMPWF.W3 · active

The decision

The tip's test/v2 and doc/v1 notes are written by cargo xtask notes write <wu|epic|commit> <tip> [--target <ref>] [--judgment <path>|--template], from one YAML judgment document — stdin, or --judgment — that is the two notes with every derived field removed: tests without count, changes without tier, and no schema, level, epic, wu or branch. The command puts those back from the range, so a derived fact has one author and cannot be typed wrongly. --template prints the derived skeleton — the touched doc paths with their tiers, and the layer the level requires — and writes nothing.

It writes nothing unless the notes it derived would pass the gate's own note checks: it renders both notes, parses them back, and runs 2·manifest and 6·doc-note with the same functions the merge calls. A judgment the range denies comes back as those blocks, or as its own 0·judgment when the disagreement is inside the document itself, and the tip is left untouched. On success it prints the range it pinned — base, head, diff_sha256 — which is what the review writes into its cr/v3 note, so the notes and the verdict are about one diff.

Why it needed deciding

The evidence the merge reads is written by an agent between two other steps, and every field in it that git already knows was retyped from the diff: a doc's tier, the list of changed docs, the identity block, the per-layer counts. The gate catches a wrong one — 6·doc-note compares the note against the diff, 2·manifest against the level, 1·notes across the three notes — but it catches it at the merge, after the fleet has judged the tip and the human has been asked to sign it. The repair is then a commit, and a commit after a verdict orphans it (DEC-27).

The authoring step is therefore the cheapest place for these facts to be right, and the only place where "right" can mean computed rather than checked. What the agent alone can answer — what the tests establish, why a layer owes none, what a document now carries — stays the agent's, and is what makes the note evidence rather than a restatement of the diff.

level, and the identity block epic/wu derived the level is the scope the caller named; the epic half is computed from the declared WU id (E-SIMPWF.W3 ⇒ E-SIMPWF), and one block is written into both notes, so 1·notes has nothing to compare that could differ. The unit's own number stays the caller's declaration — nothing in the tree carries it
the branch label derived the named ref when the tip was named by one, omitted for a raw sha — the receipt's own rule, because a sha names no branch
every changed docs/ path, and its tier derived git diff --name-only base..head through the gate's own tier_of, plus a component design the range retired at bytes the base never held (DEC-29), which an endpoint diff cannot show
each layer's count derived the files the judgment names, read at the tip, counted by the declaration the language writes: #[test] and #[tokio::test] for Rust — which is what a proptest! property carries in this tree — and it(/test( for TypeScript. A file the counter does not know, or one the tip does not hold, is refused rather than counted as zero
covers, waived, t2_waived judged the agent: what those tests establish, why a layer owes none, why a code change distilled into no T2 doc. No command can read these out of the tree, and the review judges them
each entry's action, distills, distilled_to judged the agent: what happened to the document and what it now carries. The action is validated against the documented vocabulary (added | updated | archived | deleted) because the gate reads only archived and would otherwise pass a typo; an archived entry's lineage is the gate's own distilled_to rule
the verdict, the design verdict, the human signature not here the cr/v3 note is the review's output (DEC-43), and the mr/v1 note is a human's. This command writes the two notes the review reads

One derivation, one writer: the range answers the note's facts, the agent answers its sentences, and the gate's own checks decide whether they may be written at all.

It reads committed bytes only. The paths come from the range and the counts from the files at the tip, never from the working tree, so the notes are about the tip whoever runs it and whatever is on disk. The preflight is what proves the checkout is that tip and the tree is green (DEC-43) — this command is a writer, not a second gate, and it leaves the review's own evidence, the design verdict, the signature, and the checks that judge the merge to the steps that own them.

What follows

Follows from thisWhere it shows
The authoring step of the workflow is a command, on the same footing as the preflight and the merge gate workflow.html, and cargo xtask notes write
A tip that moves — a fix, a review round, a doc commit — gets its notes rewritten rather than repaired: the same judgment is replayed against the new range, and the counts follow the files xtask/src/notes_write.rs; the range is resolved on every run, and nothing is cached
No note schema changed: the command writes the same test/v2 and doc/v1 the standard already documents, with the derived fields filled in rather than promised testing-strategy.html §Testing DoD, unchanged
The gate and the writer share one implementation of a note's facts — the same check_manifest, the same check_docs — so an authoring refusal and a merge refusal are the same sentence xtask/src/gate.rs (check_manifest, Gate::check_docs)

Rejected

AlternativeWhy not
One judgment document per note the identity block and the range are shared, and two documents are two chances to disagree about them — which is the 1·notes refusal the epic exists to make impossible
Let the agent type the counts and have the tool validate them a number the agent writes is a number that can be wrong, and validating it afterwards is the repair the command replaces. The count is read from the bytes the note attests
Count the tests by running the suite the count is a fact about the tip's source, and a build in front of every note write is the preflight's job (DEC-43). A named-file rule is deterministic, hermetic, and says which files a claim rests on
Accept a test file whose kind has no counting rule it would be counted as zero — a number the tree never said — turning the honest refusal of a zero layer into a false one
Refuse to overwrite a note that already exists rewriting the notes is how a moving tip is served: the evidence is the note on the tip, and a stale judgment replayed against a new range is exactly what should replace it
