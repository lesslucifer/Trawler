DEC-1 FlowEvent carries the full record, not a notification-sized projection

Statusaccepted · 2026-07-05
OriginCode review E0 — finding “Store::insert clones the full RequestRec (headers, version strings) solely to populate FlowEvent::RequestCaptured, whose only consumer reads method/uri/body-state.” Waived by this record.
Wheresrc/event.rs (payload shape) · src/store.rs insert/set_response (the clone) · src/api/view.rs sse_event (the projection)

Context

FlowEvent::RequestCaptured/ResponseCaptured embed the full RequestRec/ResponseRec. Filling the event forces a clone of the record on every insert (header name/value Strings allocate; captured body Bytes are refcount bumps, never payload copies). The sole current consumer — the SSE endpoint — projects a compact lifecycle notification and ignores the rest.

Options

OptionTrade
A — bus carries the record (chosen)Every subscriber gets the whole domain object without a store read-back; cost is one record clone per lifecycle event.
B — bus carries notification-sized fieldsNo clone, but each new subscriber that needs more than the SSE view (TUI detail pane, HAR exporter, disk persister) must re-query the store per event, racing eviction.

Choice & consequences

Keep the record on the bus. The architecture’s subscriber model (see core architecture: the bus “carries the record per the design; the SSE layer projects a compact notification from it”) is the point — interfaces subscribe and get everything, the store stays a query surface. The per-event clone of header strings is the accepted price; body payloads are Bytes and never copied.

Consequences: code review runs must not flag the insert/set_response record clone or the “consumer uses only a few fields” asymmetry — refute against this record. Revisit (supersede, don’t rewrite) only if profiling shows the clone on the proxy hot path is material, or if the bus gains untrusted/remote subscribers (then P3 containment argues for projections at the bus boundary instead).
