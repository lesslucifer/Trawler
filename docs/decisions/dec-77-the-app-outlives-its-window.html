DEC-77 — the app outlives its window

The background service is the app process with no window: it keeps supervising its core after the main window closes, but only while a menu-bar icon can bring the window back.

v4 · 2026-11-05 · Trawler · T2 decision · minted by E-BGSVC.W1 from the owner's rulings on the epic plan's Q1–Q4, Q6–Q8, Q10–Q13 · rule 8 by E-BGSVC.W2, rule 9 by E-BGSVC.W4, rule 10 by E-BGSVC.W3, amended by E-BGSVC.W8 · UC-BG, UC-4 · amends DEC-69 rule 14 · active

Why this record exists

Before (DEC-69 rule 14)The limit
the main window is the app: its destruction exits, and the exit stops the corecapture needs an open window, and Trawler cannot be running before the user opens it

Decision. The main window's destruction exits the app unless the shell preference keep_capturing is on and a menu-bar icon exists. Then the process, its supervisor and its core keep running with no window, and the main window is rebuilt when the user reaches for it.

The rules

#RuleWhy
1Never windowless without a menu-bar icon. The shell records whether a tray could be created; with none, the main window's destruction exits whatever the preference saysa windowless app nobody can reach is a stuck process holding the ports
2keep_capturing is a shell preference, keep-capturing.json in the app's config dir: absent = unanswered, {"keepCapturing": bool} = on / off, anything else = off. It is read on every decision, never cached. Unanswered behaves as off until the first close asks (Q3)a shell concern (DEC-12), so the core never sees it; a corrupt file must not strand the app windowless
3Windowless, the main window is destroyed, not hidden; a second launch (single-instance) or a Dock click rebuilds it through launch's own builder — the config's window, its saved geometry, the core-address script every webview getsQ2: no webview renders a live list for hours unseen; the list reloads from the core
4While a tray exists, Tauri's own exit on the last window closing is held: only rule 1's exit or a quit ends the appa --background app whose Settings window closes must not quit
5macOS: Accessory activation policy (no Dock icon) while no Trawler window is open, Regular from the first one builtQ11: the menu-bar convention
6--background skips the launch window, only while a tray exists; else the window opens. A second launch always opens or focuses itQ6: the login item launches with no window (expected #8, #9)
7Data windows close with the main window in either caseQ13, DEC-76 rule 6
8The menu-bar icon is built at every launch, after the core and before the launch window is decided; built = the host's tray availability (rule 1). A template glyph (ring + disc running, ring alone stopped) and a first line follow the core's state — Capturing · Capture service starting · Capture service stopped · Attached to <api> — then Open Trawler, Settings…, Restart capture service (enabled only while an owned core is stopped, through the supervisor's restart) and Quit Trawler. No notificationQ4, Q10: one place that always says whether capture runs and reaches the window. Restart greys out rather than vanishing, so the menu keeps its shape
9Open at login is the OS's own entry, written by Trawler: macOS the bundled launch agent Contents/Library/LaunchAgents/dev.trawler.app.plist (BundleProgram, --background, RunAtLoad) registered with SMAppService so System Settings shows “Trawler” at once (unavailable from a binary with no bundle; W8, DEC-84), Linux $XDG_CONFIG_HOME/autostart/dev.trawler.app.desktop, Windows the HKCU\…\Run value Trawler. It reads on whenever an entry exists, with the program it starts, read back each time and never cached; writing on points it at the binary now running (the last write wins). No launchctl: it takes effect at the next login. On macOS it reads on only while the service is enabled, so awaiting approval reads offQ7(a): works for any build, and a test writes it under a temp root. Q8: a mismatch is a debugging case, shown as the path on hover, not a state of its own
10The first ✕ that would quit — the switch unanswered and a menu-bar icon present — asks once, keep capturing after the window closes?, and the answer is the switch: keep capturing stores on and closes with no proxy read; quit stores off, then runs DEC-64's check; ✕ or Esc cancels, storing nothing, so the next ✕ asks again. With the switch on and an icon ✕ closes at once; ⌘Q and the menu-bar's Quit are quit requests and never ask itQ3: the feature is found by being asked, once; only a close can leave the app running, so only a close asks. An answer that cannot be stored leaves the window open when keeping and still quits when quitting
