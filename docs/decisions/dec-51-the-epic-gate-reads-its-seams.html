DEC-51 — the epic gate reads its seams, it does not re-review them

An epic's diff is the union of seams every Working Unit review already cleared. It is the only place in the workflow where the same bytes are judged twice, and 29 recorded epic rounds returned 52 findings for it. The epic tip stops owing a review of its own; 7·walk — every seam's review re-read at its declared binding — does not move.

Decided 2026-09-16 · E-SIMPWF.W9 · active

The decision

The rule. Code owes a review where it lands. An epic tip therefore owes no review of its own diff — and never stops owing that everything in it carries one.

The distinction is narrow and worth stating plainly, because the two halves are easy to confuse: what left is the re-judging of already-cleared bytes; what stayed is the guarantee that no byte reached the epic unjudged.

Code lands in two places, not one. The first draft of this record said "the seams were reviewed", and that is only true of code that arrived through a Working Unit merge. Code also lands as a standalone commit directly on an epic branch — a category CLAUDE.md and the gate have always permitted, carrying a test/v2 note at level: commit. Nothing reviewed those. The epic-level review had been their blunt backstop, covering every byte in base..tip regardless of how it arrived, and removing it let such a commit reach main with no review anywhere in its history.

So 3·review (with 3·review-nits, 4·review-base and 5·diff-binding) runs at commit level too, bound to that commit's own code paths. The epic's re-read is then sound rather than merely cheap: every level where code can land owes a review of it, and 7·walk re-reads all of them.

Found by this Working Unit's own second review round, as a reproduced blocker — a standalone code commit merging to main through the real hook and signing, with zero cr notes in its history. It is recorded here as the reason the rule reads "where it lands" rather than "the seams", not as a footnote to a rule that was already right.

Consequences

WhereWhat changed
xtask/src/gate.rs One table says which checks each level runs. The receipt's checks: line renders from it and the guard around the review checks reads it, so a check that stopped running cannot keep being advertised. An epic tip's cr note is read when present — the walk's waivers live on it — and never demanded
Standalone code commits They now owe a cr/v5 PASS bound to their own code paths, read at Level::Commit and re-read by 7·walk. A standalone commit that changes no code owes none, exactly as a docs-only Working Unit does — the demand follows the code, never the level
xtask/src/mr.rs mr confirm epic stops holding a tip for a review note. Its readiness rule is "never refuse a tip the merge gate would green"; leaving the demand there would have made a signed epic impossible
The epic's walk waiver It still rides the epic tip's cr note and the walk still reads it. What it loses is self-expiry: the note is bound by no check any more, so a moved main that moves the code re-validates neither the note nor the waiver. A waiver on an epic tip outlives its diff until someone removes it — which is why its why is read by the owner at 8·manual-review. A waiver that should expire with its diff belongs on a note something still binds, and that is a later record, not this one
The review skill Unchanged for epic scope — a caller may still review an epic deliberately. What changed is that nothing demands it

What an epic still owes: test/v2, doc/v1, mr/v1, its design checks, and a clean walk. Removing the review from the tip removed nothing else, and an epic whose seam — or whose standalone code commit — has lost its review is refused exactly as before.
