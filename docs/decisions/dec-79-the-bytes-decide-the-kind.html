DEC-79 — the bytes decide the kind

What a body or payload is read as comes from its bytes first; the served or handed-over media type is a hint, and every surface says what decided it.

Decision. One function, readKind(bytes, label?), decides among nine kinds — json · form · xml · html · javascript · css · text · hex · image — and returns what decided it: the label or the bytes, with the label as served. A whole parse beats a label; a label beats a guess. The pane and the data window both read through it.

The rules

#RuleWhy
1A label is generic when it names no kind: text/plain, application/octet-stream, binary/octet-stream, absent, or any type the table below does not list. A generic label never decides these labels say "some bytes"; they are where mislabels live
2A whole JSON object or array is json under every text label — javascript, css and form included (owner, Q5 reading, 2026-11-05)JSON is also valid JavaScript, so "the bytes fail the label" alone would keep the commonest mislabel; no CSS, form or meaningful script is a whole JSON object
3An html signature is a leading <!doctype html, <html, <head or <body, any case, after a BOM, whitespace, comments and an XML prologHTML parses from anything, so only its opening says it is a page
4JavaScript, CSS and form are never read from bytes; only a label or the user's pick names them (Q6) no cheap whole-parse tells them from text
5An image/* label is never overruled; bytes that are not text are hex under any other label an image surface already says when it cannot draw; text tools over binary bytes would lie
6A JSON label over broken JSON stays jsonthe surface's parse notice says why — more use than plain text
7Every consumer states what decided the kind; when the bytes overrule a non-generic label the pane says served as …the evidence rule (UC-5): the pane still shows the captured bytes, so a reader must see that the renderer choice moved
8The data window's kind picker still overridesthe user knows the bytes better than any rule
9A form reads the bytes handed in as one shape, each a whole parse: URL (one line, no whitespace, scheme:// or a leading /) — scheme, user, host, port, path and fragment as read-only labelled rows, then its query's pairs; name: value lines (every line a field name and a colon, a leading : for a pseudo-header, an indented line folding into the one above) — one row per line, values verbatim; URL-encoded pairs (any other single line). Text with a raw ", <, > or a line break that is none of these is not a form: the window says so and shows the text. + is a space in a query as in a body; a path, user and fragment are percent-decoded only; a bad escape is kept as sent. Edits touch only the query or the linesthe openers hand headers and URIs, and splitting either on & and = made a URL's first key the whole URL; WHATWG's URLSearchParams reads a query with the form parser, and its percent-encode sets never leave " < > raw
