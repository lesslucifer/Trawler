DEC-86 — a tag ships every platform, as a draft the owner publishes

How a pushed v* tag becomes installers and an update channel, and what can stop it.

The rules

#RuleWhy
1release.yml runs on a v* tag push and nothing else. Its first job fails unless the tag is v plus [workspace.package] version; it rewrites nothing (Q18)the released binary is built from exactly the tagged, gate-proven tree. A dispatch has no tag to check
2Five targets build with cargo xtask package: macOS universal, Windows x64 and arm64, Linux x64 and arm64 (Q16). Not tauri-action. The matrix is fail-fast: false; the release job still needs all fiveDEC-81 rule 3: the one command that builds an installer also verifies it. A second build path would skip that
3Each build runs cargo xtask smoke before its upload: the package's own installer is installed in a temp dir, its core runs headless, a request through the proxy is captured, the CA is served, and quitting frees both ports. The macOS packaging test runs the same commanda red smoke uploads nothing. One code path runs in the gate and in the release
4The signing key and its password reach only the --sign-only step, by secret name (DEC-82 rule 6). --build-only (pnpm install, vite, every build.rs) and --bundle-only run keyless; xtask writes the macOS .app.tar.gz itself. --sign-only runs only the tauri CLI the build installed from the lockfile, as ui/node_modules/.bin/tauri (tauri.cmd on Windows) and never through pnpm, whose verify-deps-before-run defaults to install in pnpm 11: tauri signer sign --app-version ‹version› per file the release manifest maps (the bundler's own sign_file, so the version stays in the signed comment, DEC-82 requireSignedVersion). The first build step fails when the key secret is empty. The job token is read-only except in the release job, and no checkout keeps it in gitleast privilege: third-party build code, and the tools the bundler downloads (AppImage's linuxdeploy and its unhashed continuous plugin, WiX, NSIS), never see the key; no agent ever holds the key
5cargo xtask release-manifest writes latest.json with an entry per target and install kind (deb and rpm included, Q20): 18 for a final, 16 for a pre-release, which ships no rpm (rule 7); signatures and tag-scoped URLs; notes from .github/release-notes.md: a pre-release's one-line Release candidate header (a final drops it), What's new (the body of the version's ## [‹version›] - ‹date› section of CHANGELOG.md, Keep a Changelog 1.1 under an ## [Unreleased] heading; a pre-release reads its final's, 0.1.0-5 → ## [0.1.0]; the final's cut dates it), each OS's first-open steps (a pre-release drops the template's .rpm line) and Check your download; and SHA256SUMS, one sha256sum line per installer (every file but .sig), which the release job re-checks with sha256sum --strict -c before the draft and attaches. It refuses a missing .sig, target or CHANGELOG section (or one with no entry under its group headings)a partial release never reaches a draft, and an update never meets a platform with no entry. The installers are unsigned (DEC-81 rule 4), so the checksum is the user's integrity check. No rc exemption: an rc rehearses its final's notes, so a missing section fails on the rc tag, never on the final's after the hand checks
6The release is created with --draft, never --prerelease; publishing the draft is the release (Q5). What the owner ticks when publishing: a final — not pre-release, Set as the latest release; an rc while no final is published (up to 0.1.0) — not pre-release, latest (the rc→rc update test needs it on the channel); an rc once a final is published — Set as a pre-release, so it never becomes latest; testers install it by handinstalled apps read releases/latest/download/latest.json, and GitHub's latest skips drafts and pre-releases: a ticked rc reaches no installed app, an unticked one reaches all. After a final, an rc on the channel would be offered to every user and leave rpm installs without an entry (Known limits)
7A version is ≤255.≤255.≤65535 with at most a numeric pre-release ≤65535: rcs are 0.1.0-1, 0.1.0-2, never 0.1.0-rc.1. cargo xtask package's version check calls anything else drift. A pre-release bundles Linux as deb and AppImage only (package::rpm_takes)WiX (tauri-bundler convert_version) maps the pre-release into the MSI's fourth field and refuses a non-numeric one; NSIS only warns. No wix.version override to keep in sync. tauri-bundler's rpm.rs passes the version verbatim and rpm refuses -, with no rpm-only override (v0.1.0-2 went red there, E-RELFIX.W1); deb takes it as a Debian revision
8Every action is pinned to a commit SHA (version in the trailing comment); no cache is restored; each runner's rustc -vV host must be its row's (Windows arm64 really builds arm64), captured by sed and compared with [ ]: the build job's bash runs -o pipefail, so no run: pipes into an early-exiting reader (grep -q, head) whose SIGPIPE (exit 141) turns a true check red; one release per ref runs at a time, never cancelleda moved tag or a poisoned cache cannot reach a signed release; an emulated x64 toolchain cannot ship as arm64
9The release job downloads each artifact into its own folder and flattens with mv -n; a leftover folder (two artifacts sharing a name) is red. A re-run deletes a pre-existing draft of its tag before creating; a published release makes the create failno silent overwrite; a re-run never needs hand cleanup and never touches a published release

Known limits

LimitWhy accepted
The version job proves tag = workspace version, not that the tagged commit is on main or green in CIonly the owner tags; the merge gate already proves every main tree
The smoke passes the NSIS /D= destination through Rust's argument quoting, and the silent installer has no own timeoutthe runner temp path has no spaces, so no quote is added; a hung installer is ended by the job's 90-minute timeout. Windows-only, cannot be proven off a Windows runner
A pre-release ships no rpm. An rpm-installed final that meets a pre-release's latest.json (published as latest, newer than it) finds no linux-‹arch›-rpm entry, so the updater falls back to linux-‹arch›, the AppImage, which rpm -U refuses: the install fails and the app stays as it wasrpm cannot carry a hyphenated version at all; an rc rpm could never update to its final anyway (rpm orders 0.1.0-1 above 0.1.0). Rule 6 keeps every rc after the first final off the channel, so an rpm-installed final never meets an rc's manifest; before 0.1.0 no rpm install exists
Windows' pnpm.cmd through cmd.exe (argument quoting of the bundle and sign steps) has never run on CI: ci.yml never runs cargo xtask package on Windows or arm64the first rc tag is its first run (E-PKG2.W6); a red step leaves no draft
The sign step runs files earlier keyless steps could write: esbuild's postinstall, every build.rs and vite run before it and could tamper with ui/node_modules/@tauri-apps/cli or .bin/tauri; cargo xtask itself may recompile in that stepall of it is lockfile- or repo-pinned code the same job already trusts to build the shipped binary; isolating the signer would need a second, clean job that re-downloads the artifacts. pnpm stays version: 11, as in ci.yml: it no longer runs beside the key
Nothing re-verifies the macOS code signature after the updater extracts .app.tar.gz; the archive drops extended attributes (--no-mac-metadata)the signature lives in _CodeSignature and the Mach-O, not in xattrs, and the app has no externalBin or signed non-Mach-O file. package's unit test signs an app, archives it, extracts it and passes codesign --verify --deep --strict
The smoke of the universal macOS .app runs only its arm64 half on the arm64 runnerno x86_64 macOS runner in the matrix; the x86_64 slice is compiled and lipo-joined by tauri but not launched
First runs on GitHub: v0.1.0-1 went red at the host check (rustc -vV | grep -qx exit 141, SIGPIPE under pipefail; E-RCFIX). v0.1.0-2 went red at linux-arm64's --bundle-only (rpm refuses 0.1.0-2; E-RELFIX.W1); fail-fast cancelled the others. v0.1.0-3, cut on epic/release-fixes's tip (aea42eb3), ran green end to end (run 42162191987): five builds, each smoke, sign, upload and a draft with a 16-entry latest.json. A green run proves the pipeline, not an install or an update on a real machinea tag is never moved or deleted; the next numeric pre-release is the retry. The install and rc-to-rc update checks are the roadmap's hand checks

Held by

xtask/tests/suite/release_workflow.rs pins rules 1 to 4, 6, 8 and 9; package's unit tests pin rule 7, the keyless build and bundle, the .app.tar.gz and the signed set (and the toolchain of DEC-85, which now also covers release.yml's jobs: a bump changes rust-toolchain.toml and every toolchain: line in ci.yml and release.yml). The release_manifest and smoke unit tests pin rules 3 and 5. Rule 5's checksum re-check is pinned by release_workflow; rule 6's publish ticks are an owner act no test sees, listed in the release process (docs/release-process.html); CHANGELOG.md holding the workspace version's section is a release_manifest unit test, so a bump without one is red before the tag. The run itself needs GitHub, the secrets and a public repository, and is proven by the first rc tag (E-PKG2.W6).
