DEC-93 — the owner answers on a Vikunja task, by removing its label

The router↔owner surface is one local Vikunja project: every epic and WU is a task, an ask is a comment plus the owner assigned plus the needs-owner label, and only the label's removal answers it.

The rules

#RuleWhy
1One Vikunja project; an epic is a task, a WU its subtask; blocking relations carry order only, the hierarchy carries nothing else. No buckets: position, view and dates mean nothing (the Kanban view is deleted)owner ruling (mapping); kanban columns conflated hierarchy, order and state
2An ask = comment → assign vuluu → add needs-owner, label last; the owner's queue is exactly open ∧ vuluu ∧ needs-owner (saved filter Needs me)owner ruling (signal): a plain comment or a column move is not a signal — the Done/Approved near-miss
3Only removing needs-owner answers; marking a task done is archival and discards a pending askone explicit, unambiguous marker
4Task before branch; the task's Branch: line is the only task ↔ branch link; vikunja check flags an untasked work worktree and an open task whose worktree is gone — detection, never preventionE-KANBAN retro: E-APIDOC started off-board
5The server and the listener are standing processes: started at session start, checked every heartbeat tick, relaunched the tick they are found dead; nothing registers persistence on the owner's machineretro: "watch X" is a standing duty; a dead listener is silent
6The listener verifies the HMAC, treats each delivery as a trigger and diffs the API's task against its state; it reconciles at start and every 60 sW1/W3 probes: deliveries arrive out of order, read at send time, never retried
7The router token is scoped (no user read, no label create, no bulk endpoints) and never printed; every task-field write is a whole-task read-modify-writeW1: a partial POST /tasks/<id> cleared the assignee
