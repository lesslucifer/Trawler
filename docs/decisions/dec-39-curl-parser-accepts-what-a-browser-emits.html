DEC-39 — The curl parser accepts what a browser emits, expands only the flags that are headers, and refuses the rest by name

A pasted curl command is the inverse of copy-as-curl, not a reimplementation of curl. The parser's boundary is the set a developer actually pastes; everything outside it is a refusal that names the token, never a guess.

DEC-39 · 2026-09-05 · Trawler · E-EXPORT.W7 · minted as DEC-32 on the E-EXPORT branch, renumbered at the E-REDESIGN merge · status: active

Context

The app already serializes a captured request as a curl command (UC-5), and E-EXPORT was asked at plan review for the inverse: paste a command, get a flow. curl has several hundred flags and a full shell grammar sits in front of any pasted line, so the question was never whether to parse it but where to stop — and what to do at the edge.

The decision

Accept what a developer actually pastes — a browser's "Copy as cURL" and Trawler's own toCurl — and refuse everything else naming the flag. The accepted set is closed and enumerated in code: the method, the URL, headers, the -d family, cookies, basic auth and --compressed, plus the shell quoting those tools emit. A second, equally closed list of transfer-only flags is consumed in silence. A token in neither list is a 400 whose body names it.

AlternativeWhy not
Reimplement curl's command line Hundreds of flags, most of which change nothing about the request on the wire, and a permanent compatibility obligation to a tool that adds flags every release. The parser's job is to read what people paste, and what people paste is what four tools emit
Accept everything, ignore what is not understood The one thing a paste target must never do. -F ignored turns a multipart upload into a bare POST; -G ignored moves a body that curl would have put in the query string. Each produces a flow subtly unlike the request the user pasted, and the user has no way to see the difference. A refusal is one edit away; a silent divergence is a wrong bug report
Shell out to a real curl It would run the request — which is E-REPLAY's capability, not an import — need a network, and make the parser's behaviour depend on whichever curl the machine has. Tests could not be hermetic
A shell-words dependency for the tokenizer The subset is small, each refusal needs its own wording, and bash's $'…' — which Chrome emits for any body carrying a control character or a ! — is outside what the common crates read. Written in the crate, no new dependency

Which headers exist that the user did not type

curl adds headers of its own when it runs — Host, User-Agent: curl/8.x, Accept: */*, Content-Length, and Content-Type: application/x-www-form-urlencoded for any -d. Some flags, meanwhile, are headers spelled differently. The rule separates the two:

KindRuleWhy
A flag that is a header — -u, -b, --compressed expanded into Authorization: Basic …, Cookie, Accept-Encoding Dropping it changes what the request is: a request without its credentials is a different request. The header is the flag's entire meaning
curl's runtime defaults never invented The flow records the command, not one tool's runtime. A request copied out of Chrome was sent by Chrome, and stamping it User-Agent: curl/8.x would be a lie about the capture. It is also what makes toCurl → parse an exact inverse: a flow that grew headers on every round trip would not be the same flow
Headers in disguise a browser never emits — -A, -e, -r, -I refused, like any flag outside the set Each is one -H away, and the refusal says which flag. Widening the set is a deliberate reopening of this record, not an accretion

The wire

ChoiceWhy
The command travels as the raw request body, UTF-8 text, not JSON-wrapped A wrapper adds a quoting layer to an input whose whole difficulty is quoting. The paste target sends what was pasted; the same bytes work from a shell with --data-binary @-
Selected by ?format=curl on the existing POST /flows/import; an unknown value is refused naming format One door, two formats, one { "imported": n } envelope. A silently defaulted format would parse a curl command as JSON and refuse it for the wrong reason — the same refuse-by-name rule ?source= already follows
The refusal is 400 with the reason as the body — HAR import's shape The paste target renders the reason verbatim under the textarea (the capture-controls design), so every reason is written for a person: one lowercase sentence, the offending token quoted. The design run pinned this contract before the parser existed, and the parser was built to it
The flow is stamped with the moment it was read, carries HTTP/1.1, and has no response Nothing happened on a wire; the only truthful instant is when the flow came to exist, and the request-only shape is one the store, the API and the UI already handle between a request and its reply

What the inverse guarantees, and where it stops

Any flow rendered by toCurl and parsed back compares equal on method, URI, headers and body — proven as a property over generated flows, with the serializer mirrored in Rust and that mirror anchored to the literal outputs the TypeScript test file pins. The boundary is curl's own, not the parser's:

Not round-trippedBecause
a header whose value is blank toCurl writes it as -H 'Name: ', which curl reads as "send no such header" and drops. The parser agrees with curl; the loss is in the serialization, and Name; is curl's spelling for an empty value that is actually sent
a GET carrying a body toCurl omits -X for GET and writes the body as --data-raw; curl — and the parser — make that a POST
