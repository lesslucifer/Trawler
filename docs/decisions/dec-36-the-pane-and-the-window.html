DEC-36 — the pane width and the window are one decision

The flow detail pane is 520 px and the app's default window is 1440. Neither number is decidable alone: a wider pane inside the window the app opened at pays for every character it gains out of the path column beside it.

DEC-36 · 2026-09-09 · Trawler · E-RFINISH.W4 (designed) · W6 (built) · the observable half of DEC-32 · status: active

Context

The pane shipped at 380px — a token nobody chose, inherited from the first shell. DEC-32 makes the headers clamp at three lines with more / less beneath, so how much of a long value a reader sees before acting is the pane's width. A 900-character cookie is thirty lines at 380 and twenty at 520. E-REDESIGN recorded the cost and deferred the width to a design run, because a width chosen at a merge seam is a width nobody designed.

The screen is one identity, split. path = window − pane − 612, where 612 px is the flow row's fixed tracks. Every pixel the pane takes comes out of the path cell in the list — the one column whose content is unbounded. So a pane width proposed without a window is half an answer, and the half it omits is the one that gets worse.

The decision

Pane 520px, default window 1440 — one decision, two configuration values. The pane is the pane token in ui/tailwind.config.js and the window is ui/src-tauri/tauri.conf.json; neither is ever an inline magnitude — a width is legal only as a member of a declared scale (DEC-17).

Both halves of the identity improve because the window moved further than the pane did. Widening the pane alone would have bought the header value 60 characters at the cost of 140 px of every path on screen — which is why the two numbers land together or not at all.

Rejected

AlternativeWhy not
Keep 380 It is the shape DEC-32's clamp was written to survive, not one anybody chose for it. Thirty lines of cookie behind a more is the cost the epic opened to price.
440 27 characters of header value for 60 px off every path. The trade is real at every width; this one is simply a bad rate.
560 and above The path cell stops holding a recognisable endpoint before the header value stops needing more. Past 520 the pane is winning an argument the list is paying for.
A bounded share — min(40%, 520px) Measured, not argued: 8 px from the fixed choice at 1280 and identical above 1300. It buys nothing at the widths the app is used at, and costs a rule every reader of the layout has to hold.
A draggable split Three things the shell does not have — a stored preference, a drag affordance, and a minimum on both sides — for a gain the run could not show is needed. The default in the epic plan's open question was a fixed width, and the evidence did not overturn it.
Raising the app's minimum window It would narrow a capability the list alone uses today: the flow list is usable in a narrow window when no flow is selected, and the minimum exists for that case, not for this one.

What this forces

WhoWhat changes
Any WU opening the shell's grid The two values move together or the identity above is violated. A pane widened without its window is a change to the list, made silently, in a file about the pane.
DEC-32 Unchanged as a ruling, and now measurable: the clamp's cost has a number, and the number is a decision rather than an accident.
Whoever next arranges the flow row The shell has no valid arrangement below 1132 px with the pane open, and tauri.conf.json declares a minimum of 800. This decision moved that threshold from 992 — a known defect, made wider, deliberately. Below it the row region scrolls horizontally while the column-label row above it does not, so the labels and the cells they name come apart. Both fixes (the row's column widths, a second arrangement of the whole screen) decide the row grammar E-RFINISH's non-goals reserved, so the run escalated the arithmetic instead of hiding it and the roadmap carries the row.
