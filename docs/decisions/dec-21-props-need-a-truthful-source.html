DEC-21 — a prop whose value can only be a guess does not exist, and the default is opt-out

Four components refused a prop and one reversed its own default. The test in both directions is the same: which way does the component fail when the caller does not think about it?

DEC-21 · 2026-08-12 · Trawler · E-DFLOW.W7 · distilled from StepList D2 · DurationText D2 · Select D2 · Notice D2 · SegmentedControl D2 · status: active

Context

Every component fork reached a point where an extra prop would make the design more flexible and cost nothing when unused. Five of them said no, for two different reasons that are easy to conflate — the prop has no truthful source, and the prop has no tenant — plus one reversal that shows what the default should be when a prop is warranted.

Choice

TestThe ruleWhere it was applied
No truthful source If nothing in the system can observe the value, the first caller will fill it with a guess. A component whose prop can only be filled with a guess should not have the prop StepList's per-step done: nothing observes which step you did — only whether the CA is now trusted. A click would record "I read this", not "this is done". One honest probed verdict beats four unverifiable ticks
Not this component's knowledge A threshold that varies by application belongs to the screen, not the primitive DurationText's slow threshold — see DEC-19 for the colour half
No tenant A mode nobody has asked for is a different component wearing the same clothes. Add it as a sibling when a real tenant appears, not before SegmentedControl's multi-select: it would change the value shape to a set and the ARIA pattern to independent toggles
One component with a tone beats two components When two candidate components share an anatomy and differ by one colour, and the boundary between them moves, they are one component Notice for absence and failure both: "not captured" is an absence, "could not load" is a failure, and a fifth state sits between. Two components force every tenant to pick — and a tenant picking wrong is a documented finding
Opt out, never opt in When a prop is warranted, the default is the one whose failure is cheap Select's searchable, defaulting true — see below
The asymmetry that sets a default. An unnecessary search row costs one line of chrome. A missing one, on a list that grew, costs the user the ability to find their option at all. So searchable defaults to true and a caller with two obvious options opts out — nobody has to opt in, and the failure mode is a redundant filter box rather than a missing one.

Options rejected

OptionWhy not
A component-owned threshold — Select shows search above 8 options, no prop The first draft settled this, to keep "is this list long?" out of every call site. Reversed at review. The threshold is a guess about scannability that varies by content — six near-identical mono strings are harder to scan than twelve distinct words — so a fixed number is wrong on both sides of itself, and a caller who disagrees has no recourse. What survived: typing filters even when searchable is false, and the row appears the moment it is used
An optional done flag on StepList — familiar, and free when unused "Free when unused" is the trap. The flag has no truthful source, so the first caller drives it from a click
EmptyState + ErrorState as two components Reads tidier in a roster and is how most systems do it. Rejected: it duplicates the entire anatomy for one changed colour, and the first tenant needing "absence, but you can retry" has to choose a parent arbitrarily
A cycling button instead of a segment group One touch target, but "show decoded" implies decoded is not current while "decoded" implies it is — either reading is ambiguous. All options visible makes the current state unambiguous at a glance

Consequences

  • A design run proposing a prop answers where its value comes from. "The caller decides" is an answer only when the caller can actually know.
  • A proposed variant with no tenant is deferred with its escape path written down, the way the shared-shell lift was (DEC-18) — a deferral that names its trigger resolves itself later instead of being re-litigated.
  • Where a default is set, the record names which failure it prefers. That is the reviewable part; the boolean itself is not.
