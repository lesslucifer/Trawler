DEC-30 — HAR 1.2 is the one interchange format, and a fact Trawler does not hold is never invented to fill it

One format, chosen because the tools a user already has can open it. The hard part was not the choice — it was what to write where HAR has a required field and Trawler has no truthful value for it.

DEC-30 · 2026-09-04 · Trawler · E-EXPORT.W2, amended by E-EXPORT.W3 · status: active

Context

Until E-EXPORT every flow died with the process: the store had no way out and no way in. Handing a capture to someone else, and opening the one they handed you, both need a serialized form — and that form is a compatibility decision, not an implementation detail, because whatever Trawler writes must be readable by something the recipient already runs.

The decision

HAR 1.2, and only HAR 1.2. Trawler exports (GET /flows/export) and imports one capture format — the W3C/HTTP-Archive JSON format that Chrome, Firefox, Safari, Charles, Proxyman, Insomnia and Postman all read or write. No .saz, no Charles .chls, no Postman collection: one format done properly beats four done partially, and every additional format is a parser with its own malformed-input surface.

AlternativeWhy not
Trawler's own JSON (the existing FlowView shape) It already exists and would need no projection — but nothing else on the machine can open it. An export whose only reader is Trawler does not solve "hand a capture to someone else"
HAR plus a native format for full fidelity Two formats means two parsers, two round-trip contracts, and a user decision at every export. The fidelity gap HAR leaves (below) is narrow and is honestly representable inside HAR itself
Several capture formats Each is an untrusted-input parser and a permanent compatibility obligation. HAR is the one every tool in this space already speaks

The real problem: HAR requires fields Trawler cannot truthfully fill

HAR was designed by browsers, which know things a proxy does not — the raw header-block size, the phase breakdown of a request's timing, the reason phrase the server actually sent. Several of those fields are required. So every required field forced a choice between two ways to be wrong and one way to be right:

Hình 1 — HAR anticipated the gap: -1 means "not available", not "zero". Using it is how a valid file stays honest.

The body states — the case where the sentinel was not enough

Trawler's capture path distinguishes four body outcomes — captured, genuinely empty, streamed (never buffered, by design), and not captured (too large, or a read error). HAR's body object has vocabulary for exactly one of the three non-captured cases. Reporting the other two as an empty body would make a 4 MB event stream indistinguishable from a 204 — erasing the exact distinction Trawler's domain model exists to preserve.

StateHow the file says it
captured the bytes, as text when the content type says text and the bytes really are UTF-8, otherwise base64 under HAR's own encoding convention — a text content type is a claim about the bytes, not a guarantee, and base64 is what keeps them recoverable when the claim is false
empty a measured size of 0 and no text — the one state where "nothing" is the truth
streamed · too large · read error no text at all, plus a comment naming which one. The absent text carries the fact structurally (a reader that ignores comments still cannot mistake it for an empty body); the comment carries the reason for one that shows it. comment is a standard HAR field, so this costs no validity
too large, specifically reports the size it had alongside the missing bytes — that size is known, and is exactly why the body was dropped. Only the two states where the size was never obtained report -1

The reason tokens reuse the vocabulary the API's own body view already publishes (streaming · too_large · read_error) rather than inventing a second spelling of the same four states — and the importer reads them back to restore the variant, which is what makes the round-trip below lossless for body state even where it cannot be lossless for body bytes.

What a round-trip preserves, and what it does not

The guarantee is stated in both directions, because "lossless" without a boundary is a claim no format can keep:

Preserved

  • method, URL, both HTTP versions, status
  • every header, in order, duplicates included
  • the time the exchange was captured, and its duration
  • captured body bytes, exactly — base64 wherever text would be lossy
  • which of the four states each body was in

Not preserved — and why that is a fact, not a defect

  • the raw header-block size — never retained; a proxy sees parsed headers
  • the wire reason phrase — not retained; the file carries the canonical phrase for the status code
  • the timing phase breakdown — Trawler measures one span, so it is reported as one span that sums to the total HAR requires. This is also the one place the sentinel rule above does not apply: HAR permits -1 for the total but requires the three phases Trawler reports to be non-negative, so an exchange whose duration was never measured carries an unknown total beside zeroed phases — the sum is unhonourable there, and zeroed phases claim less than a negative phase no reader would accept
  • a cookie's optional attributes — the header they came from is preserved verbatim, so nothing is lost from the file; only the parsed-out convenience fields are absent
  • the flow's id — an id is a handle in this store, so an imported flow gets a fresh one while keeping its original timestamp
  • a foreign writer's body it did not keep — a body with no text but a size claiming one existed comes back as an explicit not captured, because the alternative (reading it as empty) would assert a 4 MB response was a 204. Trawler's own four states round-trip exactly; a foreign tool's "there was a body, I don't have it" collapses to the one state that says exactly that
  • a request body Trawler never captured — HAR's postData has no shape for it, so the export omits postData and carries the fact in bodySize alone; on the way back in, every uncaptured state on the request leg therefore collapses to the coarsest honest one. The response leg, where every capture-path skip actually occurs, keeps the full vocabulary

On the way back in, a body's bytes outrank a size that disagrees with them. Real tools emit files whose declared size and carried text do not match, so such a file is accepted rather than refused — but the ring is weighted by retained bytes, and letting a client's arithmetic set that weight would put eviction under the file's control. What Trawler holds is what Trawler counts.

The export does not decode compressed bodies. The bytes written are the bytes captured, with the Content-Encoding that describes them still attached — so the file stays a faithful record of the wire and never contradicts its own headers. The decoding surface stays where it was, on the body endpoints' ?decode=1.
