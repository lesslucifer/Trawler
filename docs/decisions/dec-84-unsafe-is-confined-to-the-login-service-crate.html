DEC-84 — unsafe is confined to the login-service crate

The one exception to the workspace's unsafe_code = "forbid": a tiny macOS crate that wraps SMAppService.

v2 · 2026-11-06 (rule 4 — E-PKG2.W5) · v1 · 2026-11-05 · Trawler · T2 decision · minted by E-BGSVC.W8 from the owner's ruling (option 1) · amends DEC-77's login item on macOS · active

Why this record exists

FactConsequence
every SMAppService method in objc2-service-management 0.3.2 is unsafe fnregistering a login item that Background Task Management shows at once needs unsafe code
[workspace.lints.rust] unsafe_code = "forbid" reaches every member, and a forbid cannot be relaxed below itthe calls cannot live in trawler-ui or trawler

Decision. Unsafe is confined to the login-service crate and its one #[allow(unsafe_code)] module. The crate is macOS only, sets unsafe_code = "deny", and exposes a safe API; every other member keeps the workspace's forbid.

The rules

#RuleWhy
1login-service is the only workspace member whose lints differ on unsafe_code, and it holds exactly one #[allow(unsafe_code)], on the module that makes the four SMAppService callsthe exception stays one place to read
2The crate's public API is safe and carries no objc2 type; trawler-ui depends on it only on macOS and stays forbidnothing outside the crate can reach the unsafe surface
3A test over the crate's sources fails when a second allow(unsafe_code) appearsthe confinement is checked, not remembered
4AgentService::new returns none below macOS 13 (NSProcessInfo isOperatingSystemAtLeastVersion), so no SMAppService call is reachable there and the login item reads unavailable. The app's minimum stays macOS 11. CI runs the crate's tests on every OSnaming the class on macOS 11/12 panics in objc2, and the bundle's minimumSystemVersion is 11.0

AlternativeWhy not
