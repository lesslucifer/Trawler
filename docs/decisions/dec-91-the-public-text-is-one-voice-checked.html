The rules

#RuleWhy
1Voice: plain, second person, present tense; OS and UI labels in bold exactly as shown; limits stated where they bite; no hype, no futures, no internal idsthe reader is a user, not a maintainer
2No other tool is named in any published file (README, community files, issue forms, PR template, CHANGELOG, release notes)owner ruling (W11 Q5); held by a deny-list test
3The README's install table names exactly the installer kinds package.rs bundles per host for a final; an .rpm row says final releases onlyDEC-86 rule 7; a table that drifts from the build sends users to files that don't exist
4Every relative link and image in a published file resolves, a markdown anchor included; a file linked before it exists sits in NOT_YET_WRITTEN and must leave it the moment it landsno broken link on the repo's front page
5Outside pull requests are not taken at 0.1.0: issues only, said politely in CONTRIBUTING, the PR template and the FAQowner ruling (W11 Q10)
6Product screenshots come from cargo xtask ui screenshots (the walkthrough's scenario build, a HAR fixture of reserved hosts, a temp HOME) into .github/screenshots/; only the OS prompts (S8, S9) are hand-captured once, on the last rcreproducible shots that follow the UI; CI cannot show OS dialogs (W11 Q8)
7Privacy and security claims are only those the code backs: in memory only, loopback unless a device is allowed, an unencrypted CA key in the app data folder, two outbound calls (the update check with its switch, the setup test)a public promise the code breaks is the worst bug

Held by

xtask/src/public_text.rs' unit tests (links and anchors resolve, the install table matches Os::bundles, no denied name, issue forms and their config parse) and xtask/src/screenshots.rs' (a run is green only when every listed shot is a PNG; the spec takes exactly the listed shots).
