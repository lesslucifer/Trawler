DEC-36 — An imported flow is a first-class flow carrying a provenance mark, not a second collection beside the ring

The ring now holds flows the proxy never saw. One closed-enum field on the domain model says so — and the first mutating method it enables is what widened the CORS grant.

DEC-36 · 2026-09-04 · Trawler · E-EXPORT.W3, amended by W4 and W7 · minted as DEC-31 on the E-EXPORT branch, renumbered at the E-REDESIGN merge · status: active

Context

Until DEC-35's import half landed, every flow in the store came from the proxy — so nothing recorded that fact, because nothing else could produce a flow. POST /flows/import breaks that assumption: a listing can now mix a live capture with a colleague's file, and a user who cannot tell them apart cannot trust either. Two questions had to be answered together, because the answer to the first decides whether the second even arises: where does an imported flow live, and how does a client select one kind without the other.

The decision

One ring, one field. An imported flow is inserted into the same byte-weighted ring as a captured one and carries source: Captured | Imported — a closed enum on Flow, surfaced as a source string on both API projections and selectable as ?source= on every endpoint that selects flows.

Hình 1 — provenance is a property of a flow, not a place it is stored. Every read path and the ring's own rules apply to both kinds unchanged.
AlternativeWhy not
A second store for imported flows Every read path in the API would double — the listing, paging, the detail endpoint, both body endpoints, the export, the event bus — and each would need a rule for "which store, or both". That is a large, permanent cost for a distinction one field expresses, and it would make "an imported flow is otherwise an ordinary flow" a claim the code contradicts rather than one it enforces
No mark at all — an imported flow is simply a flow Cheapest, and wrong: a user reproducing a bug against a live capture cannot see which rows are theirs, and cannot clear the file's rows without clearing their own. The provenance is information the user needs, so the model has to hold it
A free-text source (a filename, a tool name) It looks more informative and is less useful: a filter over free text is a substring match with no closed set to validate against, so a typo silently returns nothing. The two values are exhaustive today, and a third — a replayed flow, say — is a deliberate extension of a closed enum rather than an accident of what someone typed

What one ring costs, stated plainly

  • An import can evict a live capture. Imported flows weigh their retained bodies like anything else, so importing a large file pushes the oldest rows out — possibly rows the user was about to look at. That is the honest consequence of the ring being the one store, and the alternative (an import that cannot be evicted) would mean a file could permanently consume the memory the live capture needs.
  • An imported flow gets a fresh id and keeps its original instant. An id is this store's handle and must be unique here; the instant is the captured truth, so an imported capture sorts by when it happened. Importing the same file twice therefore yields two independent sets of flows carrying identical timestamps — which is correct: they are two copies in the ring, not one row seen twice.
  • The mark is on the summary row, not just the detail view. A client that can filter on a field it cannot see in the rows it gets back has to re-fetch to confirm what it asked for.
  • An unrecognised ?source= is refused, not ignored. A silently empty listing reads to a caller exactly like "nothing matched" — the one failure mode a filter must never have.

The CORS widening, and why it extends DEC-12 rather than reversing it

DEC-12 granted the API an open CORS * because the native app's webview is a cross-origin client, and justified it on two grounds: the surface is loopback-bound, and everything it exposes is equally reachable with curl. The grant advertised GET, OPTIONS because the API was read-only. Import was the first method that changes capture state and clearing (UC-7) the second, so the grant now advertises GET, POST, DELETE, OPTIONS.

Both of DEC-12's grounds still hold, which is the whole argument. The bind address is unchanged, and POST /flows/import is as reachable with curl as GET /flows always was — so the widening grants a webview exactly the access an already-local caller has, and nothing more. What would reverse DEC-12 is binding beyond loopback or exposing something curl cannot reach; neither is on the table. Without the widening the app's import control would be dead on arrival: a webview's fetch cannot POST to an origin whose grant omits the method.

The epic's own plan scheduled this widening with the DELETE work, assuming that would be the first mutating method. Import landed first, so the widening landed with it and E-EXPORT.W4 added DELETE to the same list on the same argument — a change of placement, not of reasoning. The list is now closed for this epic: no further method changes capture state.

All-or-nothing, and why the store is never the thing that cleans up

Import is the first endpoint taking untrusted structured input from a client, so the refusal contract is part of this decision rather than an implementation detail. The whole document parses into flows before the store is touched at all; the handler holds either a complete Vec<Flow> or an error.

PropertyWhy it follows from the shape, not from care
A refused import changes nothing There is no partial state to roll back, because nothing was inserted. "Never a partially-populated store" is structural — a cleanup path could be forgotten, a type signature cannot
One bad entry refuses the document, naming its index A caller who cannot tell which of 900 entries landed cannot recover. Refusing with the index is actionable; a partial success is not
The parser never panics Asserted as a property over arbitrary bytes and over HAR-shaped documents whose every member may be the wrong type or out of range — an all-inputs claim no list of named malformations can cover
The body's bytes outrank a size that disagrees with them Accepted rather than refused, because real tools emit it — but the ring must weigh what it actually holds, or eviction goes wrong. Trusting the declared size would put a client's arithmetic in charge of Trawler's memory accounting
