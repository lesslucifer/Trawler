DEC-34 — a fixed-height virtualized row may truncate, on three conditions

wrap-not-truncate reads as absolute and one screen cannot obey it. The rule keeps its predicate; the escape is declared, bounded, and costs a receipt line.

DEC-34 · 2026-09-06 · Trawler · E-REDESIGN.W11 · distilled from the flow-list design run's collision table (archived) · status: active · amended by DEC-53 (2026-09-17): the escape is declared on the run's review item, the receipt having gone

Context

The rulebook's wrap-not-truncate says long values wrap — never truncate, never widen the column, checked as no truncate/ellipsis/nowrap on payload elements. The flow list cannot satisfy it. Its rows are virtualized at a fixed 30 px — a Frame constraint, not a styling preference — and a URL path is unbounded. Wrapping needs variable row height; virtualization needs a known one. The two cannot both hold.

The design run recorded violated on two slugs with the full argument rather than claiming a satisfaction it had not earned, and escalated the missing clause to the epic's distillation. W4 then built the truncating cell and stated the breach in UC-4. This record is that escalation, answered.

Decision

The predicate does not move. truncate on a payload element stays a Tier-1 red, and no design gets it for free. What this record adds is a named, bounded escape: a screen may record violated against wrap-not-truncate and ship the truncation when all three conditions below hold. The escape is a declaration on the receipt, never a silent pass — a reviewer reads it, and a design that meets none of the three is simply wrong.

#ConditionWhy it bounds the escape
1A declared Frame constraint makes wrapping impossible — not merely inconvenient. In the flow list: rows are virtualized, which fixes row height before any cell is styled. Ties the escape to a constraint the Frame already stated and a reviewer can check, rather than to the builder's convenience. "It looked untidy" is not a constraint.
2The full value stays reachable by a named route, and the route is named in the receipt. In the flow list: the path on the row's title, and both host and path in the detail panel's URI. Truncation may cost a glance, never the data. A cut value with no route to the whole is data loss, and no constraint excuses that.
3The cut is visible — an ellipsis, never a hard clip. A silently clipped value reads as a complete one. The user must be able to see that there is more before they go looking for it.

Rejected

AlternativeWhy not
Overrule the design — make the cells wrap. Variable row height ends virtualization, and the list is the screen that must stay fluid under live traffic. The rule would win the argument and lose the screen.
Widen the column instead. The rule forbids it in the same breath, and rightly: a path is unbounded, so any width is arbitrary and every other column pays for it.
Weaken the predicate — allow truncate on a payload element inside a fixed-height row. The predicate cannot see row height, so the check would have to trust a data- attribute the design writes about itself — a rule that asks the subject whether it is allowed. Worse, it would go quiet: today the violation is stated on the receipt and read by a reviewer, and that is the part worth keeping.
A new verdict, violated-by-constraint. An eighth verdict for one case, beside the seven DEC-15 fixed — and it reads as absolution. violated plus a reason is already the honest shape: the receipt says the rule is broken and says why, which is exactly what a reader needs.

Consequences

  • The rulebook's wrap-not-truncate row carries the clause and points here; the Tier-1 check text is unchanged, because the check is unchanged.
  • A design run meeting the three conditions writes violated with the constraint, the route to the full value, and the visible cut. A Tier-3 reviewer judges those three, not the truncation itself.
  • The flow list is the one sighting today. display-equals-payload carries the same violation for the same reason — one finding, two slugs — and is answered by the same three conditions.
  • A second sighting is the signal to look again: two screens needing the escape means the payload cell wants a component, which the flow-list run already named as a near-miss proposal awaiting its second call site.

What counts as the second sighting (E-RFINISH.W4, the shell and flow-list second pass). A sighting is an element that is mono, inert, unbounded and visibly cut — all four. The criterion is here rather than in the run that wrote it so the next design tests against it instead of judging by resemblance.

That run tested four candidates and the answer was no. The one the first pass predicted — the flow detail panel's identity bar — shipped and refused: it wanted CopyText, which wraps and is never cut, because a pane has height to spend. The truncating cell is a consequence of the fixed-height row, so a surface that can grow downwards is not a second sighting however much it looks like one. Proposing the entry on a sample of one screen was rejected in the same breath: one call site cannot show which of the four properties the component is actually for.

What this record does not do. It does not excuse the Tier-1 blindness the same run found — that wrap-not-truncate's predicate cannot read a mockup's <script type="text/babel"> block at all, so every design run's mounted JSX is unchecked by it. That is a harness hole, it is recorded as an epic follow-up, and it would be a hole whether or not this clause existed.
