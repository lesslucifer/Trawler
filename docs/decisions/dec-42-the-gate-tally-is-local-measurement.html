DEC-42 — the gate tally is local measurement, and a review round is a cr note in the range

E-SIMPWF decides which cuts to adopt by counting what the workflow actually costs, so the counts have to exist before W5 and W7 can be argued either way. This records what is counted, where it is kept, and why it is never evidence.

Decided 2026-09-12 · E-SIMPWF.W1 · active

The decision

Every gate run appends one record to target/.gate-tally: the level it ran at, the tip and base it judged, the check ids that refused, and how many review rounds the tip's own line paid. A gate run is an invocation that computes a report — verify-dod wu|epic (including the merge hook) or verify-dod commit; the pre-push range sweep re-checks commits that already paid their own gate. cargo xtask tally aggregates the file — refusals counted per check id per level, rounds listed per tip. The file is local measurement: under the gitignored target/, in the shape of Gate 0's cache, never a git note, never synced, and never read back by any gate check.

Why it needed deciding

The epic's own rule is DEC-11's: a cut is adopted on a measurement, not on an impression. W5 (a nit stops restarting the review) and W7 (a delta re-runs only the dimensions it can reach) both lower a bar if they are wrong, so both need a before/after number — and an epic that argues about which numbers matter after the work has landed has already lost the argument. Three questions had no answer in the tree: what a "refusal" is, what a "review round" is, and whether the answer belongs in the evidence chain at all.

What is counted, and where it lives

RecordedWhy that, and not something else
Every gate run, green, red or exempt — verify-dod wu|epic|commit, one commit inside range, and the merge hook A tally of refusals alone would never show the denominator: 3 of 6 tips refused is a different fact from 3 refusals, and a green tip still paid for its rounds.
The refused check ids, as the gate printed them (1·notes, 6·doc-note, 7·walk·2·manifest) The id is the unit a later cut targets: "manifest refusals cost the most repair time" is actionable, "something went red" is not. Waivers are not refusals and are not counted.
The rounds a tip paid — one cr note per review run, attached to the commit that run judged, so the notes on the tip's own first-parent line from the gate's base are the rounds that line paid for The rounds are the cost W5 and W7 exist to cut, and they are already on the record: the code review writes its note whether the verdict is PASS or FAIL.
Nothing else — no durations, no token counts, no estimates The two facts a later cut is argued from are the two the tooling already knows. A number nobody can recompute is an impression with a decimal point.

A review round is a cr note in the range

The code-review skill writes one note per run on the tip it judged (workflow §Evidence), PASS or FAIL. Attaching each round to the commit it judged is what makes the count recoverable later without a transcript: the notes are immutable, they survive on the branch, and a fix that produces a new commit adds a round rather than replacing one. The count is taken over the tip's first-parent line from the gate's merge-base — the commits the tip's own work added — because a branch that merged another's reviewed work in would otherwise bill this tip for rounds it never paid.

Rejected definitionWhy it does not measure the same thing
Every cr note reachable in the gate's base..tip range A back-merge brings another branch's reviewed commits into the range, so this tip is billed for rounds paid elsewhere — and summed across an epic, the same rounds are counted twice.
The number of times a note was rewritten on one commit (the notes ref's history) A fix is a new commit, so re-runs land on new tips and the per-commit rewrite count stays at 1 — it would have reported the W7 tip at 1 round where it actually paid 4.
The number of gate invocations that refused on a tip That counts repairs triggered late, not review runs. A review re-run after a red test is a round; a gate run three times by hand while debugging is not.
What the triggering session reports in its transcript Unrecoverable and unfalsifiable. The epic's expected result is that the owner can answer the question without reading a transcript.

A range the gate cannot read records no round count at all, and the summary says so rather than contributing a zero: an unreadable reading and a reading of nothing are different facts.

Why it is never evidence

It is a reading, not a receipt

A receipt says this tip was verified and is recomputed by the gate that reads it (DEC-2). A tally says this checkout saw these refusals and is true of one machine. Keeping it in refs/notes would put a per-machine reading into the permanent chain, where a fresh clone would have to treat it as history it can trust.

It expires honestly

target/ is gitignored and cargo clean takes it. The measurement starts again from zero on a clean checkout, which is the truth about it — a count that survived a clone would be a claim about a machine nobody can inspect. It is a reading rather than a history, so it is also bounded: past 2048 records the oldest half goes.

It is written on the way past

The gate appends its record after it has computed the verdict. A tree where the file cannot be written — a read-only checkout — still gates exactly as it did before, and no check reads the file back.

Consequences

W5 and W7 argue from a number that exists before they land, and a dropped WU is dropped with its count beside it (the epic's stopping rule) cargo xtask tally, per-check and per-tip rows
The measurement's shape can change without a schema bump or a note rewrite, because nothing persists in git xtask/src/tally.rs — the code is the contract
No gate check, note schema or merge rule changes: this decision adds a subcommand and a local file the W1 diff
A reader who wants the rounds of a tip that predates this decision can still count them by hand — the notes are in the range git notes --ref=cr list against git rev-list base..tip
